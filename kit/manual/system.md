# CDP — 시스템 정본

    이 문서가 정본이다. CDP 가 지금 무엇인지 여기에 있다.

`docs/design/` 의 설계서들은 **어떻게 여기까지 왔는지**의 기록이다. 판단이
바뀔 때마다 지우지 않고 정정을 붙여 왔으므로, 그 문서만 읽으면 무효가 된
대목과 살아 있는 대목이 섞여 있다. **지금의 답이 필요하면 이 문서를 본다.**

---

# 1. 무엇을 푸는가

## 1.1 문제

프로젝트가 반년쯤 돌면 이런 일이 생긴다.

```
"이 컬럼 왜 nullable 이지?"        → 아무도 모른다
"그 화면 버튼 이름 뭐로 정했지?"    → 세 사람이 세 가지로 안다
"작년에 이거 검토했었는데…"        → 어느 문서인지 못 찾는다
```

문서가 없어서가 아니다. **문서는 많은데 어느 것이 지금 맞는지 알 수 없어서**다.
회의록·검토서·설계서가 쌓이고, 그중 무엇이 최신인지는 사람의 기억에 있다.
그 사람이 나가면 같이 나간다.

## 1.2 왜 검색으로 안 되는가

*"검색하면 되지 않나."* 안 된다.

검색은 **문서를 준다.** 필요한 것은 **답**이다. `rp_plnd_mst` 를 검색하면
그 이름이 나오는 문서 열두 개가 나오고, 그중 어느 것이 지금 맞는지는
여전히 모른다. 열두 개를 다 읽어야 하고, 다 읽어도 서로 어긋나면 판단은
다시 사람 몫이다.

RAG 도 같은 문제를 다르게 겪는다. 의미가 가까운 조각을 모아 오지만
**가까운 것과 맞는 것은 다르다.** 낡은 문서일수록 문장이 잘 다듬어져 있어
더 잘 뽑힌다.

## 1.3 그래서 좌표다

**대상마다 정본이 하나 있고, 그 자리를 이름으로 부른다.**

```
table:rp_plnd_mst      계획서마스터라는 대상
screen:EXD020          출장복명작성이라는 화면
code:PS130             업무구분이라는 코드그룹
```

이 이름이 **좌표**다. 좌표를 물으면 답이 하나 나온다 — 검색 결과가 아니라
**지금 상태**가.

```
$ ctx where screen:EXD020
screen:EXD020
  문서   docs/화면설계서.md
  섹션   ## EXD020            ← 정본은 여기 하나뿐이다
  상태   반영 2026-0922-EXD020-첨부용량
  작업   6건                  ← 여기까지 오는 동안 있었던 일
```

## 1.4 두 층

```
docs/    관리 문서 — 지금 어떤 상태인가.  가변.  팀이 하나로 관리한다
work/    작업 기록 — 무슨 일이 있었나.    불변.  append-only
```

**둘을 섞으면 둘 다 안 맞는다.**

한 파일에 "지금 상태" 와 "그때 있었던 일" 을 같이 적으면, 상태를 고칠 때
과거가 지워지고 과거를 남기려면 상태가 지저분해진다. 나눠야 각각이 자기
일만 한다.

| | `docs/` | `work/` |
|---|---|---|
| 답하는 질문 | **지금 어떤가** | **왜 그런가** |
| 고치나 | 고친다 | **고치지 않는다** |
| 몇 개 | 대상당 하나 | 사건마다 하나 |

두 층을 잇는 것이 좌표다. 관리 문서의 섹션은 자기가 **어느 작업 기록까지
실었는지**를 한 줄로 적어 둔다.

```markdown
## EXD020 — 출장복명작성
<!-- applied: 2026-0922-EXD020-첨부용량 -->
```

이 한 줄이 CDP 의 유일한 규약이다. 나머지는 전부 이것에서 나온다.

# 2. 파일

## 2.1 지식 레포

```
_vocab.md          통제 어휘 — 좌표의 이름표
_managed.md        등록부 — 좌표 패턴 → 정본 문서 · 섹션
docs/              관리 문서
work/              작업 기록
INDEX.md           자동 생성 (훅이 커밋마다 갱신한다)
INDEX-by-coord.md  자동 생성
bin/ctx            도구
.githooks/         pre-commit
.claude/skills/    절차
tools/cdp.exe      앱 + ctx
```

**`_vocab.md` 와 `_managed.md` 가 있는 폴더가 지식 레포다.** 폴더 이름으로
판단하지 않는다 — 이름은 사람이 바꾸고 규약 파일은 안 바꾼다.

## 2.2 `_vocab.md` — 이름표

```markdown
## table

- `table:rp_plnd_mst` — 계획서마스터
  aliases: 계획서마스터, RP_PLND_MST, 계획서
- `table:rp_trip_photo_list` — 출장사진목록
```

| | |
|---|---|
| `## <타입>` 섹션 순서 | **화면의 카테고리 순서와 같다** |
| 섹션 안 | 이름순 |
| `aliases` | 같은 것을 부르는 다른 이름. 정규화에 쓴다 |

**어휘에 없는 이름은 좌표가 아니다.** 등재하지 않고 쓰면 같은 테이블이
`rp_trip_photo` · `trip_photo_list` 로 갈라져 쌓이고, 갈라진 뒤에는
되돌릴 수 없다. `ctx check` 가 오류로 막는 이유다.

## 2.3 `_managed.md` — 등록부

```markdown
| 좌표 패턴 | 정본 문서 | 섹션 |
|---|---|---|
| `table:*` | `docs/테이블정의서.md` | `## {값}` |
| `screen:*` | `docs/화면설계서.md` | `## {값}` |
```

위에서부터 훑어 **먼저 걸리는 패턴**을 쓴다. 좁은 것을 위에 둔다.

```
| screen:PS* | docs/화면정의서_인사.md | ## {값} |     ← 먼저
| screen:*   | docs/화면설계서.md      | ## {값} |     ← 나중
```

### 등록부에 없는 좌표는 결함이 아니다

`domain:` 은 **축**이지 바뀌는 대상이 아니다. `module:` 은 프로젝트에 따라
정본 문서가 없을 수 있다. 등록부에 없으면 파생 의무도 없다 — 정상이다.

## 2.4 작업 기록

```markdown
---
id: 2026-0922-EXD020-첨부용량        ← 파일명과 **반드시 같다**
title: EXD020 사진 첨부 용량 10MB
date: 2026-09-22 14:30               ← 그 일이 있었던 **때**
author: kjsa
touches:
  - screen:EXD020
tags: [출장]
---

(자유 형식)
```

| 필드 | | |
|---|---|---|
| `id` | 필수 | `YYYY-MMDD-slug`. 파일명과 같다 |
| `title` | 필수 | |
| `date` | 필수 | **사건의 날짜.** 오늘이 아니다. `2026-09-22` 또는 `2026-09-22 14:30` |
| `author` | 필수 | |
| `touches` | 필수 | 0개여도 `[]` 로 적는다 |
| `source` | | 밖에서 들인 문서의 원문 위치 |
| `supersedes` | | **이 기록 자체가 틀렸을 때만** |
| `status` | | **쓸 수 있는 값이 없다** (§4.3) |

# 3. 좌표

## 3.1 무엇이 좌표인가

**이 작업이 바꾼 것만이다.**

| 이 작업이 그 대상을… | 좌표 |
|---|:--:|
| 신설했다 | **O** |
| 변경했다 (컬럼 추가 · 규격 변경 · 상태값 추가) | **O** |
| 삭제·폐기했다 | **O** |
| 참조했다 · 호출했다 · 언급했다 | **X** |
| 그것을 쓰는 다른 것을 만들었다 | **X** |

판정 기준은 하나다 — **6개월 뒤 그 대상을 맡은 사람이 이 작업을 찾아야
하는가.** *"주제인가?"* 는 답이 갈리지만 *"바꿨는가?"* 는 결판난다.

**0개도 정상이다.** 일정을 정했을 뿐 아무 대상도 안 바꾼 작업이 실제로
있다. 그때는 `touches: []` 로 적는다 — 키를 빼지 말고 **0개임을 확인했다는
선언**으로 남긴다.

**억지 좌표는 없는 좌표보다 나쁘다.** 그 좌표를 찾는 사람에게 무관한 문서를
내밀고, 채울 내용 없는 파생 의무를 만들고, 억지로 채우면 틀린 내용이
정본에 들어간다.

## 3.2 계산은 하나다

```
later(기준, 좌표) = 그 좌표를 touches 에 가진 작업 기록 중 기준보다 나중인 것
```

이 하나가 세 곳에 쓰인다.

| 기준 | 답하는 질문 |
|---|---|
| 작업 기록 | 이 기록의 이 좌표 부분은 최신인가 |
| 섹션의 `applied` | 이 섹션에 남은 파생이 있는가 |
| 없음 | 이 좌표의 최신 작업 기록은 무엇인가 |

**문서 단위로 판정하지 않는다.** 문서는 사건이라 통째로 낡지 않는다 —
후속이 붙는 것은 `(문서, 좌표)` 쌍이다. 좌표가 여럿인 문서에서 문서 단위로
판정하면 반드시 둘 중 하나가 틀린다.

### 같은 날짜는 후속이 아니다 — 시각이 없을 때만

`date` 에 **시각까지 적으면 순서가 결판난다.** 아래는 시각이 없는 기록
끼리의 이야기다.

```
2026-09-08 · 2026-09-08              동배. 순서를 모른다 → 경고
2026-09-08 09:10 · 2026-09-08 14:30  후속. 파생 누락은 **오류**다
2026-09-08 · 2026-09-08 14:30        동배. 한쪽이 시각을 모르니 단정하지 않는다
```

시각을 쓰기 시작하면 아래 사각지대는 **옛 기록에서만** 남는다.

날짜 입도가 하루이므로 **하루 안의 순서를 알 수 없다.** 그리고 섹션의
`applied` 는 하나만 가리키는데 하루에 같은 좌표를 두 번 건드리면 섹션은
둘 다 반영하고 `applied` 는 그중 하나만 적는다.

id 문자열로 순서를 매기면 남은 하나가 파생 누락으로 잡힌다 — 실측에서
`screen:PLA011` 이 그랬다. 셋 다 반영했는데 1건이 남았다.

**이 목록의 오탐은 부식성이 크다.** 한 번 틀리면 사람들이 그 목록 전체를
안 믿는다. 그래서 같은 날짜는 동료로 본다.

대가는 **경고로 갚는다.**

```
[경고] 같은 날 기록이 더 있습니다 — 반영됐는지 눈으로 확인하세요
```

막지 않는다. 반영됐는지 기계가 알 수 없기 때문이다. 경고는 틀려도
부식되지 않고, 맞으면 눈에 띈다.

# 4. 판정 — 사실과 오류만 있다

## 4.1 상태는 없다

```
반영(applied)   이 섹션이 어느 작업까지 실었다        — 사실
파생 누락       갱신을 안 했다                        — 오류
섹션/문서 없음  등록부가 없는 자리를 가리킨다          — 오류
끊김            applied 가 유령을 가리킨다             — 오류
```

**"밀림" · "미작성" 은 상태가 아니다.** 파생은 필수이므로 안 한 것은 상태가
아니라 오류다. 화면에 상태로 보여 주면 사람들이 그것을 정상 범주로 받아
들이고, 그 순간 목록이 늘 뭔가 쌓여 있는 통이 된다.

## 4.2 아젠다는 여기 없다

**지식공유문서는 작업의 완료에서 발생하는 문서다.** 결정을 기다리는 것은
완료가 아니라 아젠다이고, 아젠다는 위험및이슈관리대장 같은 스케줄 문서가
다룬다.

불변인 사건(`work/`)과 가변인 상태(아젠다)를 같은 폴더에 섞으면 지식
레포가 **할 일 목록** 노릇을 하기 시작하고, 그러면 둘 다 안 맞는다.

## 4.3 `status` — 쓸 수 있는 값이 없다

```
확정 · 완료   기본값이다. 파싱 경계에서 지운다
미결 · 제안   결정이 안 났다. 아젠다이고 갈 곳은 이슈 대장이다
진행중        그런 상태가 없다. 끝나지 않은 일은 문서가 아니다
```

`진행중`(점유)은 초안에 있었다. 뺐다 — 같은 좌표를 동시에 건드릴 걱정은
남지만 그것은 **일감 분배**의 문제지 문서 형식으로 풀 것이 아니다.

**`status` 칸은 비어 있는 것이 유일한 정상이다.**

## 4.4 `supersedes` — 오기재 정정에만

```yaml
supersedes: 2026-0908-사진첨부-용량
```

**이 기록 자체가 틀렸을 때만** 쓴다. 같은 좌표를 나중에 또 바꾼 것은 적을
필요가 없다 — 그것은 `later()` 로 계산해서 나온다.

그리고 **앞 기록을 지우지 않는다.** 20MB 로 잘못 알고 진행한 구간이
있었다는 사실 자체가 맥락이다.

# 5. 기록이 생기는 세 길

**어느 길이든 관리 문서 갱신이 함께 간다.** 그것이 이 프로토콜의 전부다.

| | 어떤 일이었나 | skill |
|---|---|---|
| **A** | 이 세션에서 작업했다 | `cdp-work` → `cdp-save` |
| **B** | 이미 쓴 문서가 있다 (회의록·검토서) | `cdp-import` |
| **C** | 작업은 없고 **문서를 고치라는 지시** | `cdp-edit` |

## 5.1 A — 이 세션에서 작업했다

```
cdp-work    ① 검토      대상을 뽑는다. 레포 본문은 안 읽는다
            ② 주입      관리 문서 섹션을 읽어 맥락으로
            ③ 수행      요청을 처리한다
cdp-save    ① pull      ② 좌표 판정  ③ 기록  ④ 파생  ⑤ 한 커밋
```

## 5.2 B — 밖에서 온 문서

`cdp-import`. cdp-save 와 뼈대는 같고 **날짜와 좌표**가 다르다.

- **날짜는 사건의 날.** 오늘로 적으면 반년 전 회의록이 어제 결정을 덮는다
- **언급은 좌표가 아니다.** 밖에서 온 문서는 규약을 모르고 쓰였다 — 화면
  이름이 열다섯 개 나와도 그 회의가 바꾼 것은 둘일 수 있다
- **본문을 다시 쓰지 않는다.** 회의록의 반대 의견이 6개월 뒤 유일한 단서다
- 편입 문서가 `applied` 보다 **과거**면 `applied` 를 바꾸지 않는다

## 5.3 C — 문서 수정 지시

`cdp-edit`. 문서를 고치고 **지시 자체를 기록의 본문으로** 남긴다.

```markdown
## 지시
> 사진 첨부 용량은 10MB 로 해줘. WAS 업로드 상한이 그거라서 20MB 로
> 적어 놔도 어차피 안 올라가.
kjsa, 2026-09-22.

## 반영
docs/화면설계서.md ## EXD020 의 첨부 대목에 10MB.

## 확인한 것
앞서 20MB 로 적혀 있었다. 회의에서 나온 말을 옮긴 것이고 WAS 설정을 본
것이 아니었다.
```

**지시를 요약하지 않는다.** "20MB 로 적어 놔도 어차피 안 올라가" 가 제약의
출처를 담고 있고, "10MB 로 변경" 으로 줄이면 그것이 사라진다.

### 이 자리는 기계가 막지 못한다

관리 문서만 고치고 기록을 안 남기면 `ctx check` 는 **아무 말도 하지
않는다.** 파생 누락 검사는 작업 기록을 기준으로 도는데 기록이 없으면
기준이 없다.

**2층이 닿지 않는 유일한 자리다.** 그래서 `cdp-edit` 이 있다.

# 6. 보증 — 층이 둘이다

| 층 | 수단 | 성질 |
|---|---|---|
| 1 | **skill** — 절차를 품는다 | 비결정적 · **편의** |
| 2 | **git 훅** — 커밋 시점에 기계가 검사한다 | **결정론적 · 보증** |

> skill 은 LLM 에 대한 지시이므로 비결정적이다. 대체로 잘 지켜지지만
> 항상은 아니다. **skill 은 편의, hook 은 보증.**

skill 을 건너뛰고 문서를 고쳤다면 git 훅이 커밋 시점에 잡는다 — **피해가
발생하는 경계에서 기계가 막는다.**

## 6.1 최신화 — 읽기와 쓰기가 다르다

```
쓰기  git pull --ff-only    실패하면 시작하지 않는다
읽기  ctx sync              받지 않는다. 받을 것이 있으면 알리고 묻는다
```

| | 낡은 채로 하면 | 언제 드러나나 |
|---|---|---|
| 쓰기 | 남의 갱신을 덮는다 | 커밋 diff |
| 읽기 | **낡은 그림 위에서 설계한다** | `cdp-save` 의 pull. **이미 만든 뒤다** |

쓰기의 pull 은 **레포가 깨지는 것**을 막고, 읽기의 확인은 **틀린 것을
만드는 것**을 막는다.

**읽기에 pull 을 강제하지 않는다.** ff 가 안 되는 상태에서 보는 것조차
막히면 과하다 — 낡은 것이라도 보는 편이 낫고, 낡았다는 사실만 알면 사람이
판단한다.

## 6.2 검사 규칙 — 전부

`error` 는 커밋을 막는다. `warn` · `info` 는 막지 않는다.

| 등급 | 이름 | |
|---|---|---|
| **error** | `missing-field` | 필수 필드 누락 |
| **error** | `frontmatter` | 프론트매터 오류 |
| **error** | `id-mismatch` | `id` 와 파일명 불일치 |
| **error** | `unregistered-coord` | `_vocab.md` 미등재 좌표 |
| **error** | `dangling-anchor` | 등록부가 가리키는 섹션이 없음 |
| **error** | `orphan-applied` | `applied` 가 없는 작업 기록을 가리킴 |
| **error** | `derive-missing` | **관리 문서 파생 누락** |
| **error** | `agenda-status` | `status: 미결·제안` — 아젠다다 |
| **error** | `status-value` | `status` 에 쓸 수 있는 값이 없다 |
| **error** | `broken-supersedes` | `supersedes` 대상 문서 없음 |
| **error** | `cycle` | `supersedes` 순환 참조 |
| warn | `derive-sameday` | 같은 날 기록이 더 있다 — 눈으로 확인 |
| warn | `deprecated-coord` | 폐기된 좌표 사용 |
| warn | `hooks-off` | **git 훅이 설치되지 않았다** |

`hooks-off` 가 **가장 조용한 실패**다. 훅이 없으면 커밋은 통과하고 검사는
안 돈다 — 그리고 아무도 모른다.

```
git config core.hooksPath .githooks     ← clone 직후 한 번. 훅은 clone 을 안 따라온다
```

# 7. 프로그램

## 7.1 형태

```
cdp.exe  (단일 실행 파일 · 약 68MB)
  ├── 앱        더블클릭 → 브라우저가 열린다
  └── ctx CLI   cdp.exe ctx <명령>
```

Node SEA. **런타임과 화면 자산이 전부 안에 들어 있다.** 폐쇄망에서 CDN 을
쓸 수 없으므로 화면의 폰트까지 base64 로 인라인돼 있다.

## 7.2 스택 — 무엇으로 만들었나

    확인 시점 2026-09-09 · v0.3.8

| | | |
|---|---|---|
| 런타임 | **Node 20** | SEA 로 exe 에 그대로 들어간다 |
| 화면 | **React 18.3** + **react-dom** | 상태관리·라우팅 라이브러리 **없다** |
| 번들 | **Vite 6** + `@vitejs/plugin-react` | `out/web/` 으로 |
| 스타일 | **CSS 4파일** | `tokens · app · doc · font`. 프레임워크 없다 |
| 마크다운 | **markdown-it 14** + `markdown-it-anchor` | 렌더는 **전부 클라이언트**가 소유한다 |
| 살균 | **DOMPurify 3** | 렌더 결과를 그대로 넣지 않는다 |
| 코드 강조 | **highlight.js 11** | **동적 import** — 코드블록이 보이는 순간에만 |
| 검색 | **MiniSearch 7** | 서버쪽 색인 |
| 프론트매터 | **js-yaml 4** | |
| 감시 | **chokidar 3** | 파일 변경 → SSE |
| 그래프 | **Canvas 2D** | 3D 힘배치를 손으로 짰다. **라이브러리 없다** |
| ctx 번들 | **esbuild** | 한 파일로 |
| exe | **Node SEA** + `postject 1.0.0-alpha.6` + `rcedit` | blob 주입 · 아이콘 · 서브시스템 패치 |

`node` 판은 **빌드에 쓴 것이 그대로 exe 에 들어간다** — SEA 는 실행 중인
node 바이너리를 복사해 blob 을 주입하는 방식이다.

### 없는 것이 더 중요하다

**CDN 을 타는 것이 하나도 없다.** 폐쇄망이 전제이므로 화면의 폰트까지
base64 로 인라인돼 있다. 웹폰트 링크 하나가 남아 있으면 그 PC 에서는
글자가 다르게 보이고, 그 사실을 아무도 모른다.

**UI 프레임워크·상태관리·라우터가 없다.** 화면이 넷(관리문서·작업문서·
좌표·그래프)이고 상태가 얕다 — 라우터를 넣으면 URL 이 상태가 되고, 그러면
`?t=<토큰>` 과 섞인다.

**그래프에 three.js 를 쓰지 않는다.** 번들하면 exe 가 크게 늘고, 3D 힘배치 +
원근 투영 + z 정렬이면 150줄이다. 그것으로 충분하다.

**highlight.js 는 초기 번들에 없다.** 코드블록이 화면에 나타나는 순간
동적 import 한다 — 대부분의 문서에는 코드블록이 없다.

### 빌드에 필요한 것은 전부 선언돼 있다

`npm ci` 만 하면 빌드가 돈다. **망에서 뭔가를 더 받아 오지 않는다.**

전에는 그렇지 않았다. exe 를 만드는 마지막 단계(SEA blob 주입)를
`npx --yes postject` 로 불렀다 — 선언되지 않은 의존이라 —

| | |
|---|---|
| 재현 | `npm ci` 가 안 깐다. 태그로 되살려도 이것만 안 따라온다 |
| 판 | `--yes` 는 그때 npm 이 주는 **최신**을 받는다. postject 가 바뀌면 말없이 다른 도구로 exe 를 만든다 |
| 망 | 캐시가 비고 끊긴 PC 에서는 그 줄에서 죽는다 |

**폐쇄망은 쓰는 쪽의 전제이지 만드는 쪽의 전제가 아니다** — exe 는 망 밖에서
만들어 반입한다(설치 시나리오 ①②). 그래도 재현되지 않는 빌드는 곤란하다.
지금은 `devDependencies` 에 판이 박혀 있고 로컬 bin 을 부른다.

```
postject 1.0.0-alpha.6      ^ 없이 정확한 판
node node_modules/postject/dist/cli.js …
```

빌드는 **시작 전에** postject 가 있는지 본다. 없으면 `npm ci` 를 돌리라고
하고 멈춘다 — 66MB node 바이너리를 복사한 뒤에 죽으면 **반쪽 exe 가
남는다.** 그 파일은 실행은 되는데 `Cannot find module 'ctx'` 를 뱉는다.

### 판을 어디서 보나

```
package.json          선언된 범위 (^)
package-lock.json     **실제 판.** 재현은 이것이 고정한다
npm ls --depth=0      지금 깔린 것
```

배포본을 되살릴 때 `npm ci` 를 쓰는 이유가 그것이다 — `npm install` 은
`^` 를 다시 풀어 다른 판을 가져올 수 있다.

## 7.3 층 구조

```
server/core/      스캔 · 프론트매터 · 어휘 · 등록부 · 최신성 · 검색 · 검사
server/adapter/   HTTP + SSE · 트레이 · 토큰/Origin/경로 봉인
src/              화면 (React). 마크다운 렌더는 전부 클라이언트가 소유한다
bin/ctx-cli.mjs   CLI. core 를 그대로 부른다
```

**앱과 `ctx` 는 같은 함수를 부른다.** `runBuiltinCheck` 하나다 — 그래서
화면의 검사 결과와 커밋 훅의 판정이 어긋날 수 없다.

## 7.4 화면

| 탭 | |
|---|---|
| 관리문서 | 정본. 섹션마다 반영 상태 |
| 작업문서 | 기록. **작성일자순**. 제목 옆에 작성자 |
| 좌표 | 카테고리순 + 카테고리 안 이름순 |
| 그래프 | 좌표망 3D. 크기 = 작업 건수. 배치가 **캔버스 비율을 따른다** |

**뻗어나가기** — 지금 보는 것에서 한 층만 편다.

```
작업문서  →  관리문서 · 좌표
좌표      →  관리문서 · 작업문서
관리문서  →  섹션
```

### 배치는 구다. 그리고 **반지름이 뜻을 갖는다**

```
많이 이어진 좌표   안쪽    이 프로젝트의 중심이다
적게 이어진 좌표   바깥    가장자리다
```

구는 원래 안쪽이 비어 보인다 — 표면에만 점이 있으면 껍데기다. 연결도로
반지름을 주면 그 빈 곳이 의미로 채워지고, 돌릴 때 **중심에 무엇이 있는지**가
보인다.

잠깐 캔버스 비율을 따르는 렌즈로 바꿨다가 되돌렸다. 비율을 따르려면 창이
바뀔 때마다 O(n²) 배치를 다시 풀어야 하는데 283개에서 그것이 **끌 때마다
걸렸다.** 모양을 얻고 반응을 잃은 것이다.

### 이름은 끌 수 있다

283개에 이름을 다 적으면 서로를 덮어 글자 더미가 된다. **덮인 글자는 없는
것보다 나쁘다** — 읽으려다 시간을 쓴다.

```
자동   배율이 낮으면 끈다 (기본)
켬     항상 그린다
끔     점만. 짚거나 고른 것과 그 1단계 이웃만 이름이 뜬다
```

**상태로 색을 쓰지 않는다.** 노드는 전부 같은 원이고 크기만 다르다 —
색은 *지금 고른 것* 하나에만 쓴다.

## 7.5 `ctx`

```
ctx check [--json]        커밋 가능한가. 오류가 있으면 exit 1
ctx index                 INDEX 재생성 (훅이 커밋마다 한다)
ctx match <이름...>       이름 → 정본 좌표
ctx where <좌표>          그 좌표가 어느 문서 어느 섹션인가
ctx derive                파생이 안 된 섹션 목록
ctx term <이름>           어휘 조회
ctx apply <좌표>          파생할 섹션에 붙일 변경 줄 초안
ctx brief                 두 줄 요약
ctx sync [--pull]         원격과의 차이. --pull 은 ff 만
ctx setup <작업 레포>     그 레포에 규약과 skill 을 넣는다
ctx version               번들 시각
```

### 실행기를 고른다

`bin/ctx` 는 sh 스크립트다.

```
① node 가 있으면       node bin/ctx.mjs
② 없으면               tools/cdp.exe ctx
③ 둘 다 없으면         exit 127
```

**127 로 내는 것이 중요하다.** 검사 실패(1)와 구분해야 한다. 폐쇄망 실측에서
이걸 1 로 냈더니 git 훅이 "검사 실패" 로 읽고 커밋을 막았다 — git 은 있고
Node·exe 가 없는 PC 에서 **아무도 커밋을 못 하게 됐다.** 그리고 메시지가
"고친 뒤 다시 커밋하세요" 라 사용자는 자기 문서가 잘못된 줄 안다.

### 레포를 어떻게 찾나

```
① --repo 인자
② CDP_REPO 환경변수
③ cwd 에서 위로 (6단계)
④ 자기 위치의 부모        <repo>/bin/ctx.mjs · <repo>/tools/cdp.exe
```

④ 가 필요한 이유 — 작업 레포(`C:\gdi`)에 서서 `C:\cdp\bin\ctx` 를 **전체
경로로 부르는데도** 못 찾았다. `C:\cdp` 는 `C:\gdi` 의 형제라 상위 탐색에
걸리지 않는다.

## 7.6 CRLF — 조용히 깨지는 자리

```
.gitattributes
  * text=auto eol=lf
```

`bin/ctx` 와 `.githooks/pre-commit` 은 sh 가 읽는다. CRLF 로 체크아웃되면
셔뱅 뒤에 캐리지리턴이 붙어 **훅이 실행되지 않는다.** 커밋은 통과하고
검사만 사라진다.

`core.autocrlf=true` 인 PC 에서만 깨지므로 **폐쇄망에 옮긴 뒤에 발견된다.**
그때는 물어볼 사람이 없다.

# 8. 배치

**경로는 사람마다 다르다.** 지식 레포도 작업 레포도 어디든 둘 수 있고,
작업 레포는 여럿이어도 된다. 중요한 것은 **지식 레포가 하나**인 것이다.

```
<지식 레포>            _vocab.md 가 있는 곳.  하나
<작업 레포> …          코드가 있는 곳.  여럿이어도 된다
```

### 경로는 커밋되지 않는다

| 파일 | | |
|---|---|---|
| `CLAUDE.md` | 커밋 | 규약. **경로가 없다** |
| `.claude/cdp.json` | **커밋 안 함** | `{ "knowledgeRepo": "…" }` |

전에는 `CLAUDE.md` 에 지식 레포의 절대경로를 박았다. 그 파일은 커밋되어
팀에 퍼지는데 **경로는 사람마다 다르다** — 그래서 "팀이 같은 경로를 쓴다"
는 규약을 강요해야 했다. 규약이 아니라 설계로 풀 문제였다.

포인터 파일이 있으면 **작업 레포당 지식 레포가 정확히 하나**로 기계적으로
지켜진다. `ctx` 는 작업 레포 안 어디서 불러도 이 파일을 보고 찾는다.

## 8.1 작업 레포에도 skill 을 둔다

**하네스는 프로젝트 루트의 `.claude/skills/` 만 읽는다.** 지식 레포에만
두면 코드 레포에서 클로드를 열었을 때 skill 이 목록에 아예 없다 — 절차
층이 통째로 빠진다.

```
<지식 레포>/tools/cdp.exe ctx setup <작업 레포>       터미널
설정 → 작업 레포 → [에이전트 설치]                    앱
```

둘은 **같은 함수를 부른다**(`core/setup.js`). 화면이 다른 일을 하면 둘 중
하나는 반드시 거짓말이 된다.

**남의 것을 지우지 않는다.**

| | |
|---|---|
| skill | `cdp-` 로 시작하는 것만. 그 레포의 다른 skill 은 그대로 |
| `CLAUDE.md` | `<!-- cdp:begin -->` … `<!-- cdp:end -->` **블록만** 갈아 끼운다 |
| 대상 | **git 레포일 때만.** 아무 폴더에나 쓰지 않는다 |

앱에서 누를 때는 **무엇을 쓸지 먼저 보여 준다.** 레포 밖에 파일을 쓰는
유일한 자리라, 모르고 누르게 하지 않는다.

사본이 느는 것은 이 설계가 계속 피해 온 것이지만 대안이 더 나쁘다. 전역
설치와 정션은 둘 다 **그 PC 에만** 남아 팀에 퍼지지 않는다. 퍼지지 않는
것은 절차로 못 막고, 드리프트는 막을 수 있다.

그리고 이 사본이 낡아도 **2층은 지식 레포 쪽에서 돈다** — 보증은 흔들리지
않는다. 낡는 것은 편의 층뿐이다.

## 8.2 정본이 어디인가

```
kit/                  **받는 사람에게 가는 것의 원본**
  agent/                CLAUDE.md 2종 · skill · TEMPLATE
  hooks/pre-commit
  manual/               system · user · admin
  install.md
release/v<버전>/      배포본
<지식 레포>/          배포본의 사본
<작업 레포>/          ctx setup 이 넣은 사본
```

**사본을 고치면 다음 빌드에 덮인다.**

# 9. 불변조건

이것들이 깨지면 CDP 가 아니다.

| | |
|---|---|
| 1 | `work/` 는 append-only. 기록을 고치지 않는다 |
| 2 | 좌표 하나에 정본 섹션 하나 |
| 3 | 섹션은 자기가 어디까지 실었는지 한 줄로 적는다 (`applied`) |
| 4 | 기록을 남기면 파생 갱신은 **필수**다 |
| 5 | 어휘에 없는 이름은 좌표가 아니다 |
| 6 | `status` 는 비어 있다 |
| 7 | 상태는 없다. 사실과 오류만 있다 |
| 8 | 계산은 하나다 — `later(기준, 좌표)` |
| 9 | 같은 날짜는 후속이 아니다 — **시각이 없을 때만** (경고로 갚는다) |
| 10 | 보증은 git 훅 하나다. 나머지는 편의다 |
| 11 | 쓰기 전에는 받는다. 읽기 전에는 확인한다 |
| 12 | 앱과 `ctx` 는 같은 함수를 부른다 |
| 13 | 인터넷을 타는 것이 하나도 없다 |
| 14 | 실패는 조용하지 않다 — exit 코드와 메시지로 구분된다 |

# 10. 거부한 설계

**안 한 것에도 이유가 있다.** 다시 제안되는 것들이다.

| | 왜 안 했나 |
|---|---|
| 상태 필드로 밀림 관리 | 상태로 보이면 정상 범주가 된다. 오류여야 막힌다 |
| 문서 단위 최신성 | 좌표가 여럿인 문서에서 반드시 둘 중 하나가 틀린다 |
| 같은 날짜를 후속으로 | 오탐. 한 번 틀리면 목록 전체를 안 믿는다 |
| 최신성을 저장 | 저장하면 반드시 낡는다. 질의 시점에 계산한다 |
| `UserPromptSubmit` 훅으로 절차 재주입 | 비결정을 비결정으로 덮는 것이다. 뒤에 결정론적 2층이 있다 |
| `CLAUDE.md` 에 절차를 적기 | skill 과 중복. 한쪽만 고쳐지면 어느 쪽이 맞는지 알 수 없다 |
| RAG · 임베딩 | 가까운 것과 맞는 것은 다르다 |
| 지식 폴더 자동 최신화 | pull 이 유일한 수신 채널이다. 그 위에 층을 더 쌓지 않는다 |
| 뷰어에서 쓰기 | 쓰기는 pull 선행이 필수인데 앱이 그것을 강제할 수 없다 |
| exe 를 git 에 커밋 | 68MB 는 이력에서 되돌릴 수 없다 |
| 읽기에 pull 강제 | 보는 것조차 막히면 과하다 |
