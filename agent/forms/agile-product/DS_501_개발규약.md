<!-- form:head -->
서술형. 코드를 **어떻게 함께 쓰고 내보내나** — 브랜치 · 커밋 · 리뷰 · 완료의 정의 ·
CI 게이트.

<!-- form:guide -->
**무엇** — 팀이 매일 지키는 규칙. **린터 · 포매터 · CI 가 강제하는 것은 설정 파일이 정본**이고,
여기는 그 규칙이 왜 있는지와 기계가 못 보는 것을 적는다.
**언제** — 첫 스프린트 전에 세운다. 회고에서 규칙을 바꾸기로 하면 그 주에 고친다.
**누가** — 리드 개발자가 쓰고 팀 합의로 바꾼다.

**여기 적지 않는 것**

| | 어디로 |
|---|---|
| 시험의 층 · 범위 · 품질 게이트 기준 | `테스트전략` |
| 플래그를 언제 켜고 지우나 | `기능플래그` |
| 환경 · 배포 경로 | `시스템아키텍처` 의 deploy |
| 린트 · 포맷 규칙 원문 | 코드 레포의 설정 파일 |
| 규칙을 바꾼 이유 | 작업 기록(`work/`) — 회고 액션이면 `스프린트기록` 이 가리킨다 |

### 골격

| # | 절 |
|--:|---|
| 1 | 브랜치 — 트렁크 기반 |
| 2 | 커밋 · PR |
| 3 | 리뷰 |
| 4 | 완료의 정의(DoD) |
| 5 | CI 게이트 |
| 6 | API 공통 |

### 작성지침

| 항목 | 작성방법 | 필수 |
|---|---|:--:|
| 절 구성 | 위 뼈대. 빼면 **왜 뺐는지** 그 자리에 한 줄 | 필수 |
| 근거 | 기계가 강제하는 규칙은 설정 파일을 가리키고 옮기지 않는다 | 필수 |
| 결정 | 규칙을 바꾼 이유는 작업 기록에. 여기는 바뀐 규칙만 | 필수 |
| 제목 | 자유롭다 — 등록부 비대상이라 좌표와 충돌하지 않는다 | 필수 |
| 경과 | 문서 맨 아래에 `**경과**` 아래 한 줄 `- 날짜 [작업 기록](../work/…) 무엇이` 를 쌓는다 | 반영 때 필수 |

<!-- form:example -->
> 아래는 **권장 출발점**이다 — 팀에 맞게 고친다. 안 쓰는 절은 지우고 그 자리에 왜 뺐는지
> 한 줄을 남긴다. 규칙을 바꾼 이유는 작업 기록에 쓴다 — **작업 기록이 ADR 이다.**

### 예시 — 브랜치 — 트렁크 기반

- `main` 하나가 늘 배포할 수 있는 상태다. 작업 브랜치는 **하루 · 이틀 안에** 머지한다
- 끝나지 않은 기능은 브랜치에 오래 두지 않고 **기능 플래그 뒤에** 머지한다
- 릴리스 브랜치를 두지 않는다. 앱 스토어 심사처럼 묶어 내야 하면 태그에서 핫픽스 브랜치를 딴다

### 예시 — 커밋 · PR

| 규칙 | 왜 |
|---|---|
| PR 하나에 변경 하나 · 400줄 안팎 | 리뷰가 실제로 읽는 크기다 |
| 제목은 Conventional Commits(`feat` · `fix` · `chore` …) | 릴리스노트 초안이 여기서 나온다 |
| 이슈 키를 제목이나 본문에 | 무엇을 왜 했는지 따라간다 |
| 스키마는 앞으로만 바꾼다(expand → migrate → contract) | 무중단 배포 · 되돌리기 |

### 예시 — 리뷰

- 승인 1명 이상. 작성자가 머지한다
- **첫 응답은 24시간 안에.** 막히면 짝 리뷰로 바꾼다
- 리뷰어는 동작 · 시험 · 이름 · 보안을 본다. 스타일은 포매터가 본다

### 예시 — 완료의 정의(DoD)

| # | 기준 |
|--:|---|
| 1 | 수용 기준(`기능명세`)의 행마다 시험이 있다 |
| 2 | CI 초록 · 리뷰 승인 |
| 3 | 바꾼 대상을 작업 기록의 `touches:` 에 적었다 — 관리 문서는 큐레이터가 반영한다(그 전까지 섹션에 「미반영」 으로 보인다) |
| 4 | 플래그를 만들었으면 `기능플래그` 에 행과 제거 예정일이 있다 |
| 5 | stg 에서 확인했고 지표 이벤트가 찍힌다 |
| 6 | 사용자에게 보이는 변화면 `릴리스노트` 초안에 한 줄 |

### 예시 — CI 게이트

| 단계 | 막는 조건 |
|---|---|
| 정적 검사 | 린트 · 타입 검사 실패 |
| 단위 · 통합 시험 | 실패 하나라도 · 변경 줄 커버리지 80% 아래 |
| 계약 시험 | 소비자 계약이 깨짐 — `인터페이스명세` 의 계약 시험 |
| 보안 | 의존성 취약점 높음 이상 · 비밀 유출 탐지 |
| E2E 스모크 | 핵심 흐름(로그인 · 장바구니 · 결제) 실패 |

### 예시 — API 공통

- 오류 형식 RFC 9457(Problem Details) · 시각은 ISO 8601 UTC · 금액은 정수(원) · 목록은 커서 페이지
- 깨지는 변경은 판(`/v2`)으로 낸다 — 자원별 호환성은 `인터페이스명세`
