<!-- form:head -->
운영 중인 AI 기능을 **무엇으로 보고, 언제 깨우고, 어떻게 평가셋으로 되돌리나.**

<!-- form:guide -->
**무엇** — 추적 · 품질 드리프트 · 비용 · 지연 · 사용자 피드백 · 경보 · 평가셋으로 되돌리기(피드백 루프).
**언제** — 출시 전에 세우고, 지표나 문턱을 바꾸면 고친다.
**누가** — AI 엔지니어 · 운영 담당.

**여기 적지 않는 것**

| | 어디로 |
|---|---|
| 무엇을 어디에 기록하나(추적 구성) | `시스템아키텍처` |
| 출시 기준 | `평가셋` |
| 위험으로 올릴 것 | `AI위험관리` |
| 지난 사고의 경과 · 원인 | 작업 기록(`work/`) |
| 대시보드의 숫자 자체 | 지표 도구 — 여기는 무엇을 보고 언제 움직이나 |

> **운영은 평가셋의 원천이다.** 신고 · 낮은 채택 · 이상한 추적은 고쳐야 할 사례이고,
> 고친 뒤에는 **평가셋의 사례**가 되어야 다시 깨지지 않는다.

| 4 | 사용자 피드백 |
| 5 | 평가셋으로 되돌리기 |

### 작성지침

| 항목 | 작성방법 | 필수 |
|---|---|:--:|
| 지표와 경보 | 지표마다 재는 법 · 문턱 · 누구를 깨우나. **문턱 없는 지표는 보기만 하는 그림이다** | 필수 |
| 품질 · 비용 · 지연 | 셋 다 둔다 — 하나만 보면 다른 둘을 희생한다 | 필수 |
| 피드백 | 어디서 모으고 어디로 보내나. 평가셋으로 가는 길이 있어야 한다 | 필수 |
| 되돌리기 | 틀린 사례가 평가셋 사례가 되는 절차 | 필수 |
| 근거 | 다른 문서에 있는 것은 **옮겨 적지 말고 이름으로 가리킨다** | 필수 |
| 경과 | 문서 맨 아래에 `**경과**` 아래 한 줄 `- 날짜 [작업 기록](../work/…) 무엇이` 를 쌓는다 | 반영 때 필수 |

### 예시 — 지표와 경보

| 지표 | 어떻게 재나 | 문턱 | 경보 · 누구 |
|---|---|---|---|
| (예시) 초안 채택률 | 고치지 않거나 조금 고쳐 보낸 비율 · 일 단위 | 7일 평균 50% 아래 | 메신저 채널 · AI 리드 |
| (예시) 근거 충실(운영 표본) | 하루 200건 표본을 LLM 심판으로 | 0.85 아래 | 〃 |
| (예시) 신고 | 상담원 「틀림」 단추 | 하루 10건 위 | 〃 · 상담 운영 |
| (예시) 지연 p95 | 게이트웨이 기록 | 6초 위 15분 | 당번 |
| (예시) 오류 · 대체 모델 전환율 | 게이트웨이 기록 | 5% 위 | 당번 |
| (예시) 토큰 비용 | 일 비용 · 문의당 비용 | 일 예산의 130% 위 | AI 리드 |

### 예시 — 추적으로 원인 가르기

(예시) 신고 하나 → 추적 ID → 단계별 입력 · 출력 · 판 → **검색이 틀렸나 · 생성이 틀렸나 · 도구가
틀렸나**를 가른다. 검색이면 지식소스, 생성이면 프롬프트 · 모델 쪽 작업이 된다.

### 예시 — 품질 드리프트

(예시) 문의 주제 분포 · 검색 결과 없는 비율 · 평균 근거 점수를 주 단위로 지난 4주와 견준다.
원천(도움말) 개편 · 시즌 이벤트 · 공급자 판 종료가 흔한 원인이다. 드리프트가 보이면 평가셋이
지금의 문의를 대표하는지부터 본다.

### 예시 — 사용자 피드백

| 피드백 | 어디서 | 어디로 |
|---|---|---|
| (예시) 상담원이 고친 차이 | 상담 화면 | 주 1회 표본 검수 → 평가셋 후보 |
| (예시) 「틀림」 신고 | 상담 화면 | 하루 안에 분류 → 위험이면 `AI위험관리` |
| (예시) 고객 불만 | 상담 시스템 | 월 1회 묶어 본다 |

### 예시 — 평가셋으로 되돌리기

1. 신고 · 표본 검수에서 틀린 사례를 고른다
2. 개인정보를 가리고 정답을 단다
3. 평가셋 정본 위치에 더하고 판을 올린다 — 작업 기록에 평가셋 좌표를 적고 그 섹션의 크기 · 판을 고친다
4. 다음 출시부터 그 사례가 출시 기준에 들어간다

> ⚠ **예시 행이다 — 지우고 시작한다.** 절 제목은 두고 내용을 팀의 것으로 바꾼다.
