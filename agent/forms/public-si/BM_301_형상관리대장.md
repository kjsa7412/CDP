산출물의 지금 상태. 행 하나가 산출물 하나다. **이 대장이 산출물의 정본
목록**이다 — 폴더 구조가 아니다.

| 구분 | 공정 | 관리번호 | 산출물명 | 제출 | 제출시기 | 계획일 | 승인 1.0 | 변경 1.1 | 비고 |
|---|---|---|---|:--:|---|---|---|---|---|

<!-- form:guide -->
**무엇** — 무엇을 언제 내기로 했고, 어느 버전이 언제 승인됐는지를 적는다.
**언제** — 착수 시 목록을 세우고, 승인·변경이 있을 때마다 날짜를 채운다.
**누가** — PM 또는 형상관리 담당.

**여기 적지 않는 것**

| | 어디로 |
|---|---|
| 산출물의 **내용** | 각 산출물 문서 |
| 작업 일정 | `WBS` |
| 파일이 실제로 어디 있나 | 이 레포의 `docs/` 가 그 자리다 |

> **손으로 유지하면 반드시 샌다.** 원본 대장에서 실측한 것 — 관리번호 하나에
> 산출물이 둘(`DE_431`), 대장 번호와 파일명이 어긋난 자리가 넷, 그리고
> **회의록은 폴더·번호·실물이 다 있는데 대장에만 빠져 있었다.**
>
> 그래서 이 패키지는 **문서명을 식별자로** 쓴다. 관리번호는 속성이다.

### 작성지침

| 항목 | 작성방법 | 필수 |
|---|---|:--:|
| 구분 | 관리 / 개발 | 필수 |
| 공정 | `<단계> › <세부>`. 원본의 D1·D2·D3 를 한 칸으로 접었다 | 필수 |
| 관리번호 | 규칙은 [`관리번호.md`](../../관리번호.md). **식별자가 아니라 속성이다** | 필수 |
| 산출물명 | **이 레포 `docs/` 의 문서명과 같게** 쓴다 — 번호 접두는 빼고 | 필수 |
| 제출 | 계약상 필수면 `●` | 필수 |
| 제출시기 | 착수 시 · 분석완료 · 설계완료 · 구현완료 · 테스트완료 · 이행완료 · 사업 종료 · 수시 · 매주 · 매월 | 필수 |
| 승인 1.0 · 변경 1.1… | 승인된 날짜. 칸이 모자라면 **열을 늘린다** | 승인 시 필수 |
| 비고 | 무엇이 바뀌어서 버전이 올랐나 | 변경 시 필수 |

> **제출시기 표기를 한 가지로 쓴다.** 원본은 두 시트가 `설계 완료` 와
> `설계완료` 로 갈려 있었고, 그래서 *"설계가 끝나면 뭐가 나와야 하나"* 의
> 답이 15건과 1건으로 쪼개졌다. 빠진 하나가 하필 중간보고서였다.

### 예시 — 행

| 구분 | 공정 | 관리번호 | 산출물명 | 제출 | 제출시기 | 계획일 | 승인 1.0 | 변경 1.1 | 비고 |
|---|---|---|---|:--:|---|---|---|---|---|
| 관리 | 보고관리 › 착수보고 | `BM_111` | (예시) 착수보고서 | ● | 착수 시 | 2026-01-05 | 2026-01-05 | | |
| 관리 | 일정관리 | `BM_201` | (예시) WBS | ● | 착수 시 | 2026-01-05 | 2026-01-05 | 2026-02-10 | 범위 조정 반영 |
| 개발 | 설계 › DB설계 › 테이블정의 | `DE_431` | (예시) 테이블정의서 | | 설계완료 | 2026-03-20 | | | |

> ⚠ **예시 행이다 — 지우고 시작한다.** 관리번호는 진짜 번호를 적어 두었다.
> 규칙은 [`관리번호.md`](../../관리번호.md) 에 있고, **제출물 파일명에만**
> 앞에 사업 코드가 붙는다.
>
> 원본 대장은 WBS 의 공정을 `보고관리 › 착수보고` 로 적어 두었는데 번호가
> `BM_201`(일정관리)이다. **번호와 공정이 어긋나면 폴더를 믿는다** — 번호도
> 공정도 폴더에서 나온다. 여기 예시는 고쳐서 적었다.
>
> **이 대장을 원본 그대로 옮겨 적지 마라.** 원본 대장은 이 사업에서 고쳐야
> 할 문서다 — 번호가 겹치고, 공정이 폴더와 어긋나고, 회의록이 빠져 있다.
> 패키지의 문서 목록(`README.md`)이 이미 고친 것이고, 그것을 여기 옮긴다.
