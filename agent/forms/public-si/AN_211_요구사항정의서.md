<!-- form:head -->
요구사항의 지금 상태. 섹션 하나가 요구사항 하나다. 발주(RFP)와 현업 요구를
**한 문서에** 둔다 — ID 공간이 다르므로 충돌하지 않는다.

<!-- form:guide -->
**무엇** — 무엇을 만들기로 했는지와 **어디까지 하기로 했는지**를 건별로 적는다.
**언제** — 분석에서 만들고, 협의로 범위가 바뀔 때마다 그 섹션을 고친다.
**누가** — PM · PL 이 발주 요구를, 업무 담당이 현업 요구를 적는다.

**여기 적지 않는 것**

| | 어디로 |
|---|---|
| 그 요구를 어떤 기능으로 푸는가 | `기능정의서` |
| 화면 생김새 | `화면설계서` |
| 검증 절차 | `통합테스트시나리오` |

> **추적표를 따로 만들지 않는다.** 요구사항 → 화면 → 프로그램 → 시험의 연결은
> **작업 기록의 `touches`** 가 만든다. 원본 엑셀에는 추적 컬럼이 있었지만
> 84건 중 **0건이 채워져 있었다** — 손으로 채우는 칸은 비어 있게 된다.

### 작성지침

| 항목 | 작성방법 | 필수 |
|---|---|:--:|
| 섹션 제목 | `<요구사항ID> — <한 줄 요약>` | 필수 |
| 출처 | `RFP · <항목>` 또는 회의록 · 문서명. **어디서 나왔는지가 근거다** | 필수 |
| 유형 | 기능 / 비기능 | 필수 |
| 수용여부 | 수용 / 미수용 / 보류. 미수용이면 **왜**를 내용에 적는다 | 필수 |
| 내용 | 요구의 실체. 배경이 있으면 같이 | 필수 |
| 검사기준 | 무엇을 보면 됐다고 할 수 있나 | 선택 |
| 협의 | `**협의** · 날짜 <결정>`. 범위가 바뀐 기록 | 바뀌면 필수 |
| 경과 | `**경과**` 아래 한 줄 `- 날짜 [작업 기록](../work/…) 무엇이` | 반영 때 필수 |

### 예시 — EX-SFR-01-01 — 반응형 웹 지원

| | |
|---|---|
| 출처 | RFP · `EX-SFR-01` 시스템 구축 기본사항 |
| 유형 | 비기능 |
| 식별일자 | 2026-01-05 |
| 수용여부 | 수용 |

**내용** — 최신 UI/UX 프레임워크 기반의 반응형 웹으로 구축한다. 5대 주요
브라우저에서 동작해야 한다.

**검사기준** — 통합테스트에서 브라우저 5종 · 해상도 3종으로 확인한다.

**협의** · 2026-01-20 IE 는 대상에서 제외하기로 합의(발주처 확인).

<!-- 현업 -->

### 예시 — EX-USR-RP-01 — 참여율 이력 관리

| | |
|---|---|
| 출처 | `회의록 2026-01-05 착수미팅` |
| 요청자 | 전산총무팀 |
| 유형 | 기능 |
| 수용여부 | 수용 |

**내용** — 과제 참여 인력이 중도 이탈하면 참여율을 기간 기준으로 분할해야
한다. 지금은 덮어써서 이력이 남지 않는다.

**협의** · 2026-02-04 연구계획서 참여율과 평가 참여율을 **구분해서** 관리하기로.

> ⚠ **두 섹션 다 예시다 — 지우고 시작한다.**

### 예시 — 어휘

```
## 요구사항

- `요구사항:EX-SFR-01-01` — (예시) 반응형 웹 지원
  example: 서식 예시 — 지우고 시작한다
  aliases: 반응형, 모바일 지원
- `요구사항:EX-USR-RP-01` — (예시) 참여율 이력 관리
  example: 서식 예시 — 지우고 시작한다
  aliases: 참여율 이력, 참여율
```
