# cdp-work — 요청 하나를 CDP 절차로 수행한다

이 skill 은 **요청 하나**를 세 단계로 처리한다. 순서를 바꾸지 말고, 단계를 건너뛰지 마라.

```
① 검토       요청을 이해하고 대상을 뽑는다.  지식 레포 본문은 읽지 않는다
② 주입       필요하면 관리 문서 섹션을 읽어 맥락으로 삼는다
③ 요청수행   주입된 상태를 근거로 요청을 수행한다
```

**요청된 작업이 우선이다.** 절차는 그것을 돕는 것이고, 절차 자체가 산출물이 되면 실패다.

## 준비 — 지식 레포 위치

지식 레포는 프로젝트 레포의 `CLAUDE.md` 에 경로가 적혀 있다. 없으면 상위 폴더에서
`_vocab.md` 와 `_managed.md` 를 가진 폴더를 찾는다. 그래도 못 찾으면 **사용자에게 묻고 멈춘다** —
경로를 모르면 이 skill 이 할 수 있는 것이 없다.

이하에서 `<repo>` 는 그 경로다.

> **`ctx` 호출은 MCP 도구 `cdp:*` 가 있으면 그것으로, 없으면 `<repo>/bin/ctx …` 로.
> 둘은 같은 함수다** — 결과가 바이트까지 같다(MCP 설계서 §3.3 · §10). 아래 예시는
> CLI 로 적혀 있고, 도구가 있으면 같은 이름의 도구를 부른다.
>
> | 이름이 다른 것 | 도구 |
> |---|---|
> | `ctx where <좌표>` 뒤에 섹션을 Read | `where` → **`section`**. 파일을 열지 않는다 |
>
> **`save` 도구가 있으면 서버 모드다**(§4.8). 그때는 쓰기 경로가 바뀐다 —
>
> | | `save` 없음 (모드 A) | `save` 있음 (모드 B) |
> |---|---|---|
> | 시작 | `git pull --ff-only` | **생략.** 서버가 언제나 origin HEAD 다 |
> | 고치기 | Write · Edit 로 파일에 | **메모리에 준비해 사람에게 보인다.** 파일을 안 만든다 |
> | 끝 | `git commit` → 커밋 훅이 검사 | `save({ work, sections, vocab })` **한 번.** 서버가 검사하고 커밋한다 |
> | 충돌 | 훅이 막는다 | `E_CONFLICT` 면 `section` 을 **다시 읽고 다시** 만든다 |
>
> 훅은 모드 A 에서만 돈다. 모드 B 는 클라이언트에 작업 트리가 없다.

## ① 검토

### 하는 일

1. **요청을 한 줄로 요약한다.** 무엇을 해달라는 것인가.

2. **대상 후보를 뽑는다.** 요청문·`git diff`·열려 있는 파일에서 이름을 긁는다.
   테이블명·화면 코드·API 경로·모듈명·도메인 용어·코드그룹.

3. **이름을 정본 좌표로 대조한다.**

   ```
   <repo>/bin/ctx match "면접심사의견등록" "PS130" "서류심사"
   ```
   ```
   면접심사의견등록  ->  screen:PSC043  (이름 일치 · _vocab.md:70)
   PS130             ->  code:PS130     (값 일치 · _vocab.md:112)
   서류심사          ->  screen:PSC031  (alias 일치 · _vocab.md:68)
   ```

   **타입 이름을 짐작하지 마라.** 위 출력의 `screen:` · `code:` 는 이 예시
   레포의 것이고, 타입은 `_vocab.md` 가 정한다 — 관리문서 이름을 한글로 쓰는
   레포도 있다(`화면설계서:PSC043`). `ctx match` 가 그 레포의 정본을 돌려준다.

   **Node 가 없어도 된다** — `bin/ctx` 가 `tools/cdp.exe` 로 넘긴다.
   `(미등재)` 로 나오면 어휘에 없는 것이다. 그대로 두고 ①의 출력에 적어라 —
   커밋 때 `ctx check` 가 막는다. 여기서 임의로 다른 좌표로 바꾸지 마라.

   **폐기 좌표를 쓰면 후속을 알려준다.** 그러면 후속 좌표를 쓴다.
   ```
   연심회의견상세  ->  table:rp_rdc_opl_dtl  [폐기 2026-03-26 -> table:rp_rdc_opl_mst]
   ```

   `bin/ctx` 가 아예 없는 레포라면 `_vocab.md` 를 직접 읽어 대조한다.
   그 파일은 사람이 읽는 마크다운이고 `aliases:` 줄에 별칭이 있다.

4. **각 대상이 좌표인지 판정한다.**

   | 이 작업이 그 대상을… | 좌표 |
   |---|:--:|
   | 신설했다 | **O** |
   | 변경했다 (컬럼 추가, 규격 변경, 상태값 추가) | **O** |
   | 삭제·폐기했다 | **O** |
   | 참조했다 · 호출했다 · 언급했다 | **X** |
   | 그것을 쓰는 다른 것을 만들었다 | **X** |

   판정 기준은 하나다 — **6개월 뒤 그 대상을 맡은 사람이 이 작업을 찾아야 하는가.**
   "주제인가?"는 답이 갈리지만 **"바꿨는가?"는 결판난다.**

5. **`(미등재)` 가 나온 말이 있으면 `ctx search` 로 후보를 넓힌다.**

   ```
   <repo>/bin/ctx search 지출결의서 입출금계좌코드 거래처코드
   ```
   ```
   api:/adapter/a10/expense-slip
       걸린 말  지출결의서 · 입출금계좌코드 · 거래처코드   (섹션)
       docs/인터페이스정의서.md
       2026-0908-A10-결의서-예금-계좌연동
   ```

   **왜 필요한가.** `ctx match` 는 `_vocab.md` 의 이름·alias 만 본다 — 즉
   **자연어 도메인 용어가 alias 로 등재돼 있어야만 걸린다.** 등재가 얇으면
   요청문의 핵심 명사가 전부 `(미등재)` 로 떨어지고, 그러면 주입할 좌표가
   없다. **답을 가진 섹션이 레포에 멀쩡히 있는데도 빈손으로 돌아온다.**

   실제로 밟은 사례 — *"결의서 결제수단 디폴트"* 요청에서 `결제수단` ·
   `과세구분` · `채주유형` 만 걸렸다. 그 셋은 **코드값 목록이라 요청문이 이미
   전부 나열해 놓은 것**이고, 답은 `api:/adapter/a10/expense-slip` 섹션에
   있었다. 좌표 이름이 API 경로여서 요구사항서의 어떤 단어와도 이어지지
   않았다.

   `ctx search` 는 **좌표 이름만** 낸다. 본문은 싣지 않으므로 아래의 편향
   금지를 깨지 않는다 — 본문은 ②에서 `cdp-load` 가 읽는다.

   후보가 나오면 4번의 판정을 그 후보에도 적용한다. **후보를 그대로 다
   주입하지 마라.**

6. **주입할 좌표를 정한다.**
 좌표로 판정된 것 중, **그 대상의 현재 상태를 모르면
   요청을 수행할 수 없는 것**만. 애매하면 넣되 **후보를 늘리지 마라** — 많이 주입할수록
   요청의 해석이 그 맥락에 편향된다.

### 출력

판정을 낸 뒤, **주입할 좌표에 대해 자리를 한 번에 묻는다.**

```
<repo>/bin/ctx where screen:PSC043 code:PS130
```

좌표 여럿을 한 번에 받아 **어느 문서 어느 섹션인지와 그 섹션의 크기**를 준다.

### 형태

```
【검토】
요청  PSC043 면접심사의견등록에 심사위원 연대서명 출력물을 추가한다

대상
  screen:PSC043      변경   출력물 2종 추가
  code:PS130         ?      업무구분 코드를 쓸지 미정
  screen:PSC031      참조   첨부를 읽어오지만 PSC031 은 안 바뀜 → 좌표 아님

주입  2건 — 각 좌표의 **섹션 하나씩**이다 (문서 전체가 아니다)

  screen:PSC043   docs/화면설계서.md  ## PSC043
                  22줄 · 약 610자 · 반영 2026-0821-면접심사의견-개편
  code:PS130      docs/코드정의서.md  ## PS130
                  9줄 · 약 88자 · 아직 실린 작업 없음

  viewer: 검색창(Ctrl+K)에 좌표를 붙여 넣으면 그 문서로 간다.
          섹션은 오른쪽 목차에서 고른다
```

- **좌표 아닌 것도 적는다.** 무엇을 왜 제외했는지가 판정의 근거다
- 애매한 것은 **`?`** 로 두고 단정하지 마라
- 주입할 것이 없으면 `주입  없음` 한 줄

### 주입 범위를 반드시 적는다

**좌표 이름만 늘어놓지 마라.** 그러면 읽는 사람은 *"그 좌표에 관한 것이 전부
들어온다"* 고 읽는다. 실제로 들어오는 것은 **섹션 하나**다 — 그 문서의 다른
섹션도, 그 좌표를 건드린 작업 기록도 안 들어온다.

| 반드시 적을 것 | 왜 |
|---|---|
| **문서 경로와 섹션 앵커** | 사용자가 viewer 나 편집기에서 그 자리를 열 수 있다 |
| **섹션 크기**(줄·글자) | 그것이 문서 전체가 아니라 한 조각임이 눈에 보인다 |
| **상태**(`반영 <id>` · `파생 남음` · `아직 실린 작업 없음`) | 지금 실린 것이 언제 것인지 |
| `** 사실상 비어 있다` | `ctx where` 가 그렇게 말하면 **그대로 옮겨 적어라.** 아래 |
| **작업 기록 id** | 제목이 요청과 겹치는 것이 있으면 **그것을 적어라.** 아래 |

**빈 섹션을 조용히 주입하지 마라.** 등록부에 걸리는데 섹션이 비어 있으면
주입은 성공하고 내용은 없다. 그 상태에서 답하면 *"레포에 정의가 없다"* 를
*"제약이 없다"* 로 바꿔 읽게 된다 — 확신 있게 틀린 답이 나온다.

```
  screen:ACA011   docs/화면설계서.md  ## ACA011
                  3줄 · 약 12자 · ** 사실상 비어 있다
                  → 이 화면의 현재 규칙은 문서에 없다. 코드에서 읽어야 한다
```

### 요청이 이미 결정된 것인지 본다

`ctx where` 가 좌표마다 **작업 기록 id 를 최신 3건까지** 낸다. CDP 의 id 는
`날짜-주제` 라서 **id 만으로 주제가 읽힌다.** 요청과 겹치는 것이 있으면
검토에 적어라.

```
  api:/adapter/a10/expense-slip
      2026-08-31  2026-0831-A10-결의서-기본값    ← 요청과 같은 주제다
```

**이것을 놓치면 이미 정해진 것을 처음부터 다시 정하는 작업이 시작된다.**
실제로 그렇게 됐다 — *"결제수단·과세구분·채주유형 디폴트를 정해라"* 는
요청이 두 번 왔고, 첫 번째가 남긴 기록의 id 가 검토에 떠 있었는데도
아무도 그것을 읽지 않았다.

id 는 **이름**이라 읽어도 요청 해석이 편향되지 않는다. 본문은 ②에서 읽는다.
겹쳐 보이면 ③의 답변을 *"새로 정하자"* 가 아니라 **"이미 이렇게 정해져 있다.
이번 요청과 다른 부분은 이것뿐이다"** 로 시작하라.

관리 문서가 없는 타입(`module:` · `domain:`)은 자리 대신 근거를 적는다.

```
  module:date-range   등록부에 없음 — 관리 문서가 없는 타입 (정상)
                      작업 기록 최신 3건까지 주입 (총 5건 · 2건은 절단)
```

### 금지

- **`<repo>/docs/` 와 `<repo>/work/` 를 읽지 마라.** 이 단계에서 읽어도 되는 것은
  `_vocab.md` 와 `_managed.md` 뿐이다. `ctx search` 는 본문을 훑지만 **좌표
  이름만 돌려주므로** 써도 된다 — 이름표는 요청 해석을 편향시키지 않는다.
  어휘·등록부는 **이름표**라서 읽어도 요청 해석이 편향되지 않지만,
  관리 문서와 작업 기록은 **의견을 담으므로** 요청을 이해하기 전에 읽으면
  그 틀로 요청을 읽게 된다.

- **검토를 출력한 뒤 멈추지 마라.** 승인을 구하지 말고 바로 ②로 간다.
  판정이 틀렸으면 ③의 답변에서 드러나고 그때 사용자가 고친다.
  **모든 요청에 정지를 거는 비용이 잘못된 주입의 비용보다 크다.**

- **길게 쓰지 마라.** 검토가 답변보다 길면 절차가 작업을 잡아먹은 것이다.

### 압축·생략

| 상황 | |
|---|---|
| 사용자가 대상을 이미 명시 (*"PSC043 화면에…"*) | 대상 한 줄로 압축 |
| 좌표 후보가 0개 | `주입  없음` 만 적고 ③으로 |
| **요청이 크고 모호** (*"채용 쪽 정리해줘"*) | **여기서 되묻고 멈춘다.** ②③으로 가지 마라. 맥락 문제가 아니라 요청 문제다 |

## ② 주입

①에서 정한 좌표가 있을 때만 한다. 없으면 건너뛰고 ③으로 간다.

### 먼저 최신인지 본다 — 받지는 않는다

```
<repo>/bin/ctx sync
```

`받을 것 N건` 이 있으면 **주입 전에 알린다.**

```
⚠ 받을 것이 3건 있습니다. 지금 주입하는 섹션이 최신이 아닐 수 있습니다.
   먼저 받을까요?
```

**여기서 주입한 것이 ③ 전체의 근거가 된다.** 동료가 오늘 아침 그 섹션을
고쳤는데 모르고 설계하면, 끝에 가서 `cdp-save` 가 pull 할 때야 안다 —
그때는 이미 만든 뒤다.

pull 을 강제하지는 않는다. ff 가 안 될 때 **보는 것조차 막히면** 과하다.
낡았다는 사실만 알면 사람이 판단한다.

**`cdp-load` skill 을 부를 수 있으면 부른다.**

```
cdp-load screen:PSC043 code:PS130
```

**부를 수 없으면 `<repo>/.claude/skills/cdp-load/SKILL.md` 를 읽어 그 절차를 그대로 따른다.**
지시문이지 API 가 아니므로 사람이나 다른 LLM 도 따라갈 수 있다.

좌표 하나만 빠르게 보려면 `ctx where` 가 더 싸다.

```
<repo>/bin/ctx where table:ps_ext_emp_mst
```
```
table:ps_ext_emp_mst
  문서   docs/테이블정의서.md
  섹션   ## ps_ext_emp_mst
  상태   파생 남음 — 작업 2건 (ctx apply table:ps_ext_emp_mst)
  주입   그 섹션만 — 18줄 · 약 520자 (docs/테이블정의서.md:839)
```

`주입` 줄이 **들어오는 것의 범위**다. 그 문서의 다른 섹션은 안 들어온다.

주입 결과에서 **반드시 확인해야 하는 것**:

| | |
|---|---|
| **파생 남음** | `ctx where` 가 그렇게 답하면 **그 사실을 ③의 답변에 포함하라.** 안 채워진 섹션은 낡은 것보다 나쁘다 — 확신 있게 틀린 답을 준다 |
| **좌표별 후속** | 작업 기록을 근거로 쓸 때, 그 기록의 어느 좌표 부분이 최신인지 따로 본다. "이 문서는 낡았다"가 아니라 "이 문서의 `table:X` 부분은 이후 3건이 더 있다" 로 판단하라 |
| **절단** | 매칭됐으나 주입되지 않은 것이 있으면 그것도 답변에 적는다 |
| **빈 섹션** | `** 사실상 비어 있다` 가 나오면 **답변에 그대로 옮긴다.** 주입은 성공하고 내용은 없는 상태다 — 밝히지 않으면 *"정의가 없다"* 가 *"제약이 없다"* 로 읽힌다 |

---

## ③ 요청수행

**주입된 상태를 근거로 요청을 수행한다.** 요청이 요구한 것이 코드든 답변이든 문서든 분석이든,
그것을 낸다. 이 단계에 정해진 산출물 형태는 없다.

지켜야 할 것 셋:

1. **주입된 것을 근거로 쓴다.** 관리 문서 섹션이 현재 상태이므로 그것과 어긋나게
   설계하지 마라. 어긋나야 한다면 왜 그런지 답변에 적어라.

2. **파생 남음·후속·절단을 답변에 옮긴다.** ②에서 확인한 것을 사용자가 알아야 한다.

   ```
   ⚠ 테이블정의서의 ps_ext_emp_mst 섹션에 파생이 2건 남아 있습니다.
      아래 설계는 아직 안 채워진 상태를 기준으로 한 것이므로,
      2026-0902·2026-0903 작업 내용을 확인하는 것이 좋습니다.
   ```

3. **"왜"가 필요해지면 그때 작업 기록을 연다.** *"이 컬럼이 왜 nullable 이지"* 같은
   질문이 생기면 섹션의 변경 줄이 어느 작업 기록을 볼지 알려준다.
   ②에서 미리 다 읽지 않는다.

---

## 이 skill 을 다시 부르지 않는 경우

**작업 주제가 그대로면 다시 부르지 마라.** 이미 주입된 맥락을 쓴다.
매 턴 부르면 같은 섹션이 반복 주입되고 절차가 소음이 된다.

다시 부르는 것은 **작업 주제가 바뀔 때**다 — 다른 화면, 다른 테이블로 넘어갈 때.

## 작업이 끝나면

이 skill 은 **기록하지 않는다.** 요청 여러 개가 한 작업일 수 있으므로,
작업이 끝난 시점에 **`cdp-save` 를 따로 부른다.**

```
요청1 → cdp-work
요청2 → cdp-work
요청3 → cdp-work
        ──────────
        작업 종료 → cdp-save  (한 번)
```

# 실사용 예시

## 예시 1 — 화면 하나를 고친다

### 사용자

> 출장복명작성 화면에 차량 안 가져간 사람용 사진 첨부 넣어 줘.

### ① 검토

지식 레포 본문은 아직 읽지 않는다. **이름만 뽑는다.**

```
$ C:\cdp\bin\ctx match "출장복명작성"
출장복명작성  ->  screen:EXD020  (alias · _vocab.md:118)
```

```
【대상】
  screen:EXD020    출장복명작성 — 이 화면을 바꾼다
```

### ② 주입

```
$ C:\cdp\bin\ctx sync
브랜치  main  ->  origin/main
차이    받을 것 0건 · 보낼 것 0건          ← 최신이다. 그대로 간다
```

```
$ C:\cdp\bin\ctx where screen:EXD020
screen:EXD020
  문서   docs/화면설계서.md
  섹션   ## EXD020
  상태   반영 2026-0821-출장복명-입력영역
  작업   1건
```

섹션을 읽는다.

```markdown
## EXD020 — 출장복명작성
<!-- applied: 2026-0821-출장복명-입력영역 -->

출장복명작성.

**화면 내 입력 영역을 별도로 구축한다.** 이유 셋 —

- 본인이 출장자가 아닌 경우 화면이 너무 길어 입력해야 하는 줄
  모르고 넘어간다
- 스크롤이 생기지 않게 해야 한다
- 차를 안 가져간 사람이 사진을 붙이려는데 **붙일 곳이 없어서**
  복명만 하고 담당자에게 전화했다
```

**여기서 결정적인 것이 나왔다.** 세 번째 줄이 지금 요청의 배경 그 자체다.
이걸 모르고 작업하면 "사진 첨부를 어디에 둘까" 를 처음부터 다시 고민하고,
이미 만들어 둔 입력 영역과 따로 노는 자리에 붙일 수 있다.

### ③ 수행

```
입력 영역 안, 복명 내용 아래에 첨부를 답니다. 이미 그 이유로 입력 영역을
따로 만들어 둔 화면이라 같은 영역 안에 두는 것이 맞습니다.

(구현 …)

⚠ 참고 — 이 섹션은 반영이 최신입니다(파생 남음 없음).
```

작업이 끝나면 **`cdp-save` 한 번.**

## 예시 2 — 요청 셋이 작업 하나다

### 사용자 (같은 세션에서 이어서)

> 1. 첨부는 여러 장 되게
> 2. jpg png 만 받자
> 3. 아 그리고 입력 영역을 맨 위로 올려 줘

### 어떻게 하나

**셋 다 같은 화면의 같은 작업이다.** `cdp-work` 을 세 번 돌리지 않는다 —
①에서 뽑은 좌표가 같으면 ②는 이미 주입돼 있고, ③만 이어서 한다.

기록도 **하나**다. 요청마다 기록하면 이력이 파편화되고, 같은 좌표에 남은
기록들이 서로의 후속이 되어 파생 판정이 시끄러워진다.

```
        요청 1 ─┐
        요청 2 ─┼─→ 작업 하나 → cdp-save 한 번 → 기록 하나
        요청 3 ─┘
```

---

## 예시 3 — 좌표가 없는 요청

### 사용자

> 이 정규식이 왜 안 먹지? `^[A-Z]{3}\d{3}$`

### 어떻게 하나

**`cdp-work` 을 부르지 않는다.** 지식 레포와 무관하다 — 프로젝트의 테이블·
화면·API·용어·코드 상태를 알 필요가 없는 요청이다.

①에서 대상이 0개면 ②를 건너뛰고 ③으로 간다. 그리고 이런 요청은 애초에
skill 이 발동하지 않는 것이 맞다.

**억지로 좌표를 붙이지 마라.** `screen:EXD020` 을 다루는 코드 안의 정규식
이라 해도, 그 정규식을 고치는 것이 화면 사양을 바꾸는 것은 아니다.

## 예시 4 — 받을 것이 있을 때

```
$ C:\cdp\bin\ctx sync
차이    받을 것 3건 · 보낼 것 0건
```

```
⚠ 받을 것이 3건 있습니다. 지금 주입하는 섹션이 최신이 아닐 수 있습니다.
   먼저 받을까요?
```

받으면 그 뒤에 주입한다. 안 받겠다고 하면 **주입은 하되 답변에 적는다** —

```
⚠ 원격에 3건이 있는데 받지 않은 상태로 설계했습니다. cdp-save 가 시작할 때
   pull 하므로, 그때 EXD020 섹션이 달라져 있으면 다시 봐야 합니다.
```
