# cdp-edit — 지시로 관리 문서를 고치고, 그 지시를 남긴다

```
① pull        쓰기 전에 받는다.  실패하면 시작하지 않는다
② 현재 상태    고칠 섹션을 읽는다 (cdp-load 와 같다)
③ 지시 확인    어긋나면 되묻는다.  **그대로 실행하지 않는다**
④ 문서 수정    관리 문서 섹션
⑤ 작업 기록    **지시가 곧 본문이다**
⑥ 한 커밋      작업 기록 1 + 관리 문서 N.
               모드 A: push 는 하지 않는다 (사람이 누른다)
               모드 B: `save` 한 번 — 서버가 커밋하고 미러로 보낸다. push 안내 없음
```

> **본문의 호출은 MCP 도구다.** `cdp` 서버가 붙어 있으면 `match(...)` 처럼
> 그대로 부른다 — 모드 A(stdio)든 모드 B(HTTP)든 같다. 도구가 없는 자리
> (커밋 훅 · 사람이 터미널에서 칠 때)는 맨 끝 **「도구가 없을 때」** 를 본다.
> 둘은 같은 함수라 결과가 바이트까지 같다(MCP 설계서 §3.3 · §10).
>
> **`save` 도구가 있으면 서버 모드다**(§4.8). 그때는 쓰기 경로가 바뀐다 —
>
> | | `save` 없음 (모드 A) | `save` 있음 (모드 B) |
> |---|---|---|
> | 시작 | `git pull --ff-only` | **생략.** 서버가 언제나 origin HEAD 다 |
> | 고치기 | Write · Edit 로 파일에 | **메모리에 준비해 사람에게 보인다.** 파일을 안 만든다 |
> | 끝 | `git commit` → 커밋 훅이 검사 | `save({ work, sections, vocab })` **한 번.** 서버가 검사하고 커밋한다. `sections[].body` 는 `section` 의 **`content`**(헤딩 · applied 없이) — 헤딩을 넣으면 E_INPUT |
> | 충돌 | 훅이 막는다 | `E_CONFLICT` 의 `detail.content`(지금 본문) 위에 **다시 만들어** `applied` 에 `detail.current` 를 넣어 보낸다 — `section` 을 다시 부르지 않는다(`truncated` 일 때만) |
>
> 훅은 모드 A 에서만 돈다. 모드 B 는 클라이언트에 작업 트리가 없다.

---

## 왜 기록이 필요한가

관리 문서만 고치면 **출처 없는 변경**이 된다.

```
$ git log -p docs/화면설계서.md
  + 사진 첨부는 10MB 까지.
```

6개월 뒤 "왜 10MB 인가" 를 물으면 답할 것이 없다. 커밋 메시지 한 줄은
diff 를 설명할 뿐 **왜 그렇게 정했는지**를 담지 못한다. 그것을 담는 자리가
`work/` 이고, 그것이 이 레포가 두 층인 이유다.

  docs/   지금 어떤 상태인가   ← 고친다
  work/   무슨 일이 있었나     ← **지시가 그 사건이다**

그리고 실무적으로도 필요하다. 섹션의 `<!-- applied: … -->` 는 작업 기록을
가리키는데, 가리킬 기록이 없으면 섹션은 옛 기록을 가리킨 채 남는다 —
내용은 새것인데 출처는 옛것을 가리키는 상태다.

---

## ① pull

> **모드 B 면 이 절은 없다.** `save` 도구가 있으면 받을 것이 없다 — 서버 트리가
> 그 레포의 유일한 작성자이고 언제나 origin HEAD 다. 다음 절로 간다.

```
git -C <repo> pull --ff-only
```

실패하면 멈춘다. 남이 이미 그 섹션을 고쳤을 수 있다.

---

## ② 현재 상태를 읽는다

```
where("<좌표>")
```

섹션 본문과 `applied`, 그리고 **파생이 남아 있는지**를 본다.

파생이 남아 있으면 사용자에게 먼저 알린다 —

```
⚠ 이 섹션에 파생이 2건 남아 있습니다 (2026-0902 · 2026-0903).
   지시하신 수정을 그 위에 얹으면 남은 것이 묻힙니다.
   먼저 cdp-managed 로 채울까요?
```

---

## ③ 지시를 확인한다 — 그대로 실행하지 않는다

**지시가 현재 문서와 어긋나면 되묻는다.**

| 어긋남 | 어떻게 |
|---|---|
| 지시가 이미 적힌 것과 다르다 | 무엇이 맞는지 묻는다. 조용히 덮지 않는다 |
| 지시가 좌표를 특정하지 않는다 | `ctx match` 로 후보를 보이고 고르게 한다 |
| 지시가 등록부 밖 문서를 가리킨다 | 회의록·일정 등은 좌표-섹션이 없다. 그냥 고치고 기록은 남기지 않는다 |
| 사실 관계를 모른다 | **묻는다.** 문서는 정본이라 틀리면 조용히 퍼진다 |

지시가 **아직 결정이 아닌 경우**도 있다. "이렇게 하면 어떨까?" 는 지시가
아니다. 그때는 고치지 말고 위험및이슈관리대장으로 보낸다.

---

## ④ 문서 수정

해당 섹션만 고친다. `<!-- applied: … -->` 는 ⑤ 의 기록 id 로 바꾼다.

**섹션 밖을 건드리지 마라.** 지시 하나가 문서 여러 곳을 바꿔야 한다면 그것은
좌표가 여럿인 것이고, `touches` 에 전부 적는다.

**그림 · pdf 를 넣으라는 지시**("구성도 넣어줘", "이 캡처 붙여줘")면 파일은 `work/assets/<⑤ 의 id>/` 에 두고
섹션에는 `![설명](../work/assets/<id>/<이름>)` 을 적는다. 모드 A 는 복사해 ⑥ 의 커밋에 같이, 모드 B 는 올려서
받은 `ref` 를 `save` 의 `assets` 에 — `cdp-save` 「그림 · 첨부」 그대로다. 사람에게 레포를 받아 올리라고 하지 않는다.

---

## ⑤ 작업 기록 — 지시가 곧 본문이다

```
<repo>/work/YYYY-MMDD-slug.md
```

`date` 는 **지시받은 날**이다. 그날 그 결정이 있었다.

```markdown
---
id: 2026-0908-BZD020-첨부용량
title: BZD020 사진 첨부 용량 10MB — 문서 반영
date: 2026-09-08
author: dev.a
touches:
  - screen:BZD020
tags: [문서반영]
---

# BZD020 사진 첨부 용량

## 지시

> 사진 첨부 용량은 10MB 로 해줘. WAS 업로드 상한이 그거라서 20MB 로
> 적어 놔도 어차피 안 올라가.

dev.a, 2026-09-08.

## 반영

`docs/화면설계서.md` `## BZD020` 의 첨부 표에서 용량을 20MB → 10MB.

## 확인한 것

기존 섹션에 20MB 로 적혀 있었다. 어디서 온 값인지 `2026-0908-사진첨부-용량`
을 확인했고, 회의에서 나온 말을 옮긴 것이지 WAS 설정을 본 것이 아니었다.
```

### 세 대목이 필요하다

| | |
|---|---|
| **지시** | **말한 그대로 인용한다.** 요약하지 마라 |
| **반영** | 어느 문서 어느 섹션을 어떻게 바꿨나 |
| **확인한 것** | 되물은 것, 근거를 확인한 것, 판단한 것 |

**지시를 요약하지 않는 이유** — 말의 표현 자체가 맥락이다. "20MB 로 적어
놔도 어차피 안 올라가" 는 *제약이 어디서 왔는지*를 담고 있고, 그것을
"10MB 로 변경" 으로 줄이면 6개월 뒤 "왜 10인가" 에 다시 답할 수 없다.

`author` 는 **지시한 사람**이다. 문서를 고친 것은 에이전트지만 정한 것은
사람이다.

### 지시가 여럿이면

한 세션에서 여러 섹션을 고치라는 지시를 받았다면 —

- **한 주제면 기록 하나.** `touches` 에 좌표를 여럿 적는다
- **다른 주제면 기록을 나눈다.** 6개월 뒤 따로 찾을 것이면 따로다

---

## ⑥ 한 커밋

> **모드 B 면 이 절을 건너뛰고 `save` 도구 한 번으로 끝낸다.** 커밋할 작업
> 트리가 클라이언트에 없고 훅도 없다. 인자 모양과 `E_CONFLICT` 대처는
> **`cdp-save` 의 ⑤B** 에 있다 — 여기서 되풀이하지 않는다. **끝 보고도 거기 「모드 B 의
> 종료 보고」 표를 따른다** — `save` 응답의 `commit` · `mirror` · `mirrorReason` 만 근거로 말하고,
> 「push 하지 않았다」 · 「push 하세요」 는 말하지 않는다.

**모드 A 만:**

```
git -C <repo> add work/<id>.md docs/<...>.md
git -C <repo> commit -m "<제목>"
```

**push 는 하지 않는다.** 사람이 누른다. (모드 B 에는 해당 없다.)

---

## 이것을 건너뛰면 무엇이 깨지나

관리 문서만 고치고 기록을 안 남기면 `ctx check` 는 **아무 말도 하지 않는다.**
파생 누락 검사는 작업 기록을 기준으로 도는데, 기록이 없으면 기준이 없다.

**즉 이 절차는 기계가 막아 주지 않는다.** 그래서 skill 로 둔다 — 2층이
못 잡는 자리이므로 1층이 지켜야 한다.

# 실사용 예시

## 예시 1 — 값 하나를 고친다

### 사용자

> 사진 첨부 용량은 10MB 로 해줘. WAS 업로드 상한이 그거라서 20MB 로
> 적어 놔도 어차피 안 올라가.

코드 작업은 없다. **문서만 고친다.**

### ① pull · ② 현재 상태

```
$ git -C C:/cdp pull --ff-only
Already up to date.

where("screen:BZD020")
screen:BZD020
  문서   docs/화면설계서.md
  섹션   ## BZD020
  상태   반영 2026-0921-B-첨부제한
```

섹션을 읽으니 이렇게 적혀 있다.

```markdown
| 사진 첨부 | |
|---|---|
| 용량 | 한 건당 20MB |
```

### ③ 확인한다

**어긋난다.** 지시는 10MB, 문서는 20MB. 조용히 덮지 않고 어디서 온
값인지 본다.

```
where("screen:BZD020")
    2026-09-21  2026-0921-B-용량
```

그 기록을 열어 보니 회의에서 나온 말을 옮긴 것이고 **WAS 설정을 본 것이
아니었다.** 지시 쪽에 근거가 있다.

### ④ 문서 수정

```markdown
## BZD020 — 출장보고작성
<!-- applied: 2026-0922-BZD020-첨부용량 -->      ← ⑤ 의 기록 id 로

| 사진 첨부 | |
|---|---|
| 용량 | 한 건당 **10MB** — WAS 업로드 상한 |
```

**근거를 함께 적었다.** 숫자만 있으면 다음 사람이 또 올린다.

### ⑤ 작업 기록 — 지시가 곧 본문이다

`C:/cdp/work/2026-0922-BZD020-첨부용량.md`

```markdown
---
id: 2026-0922-BZD020-첨부용량
title: BZD020 사진 첨부 용량 10MB — 문서 반영
date: 2026-09-22 10:15
author: dev.a
touches:
  - screen:BZD020
tags: [문서반영, 출장]
---

# BZD020 사진 첨부 용량

## 지시

> 사진 첨부 용량은 10MB 로 해줘. WAS 업로드 상한이 그거라서 20MB 로
> 적어 놔도 어차피 안 올라가.

dev.a, 2026-09-22.

## 반영

`docs/화면설계서.md` `## BZD020` 의 사진 첨부 표에서 용량 20MB → 10MB.
근거(WAS 상한)를 함께 적었다.

## 확인한 것

앞서 `2026-0921-B-용량` 이 20MB 로 적어 두었다. 어디서 온 값인지 확인했더니
회의에서 나온 말을 옮긴 것이고 WAS 설정을 본 것이 아니었다.
```

### 왜 인용인가

**"10MB 로 변경" 으로 줄이면 안 되는 이유** —

```
줄인 것    사진 첨부 용량을 10MB 로 변경했다
            → 6개월 뒤 "왜 10인가" 에 답할 수 없다
            → 누가 "20으로 늘리자" 고 하면 막을 근거가 없다

인용한 것  "WAS 업로드 상한이 그거라서 20MB 로 적어 놔도 어차피 안 올라가"
            → 제약이 WAS 에 있다는 것이 남는다
            → 늘리려면 WAS 를 먼저 봐야 한다는 것까지 따라온다
```

**말의 표현 자체가 맥락이다.**

### ⑥ 커밋

```
$ git -C C:/cdp add work/2026-0922-BZD020-첨부용량.md docs/화면설계서.md
$ git -C C:/cdp commit -m "BZD020 첨부 용량 10MB — 문서 반영"
[main 4c3e9b2] BZD020 첨부 용량 10MB — 문서 반영
 4 files changed, 44 insertions(+), 5 deletions(-)
```

## 예시 2 — 되물어야 하는 경우

### 사용자

> 화면설계서에 BZA021 버튼 이름 '추가' 로 바꿔 줘.

### 확인

```
where("screen:BZA021")
```

섹션에 이렇게 적혀 있다.

```markdown
버튼 명칭은 **'선택'** 이다 — '추가' 가 아니다.
```

그리고 그 근거가 작업 기록에 있다.

> 동작이 새로 만드는 것이 아니라 **이미 있는 외부인원을 고르는 것**이다.
> `추가` 라고 쓰면 여기서 사람을 등록할 수 있다고 읽힌다.

### 되묻는다

```
⚠ 지금 문서는 '선택' 이고, 그렇게 정한 이유가 적혀 있습니다 —

   "동작이 새로 만드는 것이 아니라 이미 있는 외부인원을 고르는 것이다.
    '추가' 라고 쓰면 여기서 사람을 등록할 수 있다고 읽힌다."
   (2026-0902-BZA021-외부심의위원)

   '추가' 로 되돌리는 것이 맞습니까? 맞다면 그 이유를 기록에 남기겠습니다.
```

**조용히 덮지 않는다.** 정본을 뒤집는 것이므로 근거가 필요하고, 그 근거가
다음 기록의 본문이 된다.

```
지금 기록해 두려면 위험및이슈관리대장으로 보내겠습니다 — 결정 대기 항목은
거기가 자리입니다.
```

## 예시 4 — 등록부 밖 문서 · 머리말을 고치라고 할 때

### 사용자

> 회의록 문서에 다음 회의 일자 좀 적어 줘.
> (또는) 회의록 머리말의 「등록부 비대상」 문구를 고쳐 줘.

`docs({ doc: "회의록" })`(관리번호 `BM_411` 도 된다)으로 먼저 본다 — `registered: false` 면 **등록부 비대상**이다. 좌표-섹션이
1:1로 대응하지 않는 날짜축 문서이고, 머리말(첫 `##` 앞)은 어느 좌표의 섹션도 아니다.

### 할 수 있는지를 **승인을 받기 전에** 말한다

| | 모드 A (`save` 없음) | 모드 B (`save` 있음) |
|---|---|---|
| 비대상 문서 본문 · 머리말 · `_vocab.md` 산문 | Edit 로 고치고 커밋. 작업 기록은 남기지 않아도 된다(파생 의무가 없다) | **`save` 의 `edits`** — `docs` 의 `text` 에서 뗀 `old` → `new`. **작업 기록이 같이 간다**(서버형은 기록 없이 쓰는 길이 없다 · 좌표가 없으면 `touchesEmpty` 사유) |
| 좌표 섹션 | ②~⑥ (이 스킬 본문) | `sections` — `edits` 로는 **못 한다** |
| 머리 표의 `등록부` 칸 · `_vocab.md` 「지금 등록부」 | 손대지 않는다 — `ctx index` 가 찍는다 | 손대지 않는다 — 서버가 찍는다 |
| 어휘 줄 · 등록부 행 | 파일을 고친다 | `vocab` · `managed` (정리 rename · merge · retire 는 **admin**) |
| 작업 기록 고치기 | 안 한다 — 정정 기록 | 안 한다 — 정정 기록 |

**못 하는 것이면 먼저 말하고 멈춘다** — 「그건 좌표 섹션이라 섹션 갱신으로 하겠습니다」 · 「등록부 정리는 admin 권한이라
제가 할 수 없습니다 — admin 에게 요청하세요」. 되는 것처럼 계획을 보이고 승인받은 뒤 서버에서 거절당하게 두지 않는다.

### 모드 B 에서 보이는 것

```
【섹션 밖 — 승인해 주세요】
  파일     docs/1.관리/BM_411_회의록.md (등록부 비대상 · 머리말)
  바꾸는 줄 3행  「날짜축. 회의는 대상이 아니라 사건이라 …」
         →     「날짜축. 회의 하나가 섹션 하나다.」
  작업 기록 2026-0930-회의록-머리말 (touchesEmpty: 「회의록 머리말 정리 — 바꾼 좌표 없음」)
```

승인되면 `save({ repo, work, edits: [{ file, old, new }] })` 한 번. `old` 가 없다는 `E_CONFLICT` 면 누가 그 사이 고친
것이다 — `docs` 로 다시 읽고 만든다.

### 모드 A 에서

```
docs/1.관리/BM_411_회의록.md 는 등록부에 없는 문서(날짜축)라 작업 기록 없이 고쳤습니다.
```

## 도구가 없을 때

**에이전트는 이 절을 쓸 일이 없다.** `cdp` 서버가 붙어 있으면 본문 그대로 부른다.
여기는 **커밋 훅**과 **사람이 터미널에서 칠 때**를 위한 것이다.

`<repo>` 는 지식 레포 경로, `ctx` 는 `<repo>/bin/ctx` — **Node 가 없어도 돈다**
(없으면 `cdp.exe` 로 넘어간다 · 작업환경 §3.1).

| 본문 | 터미널 |
|---|---|
| `match(["a","b"])` | `ctx match "a" "b"` |
| `where("screen:HRC043")` | `ctx where screen:HRC043` |
| `section("screen:HRC043")` | `ctx where` 뒤에 그 섹션을 연다 — **도구 쪽이 한 번에 준다** |
| `apply("screen:HRC043")` | `ctx apply screen:HRC043` |
| `derive()` | `ctx derive` |
| `check()` | `ctx check` |
| `sync()` | `ctx sync` |
| `search("말")` | `ctx search "말"` |

**`cdp` 가 안 붙어 있으면 그것부터 고친다.** `ctx setup <작업레포>` 가
`.mcp.json` 을 쓰고, Claude Code 를 다시 켜면 `/mcp` 에 `cdp` 가 뜬다.
붙지 않은 채로 bash 로 `ctx` 를 부르는 것은 **되기는 하지만 정상이 아니다** —
그 상태에서는 도구 명함이 없어서 무엇을 언제 부를지가 이 문서에만 있다.
