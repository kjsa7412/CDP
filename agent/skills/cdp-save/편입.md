# 편입 — 밖에서 온 문서를 작업 기록으로

cdp-save 의 둘째 길이다. 뼈대(좌표 판정 → 승인 → `save`)는 같고, 다른 것은 **날짜 · 문서 성격 · 원문 보존**이다 — 본문을 쓰는 것이 아니라 이미 있는 본문에서 좌표를 읽어 내야 하고, 그 본문은 지식 레포의 규약을 모르고 쓰였다.

| 쓰지 않는 때 | |
|---|---|
| 이 세션에서 한 작업 | cdp-save 첫째 길 — 본문을 새로 쓴다 |
| 결정이 하나도 안 난 문서 | 아젠다다 — cdp-save 「결정이 안 났으면」 |
| 코드 · 설정 파일 | 지식이 아니다 — 작업 레포에 둔다 |

**여러 문서는 하나씩 들인다.** 좌표 판정이 문서마다 다르고, 한 기록에 묶으면 어느 좌표가 어느 문서에서 왔는지 사라진다.

## 날짜 — 사건의 날이다

**오늘 날짜를 쓰지 않는다.** `date` 는 그 일이 일어난 날이다. 오늘로 적으면 이력이 통째로 어긋나고, 대기열과 경과가 그 날짜로 줄을 선다 — 반년 전 회의록이 어제 결정보다 늦은 것이 된다.

```
① 본문의 날짜      회의 일자 · 작성일 · 결재일 — 여럿이면 사건이 일어난 날(회의록은 회의한 날)
② 파일명의 날짜
③ 파일 수정 시각   위 둘이 없을 때만
```

셋 다 없으면 묻는다. 시각을 모르면 날짜만 쓴다 — `source` 가 있으면 서버가 시각 없음을 경고하지 않는다. 날짜가 옛것이면 대기열 앞쪽에 선다 — 큐레이터가 날짜순으로 반영한다.

## 문서 성격을 먼저 가른다

판정은 두 방향으로 틀린다.

| 틀리는 방향 | 결과 |
|---|---|
| **넘치게** — 언급만 한 것까지 넣는다 | 그 좌표를 찾는 사람에게 무관한 문서가 나오고, 큐레이터가 채울 내용 없는 섹션을 붙들고 있다 |
| **모자라게** — 정의한 것까지 뺀다 | **그 기록은 어떤 좌표로도 닿지 않는다.** `match` 는 계속 미등재를 내고 검사는 아무 말도 안 한다 |

넘치는 쪽은 시끄럽지만 **모자라는 쪽은 조용하다.**

| 성격 | 예 | 좌표가 되는 것 |
|---|---|---|
| **결정 문서** | 회의록 · 검토서 · 설계 메모 | 신설 · 변경 · 폐기하기로 **정한** 대상 · 이슈로 올린 것 |
| **정의 · 지식 문서** | 도메인 설명 · 용어 정리 · 구조 설명 · 인수인계 | 문서가 **정의하거나 레포에 처음 도입한** 용어 · 개념 · 대상 |

한 문서가 둘 다일 수 있다(인수인계 문서 안의 결정 몇 개) — 그때는 두 기준을 다 댄다. **정의 · 지식 문서에 결정 문서의 기준만 대면 좌표가 0개가 된다** — 무엇도 「바꾸기로 정하지」 않았으니 전부 「설명」 으로 떨어진다. 그 문서가 들어오는 이유가 바로 그 설명이다.

「정의했다」 의 기준 — **그 대상이 무엇인지 이 문서를 읽고 알게 되는가.** 절 하나 · 표의 한 행 · 용어 설명 한 단락이 그 대상에 할애돼 있으면 정의다. 지나가며 이름만 나오면 언급이다. 결정 문서는 X 가 많은 것이, 정의 문서는 O 가 여럿인 것이 정상이다.

**0개가 나오면 먼저 성격 판정을 의심한다** — 정의 문서를 결정 문서로 본 것이 가장 흔한 원인이다.

원문은 통제 어휘를 모른다 — 별칭 · 구어 · 오타가 섞여 있으니 `match` 를 반드시 돌린다. 이름은 레포의 규약대로 짓고 원문 표기는 `aliases` 에 넣는다. `match` 를 거치지 않으면 같은 대상에 이름이 조용히 둘 생긴다.

【좌표 판정】 머리에 원문과 성격을 적는다 — `【좌표 판정】 원문: 2026-08-14 심의회 준비회의록.md · 성격: 결정 문서`.

## 원문을 보존한다

**프론트매터만 씌우고 본문은 그대로 둔다.** 요약하고 싶어진다 — 하지 않는다. 군더더기처럼 보이는 대목(회의록의 반대 의견 · 검토서의 각주 · 인수인계의 여담)이 6개월 뒤 「왜 그렇게 정했나」 의 유일한 단서인 경우가 많다.

| `work.` | |
|---|---|
| `id` | `YYYY-MMDD-slug` — 사건의 날 + 원문 제목에서 뽑은 짧은 주제 |
| `title` | 원문 제목을 쓰되 무엇에 관한 것인지 보이게 다듬는다 |
| `date` | 위 「날짜」 |
| `source` | **원문이 어디서 왔나** — 지우지 않는다. 되짚을 유일한 길이다 |
| `body` | 첫 줄에 `원문 작성: <작성자> · 편입: <지금 날짜>` 한 줄, 그 아래 원문 그대로 |

`author` 는 서버가 토큰(편입한 사람)에서 채운다 — 원문 작성자는 본문 첫 줄에 남긴다.

**형식만 손댄다** — 깨진 표 · 목록을 md 문법으로, 제목 레벨 정리(`#` 은 문서 제목 하나). **내용을 고쳐야 할 것 같으면 고치지 말고 알린다** — 원문이 틀렸다면 그것은 편입 뒤 정정 기록의 일이다.

**그림 · 첨부** — 원문의 그림 · pdf · 옆에 딸린 한 장짜리 HTML 시각 자료는 하나씩 올려 `assets` 에 싣고, 원문이 가리키던 경로(`../projects/비교/layout.png`)를 새 자리(`assets/<id>/<이름>`)로 고쳐 건다 — [첨부.md](첨부.md). 고치지 않으면 `save` 가 「본문이 가리키는 그림이 레포에 없다」 경고를 낸다. HTML 안의 요지 · 결정 · 확인 목록은 본문에 md 로 적는다 — 검색 · 주입은 md 만 본다.

**결정이 안 난 대목** — 「다음 회의까지 확인하기로 했다」 는 결정이 아니다. 원문은 그대로 두고, 그 물음을 【좌표 판정】 에 「제기」 로 올린다(cdp-save 「결정이 안 났으면」). 이미 같은 주제의 이슈 좌표가 있으면 새로 내지 않고 그 좌표를 `touches` 에 넣는다 — 같은 것이 둘이면 결정권자가 두 줄을 좇는다.

**이미 들인 기록의 좌표가 빠졌으면** — 정정 기록이다(cdp-save 「오기재는 정정 기록으로」). `date` 와 `source` 는 원 기록 그대로.

## 예시 하나 — 회의록 · 넷 중 둘

원문 `2026-08-14 심의회 준비회의록.md` — 일시 2026년 8월 14일, 작성 dev.a.

1. BZA021 외부 심의위원 그리드에 **소속 컬럼을 추가**하기로 했다. 명단 출력 때 담당자가 손으로 채우고 있었다(「소속 없으면 명단이 아니죠」).
2. BZA022 안건 등록 화면도 봐야 한다는 얘기 — **이번 범위는 아니다.**
3. 외부인원을 위원회 성격으로 묶는 **HR130 업무구분 코드그룹을 신설한다** — 심의회 · 평가위원회 · 위원회. 부서로 묶으면 외부인원에는 부서가 없다.
4. 외부 ERP 결재 취소가 자동 반영되는지 — **다음 회의까지 확인.** 결정 못 함.
5. hr_ext_emp_mst 테이블은 지금 그대로 쓴다.

```
match({ repo, names: ["BZA021", "BZA022", "업무구분", "hr_ext_emp_mst"] })
```

```
【좌표 판정】 원문: 2026-08-14 심의회 준비회의록.md · 성격: 결정 문서
  ―― 넣는다 ――
  screen:BZA021          변경   외부 위원 그리드에 소속 컬럼 추가로 결정
  code:HR130             신설   업무구분 코드그룹 신설로 결정 (미등재 → 등재 · aliases 업무구분, 업무구분코드그룹)
  issue:ISS-003          제기   외부 ERP 결재 취소의 자동 반영 — 결정 못 함. 같은 주제의 이슈가 이미 있어 새로 내지 않는다
  ―― 뺀다 ――
  screen:BZA022          언급   「이번 범위는 아니다」 → 결정 아님
  table:hr_ext_emp_mst   배경   「지금 그대로 쓴다」 → 바뀐 것 없음
```

넷 다 넣었으면 BZA022 를 찾는 사람에게 「이번 범위는 아니다」 만 적힌 문서가 나오고, 큐레이터는 채울 내용 없는 섹션 둘을 붙들게 된다. 본문은 원문 그대로 — `> lead: 소속 없으면 명단이 아니죠.` 한 줄이 6개월 뒤 「왜 소속을 넣었나」 의 답이다. `date: 2026-08-14` · `source: 2026-08-14 심의회 준비회의록.md` · 본문 첫 줄 `원문 작성: dev.a · 편입: 2026-09-08`.

## 예시 둘 — 도메인 지식 문서 · 반대 방향으로 틀린다

원문 `PLC_CIMON_SCADA_구조_및_데이터흐름.md` — 현장 설비가 어떻게 연결되고 데이터가 어디로 흐르는지 설명한 문서. 결정은 하나도 없고, PLC · SCADA · CimonD · CimonX · I/O 드라이버를 절마다 정의한다.

**틀린 판정**(실제로 있었다) — 결정 문서의 기준을 댔다. 무엇도 「바꾸기로 정하지」 않았으니 전부 「설명 → 좌표 아님」, `match` 의 미등재를 「관계없는 말」 로, `registry: null` 을 「좌표가 필요 없다」 로 읽었다. 【좌표 판정】 을 보이지 않고 `touches: []` 로 커밋했다 — 정의한 용어 아홉이 어느 좌표로도 안 닿았다.

**맞는 판정** — 성격: 정의 · 지식 문서. 문서가 정의한 용어가 좌표다.

```
【좌표 판정】 원문: PLC_CIMON_SCADA_구조_및_데이터흐름.md · 성격: 정의 · 지식 문서
  ―― 넣는다 (전부 미등재 → 등재) ――
  term:PLC              정의   PLC 의 역할과 스캔 주기
  term:PLC디바이스주소    정의   디바이스 주소 체계 표            (이름 제안 — 원문 「PLC 디바이스 주소」)
  term:SCADA            정의   SCADA 구성
  term:CimonD           정의   수집 서버
  term:IO드라이버         정의   통신 드라이버                   (이름 제안 — 원문 「I/O 드라이버」)
  ―― 뺀다 ――
  term:OPC              언급   「OPC 로도 붙일 수 있다」 한 줄 → 정의 아님
  새 타입 term — 등록부에 없다(registry: null). 본문 끝에 「큐레이터에게 — term 좌표 5개를 받을 용어집이 없다」
```

용어집을 세울지는 큐레이터가 정한다. 그 전에도 이 기록은 `touches` 로 그 좌표들에 닿아 있다 — 문서가 없어도 `section` 이 그 좌표의 미반영 기록으로 이 기록을 낸다.
