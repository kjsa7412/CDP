# cdp-save — 작업을 기록하고 파생을 갱신한다

```
모드 A — `save` 도구가 없다 (로컬 지식 레포)
  ① pull        쓰기 전에 받는다.  실패하면 시작하지 않는다
  ② 좌표 판정    이 작업이 **바꾼** 것만.  판정 근거를 보여준다
  ③ 작업 기록    파일에 쓴다
  ④ 파생 갱신    등록부에 걸리는 관리 문서 섹션.  **③ 과 함께 필수**
  ⑤ 커밋·push    작업 기록 1 + 관리 문서 N 을 한 커밋으로

모드 B — `save` 도구가 있다 (서버)
  ① 없다        서버가 언제나 origin HEAD 다
  ②            같다
  ③④           **파일을 만들지 않는다.** 메모리에 준비한다
  ⑤B-0 승인     【좌표 판정】 · 기록 · 섹션 초안을 보이고 **승인을 받는다.  필수**
  ⑤B `save` 한 번  서버가 검사하고 커밋하고 미러한다
```

> **금지 — 사람이 【좌표 판정】을 승인하기 전에는 `save` 를 부르지 않는다**(모드 A 는
> 커밋하지 않는다). 서버 검사는 좌표를 **빠뜨린** 것을 모른다 — `touches` 가 아예 비어야
> 막고, 하나라도 있으면 나머지가 빠져도 통과한다. 빠진 것을 잡는 것은 사람뿐이다.

**요청 하나가 작업 하나가 아니다.** 요청 세 개가 한 작업일 수 있고, 그때 기록은 하나다.
요청마다 기록하면 이력이 파편화되고, 같은 좌표에 남은 기록들이 서로의 후속이 된다.

> **본문의 호출은 MCP 도구다.** `cdp` 서버가 붙어 있으면 `match(...)` 처럼
> 그대로 부른다 — 모드 A(stdio)든 모드 B(HTTP)든 같다. 도구가 없는 자리
> (커밋 훅 · 사람이 터미널에서 칠 때)는 맨 끝 **「도구가 없을 때」** 를 본다.
> 둘은 같은 함수라 결과가 바이트까지 같다(MCP 설계서 §3.3 · §10).
>
> **`save` 도구가 있으면 서버 모드다**(§4.8). 그때는 쓰기 경로가 바뀐다 —
>
> | | `save` 없음 (모드 A) | `save` 있음 (모드 B) |
> |---|---|---|
> | 시작 | `git pull --ff-only` | **생략.** 서버가 언제나 origin HEAD 다 |
> | 고치기 | Write · Edit 로 파일에 | **메모리에 준비한다.** 파일을 안 만든다 |
> | 승인 | ④ 에서 diff 를 보이고 | **⑤B-0 — 필수.** 【좌표 판정】 · 기록 · 섹션 초안을 보이고 승인을 받기 전에는 **`save` 를 부르지 않는다** |
> | 끝 | `git commit` → 커밋 훅이 검사 | `save({ work, sections, vocab })` **한 번.** 서버가 검사하고 커밋한다. `sections[].body` 는 `section` 의 **`content`**(헤딩 · applied 없이) — 헤딩을 넣으면 E_INPUT |
> | 충돌 | 훅이 막는다 | `E_CONFLICT` 의 `detail.content`(지금 본문) 위에 **다시 만들어** `applied` 에 `detail.current` 를 넣어 보낸다 — `section` 을 다시 부르지 않는다(`truncated` 일 때만) |
>
> 훅은 모드 A 에서만 돈다. 모드 B 는 클라이언트에 작업 트리가 없다.

## ① pull — 쓰기 전에 받는다

> **모드 B 면 이 절은 건너뛴다.** `save` 도구가 있으면 받을 것이 없다 —
> 서버 트리가 그 레포의 유일한 작성자이고 언제나 origin HEAD 다. ②로 간다.

```
git -C <repo> pull --ff-only
```

| 결과 | |
|---|---|
| 성공 | ②로 간다 |
| **실패 (ff 불가)** | **여기서 멈춘다.** 사용자에게 알리고 기다린다 |
| remote 없음 | 정상이다. 알리고 ②로 간다 |

**멈추는 이유는 편의가 아니라 정확성이다.** 낡은 섹션 위에서 diff 를 만들면
남이 갱신한 내용을 덮어 없앤다. 그리고 그 손실은 조용하다 — 충돌이 아니라
"내가 쓴 것이 맞는 것처럼" 보인다.

**merge 도 rebase 도 하지 마라.** ff 가 안 되면 사람이 볼 일이다.

## ② 좌표 판정

> **타입 이름은 `_vocab.md` 가 정본이다.** 아래 예시의
> `screen:` · `table:` 은 설명용이고 레포마다 다르다 — 관리문서 이름을
> 한글로 쓰는 레포도 있다(`화면설계서:HRC043`). **먼저 `_vocab.md` 를 열어라.**

### 무엇이 좌표인가

**이 작업이 바꾼 것만이다.**

| 이 작업이 그 대상을… | 좌표 |
|---|:--:|
| 신설했다 | **O** |
| 변경했다 (컬럼 추가 · 규격 변경 · 상태값 추가) | **O** |
| 삭제·폐기했다 | **O** |
| 작업 중 발견해 **이슈로 제기했다** (`issue:`) | **O** |
| 용어 · 개념을 **정의했다 · 레포에 처음 도입했다** (용어 정리 · 구조 설명을 쓴 작업) | **O** |
| 참조했다 · 호출했다 · 언급했다 | **X** |
| 그것을 쓰는 다른 것을 만들었다 | **X** |

`issue:` 는 **제기**가 동사다 — 신설·변경이 아니라서 위 세 행에 안 걸린다.
그래서 "언급했다 → X" 로 떨어지기 쉬운데, **틀린 판정이다.** 이슈를 대장에
올렸으면 그 좌표는 이 작업이 만든 것이다.

판정 기준은 하나다 — **6개월 뒤 그 대상을 맡은 사람이 이 작업을 찾아야 하는가.**
"주제인가?"는 답이 갈리지만 **"바꿨는가?"는 결판난다.**

**0개도 정상이다.** 일정을 정했을 뿐 아무 대상도 안 바꾼 작업이 실제로 있다.
그때는 `touches: []` 로 적는다 — 키를 빼지 말고 **0개임을 확인했다는 선언**으로 남긴다.
좌표를 억지로 붙이지 마라. **억지 좌표는 없는 좌표보다 나쁘다** — 그 좌표를 찾는
사람에게 무관한 문서를 내민다.

**다만 0개가 나오면 멈추고 사용자에게 알린다** — *"이 기록은 어떤 좌표로도 찾을 수
없게 됩니다."* 0개는 판정이 모자라게 틀렸을 때도 나온다(정의한 용어를 전부 "설명" 으로
뺐을 때). 사용자가 0개를 승인하면 그 사유를 남긴다 — 모드 B 는 `save` 의
**`work.touchesEmpty`**(없으면 서버가 `E_INPUT` 으로 거절한다), 모드 A 는 `touches: []`
아래 `touchesEmpty: <사유>`.

### 정규화

```
match(["면접심사의견등록", "업무구분코드", "서류심사"])
```

- `(미등재)` 로 나오면 **③에 그대로 적고 ④에서 어휘에 등재한다.** 등재하지 않으면
  `ctx check` 가 커밋을 막는다
- `[폐기 … -> …]` 로 나오면 **후속 좌표를 쓴다**
- 이름은 `_vocab.md` 의 명명 규약을 따른다. 규약이 없는 타입이면 지은 이름을 판정표에
  **「이름 제안」** 으로 표시한다

**도구의 답을 거꾸로 읽지 마라** —

| 답 | 뜻 | 틀린 해석 |
|---|---|---|
| `미등재` | 어휘에 아직 없다 — 이 작업이 바꾸거나 정의한 대상이면 **등재 후보다** | ~~"레포와 관계없는 말"~~ |
| `where` 의 `registry: null` | 관리 문서가 없는 타입이다 — **`touches` 가 그 좌표로 닿는 유일한 길이다.** 새 타입이고 좌표가 여럿으로 자라면 **관리 문서를 만들자고 제안한다**(아래 「등록부 변경」) | ~~"채울 섹션이 없으니 좌표가 필요 없다"~~ |

### 근거를 보여주고 승인을 받는다

```
【좌표 판정】
  ―― 넣는다 ――
  screen:HRC043         변경   출력물 2종 추가
  table:hr_ext_emp_mst  변경   wrk_tp_cd · tel_no 추가
  code:HR130            신설   업무구분 코드그룹 (미등재 → 등재한다)
  ―― 뺀다 ――
  screen:HRC031         참조   첨부를 읽어오지만 안 바뀜 → 좌표 아님
  module:grid-common    사용   컴포넌트를 썼을 뿐 → 좌표 아님
  ―― 이슈로 ――
  (없음)
```

**넣은 것 · 뺀 것 · 이슈로 보낸 것을 모두 싣는다. 제외한 것을 적어야 사용자가 고칠 수 있다.** 좌표를 잘못 붙이면 6개월 뒤
찾는 사람이 못 찾고, 그때는 이 판정을 되짚을 수 없다.

### 등록부 변경 — 새 타입 · 새 관리 문서 · 좌표 부착

패키지가 깐 관리 문서는 **프로젝트 전체를 덮지 못한다.** `where` 가 `registry: null` 을 답한 **새 타입의 좌표를
섹션으로 받을 관리 문서가 없으면 만든다** — 모드 B 는 `save` 의 `managed`, 모드 A 는 `_managed.md` 에 행을
더하고 `docs/` 에 골격을 만든다. 만들지 않으면 그 좌표는 `touches` 로만 닿고 **현재 상태의 정본이 없다.**

| 상황 | 제안 |
|---|---|
| 새 타입이고 **좌표가 여럿으로 자란다**(용어 · 개념 · 표 · 화면) — 이 작업이 그것을 **정의했다 · 신설했다** | **관리 문서를 만든다** — 섹션이 그 좌표의 지금 상태가 된다 |
| 좌표가 하나뿐이거나 바뀌는 대상이 아니다(`module:` · `domain:` 류) | 만들지 않는다 — `touches` 만 |
| **이미 같은 것을 받는 타입 · 문서가 있다**(이름만 다르다) | **만들지 않는다** — `match` · `where` 로 먼저 보고 그 타입 · 문서를 쓴다 |

**【좌표 판정】 아래에 【등록부 변경】 을 덧붙여 같은 승인을 받는다**(있을 때만 · 별도 승인 단계를 만들지 않는다).

```
【등록부 변경】 — 사람이 승인한다
  신규 어휘 타입   term              (_vocab.md 끝에 ## term — 오타로 만들면 못 지운다)
  신규 관리 문서   docs/용어집.md     (새로 만든다 · 제목 「용어집」 · 섹션 레벨 ##)
  좌표 부착        term:*  →  docs/용어집.md ## {값}     (등록부 맨 끝에 붙는다 · 기존 행은 안 바뀐다)
  기존 좌표        term:X — 작업 기록 1건이 이미 닿았다 → 그 섹션도 이 save 에 같이 보낸다
  영향 문구        docs/용어집.md 머리말 · _vocab.md 규칙 — 이 행과 어긋나는 줄 없음
                   (있으면: BM_411:3 「대상이 아니라 사건」 → edits 로 「날짜마다 섹션」 으로 고친다)
  정리(admin)      없음
```

- **영향 문구를 먼저 본다.** 행을 더하면 그 문서 머리말의 「비대상 · 1:1로 대응하지 않는다」 와 `_vocab.md` ·
  `_managed.md` 의 「`회의록:` 타입이 없다 · 13개가 전부다」 같은 줄이 **거짓이 된다.** `docs({ doc })` 로 그 문서와
  `_vocab.md` 를 읽고, 어긋나는 줄을 **같은 save 의 `edits`** 로 고치는 안을 【등록부 변경】 에 싣는다. 서버도 막는다 —
  남으면 `E_INPUT` 의 `detail.lines` 에 `파일:행` 이 온다. 맞는 줄이면(오탐) `managed[].reviewed: ["파일:행"]`.
  머리 표의 `등록부` 칸과 `_vocab.md` 의 「지금 등록부」 블록은 **서버가 찍는다** — 손대지 않는다.

- **패턴은 타입 하나에 `type:*`** 가 기본이다. 좁히는 것(`type:P*`)은 이유가 있을 때.
- **문서 경로는 그 레포의 폴더 규약을 따른다**(`docs/2.개발/…` 이면 그 아래). 없으면 `docs/<이름>.md`.
  `docs/` 밖 · `..` · 절대경로는 서버가 거절한다.
- **새 행이 걸리는 좌표에는 섹션을 같이 보낸다.** 이 작업이 `touches` 한 것 · 전에 `touches` 만 한 기록이 있는 것
  전부다 — 안 보내면 서버가 `E_INPUT { needSections }` 로 거절한다(그 커밋부터 그 좌표가 앵커 없음이 되어 다음
  save 가 전부 막히기 때문이다). 50개를 넘으면 패턴을 좁혀(`term:P*`) 나눠 붙인다.
- **새 섹션의 `heading` 은 제목 줄 전체**(`PLC — 프로그래머블 로직 컨트롤러`)다 — 값으로 시작해야 한다. 안 주면 값이 제목이다.
- 서버가 **앞 행에 완전히 덮이는 패턴**(`table:*` 뒤의 `table:a*`)은 거절하고, 같은 패턴이 이미 다른 문서에 있으면
  `E_CONFLICT { detail.current }` 를 준다 — 그 문서에 붙이거나 다른 패턴을 고른다.
- **쓰기 전에** `where` 로 같은 타입 · 같은 문서가 이미 있는지 본다. 한 번 만든 타입 · 행은 `save` 로 못 고친다 —
  정리는 `cdp-managed` 의 「구조 정리」(admin).
- **이름 바꾸기 · 합치기 · 폐기는 이 절차가 아니다** — `cdp-managed` 「구조 정리」 · **admin 만.**
- 모드 A — `_managed.md` 의 **마지막 규칙 행 바로 뒤**(같은 표)에 표 한 줄 — 좌표 패턴 `term:*` · 관리 문서 `docs/용어집.md` · 섹션 `## {값}` — 을 더하고
  `docs/용어집.md` 골격(제목 한 줄)을 **같은 커밋**에 넣는다. 훅(`ctx check`)이 덮인 행 · 앵커 없음을 본다.

`ctx check` 가 뒤에서 한 번 더 본다 — **본문에 `` `type:값` `` 으로 쓴 좌표가
`touches` 에 없으면 경고**한다. 참조만 한 것이면 무시하면 되고, 바꾸거나
제기한 것이면 그때 넣는다.

## ③ 작업 기록

### `date` 에 시각을 적는다

```yaml
date: 2026-09-08 14:30
```

**하루에 같은 좌표를 두 번 건드리는 것은 드문 일이 아니다.** 오전에 화면을
고치고 오후에 같은 화면의 용량 제한을 정하면 기록이 둘이 된다.

날짜만 적으면 **둘의 순서를 알 수 없다.** 그래서 CDP 는 같은 날짜를 동배로
보고, 두 번째 기록의 파생 누락을 오류로 잡지 못한다 — 경고만 뜬다.

시각을 적으면 그 사각지대가 닫힌다.

```
날짜만    2026-09-08 · 2026-09-08     → 동배. 파생 누락이 경고에 그친다
시각까지  2026-09-08 09:10 · 14:30    → 순서가 결판난다. 오류로 막힌다
```

`id` 와 파일명은 그대로 날짜 단위(`2026-0908-slug`)다. 파일명이 길어지면
읽기 어렵고, 하루에 같은 slug 를 두 번 쓸 일은 없다.


`<repo>/work/YYYY-MMDD-slug.md` 에 쓴다. `<repo>/TEMPLATE-work.md` 참고.

```markdown
---
id: 2026-0821-면접심사의견-개편
title: 면접심사의견등록(HRC043) 개편 — 현황/작성 화면 분리
date: 2026-08-21
author: dev.a
touches:
  - screen:HRC043
  - table:hr_ext_emp_mst
  - code:HR130
tags: [채용, 화면개편]
---

# 면접심사의견등록(HRC043) 개편 — 현황/작성 화면 분리

(본문 — 자유 형식)
```

| 필드 | |
|---|---|
| `id` | **파일명과 같아야 한다.** `ctx check` 가 본다 |
| `status` | **적지 않는다. 쓸 수 있는 값이 없다.** 지식공유문서는 작업의 완료에서 발생하고, 항상 그 시점에 완료된 것이 넘어온다. 값이 있으면 `ctx check` 가 오류로 막는다 |
| `touches` | ②의 결과. 0개면 `touches: []` 와 **`touchesEmpty: <사유>`** — 사용자가 0개를 승인했을 때만 |
| `supersedes` | **이 기록 자체가 틀렸을 때만.** 아래 |

### 본문은 자유 형식이다

**섹션을 강요하지 않는다.** 산문이든 표든 코드펜스든 상관없다.

다만 6개월 뒤 이 결정을 뒤집으려는 사람은 *"무엇을 했는지"* 가 아니라
**"어떤 제약 때문에 그렇게 했는지"** 를 찾는다. 그것이 본문에 없으면 그 사람은
같은 함정을 다시 밟는다.

**이유가 안 보이면 한 번 묻는다** — *"이 판단의 제약이 뭐였나요?"*
한 번만 묻고, 답이 없으면 그대로 쓴다. 캐물으면 기록 자체를 안 하게 된다.

### 제목 인용

YAML 에서 `[` `{` `&` `*` `!` `|` `>` `%` `@` 로 시작하거나 `: ` 를 포함하는 제목은
**따옴표로 감싼다.** `title: [오기재] …` 는 배열로 파싱돼 제목이 사라진다.

### `supersedes` 는 오기재 정정에만

```yaml
supersedes: 2026-0902-업무이력-오기재
```

**좌표 누락도 오기재다.** 이미 커밋된 기록의 `touches` 에 좌표가 빠졌으면 정정 기록을
낸다 — 모양(id · 원 기록의 date · 빠졌던 좌표만 · 본문은 원문을 다시 싣지 않는다)은
`cdp-import` ④ 「이미 들인 기록의 좌표가 빠졌으면」 에 있다. 기존 기록의 `touches` 를
고치는 길은 없다(`save` 는 `E_EXISTS`).

**같은 좌표를 나중에 또 바꾼 것은 적지 않는다.** 그건 계산으로 나온다 —
날짜와 `touches` 만 있으면 도구가 "이 좌표에 이후 N건" 을 뽑는다.
`supersedes` 를 그 용도로 쓰면 손으로 그래프를 관리하게 되고, 곧 어긋난다.

**틀린 기록도 지우지 않는다.** 잘못된 이름으로 만든 스크립트가 어딘가 있을 수 있고,
그것을 찾을 단서가 필요하다.

## ④ 파생 갱신

### 대상 찾기

**등록부가 답한다. 어느 문서를 고칠지 생각하지 마라.**

```
where("screen:HRC043")
where("table:hr_ext_emp_mst")
where("code:HR130")
where("module:grid-common")
```

`module:` 과 `domain:` 은 관리 문서가 없다. 작업 기록에만 남고 **그것이 정상이다.**

### 초안 받기

```
apply("table:hr_ext_emp_mst")
```
```
# docs/테이블정의서.md  ## hr_ext_emp_mst

<!-- applied: 2026-0821-면접심사의견-개편 -> 2026-0902-BZA021-외부심의위원 -->

**변경** · 2026-09-02 [`BZA021-외부심의위원`](../work/2026-0902-BZA021-외부심의위원.md)
```

`ctx apply` 는 **파일을 고치지 않는다.** 변경 줄과 새 `applied` 값만 준다.
본문(컬럼 행·규격 표·상태값)은 **네가 쓴다** — 그것이 이 작업이 실제로 바꾼 내용이고
기계는 그 내용을 모른다.

### 섹션만 바꾼다

```diff
  ## hr_ext_emp_mst — 외부인원마스터
- <!-- applied: 2026-0715-외부인원-신설 -->
+ <!-- applied: 2026-0821-면접심사의견-개편 -->

  | 컬럼 | 타입 | 길이 | NULL | 키 | 설명 |
  |---|---|---|:--:|:--:|---|
  | `email` | varchar | 100 | Y | | 이메일 |
+ | `wrk_tp_cd` | varchar | 10 | Y | | 업무구분코드 (HR130) |
+ | `tel_no` | varchar | 20 | Y | | 전화번호 |

+ **변경** · 2026-08-21 [`면접심사의견-개편`](../work/2026-0821-면접심사의견-개편.md) `wrk_tp_cd`·`tel_no` 추가
```

**그 섹션 밖은 건드리지 마라.** 다른 좌표의 섹션을 같은 커밋에서 손보면
남이 그 좌표를 갱신하는 중일 때 충돌한다.

### 섹션은 홀로 서야 한다

**그 섹션만 읽고 대상의 현재 상태를 알 수 있어야 한다.** 작업 기록 링크를
타고 가야 알 수 있으면 파생이 안 된 것이다.

이유는 하나다 — **주입은 섹션만 싣는다.** `cdp-load` 는 관리 문서 섹션이
현재 상태라는 전제로 돌고, 작업 기록은 기본으로 넣지 않는다. 그래서 값이
기록에만 있으면 **주입받은 쪽은 그 값이 없다고 판단하고 새로 정하려 든다.**

실제로 이렇게 새 나갔다. `2026-0831-ERP-결의서-기본값` 이 지불 수단별
기본값 표를 정했는데, 파생된 섹션에 남은 것은 이 한 줄이었다.

```
결의서입력으로 넘어간다. 작성자·결의일·결제수단 기본값이 여기서 정해진다
                                          ↑ "정해진다" 만 있고 값이 없다
```

**표가 기록에만 남았다.** 그 뒤 같은 요청이 다시 왔을 때 주입은 이 한 줄을
싣고, 이미 정해진 값을 처음부터 다시 정하는 작업이 시작됐다.

**옮길 것** — 판단 · 표 · 규칙 · 값 · 제약. *"왜 그렇게 정했나"* 중 **대상의
성질이 된 것**은 전부. `ctx apply` 가 작업 기록의 목차를 보여준다.

**남길 것** — 그 결정에 이른 경위, 논의, 대안. 그것은 사건이라 기록의 것이다.

| 요약해도 되는 것 | 반드시 옮길 것 |
|---|---|
| *"현장 요청으로"* · *"협의 결과"* | **그래서 값이 무엇인가** |
| 누가 언제 무엇을 물었나 | 그 답이 만든 **규칙과 예외** |

> 변경 줄(`**변경** · 날짜 [링크]`)은 **출처 표시이지 내용이 아니다.**
> 그 줄만 붙이고 끝내면 섹션은 여전히 빈 것이다. 링크는 *"더 알고 싶으면"*
> 이고, *"알아야 하면"* 이 되면 안 된다.

### 섹션이 없으면

| 상황 | |
|---|---|
| `ctx where` 가 `섹션이 없음` | **섹션을 새로 만든다.** 등록부가 정한 앵커 형태 그대로 (`## {값}`) |
| `문서가 없음` | 문서를 만든다. 제목 한 줄 + 그 섹션 |
| `아직 작성되지 않음` (`applied: null`) | 본문을 채우고 `applied` 를 이 기록의 id 로 |

앵커 형태를 임의로 바꾸지 마라 — `ctx check` 가 등록부와 대조해 커밋을 막는다.

### 신규 용어 등재

②에서 `(미등재)` 가 나왔으면 `<repo>/_vocab.md` 의 해당 타입 섹션에 **한 줄 추가**한다(모드 B 는 `save` 의 `vocab` — 타입 섹션이 없으면 서버가 만든다. 새 타입이면 사용자에게 먼저 알린다. 그 타입을 받을 관리 문서도 없으면 ② 「등록부 변경」).

```markdown
- `code:HR130` — 외부인원 업무구분
  aliases: 업무구분코드, HR130
```

**`aliases` 가 이 파일의 값어치다.** 정본만 적으면 작성자만 편해지고, alias 가 있어야
수신자가 자연어로 물어도 걸린다. 그 작업에서 실제로 쓴 표현을 그대로 넣어라.

### 사람이 승인한다 — 그러나 건너뛰지 않는다

파생 갱신 diff 를 **보여주고 승인을 받는다.**

**건너뛸 수 없다.** ③ 과 ④ 는 한 벌이고 `ctx check` 가 파생 누락을 **오류**로
잡아 커밋을 막는다. 미루고 싶어지는 이유 셋이 다 성립하지 않기 때문이다 —

| 미루고 싶어지는 이유 | 왜 안 되나 |
|---|---|
| 파생이 넓다 | 넓어도 해야 한다. 넓다는 것은 그 작업이 실제로 그만큼 건드렸다는 뜻이다 |
| 남의 확인이 필요하다 | 필요 없다. 판단 근거는 ③ 에 이미 다 들어 있다 |
| 급하다 | **막히는 것은 코드 커밋이 아니라 지식 레포 커밋이다.** 코드를 먼저 커밋하고 그 뒤에 여기 오면 된다 |

정말 지금 못 하겠으면 **지식공유문서를 아직 쓰지 마라.** 작업 완료와 지식공유는
분리된 일이다.

## ⑤ 커밋 · push

> **모드 B 면 이 절 전체를 건너뛰고 [⑤B](#5b-save--모드-b) 로 간다.**
> 커밋할 작업 트리가 클라이언트에 없다. 훅도 없다.

```
git -C <repo> add work/<id>.md docs/... _vocab.md
git -C <repo> commit -m "<id>: <title>"
git -C <repo> push
```

**작업 기록 1 + 관리 문서 N 을 한 커밋에 넣는다.** 그러면:

```
git log -L '/## hr_ext_emp_mst/,/^## /:docs/테이블정의서.md'
```

그 테이블의 변경 이력이 그대로 나온다. **git 이 이미 형상관리 도구이고 우리는
파일 배치만 맞춰주면 된다.**

### 커밋이 거부되면

`.githooks/pre-commit` 이 `ctx check` 를 돌린다. 거부되면 **고치고 다시 커밋한다.**
`--no-verify` 로 넘기지 마라 — 그 검사가 유일한 기계 보증이다.

| 거부 사유 | 고치는 법 |
|---|---|
| **관리 문서 파생 누락** | ④를 끝낸다. `ctx apply <좌표>` 가 초안을 준다 |
| **`status: 미결` · `제안`** | 둘 다 아젠다다. `docs/위험및이슈관리대장.md` 로 옮긴다 |
| `_vocab.md` 미등재 좌표 | ④의 어휘 등재 |
| 등록부가 가리키는 섹션이 없음 | ④의 "섹션이 없으면" |
| 필수 필드 누락 | ③의 프론트매터 |
| `id` ≠ 파일명 | 둘을 맞춘다 |

훅이 안 돌면 (`core.hooksPath` 미설정) `ctx check` 를 **직접 돌려 확인한다.**

### push 까지 한다

```
git -C <repo> push
```

**안 올린 지식은 없는 지식이다.** 이 레포의 독자는 나중에 이 좌표를 맡을 남이고,
내 PC 에만 있는 커밋은 그 사람에게 닿지 않는다. 전에는 여기서 멈추고 앱 상단의
`⬆ 보내지 않은 커밋 N건 [보내기]` 를 사람이 누르게 했는데, **누르는 것을 잊으면
아무도 모른다** — 기록은 남았고 검사도 통과했으니 화면 어디에도 빨간 것이 없다.

멈출 이유였던 "남의 눈에 들어간다" 도 여기서는 성립하지 않는다. ① 에서 이미
받았고, `ctx check` 가 커밋을 막아 파생 누락·미등재 좌표·아젠다 상태를 걸러냈다.
**나가는 것은 이미 검사를 통과한 것이다.**

| 상황 | |
|---|---|
| **원격 없음** | 커밋까지 하고 *"원격이 없어 push 하지 않았다"* 고 **말한다.** 실패가 아니다 |
| **거부 (non-fast-forward)** | **여기서 멈춘다.** ① 이후에 남이 올린 것이다. 사용자에게 알리고 기다린다 — `merge` 도 `rebase` 도 하지 마라 |
| push 실패 (네트워크·인증) | 커밋은 그대로 둔다. **무엇이 안 올라갔는지 말한다.** 앱 상단의 `[보내기]` 가 남는다 |

**커밋을 되돌리지 마라.** push 가 안 됐다고 커밋을 지우면 ③④ 를 다시 해야 한다.
올리는 것만 다시 하면 된다.

> 이 스킬이 올리는 것은 **지식 레포뿐이다.** 코드 레포는 `cdp-push` 가 본다 —
> 이 스킬은 자기가 방금 만든 커밋 하나만 안다.

## ⑤B-0 승인 — 모드 B · 필수

먼저 **`brief({ repo })` 를 한 번** 부른다 — `repo` 는 작업 레포 `.claude/cdp.json` 의 값이다. 이 연결(`.mcp.json`)의
기본 레포와 다르면 경고 줄이 붙는다 — 그 줄을 사용자에게 그대로 전한다(설치 한 줄을 다시 돌리면 맞춰진다).

`save` 를 부르기 **전에** 사람에게 셋을 보이고 승인을 받는다.

1. **【좌표 판정】** — 넣은 것 · 뺀 것 · 이슈로 보낸 것 (② 의 모양 그대로). 미등재 · 이름 제안 · 0개 사유도
   **【등록부 변경】** — 새 어휘 타입 · 새 관리 문서 · 좌표 부착 · 기존 좌표 · **영향 문구** · 정리가 있을 때만 (② 「등록부 변경」)
   **【섹션 밖】** — `edits` 로 고칠 머리말 · 산문 · 비대상 문서 줄(있을 때만 · 아래 「섹션 밖 쓰기」)
2. **작업 기록** — 제목 · date · 본문 요지
3. **섹션 초안** — 좌표마다 바뀌는 대목

**승인 없이 `save` 를 부르지 않는다.** 한 번에 끝내 달라는 요청이어도 판정표는 보이고
한 번 묻는다 — 커밋된 기록은 고칠 수 없고(정정 기록만 된다), 서버 검사는 좌표를
빠뜨린 것을 모른다. 승인 뒤에 사용자가 고친 좌표가 있으면 판정표를 다시 보이지 않고
고친 대로 보낸다.

## ⑤B `save` — 모드 B

**한 번에 보낸다.** ③④ 에서 준비한 것을 인자로 넘기면 서버가 검사하고
커밋하고 미러까지 한다. 나눠 보낼 수 없다 — 작업 기록만 들어가고 파생이
빠진 상태가 **커밋으로 남으면** 그것이 가장 나쁜 결과다.

```
save({
  repo: "alpha",                        // **필수.** 쓰기에서 기본값은 사고다
  work: {                               // ③ 의 프론트매터 + 본문
    id: "2026-0908-출장보고-사진첨부",
    title: "BZD020 — 차량 미이용자 사진 첨부",
    date: "2026-09-08 14:30",
    touches: ["screen:BZD020", "table:pj_trip_photo_list"],
    // touchesEmpty: "일정만 정했다 — 바꾼 대상 없음",   // touches 가 빌 때만 · 없으면 E_INPUT
    // source: "공유드라이브/…/원문.md",                  // 편입(cdp-import)일 때만
    tags: ["출장"],
    body: "# BZD020 — …

(③ 의 본문 전체)"
  },
  sections: [                           // ④ 의 결과. 좌표 하나에 하나
    {
      coord: "screen:BZD020",
      applied: "2026-0715-외부인원-신설",   // **`section` 이 준 값 그대로**
      body: "출장보고작성.

(`section` 이 준 **content** 를 고친 것 — 헤딩 줄 · applied 주석 없이)"
    }
  ],
  vocab: [                              // ② 에서 `(미등재)` 였던 것만
    { coord: "table:pj_trip_photo_list", label: "출장사진목록",
      aliases: ["출장사진", "사진목록"] }
  ],
  // managed: [{ pattern: "term:*", doc: "docs/용어집.md", title: "용어집" }]   // 【등록부 변경】 을 승인받았을 때만 — 새 타입의 행 · 문서
  // assets: [{ ref: "sha256:…", name: "사진첨부 영역.png" }]   // 그림 · pdf — 아래 「그림 · 첨부」. 바이트는 싣지 않는다
  // edits: [{ file: "docs/1.관리/BM_411_회의록.md", old: "…지금 글 그대로…", new: "…" }]   // 좌표 섹션 밖 — 아래 「섹션 밖 쓰기」
  // examples: "purge"                  // 서식 예시 정리 — cdp-managed 「서식 예시 정리」
})
```

### 섹션 밖 쓰기 — `edits`

좌표 섹션은 `sections` 로 쓴다. **그 밖** — 문서 머리말(첫 `##` 앞) · 등록부 비대상 문서(회의록 · 대장 같은 날짜축 ·
집계 문서)의 섹션 · `_vocab.md` · `_managed.md` 의 산문 — 은 `edits` 다.

```
docs({ doc: "BM_411" })                  → text (원문) · headings · registered
edits: [{ file: <text 의 path>, old: <text 에서 그대로 뗀 글>, new: <바꿀 글> }]
```

- `old` 는 **정확히 한 번** 나와야 한다. 두 번 이상이면 앞뒤 줄을 더 붙인다(`E_INPUT`). 없으면 읽은 뒤 누가 바꾼 것이다 —
  `E_CONFLICT` · `docs` 로 다시 읽고 만든다. 지우려면 `new: ""` · 새 섹션은 앞 섹션 끝(또는 `## 작성지침` 앞)에 붙인다.
- **못 건드리는 자리** — 좌표 섹션(→ `sections`) · `<!-- applied -->` · 어휘 줄(→ `vocab`) · 등록부 행(→ `managed`) ·
  `_vocab.md` 의 생성 블록. 서버가 `E_INPUT` 에 그 줄과 갈 곳을 적어 준다.
- 작업 기록은 언제나 같이 간다 — 바꾼 좌표가 없으면 `touchesEmpty` 에 사유(「회의록 머리말 정리」).
- 작업 기록(`work/`)은 고치지 않는다 — 정정은 `supersedes` 를 단 새 기록이다.

### `body` 에 헤딩을 넣지 않는다 — `section` 의 `content` 를 보낸다

`section` 은 둘을 준다. `body` 는 **헤딩 줄부터** 실린 원문이고, `content` 는 헤딩 줄과
`<!-- applied: … -->` 를 뺀 본문이다. **`save` 에 보낼 것은 `content` 를 고친 것**이다 — 헤딩과
applied 주석은 서버가 붙인다.

`body` 를 그대로 고쳐 보내면 헤딩이 두 번 들어가고, 파서가 둘째 헤딩을 새 섹션의 시작으로
읽어 정작 그 좌표의 섹션은 두 줄만 남고 빈다. 실제로 그렇게 됐고 그때는 save 도 check 도
where 도 조용했다(2026-09-23). 지금은 서버가 `E_INPUT`(헤딩 줄이 있다)으로 거절하고,
`ctx check` 가 같은 좌표 섹션이 둘이면 `dup-anchor` 오류를 낸다.

### 섹션이 없으면 `heading` 을 준다

`section` 이 `missing` 을 답한 좌표는 섹션을 새로 만드는 것이다. 그때만
`heading` 을 같이 보낸다 — 제목 줄이 `## {값}` 이 아니어야 할 때다
(`## pj_trip_photo_list — 출장사진목록`).

```
{ coord: "table:pj_trip_photo_list", applied: null,
  heading: "pj_trip_photo_list — 출장사진목록", body: "…" }
```

없으면 서버가 좌표 값을 그대로 제목으로 쓴다. `heading` 은 제목 줄 **전체**라 값으로 시작해야 한다(값이 빠지면 `E_INPUT`). `applied` 는 `null` 이다 —
읽을 때 없었으니 보낼 것도 없다.

### 그림 · 첨부 — `assets`

화면 캡처 · 구성도 · 사양 pdf 를 문서에 넣을 때다. **「첨부는 못 한다」 로 멈추지 않는다** — 사람에게 레포를
받아 push 하라고 하지도 않는다. 파일은 **작업 기록에 딸린다** — 자리는 모드 A · B 모두
`work/assets/<작업 기록 id>/<이름>` 이다.

| 본문이 있는 곳 | 링크 |
|---|---|
| 관리 문서(`docs/*.md`) 섹션 | `![구성도](../work/assets/<id>/구성도.png)` |
| 작업 기록(`work/<id>.md`) | `![구성도](assets/<id>/구성도.png)` |

이름에 공백이 있으면 `![구성도](<../work/assets/<id>/시스템 개요.png>)` 처럼 꺾쇠로 싼다. 받는 종류는
png · jpg · gif · webp · pdf, 하나에 10 MB · save 한 번에 20개 · 합 30 MB. svg 는 받지 않는다(png 로 바꾼다).

**모드 B — 올리고 `ref` 를 싣는다.** 바이트는 도구 인자로 보내지 않는다(모델이 파일을 옮겨 적으면 수십만
토큰이고 한 글자만 틀려도 깨진 그림이 커밋된다). 셸에서 올린다 — 토큰은 MCP 가 쓰는 그 `CDP_TOKEN`,
서버 주소는 작업 레포 `.mcp.json` 의 `url` 에서 `/mcp/<repo>` 를 뗀 것:

```bash
curl -sS -H "Authorization: Bearer $CDP_TOKEN" --data-binary @"docs/캡처/구성도.png" "http://cdp.example:7374/api/alpha/assets"
# → { "ref": "sha256:9f2c…", "size": 48213, "type": "image/png", "expiresInHours": 24, … }
```

그 `ref` 를 `save` 의 `assets: [{ ref, name: "구성도.png" }]` 에 싣고, 본문(`work.body` · `sections[].body`)에
위 표의 링크를 적는다. 올리기만으로는 레포가 바뀌지 않는다 — 서버가 24시간 들고 있다가 **`save` 가 작업
기록 · 섹션과 한 커밋에 넣는다**(검사에서 걸리면 같이 되돌린다). 응답 `assets: [{ path, size }]` 가 들어간 자리다.

| 올리기 응답 | |
|---|---|
| `403` | 쓰기 권한이 없다 — 관리자에게 |
| `413` | 10 MB 넘는다 — 줄이거나 나눈다 |
| `415` | 받는 종류가 아니다(내용으로 가린다 · 확장자가 아니라) |
| `401` · 셸에 `CDP_TOKEN` 이 없다 | 사람에게 토큰을 청하지 말고 그대로 알린다 — 설치(작업 레포 설치 한 줄)가 넣는 값이다 |

`save` 가 `warnings` 에 **「본문이 가리키는 그림 … 이 레포에 없다」** 를 내면 링크가 틀린 것이다(화면에서
「그림을 찾을 수 없음」 으로 나온다) — 위 표와 다시 대 보고, 틀렸으면 정정 기록으로 고친다.
**「올린 첨부 … 를 어느 본문도 가리키지 않는다」** 면 링크를 빠뜨린 것이다.

**모드 A — 복사하고 커밋에 같이 넣는다.** `work/assets/<id>/` 에 파일을 두고 ⑤ 의 `git add` 에 그 경로를 더한다.
링크 규칙은 위 표와 같다.

### `author` 를 보내지 않는다

서버가 토큰에서 채운다. 보내면 거부된다 — 남의 이름으로 기록이 남으면
기록의 의미가 없어서다. ③ 의 예시에 `author:` 가 있는 것은 모드 A 용이다.

### `applied` 가 낙관적 잠금이다

`sections[].applied` 는 **`section` 으로 그 섹션을 읽었을 때 받은 값을 그대로**
넣는다. 고치지도 비우지도 않는다. 그 사이 남이 같은 섹션을 갱신했으면 서버가
`E_CONFLICT` 를 낸다.

| | |
|---|---|
| `E_CONFLICT` | 그 사이 남이 같은 섹션을 갱신했다. 거절에 **재료가 실려 온다** — `detail.currentWork { id, title, author, date }`(누가 · 언제 · 어느 기록으로) · `detail.content`(지금 본문 · 헤딩 · applied 없이) · `detail.current`(지금 applied). **`content` 위에 ④ 를 다시 만들고 `applied` 에 `current` 를 넣어 다시 보낸다.** 옛 본문을 그대로 재전송하면 그 사람의 갱신이 사라진다. `truncated: true`(8,000자 초과)일 때만 `section` 을 다시 읽는다 |
| `E_FORBIDDEN` | 그 레포에 쓰기 권한이 없다 — 또는 `managed` 의 정리(rename · merge · retire)를 admin 이 아닌 사람이 보냈다. 관리자에게 말한다(요청문을 만들어 준다) |
| `E_CONFLICT` `detail.kind: 'managed'` | 등록부에 같은 패턴이 이미 다른 자리에 있다. `detail.current` 의 문서에 붙이거나 다른 패턴을 고른다 |
| `E_INPUT` | 스키마다. 메시지의 `field` 를 본다. "헤딩 줄이 있다" 면 `body` 에 `## …` 를 넣은 것 — `section` 의 `content` 를 보낸다. `detail.needSections` 면 새 등록부 행이 걸리는 기존 좌표의 섹션을 안 보낸 것이다 — `sections` 에 더해 다시. `detail.shadowedBy` 면 앞 행이 그 패턴을 덮는다 — 그 행의 문서에 붙인다. `field: work.touches` 면 좌표가 0개다 — **② 를 다시 본다**(정의한 용어 · 바꾼 대상을 뺐나). 정말 0개면 사용자 승인을 받고 `touchesEmpty` 에 사유를 적는다 |
| 검사 실패 | 「커밋이 거부되면」 의 표와 **같은 오류들**이다. 고치고 다시 `save` |

`section` → ④ → `save` 사이가 짧을수록 충돌이 적다. **미리 다 읽어 두고 오래
붙들지 마라.**

### 무엇이 돌아오나

```
{ commit: "1bc1eec", id: "…", sections: 2, vocab: 1, assets: [{ path: "work/assets/…/구성도.png", size: 48213 }],
  mirror: "ok", mirrorReason: null, mirrorLast: { state, reason, at, ahead, behind }, warnings: [...] }
```

`mirror` 는 origin 미러의 **실제 상태**다 — `ok`(갔다) · `queued`(아직 가는 중 — 1.5초 안에 안 끝났다) ·
`lag`(못 갔다 — `mirrorReason` 이 사유: `auth` 는 PAT · `net` 은 망) · `diverged`(origin 에 서버가 모르는
커밋이 있다 — 관리자가 맞춘다) · `off`(원격 없음). 어느 경우든 **커밋은 서버 트리에 있다.** `ok` 가 아니면
`warnings` 의 그 줄을 사람에게 그대로 전한다 — 고치는 것은 관리자(콘솔 > 지식 레포)이지 이 절차가 아니다.
`E_GIT` 에 `detail.reason: 'dirty'` 면 서버 트리에 커밋 안 된 변경이 있어 거절된 것이다 — 관리자에게
「트리 되돌리기」 를 청한다. 다시 보낼 것은 그대로다.

### push 는 사람이 누르지 않는다

모드 A 의 「push 까지 한다」가 여기서는 서버의 일이다. 클라이언트가 할 것도,
잊을 것도 없다.

### 모드 B 의 종료 보고 — 응답에 있는 것만 말한다

**모드 B 의 끝에서는 「push 는 하지 않았다」 도, 사람에게 push 를 권하는 말도 하지 않는다.** 그 말은 모드 A
(사람이 `git commit` 한 작업 트리)의 것이다 — 모드 B 에는 클라이언트 작업 트리가 없어 누를 push 가
없다. 아래 표대로, **`save` 응답의 `commit` · `mirror` · `mirrorReason` · `mirrorLast` 만** 근거로 쓴다.

| 응답 | 이렇게 보고한다 |
|---|---|
| `mirror: "ok"` (`mirrorLast.ahead: 0`) | 「서버에 커밋했고(`<commit>`) origin 미러에도 올라갔다」. `ok` 는 서버의 `git push` 가 성공했거나 보낼 것이 남아 있지 않다는 뜻이고, `ahead` 는 그 뒤 origin 보다 앞선 커밋 수다 |
| `mirror: "queued"` | 「서버에 커밋했다. 미러는 아직 가는 중이다」. 마지막으로 알려진 상태는 `mirrorLast` 를 그대로 |
| `mirror: "lag"` · `"diverged"` | 「서버에 커밋했다. 미러는 못 갔다」 + **`mirrorReason` 을 그대로**(`warnings` 의 줄도). 고치는 것은 관리자(콘솔 > 지식 레포)다 — 사용자에게 push 를 시키지 않는다 |
| `mirror: "off"` | 「서버에 커밋했다. 이 레포는 원격이 없다(또는 서버가 미러 없이 떠 있다)」 |

응답에 없는 사실은 단정하지 않는다 — `mirrorLast` 가 `null` 이면 미러 상태를 모른다고 말하고, 「origin 에서
확인했다」 처럼 응답 밖의 것을 보태지 않는다. 다른 스킬(`cdp-import` · `cdp-edit` · `cdp-managed`)의
모드 B 끝도 이 표를 쓴다.

## 작업이 끝나지 않았으면 — 아직 쓰지 않는다

**지식공유문서는 작업의 완료에서 발생한다.** 끝나지 않은 것은 기록할 사실이
아직 없다는 뜻이다.

전에는 `status: 진행중` 으로 자리를 잡아 두게 했다. 뺐다 — 그 상태가 존재하면
지식 레포가 **할 일 목록** 노릇을 하기 시작하고, 불변인 사건과 가변인 상태가
섞이면 둘 다 안 맞는다.

같은 좌표를 동시에 건드릴 걱정이라면 그것은 지식 레포가 아니라 **일감 분배**의
문제다.

## 결정이 안 났으면 — 여기 쓰지 않는다

**지식공유문서는 작업의 완료에서 발생하는 문서다.** 결정을 기다리는 것은
완료가 아니라 **아젠다**이고, 아젠다는 스케줄 문서가 다룬다.

`미결` 도 `제안` 도 쓰지 않는다 — **둘은 같은 것이다.** 이름이 둘이면
한쪽만 막히고 다른 쪽으로 흘러 들어간다. `ctx check` 가 둘을 같이 잡는다.

> **판단이 끝난 부분과 안 끝난 부분을 가른다.** "왜 이렇게 하는가"가 정해졌으면
> 그것은 지식공유문서다 — 남은 것이 남의 회신뿐이라면 그 **회신 대기만**
> 이슈 대장으로 보내고, 작업 기록은 상태 없이 그대로 남긴다.

**대장으로 보내되 `touches` 에는 남긴다 — 파일은 갈라도 좌표는 잇는다.**
대장 항목은 가변이지만 *그 이슈를 제기한 사건*은 불변이고, 그것은 작업 기록
쪽이다. `touches` 에서 빼면 `ctx where issue:…` 가 "작업 0건" 을 답하고,
**왜 제기됐는지 되짚을 길이 `grep` 밖에 안 남는다.**

`docs/위험및이슈관리대장.md` 에 적는다.

```markdown
## ISS-014 — 심의회 보류 상태값 추가 여부
- 제기: 2026-08-17 dev.a
- 내용: 현장은 "다음 회차로 넘긴다"를 쓰는데 상태값에 없다
- 결정권자: 기획팀
- 상태: 대기
```

| | 지식공유문서 | 이슈 대장 |
|---|---|---|
| 언제 | 작업이 **끝났을 때** | 문제를 **발견했을 때** |
| 성질 | 불변. 사건 | 가변. 상태가 바뀐다 |

둘을 같은 파일에 섞으면 지식 레포가 할 일 목록 노릇을 하기 시작하고,
그 순간 둘 다 안 맞는다.

# 실사용 예시 — 처음부터 끝까지

> **아래는 모드 A 다** — 이 PC 에 지식 레포(`C:/cdp`)가 있고 **git 으로 커밋**하는 경우.
> 도구 호출은 두 모드가 같고, 다른 것은 시작의 `pull` 과 끝의 커밋뿐이다.
> 모드 B 의 대조는 맨 끝 [「같은 작업을 모드 B 로」](#같은-작업을-모드-b-로) 에 있다.

## 상황

`cdp-work` 으로 BZD020 에 사진 첨부를 넣는 작업을 마쳤다. 이제 기록한다.

## ① pull

```
$ git -C C:/cdp pull --ff-only
Already up to date.
```

실패하면 **여기서 멈춘다.** 낡은 섹션 위에서 diff 를 만들면 남이 갱신한
것을 덮어 없애고, 그 손실은 조용하다 — 충돌이 아니라 "내가 쓴 것이 맞는
것처럼" 보인다.

## ② 좌표 판정

이번 작업에서 건드린 것을 훑는다.

```
match(["출장보고작성", "출장사진목록", "운행일지"])
출장보고작성   ->  screen:BZD020          (alias · _vocab.md:118)
출장사진목록   ->  (미등재)  _vocab.md 에 없습니다
운행일지       ->  (미등재)  _vocab.md 에 없습니다
```

판정 근거를 보여준다.

```
【좌표 판정】
  screen:BZD020         변경   사진 첨부 영역 신설 · 입력 영역을 맨 위로
  table:pj_trip_photo_list  신설   사진 저장 테이블 (미등재 → ④에서 등재)
  issue:ISS-015         제기   차량 이용 여부를 무엇으로 판정하는지 안 정해짐
  screen:BZD012         참조   출장등록에서 넘어오지만 안 바뀜  → 좌표 아님
  운행일지              언급   "차량 이용자는 운행일지로 갈음" → 대상 아님
```

작업 중 결정 못 할 것을 만나 대장에 올렸으면 **그것도 이 작업이 만든 좌표다.**
대장으로 보내되 `touches` 에는 남긴다.

**제외한 것을 적어야 사용자가 고칠 수 있다.** 좌표를 잘못 붙이면 6개월 뒤
찾는 사람이 못 찾고, 그때는 이 판정을 되짚을 수 없다.

## ④ 파생 갱신 — ③ 과 함께 필수

### 어휘 등재부터

`_vocab.md` 의 `## table` 에 이름순 자리로.


**이 섹션만 읽고 화면의 현재 상태를 알 수 있다.** 이렇게 쓰면 안 된다 —

```markdown
## BZD020 — 출장보고작성
<!-- applied: 2026-0908-출장보고-사진첨부 -->

출장보고작성. 사진 첨부 영역을 추가했다.
```

*"추가했다"* 는 **사건**이고 섹션이 담을 것은 **상태**다. 어디에 붙는지,
누구용인지, 몇 장인지, 이용자는 어떻게 되는지가 없다. 주입은 이 섹션만
싣기 때문에 저 링크는 아무도 안 탄다.

`docs/테이블정의서.md` 에는 `## pj_trip_photo_list` 섹션을 **새로 만든다.**
등록부의 `table:*` 이 이미 이 좌표를 거기로 보내므로, 안 만들면 —

```
[오류] 등록부가 가리키는 섹션이 없음  1건
   table:pj_trip_photo_list  docs/테이블정의서.md 에 `## pj_trip_photo_list` 섹션이 없음
```

`docs/위험및이슈관리대장.md` 에도 `## ISS-015` 를 **새로 만든다.** 등록부의
`issue:*` 이 이 좌표를 거기로 보낸다 — `module:` · `domain:` 과 달리 **대장은
파생 대상이다.**

```markdown
## ISS-015 — 차량 이용 여부 판정 기준
```

## 같은 작업을 모드 B 로

①이 없고 ⑤가 도구 한 번이다. ②③④ 의 판단은 **글자 하나 다르지 않다.**

```
# ① 없다

# ② 같다 — 도구 이름이 같다
match(["출장보고작성", "출장사진목록", "운행일지"])

# ④ 섹션을 읽는다. **파일을 열지 않는다** — where 뒤에 Read 가 아니라 section 이다
section("screen:BZD020")
  → { coord, doc, anchor, applied: "2026-0715-외부인원-신설", body: "…" }
apply("screen:BZD020")          # 변경 줄 초안

# ③④ 를 메모리에 만든다. **파일은 안 만든다**

# ⑤B-0 【좌표 판정】 · 기록 · 섹션 초안을 보이고 승인을 받는다 — 승인 전에는 save 를 부르지 않는다

# ⑤B 한 번
save({ repo: "alpha", work: {...}, sections: [{ coord: "screen:BZD020",
       applied: "2026-0715-외부인원-신설", body: "…" }], vocab: [...] })
  → { commit: "1bc1eec", sections: 2, vocab: 1, mirror: "queued" }
```

`applied` 에 `section` 이 준 값을 그대로 넣은 것이 중요하다. 거기에 이 기록의
`id` 를 넣으면 안 된다 — **그것은 서버가 쓴다.** 낙관적 잠금이라 보낸 값이
현재와 다르면 `E_CONFLICT` 로 거부된다.

확인도 도구다 — `derive()` · `where("issue:ISS-015")` · `check()`.
`check` 는 `save` 가 안에서 같은 것을 돌리므로 **미리 보는 용도**다.

## 자주 걸리는 자리

### "정본에 뭘 써야 할지 모르겠다"

**확신이 없으면 반영하지 마라. 그리고 그때는 ③ 도 아직 쓰지 마라.**

안 채운 것은 검사가 알려주지만 **틀리게 채운 것은 아무도 모른다.**

### "바뀐 게 없는데 파생하라고 한다"

그 작업이 그 좌표를 **쓰는 방식만** 바꿨을 수 있다. 그러면 섹션 본문은
그대로 두고 변경 줄만 남긴다.

```markdown
**변경**
· 2026-09-02 [`BZA021-외부심의위원`](../work/2026-0902-BZA021-외부심의위원.md) `wrk_tp_cd` 를 선택 모달 그룹핑 키로 사용. 컬럼 변경 없음
```

### "요청이 셋이었는데 기록도 셋인가"

**아니다.** 한 작업이면 기록 하나다. 요청마다 기록하면 이력이 파편화되고,
같은 좌표에 남은 기록들이 서로의 후속이 되어 파생 판정이 시끄러워진다.

### "커밋이 막혔다"

메시지를 읽는다. 오류 이름이 무엇을 해야 하는지 말해 준다.

| | |
|---|---|
| `unregistered-coord` | `_vocab.md` 에 등재 |
| `dangling-anchor` | 관리 문서에 섹션 신설 |
| `derive-missing` | `ctx apply <좌표>` · `cdp-managed` |
| `id-mismatch` | `id` 와 파일명을 맞춘다 |
| `agenda-status` | 결정이 안 났다 → 이슈 대장으로 |

**`--no-verify` 로 넘기지 마라.** 한 번 통하는 것을 보면 다음에 급할 때 쓴다.

## 도구가 없을 때

**에이전트는 이 절을 쓸 일이 없다.** `cdp` 서버가 붙어 있으면 본문 그대로 부른다.
여기는 **커밋 훅**과 **사람이 터미널에서 칠 때**를 위한 것이다.

`<repo>` 는 지식 레포 경로, `ctx` 는 `<repo>/bin/ctx` — **Node 가 없어도 돈다**
(없으면 `cdp.exe` 로 넘어간다 · 작업환경 §3.1).

| 본문 | 터미널 |
|---|---|
| `match(["a","b"])` | `ctx match "a" "b"` |
| `where("screen:HRC043")` | `ctx where screen:HRC043` |
| `section("screen:HRC043")` | `ctx where` 뒤에 그 섹션을 연다 — **도구 쪽이 한 번에 준다** |
| `apply("screen:HRC043")` | `ctx apply screen:HRC043` |
| `derive()` | `ctx derive` |
| `check()` | `ctx check` |
| `sync()` | `ctx sync` |
| `search("말")` | `ctx search "말"` |

**`cdp` 가 안 붙어 있으면 그것부터 고친다.** `ctx setup <작업레포>` 가
`.mcp.json` 을 쓰고, Claude Code 를 다시 켜면 `/mcp` 에 `cdp` 가 뜬다.
붙지 않은 채로 bash 로 `ctx` 를 부르는 것은 **되기는 하지만 정상이 아니다** —
그 상태에서는 도구 명함이 없어서 무엇을 언제 부를지가 이 문서에만 있다.
