# cdp-curate — 대기열의 기록을 관리 문서에 반영한다

```
① 대기열   queue — 아직 판정 안 받은 작업 기록, 오래된 순
② 묶기     같은 좌표 · 같은 주제 — 섹션 50 이하가 save 하나
③ 재료     queue({ id }) · work · section — 기록 본문 · 지금 섹션 · applied · 기준선 · 건 정본
④ 판정     기록마다 반영 · 새 문서 · 기록으로 둠 — 사실마다 정본 자리 하나
⑤ 쓰기     정본 한 곳 · 현재형 · 경과 한 줄 · 기준선 블록 밖 · 종류별 모양
⑥ 미리보기  save({ …, dryRun: true }) — 판정표 + 섹션 diff 를 보이고 승인
⑦ save     승인받은 입력에서 dryRun 만 뺀다 — 큐레이션 기록 하나 + 섹션 · 새 문서 한 커밋
⑧ 끝 보고   커밋 · 미러 · 남은 대기
```

**큐레이터만 쓴다.** 큐레이터는 레포별 권한이다(명부의 `curate` · admin 은 모든 레포의 큐레이터). `queue` 도구가 안 보이거나 `E_FORBIDDEN` `need: curate` 가 오면 여기서 멈추고 그렇게 말한다 — writer 는 고칠 것을 **기록만 남기고**(cdp-save) 큐레이터에게 맡긴다.

**서버는 글을 쓰지 않는다.** 반영의 판단과 글은 이 세션이 하고, 서버는 권한 · 검사 · 커밋 · `applied` 계산만 한다. 그래서 승인이 이 대화에 있어야 한다.

인자 — `cdp-curate <레포> [기록 id …]`. 화면의 [에이전트 지시 복사] 는 같은 뜻을 여러 줄로 준다 — 첫 줄 `cdp-curate <레포>` · `대상:` 뒤에 기록 id 를 한 줄에 하나 · 끝에 규칙 한 줄(「대상: (대기열 전부 …)」 이면 id 없음과 같다). 레포를 안 주면 `.claude/cdp.json` 의 `repo` · id 가 없으면 ① 부터.

## ① 대기열

```
queue({ repo })
```

- `items` — 아직 아무도 판정하지 않은 작업 기록, **오래된 순**. 행마다 `coords: [{ coord, cls }]` · `zero`(좌표 0) · `ageDays`. `oldestDays` 가 14일을 넘으면 검사가 경고한다 — 오래된 것부터 다룬다.
- `cls` — `section`(섹션이 있다 · 반영 후보) · `anchor`(등록부 행은 있는데 문서 · 섹션이 없다 · 섹션을 만들며 반영) · `unregistered`(등록부가 없다 · 새 문서 후보 또는 기록으로 둠).
- 대기열 밖(이미 판정된) 기록도 다시 다룰 수 있다 — 섹션을 고쳐 쓸 때. **가장 늦은 판정이 이긴다.**
- 큐레이션 · 기준선 · 등록부 정리 기록은 대기열에 서지 않는다.

## ② 묶기 — save 하나의 크기

- **같은 좌표를 건드린 기록은 한 묶음이다** — `queue({ id })` 의 `together` 가 알려 준다. 따로 반영하면 같은 섹션을 두 번 쓰고 둘째가 첫째를 덮는다.
- **같은 주제**(한 결정의 사전 조사 · 초안 · 결정)는 한 묶음이다 — 정본 자리를 한 번에 정한다.
- 한 묶음 = save 하나 = 큐레이션 기록 하나. **섹션 50 이하**(save 상한). 넘으면 주제로 나눈다.
- 대기가 많으면 묶음 목록을 먼저 보이고 하나씩 승인받는다. **한 번에 다 하지 않는다** — 큰 diff 는 승인이 형식이 된다.

## ③ 재료

```
queue({ repo, id: "2026-0908-ERP-연계방식-결정" })
work({ repo, id: "2026-0908-ERP-연계방식-결정" })
section({ repo, coord: "이슈:ISS-007" })
```

| 도구 | 주는 것 |
|---|---|
| `queue({ id })` | `record`(제목 · 날짜 · 작성자 · touches · 첫 문단) · `coords`(좌표마다 `cls` · `doc` · `state` · `applied` · `pending`) · `unregisteredTypes`(등록부 없는 타입 — 서식 후보) · `bodyOnly`(본문에만 있는 좌표) · `together` |
| `work({ id })` | 기록 본문. **오래된 기록부터 읽는다** — 추가했다가 이름을 바꾼 경우 최신만 읽으면 추가를 놓친다 |
| `section({ coord })` | `content`(지금 큐레이터의 글) · `applied`(**잠금 값 — 그대로 보낸다**) · `baseline`(기계 블록) · `pendingRecords`(이 좌표의 미반영 전부 — 묶음 밖 기록이 여기서 보인다) · `refs`(건 정본) · `form`(그 문서의 서식) |

- 기록이 홀로 서지 못하면(「섹션 X 참조」 · 「DB 에서 확인」 · 값 없는 「정했다」) **지어내지 않는다** — 작성자에게 묻거나 대기열에 남긴다.
- `bodyOnly` — 본문에만 있는 좌표다. 기록이 그 대상을 바꿨으면 반영할지 판정표에 적고, 언급이면 둔다.

## ④ 판정 — 기록마다 하나

| 판정 | `verdict` | 언제 | 보낼 것 |
|---|---|---|---|
| **반영** | `reflect` | 기록의 사실이 있는 섹션(또는 등록부 행만 있는 자리)에 들어간다 | `into: [좌표]` — **그 좌표들이 이 save 의 `sections` 에 있어야 한다** |
| **새 문서** | `new` | 받을 문서가 없다 — 서식에서 세우고 반영한다 | `into` + `managed` 의 새 행 · 문서(아래 「새 문서」) |
| **기록으로 둠** | `keep` | 섹션에 옮길 사실이 없다 — 경위 · 회의 논의 · 사전 지식 · 버린 안 · 참조만 한 기록. 기록이 원천으로 남는다 | `reason` 한 줄 |

- **판정은 기록 단위지만 미반영은 섹션마다다** — 반영(`reflect` · `new`)은 `into` 의 섹션에서만 미반영을 지운다. 그 기록이 건드린 다른 좌표의 섹션은 그 기록이 applied 보다 늦으면 **계속 미반영으로 남는다**(그 섹션은 아직 그 기록을 싣지 않았다). 그래서 기록의 `touches` 를 하나씩 본다: 반영할 좌표는 전부 `into` 에(그 섹션은 이 save 의 `sections` 에), 바뀐 게 없는 좌표도 `into` 에 넣고 경과 한 줄(아래), 그 섹션과 정말 무관하면 판정표에 까닭을 적는다. `keep` 은 기록 전체에 대한 판정이라 모든 좌표에서 미반영이 사라진다. 한 기록의 좌표를 이번 묶음에서 다 다루지 못하면 그 기록은 이번 `curates` 에서 빼 둔다.
- **바뀐 게 없는데 좌표가 걸렸으면** — 그 기록이 대상을 쓰는 방식만 바꿨을 수 있다. `reflect` 로 섹션 `content` 를 그대로 두고 경과 한 줄만 더한다(「컬럼 변경 없음 — 선택 모달의 묶음 키로 쓴다」). 바뀐 게 없다는 것도 사실이다 — 안 적으면 다음 사람이 같은 확인을 다시 한다. 경과에도 남길 것이 없으면 `keep`.
- **확신이 없으면 판정하지 않는다** — `curates` 에서 빼면 대기열에 남고 섹션 옆에 계속 실린다. `keep` 은 「옮길 것이 없다」 는 판정이라 미반영 표시가 사라진다 — 모를 때 쓰지 않는다. 안 채운 것은 대기열이 말하지만 **틀리게 채운 것은 아무도 모른다.**
- **문서를 고치라는 지시 기록** — 본문의 「지시 · 바꿀 것 · 확인한 것」 이 재료다. 지금 섹션이나 다른 기록이 정한 이유와 어긋나면 반영하지 않고 지시한 사람에게 묻는다(대기열에 남긴다). 반영하면 경과에 그 지시 기록을 건다.
- **등록부 밖 문서**(회의록 · 가이드처럼 서식의 `registry` 가 빈 사건 · 서술 문서)에 옮길 것은 `edits` 로 쓴다(cdp-registry 「섹션 밖 글」). `into` 는 좌표만 받으므로 그 기록은 `keep` 에 `reason: "<문서> 에 반영(edits)"`.
- **좌표 0 기록**(`zero`)은 대개 `keep` 이다. 옮길 사실이 있으면 그 자리에 반영해도 된다 — `into` 는 기록의 `touches` 밖이어도 된다. 기록의 `touches` 가 틀렸으면(빠진 좌표) 반영은 맞는 자리에 하고 작성자에게 정정 기록을 청한다 — 좌표로 찾아오는 길은 `touches` 뿐이다.

### 정본 자리 — 사실 하나에 하나

한 결정이 여러 좌표에 걸리면 — 이슈 · 아키텍처 · 용어 · 인터페이스를 다 건드리면 — **정본은 하나다.**

- 그 사실을 **가장 오래 책임지는 대상**의 섹션이 정본이다 — 규격이면 인터페이스 · 컬럼이면 테이블 · 뜻이면 용어. 대장(이슈 · 위험)은 정본이 되지 않는다 — 결론 한 줄과 정본 좌표만 둔다.
- **정본 자리가 비어 있으면 가까운 좌표에 쓰지 않는다** — 새 좌표를 등재(`vocab`)하고 그 섹션을 세운다. 이미 있는 좌표(이슈)가 받아 주면 대장이 설계서가 된다.
- 판정표의 **「정본」 줄**에 적고 같이 승인받는다.

## ⑤ 섹션 쓰기

`sections[].body` 는 `section` 이 준 **`content` 를 고친 것**이다 — 헤딩 줄 · `<!-- applied -->` · 기준선 블록 없이. 헤딩과 applied 는 서버가 붙인다(섹션 레벨의 `##` 헤딩 줄을 넣으면 `E_INPUT`). 섹션 안의 소제목은 `###` 아래나 굵은 글씨로. `applied` 는 `section` 이 준 값 그대로 보낸다 — 낙관 잠금이다. 새 `applied` 는 서버가 계산한다(반영한 기록 중 그 좌표의 가장 늦은 것). 그래서 `sections` 의 좌표는 어느 판정의 `into` 에 들어 있게 한다 — 판정 없이 섹션만 고치면 그 섹션의 `applied` 가 이 큐레이션 기록이 된다(글만 다듬을 때는 그래도 되지만 판정표에 적는다).

| 규칙 | |
|---|---|
| **정본 한 곳** | 사실은 정본 섹션에만 쓴다. 다른 섹션은 한 줄 — 무엇이 바뀌었나 + 정본 좌표를 `` `좌표` `` 로 건다. `section` 이 그 정본을 한 단계 따라가 같이 싣는다(`refs`) — 복제하지 않아도 읽는 쪽이 값을 본다 |
| **정본 섹션은 홀로 선다** | 그 섹션만 읽고 대상의 지금을 알 수 있어야 한다 — 판단 · 표 · 규칙 · 값 · 제약 중 대상의 성질이 된 것은 전부 옮긴다. 경위 · 논의 · 대안은 기록의 것이다 |
| **현재형으로 다시 쓴다** | 섹션은 대상의 **지금**이다. 날짜별로 덧붙이지 않는다. 뒤집힌 판단은 본문에서 지우고 경과에 한 줄로 남긴다. 「추가했다」 는 사건이다 — 섹션이 담을 것은 상태(어디에 · 누구용 · 몇 개 · 예외)다 |
| **경과는 끝 목록 한 줄씩** | 섹션 끝 `**경과**` 아래 `- YYYY-MM-DD [`<id 의 주제>`](<상대경로>/work/<id>.md) 무엇이` — 날짜는 기록의 날. 추가만 한다(지난 줄을 지우지 않는다). 경과는 출처 표시지 내용이 아니다 — 경과만 붙이고 본문을 안 고치면 반영이 아니다 |
| **기준선 블록은 손대지 않는다** | `baseline`(컬럼 표 같은 기계 추출)은 생성기의 자리다. 큐레이터의 글은 블록 밖에만 — 블록 표지를 본문에 넣으면 거절된다. 서버가 블록을 `**경과**` 앞에 다시 붙인다. 블록이 이미 말하는 값을 서술에 다시 옮기지 않는다. 블록이 틀렸으면 생성기 담당에게 |
| **근거보다 크게 쓰지 않는다** | 섹션이 근거 기록들보다 몇 배 크면 출처가 기록 밖이다 — 기록에 없는 것을 지어낸 것이다 |
| **종류별 모양** | 서식의 `kind` 와 `guide` 를 따른다 — 아래 표 |

- 경과 · 그림 링크는 **그 문서에서 본 상대경로**다 — `docs/X.md` 면 `../work/…` · `docs/1.관리/X.md` 면 `../../work/…`.
- 섹션 밖은 건드리지 않는다 — 문서 머리말 · 다른 문서의 산문은 cdp-registry 「섹션 밖 글」(`edits`).
- 서식 `guide` 에 옛 표기(`**변경** · 날짜 …` 줄 · 「파생이 남으면 커밋이 막힌다」)가 남아 있으면 이 스킬이 우선이다 — 목록 이름은 `**경과**`.

### 종류별 모양

종류는 문서에 적혀 있지 않다 — 그 문서의 서식(`section` 의 `form` → `forms({ form })` 의 `kind`)에서 온다. 서식 없이 세운 문서는 가장 가까운 종류로 쓴다.

| 종류 | 문서 예 | 섹션은 | 덮어쓰나 |
|---|---|---|---|
| **대상** | 테이블 · 화면 · 인터페이스 · 코드 · 기능 | 대상의 현재 사양 — 표 · 규칙 · 예외 | 본문은 덮어쓴다 · 경과만 쌓는다 |
| **대장** | 이슈 · 위험 · 형상 · 일정 | 고정 표 + **결론 한 줄** + 경과. 설계 서술 금지 — 내용은 정본 좌표로 건다. 진행상태는 서식이 정한 어휘로만 | 표 · 결론은 덮어쓴다 |
| **정의** | 용어 · 도메인 용어 | 뜻 · 쓰임 · 관련 좌표. 프로젝트의 판단 · 선례 · 수치는 넣지 않는다 | 덮어쓴다 |
| **사건** | 회의록 · 보고서 · 결과서 | 결정 · 할 일 목록만. 원문 · 논의는 작업 기록 | 추가만 |
| **서술** | 가이드 · 계획서 · 매뉴얼 | 문서 전체가 내용 — 절을 고쳐 쓴다(등록부 밖이면 `edits`) | 고쳐 쓴다 |

대장 섹션이 40줄 · 정의 섹션이 25줄을 넘으면 서술이 들어간 것이다 — 정본 자리로 옮긴다. 전후 예시(일지형 → 현재형 · 대장 · 정의 · 기준선이 있는 섹션) — **[종류별.md](종류별.md)**.

## 새 문서 — 서식에서

1. `forms({ repo, q: "<말>" })` — 제목 · 관리번호 · 등록부 타입으로 찾는다. `queue({ id })` 의 `unregisteredTypes` 가 좋은 말이다. `used: true` 면 이 레포에 그 서식의 문서가 이미 있다 — 새로 세우지 말고 거기 붙인다.
2. `forms({ repo, form: "<id>" })` — `head`(새 문서의 첫 문단) · `guide`(무엇 · 여기 적지 않는 것 · 섹션 모양) · `example` · `stamp`(서버가 실제로 찍을 빈 문서) · `registry`(패턴 제안) · `coordValue`(좌표 값이 무엇인가) · `kind`. **guide 를 읽고 쓴다** — 「여기 적지 않는 것」 이 정본 자리를 정한다.
3. 맞는 서식이 없으면 서식 없이 세운다(`# 제목` 한 줄) — 억지로 비슷한 서식을 고르지 않는다. 이름이 같은 서식이 묶음마다 있으면(`시스템아키텍처` 넷) `group` 을 보고 고른다.
4. `managed: [{ pattern: "<타입>:*", doc: "docs/<경로>.md", form: "<id>" }]` — **패턴의 타입은 기록이 쓴 좌표의 타입이다**(서식의 `registry` 는 제안). 경로 · 패턴 · 겹침 · 어긋나는 문구 · `needSections` 의 규칙은 **cdp-registry 「행 더하기」**.
5. 새 섹션은 `applied: null` · `heading: "<값> — <설명>"`(값으로 시작). 서버는 제목 · 서식 표지 · 첫 문단만 찍는다 — 예시 · 작성지침은 문서로 가지 않는다.

## ⑥ 미리보기와 승인

승인 게이트는 cdp-save 「승인 게이트」 와 같다 — **승인 전에는 커밋하는 `save` 를 부르지 않는다.** 먼저 같은 입력에 `dryRun: true` 를 붙여 보낸다 — 서버가 권한 · 판정(`into` 가 `sections` 에 있나) · 잠금(`applied`) · 등록부 · 검사까지 돌고 **커밋하지 않는다.** 걸리는 것은 여기서 고친다. dryRun 은 diff 를 주지 않는다 — diff 는 `section` 의 `content`(전)와 보낼 `body`(후)로 네가 만든다.

```
【판정표】 큐레이션 — ERP 연계 기록 3건 · 섹션 3 · 새 문서 1
  기록                              판정       어디로 · 사유
  2026-0901-ERP-연계-사전조사         keep       사전 조사 — 결론은 방향 결정 기록이 원천
  2026-0903-ERP-전문규격-초안         new        인터페이스:ERP-결의서전송(새 문서 docs/인터페이스정의서.md · 서식 public-si/DE_501) · 이슈:ISS-007(경과 한 줄)
  2026-0908-ERP-연계방식-결정         reflect    인터페이스:ERP-결의서전송 · 이슈:ISS-007 · 시스템아키텍처:link
  정본   전문 규격 → 인터페이스:ERP-결의서전송 (이슈 · 아키텍처는 결론 한 줄 + 좌표)
【등록부 변경】 행 인터페이스:* → docs/인터페이스정의서.md ## {값} (서식 public-si/DE_501 · 새 문서)
【섹션 diff】 좌표마다 지금 content → 보낼 body (바뀐 대목만 · 새 섹션은 전문)
【dryRun】 통과 · warnings 그대로
승인하시면 커밋합니다. 판정 · 정본 · 문장을 고칠 것이 있으면 알려 주세요.
```

사람이 고치라고 하면 고쳐서 다시 dryRun → 다시 보인다. 승인되면 ⑦. (좌표 · 문서 이름은 예시다 — 그 레포의 것을 쓴다.)

## ⑦ save — 큐레이션 기록 하나

```
save({
  repo: "alpha",
  work: {
    id: "2026-0910-큐레이션-ERP연계",
    title: "큐레이션 — ERP 연계 기록 3건",
    date: "2026-09-10 10:20",
    curates: [
      { id: "2026-0901-ERP-연계-사전조사", verdict: "keep", reason: "사전 조사 — 결론은 방향 결정 기록이 원천" },
      { id: "2026-0903-ERP-전문규격-초안", verdict: "new", into: ["인터페이스:ERP-결의서전송", "이슈:ISS-007"] },
      { id: "2026-0908-ERP-연계방식-결정", verdict: "reflect", into: ["인터페이스:ERP-결의서전송", "이슈:ISS-007", "시스템아키텍처:link"] }
    ],
    body: "# 큐레이션 — ERP 연계 기록 3건\n\n(판정표 — 기록마다 판정 · 어디로 · 사유 · 정본)"
  },
  sections: [
    { coord: "인터페이스:ERP-결의서전송", applied: null, heading: "ERP-결의서전송 — ERP 결의서 전송", body: "…" },
    { coord: "이슈:ISS-007", applied: "<section 이 준 값>", body: "…" },
    { coord: "시스템아키텍처:link", applied: "<section 이 준 값>", body: "…" }
  ],
  managed: [{ pattern: "인터페이스:*", doc: "docs/인터페이스정의서.md", form: "public-si/DE_501" }]
  // vocab: [{ coord, label, aliases }]   — 어느 기록도 안 건드린 새 정본 좌표를 세울 때만
})
```

- **큐레이션 기록은 `touches` 를 갖지 않는다** — 서버가 `touchesEmpty: 큐레이션` · 태그 `curate` 를 붙인다. 다룬 기록과 좌표는 `curates` 의 `id` · `into` 에 있다.
- **본문은 판정표다** — 기록마다 판정 · 어디로 · 사유, 그리고 정본을 어디로 정했나. 기록 링크는 같은 폴더라 `[2026-0908-ERP-연계방식-결정](2026-0908-ERP-연계방식-결정.md)`. 좌표는 **백틱 없이** 적는다 — 큐레이션 기록은 `touches` 가 없어 백틱 좌표마다 「본문에만 있는 좌표」 경고가 난다.
- `id` 는 `YYYY-MMDD-큐레이션-<주제>` · `date` 는 지금(시각까지).
- 한 save 에 기준선(`baseline`)과 큐레이션을 섞지 않는다 — 기계의 자리와 사람의 판단은 따로 남긴다.

## 충돌 · 거절 — 한 벌

| 응답 | 할 일 |
|---|---|
| `E_CONFLICT` (섹션) | 읽은 뒤 누가 그 섹션을 바꿨다 — `detail.current`(지금 applied) · `detail.currentWork`(그 applied 가 가리키는 기록 — 제목 · 작성자 · 날짜) · `detail.currentCuration`(그 기록을 반영해 섹션을 고친 큐레이션 기록 — 작성자 · 날짜, 있을 때) · `detail.content`(지금 본문). **`content` 위에 다시 만들고 `applied` 에 `current` 를 넣어** dryRun 부터 다시. 옛 본문을 그대로 다시 보내면 그 사람의 반영이 사라진다. `truncated: true` 일 때만 `section` 을 다시 읽는다. 다른 큐레이터였으면 `work({ id })` 의 `curation` 으로 내 묶음의 기록이 이미 판정됐는지 보고, 됐으면 빼거나 알고 다시 다룬다 |
| `E_CONFLICT` (`edits`) | `old` 가 원문에 없다 — 읽은 뒤 바뀌었다. `docs({ repo, doc })` 로 다시 읽고 `old` 를 다시 뗀다 |
| `E_CONFLICT` `detail.kind: managed` | 같은 패턴이 다른 문서에 이미 있다 — cdp-registry 「행 더하기」 |
| `E_INPUT` 「into … 가 이 save 의 sections 에 없다」 | 반영한 섹션을 같이 보낸다(바뀐 게 없으면 `content` 그대로 + 경과) · 반영하지 않을 기록이면 `keep` |
| `E_INPUT` 「헤딩 줄이 있다」 · 「기준선 블록 표지가 있다」 | `body` 에 `##` 헤딩이나 블록을 넣었다 — `section` 의 `content` 를 고쳐 보낸다(헤딩 · 블록은 서버가 붙인다) |
| `E_INPUT` `needSections` · `lines` · `shadowedBy` | 등록부 행의 일 — cdp-registry 「행 더하기」 |
| `E_INPUT` 「큐레이션 · 기준선 · 옛 기계 기록이다」 | `curates` 에는 사람의 작업 기록만 넣는다 |
| `E_EXISTS` | 큐레이션 기록 id 가 있다 — 다른 id |
| `E_CHECK` | **이 save 가 만든** 오류다(같은 이름의 섹션이 둘 · 미등재 좌표 등) — `detail.findings` 를 고쳐 다시. 원래 있던 오류는 경고로 온다 |
| `E_FORBIDDEN` `need: curate` | 이 레포의 큐레이터가 아니다 — 멈춘다 |

`section` → 쓰기 → `save` 사이가 짧을수록 충돌이 적다 — 묶음 하나씩 읽고 바로 보낸다.

## ⑧ 끝 보고

커밋 · 미러는 cdp-save 「끝 보고」 표 그대로. 그리고 —

- 판정 수(반영 n · 새 문서 n · 기록으로 둠 n) · 바뀐 섹션 · 세운 문서.
- `brief({ repo })` 의 `curation.queue` — 남은 대기 n건 · 가장 오래된 m일. 다음 묶음이 있으면 제안한다.
- 판정하지 않고 남긴 기록과 그 까닭(작성자에게 물을 것).

## 하지 않는 것

| | 어디로 |
|---|---|
| 이 세션 자신의 작업 기록 | cdp-save |
| 등록부 행만 · 이름 · 합치기 · 폐기 · 지우기 · 서식 예시 정리 · 섹션 밖 글 | cdp-registry |
| 기준선 블록 안 | 프로젝트의 생성기(기준선 save) |
| 옛 레포를 기록만으로 다시 세우기 | admin — 콘솔 「새 지식 레포」 · `ctx repo new --records-from` |
| 기록 고치기 · 지우기 | 없다 — 기록은 불변이다(작성자가 정정 기록을 낸다) |
