# 종류별 섹션 — 전후 예시

cdp-curate ⑤ 의 표를 실물로 본다. 좌표 · 문서 이름은 예시다. 섹션은 `section` 의 `content` 모양 — 헤딩 줄과 `<!-- applied -->` 는 서버가 붙이므로 `body` 에 넣지 않는다(아래에서는 읽기 쉽게 헤딩을 같이 보인다).

## 대상 — 사건이 아니라 상태

**틀린 것** — 기록의 사건을 옮겼다.

```markdown
## BZD020 — 출장보고작성
출장보고작성. 사진 첨부 영역을 추가했다.

**경과**
- 2026-09-08 [`출장보고-사진첨부`](../work/2026-0908-출장보고-사진첨부.md) 사진 첨부 영역
```

「추가했다」 는 사건이다. 어디에 붙는지 · 누구용인지 · 몇 장인지 · 예외가 없다 — 이 섹션만 읽은 사람은 첨부 규칙을 모른 채 다시 정한다.

**맞는 것** — 대상의 지금.

```markdown
## BZD020 — 출장보고작성
출장보고작성. **입력 영역은 화면 맨 위**다 — 아래에 두면 본인이 출장자가 아닐 때 입력할 줄 모르고 넘어간다.

입력 영역 안, 보고 내용 아래에 **사진 첨부**가 있다. 차량 미이용자용이고 여러 장이다(`table:pj_trip_photo_list` 에 순번으로).
차량 이용자는 운행일지로 갈음한다. 누가 미이용자인지 가르는 기준은 아직 열려 있다 — `issue:ISS-015`.

**경과**
- 2026-08-21 [`출장보고-입력영역`](../work/2026-0821-출장보고-입력영역.md) 입력 영역을 따로
- 2026-09-08 [`출장보고-사진첨부`](../work/2026-0908-출장보고-사진첨부.md) 사진 첨부 · 입력 영역 상단
```

## 대상 + 기준선 — 기계의 자리와 사람의 자리

```markdown
## pj_trip_photo_list — 출장사진목록
출장 건별 사진. 여러 장이라 목록 테이블이다 — `screen:BZD020` 의 첨부 영역이 쓴다.
차량 이용자는 운행일지로 갈음해 행이 없다.

**제약** — `file_key` 는 파일 저장소 키다. 행을 지우면 파일도 지운다.

<!-- cdp:baseline src="개발 DB 카탈로그" asof="2026-09-20" -->
| 컬럼 | 타입 | NULL | 키 | 설명 |
|---|---|:--:|:--:|---|
| `trip_id` | varchar(20) | N | PK | 출장 건 |
| `seq` | int | N | PK | 순번 |
| `file_key` | varchar(100) | N | | 파일 저장소 키 |
<!-- /cdp:baseline -->

**경과**
- 2026-09-08 [`출장보고-사진첨부`](../work/2026-0908-출장보고-사진첨부.md) 테이블 신설
```

- 큐레이터가 보내는 `body` 는 블록 **밖**뿐이다 — 서술 · 제약 · 경과. `section` 의 `content` 도 블록을 뺀 것이고, 서버가 블록을 `**경과**` 앞에 다시 붙인다.
- 컬럼 표를 서술에 다시 옮기지 않는다 — 블록이 말한다. 서술이 담는 것은 블록이 모르는 것(누가 쓰나 · 왜 · 제약)이다.
- 기준선이 없는 레포(생성기가 없다)면 기록이 준 컬럼 표를 서술에 쓴다 — 그때는 기록이 원천이다.

## 대장 — 일지를 결론으로

**틀린 것** — 기록마다 덩어리를 덧붙였다. 지금 상태를 알려면 다섯 덩어리를 머릿속에서 합쳐야 하고, 앞 덩어리의 판단은 뒤에서 뒤집혔는데 지워지지 않았다.

```markdown
## ISS-007 — ERP 결의서 연계 방식
| 진행상태 | 처리중 |
### 사전 조사 (09-01)
ERP 는 파일 연계와 DB 직접 연계를 둘 다 받는다. 파일 연계가 무난해 보인다 …
### 전문 규격 초안 v0.1 (09-03)
(필드 32개 표 · 40줄)
### 방향 결정 (09-08)
DB 직접 연계로 간다. 파일 연계는 야간 배치가 늦어 버린다 …
```

**맞는 것** — 고정 표 + 결론 한 줄 + 경과. 규격은 정본 자리(인터페이스)로 옮기고 좌표만 건다.

```markdown
## ISS-007 — ERP 결의서 연계 방식
| 유형 | 기술 |
|---|---|
| 처리 담당 | 연계 개발 |
| 진행상태 | 해결 |

**결론** — DB 직접 연계로 간다(파일 연계는 야간 배치가 늦어 버렸다). 전문 규격은 `인터페이스:ERP-결의서전송`.

**경과**
- 2026-09-03 [`ERP-전문규격-초안`](../work/2026-0903-ERP-전문규격-초안.md) 전문 규격 초안 — 인터페이스로
- 2026-09-08 [`ERP-연계방식-결정`](../work/2026-0908-ERP-연계방식-결정.md) DB 직접 연계로 결정 · 해결
```

- 진행상태는 서식 `guide` 가 정한 어휘로만 — 칸에 문장을 쓰지 않는다. 해결이면 결론에 정본 좌표를 단다.
- 대장은 **아직 끝나지 않은 것**의 자리다. 끝난 판단의 내용은 기록과 정본 섹션에 있다.

## 정의 — 뜻만

**틀린 것** — 용어에 프로젝트의 판단이 섞였다.

```markdown
## ODBC — 데이터베이스 연결 표준
DB 에 접속하는 표준 인터페이스. 우리 프로젝트는 ERP 연계에서 ODBC INSERT 로 간다.
선례 현장에서 이 방식의 오류율이 높았고 …(판단 · 선례 · 수치 20줄)
```

**맞는 것** — 뜻 · 쓰임 · 관련 좌표. 판단은 그 판단의 정본(이슈 결론 · 인터페이스)에 있고 여기서는 건다.

```markdown
## ODBC — 데이터베이스 연결 표준
DB 에 접속하는 표준 인터페이스. 드라이버만 바꾸면 DBMS 가 달라도 같은 호출로 붙는다.
쓰는 곳 — `인터페이스:ERP-결의서전송`.
```

## 사건 — 결정과 할 일만

회의록 · 보고서는 대개 서식의 `registry` 가 비어 있다(날짜축) — 좌표 섹션이 아니라 `edits` 로 쓴다(cdp-registry 「섹션 밖 글」). 회의를 들인 **작업 기록이 원문**이고, 문서에는 결정 · 할 일 · 이어지는 곳만 남긴다.

```markdown
## 2026-08-14 — 심의회 준비 회의
**정한 것**
1. BZA021 외부 위원 그리드에 소속 컬럼 — `screen:BZA021`
2. 업무구분 코드그룹 HR130 신설 — `code:HR130`

**정해지지 않은 것** — 외부 ERP 결재 취소의 자동 반영 → `issue:ISS-003`

원문 [`심의회준비-회의록`](../work/2026-0814-심의회준비-회의록.md)
```

그 기록의 판정은 — 결정이 들어간 섹션(BZA021 · HR130)이 이 save 에 있으면 `reflect`(`into` 는 그 좌표들), 회의록 문서에만 옮겼으면 `keep` 에 `reason: "회의록에 반영(edits)"`.

## 서술 — 절을 고쳐 쓴다

가이드 · 계획서는 문서 전체가 내용이다. 규칙이 바뀌면 그 절을 지금 규칙으로 고쳐 쓴다(`edits` — `docs({ doc })` 의 `text` 에서 `old` 를 뗀다). 날짜별 덧붙이기 · 「변경 이력」 절을 만들지 않는다 — 이력은 기록에 있다. 판정은 `keep` 에 `reason: "<문서> <절> 에 반영(edits)"`.

## 정본 한 곳 — 한 결정이 셋에 걸릴 때

기록 `ERP-연계방식-결정` 이 인터페이스 · 이슈 · 아키텍처를 건드렸다. 정본은 인터페이스다 — 규격을 가장 오래 책임지는 대상이다.

| 섹션 | 쓰는 것 |
|---|---|
| `인터페이스:ERP-결의서전송` (정본) | 방식 · 전문 규격 표 · 오류 처리 · 제약 — 홀로 서게 전부 |
| `이슈:ISS-007` | 결론 한 줄 + 정본 좌표 + 경과 |
| `시스템아키텍처:link` | 구성 한 줄(「결의서는 DB 직접 연계 — `인터페이스:ERP-결의서전송`」) + 경과 |

같은 서사를 세 번 쓰면 결정이 바뀔 때 세 곳을 고쳐야 하고, 하나를 놓쳐도 아무도 모른다. 이슈 · 아키텍처를 읽는 쪽은 `section` 의 `refs` 로 정본을 같이 받는다.
