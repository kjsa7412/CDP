# 관리 문서 등록부

좌표가 어느 관리 문서의 어느 섹션에 대응하는지 **여기에만** 적는다.
매핑이 두 곳에 있으면 반드시 어긋난다.

| 좌표 패턴 | 관리 문서 | 섹션 |
|---|---|---|
| `req:*` | `docs/요구사항정의서.md` | `## {값}` |
| `proc:*` | `docs/프로세스정의서.md` | `## {값}` |
| `func:*` | `docs/기능정의서.md` | `## {값}` |
| `arch:*` | `docs/시스템아키텍처정의서.md` | `## {값}` |
| `screen:*` | `docs/화면설계서.md` | `## {값}` |
| `prog:*` | `docs/프로그램사양서.md` | `## {값}` |
| `table:*` | `docs/테이블정의서.md` | `## {값}` |
| `term:*` | `docs/DB도메인용어정의서.md` | `### {값}` |
| `code:*` | `docs/코드정의서.md` | `## {값}` |
| `api:*` | `docs/인터페이스정의서.md` | `## {값}` |
| `batch:*` | `docs/인터페이스정의서.md` | `## {값}` |
| `scenario:UT-*` | `docs/단위테스트시나리오.md` | `## {값}` |
| `scenario:PT-*` | `docs/성능테스트시나리오.md` | `## {값}` |
| `scenario:IT-*` | `docs/통합테스트시나리오.md` | `## {값}` |
| `issue:*` | `docs/위험및이슈관리대장.md` | `## {값}` |

**패턴은 위에서부터 먼저 걸리는 것을 쓴다.** 그리고 **대소문자를 구분한다** —
`scenario:ut-…` 는 `scenario:UT-*` 에 걸리지 않는다.

## 등록부에 없는 좌표는 정상이다

관리 문서는 **자주 쓰는 내용을 하나로 모아 둔 것**이다. 모든 것이 여기 녹지
않는다 — 덜 쓰는 것을 하나로 모으는 부담이 이득보다 크다.

| | 원천 |
|---|---|
| 자주 쓰는 내용 | 관리 문서 섹션 — 하나로 수렴시키고 그 대가로 갱신 부담을 진다 |
| 덜 쓰는 내용 | **그 작업 기록 자체** |

`domain:`(업무 영역)이 그렇다. 바꾸는 대상이 아니라 **작업을 묶는 축**이라
등록부에도 없고 최신성 계산에서도 뺀다.

## 등록부 대상이 아닌 관리 문서 — 32종

대장형 9 · 사건형 10 · 서술형 13. 집계 · 날짜 · 서술 축이라 좌표-섹션이
1:1로 대응하지 않는다. **앱은 문서로 읽고 열 수 있지만 섹션 판정을 하지 않는다.**

## CDP 16종 등록부에서 바뀐 것

| | 16종판 | 여기 | 왜 |
|---|---|---|---|
| `batch:` | 프로그램사양서 | **인터페이스정의서** | 배치는 인터페이스의 `Object` 다 |
| `module:` | 프로그램사양서 | **없다** | 대응 개념이 없다 |
| `test:` | 테스트케이스 | **없다** | 테스트케이스라는 산출물이 없다. 두면 앵커 없음이 난다 |
| `scenario:` | 테스트시나리오 1 | **3으로 쪼갬** | 단위·성능·통합이 별개 산출물이고 제출시기가 다르다 |
