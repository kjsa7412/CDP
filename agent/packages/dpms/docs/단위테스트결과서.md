# 단위테스트결과서

날짜축. **회차마다 쌓인다** — 지난 회차를 덮지 않는다.

| | |
|---|---|
| 관리번호 | `GDI_TE_101` |
| 제출시기 | 구현완료 |
| 필수 제출 | 아니오 |
| 등록부 | **비대상** — 날짜축이다 |

**무엇** — 단위테스트시나리오를 **실제로 밟은 결과**. 무엇이 통과했고 무엇이
실패했으며 그것을 어떻게 처리했는지.
**언제** — 테스트 당일. 처리 결과는 나중에 같은 회차 섹션에 채운다.
**누가** — 테스트를 주관한 사람.

**여기 적지 않는 것**

| | 어디로 |
|---|---|
| 절차 · 중점 점검사항 | `단위테스트시나리오` — **대상에 붙는 상태**다 |
| 언제 누가 모이나 | `단위테스트계획서` |
| **고치지 못하고 남은 것** | `위험및이슈관리대장` — 회차가 끝나도 열려 있으면 이슈다 |

> **시나리오는 상태이고 결과는 사건이다.** 원본은 한 시트에 절차와 결과를
> 섞어 두어 **다음 회차가 지난 회차를 덮었다.** 1차에서 무엇이 FAIL 이었는지
> 남지 않으면 고쳐졌는지 확인할 방법이 없다.

## 작성지침

| 항목 | 작성방법 | 필수 |
|---|---|:--:|
| 섹션 제목 | `<YYYY-MM-DD> — <N>차` | 필수 |
| 참가 · 대상 | 역할 단위. 현업이 참여했으면 반드시 적는다 | 필수 |
| 결과 요약 | `N건 중 M건 PASS` | 필수 |
| 대상 | `단위테스트시나리오` 의 섹션과 **같은 단위** | 필수 |
| 결과 | `PASS` / `**FAIL**`. **FAIL 을 굵게** 해서 눈에 걸리게 | 필수 |
| 수정요청 | FAIL 이면 **무엇이 문제인지** 구체적으로 | FAIL 시 필수 |
| 처리 | `날짜 · 무엇을 고쳤나`. 안 고쳤으면 비운다 | 처리 시 필수 |
| 미처리 | 회차를 닫을 때 남은 것. **없으면 "없음" 이라고 적는다** | 필수 |

> **회차를 새로 열 때 지난 섹션을 지우지 마라.** 그것이 이 문서가 사건형인
> 이유다. 1차 FAIL 이 2차에서 PASS 가 된 것이 증거가 된다.
