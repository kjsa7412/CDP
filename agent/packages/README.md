# packages — 프로젝트마다 **고르는** 것

```
agent/             모든 프로젝트가 같은 것을 받는다   도구 · 매뉴얼 · skill · 훅
agent/packages/    프로젝트마다 고른다               docs/ · _managed.md · _vocab.md
```

둘 다 "받는 사람에게 가는가" 를 통과한다. **고르는가**에서 갈린다 — 그래서
배포본에서는 **합쳐져** `knowledge-repo-<이름>/` 하나로 나간다.

## 고르는 법 — 폴더를 복사한다

```
xcopy /E /I <배포본>\knowledge-repo-<고른 것> C:\cdp
copy <배포본>\cdp.exe C:\cdp\tools\
cd /d C:\cdp
git init && git config core.hooksPath .githooks
```

**네 줄이다.** `ctx init --package` 같은 명령을 만들지 않는다 — 설치가 이미
복사이고, 방식이 둘이면 어느 것이 맞는지 묻게 된다.

복사한 순간 그 폴더가 지식 레포다 — `ctx` 는 `_vocab.md` 로 알아보고,
그 파일이 폴더 안에 이미 있다. `cdp.exe` 는 배포본 루트에 **하나**다(패키지가 여럿이어도) —
`tools\` 에 복사한다.

## 무엇이 들어 있나 — 서식이지 내용이 아니다

| 있다 | 없다 |
|---|---|
| `docs/` 문서 골격 — 머리 표 · 작성지침 · 예시 섹션 | 그 프로젝트의 데이터 |
| `_managed.md` 좌표 패턴 → 문서 · 섹션 | |
| `_vocab.md` 좌표 타입과 순서 | **좌표 값** |

값을 넣으면 이 패키지를 고른 다른 프로젝트에 **남의 프로젝트 데이터가 따라
들어온다.**

## 매니페스트 — `_package.json`

패키지마다 하나. **사람이 정하는 것만** 적는다 — `name`(폴더명과 같아야 한다) ·
`title` · `version` · `description` · `source`(만든 기록이 어디 있나) · `updated`.
문서 수 · 좌표 타입 · 등록부 패턴은 **폴더에서 센다** — 적어 두면 갈라진다.

```
ctx package list                     패키지 · 판 · 문서 · 타입 · 패턴
ctx package show public-si           등록부 · 타입 순서 · 문서 목록
ctx package check public-si          부어서 ctx check — 등록부가 없는 문서를 가리키나 · 예시 어휘만 남았나
ctx package new <이름> --from agile-product
```

`check` 는 CI 가 패키지마다 돈다(`npm run check:packages`). 릴리스가 깨진 패키지를
싸는 일이 없다. 매니페스트는 **받는 사람에게 가지 않는다** — 조립(`ops/lib/assemble.mjs`)이 뺀다.
`convert/` 폴더도 같다 — 그 문서 종류의 변환기 자리. 원본 xlsx 가 없으면 돌지 않는다.

**일하는 방식으로 고른다.** 패키지 이름은 서식의 이름이다 — 프로젝트 이름이 아니다.

| 패키지 | 문서 | 이런 팀 |
|---|--:|---|
| [`blank/`](blank/README.md) | 0 | 서식 없이 — 첫 관리 문서와 좌표 타입을 팀이 세운다 |
| [`public-si/`](public-si/README.md) | 40 | 발주처에 단계별 산출물을 내는 공공 · SI 사업 (사업관리 · 분석 · 설계 · 구현 · 시험 · 이행) |
| [`agile-product/`](agile-product/README.md) | 14 | 웹 · 모바일 서비스를 스프린트로 만들고 자주 내보내는 제품팀 |
| [`cloud-native/`](cloud-native/README.md) | 13 | 여러 서비스를 쿠버네티스 · 클라우드에서 운영하는 플랫폼 · SRE 팀 |
| [`ai-service/`](ai-service/README.md) | 12 | LLM · RAG · 에이전트 기능을 만들고 평가하며 운영하는 팀 |

문서 수는 `docs/**/*.md` 를 센 것이다 — `ctx package list` 가 내는 값과 같다. 왜 이 다섯인가는
[`docs/design/CDP_패키지_재편_검토_v0.1.md`](../../docs/design/CDP_패키지_재편_검토_v0.1.md).

**새 셋(`agile-product` · `cloud-native` · `ai-service`)의 원칙** — ① **작업 기록이 ADR 이다** — 결정 문서를
따로 두지 않는다(`work/` 는 불변 · 결정을 뒤집으면 같은 좌표에 새 기록 · `supersedes` 는 기록이 틀렸을 때만). ② **코드가 정본인 것은 옮기지 않는다** —
OpenAPI · 마이그레이션 · IaC · 프롬프트 원문은 코드 레포에 두고, 문서에는 `정본 위치` 와 코드가 말하지
못하는 것(왜 · 누가 쓰나 · 호환성 · 정책)만. ③ **좌표는 바뀌고 여럿이 보는 대상에만** — 사건(릴리스 ·
스프린트 · 실험)은 날짜축, 집계(로드맵 · 플래그 · 비용)는 대장.

## 이름 — 서식의 이름이다

패키지는 **일하는 방식의 서식**이다. 프로젝트에 맞추는 일은 패키지가 아니라 **세운 레포 안에서** 한다 —
안 쓰는 문서를 지우고(콘솔 새 레포의 「문서 고르기」 · 레포 › 관리 › 「관리 문서」 · `ctx docs drop`),
좌표를 등록하고, 모자란 문서는 `save` 의 `managed` 로 더한다. 그래서 패키지를 프로젝트마다 복제하지 않는다.

| | |
|---|---|
| **패키지 이름 ≠ 지식 레포 이름** | 레포 이름은 세울 때 정한다(`ctx repo new <경로> --package <이름>`). `public-si` 로 `alpha` 레포를 세울 수 있다 |
| 이미 세운 레포 | 그대로다. 레포는 패키지의 사본이고 이름을 따로 갖는다 — 패키지 이름이 바뀌어도 무관하다 |
| 서버의 `packages/` | 다음 산출물(`release:server` → `upgrade.sh`)이 통째로 갈아 끼운다 |
| 클라이언트 배포본 | 다음 릴리스의 `knowledge-repo-<이름>/` 이 된다 |

이름을 바꿀 일이 있으면(서식의 이름이 내용을 말하지 못할 때) —

```
ctx package rename <이름> <새 이름> [--title "…"]
```

폴더 · `_package.json` 의 `name` · `README.md` 첫 제목을 **한 번에** 바꾼다 — 셋 중 하나만 바꾸면 매니페스트가
"폴더명과 다르다" 로 거절하거나 레포를 연 사람이 옛 이름을 읽는다. 바꾼 뒤 이 README 의 목록 줄 · 그 이름을
부르는 시험 · 하네스 · 설명서를 고치고 `ctx package check <새 이름>`. `dpms` → `public-si`(2026-10-02)가 이 길로 갔다.

## 새 패키지를 만들려면

`ctx package new <이름> --from <가까운 것>` 이 복사하고 매니페스트를 고쳐 준다. 그다음 문서 목록 · 등록부 ·
어휘를 그 방식에 맞게 고친다 — **원본과 다른 것만이 그 패키지다.** 서식 규약(머리 표 · 섹션 ·
`applied` · 작성지침)은 `docs/관리문서패키지/03_템플릿규약.md` 에서 공유한다 — 패키지마다 복사해 넣으면 두
벌이 되고 두 벌은 갈라진다. `new` 는 `README.md` 의 첫 제목을 새 이름으로 바꾸고 출처 한 줄을 넣는다 —
조립되면 그것이 지식 레포의 루트 README 다. `convert/`(변환기 자리)는 복사하지 않는다.

**타입 이름은 한글로 시작하거나 영문 소문자다.** 어휘(`_vocab.md`)는 `API명세:` 같은 대문자 영문 시작도
받지만 MCP 도구와 서버형 `save` 의 등록부 연산이 받지 않는다 — 패키지를 부은 레포가 서버형에서 그 좌표를
못 쓴다. `test/packages-shipped.test.mjs` 가 나가는 패키지마다 이것과 README 문서 표 · 고정 좌표의 섹션 ·
사내 흔적을 본다.
