# DS_401 데이터모델

저장하는 것의 지금 상태. **섹션 하나가 엔터티 하나**다 — 컬럼 · 타입은 마이그레이션이
정본이고, 여기는 **뜻 · 규칙 · 보존 · 개인정보**를 적는다.

| | |
|---|---|
| 관리번호 | `DS_401` |
| 언제 | 엔터티를 더할 때 · 필드의 뜻 · 허용 값 · 보존을 바꿀 때 |
| 등록부 | `데이터모델:*` → `## {값}` |
| 좌표 값 | 엔터티 키 — 소문자 · 밑줄 · 단수형(`ex_order`). 테이블 · 컬렉션 이름과 맞춘다 |

**무엇** — 엔터티마다 정본 위치(마이그레이션) · 소유 · 필드의 **뜻** · 불변식 · 상태 전이 ·
보존 · 개인정보.
**언제** — 마이그레이션을 쓰는 PR 에서. 컬럼 이름만 바꾸면 안 고쳐도 되지만 **뜻 · 허용 값 ·
보존이 바뀌면 고친다.**
**누가** — 그 엔터티를 소유한 백엔드 개발자. 개인정보 항목은 보안 · 개인정보 담당이 함께 본다.

**여기 적지 않는 것**

| | 어디로 |
|---|---|
| 컬럼 타입 · 인덱스 · DDL | 코드 레포의 마이그레이션 — `정본 위치` 로 가리킨다 |
| API 로 내보내는 모양 | `인터페이스명세` |
| 저장소의 종류 · 판 · 백업 | `시스템아키텍처` 의 container · deploy |
| 지표 계산 | `제품지표` |
| 왜 이렇게 모델링했나 | 작업 기록(`work/`) |

> **마이그레이션을 옮겨 적지 않는다.** 스키마는 코드가 정확히 말한다. 코드가 말하지
> 못하는 것 — 「결제된 주문이 다시 생성됨으로 돌아갈 수 있나」 · 「주소를 몇 년 두나」 —
> 가 여기 몫이다.

## ex_order — (예시) 주문
<!-- applied: null -->

| | |
|---|---|
| 정본 위치 | (예시) `api/db/migrations/` · 테이블 `orders` |
| 소유 | 결제 스쿼드 |
| 개인정보 | **있음** — 받는 사람 이름 · 연락처 · 주소 |
| 관련 좌표 | `인터페이스:ex-orders` · `기능명세:EX-CHECKOUT` |

**필드의 뜻** — 이름만으로 모르는 것만

| 필드 | 뜻 | 규칙 |
|---|---|---|
| `status` | 주문 상태 | 아래 전이만 허용 |
| `total_amount` | 결제할 금액(원) — 할인 · 배송비를 반영한 뒤 | 정수 · 0 이상. 결제 승인 뒤 바뀌지 않는다 |
| `idempotency_key` | 생성 요청의 멱등 키 | 회원별로 유일 · 24시간 |
| `recipient_*` | 받는 사람 — 회원 정보의 **사본** | 회원이 주소를 바꿔도 지난 주문은 그대로 |

**상태 전이** — `CREATED` → `PAID` → `SHIPPED` → `DELIVERED`. `CREATED` · `PAID` 에서만
`CANCELLED` 로 간다. **뒤로 가지 않는다.**

**보존** — (예시) 계약 · 결제 기록은 전자상거래법에 따라 5년. 5년이 지나면 `recipient_*` 를
지우고 금액 · 상태만 통계로 남긴다.

**개인정보** — `recipient_phone` · `recipient_address` 는 컬럼 암호화. 조회는 운영자 권한 +
조회 기록.

> ⚠ **이 섹션은 예시다 — 지우고 시작한다.**
