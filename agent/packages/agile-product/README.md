# agile-product — 애자일 제품 개발

**문서 14종.** 웹 · 모바일 서비스를 스프린트로 만들고 자주 내보내는 제품팀의
한 벌이다 — 제품(왜 · 무엇) · 설계(어떻게) · 출시(언제 · 무엇이 나갔나).
기능 · 지표 · 화면 · API · 데이터 모델을 좌표로 잇고, **결정은 작업 기록이 갖는다.**

## 이런 팀

**맞는다** — 제품 책임자 · 디자이너 · 개발자 · QA 가 한 팀이고, 1~2주 스프린트로
일하며, 트렁크 기반 개발 · 기능 플래그 · CI/CD 로 하루에도 여러 번 내보낸다.
「이 기능 수용 기준이 뭐였지」 · 「이 API 누가 쓰지」 · 「이 플래그 아직 필요해?」 를
매주 묻는 팀이다.

**다른 패키지가 맞는 팀**

| 이런 팀이면 | 고른다 |
|---|---|
| 발주처에 단계별 산출물(착수 · 설계 · 시험 · 이행)을 내야 한다 | `public-si` — 공공 SI 산출물 세트 |
| 여러 서비스를 쿠버네티스 · 클라우드에서 운영하는 것이 주 일이다 | `cloud-native` — 서비스 · SLO · 런북 · 장애회고 |
| LLM · RAG · 에이전트 기능을 만들고 평가하며 운영한다 | `ai-service` — 모델카드 · 프롬프트 · 평가셋 |
| 서식 없이 문서 · 타입을 직접 세운다 | `blank` — 빈 지식 레포 |

## 이 패키지는 **서식**이다

| 있다 | 없다 |
|---|---|
| 문서 14개 골격 — 머리 표 · 예시 섹션 · 작성지침 | 그 제품의 기능 · 화면 · API |
| `_managed.md` — 좌표형 문서의 등록부 | **ADR 문서** — 작업 기록이 그것이다 |
| `_vocab.md` — 좌표 타입과 **순서** | 좌표 값 (`시스템아키텍처:` 넷만 예외) |
| 같은 가상 업무 「(예시) 온라인 상점」 의 예시 한 벌 | OpenAPI · 마이그레이션 · 디자인 원본 — 코드 레포 · 디자인 도구가 정본이다 |

## 붓는다

```
xcopy /E /I <배포본>\knowledge-repo-agile-product C:\cdp
copy <배포본>\cdp.exe C:\cdp\tools\
cd /d C:\cdp
git init && git config core.hooksPath .githooks
```

서버형은 콘솔 › 지식 레포 › 새 레포에서 `agile-product` 를 고른다.
부으면 `_vocab.md` 가 생기고 **그 순간 그 폴더가 지식 레포**가 된다.
바로 `ctx check` 가 돈다 — 작업 기록이 0건이면 `이상 없음` 이다.

## 첫날

```
1  안 쓰는 문서를 지운다            14종을 다 쓰는 팀도 있다 — 리서치 도구 · 이슈 트래커가 대신하는 것은 뺀다
2  서식 예시를 지운다              ctx examples --purge · 서버형은 save 의 examples: "purge"
3  _vocab.md 에 좌표를 등록한다      진행 중인 기능 · 화면 · API 부터. 여기 없는 좌표를 쓰면 커밋이 막힌다
4  ctx check                       이상 없음이 나오면 시작할 수 있다
```

**1 은 한 번에 한다.** 파일만 지우면 등록부 행이 없는 파일을 가리킨 채 남는다.

| | 어떻게 |
|---|---|
| 서버형 · 세울 때 | 콘솔 › 지식 레포 › 새 레포의 「문서 고르기」 에서 체크를 푼다 |
| 서버형 · 세운 뒤 | 레포 › 관리 › 「관리 문서」(admin) — 사용 현황을 보고 골라 미리보기 → 지우기 |
| 셸(모드 A) | `bin/ctx docs drop PD_501 --dry-run` → `--apply-suggest --reason "조사는 리서치 도구에"` → `bin/ctx index` → 커밋 |
| 에이전트(큐레이터) | `cdp-registry` 「안 쓰는 문서 지우기」 — 산문 언급까지 고쳐 쓴다 |

**3 은 처음부터 다 하지 않는다.** 지금 스프린트에서 건드리는 기능 · 화면 · API 를
먼저 올리고, 나머지는 작업 기록이 닿을 때 한 줄씩 더한다.

## 원칙

| 원칙 | 무엇 |
|---|---|
| **작업 기록이 ADR 이다** | 결정 · 버린 대안 · 이유는 `work/` 의 작업 기록에 쓴다 — ADR 문서를 따로 두지 않는다. 그 결정이 바꾼 대상을 `touches:` 에 적으면 정본 문서가 따라 고쳐진다. 기록은 고치지 않는다 — 결정을 뒤집으면 같은 좌표에 새 기록을 내고(어느 것이 뒤인지는 도구가 날짜로 센다), `supersedes` 는 기록 자체가 틀렸을 때만 단다 |
| **코드가 정본인 것은 옮기지 않는다** | OpenAPI · DB 마이그레이션 · 인프라 코드 · 디자인 원본(Figma) · 플래그 설정은 제자리에 둔다. 문서에는 `정본 위치` 한 줄과 **코드가 말하지 못하는 것** — 왜 · 누가 쓰나 · 호환성 · 정책 — 만 적는다. 옮긴 스키마는 다음 PR 에서 틀린다 |
| **좌표는 바뀌고 여럿이 보는 대상에만** | 기능 · 지표 · 화면 · API 자원 · 엔터티 · 아키텍처 관점. 할 일 · 버그 · 스토리는 이슈 트래커의 것이다 |
| **사건은 날짜축 · 집계는 대장** | 조사 · 릴리스 · 스프린트는 날짜(판 · 스프린트 번호)로 쌓고, 로드맵 · 플래그는 표 하나로 본다 |

## 번호

| | |
|---|---|
| 모양 | **묶음 접두 + 세 자리** — `PD` 제품 · `DS` 설계 · `RL` 출시. 백의 자리가 문서 종류다 |
| 성격 | **번호는 속성이지 식별자가 아니다.** 등록부 · 링크는 파일 경로를 가리키고, 이름은 문서명이다. 번호는 문서 고르기 · 참조 찾기 · `ctx docs drop` 이 부르는 손잡이다 |
| 새 번호 | 새 종류는 그 묶음에서 쓰지 않은 백의 자리(예: PD 의 다음은 PD_601), 같은 종류를 나누면 끝자리(예: DS_301 을 둘로 나누면 DS_302). 파일 이름 `<번호>_<문서명>.md` · 첫 줄 `# <번호> <문서명>` · 머리 표 `관리번호` 를 같이 쓴다 |
| 새 묶음 | 두 글자 영문 대문자. 폴더는 `docs/<순번>.<묶음 이름>/` |

## 더할 만한 것

이름만 둔다 — 쓰는 팀이 생기면 그때 세운다.

| | 언제 |
|---|---|
| 용어집 | 같은 낱말을 기획 · 개발 · 운영이 다르게 쓸 때 |
| 실험기록 | A/B 시험을 자주 돌려 결과를 날짜축으로 모아 볼 때 |
| 위험관리 | 규제 · 보안 · 일정 위험을 닫힐 때까지 따라가야 할 때 |

**세우는 법** — 서버형은 save 의 `managed` 로 등록부 행 · 문서 · 어휘를 **한 커밋**에 낸다
(writer · 사람의 승인). 셸은 `_managed.md` 에 행을 더하고 `docs/` 에 문서를 세우고 `_vocab.md` 에
타입 절을 더한 뒤 `bin/ctx index` → `bin/ctx check` → 커밋. 서식은 이 패키지 문서의 머리 표 ·
`## 작성지침` 을 본뜬다.

## 알려진 한계

| | |
|---|---|
| 대장 · 사건 · 서술 문서 | 결정론적 보증이 없다 — 기능 플래그의 제거 예정일이 지나도 커밋은 막히지 않는다. 스프린트 리뷰에서 본다 |
| 코드와 문서의 어긋남 | `정본 위치` 는 가리킬 뿐이다 — OpenAPI 에서 필드를 지웠는데 호환성 칸을 안 고쳤는지는 사람이 본다. 작업 기록에 `인터페이스:` 좌표를 거는 습관이 유일한 장치다 |
| 그림 | 뷰어는 mermaid 를 그리지 않는다 — 흐름은 번호 목록 · 표로 적고, 그림은 디자인 도구 · `work/assets/` 에 두고 링크한다 |
| 기능 상태 | 기능명세의 상태와 로드맵 · 플래그 표의 상태는 손으로 맞춘다 — 셋이 어긋날 수 있다 |
