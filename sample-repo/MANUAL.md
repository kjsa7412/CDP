# CDP 사용 매뉴얼 — 일반 사용자용

**폐쇄망에서는 물어볼 사람이 없다.** 이 문서가 그 사람을 대신한다.

설치·배포·어휘 관리는 [MANUAL-관리자.md](MANUAL-관리자.md) 에 있다. 여기는
**하루 쓰는 법**만 다룬다.

---

## 0. 이게 무엇인가

세 줄이다.

```
① 작업이 끝나면 무엇을 왜 그렇게 했는지 한 문서로 남긴다   (work/)
② 그 문서가 바꾼 대상에 좌표를 붙인다                     (table: screen: …)
③ 그 대상의 "지금 상태"를 정본 문서에 옮긴다              (docs/)
```

①은 **사건**이라 고치지 않는다. ③은 **상태**라 계속 덮어쓴다. 6개월 뒤
누군가 *"이 컬럼 왜 이렇게 생겼지"* 를 물으면 ③이 답하고, *"왜 그렇게
정했지"* 를 물으면 ①이 답한다.

> **좌표가 이 시스템의 전부다.** 검색이 아니라 좌표로 찾는다. 이름은 사람마다
> 다르게 부르지만 좌표는 하나다.

---

## 1. 하루 흐름

```
작업 요청  ─┐
            │  ① 검토      무엇을 바꿀 것인가.  4~6줄
            │  ② 주입      그 대상의 지금 상태를 가져온다 (필요할 때만)
            │  ③ 요청수행   그것을 근거로 답한다
            ─┘   ← 여기까지가 cdp-work skill 하나

작업이 끝나면 → cdp-save   기록 + 정본 문서 갱신 + 커밋
```

**요청 하나가 작업 하나가 아니다.** 요청 세 개가 한 작업일 수 있고, 그때 기록은
하나다. 요청마다 기록하면 이력이 파편화된다.

| 언제 | 무엇을 |
|---|---|
| 아침 | 앱을 켠다. **상단 `⚠ 검증 N`** 이 켜져 있으면 눌러 검사 결과를 본다 |
| 작업 요청 | AI 가 `cdp-work` 로 처리한다. 규약에 적혀 있다 |
| 작업 끝 | `cdp-save`. 커밋까지 간다. **push 는 사람이 누른다** |
| 퇴근 전 | `⬆ 미전송` 이 있으면 보낸다 — **안 보내면 남에게는 없는 일이다** |

기록이 생기는 길은 셋이다. **어느 길이든 관리 문서 갱신이 함께 간다.**

| 어떤 일이었나 | |
|---|---|
| 이 세션에서 작업했다 | `cdp-work` → `cdp-save` |
| 이미 쓴 문서가 있다 (회의록·검토서) | `cdp-import` — 원문을 보존한 채 들인다 |
| 작업은 없고 **문서를 고치라는 지시**다 | `cdp-edit` — **지시가 곧 기록의 본문**이다 |

셋째가 중요하다. 관리 문서만 고치고 기록을 안 남기면 **출처 없는 변경**이
되고, 6개월 뒤 "왜 이렇게 적혀 있지" 에 답할 것이 없다. 그리고 이 경우는
`ctx check` 가 잡지 못한다 — 기준이 될 기록이 없기 때문이다.

## 2. 앱 보는 법

화면은 **좌우 2분할**이다. 왼쪽에서 찾고, 오른쪽에서 읽는다.

```
┌── 왼쪽 ─────────────────────┬── 문서 ──────────────┐
│ [목록] [뻗어나가기]          │                      │
│                             │   오른쪽은 문서다.    │
│   한 번에 하나만 한다.       │   문서로서의 정보만.  │
│   고르는 중이면 목록,        │                      │
│   따라가는 중이면 뻗어나가기. │                      │
│                             │                      │
└─────────────────────────────┴──────────────────────┘
```

**왼쪽은 한 번에 하나만 한다.** 목록과 뻗어나가기가 같은 자리를 쓰므로 각각이
**세로 전체**를 받는다. 폭도 따로 기억한다 — 목록은 좁아도 되고 뻗어나가기는
열이 여럿이라 넓어야 한다. 그래서 비율 버튼(`1:1` `2:1` `3:1` `찾기만`)이
없어졌다. 매번 비율을 맞춰야 했다는 것 자체가 화면이 안 맞았다는 뜻이다.

### 화면을 넓게 쓰는 법

| | |
|---|---|
| 왼쪽 위 **◀** | 왼쪽을 접는다. 문서가 창 전체를 쓴다 (`⌘.`) |
| 접은 뒤 상단 **▶ 목록** | 다시 편다 |
| 가운데 구분선 | 끌어서 좌우를 마음대로. **하는 일마다 따로 기억한다** |
| 상단 **그래프** | 창 전체가 그래프가 된다. `Esc` 로 돌아온다 |

### 오른쪽 — 문서

본문 오른쪽에 **목차가 세로로** 선다. 지금 읽는 섹션이 파랗게 남고, 스크롤하면
따라온다. 눌러서 그 섹션으로 간다.

- 섹션이 159개여도 **다 들어간다** — 넘치면 목차만 스크롤된다
- 머리(`▸ 목차 N`)를 누르면 접힌다. 접으면 띠만 남고, **띠 아무 데나** 누르면 펴진다
- 접은 상태는 기억된다 — 문서를 바꿔도 그대로다
- 제목이 없는 문서에는 목차가 아예 안 생긴다

### 왼쪽 — 목록

**층이 다른 것을 한 탭에 섞지 않는다.** 관리문서와 작업문서는 성질이 다르다 —
하나는 지금 상태, 하나는 사건이다.

| | |
|---|---|
| **관리문서** | 정본 문서 16종. 옆 숫자는 섹션 수 |
| **작업문서** | 작업 기록. **제목이 맨 앞이다.** 안 읽은 것은 왼쪽 모서리에 파란 선 |
| **좌표** | 카테고리 칩으로 좁힌다. 우클릭하면 `내 좌표` 로 표시된다 |

- 찾기는 탭 아래 **자기 줄**에 있다. 제목·id·좌표에 **작성자**까지 걸린다
- 작성자는 왼쪽이 넓을 때만 나온다 — **좁으면 제목이 이긴다**
- 시각(`11:06`)은 **같은 날 두 건 이상일 때만** 붙는다

**고르면 어떻게 되나**

| 고른 것 | |
|---|---|
| 관리문서 · 작업문서 | 오른쪽에 문서가 열리고 **목록은 그대로 남는다** — 차례로 읽을 수 있다 |
| 좌표 | **뻗어나가기로 넘어간다.** 좌표는 오른쪽에 열 것이 없다 |

### 왼쪽 — 뻗어나가기

**이 화면의 핵심이다.** 고른 것에서 **다음 한 단계만** 펼친다. 계층이 섞이지
않는다.

| 지금 보는 것 | 다음에 나오는 것 |
|---|---|
| 작업문서 | 관리문서 · 좌표 |
| 좌표 | 관리문서 · 작업문서 |
| 관리문서 | 섹션 |

- 열 하나가 한 단계다. **가로로** 뻗으므로 지나온 길이 왼쪽에 남는다
- 열이 하나면 왼쪽 전부를, 둘이면 반씩 쓴다. 셋째부터 가로로 스크롤된다
- 중간 열에서 다시 고르면 그 **오른쪽이 전부 교체**된다
- **루프를 허용한다.** 같은 노드가 여러 열에 다시 나올 수 있다 — 트리가 아니라
  그래프다. `작업A → 좌표X → 작업A` 를 막으면 *"이 좌표를 이 작업이 또
  건드렸다"* 가 화면에서 사라진다
- 어디서 멈춰도 오른쪽에 문서가 뜬다. **줄 이름이 곧 다음 열이다**
- **지금 뿌리는 탭 옆에 늘 적혀 있다** — 가로로 밀려도 어디서 출발했는지 남는다

정렬은 늘 같다 — 좌표는 카테고리순+이름순, 작업문서는 작성일자순, 관리문서와
섹션은 섹션 순서. **상태로 정렬하지 않는다.** 그러면 같은 것을 두 번 봐도
자리가 달라진다.

### 상단 — 그래프

**패널이 아니라 화면이다.** 좌표 288개짜리 그림을 400px 안에서 읽을 수 있는
사람은 없다. 상단 `그래프` 를 누르면 창 전체를 쓰고, `Esc` 나 `← 문서` 로
돌아온다.

**기본은 이어진 좌표만 그린다.** 실측 — 좌표 288개 중 **216개가 고립**이다.
어휘(`_vocab.md`)는 DB 덤프에서 이름표를 대량으로 받아 오는데(`code:` 만
159개) 작업 기록은 그중 일부만 건드린다. 그 216개를 같이 그리면 배율이
거기에 맞춰져 정작 볼 덩어리가 가운데로 밀린다. `고립 +216` 을 누르면 켜진다.

| | |
|---|---|
| **왼쪽 카테고리** | 고르면 **그 좌표만 색이 붙는다.** 다시 누르면 해제 |
| **노드를 누르면** | **1단계로 이어진 것만 진해지고** 나머지가 옅어진다. 고정돼 남는다 — 다시 누르거나 빈 곳을 누르면 풀린다 |
| **아래 바의 `뻗어나가기 →`** | 그 좌표를 시작점으로 잡고 문서 화면으로 나간다 |
| 휠 · `−` `+` | 확대·축소 |
| 끌기 | 회전 |
| `Shift`+끌기 · 가운데 버튼 | 공간 이동 |
| `맞춤` | 기본 배율(100%)로 · 위치·고정 초기화 |

> **노드를 누르는 것은 고르는 것이지 떠나는 것이 아니다.** 그 클릭은 "이어진
> 것만 보여 달라"는 뜻이고, 그것이 이 그림을 읽는 방법이다. 떠날지는 읽고 나서
> 아래 바에서 정한다.

### 그 밖

| | |
|---|---|
| `Ctrl+K` | 검색·이동. **별칭으로도 걸린다** — 좌표를 몰라도 *"연구계획서"* 로 찾는다 |
| `\` | 왼쪽 전환 — 목록 ↔ 뻗어나가기 |
| 상단 **⚠ 검증 N** | 눌러서 **검사 결과.** `Esc` 로 닫는다. 0건이면 `✓ 검사` 로 조용하다 |
| 상단 **⋯** | 문서 동기화(⭮) · 매뉴얼(📖) · 읽기 모드 · 글자 크기 · 본문 폭 · 테마 · 설정 |
| `⌘.` / `Ctrl+.` | 읽기 모드 — 왼쪽을 접는다 |
| `⚙ 설정` | **지식 레포 경로** · 작업 레포 에이전트 설치 · 원격 · 매뉴얼. `Esc` · 바깥 클릭 · `✕` 로 닫는다 |

> **보내기(push)는 상단에 없다.** 상태바의 `⬆ 미전송 N건 보내기` 뿐이다 —
> 커밋은 되돌릴 수 있지만 push 는 남의 눈에 들어간다. 받는 것과 보내는 것을
> 같은 자리에 두지 않는다.

> **본문의 좌표에 상태 배지가 붙지 않는다.** 붙일 상태가 없다 — 정본 문서
> 갱신은 필수이고, 안 했으면 그것은 상태가 아니라 커밋을 막는 오류다.
> 좌표는 눌러서 갈 수 있는 자리라는 것만 말한다.

## 3. 작업 절차

### 왜 순서가 이런가

**요청이 먼저다.** 세션이 시작되자마자 맥락을 넣으면 두 가지가 어긋난다.

1. **좌표는 "이 작업이 바꾼 대상"이다.** 무엇을 바꿀지 모르면 뽑을 것이 없다.
2. **일찍 주입하면 요청의 해석이 오염된다.** 정본 문서 다섯 개가 먼저 들어오면
   AI 는 그 다섯의 틀로 요청을 읽고, 요청이 실제로 가리키는 여섯 번째를 못 본다.

> **주입은 답을 좁히는 행위다.** 무엇을 좁혀야 하는지 알기 전에 좁히면
> 엉뚱한 곳을 좁힌다.

### ① 검토 — 4~6줄

```
【검토】
요청  PSC043 면접심사의견등록에 심사위원 연대서명 출력물을 추가한다

대상
  screen:PSC043      변경   출력물 2종 추가
  code:PS130         ?      업무구분 코드를 쓸지 미정
  screen:PSC031      참조   첨부를 읽어오지만 PSC031 은 안 바뀜 → 좌표 아님

주입  screen:PSC043 · code:PS130
```

| 규칙 | 왜 |
|---|---|
| **`_vocab.md` 만 읽는다** | 어휘는 이름표라 의견이 없다. 정본 문서·작업 기록은 의견을 담으므로 요청을 이해하기 전에 읽으면 그 틀로 읽게 된다 |
| **좌표 아닌 것도 적는다** | 무엇을 왜 제외했는지가 판정의 근거다 |
| **멈추지 않는다** | 아래 |

### ② 검토 뒤에 멈추지 않는다

검토 출력은 **감사 흔적이지 승인 관문이 아니다.**

| | 관문으로 두면 | 흔적으로 두면 |
|---|---|---|
| 매 요청 | **정지 1회.** 절차가 작업을 잡아먹는다 | 흐름이 안 끊긴다 |
| 판정이 틀리면 | 미리 막는다 | **출력에 보이므로 사후 교정된다** |

**틀린 주입의 비용은 틀린 답이 아니라 낭비된 토큰이다.** 판정이 어긋났으면
답변에서 드러나고, 그때 *"PS130 은 아니야"* 라고 하면 된다.

**멈추는 경우는 하나뿐이다** — *"채용 쪽 정리해줘"* 처럼 요청 자체가 무엇을
원하는지 모를 때. 그건 맥락 문제가 아니라 요청 문제다.

### ③ 언제 건너뛰나

| 상황 | |
|---|---|
| *"이 정규식 왜 안 되지"* | **`cdp-work` 를 안 부른다.** 지식 레포와 무관하다 |
| *"이 함수 이름 바꿔줘"* | 안 부른다 |
| **내가 그 도메인의 리더이고 내 로컬이 최신** | **안 부른다.** 아래 |
| 이어지는 대화 (같은 주제) | **다시 안 부른다.** 이미 주입된 맥락을 쓴다 |

**세 번째가 중요하다.** 지식 레포가 나보다 뒤에 있으면 주입은 나를 어제로
되돌린다. 그때는 내 코드가 정본이고, 그걸로 작업하는 것이 맞다.

> **다만 그 뒤가 구멍이다.** 그렇게 올바르게 작업하고 **지식 레포에 아무것도
> 안 쓰면**, 그 결정이 내 머리와 로컬 코드에만 남는다. 그리고 더 나쁜 것 —
> 기록이 없으면 갱신 누락 검출이 **속는다.** 그 좌표를 건드린 기록이 없으니
> 그 섹션은 **최신인 척한다.**
>
> 리더일수록 기록이 중요하다. 6개월 뒤 그 결정을 되짚는 첫 사람은 대개 자기
> 자신이고, 그때 코드에는 *"무엇을"* 만 있고 *"왜"* 가 없다.

## 4. 좌표 붙이기

**이 작업이 바꾼 것만이다.**

| 이 작업이 그 대상을… | 좌표 |
|---|:--:|
| 신설했다 | **O** |
| 변경했다 (컬럼 추가 · 규격 변경 · 상태값 추가) | **O** |
| 삭제·폐기했다 | **O** |
| 작업 중 발견해 **이슈로 제기했다** (`issue:`) | **O** |
| 참조했다 · 호출했다 · 언급했다 | **X** |
| 그것을 쓰는 다른 것을 만들었다 | **X** |

`issue:` 는 **제기**가 동사다 — 신설·변경이 아니라서 위 세 행에 안 걸린다.
그래서 "언급했다 → X" 로 떨어지기 쉬운데, **틀린 판정이다.** 이슈를 대장에
올렸으면 그 좌표는 이 작업이 만든 것이다.

판정 기준은 하나다 — **6개월 뒤 그 대상을 맡은 사람이 이 작업을 찾아야 하는가.**

*"주제인가?"* 는 답이 갈리지만 **"바꿨는가?"는 결판난다.** 그리고 diff 로
확인된다.

`ctx check` 가 뒤에서 한 번 더 본다 — **본문에 `` `type:값` `` 으로 쓴 좌표가
`touches` 에 없으면 경고**한다. 참조만 한 것이면 무시하면 되고, 바꾸거나
제기한 것이면 그때 넣는다.


### 예시 12개

| # | 작업 | 좌표 | 아닌 것 |
|---|---|---|---|
| 1 | `PS_EXT_EMP_MST` 에 컬럼 2개 추가 | `table:ps_ext_emp_mst` | |
| 2 | PSC043 을 현황/작성 화면으로 분리 | `screen:PSC043` | `module:grid-common` (쓰기만 함) |
| 3 | 코드그룹 PS130 신설 | `code:PS130` | |
| 4 | EXA021 에서 `wrk_tp_cd` 로 트리 그룹핑 | `screen:EXA021` | **`table:ps_ext_emp_mst`** — 읽기만 한다 |
| 5 | SEC013 의견 컬럼을 상태로 필터 | `screen:SEC013` | **`table:rp_rpmc_insp_targr_list`** — 표시만 바뀐다 |
| 6 | SEB020 임시저장에 작성일 미기록 | `screen:SEB020` · **`table:rp_pre_rview_opl_list`** | — 컬럼이 언제 채워지는지가 바뀌었다 |
| 7 | 통합테스트 일정 확정 | **없음** (`touches: []`) | 아무 대상도 안 바꿨다 |
| 8 | `dateRange2` 종료일 역전 방지 | `module:date-range` | 그 컴포넌트를 쓰는 화면들 |
| 9 | 계획서 관리번호 중복 검증 | `screen:PLA011` · `screen:PLA021` · `table:rp_plnd_mst` | 유니크 제약은 안 걸었지만 그 **판단**이 테이블 정의에 남는다 |
| 10 | PLA011 신규 진입 디폴트를 과제에서 | `screen:PLA011` | **`table:rp_rsch_prj_mst`** — 읽기만 한다 |
| 11 | 알림 문구를 사용자 말로 | `screen:SEA021` | 조건은 그대로다. 문구도 그 화면의 정의다 |
| 12 | 테이블명 오타 정정 | `table:rp_rdc_opl_mst` | |

**4·5·10 이 헷갈리는 자리다.** 다 "그 테이블을 쓰는 화면 작업"인데 테이블은
안 바뀐다. **6 은 반대다** — 컬럼이 언제 채워지는지가 바뀌었으니 그 컬럼을
맡은 사람이 알아야 한다.

### 스스로 검산하는 법

**갱신할 것이 없으면 좌표 판정이 틀린 것이다.**

`cdp-save` 가 정본 문서 갱신을 요구하는데 그 섹션에 **고칠 내용이 떠오르지
않으면**, 그 좌표는 참조였다. 빼라.

### 억지로 붙이지 마라

**없는 좌표보다 억지 좌표가 나쁘다.** 그 좌표를 찾는 사람에게 무관한 문서를
내밀기 때문이다. 0개면 `touches: []` 로 적는다 — **키를 빼지 말고** 0개임을
확인했다는 선언으로 남긴다.

## 5. 검토·맥락 읽는 법

### 검토 출력에서 고칠 수 있는 것 셋

| 보이는 것 | 이럴 때 말한다 |
|---|---|
| 대상에 없는 것이 있다 | *"PSC031 도 바뀌어"* |
| 대상에 있으면 안 되는 것 | *"PS130 은 안 건드려"* |
| 주입이 과하다 | *"맥락 필요 없어, 그냥 해"* |

`?` 로 표시된 것은 AI 가 확신이 없다는 뜻이다. **거기가 먼저 볼 자리다.**

`(미등재)` 가 나오면 그 이름이 `_vocab.md` 에 없다는 뜻이다. 커밋 때 막히므로
그때 등재하면 된다 — **지금 다른 좌표로 바꾸지 마라.**

### 주입은 **섹션 하나**다 — 문서 전체가 아니다

먼저 이것부터. 검토가 좌표 이름을 늘어놓으면 *"그 좌표에 관한 것이 전부
들어왔다"* 고 읽기 쉬운데, 실제로 들어온 것은 **그 문서의 한 섹션**이다.

```
[정본]   docs/테이블정의서.md  ## ps_ext_emp_mst
[범위]   그 섹션만 — 18줄 · 약 520자 (docs/테이블정의서.md:839)
```

안 들어온 것 셋 — **그 문서의 다른 섹션** · **그 좌표를 건드린 작업 기록** ·
**등록부에 안 걸리는 관련 좌표**.

`ctx where` 에 좌표를 여럿 주면 자리와 범위를 한 번에 준다.

```
bin/ctx where api:/adapter/a10/expense-slip code:AC-040
```

**`** 사실상 비어 있다` 가 붙으면 주입은 성공했고 내용이 없다는 뜻이다.**
그 상태로 답을 받으면 *"문서에 정의가 없다"* 가 *"제약이 없다"* 로 바뀌어
있다 — 확신 있게 틀린 답이다. 그때는 코드나 담당자를 봐야 한다.

**보고 싶으면** — 앱 검색창(Ctrl+K)에 좌표를 붙여 넣으면 그 문서로 간다.
섹션은 오른쪽 목차에서 고른다.

### 주입 결과에서 봐야 하는 것 셋

**① 무엇이 실려 있나**

```
[상태]   docs/테이블정의서.md ## ps_ext_emp_mst
         반영 2026-0903-계획서-이력테이블
```

`ctx where <좌표>` 의 `상태` 줄이 같은 답이다.

`파생 남음` 으로 나오면 그 섹션이 아직 안 채워졌다는 뜻이다. **안 채워진
섹션은 낡은 것보다 나쁘다** — 낡은 문서는 날짜가 낡았다고 알려주는데, 안
채워진 섹션은 **최신인 척한다.** 그때는 아래 목록의 작업 기록을 직접 읽어라.

> 그 표시가 보이는 것은 아직 커밋되지 않은 중간 상태라는 뜻이다. 커밋
> 시점에는 `ctx check` 가 막으므로 남아 있을 수 없다.

**② 좌표별 후속**

```
2026-0710-A10-어댑터-v1
  table:rp_plnd_mst           후속 3건   ← 이 부분은 갱신됐을 수 있다
  api:/adapter/a10/plan-sync  최신       ← 이 부분은 이 문서가 마지막 말이다
```

**한 문서 안에서 좌표마다 판정이 다르다.** *"이 문서는 낡았다"* 는 말은
반드시 절반이 틀린다.

**"후속 있음"이 "덮임"은 아니다.** 이후 문서가 그 좌표를 조금 손봤는지 완전히
뒤집었는지 도구는 모른다. **아는 것만 말한다.**

**③ 절단**

```
[절단] 매칭 8건 중 3건 주입. 나머지 id: 2026-06…, 2026-05…
```

이 줄이 없으면 읽는 쪽은 **그 5건이 존재하지 않는다고 판단한다.**

## 6. 기록 — `cdp-save`

```
① pull        실패하면 시작하지 않는다
② 좌표 판정    §4.  판정 근거를 보여준다
③ 작업 기록    자유 형식
④ 정본 갱신    관리 문서 섹션.  **③ 과 함께 필수.** 사람이 승인한다
⑤ 한 커밋      작업 기록 1 + 관리 문서 N.  push 는 안 한다
```

**③ 만 하고 ④ 를 미룰 수 없다.** 전에는 이 표에 "③ 까지가 필수" 라고
적혀 있었는데 틀렸다 — `ctx check` 가 파생 누락을 **오류**로 잡아 커밋을
막는다. 미룬 파생은 상태가 아니라 오류다.

④ 를 채울 자신이 없으면 **③ 도 아직 쓰지 마라.** 안 채운 것은 검사가
알려주고, 틀리게 채운 것은 아무도 모른다.

### 프론트매터

```yaml
---
id: 2026-0821-면접심사의견-개편        # 파일명과 같아야 한다
title: PSC043 개편 — 현황/작성 화면 분리
date: 2026-08-21
author: kjsa
touches:
  - screen:PSC043
  - code:PS130
tags: [채용, 화면개편]
---
```

**`date` 에 시각까지 적는다.** `2026-09-22 14:30`

하루에 같은 좌표를 두 번 건드리는 것은 드물지 않다. 날짜만 적으면 둘의
순서를 알 수 없어 두 번째의 파생 누락이 **경고에 그친다.** 시각을 적으면
오류로 막힌다.

`id` 와 파일명은 그대로 날짜 단위다.


**`status` 는 적지 않는다.** 지식공유문서는 작업의 **완료**에서 발생하므로
완료가 기본값이고, 기본값은 적지 않는다. **그 밖에 쓸 수 있는 값이 없다** —
값이 있으면 `ctx check` 가 오류로 막는다.

제목이 `[` `{` `&` `*` 로 시작하거나 `: ` 를 포함하면 **따옴표로 감싼다** —
안 그러면 YAML 이 배열로 읽어 제목이 사라진다.

### 본문은 자유 형식이다

**섹션을 강요하지 않는다.** 산문이든 표든 코드펜스든 상관없다.

다만 6개월 뒤 이 결정을 뒤집으려는 사람은 *"무엇을 했는지"* 가 아니라
**"어떤 제약 때문에 그렇게 했는지"** 를 찾는다.

> 기록은 업무이고 강제다. 그래서 *"안 쓴다"* 는 문제가 아니다.
> **남는 문제는 "비어 있게 쓴다" 이다** — `touches` 는 붙고 본문에는
> *"용량 제한을 10MB 로 올렸다"* 만 남는 것.
>
> 앱이 **본문이 얇은 기록**을 알려준다. 길이로 어림한 것이라 오탐이 있으니
> 규칙이 아니라 확인 요청으로 읽어라.

### ④ 를 건너뛸 수 없다

**정본 문서 갱신 누락은 오류라 커밋이 막힌다.**

미루고 싶어지는 이유 셋은 전부 성립하지 않는다 — 갱신이 넓어도 해야 하고
(넓다는 것은 그만큼 건드렸다는 뜻이다), 남의 확인은 필요 없고(판단 근거가
지식공유문서에 다 있다), 급할 이유도 없다. **막히는 것은 코드 커밋이 아니라
지식 레포 커밋**이고 그것은 작업이 끝난 뒤에 하는 일이다.

정말 지금 못 하겠으면 **지식공유문서를 아직 쓰지 마라.**
**조용히 사라지지 않으므로 지금 안 해도 잃는 것이 없다.**

④를 건너뛴다고 ③을 안 쓰지는 마라. **순서가 반대면 아무것도 안 남는다.**

### 섹션은 홀로 서야 한다

**그 섹션만 읽고 대상의 현재 상태를 알 수 있어야 한다.** 작업 기록 링크를
타고 가야 알 수 있으면 파생이 안 된 것이다.

이유는 하나다 — **주입은 섹션만 싣는다.** `cdp-load` 는 관리 문서 섹션이
현재 상태라는 전제로 돌고, 작업 기록은 기본으로 넣지 않는다. 그래서 값이
기록에만 있으면 **주입받은 쪽은 그 값이 없다고 판단하고 새로 정하려 든다.**

실제로 이렇게 새 나갔다. `2026-0831-A10-결의서-기본값` 이 지불 수단별
기본값 표를 정했는데, 파생된 섹션에 남은 것은 이 한 줄이었다.

```
결의서입력으로 넘어간다. 작성자·결의일·결제수단 기본값이 여기서 정해진다
                                          ↑ "정해진다" 만 있고 값이 없다
```

**표가 기록에만 남았다.** 그 뒤 같은 요청이 다시 왔을 때 주입은 이 한 줄을
싣고, 이미 정해진 값을 처음부터 다시 정하는 작업이 시작됐다.

**옮길 것** — 판단 · 표 · 규칙 · 값 · 제약. *"왜 그렇게 정했나"* 중 **대상의
성질이 된 것**은 전부. `ctx apply` 가 작업 기록의 목차를 보여준다.

**남길 것** — 그 결정에 이른 경위, 논의, 대안. 그것은 사건이라 기록의 것이다.

| 요약해도 되는 것 | 반드시 옮길 것 |
|---|---|
| *"현장 요청으로"* · *"협의 결과"* | **그래서 값이 무엇인가** |
| 누가 언제 무엇을 물었나 | 그 답이 만든 **규칙과 예외** |

> 변경 줄(`**변경** · 날짜 [링크]`)은 **출처 표시이지 내용이 아니다.**
> 그 줄만 붙이고 끝내면 섹션은 여전히 빈 것이다. 링크는 *"더 알고 싶으면"*
> 이고, *"알아야 하면"* 이 되면 안 된다.

### 커밋이 거부되면

`--no-verify` 로 넘기지 마라 — 그 검사가 유일한 기계 보증이다.

| 거부 사유 | 고치는 법 |
|---|---|
| **관리 문서 파생 누락** | ④를 끝낸다. `ctx apply <좌표>` 가 초안을 준다 |
| `status: 미결` · `제안` | 둘 다 아젠다다. 이슈 대장으로 옮긴다 (§8) |
| `_vocab.md` 미등재 좌표 | 어휘에 한 줄 (§7) |
| 등록부가 가리키는 섹션이 없음 | 그 문서에 섹션을 만든다. 앵커 형태는 등록부가 정한 그대로 |
| 필수 필드 누락 | `id` `title` `date` `author` |
| `id` ≠ 파일명 | 둘을 맞춘다 |

## 7. 정본 문서 채우기 — `cdp-managed`

```
ctx derive
```

**전부 몰아서 하지 마라.** 세 가지가 걸린다.

| | |
|---|---|
| **내용을 모른다** | 남이 바꾼 테이블의 컬럼 의미를 그 기록만 읽고 정확히 옮길 수 없다 |
| **충돌한다** | 20개 섹션을 한 번에 고치면 그 사이 아무도 커밋 못 한다 |
| **검토가 안 된다** | 큰 diff 는 승인이 형식이 된다 |

우선순위 — ① 요청받은 좌표 ② 방금 내가 작업한 좌표 ③ `섹션 없음`(내용 판단이
필요 없다) ④ 오래 남은 것.

### 확신이 없으면 반영하지 마라

**틀리게 반영하느니 작업 기록을 아직 쓰지 마라.** 안 채운 것은 검사가
알려주고, **틀리게 채운 것은 아무도 모른다.**

### 바뀐 게 없으면 그렇게 적는다

그 작업이 그 좌표를 **쓰는 방식만** 바꿨을 수 있다.

```markdown
· 2026-09-02 [`EXA021-외부심의위원`](../work/…) `wrk_tp_cd` 를 선택 모달
  그룹핑 키로 사용. **컬럼 변경 없음**
```

### `applied 깨짐` 은 고치지 마라

없는 작업 기록을 가리킨다는 것은 **이름 오기이거나 기록이 지워진 것**이다.
어느 쪽인지 모르고 바꾸면 그 섹션의 이력이 끊긴다. 사람에게 알려라.

### 새 용어·좌표

`_vocab.md` 의 해당 타입 섹션에 **한 줄**.

```markdown
- `code:PS130` — 외부인원 업무구분
  aliases: 업무구분코드, PS130
```

**`aliases` 가 이 파일의 값어치다.** 정본만 적으면 작성자만 편해지고, alias 가
있어야 수신자가 자연어로 물어도 걸린다. **그 작업에서 실제로 쓴 표현을 그대로
넣어라** — 나중에 지어낸 별칭은 아무도 안 쓴다.

```
ctx term 외부심의위원         어휘 조회
ctx match "면접심사의견등록"   이름 → 정본 좌표
```

**삭제하지 않는다.** 폐기는 `deprecated:` 로 표시한다 — 과거 문서가 그 이름을
쓰고 있고, 지우면 그 문서들이 검색에서 사라진다.

## 8. 여럿이 할 때

### pull 이 왜 필수인가

**쓰기 전에는 받고, 읽기 전에는 확인한다.**

```
쓰기  git pull --ff-only    실패하면 시작하지 않는다
읽기  ctx sync              받지 않는다. 받을 것이 있으면 알린다
```

```
pull 안 하고 cdp-save 를 돌리면
  → 낡은 섹션 위에서 diff 를 만든다
  → 승인하고 커밋
  → 남이 어제 추가한 컬럼이 사라진 diff 가 된다
```

그리고 그 손실은 **조용하다** — 충돌이 아니라 "내가 쓴 것이 맞는 것처럼" 보인다.

| 시점 | |
|---|---|
| 앱 시작 · 5분마다 · 창 포커스 | `fetch` 만. 안전하다 |
| **쓰는 skill 시작** (`cdp-save`·`cdp-import`·`cdp-edit`·`cdp-managed`) | **`pull --ff-only` 필수.** 실패하면 멈춘다 |
| **읽는 skill 시작** (`cdp-work` ② · `cdp-load`) | **`ctx sync` 로 확인.** 받을 것이 있으면 알리고 묻는다 |
| `⬇ 원격 N건 받기` 를 누름 | `pull --ff-only` |

### 읽기에는 왜 강제하지 않나

**보는 것조차 막히면 과하다.** ff 가 안 되는 상태에서도 낡은 것은 볼 수
있어야 하고, 낡았다는 사실만 알면 사람이 판단한다.

그래도 **확인은 한다.** 주입된 섹션이 그 뒤 작업 전체의 근거가 되기
때문이다 — 동료가 아침에 고친 것을 모르고 설계하면 `cdp-save` 가 pull 할
때야 알게 되고, 그때는 이미 만든 뒤다.

**쓰기의 pull 은 레포가 깨지는 것을, 읽기의 확인은 틀린 것을 만드는 것을
막는다.** 뒤쪽이 더 비싸다.

**ff 가 안 되면** 앱과 skill 은 손을 뗀다.

```
원격이 3건 앞서 있고 로컬에도 커밋 2건이 있습니다.
터미널에서 정리하세요:
  git pull --rebase
```

merge·rebase·충돌 해결을 기계가 하지 않는다. 관리 문서 섹션에서 두 갱신을
섞으면 그 결과가 정본 자리에 앉는다.

### 보내기

**커밋은 skill 이, push 는 사람이.** 커밋은 되돌릴 수 있지만 push 는 남의 눈에
들어간다. 상태바의 `⬆ 미전송 N건 보내기` 를 누른다.

**안 보낸 커밋은 남에게 존재하지 않는 것과 같다.**

### 작업이 끝나지 않았으면 — 아직 쓰지 않는다

**지식공유문서는 작업의 완료에서 발생한다.** 끝나지 않았으면 기록할 사실이
아직 없다.

전에는 `status: 진행중` 으로 자리를 잡아 두게 했다. 뺐다 — 그 상태가 있으면
지식 레포가 할 일 목록 노릇을 하기 시작하고, 불변인 사건과 가변인 상태가
섞이면 둘 다 안 맞는다.

### 결정이 안 났으면 — 여기 쓰지 않는다

**`미결` · `제안` 이라는 상태는 없다.** 둘은 같은 것 — 결정이 안 났다 — 이고,
지식공유문서는 작업의 **완료**에서 발생하므로 그 상태로 여기 올 수 없다.
`ctx check` 가 둘을 같이 오류로 잡는다.

갈 곳은 `docs/위험및이슈관리대장.md` 다. 좌표는 `issue:{번호}` 다.

```markdown
## ISS-002 — A10 고정 작성자 계정 생성
<!-- applied: null -->

- **제기** 2026-09-02 · 홍은택
- **결정권자** A10(더존)
- **상태** 회신 대기
```

> **판단이 끝난 부분과 안 끝난 부분을 가른다.** *"왜 이렇게 하는가"* 가
> 정해졌으면 그것은 지식공유문서다 — 남은 것이 남의 회신뿐이라면 그 **회신
> 대기만** 이슈 대장으로 보내고, 작업 기록은 상태 없이 그대로 남긴다.
> 통째로 옮기면 "왜 그렇게 정했나" 가 아젠다에 묻힌다.

**대장으로 보내되 `touches` 에는 남긴다 — 파일은 갈라도 좌표는 잇는다.**
대장 항목은 가변이지만 *그 이슈를 제기한 사건*은 불변이고, 그것은 작업 기록
쪽이다. `touches` 에서 빼면 `ctx where issue:…` 가 "작업 0건" 을 답하고,
**왜 제기됐는지 되짚을 길이 `grep` 밖에 안 남는다.**

**아젠다는 작성자가 관리한다.** 담당자 필드가 없다 — 작성자는 비어 있을 수
없고, **작성자가 결정권자에게 가져가는 것까지가 작성자의 일이다.**

본문에 **무엇을 결정해야 하는지와 누가 결정하는지**를 적어라.

> 알림은 없다. 무시되기 시작하면 되돌릴 수 없고, 그 시점에
> *"알림이 안 왔으니 없는 것"* 이라는 더 나쁜 오해가 자리 잡는다.

## 9. 막혔을 때

```
bin/ctx check      커밋 가능한가
bin/ctx brief      지금 레포 상태 두 줄
bin/ctx derive     정본 문서에 아직 안 채운 섹션
bin/ctx sync       원격과의 차이 · 훅 설정 여부
bin/ctx version    이 번들이 언제 만들어졌나
```

**로그** — `%LOCALAPPDATA%\cdp\logs\app.log`

포터블 모드(exe 옆에 빈 파일 `cdp.portable` 을 두면)면
`<exe폴더>\data\logs\app.log`. 콘솔 없는 앱이라 무엇이 잘못됐는지 볼 곳이
여기뿐이다.

### 자주 나는 오류 8가지

| 증상 | 원인 | 고침 |
|---|---|---|
| `관리 문서 파생 누락` | 좌표를 건드렸는데 정본 섹션을 안 채웠다 | §7 — `ctx apply <좌표>` |
| `_vocab.md 미등재 좌표` | 어휘에 없는 좌표를 썼다 | §7 — 한 줄 추가 |
| `등록부가 가리키는 섹션이 없음` | 등록부는 자리를 아는데 문서에 그 섹션이 없다 | 섹션을 만든다. 앵커 형태 그대로 |
| `status: 미결·제안` | 아젠다를 지식공유문서에 뒀다 | §8 — 이슈 대장으로 |
| `프론트매터 YAML 오류` | 제목이 `[` `{` `&` `*` 로 시작하거나 `: ` 를 포함 | **따옴표로 감싼다** |
| `id ≠ 파일명` | 둘이 다르다 | 맞춘다 |
| 커밋은 되는데 검사가 안 돈다 | `core.hooksPath` 미설정 | `git config core.hooksPath .githooks` |
| `ctx: 모르는 명령` | **번들이 낡았다** | `ctx version` 확인 → 관리자에게 새 `bin/ctx.mjs` 요청 |

### Node 가 없어도 된다

`bin/ctx` 가 알아서 넘긴다.

```
node 있으면   → node bin/ctx.mjs
없으면        → cdp.exe ctx
둘 다 없으면   → 그 사실을 말하고 멈춘다
```

**exit code 까지 같다.** git 훅도 그대로 돈다.

### LLM 이 없거나 skill 을 못 부르면

`.claude/skills/*/SKILL.md` 는 **사람이 읽는 마크다운이다.** 지시문이지 API 가
아니므로 그 파일을 열어 붙여넣어도 동작한다.

사람만 있어도 된다 — `bin/ctx where <좌표>` 가 그 좌표의 지금 상태를 알려주고,
`docs/` 를 직접 읽으면 된다.
