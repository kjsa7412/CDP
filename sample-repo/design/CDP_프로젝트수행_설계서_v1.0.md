# 제1부 — 모델

## 1. 두 층으로 나누는 이유

프로토콜은 **결정과 사건**을 다루도록 설계됐다. append-only 이고 정정된 것은 `supersedes` 로 내린다. 회의 결과·설계 판단을 남기는 데는 이것이 맞다.

SI 프로젝트에는 다른 종류의 정보가 있다.

| | 사건 | 상태 |
|---|---|---|
| 질문 | "왜 이렇게 됐나" | "**지금 어떻게 돼 있나**" |
| 예 | 8월에 A10 연동 방식을 바꾼 이유 | `RP_PLND_MST` 의 현재 컬럼 구성 |
| 성질 | 불변 | 가변. 계속 덮어쓴다 |
| append-only | 맞다 | **최악이다** |

상태를 사건 로그로만 보관하면 이렇게 된다.

```
"RP_PLND_MST 의 현재 컬럼이 뭐지?"
  → 그 좌표를 건드린 문서 7건을 찾아 날짜순으로 머릿속에서 재생한다
  → 그래도 확신이 안 선다. 놓친 문서가 있을 수 있다
```

프로토콜 §12.3의 [절단]은 "몇 건을 안 넣었다"를 통보라도 하는데 **이쪽은 7건을 다 넣어도 답이 안 나온다.** 사람이 재생해야 하고, AI 세션에 넣으면 7건이 컨텍스트를 태운다.

> **SI 프로젝트에서 압도적으로 많이 묻는 질문은 "왜"가 아니라 "지금 어떻게"다.** 테이블 정의서, 화면 정의, 인터페이스 규격, 코드값 — 전부 상태다.

### 정규화로 읽으면

프로토콜 §9.4는 `_vocab.md` 를 두면서 이렇게 적었다.

> *"이 대상의 정식 이름이 무엇인가는 문서에 딸린 정보가 아니라 **대상 자체에 딸린 정보**다."*

같은 문장이 상태에 적용된다.

> 이 테이블의 현재 컬럼 구성이 무엇인가는 문서에 딸린 정보가 아니라 **테이블 자체에 딸린 정보**다.

**이름은 이미 정규화돼 있고 상태는 그렇지 않다.** 그 비대칭을 메운다.

### 다만 좌표당 문서로 쪼개지 않는다

관계형 정규화에서도 **분해는 이득이 있을 때만 한다.** 좌표마다 문서를 하나씩 두면 두 가지를 잃는다.

**첫째, 작성 비용.** 좌표 5개짜리 작업이면 문서 5개를 고쳐야 한다. 시간이 관문은 아니지만(§16) 파생의 폭은 여전히 조절해야 한다 — 그것이 유일한 손잡이다.

**둘째, 연관관계.** 한 세션의 작업은 **하나의 일**이다.

```
"면접심사의견등록(PSC043)을 새로 만들었다.
   → 그러려면 ps_ext_emp_mst 에 업무구분·전화 컬럼이 필요했고
   → 그 과정에서 '응시원서 접수부' 라는 산출물 용어를 정의했다"

셋이 연결된 이유는 하나의 목적에서 나왔기 때문이다.
좌표당 문서로 흩으면 그 사실이 사라진다.
각자의 변경 이력 한 줄이 같은 작업 id 를 가리키지만
**그것은 색인이지 맥락이 아니다.**
```

프로토콜 §8.4가 지키려던 것이 이 맥락이다 — *"왜"에 담기는 제약과 트레이드오프는 필드로 쪼개는 순간 죽는다.*

**그래서 의도적으로 비정규화한다.** 작업 기록은 하나로 두고, 상태 조회가 실제로 필요한 대상만 관리 문서로 뽑는다. §6에서 보듯 **좌표별 정밀도는 파일 분할이 아니라 계산으로 얻는다.**

## 2. 작업 기록 — 필수이고, 하나이고, 여러 좌표를 담는다

### 2.1 세션 하나가 문서 하나를 남긴다

```
work/2026-0821-면접심사의견-개편.md

---
id: 2026-0821-면접심사의견-개편
title: 면접심사의견등록(PSC043) 개편 — 현황/작성 화면 분리
date: 2026-08-21
author: kjsa
status: 확정
touches:
  - screen:PSC043
  - table:ps_ext_emp_mst
  - term:응시원서접수부
tags: [채용, 화면개편]
---

(자유 형식 본문 — §13)

면접심사의견등록을 현황/작성 두 화면으로 나눴다.
작성 화면에서 외부 심사위원을 고를 수 있어야 해서
ps_ext_emp_mst 에 업무구분(wrk_tp_cd)과 전화(tel_no)를 추가했다.

기존 오프라인 방식은 응시자 서류 묶음을 앞에 놓고 한 명씩 넘기며 쓰는 것이었다.
화면이 그 동작을 그대로 흉내내야 해서 왼쪽에 서류, 오른쪽에 의견을 뒀다.
...
```

**좌표 셋이 한 문서 안에 있고, 왜 함께인지가 본문에 산문으로 남는다.**

### 2.2 필수인 것은 이것 하나뿐이다

| | |
|---|---|
| **작업 기록** | **필수.** 세션이 끝나면 반드시 남긴다 |
| 관리 문서 갱신 | **파생.** 등록된 좌표에 대해서만, 한 번 더 |

**작업 기록이 원본이고 관리 문서는 파생물이다.** 둘이 어긋나면 **작업 기록이 맞고 관리 문서가 틀린 것**이다. 이 방향을 정해두지 않으면 불일치가 났을 때 무엇을 고칠지 알 수 없다 — §6의 밀림 검출이 이 전제 위에 선다.

### 2.3 프론트매터

| 필드 | 필수 | 형식 | 역할 |
|---|:--:|---|---|
| `id` | O | `YYYY-MMDD-slug` | 참조 키. 파일명과 일치 |
| `title` | O | 한 줄 | 색인 표시 |
| `date` | O | `YYYY-MM-DD` | 정렬·최신성 계산의 기준 |
| `author` | O | 이름 | 문의처 |
| `status` | O | `확정`/`제안`/`진행중` | **`미결` 은 없다** (정정_판정모델_v2 §2) |
| `touches` | | `타입:값` 배열 | 이 작업이 **바꾼** 대상(§5). 0개도 정상 |
| `supersedes` | | 이전 `id` | **이 기록 자체가 오기재일 때만**(§6.3) |
| `attachments` | | 경로 배열 | 상세 문서 |
| `tags` | | 자유 문자열 | 보조 검색 |

프로토콜 §8.2에서 바뀐 것은 둘이다 — `touches` 가 필수가 아니고(§5.3), `supersedes` 의 용도가 좁아졌다(§6.3).

## 3. 관리 문서 — 팀이 하나로 관리하는 산출물

### 3.1 무엇이 관리 문서인가

**SI 프로젝트가 이미 하나로 관리하고 있는 산출물**이다. 새 개념이 아니라 이미 있는 것을 저장소 안으로 들여온다.

| 관리 문서 | 무엇 | 갱신 계기 |
|---|---|---|
| `테이블정의서.md` | 전 테이블의 컬럼·제약 | 컬럼 추가·타입 변경 |
| `코드정의서.md` | 코드그룹과 값 | 코드값 추가 |
| `용어집.md` | 도메인 용어 정의 | 새 용어 확정 |
| `인터페이스정의서.md` | 연계 규격 | API 스펙 변경 |
| `화면정의서_인사.md` | 업무별 화면 정의 | 화면 신설·변경 |

컬럼이 추가되면 테이블 정의서를 관리하는 **그 한 문서에** 기입한다.

### 3.2 입도는 좌표계가 아니라 팀이 정한다

```
좌표계가 정하면          팀이 정하면
────────────────────    ─────────────────────────────
table 31개              테이블정의서.md 1개
 → 문서 31개              → 그 안에 ## 섹션 31개
                        (SI 산출물 관행 그대로)
```

| 관리 단위 | 예 | 근거 |
|---|---|---|
| 전체 1개 | 테이블정의서 · 코드정의서 · 용어집 | 제출 산출물이 하나다 |
| 업무별 1개 | 화면정의서_인사 · 화면정의서_예산 | 화면이 많고 담당이 갈린다 |
| 대상별 1개 | 대형 인터페이스 명세 | 그것 하나가 이미 수십 쪽이다 |

**셋 다 허용한다.** 결정 기준은 하나다 — **팀이 "그 문서 열어봐"라고 말할 때 가리키는 단위.**

큰 문서를 허용할 수 있는 이유는 **`cdp-load` 가 섹션만 주입하기 때문**이다(§8.1). 테이블정의서가 977행이어도 `## rp_plnd_mst` 섹션만 들어간다. **문서를 크게 묶어도 읽기 비용이 안 는다.**

### 3.3 구조 — 상태는 덮고 이력은 섹션에 붙는다

```markdown
# 테이블 정의서

## rp_plnd_mst — 계획서마스터
<!-- applied: 2026-0821-계획서-상태값추가 -->

연구계획서 1건당 1행. 계획서변경(`RP_PLND_CHG_MST`)과 1:N.

| 컬럼 | 타입 | NULL | 설명 |
|---|---|:--:|---|
| plnd_id | varchar(20) | N | PK |
| plan_stat_cd | varchar(4) | N | 계획서 상태. 코드그룹 PL010 |

**변경** · 2026-08-21 [`상태값추가`](../work/2026-0821-계획서-상태값추가.md) `plan_stat_cd` 에 `50`(반려) 추가
· 2026-06-12 [`스키마정리`](../work/2026-0612-계획서-스키마정리.md) `rmk` 삭제

## rp_plnd_chg_mst — 계획서변경마스터
<!-- applied: 2026-0902-계획서변경-요청분리 -->
...
```

| 부분 | 성질 |
|---|---|
| 섹션 본문 | **덮어쓴다.** 현재 상태만. 과거 상태를 남기지 않는다 |
| `<!-- applied: -->` | **밀림 계산의 근거**(§6.2). Git diff 에 보이고 사람도 읽는다 |
| 변경 줄 | **쌓는다.** 날짜 + 작업 기록 링크 + 한 줄 요약 |

> **변경 줄에 상세를 복사하지 않는다.** "무엇을 왜 바꿨나"는 작업 기록에 있고 여기에는 링크와 한 줄만 둔다. 복사하는 순간 두 곳을 고쳐야 하고 정규화가 깨진다.

### 3.4 빈 섹션을 만드는 것을 두려워하지 않는다

```markdown
## SEB020 — 사전검토의견서등록
<!-- applied: null -->

> ⚠ 아직 정리되지 않았습니다. 이 화면을 작업하는 사람이 채워주세요.
```

**비어 있는 것과 없는 것은 다르다.** 비어 있으면 채울 자리가 보이고, 없으면 그 화면의 존재 자체가 안 보인다. 프로토콜 §9.6의 조용한 실패를 관리 문서 층에서도 막는 장치다.

## 4. 등록부 — 좌표에서 문서·섹션으로

좌표에서 경로를 계산하지 않는다. **`_managed.md` 에 선언한다.** 매핑이 한 곳에만 있어야 어긋나지 않는다.

```markdown
# 관리 문서 등록부

| 좌표 패턴 | 관리 문서 | 섹션 | 비고 |
|---|---|---|---|
| `table:*` | `docs/테이블정의서.md` | `## {값}` | |
| `code:*` | `docs/코드정의서.md` | `## {값}` | |
| `term:*` | `docs/용어집.md` | `### {값}` | |
| `api:*` | `docs/인터페이스정의서.md` | `## {값}` | |
| `screen:PS*` | `docs/화면정의서_인사.md` | `## {값}` | 인사·채용 |
| `screen:SE*` | `docs/화면정의서_연구.md` | `## {값}` | 연구과제 |
| `screen:*` | `docs/화면정의서_기타.md` | `## {값}` | 위에 안 걸리는 것 |
```

| 규칙 | |
|---|---|
| **패턴으로 쓴다** | `screen:PS*` 처럼. 좌표가 늘어도 등록부는 안 늘어난다 |
| **위에서부터 먼저 걸리는 것** | 구체적인 패턴을 위에 둔다 |
| **없어도 된다** | `module:` `domain:` 은 등록하지 않는다. 작업 기록에만 남고 그것이 정상이다 |
| **한 곳에만 있다** | 매핑을 바꾸려면 이 파일만 고친다 |

## 5. 좌표 — 이 작업이 바꾼 대상

### 5.1 판정 규칙

도메인 용어는 문서에 차고 넘친다. **언급을 전부 좌표로 넣으면 좌표는 태그와 다를 바 없어지고**, 프로토콜 §9.4가 경계한 붕괴가 다른 경로로 온다.

> ## 좌표 = **6개월 뒤 이 대상을 맡은 사람이 이 작업을 찾아야 하는가**

검증 가능한 형태로 바꾸면 — 이 작업이 그 대상을 **바꿨는가**, 아니면 **쓰기만 했는가**.

| 관계 | 좌표 |
|---|:--:|
| 신설했다 | **O** |
| 변경했다 (컬럼 추가, 규격 변경, 상태값 추가) | **O** |
| 삭제·폐기했다 | **O** |
| 참조했다 · 호출했다 · 언급했다 | **X** |
| 그것을 쓰는 다른 것을 만들었다 | **X** |

**"주제인가?"는 사람마다 답이 갈리지만 "바꿨는가?"는 diff 를 보면 결판난다.**

### 5.2 예시 — 신규 화면 작업

| 대상 | 관계 | 좌표 | 관리 문서 |
|---|---|:--:|---|
| `screen:PSC043` | 화면 신설 | **O** | 화면정의서_인사 `## PSC043` |
| `table:ps_ext_emp_mst` | 컬럼 2개 추가 | **O** | 테이블정의서 `## ps_ext_emp_mst` |
| `term:응시원서접수부` | 용어 신설 | **O** | 용어집 `### 응시원서접수부` |
| `screen:PSC031` | 첨부를 읽어옴 (PSC031 은 안 바뀜) | X | — |
| `module:code-help` | 기존 컴포넌트 사용 | X | — |
| `domain:인사채용` | 분류 | △ | 등록 안 함 |

**X 로 판정된 것도 본문에는 쓴다.** "PSC031 의 첨부파일을 이 화면에서 읽는다"는 중요한 정보다. 다만 **PSC031 을 맡은 사람에게 이 작업이 검색돼야 할 이유는 없다** — PSC031 은 안 바뀌었으니까.

**`domain:` 은 △다.** 관리 문서가 없어 형상관리 대상이 아니지만 분류 축으로는 쓸모가 있다. **최신성·밀림 계산에서 제외한다.**

### 5.3 좌표 개수

| 상황 | 판정 |
|---|---|
| 0개 | **정상.** 버그 수정·리팩터링. 이력엔 남고 검색엔 안 걸린다 |
| 1개 | **정상** |
| 8개 이상 | **작업을 쪼개라는 신호.** 프로토콜 §9.3이 여기서 유효하다 |

### 5.4 좌표 타입

| 타입 | 대상 | 관리 문서 | 값 규칙 |
|---|---|---|---|
| `table:` | DB 테이블 | 테이블정의서 | 물리명 소문자 |
| `screen:` | 화면 | 화면정의서_* | 화면 코드 |
| `api:` | 인터페이스 | 인터페이스정의서 | 경로 |
| `module:` | 코드 모듈 | **없음** | 패키지/모듈명 |
| `term:` | 도메인 용어 | 용어집 | 정본 표기 |
| `domain:` | 업무 영역 | **없음** | 한글 |
| `code:` | 코드그룹 | 코드정의서 | 코드그룹 ID |

**`term:`** — SI 에서 용어 정의는 산출물이고, 용어 하나가 바뀌면 화면·테이블·API 가 함께 흔들린다. 용어에 섹션을 주면 그 파급을 한 곳에서 관리한다.

**`code:`** — 코드값은 테이블도 화면도 아닌데 상태가 있고 자주 바뀐다. `plan_stat_cd` 에 값 하나가 추가되면 그것을 쓰는 모든 화면이 영향받는다. 테이블 정의에 묻어두면 못 찾는다.

> **더 늘리지 않는다.** 프로토콜 §8.3 — *"있으면 좋겠다"가 아니라 "없어서 오적용이 났다"* 로 추가한다.

## 6. 최신성 — 하나의 계산 ★

### 6.1 정의

```
later(기준, 좌표 C) = C 를 touches 에 가진 작업 기록 중 기준보다 나중의 것
```

이 함수 하나가 세 곳에 쓰인다.

| 기준 | 무엇을 판정하나 | 쓰이는 곳 |
|---|---|---|
| 작업 기록 `D` | D 의 그 좌표 서술이 최신인가 | 검색 결과 · 주입 신호(§6.3) |
| 관리 문서 섹션의 `applied` | 섹션이 밀렸는가 | `ctx stale` · 훅 경고(§6.2) |
| 없음(전체) | 그 좌표의 최신 작업 기록은 무엇인가 | `cdp-load` 가 먼저 읽을 것 결정 |

**구현이 하나면 된다.** 뷰어 `core/validity.js` 의 `buildSettledness` 가 기준점을 인자로 받게 하면 세 용도를 다 덮는다.

> **이 통일이 §1의 판단을 뒷받침한다.** 좌표당 문서를 만들지 않아도 좌표별 정밀도를 잃지 않는다 — **정밀도는 파일 분할이 아니라 계산에서 나온다.**

### 6.2 밀림 — 형상관리의 실체

관리 문서의 유일한 실패 양상은 **작업은 했는데 관리 문서를 안 고친 것**이다. 그러면 관리 문서가 자신 있게 거짓말한다. 프로토콜 §10.5가 `INDEX.md` 를 두고 한 말이 그대로다 — *"어긋난 인덱스는 없는 것보다 나쁘다."*

```
docs/테이블정의서.md
  ## rp_plnd_mst   <!-- applied: 2026-0821-계획서-상태값추가 -->

later(2026-0821, table:rp_plnd_mst) =
    2026-0902-계획서변경-요청분리
    2026-0903-계획서-이력테이블

→ 테이블정의서의 rp_plnd_mst 섹션이 2건 밀렸다
```

> **정정 (`docs/정정_판정모델_v2.md` §1) — 밀림은 거부다.**
>
> 아래는 밀림을 경고로 두고 댄 이유 셋이다. **셋 다 성립하지 않는다.**
>
> | 원래 이유 | 정정 |
> |---|---|
> | 파생의 폭이 넓다 | **넓어도 해야 한다.** 넓다는 것은 그 작업이 실제로 그만큼 건드렸다는 뜻이다 |
> | 남의 확인이 필요하다 | **필요 없다.** 판단 근거는 지식공유문서에 이미 다 들어 있다 |
> | 급한 커밋을 막으면 우회한다 | **막히는 것은 코드 커밋이 아니라 지식 레포 커밋이다.** 코드를 먼저 커밋하고 지식공유문서는 그 뒤에 쓰면 된다 |
>
> **지식공유문서를 남기면서 관리 문서 파생은 필수다. 선택이 아니다.**
> `stale-section` 은 `error` 이고 훅이 커밋을 막는다.

아래는 정정 전 서술이다 — 판단의 경위로 남긴다.

~~**밀림은 경고이지 거부가 아니다.**~~ 훅이 "관리 문서를 안 고쳤으니 거부"를 하면 안 되는 이유가 셋이다.

1. 좌표 5개면 관리 문서 3개를 그 자리에서 다 고쳐야 한다 — 파생의 폭이 감당 못 할 만큼 넓어진다
2. 관리 문서 갱신에 다른 사람의 확인이 필요한 경우가 있다
3. 급한 커밋을 막으면 훅을 우회한다 (프로토콜 §9.7 안티패턴)

```
$ git commit
[ctx] ⚠ 관리 문서가 밀립니다
       docs/테이블정의서.md    ## ps_ext_emp_mst
       docs/화면정의서_인사.md  ## PSC043
       `ctx stale` 로 확인하거나 cdp-managed skill 로 따라잡으세요
[ctx] ✓ 커밋 진행
```

**막는 것은 미등재 좌표 하나뿐이다.** 그건 1초면 고치고, 안 고치면 프로토콜 §9.6의 조용한 실패로 들어간다. **밀림은 조용한 실패가 아니다 — 계산으로 드러나고 목록에 남는다.**

프로토콜 §12.2의 최신성이 여기서 처음으로 **행동**이 된다. 경고는 무시되지만 **할 일 목록은 줄거나 안 줄거나 둘 중 하나**라서 관리가 된다.

### 6.3 좌표별 최신성 — 후속이 붙는 것은 문서가 아니다

작업 기록 하나에 좌표가 여러 개 있고(§2.1), **좌표마다 그 뒤의 사정이 다르다.**

```
work/2026-0710-A10-어댑터-v1
  touches: table:rp_plnd_mst · api:/adapter/a10/plan-sync · module:acl-a10-adapter

  table:rp_plnd_mst          이후 3건 더 있다
  api:/adapter/a10/plan-sync 이후 문서 없다
  module:acl-a10-adapter     이후 1건 있다
```

**이 문서가 "낡았는가"에는 답이 없다.** 테이블 얘기는 낡았을 수 있고 API 규격은 여전히 이 문서가 최신이다. 문서 단위로 판정하면 **둘 중 하나는 반드시 틀린다.**

> ## 문서는 사건이라 통째로 낡지 않는다. **후속이 붙는 것은 (문서, 좌표) 쌍이다.**

| `later(D, C)` | 상태 | 뜻 |
|---|---|---|
| 0건 | **최신** | 이 좌표에 대해서는 이 문서가 마지막 말이다 |
| N건 | **후속 N건** | 이 좌표에 대한 서술은 갱신됐을 수 있다. **틀렸다는 뜻은 아니다** |

**"후속 있음"을 "정정"이라 부르지 않는다.** 후속 문서가 그 좌표를 조금 손봤는지 완전히 뒤집었는지 **기계는 모른다.** 프로토콜 §12.2가 나이와 유효성을 구분한 것과 같은 절제다 — 아는 것만 말한다. 화면에서도 적색이 아니라 앰버를 쓴다(§15.3).

### `supersedes` 는 계산이 대신한다

| 상황 | 처리 |
|---|---|
| 같은 좌표를 다시 바꿨다 | **계산된다.** `supersedes` 를 안 붙인다 |
| 좌표 일부만 바꿨다 | **계산된다** |
| **기록 자체가 틀렸다** (오기재) | **`supersedes` 를 쓴다.** 이 용도만 남는다 |

프로토콜 §11.1이 `knowledge-share` 에 "supersedes 후보 제시" 단계를 넣은 이유가 *"사람은 3개월 전 문서의 id 를 기억하지 못한다"* 였다. 계산으로 대신하면 **그 단계 자체가 필요 없다. 기억할 것을 없애는 편이 기억을 돕는 것보다 낫다.**

프로토콜 §9.8이 본 문제(좌표별 입도가 필요하다)는 실재하고 이 설계에서도 그대로다. 다만 **해결 수단이 필드가 아니라 계산이다.** §9.8이 스스로 지적한 비용 — *"프론트매터를 객체 배열로 만들어 작성 마찰을 확실히 올린다"* — 을 계산은 치르지 않는다.

### 6.4 관계 용어 — 정본 ★

**여기가 관계 개념의 유일한 정의 자리다.** 설계서·코드·화면·주입 신호가 전부 이 표를 따른다. 표에 없는 말은 화면에 쓰지 않는다.

원칙 셋 —

1. **뜻이 다른 것은 합치지 않는다.** 이름만 하나로 못박는다
2. **화면어와 코드 식별자를 1:1로 고정한다**
3. **한 사실을 두 이름으로 부르지 않는다.** 주체가 달라도 이름은 하나다

#### 시간 축 — 뒤에 무엇이 왔나

| 개념 | **이름** | 코드 식별자 | 색 | 주체 |
|---|---|---|:--:|---|
| `later(D,C)` — 이 좌표를 나중에 또 바꾼 작업이 있다 | **후속** | `later` · `laterCount` | 앰버 | (작업, 좌표) 쌍 |
| 관리 문서 섹션이 `applied` 뒤의 후속을 못 싣고 있다 | **밀림** | `stale` | 앰버 | 섹션 |
| **기록 자체가 틀려서** 다른 기록이 바로잡았다 | **정정** | `supersedes` · `superseded` | 적 | 작업 |

셋 다 "더 새로운 것이 있다"인데 **주어가 다르다.** 그래서 이름이 셋이어야 한다. 후속·밀림은 §6.1의 `later()` 하나에서 기준점만 바꿔 나오고, 정정은 계산이 아니라 사람이 선언한 것이라 색이 다르다.

> **"덮임"을 쓰지 않는 이유.** `supersedes` 는 오기재 정정 전용인데(§6.3) "덮임"은 "밀림"과 소리도 뜻도 붙는다. ⛔덮임 과 ⚠밀림 이 한 줄에 같이 나오면 사용자는 둘을 정도 차이로 읽는다. **정정은 정도가 아니라 종류가 다르다 — 그건 틀린 기록이다.**

#### 반영 축 — 관리 문서에 실렸나

| 개념 | **이름** | 코드 식별자 | 색 |
|---|---|---|:--:|
| 섹션의 `applied` 가 이 작업이다 | **반영됨** | `applied` | 없음 |
| `applied` 가 비어 있다 | **미작성** | `unwritten` · `empty` | 앰버 |
| 등록부가 가리키는데 섹션이 없다 | **섹션 없음** | `anchor-missing` | 적 |
| 등록부가 가리키는데 파일이 없다 | **문서 없음** | `doc-missing` | 적 |
| `applied` 가 없는 id 를 가리킨다 | **끊김** | `orphan` | 적 |
| 등록부에 그 좌표가 없다 | **관리 대상 아님** | `section === null` | 없음 |

**"미반영"을 별도 용어로 만들지 않는다.** 그것은 밀림을 작업 쪽에서 본 것일 뿐 다른 사실이 아니다. 주어를 섹션으로 고정하고 설명절을 붙인다 — *"테이블정의서 밀림 — 이 작업이 아직 안 실렸습니다"*.

#### 나머지

| 개념 | **이름** | 코드 식별자 |
|---|---|---|
| 어휘에 등재되지 않은 좌표 | **미등재** | `unregistered` |
| 주입 시 일부만 실었다 | **절단** | 신호 `[절단]` |

#### 버리는 말

| 버림 | 대신 |
|---|---|
| 이후 N건 | **후속 N건** |
| 덮임 | **정정** |
| 결착 · 결착도 | **최신성** (계산의 이름) · **후속** (그 결과) |
| applied 깨짐 | **끊김** |

**주입 신호도 이 표를 따른다** — 프로토콜 §12.3의 `[결착]` 은 `[최신]` 이다. 화면에서 "후속 2건"을 본 사람이 붙여넣은 프롬프트에서 다른 말을 읽으면, 둘이 같은 것인지 알 수 없다.

`_vocab.md` 의 `term:최신성` 은 `결착`·`결착도` 를 alias 로 흡수한다 — **구명칭으로 검색해도 대조가 정본으로 데려온다.**

## 8. skill 3종

### 8.1 `cdp-load` — 좌표를 인자로 받아 주입한다

**호출 시점과 좌표 추출은 이 skill 의 일이 아니다.** 작업환경 v1.1 §5~7 이
정본이다 — 요청을 받으면 ① 검토에서 좌표를 뽑고, 필요하다고 판정되면
② 에서 이 skill 을 **좌표를 인자로** 호출한다.

```
cdp-load screen:PSC043 code:PS130
```

**추출이 빠진 결과 이 skill 이 순수해진다.** 같은 좌표를 주면 항상 같은 것을
주입하므로 재현하고 시험할 수 있다.

```
1. 받은 좌표를 _vocab.md 로 정규화 (프로토콜 §9.5(2) 대조)
   인자가 이미 정본이면 그대로 쓴다

2. _managed.md 대조 → 관리 문서와 섹션을 찾는다

3. **관리 문서의 해당 섹션만 주입한다**
   문서 전체가 아니다. 31개 테이블을 다 넣으면 컨텍스트가 죽는다

4. 작업 기록은 기본으로 넣지 않는다
   섹션의 변경 줄(최근 2~3개)만 제목으로 보여준다
   "왜 이렇게 됐는지"가 필요해지면 그때 연다

5. **밀렸으면 반드시 알린다**

6. 관리 문서가 없는 좌표(module: 등)는 작업 기록으로 폴백.
   이때 좌표별 최신성을 함께 싣는다(§6.3) — 작업 기록이 유일한
   근거인 좌표이므로 어느 부분을 믿을지 알려줘야 한다

7. 절단 신호는 그대로 (프로토콜 §12.3)
```

```

[상태]   docs/테이블정의서.md ## rp_plnd_mst      ⚠ 2건 밀림
[근거]   2026-0710-A10-어댑터-v1
         · table:rp_plnd_mst          후속 3건 — 이 부분은 갱신됐을 수 있음
         · api:/adapter/a10/plan-sync 최신
[절단]   매칭 8건 중 3건 주입. 나머지 id: 2026-06…, 2026-05…
```

**[근거] 줄의 좌표별 표시가 §6.3이다.** "이 문서를 믿어라/마라"가 아니라 **"어느 부분을 믿어라"** 를 말한다.

| | 프로토콜 v1.1 | 이 설계 |
|---|---|---|
| 주입 | 좌표에 걸린 문서 요약 상위 5건 | **관리 문서 섹션 1개/좌표** |
| 정확도 | 이력을 AI 가 재생 | **재생 불필요** |
| "왜" | 요약에 섞임 | 필요할 때 작업 기록을 연다 |

> **5번이 없으면 이 설계는 위험하다.** 밀린 섹션을 최신인 것처럼 주입하면 AI 는 낡은 스키마를 확신 있게 쓴다. 이력 재생은 느릴 뿐이지만 **밀린 관리 문서는 틀린 답을 빠르게 준다.**

### 8.2 `cdp-save` — 세션 종료

```
1. git diff + 세션 대화에서 변경 파악

2. 좌표 판정 — §5의 규칙. 판정 근거를 보여준다
     screen:PSC043        신설    → 좌표
     table:ps_ext_emp_mst 변경    → 좌표
     term:응시원서접수부    신설    → 좌표
     screen:PSC031        참조만  → 좌표 아님 (본문에만)

3. 작업 기록 초안 — 자유 형식(§13). **여기까지가 필수**
   이유가 안 보이면 한 번 묻는다: "이 판단의 제약이 뭐였나요?"

4. _managed.md 대조 → 파생 대상
     screen:PSC043        → 화면정의서_인사.md  ## PSC043
     table:ps_ext_emp_mst → 테이블정의서.md     ## ps_ext_emp_mst
     term:응시원서접수부    → 용어집.md          ### 응시원서접수부
     (module:code-help 는 등록부에 없다 → 파생 없음)

5. 파생 갱신 diff 제안 — **섹션만** 바뀐다
     docs/테이블정의서.md
       ## ps_ext_emp_mst
       <!-- applied: 2026-0715-… → 2026-0821-면접심사의견-개편 -->
     + | wrk_tp_cd | varchar(4)  | Y | 업무구분. 코드그룹 PS130 |
     + | tel_no    | varchar(20) | Y | 전화 (하이픈 제거 저장) |
     + **변경** · 2026-08-21 [`면접심사의견-개편`](…) wrk_tp_cd·tel_no 추가

   사람은 **승인만** 한다.  [전체 승인]  [건너뛰기]

6. 신규 용어는 _vocab.md 등재도 함께

7. 한 커밋 — 작업 기록 1 + 관리 문서 N
```

**4번이 자동이라는 것이 이 설계의 값어치다.** 사람은 "어느 문서를 고쳐야 하지"를 생각하지 않는다. 좌표를 붙이는 순간 등록부가 답한다.

> **7번이 형상관리의 실체다.** 작업과 그것이 만든 상태 변경이 한 커밋에 있으면 `git log -L '/## rp_plnd_mst/,/^## /:docs/테이블정의서.md'` 로 그 테이블의 변경 이력이 그대로 나온다. **Git 이 이미 형상관리 도구이고 우리는 파일 배치만 맞춰주면 된다.**

### 8.3 `cdp-managed` — 밀린 것 따라잡기

```
1. ctx stale 로 밀린 섹션 목록
2. 섹션 하나를 골라 밀린 작업 기록들을 순서대로 읽는다
3. 반영 diff 를 만들어 제안
4. 승인 → 섹션 갱신 + applied 갱신 + 커밋
```

**따로 두는 이유** — 세션 종료 때 파생까지 강제하면 마찰이 커져 `cdp-save` 자체를 안 부른다. **작업 기록은 반드시 남기게 하고, 파생은 밀려도 되게 하되 밀린 것이 보이게 한다.** 그 뒤처짐을 정리하는 전용 경로다.

## 9. hook

```sh
#!/bin/sh
./bin/ctx check || exit 1
./bin/ctx index
git add INDEX.md INDEX-by-coord.md
```

| 검사 | 판정 | 근거 |
|---|---|---|
| `_vocab.md` 미등재 좌표 | **거부** | 프로토콜 §9.6. 1초면 고친다 |
| 필수 프론트매터 누락 | **거부** | 같음 |
| `id` ≠ 파일명 | **거부** | 참조가 깨진다 |
| 등록부가 가리키는 섹션이 없음 | **거부** | 앵커가 끊기면 파생이 조용히 실패한다 |
| **관리 문서 밀림** | **경고** | §6.2 |
| 등록부에 없는 좌표 | **경고** | 관리 문서 없는 좌표는 정상이다(§4) |
| 본문 형식·길이·섹션 | **검사 안 함** | §13 |

> **거부 목록이 짧은 것이 중요하다.** 프로토콜 §11.2가 *"skill 은 편의, hook 은 보증"* 이라 했는데 보증할 것을 늘리면 훅이 미움받고 우회된다. **되돌릴 수 없는 것만 막는다** — 미등재 좌표는 나중에 찾을 방법이 없지만 밀림은 계산으로 찾을 수 있다.

## 10. 작업 절차 안에서의 위치

**절차의 정본은 작업환경 v1.1 §5~8 이다.** 이 문서의 skill 들이 그 안에서
어디에 놓이는지만 적는다.

```
   사용자 요청
        │
   ① 검토      요청을 이해하고 좌표를 뽑는다.  ctx match 로 대조
        │        **지식 레포 본문은 읽지 않는다**
        │        일찍 읽으면 요청 해석이 편향된다
   ② 주입      조건부.  cdp-load <좌표…>          ← §8.1
        │
   ③ 설계      관리 문서 섹션을 근거로 수행하고 답한다
        │
   ④ 기록      cdp-save                          ← §8.2
```

**세션 시작이 아니라 요청 다음이다.** 좌표는 *"이 작업이 바꾼 대상"*(§5)이므로
무엇을 바꿀지 모르는 시점에는 뽑을 것이 없다.

**③에서 사라진 것** — 테이블 정의서 엑셀을 찾아 여는 일, 그것이 최신인지
담당자에게 묻는 일, 문서 7건을 읽고 현재 상태를 재구성하는 일.

## 13. 본문 형식 — 자유

**GFM 마크다운이면 되고 그 안은 자유다.** 섹션 구조를 강제하지 않는다.

| 근거 | |
|---|---|
| **관리 문서에는 안 맞는다** | 테이블 정의서에 "누구에게 영향"을 쓸 자리가 없다 |
| **작업 기록에도 과하다** | 오타 하나 고친 기록에 빈 섹션 넷이 생긴다. 프로토콜 §8.3의 *"빈 필드는 없는 필드보다 나쁘다"* 가 본문에서 재현된다 |
| **작성 마찰** | 기록을 형식만 채우게 만든다(§16) |
| **AI 가 초안을 쓴다** | 형식 강제의 절반은 사람이 빠뜨리지 않게 하려는 것이었다 |

### 그래도 지키는 것 — 규범이지 형식이 아니다

프로토콜 §8.4의 통찰은 유효하다.

> *"6개월 뒤 이 결정을 뒤집으려는 사람이 필요로 하는 것은 무엇이 바뀌었는지가 아니라 **어떤 제약 때문에 그렇게 했는지**다."*

**형식으로 강제하지 않고 둘로 대신한다.**

1. **템플릿은 제안한다.** `TEMPLATE-work.md` 에 출발점을 두되 "지우고 자유롭게 쓰라"고 주석으로 적는다
2. **skill 이 묻는다.** `cdp-save` 가 초안에 이유가 없으면 한 번 묻는다. 훅이 막는 것보다 이쪽이 실제로 채워진다

`ctx check` 는 **본문을 검사하지 않는다.** 길이도 섹션도 보지 않는다.

> **강제를 없앤 대가는 "왜"가 빠진 문서가 생기는 것이다.** 감수한다 — 빈 섹션 넷이 있는 문서보다 짧고 솔직한 자유 문서가 낫다. 뷰어가 표시할 수는 있지만 **경고이지 거부가 아니다.**

## 14. 정보 구조 — 뷰 2개

작업 기록/관리 문서 분리가 1차 축을 만들어준다. **좌표 하나를 고르면 그 좌표의 모든 것이 나온다.**

# 제5부 — 실행

## 16. 작성 비용 — 급소가 아니다

프로토콜 §16은 *"이 프로토콜의 생사는 '작성이 5분 안에 끝나는가' 하나에 달려 있다"* 고 했다.
**이 프로젝트에서는 그렇지 않다.**

> **기록은 업무다. 강제다.** 5분이 걸리든 15분이 걸리든 한다.

그래서 §17의 관문에서 시간 실측을 뺀다. 다만 **강제가 무엇을 해결하고 무엇을
해결하지 못하는지**는 분명히 해야 한다.

| | 강제하면 |
|---|---|
| 기록이 **생기는가** | **그렇다.** 프로토콜 §16의 위험은 사라진다 |
| 기록이 **쓸모 있는가** | **아니다.** 여기가 남은 위험이다 |

### 강제는 위험을 옮긴다

억지로 쓴 기록은 형식만 채운다 — `touches` 는 붙고 본문에는 *"용량 제한을
10MB 로 올렸다"* 만 남는다. **무엇을 했는지는 있고 왜 했는지는 없다.**

그것이 §13이 형식 강제를 폐기하면서 감수한 위험이고, 강제가 그 위험을 키운다.
안 쓰는 사람은 없어지지만 **비어 있게 쓰는 사람**이 생긴다.

| 완화 | |
|---|---|
| **본문 얇음 신호** | 형식이 없으니 길이로 어림한다. **오탐이 있으므로 `info` 로만 낸다** |
| **`cdp-save` 가 한 번 묻는다** | *"이 판단의 제약이 뭐였나요?"* 한 번만. 캐물으면 기록 자체가 형식이 된다 |
| **필수는 작업 기록 하나** | 파생은 건너뛸 수 있고, 밀린 것은 목록에 남는다(§6.2) |
| **파생은 diff 승인** | 사람이 쓰지 않는다. 새로 쓰는 것보다 고치는 것이 빠르다 |
| **대상 문서를 기계가 찾는다** | "어느 문서 고치지"를 사람이 생각하지 않는다(§8.2-4) |
| **좌표가 줄어든다**(§5) | 언급이 아니라 변경만이므로 문서당 3~6개 → 1~3개 |

**얇음 신호가 유일한 품질 장치다.** 형식을 강요하지 않고 시간도 재지 않으므로,
"비어 있게 쓴 기록"을 잡을 것이 그것뿐이다. 그래서 **없애지 않는다** — 오탐이
있어도 `info` 등급으로 남긴다.

> **잘라낼 것이 생기면 등록부의 패턴 수부터 줄인다** — `table:` `code:` 만 남기고
> 나머지는 관리 문서 없이 간다. 시간이 아니라 **파생의 폭**이 조절 손잡이다.

## 부록 E. 확정된 전제와 남은 확인 사항

### E.1 정본은 md 다 — 확정

**모든 문서는 md 로 만든다. `docs/` 가 정본이다.**

엑셀·한글·PPT 는 **제출물**이다 — 사람에게 낼 필요가 생겼을 때 그 md 로 만든다.

```
docs/테이블정의서.md          ← 정본.  형상관리 대상
      │
      └─(제출 시점에 생성)──→  테이블정의서.xlsx     ← 제출물.  형상관리 안 함
```

이 방향이 확정되면서 두 가지가 따라온다.

**(1) 밀림 계산이 단순해진다.** §6.2 의 `applied` 주석이 정본의 상태를 그대로 말한다.
엑셀이 정본이었다면 md 는 투영이 되고 밀림을 엑셀 대비로 계산해야 했다.

**(2) 역방향은 만들지 않는다.** 제출물을 고쳐도 md 로 돌아오지 않는다.
**돌아오게 만들면 정본이 둘이 된다.**

> 이 구조는 샘플 레포의 `2026-0821-응시원서접수부` 작업과 정확히 같다 — 전산을
> 정본으로 두고 한글 문서를 산출물로 뽑기로 했고, 반대 방향은 쓰지 않기로 했다.
> **같은 판단을 프로젝트 문서 자체에 적용한 것이다.**

제출물 생성은 후순위다. 필요해지는 시점에 형식이 정해지고, 그때 만든다.

### E.2 남은 확인 사항
