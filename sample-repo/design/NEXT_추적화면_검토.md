# 다음 작업 — 추적 화면 · 관계 용어 통일 · 그래프 뷰

## 사용자 요청 원문

> 1개의 세션에서 나온 정본문서가 어떤 좌표와 연결되어 있고 어떤 문서로 바뀌었고
> 덮었고 이력이 어떻게 되고 같은 추적이 가장 관건인거 같다. 문서는 문서로서의
> 정보만 표출하는 걸로한다. 데스크탑 화면 기준으로 화면을 2분할해서 각자의
> 역할을 이행하면 될 것 같다. 그래서 이 문서들의 연관관계를 어떻게 하면 체계적으로
> 보여줄 수 있을지 고민하고 아까 덮힘 이력 추적 등의 용어를 이야기 했는데 이 용어도
> 통일 해야할 것같다. 또 부가 기능으로 옵시디언 처럼 3D 그래프로 문서현황을 보고
> 클릭하면 열리는 형태도 고려해라.

## 이미 확인된 사실 — 다시 조사하지 말 것

### 1. 역추적이 API 에 없다

`store.detail(id)` 가 내는 것은 `coords · settled · backlinks · supersedes · nextInCoord` 뿐이다.
그런데 서버는 이미 계산할 수 있다.

```js
s.sections.filter(r => r.applied === id)
// 2026-0821-면접심사의견-개편 → docs/테이블정의서.md   ## ps_ext_emp_mst
//                              docs/화면정의서_인사.md ## PSC043
```

**이 역참조(작업 → 반영된 섹션)가 화면에 전혀 없다.**
사용자가 말한 *"어떤 문서로 바뀌었고"* 가 정확히 이것이다.

### 2. 문서 화면이 과부하다

`src/components/DocView.jsx` 가 본문 위아래로 싣는 것 —
유효성 블록(좌표별 판정 + 섹션 상태) · 목차 레일 · 본문 · 첨부 · 이어 읽기 ·
백링크 · 좌표 타임라인 · 복사.

뷰어 v0.2 §13-⓿ 은 *"화면의 주인은 본문이다"* 인데 **관계 정보가 본문을 밀어내고 있다.**

### 3. 용어가 두 이름으로 갈려 있다 (실측)

| 용어 | 코드·화면 | 설계서 | 문제 |
|---|---:|---:|---|
| 결착 | 16 | 46 | **최신성(10)으로 개명했는데 둘 다 살아 있다.** 화면에도 남았다 — `ValidityBlock.jsx:45,47` · `App.jsx:712` · `Timeline.jsx:4` |
| 후속 / 이후 | 9 / 14 | 26 / 41 | **같은 것을 두 이름으로 부른다.** 설계서는 "후속", UI 는 "이후 N건" |
| 덮임 | 9 | 28 | `supersedes` 는 오기재 정정 전용인데 "덮임"이 밀림과 혼동된다 |
| 미작성 | 12 | **0** | UI 에만 있고 설계서에 없다 |

영어 식별자도 겹친다 — `stale` 49 · `settled` 25 · `settledness` 2 ·
`settledCoords` 5 · `laterCount` 8 · `superseded` 26.

## A. 관계 용어 통일 — 먼저 한다

이게 안 되면 화면도 갈린다.

설계서·코드·화면의 관계 개념을 **한 벌로 확정**하고 정의를 한 곳
(수행 v1.0 §6 또는 새 부록)에 모은다. 코드 식별자와 화면 문구를 거기에 맞춘다.

**뜻이 실제로 다른 것들이니 합치지 말고 이름만 확정할 것.**

| 개념 | 지금 이름 |
|---|---|
| `supersedes` 관계 = **오기재 정정** | 덮임 / superseded |
| (문서, 좌표) 쌍에 나중 작업이 있음 | 후속 / 이후 / laterCount |
| 관리 문서 섹션이 `applied` 이후를 반영 못함 | 밀림 / stale |
| `applied: null` | 미작성 / unwritten · empty |
| 등록부가 가리키는데 없음 | 섹션 없음 / 문서 없음 |
| `applied` 가 없는 id 를 가리킴 | applied 깨짐 / orphan |
| 주입 시 일부만 실음 | 절단 |
| 어휘 미등재 | 미등재 / unregistered |

**`결착`은 잔재다.** 없애든 되살리든 결정하고, 결정한 쪽으로 코드·화면·설계서를
전부 맞춘다. 지금처럼 둘 다 있으면 안 된다. — **사용자 판단 필요**

## B. 2분할 화면 — 본문 | 관계

데스크탑 기준. 문서 화면에서 관계 정보를 오른쪽 패널로 뺀다.

```
+--------------------------+-------------------------+
|  본문                     |  관계                    |
|  제목 · 본문 · 첨부        |  좌표 · 반영 · 이력 · 정정 |
+--------------------------+-------------------------+
```

### 관계 패널이 답해야 하는 것

| | |
|---|---|
| 이 작업이 **어느 좌표**를 바꿨나 | 좌표마다 후속 건수 |
| **어느 관리 문서 섹션에 반영됐나** | ← **지금 없는 것.** `sections.filter(r => r.applied === id)` |
| **아직 반영 안 된 것**은 무엇인가 | 좌표는 있는데 섹션 `applied` 가 이 id 가 아닌 경우 |
| 무엇을 **정정했나 / 정정당했나** | `supersedes` 양방향 |
| 이 좌표의 **이력 전체** 모양 | |

**관리 문서를 열었을 때는 역할이 다르다** — 각 섹션이 어느 작업에서 왔는지
(배지는 이미 있다), 어느 섹션이 밀렸는지.

### 지켜야 할 제약

- 색 예산 **4개** — 파랑 상호작용 · 빨강 무효 · amber 경고 · purple 미결
- **정상이면 표시가 사라진다**
- 유효성 블록 정상 높이 **62px** 유지 (뷰어 §17.6 예산 72px)
- 좁은 화면에서 관계 패널이 접힌다 — 반응형 분기 1440/1000/800/620 이

## C. 그래프 뷰 (부가)

옵시디언식. **3D 를 그대로 하기 전에 두 가지를 먼저 판단할 것.**

### 노드를 무엇으로 할 것인가 — **사용자 판단 필요**

| | |
|---|---|
| 문서를 노드로 | 옵시디언과 같아진다. 대개 **장식으로 끝난다** |
| **좌표를 노드로** | 밀린 좌표가 어디 몰려 있는지, 어느 좌표에 작업이 쌓였는지가 보인다. **CDP 에서는 이쪽이 값이 있을 가능성이 높다** |

### 3D 가 2D 보다 나은가

노드 55개 규모에서 3D 는 **회전 조작 비용만 늘 수 있다.**
2D force graph 로 먼저 만들고 3D 는 옵션으로 두는 것을 검토.

### 의존성

**CDN 없이 번들 가능한 것으로.** 앱은 폐쇄망에서 exe 하나로 돌아야 한다
(`tools/build-exe.mjs`).
