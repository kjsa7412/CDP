# 제1부 — 왜 지금 바꿔야 하는가

## 1. 이미 일어난 변화 — 문서의 최종 소비자가 바뀌었다

구체적인 장면에서 시작하자.

A10 연계 작업이 끝나면 문서 하나가 팀에 전달된다. AI로 정리했으니 충실하다 — 인터페이스 정의, 호출 방법과 인증, 검증 방법과 테스트 케이스, 구현 방식과 내부 구조, 장애 시 재처리 절차까지 한 문서에 300여 줄이다. 빠진 것은 없다.

이 문서를 받은 개발자는 무엇을 하는가. **읽지 않는다.** 통째로 작업 세션에 밀어넣는다.

```
> 이 문서 첨부할게. 참고해서 작업해줘
```

이것은 게으름이 아니다. **합리적인 선택이다.** 300줄 중 자기에게 걸리는 부분이 어디인지 찾는 것보다, AI에게 맡기는 편이 빠르고 정확하다. 목차는 작성자의 논리로 짜여 있고, 개발자가 아는 것은 자기가 지금 하려는 작업뿐이다.

여기서 확인해야 할 사실은 하나다.

> **문서의 최종 소비자가 사람에서 AI 세션으로 바뀌었다.**
> 누가 결정한 것도, 공지된 것도 아니다. 이미 그렇게 되어 있다.

예전 흐름과 지금 흐름을 나란히 놓으면 분명해진다.

```
[예전]  작성자 → 문서 → 사람이 읽고 자기 것을 골라냄 → 작업
[지금]  작성자 → 문서 → AI 세션에 투입 → AI가 골라냄 → 작업
```

가운데 **"사람이 읽고 골라내는" 단계가 사라졌다.** 그 단계는 이제 AI가 한다.

---

## 2. 그런데 산출물은 여전히 사람용이다

소비자가 바뀌었는데 만드는 형식은 그대로다. 지금 업무 문서는 이런 형태로 만들어진다.

| 사람을 위한 설계 | 그 이유 |
|---|---|
| 서술형 산문 | 사람은 문장으로 읽을 때 이해가 빠르다 |
| 작성자의 논리 순서로 짠 목차 | 사람은 처음부터 순서대로 읽는다 |
| 굵게·밑줄로 표시한 강조 | 사람은 시각적 무게로 중요도를 안다 |
| 배경 설명과 맥락 문단 | 사람은 이유를 알아야 납득한다 |

전부 **사람이 읽을 때는 최적인 선택**이다. 잘못 쓴 문서가 아니다.

문제는 이 형식이 실제 소비자인 AI에게 아무 도움이 되지 않는다는 데 있다. AI에게 이 문서는 구조 없는 300줄이고, "누가 이걸 봐야 하는가"를 판정할 근거가 어디에도 없다. 굵은 글씨는 토큰으로는 그냥 글자다.

> **만드는 형식(사람용)과 실제 소비자(AI) 사이에 불일치가 생겼다.**
> 이것이 이 문서가 다루는 문제다.

---

## 3. 불일치가 만드는 세 가지 낭비

이 불일치는 다음 세 가지로 나타난다. 셋 다 **누구의 잘못도 아니다** — 형식과 소비자가 어긋나서 생기는 구조적 결과다.

### (1) 선별 근거가 없다

AI가 "이 문서에서 당신에게 걸리는 부분"을 골라내려면 판정 기준이 필요하다. 그런데 문서에는 그런 표시가 없다. AI는 산문의 의미를 해석해 추정할 수밖에 없고, 추정은 틀릴 수 있다.

A10 문서의 214번째 줄 — *"연계 실패 시 A10이 5분 주기로 자동 재시도, 수신측 중복 방지 키 필수"* — 을 보자. 작성자는 이것이 수신측이 구현해야 할 항목이라는 판단을 갖고 썼다. **문서에는 사실만 남고 그 판단은 담기지 않았다.** 재시도 주기·타임아웃·로그 위치와 시각적으로 동일한 무게의 한 줄이 됐을 뿐이다. 산문에는 "이건 남이 해야 할 일"을 형식적으로 표시할 자리가 없다.

### (2) 매번 전량을 투입한다

선별 근거가 없으니 안전한 선택은 전부 넣는 것이다. 300줄이 컨텍스트를 차지하고, 관련 없는 280줄이 주의를 분산시킨다. 그리고 이 일이 **문서를 받은 모든 개발자의 모든 세션에서 반복된다.** 작성은 1회, 같은 해석이 4회, 6회, 세션 수만큼.

### (3) 판정이 세션마다 달라진다

같은 문서를 같은 질문으로 넣어도 세션마다 결과가 조금씩 다르다. 사람이 읽을 때는 문서가 기준점이었지만, 지금은 **매번 새로 하는 해석이 기준점**이다. 재현되지 않는 판정 위에서 작업이 진행된다.

214번째 줄의 "수신측"이 누구인지 문서는 말하지 않는다. 연계 담당의 세션은 "A10이 키를 붙여 보낸다"로, 연구관리 담당의 세션은 "우리가 구현한다"로 읽는다. 둘 다 성실히 해석했고, 서로 다르게 읽었다는 사실은 아무도 모른다.

---

## 4. "잘 쓰자"로는 풀리지 않는다

가장 먼저 떠오르는 해법은 "공유할 만한 것만, 명확하게 쓰자"이다. 이건 작동하지 않는다.

**무엇이 사소한지는 작성자가 판단할 수 없기 때문이다.** 무엇이 사소한지는 수신자마다 다르다.

앞의 A10 문서에서, 인터페이스 정의 23개 항목 중 하나를 보자.

> `planStatus` 필드가 추가됐다.
> — 화면 담당에겐 노이즈다.
> — 야간 집계 배치 담당에겐 집계 쿼리가 깨지는 사건이다.
> — 연계 매핑 담당에겐 매핑 테이블 수정 대상이다.

작성자에게 "덜 쓰라"고 요구하면 누군가에게 치명적인 항목이 지워진다. 다 쓰라고 하면 다시 300줄이다. **작성 단계에서 원리적으로 결정할 수 없는 문제다.**

그러므로 방향을 바꿔야 한다.

> **작성자가 고르게 하지 말고, 받는 쪽이 고를 수 있게 표시하자.**
> 필터를 생성 시점이 아니라 소비 시점에 둔다.

그리고 그 표시는 사람이 읽는 강조가 아니라 **기계가 판정할 수 있는 형식**이어야 한다. 소비자가 AI이기 때문이다.

## 5. 웹은 같은 전환을 이미 겪고 있다

### 5.1 웹에서 벌어진 일

웹사이트는 오랫동안 **사람의 눈과 손을 위해** 만들어졌다. 화면이 보기 좋고, 클릭하기 편하면 잘 만든 것이었다. 소비자가 사람이었으니 옳은 설계였다.

그런데 소비자에 AI 에이전트가 들어왔다. 그리고 그 비중이 빠르게 커졌다. 초기 에이전트는 사람을 흉내낼 수밖에 없었다 — 브라우저를 띄우고, 화면을 캡처하고, 픽셀에서 버튼을 찾아 좌표를 계산해 클릭했다. 느리고, 비싸고, 취약했다. 실제로 스크린샷 기반 에이전트가 달력 그리드의 24px 셀 하나를 정확히 집지 못해 단순한 날짜 선택에 몇 분씩 반복 시도하는 사례가 보고됐다.

서버 안에는 이미 구조화된 데이터가 있었다. 좌석 목록, 가격, 잔여 수량 — 전부 정형 데이터다. 그것이 사람용 화면으로 렌더링되는 순간 구조가 사라지고 **그림**이 됐고, AI는 그 그림에서 구조를 역추적했다. 있던 정보를 없앤 뒤 다시 복원한 셈이다.

### 5.2 웹의 대응 — 만드는 방식을 바꿨다

핵심은 여기다. 웹은 **에이전트를 더 똑똑하게 만드는 쪽이 아니라, 사이트를 만드는 방식을 바꾸는 쪽으로** 움직였다.

- 시맨틱 마크업과 ARIA 태그로 페이지의 의미 구조를 명시한다
- 에이전트는 화면 대신 접근성 트리(스크린리더가 20년간 써온 구조)를 읽는다
- Playwright MCP는 스크린샷 대신 접근성 스냅샷을 제공하고, ChatGPT Atlas는 ARIA로 페이지를 해석한다고 명시한다
- `llms.txt`, 구조화 메타데이터, 에이전트용 API, MCP 서버 — 기계용 통로를 따로 낸다

**웹 개발자는 이제 "AI가 읽을 수 있게 만들 것"을 요구사항으로 받는다.** 몇 년 전에는 없던 항목이다.

그리고 그 차이는 실측된다. CHI 2026에 발표된 UC버클리·미시간대 연구에서, 구조가 온전한 페이지의 태스크 성공률은 78%였고 구조가 망가진 페이지에서는 42%로 떨어졌다. 같은 정보인데 **전달 형태만으로 성능이 반토막 난다.**

중요한 것은 사람용 화면을 없애지 않았다는 점이다. **통로를 하나 더 낸 것이다.**

### 5.3 업무 정보는 아직 그 전환 전에 있다

두 영역은 같은 구조를 그대로 반복하고 있다.

| | 웹 · 예약 사이트 | 업무 · A10 연계 |
|---|---|---|
| **소비자 변화** | 사람의 눈 → AI 에이전트 비중 급증 | 사람의 판독 → AI 세션이 실질 소비자 |
| **원본** | 서버의 좌석·가격·잔여 수량 (정형) | 연계 개발자가 쥔 구조 — 무엇을·왜·누가 |
| **사람용 렌더링** | HTML 화면 | 「A10 연계 개발 완료 정리」 300여 줄 |
| **AI의 소비 방식** | 스크린샷 → 픽셀에서 버튼 탐색 | 문서 통째로 투입 → AI가 선별 |
| **잃는 것** | 구조를 버리고 다시 복원 | 판단을 버리고 다시 추정 |
| **실패 양상** | 24px 셀 하나를 못 집는다 | 214번째 줄의 중복 방지 키를 놓친다 |
| **대응** | 시맨틱 마크업 · ARIA · llms.txt | **← 비어 있음. 오늘의 제안** |

> **웹은 만드는 방식을 바꿨다. 업무 산출물은 아직 바꾸지 않았다.**

그래서 이 프로토콜을 한 줄로 말하면 이렇다.

> **업무 정보의 `llms.txt`.**

대면 소통과 문서를 없애자는 것이 아니다. 웹이 사람용 화면을 남겨둔 채 기계용 통로를 낸 것처럼, 업무 산출물에도 **AI가 바로 읽을 수 있는 통로를 하나 더 내자**는 것이다.

```
[지금]  사람 → 사람용 문서 → AI가 산문에서 구조를 추정 → 반영
[제안]  사람 → 구조화된 지식 단위 → AI가 직접 로드 → 반영
```

## 6. 설계 명제

이 프로토콜은 네 가지 명제 위에 서 있다.

**명제 1 — 문서가 아니라 주소가 필요하다.**
잘 쓴 문서를 만드는 것이 목표가 아니다. 각 지식이 **어디에 붙는 것인지** 기계가 판정할 수 있게 만드는 것이 목표다. 그 주소를 이 문서에서는 **좌표(coordinate)** 라고 부른다. 웹의 ARIA 태그에 해당하는 것이다.

**명제 2 — 필터는 소비 시점에 둔다.**
작성자에게 취사선택을 요구하지 않는다. 좌표만 정확하면, 받는 쪽이 자기 것만 가져간다.

**명제 3 — 인프라가 아니라 규약으로 푼다.**
서버·큐·워커·전용 웹앱을 만들지 않는다. Git 저장소 하나와 규약, 그리고 얇은 로더만으로 성립하게 한다. 무거운 시스템은 도입되지 않고, 도입되지 않은 시스템의 효과는 0이다.

**명제 4 — 관계는 유사도로 대체할 수 없다.** *(v1.1 신설)*
"이 문서가 저 문서를 대체했다", "이 지식은 저 테이블에 걸린다" 같은 **방향과 종류를 가진 관계**는, "얼마나 닮았는가"라는 하나의 연속값으로 표현되지 않는다. 검색을 유사도에 맡기는 순간 이 관계들이 전부 "닮음의 정도"로 납작해진다. 그래서 이 프로토콜은 관계를 **명시적으로 적는다.** 상세한 근거는 제3부에 둔다.

# 제2부 — 프로토콜 설계

## 7. 전체 구성

프로토콜은 네 부분으로 이루어진다.

| # | 구성요소 | 역할 |
|---|---|---|
| 1 | **지식 단위** (Knowledge Unit) | 공유되는 최소 단위. 프론트매터 + 본문 + 첨부로 된 MD 파일 |
| 2 | **좌표계와 통제 어휘** | 지식이 어디에 붙는지 나타내는 주소 체계. **프로토콜의 심장** |
| 3 | **저장소** | Git 저장소 하나. 지식 단위 + 인덱스 + 어휘 + 첨부 |
| 4 | **인터페이스** | 생성(skill) · 검증(hook) · 소비(skill / MCP) |

```
작성 세션 ──skill──> 지식 단위 ──hook 검증──> [Git 저장소] ──skill/MCP──> 소비 세션
                        │                         │
                    좌표 부여                  INDEX.md
                        └────── _vocab.md 대조 ────┘
```

## 8. 지식 단위

### 8.1 형식

파일 하나에 독자가 둘이다. **프론트매터는 기계가 읽고, 본문은 사람과 AI가 읽는다.**

```yaml
---
id: 2026-0819-a10-adapter
title: A10 연계 어댑터 인터페이스 개편 — 계획서 상태 동기화 추가
date: 2026-08-19
author: kjsa
status: 확정
touches:
  - table:tb_research_plan
  - api:/adapter/a10/plan-sync
  - module:acl-adapter
  - domain:연구관리
supersedes: 2026-0710-a10-adapter-v1
attachments:
  - assets/2026-0819-a10-adapter/interface-spec.md
tags: [연계, 인터페이스]
---

## 무엇이 바뀌었나
## 왜
## 누구에게 영향
## 후속 조치
```

### 8.2 필드 정의

| 필드 | 필수 | 형식 | 역할 |
|---|:--:|---|---|
| `id` | O | `YYYY-MMDD-slug` | 참조 키. 파일명과 일치 |
| `title` | O | 한 줄 | 인덱스 표시 |
| `date` | O | `YYYY-MM-DD` | 정렬·신선도 |
| `author` | O | 이름 | 문의처 |
| `status` | O | `확정`/`제안`/`미결` | `미결` 필터 = 결정 대기 목록 |
| `touches` | O | `타입:값` 배열 | **검색·라우팅의 전부** |
| `supersedes` | | 이전 `id` (또는 §9.8 객체 형식) | 정정된 문서는 검색에서 내림 |
| `attachments` | | 경로 배열 | 상세 문서 위치 |
| `tags` | | 자유 문자열 | 보조 검색 |

### 8.3 필드를 9개로 제한한 이유

필드는 늘릴수록 손해가 복리로 붙는다.

- **작성 마찰** — 필드마다 작성자가 멈춰 생각한다. 마찰은 곧 커버리지 하락이다
- **미기입 필드** — 애매한 필드는 반드시 빈다. 그리고 **빈 필드는 없는 필드보다 나쁘다.** 검색이 "비었으니 해당 없음"으로 잘못 판단해 조용히 틀린 답을 준다

그래서 두 필드를 의도적으로 배제했다.

**`impact`를 필드로 두지 않는다.** 영향은 수신자마다 달라 구조화가 어렵다. 배열로 강제하면 "프론트: 변경 없음" 같은 무의미한 줄만 쌓인다. 본문 산문 한 단락이 더 정확하다.

~~**`decisions`를 필드로 두지 않는다.** `status: 미결` 하나로 충분하다.~~

> **정정 (정정_판정모델_v2 §2).** 이 판단은 **문서 종류를 하나만 가정한 것**이었다.
> 지식공유문서는 작업의 **완료**에서 발생하는 문서이고, 결정 대기는 아젠다다.
> 관리 문서에 `위험및이슈관리대장` 이 들어오면서 갈 자리가 생겼다 —
> `status: 미결` 을 없애고 이슈 대장으로 옮긴다.

> **필드 추가 판단 기준** — 새 필드는 "있으면 좋겠다"가 아니라 **"없어서 실제로 오적용이 났다"** 로 추가한다. §9.8과 §14.2의 확장 항목이 전부 이 기준을 따른다.

### 8.4 본문 4섹션

```markdown
## 무엇이 바뀌었나     사실. 짧게.
## 왜                  제약과 근거. 이 섹션이 문서의 수명을 결정한다.
## 누구에게 영향        좌표별로 서술. 수신자가 자기 항목을 찾는 곳.
## 후속 조치           남은 일, 결정 대기 사항, 담당.
```

**"왜" 섹션이 가장 중요하다.** 6개월 뒤 이 결정을 뒤집으려는 사람이 필요로 하는 것은 무엇이 바뀌었는지가 아니라 **어떤 제약 때문에 그렇게 했는지**다. 이것이 빠진 문서는 반년이면 쓸모를 잃는다.

**본문은 일부러 구조화하지 않는다.** 프론트매터는 기계 판정용이므로 엄격히 정규화하고, 본문은 사람의 판단 근거이므로 산문으로 둔다. "왜"에 담기는 제약과 트레이드오프는 필드로 쪼개는 순간 죽는다. 이 **메타데이터/본문 분리**가 이 설계의 중심축이다.

### 8.5 첨부 문서

인터페이스 명세처럼 상세 문서가 별도로 존재하는 작업이 있다. 이때 **지식 단위에는 요약만 담고 상세는 첨부로 분리한다.**

```
knowledge/2026-0819-a10-adapter.md               요약 + 프론트매터
knowledge/assets/2026-0819-a10-adapter/
    interface-spec.md                            상세 원문
```

| 대상 | 처리 |
|---|---|
| 텍스트 문서 (MD·명세·스키마·샘플) | `assets/`에 **복사** |
| 대용량·바이너리 (도면·엑셀·영상) | 원본 경로만 기록 |

**왜 링크가 아니라 복사인가** — 사내 문서관리 툴(위키·그룹웨어 문서함·공유 드라이브)에 원본을 두고 링크만 거는 방식은 **반드시 썩는다.** 여섯 가지 방식으로 썩는다.

| 부패 유형 | 증상 |
|---|---|
| **접근권 파편화** | 링크는 열리는데 "권한 없음". 요청 → 승인 왕복에 하루. 외부 인력·타 부서는 아예 막힘 |
| **링크 썩음** | 페이지 이동, 스페이스 개편, 폴더 재편성으로 URL이 바뀐다. 리다이렉트를 남기는 툴은 드물다 |
| **버전 불명** | 문서관리 툴의 문서는 그 자리에서 수정된다. **지식 단위가 참조한 시점의 내용이 아니다.** 어느 버전을 보고 쓴 결정인지 알 방법이 없다 |
| **기계 판독 불가** | 인증이 필요하고, 저장 포맷이 자체 형식이며, 첨부 안에 첨부가 들어 있다. 결국 사람이 열어서 복사해 붙인다 |
| **툴 자체의 교체** | 그룹웨어·위키는 3~5년 주기로 바뀐다. 마이그레이션에서 첨부는 대개 유실되거나 깨진 링크로 남는다 |
| **검색 분리** | 지식 레포 검색과 문서 툴 검색이 따로 논다. 한쪽만 본 사람은 있는 것을 없다고 판단한다 |

마지막 두 가지가 특히 위험하다. §9.6의 **조용한 실패**와 같은 성질이기 때문이다 — 링크가 죽었다는 사실도, 문서 툴에 답이 있다는 사실도 아무도 통보받지 못한다.

반면 텍스트를 `assets/`에 복사해 넣으면 이 여섯 가지가 한 번에 사라진다.

- 커밋 시점의 내용이 **그대로 고정**된다. 나중에 원본이 수정돼도 이 결정의 근거는 남는다
- clone 하나로 자족한다. 권한은 지식 레포 하나만 관리하면 된다
- Git diff로 상세 문서의 변경까지 추적된다
- AI가 인증 없이 즉시 읽는다. 이것이 프로토콜의 목적 그 자체다

**예외 — 원본을 문서 툴에 둘 수밖에 없는 경우**

대용량·바이너리(도면·영상)이거나, 결재가 완료된 법적 원본(계약서·승인 문서)은 문서 툴이 정본이어야 한다. 이때도 **링크만 달랑 남기지 않는다.** 반드시 세 가지를 함께 적는다.

```markdown
- 원본: 그룹웨어 문서함 > 연구관리 > A10 연계 협약서 (2026-08-12 결재완료)
  링크: https://...
  요지: 상태 동기화 주기는 5분, SLA 99.5%, 장애 시 재처리는 A10 측 책임
```

**링크는 썩지만 제목·시점·요지는 썩지 않는다.** 링크가 죽어도 사람이 원본을 찾아낼 수 있고, AI는 요지만으로 대부분의 판단을 끝낼 수 있다.

**요약의 기준** — *"이게 나와 상관있는가"를 판단할 수 있을 만큼*만 쓴다. 상세를 요약에 밀어 넣으면 아래 3계층이 무너지고, 결국 모두가 모든 것을 읽게 된다.

```
INDEX.md (지형 파악) → 지식 단위 (관련성 판단) → attachments (구현 세부)
```

대부분의 수신자는 2계층에서 멈춘다. 3계층까지 가는 것은 실제로 그 인터페이스를 구현하는 한두 사람뿐이다.

## 9. 좌표계와 통제 어휘 ★

§5에서 본 대로, 웹이 AI에게 구조를 넘겨준 수단은 ARIA 태그였다. **좌표는 업무 지식에서 그 자리를 맡는다.**

프로토콜에서 **유일하게 타협할 수 없는 부분**이다. 나머지가 다소 엉성해도 좌표만 정확하면 시스템은 굴러가고, 좌표가 무너지면 나머지가 완벽해도 아무것도 찾을 수 없다.

### 9.1 좌표란 무엇인가

좌표는 **시스템의 실제 구조에 붙어 있는 안정적 식별자**다. 형식은 `타입:값`으로 고정한다.

| 타입 | 예시 | 대상 |
|---|---|---|
| `table` | `table:tb_research_plan` | DB 테이블 |
| `api` | `api:/adapter/a10/plan-sync` | 엔드포인트 |
| `screen` | `screen:계획서변경` | 화면 |
| `module` | `module:acl-adapter` | 코드 모듈·패키지 |
| `domain` | `domain:연구관리` | 업무 도메인 |

타입은 프로젝트 사정에 따라 늘릴 수 있다(`batch:`, `job:`, `policy:` 등). 다만 **늘리기 전에 기존 타입으로 표현할 수 없는지 먼저 확인한다.** 타입이 많아지면 작성자가 무엇을 골라야 할지 몰라 좌표를 아예 안 붙인다.

### 9.2 왜 키워드가 아니라 좌표인가

키워드 검색은 **표현이 갈리면 조용히 실패한다.**

> 작성자는 "승인 단계"라고 썼다.
> 수신자는 "결재 프로세스"라고 검색한다.
> 결과: 0건. 그리고 수신자는 *문서가 없다*고 결론 내린다.

사람의 표현은 문서마다 다르다. 그러나 **시스템의 구조는 다르지 않다.** `tb_research_plan`은 누가 쓰든 같은 이름이고, 그 테이블이 사라지기 전까지 변하지 않는다.

좌표는 두 가지를 동시에 해낸다.

- **찾는 쪽**: "내 모듈에 걸린 지식"을 기계적으로 특정할 수 있다
- **받는 쪽**: "이것이 나와 상관있는가"를 판단할 유일한 객관적 근거가 된다

제1부에서 **필터를 소비 시점에 둔다**고 했다. 그 필터의 실체가 바로 좌표다. 좌표가 없으면 소비 시점 필터링이 불가능하고, 프로토콜은 그냥 "문서를 잘 쓰자"로 되돌아간다.

> **의미 검색(임베딩)으로 이 문제를 풀 수 있지 않은가** — 표현 분열은 완화되지만 사라지지 않고, 대신 더 나쁜 실패 양상이 들어온다. 제3부 §13에서 다룬다.

### 9.3 좌표의 입도

너무 세밀해도, 너무 거칠어도 실패한다.

| 입도 | 예 | 문제 |
|---|---|---|
| 너무 거칢 | `domain:연구관리` 만 | 전 팀에 걸린다. 알림 피로 → 무시 |
| 적정 | `table:tb_research_plan` | 관련자만 걸린다 |
| 너무 세밀 | `column:tb_research_plan.status` | 작성 부담 급증, 매칭 누락 발생 |

**기준: 담당이 갈리는 경계까지만 쪼갠다.** 테이블은 담당이 갈리므로 좌표가 되고, 컬럼은 대개 갈리지 않으므로 되지 않는다.

한 지식 단위에는 **좌표를 3~6개** 붙이는 것이 보통이다. 1개면 대개 놓친 게 있고, 10개가 넘으면 작업을 쪼개야 한다는 신호다.

### 9.4 `_vocab.md` — 통제 어휘

좌표를 자유 태그로 두면 붕괴는 **3주면** 온다. 같은 대상을 두고 이런 것들이 공존하기 시작한다.

```
tb_research_plan / research_plan / 연구계획테이블 / TB_RESEARCH_PLAN / 계획서테이블
```

이 순간 검색은 사실상 죽는다.

`_vocab.md`는 도서관의 **전거 파일(authority file)** 과 같은 개념이다. 같은 대상을 가리키는 여러 표기 중 **정본을 하나 정하고, 나머지를 거기에 연결한다.**

```markdown
# 좌표 어휘

## table
- `table:tb_research_plan` — 연구계획 마스터
  aliases: 연구계획테이블, 계획서테이블, TB_RESEARCH_PLAN, research_plan
- `table:tb_approval_line` — 결재선
  aliases: 결재선테이블, 승인라인
- `table:tb_plan_history` — 계획서 변경 이력
  deprecated: 2026-06-01 → table:tb_research_plan_hist 로 통합

## api
- `api:/adapter/a10/plan-sync` — A10 계획서 상태 동기화
  aliases: 계획서동기화, plan-sync

## screen
- `screen:계획서변경` — 연구관리 > 계획서변경
  aliases: 계획변경화면, 계획서 변경 화면

## module
- `module:acl-adapter` — A10 연계 Anti-Corruption Layer
  aliases: ACL, 연계어댑터

## domain
- `domain:연구관리`
  aliases: 연구, 과제관리
```

**`aliases`가 이 파일의 진짜 핵심이다.** 정본 목록만 있으면 작성자만 편해진다. aliases가 있어야 **수신자가 자연어로 물어도 검색이 걸린다.**

> **`_vocab.md`가 하는 일을 DB 용어로 말하면** — "이 대상의 정식 이름이 무엇인가"는 문서에 딸린 정보가 아니라 대상 자체에 딸린 정보다. 그것을 문서마다 자유롭게 적게 두면 표기가 갈라지고, 갈라진 뒤에는 되돌릴 수 없다. `_vocab.md`는 그 정보를 **마스터 표 하나로 분리**한 것이다. 관계형 설계에서 종속된 속성을 별도 테이블로 떼어내는 것과 같은 동작이며, 이 프로토콜에서 정규화 수준이 가장 높은 부분이다.

### 9.5 대조 — 프로토콜의 핵심 연산

**대조(reconciliation)란 입력이 무엇이든 정본 하나로 수렴시키는 정규화 연산이다.** 대조는 세 지점에서, 서로 다른 목적으로 일어난다.

#### (1) 쓰기 시점 — 검증

작성된 지식 단위의 `touches` 값이 정본인지 확인한다.

```
touches: table:tb_plan
  → _vocab.md 미등재
  → 커밋 거부. 정본을 쓰거나 어휘에 등재하라.

touches: 연구계획테이블
  → alias 일치
  → table:tb_research_plan 으로 치환 제안
```

#### (2) 읽기 시점 — 질의 정규화

수신자가 자연어로 묻는다.

```
"연구계획 테이블 관련해서 최근 바뀐 거 있나?"
  → alias 테이블 조회
  → table:tb_research_plan 으로 정규화
  → INDEX.md 에서 해당 좌표 매칭
```

**사람이 정본을 외울 필요가 없어진다.** aliases를 두는 실질적 이유가 여기 있다.

#### (3) 작성 보조 — 좌표 제안

작성 skill이 `git diff`에서 발견한 이름들을 어휘에 대조해 좌표 후보를 제시한다.

```
diff 에서 발견: TB_RESEARCH_PLAN, AclPlanAdapter.java
  → 대조 → table:tb_research_plan, module:acl-adapter 제안
```

세 지점 모두 **같은 연산**이다. 방향만 다르다.

```
       [자유로운 표현]
   ↙         ↓         ↘
 작성      질의       코드
   ↘         ↓         ↙
      대조(_vocab.md)
            ↓
        [정본 좌표]
```

### 9.6 왜 반드시 커밋 시점에 막는가 — 조용한 실패

좌표 오류의 무서운 점은 **에러를 내지 않는다**는 것이다.

```
잘못된 좌표가 붙은 문서
  → 검색에 안 잡힘
  → 아무도 오류를 보지 못함
  → 수신자는 "관련 문서가 없다"고 결론
  → 잘못된 전제로 작업
  → 문제가 터진 뒤에도 원인 추적 불가
```

누락을 발견할 수단 자체가 없다. 사람들은 서서히 "이 저장소엔 별거 없다"고 믿게 되고, 그 시점에 시스템은 죽는다.

**반면 커밋 시점에는 작성자가 맥락을 쥐고 있어 1초면 고친다.** 사후 청소 비용과 비교가 되지 않는다.

> **조용한 실패는 좌표 오타에서만 오지 않는다.** 검색 방식 자체가 같은 성질의 실패를 만들 수 있다. §13.3에서 다룬다.

### 9.7 어휘 구축과 운영

**초기 구축 (반나절)**

| 타입 | 방법 |
|---|---|
| `table` | 스키마 덤프에서 자동 추출 |
| `api` | 라우팅 정의에서 자동 추출 |
| `module` | 패키지 구조에서 자동 추출 |
| `screen` | 수동 (화면 목록 문서) |
| `domain` | 수동 (10~20개면 충분) |

**운영 원칙**

- **추가 비용은 한 줄이어야 한다.** 새 좌표가 필요하면 `_vocab.md`에 한 줄 추가하고 계속 쓴다. 승인 절차를 두면 사람들은 우회한다
- **삭제하지 않는다.** 테이블이 없어져도 좌표는 남긴다. 과거 지식 단위가 그 좌표를 참조하고 있기 때문이다. `deprecated` 로 표시하고 후속 좌표를 가리킨다
- **alias는 발견될 때마다 추가한다.** 검색이 안 걸리는 사례가 나오면, 그때 쓴 표현을 alias에 넣는다. 어휘는 이렇게 쓰면서 자란다

> **"삭제하지 않는다"가 DB와 다른 지점이다.** 관계형 DB는 현재 상태 하나를 유지하므로 없어진 값을 지운다. 지식 저장소는 append-only이고 과거 문서가 그 좌표를 참조하고 있으므로, 지우면 과거 문서가 고아가 된다. 그래서 **삭제 대신 `deprecated` 표시**로 간다. 이 차이는 §12의 유효성 모델에서 다시 나온다.

**안티패턴**

| 안티패턴 | 결과 |
|---|---|
| 자유 태그 허용 | 3주 뒤 표기 분열 → 검색 사망 |
| alias 관리 안 함 | 작성자만 편하고 수신자는 못 찾음 |
| 컬럼 단위 좌표 | 작성 부담 급증 → 좌표 자체를 안 붙임 |
| 좌표 추가에 승인 절차 | 우회 → 미등재 좌표 사용 |
| 삭제된 좌표를 어휘에서 제거 | 과거 문서가 고아가 됨 |

### 9.8 좌표 단위 무효화 — 지금은 넣지 않는다 *(v1.1 신설)*

**문제 인식**

`supersedes`는 **문서 전체를 통째로 덮는다.** 그런데 실제로는 문서의 일부만 무효화되는 경우가 흔하다.

```
D1 (7월)  touches: table:tb_research_plan, api:/adapter/a10/plan-sync
          → 테이블 스키마 변경 + API 규격 정의

D2 (8월)  touches: table:tb_research_plan
          → 테이블 부분만 다시 바뀜. API 규격은 그대로 유효
```

D2에 `supersedes: D1`을 붙이면 **여전히 유효한 API 규격까지 검색에서 내려간다.** 붙이지 않으면 낡은 테이블 정보가 계속 올라온다. 둘 다 틀렸다.

**해결 형식 (도입 시)**

```yaml
# 기존 — 문서 전체 대체. 하위 호환 유지
supersedes: 2026-0710-a10-adapter-v1

# 확장 — 좌표 한정 대체
supersedes:
  - id: 2026-0710-a10-adapter-v1
    scope: [table:tb_research_plan]      # 이 좌표에 대해서만 무효화
```

`scope`가 없으면 문서 전체 대체(기존 동작), 있으면 해당 좌표에 한해서만 무효화한다. 로드 시 필터는 **좌표별로** 판정한다.

```
질의 좌표: table:tb_research_plan  → D1 제외 (D2가 이 좌표를 덮음)
질의 좌표: api:/adapter/a10/plan-sync → D1 포함 (덮이지 않음)
```

**그런데 v1.1에서는 도입하지 않는다.**

§8.3의 필드 추가 기준에 따른다. 이 확장은 프론트매터를 객체 배열로 만들어 작성 마찰을 확실히 올리고, `bin/ctx`의 검증·인덱싱 로직도 복잡해진다. **효과는 아직 추정이고 비용은 확실하다.**

**도입 신호 — 아래 중 하나가 관측되면 넣는다.**

| 신호 | 확인 방법 |
|---|---|
| 오적용 사례의 원인이 "문서 전체가 정정돼서 유효한 부분까지 사라짐"으로 분류됨 | §17 오적용 로그 |
| 작성자가 `supersedes`를 붙일지 말지 매번 망설인다는 피드백 | 2주 운용 회고 |
| 한 문서가 좌표 6개 이상을 갖고, 그중 일부만 자주 갱신됨 | `ctx index` 통계 |

**그 전까지의 대응** — 좌표가 많고 일부만 바뀔 것 같은 작업은 **처음부터 지식 단위를 쪼갠다.** §9.3의 "좌표 10개가 넘으면 작업을 쪼개야 한다는 신호"가 여기서도 적용된다. 문서를 잘게 쓰면 문서 단위 `supersedes`만으로 충분하다.

## 10. 저장소

### 10.1 구조

```
knowledge/
  2026-0819-a10-adapter.md
  2026-0817-연심회-상태값추가.md
  assets/
    2026-0819-a10-adapter/
      interface-spec.md
INDEX.md          자동 생성 · 전체 프론트매터 집계
_vocab.md         좌표 통제 어휘
TEMPLATE.md       작성 템플릿
CLAUDE.md         소비 규약
.githooks/pre-commit
bin/ctx
```

### 10.2 왜 Git인가

- 이력·diff·롤백·권한·분산 사본을 **공짜로** 얻는다. 직접 만들면 전부 개발 항목이다
- 개발자는 이미 매일 쓴다. 새 습관이 0이다
- 서버가 필요 없다. clone 한 사람마다 완전한 사본을 갖는다
- **감수하는 것**: 비개발 직군의 진입 장벽

Git이 공짜로 주는 것 중 하나를 §12에서 쓴다 — **커밋 시각**이다. `date`(결정이 내려진 날)와 커밋 시각(기록된 날)이 분리되어 있어, 별도 필드 없이 두 종류의 시간을 확보한다.

### 10.3 왜 평평한 구조인가

**(1) 지식은 여러 축에 동시에 걸린다.** "A10 어댑터 개편"은 `연계` 인가 `연구관리` 인가? 폴더는 축을 하나만 고르라고 강요하고, 어디에 넣든 반대편에서 찾는 사람은 못 찾는다. `touches`는 한 문서가 여러 좌표에 동시에 속할 수 있다.

**(2) 분류 논쟁이 작성 마찰이 된다.** 폴더 트리가 있으면 작성자는 매번 "이건 어디 넣지"에서 멈춘다.

**(3) 분류 체계는 반드시 바뀌고, 바뀌면 링크가 깨진다.** 평평한 구조에서는 옮길 것이 없다. 분류는 프론트매터에 있고, 프론트매터는 파일을 움직이지 않고 고칠 수 있다.

**(4) 규모 한계는 인지한다.** 수천 건이 되면 재고할 여지가 있다. 다만 팀 규모(연 수백 건)에서는 평평한 구조가 확실히 낫다. **먼저 한계에 닿는 것은 폴더 구조가 아니라 `INDEX.md`의 크기다.** §10.5에서 다룬다.

### 10.4 날짜 접두 파일명

`2026-0819-a10-adapter.md`

- **파일명 정렬 = 시간순.** 도구 없이 되는 정렬이 가장 튼튼하다
- **`id`와 파일명이 일치한다.** `supersedes: 2026-0710-a10-adapter-v1`을 보면 어느 파일인지 즉시 안다
- **제목만 쓰면 충돌한다.** "인터페이스 변경"은 1년에 세 번 나온다
- **목록만 봐도 시간 감각이 실린다.** 신선도의 가장 값싼 근사치다

### 10.5 `INDEX.md`와 확장 한계 *(v1.1 보강)*

전체 지식 단위의 프론트매터만 모은 표. **자동 생성한다.**

```markdown
| id | date | title | status | touches |
|----|------|-------|--------|---------|
| 2026-0819-a10-adapter | 2026-08-19 | A10 연계 어댑터... | 확정 | table:tb_research_plan, api:/adapter/a10/plan-sync, ... |
```

**왜 필요한가** — 저장소를 통째로 읽히면 컨텍스트를 다 태우고, 관련 없는 문서에 주의가 분산되어 정확도가 떨어진다. 인덱스는 **2단계 읽기**를 가능하게 한다. 후보를 좁히고 → 해당 문서만 읽는다. 책의 목차와 같은 원리이고, 문서가 늘수록 이득이 커진다.

**왜 손으로 관리하면 안 되는가** — 반드시 어긋나기 때문이다. 그리고 **어긋난 인덱스는 없는 것보다 나쁘다.** AI가 인덱스를 믿고 존재하는 문서를 없다고 판단한다.

#### 확장 한계와 대응

인덱스 한 줄은 대략 60~100 토큰이다. 규모별로 계산하면 이렇다.

| 문서 수 | INDEX.md 대략 크기 | 상태 |
|---|---|---|
| ~100건 | 6~10K 토큰 | 통째로 읽혀도 무방 |
| ~300건 | 20~30K 토큰 | 부담이 느껴지기 시작 |
| 500건+ | 40K 토큰+ | **통째 로드 불가** |

500건은 연 200건 페이스면 2년 반이다. 먼 미래가 아니다.

**대응은 단계적으로 한다. 미리 다 만들지 않는다.**

**1단계 (~200건) — 통째 로드.** 지금 설계 그대로. `CLAUDE.md`가 "INDEX.md를 먼저 읽어라"로 충분하다.

**2단계 (200~500건) — 좌표별 역인덱스 분할.** `ctx index`가 파일을 하나 더 생성한다.

```
INDEX.md              전체 표 (사람이 훑어보는 용도)
INDEX-by-coord.md     좌표 → id 목록 (기계가 읽는 용도)
```

```markdown
## table:tb_research_plan
2026-0819-a10-adapter, 2026-0731-plan-status, 2026-0612-plan-schema

## api:/adapter/a10/plan-sync
2026-0819-a10-adapter, 2026-0710-a10-adapter-v1
```

역인덱스는 좌표당 한 줄이므로 문서 수가 아니라 **좌표 수에 비례해서만 커진다.** 좌표는 수백 개에서 포화하므로 사실상 상한이 있다. `knowledge-load`는 이 파일에서 id를 얻고, 필요한 문서만 직접 연다.

**3단계 (500건+) — `bin/ctx search`가 부분 인덱스만 반환.** 파일을 읽히지 않고 명령이 필터링 결과만 내놓는다.

```sh
ctx search --coord table:tb_research_plan --limit 5
```

이 단계에 오면 MCP 서버(§11.5)를 붙일 실익도 함께 생긴다.

> **핵심** — 어느 단계에서도 **좌표 매칭의 정확도는 변하지 않는다.** 바뀌는 것은 인덱스를 어떻게 전달하느냐뿐이다. 유사도 기반 검색은 문서가 늘면 매칭 결과 자체가 흔들리는데(§13.3), 이 구조는 그렇지 않다. 규모 확장에서 이 차이가 결정적이다.

## 11. 인터페이스

세 개의 인터페이스가 있다. **생성 · 검증 · 소비.**

### 11.1 생성 — `knowledge-share` skill

클로드 코드로 작업하고 세션이 프로젝트 레포에서 열린다면, 사람이 CLI를 직접 칠 일은 없다.

```
.claude/skills/knowledge-share/SKILL.md
```

**동작**

1. `git diff` 와 세션 대화 맥락에서 변경 내용 파악
2. 발견된 이름을 `_vocab.md` 에 **대조**하여 좌표 후보 도출
3. 4섹션 본문 작성 — 요약은 "관련성 판단이 가능한 만큼"
4. 상세 문서가 있으면 `assets/<id>/` 로 복사하고 `attachments` 기록
5. **같은 좌표의 최근 문서를 조회해 `supersedes` 후보 제시** *(v1.1 추가)*
6. 프론트매터 완성 → 지식 레포에 파일 생성 → 커밋 → push

5번이 중요하다. `supersedes`는 작성자가 기억해서 붙이는 필드인데, 사람은 3개월 전 문서의 id를 기억하지 못한다. **skill이 좌표로 조회해 "이 좌표에 D1이 있는데 대체합니까?"를 물어야** 이 필드가 실제로 채워진다. 이게 없으면 §12의 유효성 모델 전체가 빈다.

**이 환경의 결정적 이점**: 세션이 **이미 코드 안에 있다.** 서버에서 처리한다면 소스 미러를 유지하고 참조 맥락을 인위적으로 재구성해야 하지만, 여기서는 그 전부가 불필요하다.

### 11.2 검증 — pre-commit hook

```sh
#!/bin/sh
./bin/ctx check || exit 1     # 필수 필드 · 미등재 좌표 · supersedes 대상 검출
./bin/ctx index               # INDEX.md 재생성
git add INDEX.md
```

**skill이 훅을 대체하지 않는다.** skill은 LLM에 대한 지시이므로 비결정적이다. 대체로 잘 지켜지지만 항상은 아니다. 미등재 좌표가 한 번 새어 나가면 그 문서는 §9.6의 조용한 실패로 들어간다.

> **skill은 편의, hook은 보증.** 둘 다 있어야 한다.

`.git/hooks/`는 clone에 따라오지 않으므로, 훅을 저장소에 커밋되는 `.githooks/`에 두고 `git config core.hooksPath .githooks`를 README에 명시한다.

### 11.3 소비 (1) — `knowledge-load` skill

```
.claude/skills/knowledge-load/SKILL.md
```

**동작**

1. 지식 레포 `git pull` (없으면 clone)
2. **현재 세션에서 좌표를 추출** — `git diff`, 열린 파일, 사용자 지시에서 테이블명·API 경로·모듈을 뽑아 `_vocab.md`로 정규화
3. `INDEX.md`에서 `touches` 매칭 → 후보 목록
4. `supersedes`로 정정된 문서 제외, 최신순 정렬, 기본 상위 5건
5. 후보의 **요약만** 세션 맥락에 주입. `attachments`는 경로만 알림
6. **§12의 유효성 신호를 함께 주입** *(v1.1 추가)*
7. 없으면 "관련 문서 없음" 한 줄

**2단계가 핵심이다.** 사용자에게 좌표를 치게 하면 안 된다. 무엇을 쳐야 할지 아는 사람은 이미 절반은 아는 상태다.

**4단계의 절단은 반드시 흔적을 남긴다.** 12건이 매칭됐는데 5건만 넣었다면, 그 사실을 맥락에 적는다. 상세는 §12.3.

### 11.4 소비 (2) — 자동 발동 규칙

여기에 이 프로토콜에서 가장 중요한 함정이 있다.

> **모르는 사람은 `knowledge-load`를 부를 생각조차 하지 않는다.**

배치 담당은 인터페이스가 바뀐 사실 자체를 모른다. 모르는 것을 찾아보는 사람은 없다. skill을 아무리 잘 만들어도 **사람이 호출을 기억해야 한다면 문제는 그대로 남는다.**

그래서 프로젝트 레포의 `CLAUDE.md`에 규칙으로 박는다.

```
작업을 시작하기 전에 knowledge-load 를 먼저 실행해
관련 맥락이 있는지 확인하라. 없으면 그대로 진행하라.
```

**사람이 아니라 세션이 기억하게 만드는 것** — 스킬 두 개보다 이 한 줄이 실제 효과를 낸다.

### 11.5 소비 (3) — MCP 서버 (선택)

| 툴 | 반환 |
|---|---|
| `search(좌표 \| 자연어)` | 매칭 목록 + 프론트매터 요약 + 유효성 신호 |
| `get(id)` | 문서 전문 |
| `recent(since)` | 기간 내 신규·변경 |

상태를 갖지 않는다. 저장소를 읽고 프론트매터를 파싱해 응답할 뿐이며, DB도 인덱싱 파이프라인도 없다.

**언제 붙이는가** — clone 경로로 먼저 운용하고, 다음 세 가지 중 하나가 필요해질 때 붙인다.

- **최신성 보장** — clone은 낡을 수 있다. MCP는 항상 최신을 본다
- **신선도 부가 정보** — `search` 응답에 *"이 좌표에 이후 문서 3건 있음"* 을 실어 보낼 수 있다
- **인덱스 규모** — §10.5의 3단계. 인덱스를 읽히지 않고 필터 결과만 반환해야 할 때

지금 당장 붙이면 `ls`와 `cat`을 감싼 래퍼에 불과하다. **경로 A로 2주 써봐야 무엇이 불편한지 나오고, 그 불편이 곧 툴 설계가 된다.**

## 12. 유효성 모델 *(v1.1 전면 개정)*

낡은 맥락을 근거로 자신 있게 틀리는 것이 이 시스템의 가장 큰 실패 양상이다.

v1.0에서는 이를 "신선도"로 다뤘다. v1.1에서는 **시간·유효성·경쟁·절단**의 네 축으로 분리한다. 넷을 섞으면 "3주 전 문서"와 "정정된 문서"가 같은 무게로 취급되어, 정작 위험한 쪽을 놓친다.

### 12.1 두 종류의 시간

지식 단위는 두 개의 시각을 갖는다. 별도 필드를 만들지 않는다 — 하나는 프론트매터에, 하나는 Git이 이미 갖고 있다.

| 시각 | 출처 | 의미 |
|---|---|---|
| **결정 시각** | `date` | 이 결정이 내려진 날 |
| **기록 시각** | Git 커밋 시각 | 저장소에 들어온 날 |

둘이 크게 벌어진 문서는 **사후 정리된 문서**다. 나쁘다는 뜻은 아니지만, 그 사이 기간에 다른 사람들은 이 정보 없이 일했다는 뜻이므로 해석에 주의가 필요하다.

`date`는 반드시 결정 시각을 적는다. 문서를 쓴 날이 아니다.

### 12.2 네 가지 개념

> **정정 (정정_판정모델_v2 §3) — 축이 셋이 됐다.** `유효성` 을 뺀다.
> `supersedes` 는 판정이 아니라 참조다 — 작업 기록은 사건이라 무효가 되지
> 않고, 지금 맞는 말을 말하는 것은 관리 문서 섹션이다. 밀림이 error 가 되면서
> (§1) 섹션이 항상 최신이므로 별도 무효 축이 필요 없어졌다.
> 남는 축: **나이 · 최신성 · 절단**.
>
> **개명 (11단계)** — `결착도` → **최신성**, 그 결과는 **후속**. `유효성` 의 정의도 `supersedes` 가 오기재 정정 전용으로 좁혀진 것(수행 v1.0 §6.3)에 맞췄다. **관계 용어의 정본은 수행 v1.0 §6.4 다.**

| 개념 | 정의 | 계산 | 성질 |
|---|---|---|---|
| **나이** | `date` 이후 경과 시간 | 자명 | 참고용. **오래됐다고 틀린 게 아니다** |
| **유효성** | 뒤에 온 기록이 이 기록을 **정정**했는가 | `supersedes` 체인 | **참/거짓.** 정정된 문서는 기본 검색 제외 |
| **최신성** | 같은 좌표를 뒤에 또 바꾼 **후속**이 몇 건인가 | 좌표별 문서 수 카운트 | 경고 부착 |
| **절단** | 매칭됐으나 주입되지 않았는가 | 매칭 수 − 주입 수 | **통보 필수** |

**나이와 유효성을 반드시 구분한다.** 2년 전 문서라도 정정되지 않았으면 그것이 현재의 정답이다. 반대로 어제 문서라도 오늘 정정됐으면 틀린 정보다. **"최근에 쓰였다"와 "지금 유효하다"는 다른 것이다.** 최신순 정렬만으로 이 문제를 풀려는 시도가 흔한 실패 원인이다.

**저장하지 않고 질의 시점에 계산한다.** 저장하면 반드시 낡는다.

### 12.3 로드 시 주입되는 신호

문서 요약과 함께 이 네 줄이 실려야 한다.

```
[유효] 이 문서는 현재 유효함 (이 기록을 정정한 문서 없음)
[나이] 결정 2026-08-19 · 3주 전 · 기록은 결정 4일 후
[최신] table:tb_research_plan 에 후속 2건
       → 2026-0828-plan-status, 2026-0830-batch-fix
[절단] 좌표 매칭 12건 중 최신 5건 주입.
       나머지 7건 id: 2026-06...(생략 목록)
```

**[절단]이 v1.1의 핵심 추가다.**

주입 개수를 제한하는 것 자체는 옳다. 맥락을 무한정 늘리면 §3(2)의 주의 분산 문제로 되돌아간다. 문제는 **자른 사실을 아무도 모르는 것**이다. 자른 사실이 프롬프트에 없으면 LLM은 그 7건이 *잘린 것*이 아니라 *존재하지 않는 것*으로 취급하고, "관련 문서는 이 5건이 전부"라고 확신 있게 답한다. 원인도 결과도 아무에게 통보되지 않는 §9.6의 조용한 실패다.

id만 나열하면 되므로 비용은 수십 토큰이고, 얻는 것은 **LLM이 "더 있다"를 알고 필요하면 요청할 수 있게 되는 것**이다.

> **이 통보가 가능한 이유는 좌표가 참/거짓 판정이기 때문이다.** "매칭 12건 중 5건"이라고 말하려면 12건이 관련 있다는 확정이 있어야 한다. 유사도 점수만 있으면 6등이 관련 있는 문서인지 아닌지 시스템 자신도 모르므로, 잘렸다고 말할 자격이 없다. §13.3 참조.

프론트매터를 세기만 하면 되므로 전체 비용은 사실상 0이고, 오적용을 막는 유일한 장치다.

# 제3부 — 검색 계층 *(v1.1 신설)*

## 13. 왜 벡터 RAG가 아닌가

이 프로토콜을 설명하면 거의 항상 나오는 질문이 있다.

> "문서를 벡터DB에 넣고 RAG로 검색하면 되지 않나? 좌표를 사람이 붙일 필요가 없는데."

타당한 질문이고, 답은 "틀렸다"가 아니라 **"층이 다르고, 순서가 있다"** 이다. 이 절은 그 근거다.

### 13.1 두 방식이 실제로 하는 일

| | 벡터 RAG | 좌표 매칭 |
|---|---|---|
| 저장 단위 | 청크 (문단·N토큰) | 지식 단위 (문서) |
| 검색 근거 | 임베딩 코사인 유사도 | `touches` 일치 |
| 판정 결과 | 연속값 (0.74) | 참/거짓 |
| 절단 방식 | 상위 k개 | 필터 후 정렬·제한 |
| 사람의 작성 부담 | 0 | 좌표 3~6개 |
| 인프라 | 임베딩 API·벡터DB·재인덱싱 | 없음 (파일 파싱) |

작성 부담이 0이라는 점은 벡터 RAG의 진짜 장점이다. 가볍게 보면 안 된다. 문제는 그 대가로 무엇을 내주느냐다.

### 13.2 유사도가 표현하지 못하는 것

임베딩 공간에도 관계는 있다. 의미가 비슷하면 가깝게 놓인다. 문제는 **그 관계가 한 종류뿐**이라는 것이다.

| | 유사도 (임베딩) | 관계 (좌표·supersedes) |
|---|---|---|
| 방향 | 대칭 — sim(A,B) = sim(B,A) | 비대칭 — "A가 B를 대체" ≠ 그 반대 |
| 종류 | 없음. 숫자 하나 | 있음. 대체·참조·소속·영향 |
| 값 | 정도 | 참/거짓 |
| 표현 가능한 것 | "닮았다" | "이것이 저것을 무효화했다" |

그리고 이 한계가 최악으로 드러나는 지점이 있다.

```
"이 좌표의 담당 모듈은 acl-adapter 다"   ─┐
                                          ├─ 코사인 유사도 0.96
"이 좌표의 담당 모듈은 batch-agg 다"     ─┘
```

**모순되는 두 진술이 임베딩 공간에서 거의 같은 자리에 있다.** 문장 구조가 같고 한 토큰만 다르기 때문이다.

유사도 관점에서 이 둘은 "거의 같은 것"이다. 그래서 검색하면 사이좋게 둘 다 상위에 올라온다. **모순일수록 더 확실하게 함께 딸려온다.** 임베딩은 "이 둘이 양립할 수 없다"를 표현할 언어를 갖고 있지 않다.

`supersedes: 2026-0710-a10-adapter-v1` 한 줄이 이것을 해결한다. 방향이 있고, 참/거짓이 명확하고, 필터가 결정론적이다. **1536차원 벡터가 못 하는 일을 문자열 한 줄이 한다.**

### 13.3 top-k 절단의 구조적 문제

여기가 §9.6의 조용한 실패와 정확히 같은 성질이다. 좌표 오타 하나 없이, 시스템 어디에도 결함 없이 발생한다.

**8월 20일** — 배치 담당이 묻는다. "야간 집계 배치 관련 최근 변경 있나?"

```
1위 0.84  배치 스케줄러 변경
2위 0.81  집계 쿼리 튜닝
3위 0.79  로그 포맷 변경
4위 0.77  모니터링 알람 추가
5위 0.74  A10 어댑터 개편 (중복 방지 키!)   ← 간신히 통과
──────── top-5 절단선 ────────
```

중복 방지 키가 맥락에 들어갔다. 잘 굴러갔다.

**8월 27일** — 누군가 무관한 문서를 올린다. "배치 서버 증설 완료". 같은 사람이 같은 질문을 한다.

```
1위 0.84  배치 스케줄러 변경
2위 0.82  배치 서버 증설          ← 새로 진입
3위 0.81  집계 쿼리 튜닝
4위 0.79  로그 포맷 변경
5위 0.77  모니터링 알람 추가
──────── top-5 절단선 ────────
6위 0.74  A10 어댑터 개편          ← 밀려서 탈락
```

LLM은 "관련된 최근 변경은 스케줄러와 서버 증설입니다"라고 답한다. **확신을 갖고.**

A10 문서는 조금도 변하지 않았다. 유사도 0.74도 그대로다. **무관한 문서 하나가 위에 끼어들었을 뿐인데 답이 뒤집혔다.**

그리고 아무도 이것을 모른다. 세 층이 전부 정상 동작하기 때문이다.

| 층 | 상태 |
|---|---|
| 벡터DB | top-5 정상 반환. 에러 없음 |
| 프롬프트 조립 | 5개 받아서 넣음. 에러 없음 |
| LLM | 받은 5개 안에 없으니 "없음". **틀렸다는 자각 없음** |

**절단은 LLM 바깥에서, LLM이 관여하지 않은 채, 흔적 없이 일어난다.** 사람이 검색했다면 스크롤을 내려 6등을 볼 수 있다. LLM에는 내릴 스크롤이 없다.

좌표 매칭에는 이 문제가 없다. `touches`에 `table:tb_research_plan`이 있는가는 참/거짓이고, **문서가 만 건 늘어도 판정이 바뀌지 않는다.** 서로 순위를 다투지 않으므로 밀려날 자리가 없다.

### 13.4 정규화 관점에서 본 청킹

"RAG는 문서를 잘게 쪼개니 더 정규화된 것 아닌가"라는 관점이 있다. 분해라는 축에서는 맞다. 그러나 정규화는 연산이 두 개다.

1. **분해** — 나눈다
2. **무손실 결합** — 나눈 것을 키로 다시 합쳤을 때 원본이 복원된다

**2번이 안 되는 분해는 정규화가 아니라 무효한 분해다.**

청킹은 여기서 실패한다. §3(1)의 214번째 줄을 청크로 떼어내면:

```
"연계 실패 시 A10이 5분 주기로 자동 재시도, 수신측 중복 방지 키 필수"
```

남은 것은 문장 하나뿐이다. 사라진 것은 — 어느 API 이야기인가(외래키), "수신측"이 누구인가(참조 대상), 언제 결정됐고 아직 유효한가(시점), 어느 문서에서 왔나(기본키). **조인할 키가 없으니 원본으로 되돌아갈 수 없고, 되돌아갈 수 없으니 LLM이 추정으로 메운다.** §3(3)의 "연계 담당과 연구관리 담당이 다르게 읽는다"가 그대로 재현된다.

기준도 다르다. 정규화는 **함수 종속**이라는 명시적 근거로 쪼갠다. 청킹은 512토큰이니 문단 경계니 하는 **의미와 무관한 기준**으로 자른다.

그래서 등급을 다시 매기면 이렇다.

| | 입도 | 키 보존 | 판정 |
|---|---|---|---|
| 청크 + 임베딩 | 잘다 | 없음 | **무효한 분해** |
| 지식 단위 + 좌표 | 거칠다 | `id`·`touches`·`supersedes` | 유효한 분해 |

> **정규화 등급은 "얼마나 잘게 쪼갰나"가 아니라 "쪼갠 뒤에도 복원되나"로 매겨진다.**

참고로 RAG 진영의 개선 기법 — 청크에 부모 문서 id·제목·날짜를 메타데이터로 붙이기, parent document retrieval, contextual retrieval — 은 전부 **청킹으로 깨진 조인 키를 사후에 복원하는 작업**이다. 이 프로토콜은 그 복원을 처음부터 안 해도 되게 만든 쪽이다.

### 13.5 정리 — 세 가지 성질

| | 재현성<br/>*같은 입력 → 같은 출력* | 안정성<br/>*같은 의미 → 같은 결과* | 설명가능성<br/>*왜 그렇게 됐는지* |
|---|:--:|:--:|:--:|
| 임베딩 검색 | O | **X** | **X** |
| 좌표 매칭 | O | O | O |
| LLM 추론 | X | X | X |

임베딩 계산 자체는 결정론적이다. 같은 텍스트를 같은 모델에 넣으면 같은 벡터가 나오고, 코사인 유사도는 사칙연산이며, top-k는 정렬이다. 여기에 주사위는 없다.

**문제는 무작위성이 아니라 근거 없음과 불안정성이다.**

- 질의 문구가 조금 바뀌면 순위가 뒤집힌다 ("계획서 상태값" vs "planStatus 필드")
- 문서가 늘면 기존 질의의 답이 바뀐다 (§13.3)
- 유사도 0.78이 관련 있음인지 아닌지 판정할 기준이 없다

> **비결정론적이어서 못 믿는 것이 아니라, 결정론적이지만 근거를 설명할 수 없어서 못 믿는 것.**

§17의 성공지표에서 **오적용 건수를 다른 모든 지표에 우선한다**고 정한 이상, 검색층의 선택은 여기서 결정된다.

## 14. 계층 설계와 확장 경로

### 14.1 층을 쌓는 순서

벡터 검색은 **금지 대상이 아니라 배치 순서의 문제다.**

```
1층  좌표 필터        참/거짓. supersedes 제외. 후보 확정
     ↓
2층  정렬·제한        최신순 / 최신성. 절단 시 [절단] 신호 부착
     ↓
2.5층 (선택) 유사도    확정된 후보 안에서만 순서 조정·단락 추출
     ↓
3층  맥락 주입        요약 + §12.3의 네 가지 신호
     ↓
──── 여기서부터 LLM ────
4층  추론
```

**1층 없이 2.5층만 쓰면** 낡은 문서가 섞이고 문서가 늘 때마다 결과가 흔들린다. 지금 겪는 문제 그대로다.
**2.5층 없이 1층만 써도** 상당 부분 굴러간다. 좌표에 안 걸리는 질의에서만 아쉽다.

**범위가 확정된 뒤의 유사도 정렬은 틀려도 피해가 작다. 범위 자체를 유사도가 정하면 틀렸다는 사실조차 아무도 모른다.** 이것이 순서를 고정하는 이유다.

### 14.2 벡터 검색을 붙이는 시점

두 신호 중 하나가 관측되면 검토한다. 그 전에는 붙이지 않는다.

| 신호 | 증상 | 왜 이때인가 |
|---|---|---|
| **좌표에 안 걸리는 질의가 반복됨** | "결재 로직이 왜 이렇게 복잡해졌지?" 같은 개념 질의. `touches` 매칭 0건인데 실제로는 관련 문서가 있음 | 좌표는 구조에 붙는 주소라 구조로 표현되지 않는 질문을 못 받는다. 여기가 유사도의 고유 영역 |
| **문서 본문 내부를 찾아야 함** | 문서는 찾았는데 300줄 첨부 어디에 있는지 모름 | 문서 단위 매칭의 한계. 첨부 내부 검색은 유사도가 낫다 |

문서 50건 규모에서 붙이면 인제스트 파이프라인 유지비만 나가고 정확도는 좌표 필터보다 떨어진다. §11.5에서 MCP를 두고 내린 판단 — *"지금 붙이면 `ls`와 `cat`을 감싼 래퍼에 불과하다"* — 이 그대로 적용된다.

### 14.3 붙일 때 지킬 규칙

**(1) 좌표 필터 뒤에 둔다.** 1층을 통과한 후보 안에서만 유사도를 계산한다. 전체 코퍼스를 대상으로 하면 §13.3이 재현된다.

**(2) 청크에 키를 전부 붙인다.** 최소한 부모 `id`, `touches`, `date`. 이게 없으면 §13.4의 무효한 분해가 된다.

```yaml
# 청크 메타데이터 (최소)
parent_id: 2026-0819-a10-adapter
touches: [table:tb_research_plan, api:/adapter/a10/plan-sync]
date: 2026-08-19
valid: true          # supersedes 체인으로 계산된 값
```

**(3) 맥락에 넣는 것은 청크가 아니라 부모 문서의 요약이다.** 유사도는 "어느 문서를 볼지" 고르는 데만 쓰고, 주입은 지식 단위 단위로 한다. 청크 조각을 그대로 넣으면 §13.4의 키 상실이 그대로 발생한다.

**(4) 인덱스는 파생물로 취급한다.** Git 저장소가 정본이고 벡터 인덱스는 언제든 재생성 가능한 캐시다. 벡터DB에만 있는 정보를 만들지 않는다.

### 14.4 붙이지 말아야 할 것

| 하지 말 것 | 이유 |
|---|---|
| 좌표를 임베딩으로 대체 | §13.2·13.3. 관계가 유사도로 납작해진다 |
| `supersedes`를 최신순 정렬로 대체 | 나이 ≠ 유효성 (§12.2) |
| `_vocab.md`를 임베딩 유사도로 대체 | 엔티티 해소는 유사도가 못 한다. `tb_research_plan`과 `계획서테이블`은 임베딩상 멀다 |
| 벡터DB를 정본으로 승격 | 임베딩 모델 교체 시 전량 재인덱싱. Git 저장소가 정본이어야 한다 |

## 15. 전체 흐름

```
① 김PL, 프로젝트 레포 세션에서 A10 어댑터 인터페이스 개편
   산출물: 코드 변경 + docs/interface-spec.md

② "지식공유 문서 만들어줘"  → knowledge-share skill

③ skill: git diff → 좌표 추출 → _vocab.md 대조 → 요약 작성
        → interface-spec.md 를 assets/ 로 복사
        → 같은 좌표 최근 문서 조회 → "2026-0710 을 대체합니까?" 확인
        → 프론트매터 작성

④ 지식 레포 커밋 → hook: ctx check
   ✗ table:tb_plan 미등재 → 거부
   → _vocab.md 에 등재 후 재커밋 → 통과 → ctx index → push

⑤ [며칠 뒤] 배치 담당, 다른 프로젝트 세션에서 야간 집계 배치 수정 착수
   인터페이스가 바뀐 걸 모른다

⑥ CLAUDE.md 규칙에 따라 세션이 knowledge-load 자동 실행
   pull → 현재 좌표 추출(table:tb_research_plan) → 대조 → INDEX 매칭
   → 지식 단위 요약 주입
   + [유효] 현재 유효
   + [최신] 이 좌표에 후속 2건
   + [절단] 매칭 8건 중 5건 주입, 나머지 3건 id 나열

⑦ 배치 담당이 맥락을 반영해 수정. 김PL에게 묻지 않았고 회의도 없었다

⑧ 작업이 끝나면 그도 ②를 호출한다. 모든 세션이 작성자이자 수신자다
```

**이 흐름에서 사라진 것**: 공유용 회의, 메신저 장문 공지, 받은 문서를 다시 AI로 해석하는 단계, "이거 왜 바뀌었죠?" 질문.

**⑥에서 세 줄의 신호가 결정적이다.** 요약만 주입하면 배치 담당의 세션은 그 5건이 전부라고 믿는다. 신호가 있으면 "이후 문서 2건"과 "미주입 3건"을 보고 필요 시 더 요청한다. 비용은 수십 토큰이다.

## 16. 비용 구조

이 설계를 벡터 RAG와 비교할 때 흔히 "정확도를 위해 비용을 감수한다"고 생각하지만, 사실과 다르다. **비용은 감수되는 것이 아니라 자리를 옮긴다.**

| | 좌표 방식 | 벡터 RAG |
|---|---|---|
| 임베딩 API | 0 | 문서 추가마다 호출 |
| 벡터DB 운영 | 0 | 인스턴스 유지 |
| 재인덱싱 | 0 | 임베딩 모델 교체 시 전량 |
| 구현 | `bin/ctx` 150줄 | 인제스트 파이프라인 |
| 컨텍스트 토큰 | 비슷하거나 적음 | — |
| **사람의 작성 부담** | **좌표 3~6개 · 문서당 5분** | **0** |

인프라 비용은 좌표 쪽이 압도적으로 싸다. **대신 유일한 비용이 사람에게 있고, 그것이 이 설계의 급소다.**

```
벡터 RAG : 작성 비용 0  ·  인프라 비용 高  ·  신뢰도 낮음
좌표     : 작성 비용 有  ·  인프라 비용 0   ·  신뢰도 높음
```

그러므로 이 프로토콜의 생사는 **"작성이 5분 안에 끝나는가"** 하나에 달려 있다. §17의 3단계(최근 작업 10건 직접 문서화)가 측정하는 것이 정확히 이것이고, 5분을 넘으면 필드를 줄이거나 skill의 자동 추출을 강화해야 한다. **이 수치가 안 나오면 나머지 설계가 아무리 옳아도 시스템은 도입되지 않는다.**

한편 맥락을 많이 넣는 것이 이 설계의 목적은 아니다. 오히려 반대다.

```
유사도만:  놓칠까 봐 20건 넣는다      (근거 없는 과잉)
좌표 있음: 3건이 전부임을 알고 3건만   (근거 있는 절약)
```

**좌표의 이점은 많이 넣는 것이 아니라, 적게 넣어도 안전해지는 것이다.** 맥락을 늘리면 §3(2)의 주의 분산이 되돌아온다.

## 17. 도입 계획

| 단계 | 작업 | 소요 | 검증 |
|---|---|---|---|
| 1 | `_vocab.md` 초기 구축 (스키마·라우팅 자동 추출 + 수동) | 반나절 | 좌표 타입이 충분한가 |
| 2 | `TEMPLATE.md` · `CLAUDE.md` 작성 | 2시간 | — |
| 3 | **최근 작업 10건을 직접 문서화** | 1일 | **필드 과부족 · 작성 소요 시간** |
| 4 | `bin/ctx` (check·index) + 훅 | 1일 | 미등재 좌표가 실제로 걸리는가 |
| 5 | `knowledge-share` skill | 반나절 | 좌표 제안 정확도 · **supersedes 후보 제시 동작** |
| 6 | `knowledge-load` skill + `CLAUDE.md` 자동 발동 규칙 | 반나절 | 관련 문서를 물어오는가 · **[절단] 신호가 실리는가** |
| 7 | 2주 운용 | 2주 | 오적용 건수 · 반복 질문 감소 · **오적용 원인 분류** |
| 8 | 필요 시 §9.8 / §10.5 2단계 / MCP / 벡터 검색 | — | 각 절의 도입 신호 충족 여부 |

### 3단계를 건너뛰면 안 되는 이유 (최근 작업 10건 직접 문서화)

필드 설계는 책상에서 검증되지 않는다. 실제 작업 10건을 넣어보면 그 자리에서 드러난다.

- 매번 비는 필드가 있는가 → 빼야 한다
- 본문에 같은 종류의 정보를 반복해서 쓰는가 → 필드로 올려야 한다
- 좌표 타입 5종으로 부족한가 → `_vocab.md` 확정 전에 알아야 한다
- **작성에 실제로 몇 분이 걸리는가** → 5분을 넘으면 팀은 쓰지 않는다 (§16)

### 7단계에서 반드시 기록할 것 *(v1.1 추가)*

오적용이 발생하면 **건수만 세지 말고 원인을 분류한다.** 8단계의 확장 판단이 전부 이 분류에 달려 있다.

| 원인 분류 | 대응 |
|---|---|
| 좌표가 안 붙어서 못 찾음 | 작성 skill 개선 · `_vocab.md` alias 추가 |
| 좌표가 틀려서 못 찾음 | `ctx check` 규칙 강화 |
| 문서 전체가 정정돼 유효한 부분까지 사라짐 | **§9.8 좌표 단위 무효화 도입** |
| 매칭됐으나 절단되어 안 들어감 | 주입 개수 조정 · [절단] 신호 강화 |
| 좌표로 표현할 수 없는 질의였음 | **§14.2 벡터 검색 검토** |
| 문서가 아예 없었음 | 커버리지 문제. 작성 마찰 점검 |

### 성공 지표

| 지표 | 의미 |
|---|---|
| 반복 질문 수 | "이거 왜 이렇게 됐죠?" 발생 빈도 |
| 맥락 진입 시간 | 특정 모듈 맥락 파악까지 걸리는 시간 |
| 커버리지 | 실제 작업 대비 지식 단위 생성 비율 |
| **오적용 건수** | 낡은 맥락을 근거로 잘못 반영한 사례 |
| 미결 대기 시간 | `status: 미결` 이 해소되기까지의 일수 |
| **문서당 작성 시간** | 5분 초과 시 커버리지가 무너진다 (§16) |

오적용 건수가 오르면 시스템은 없느니만 못하다. 다른 모든 지표에 우선한다.

## B. `CLAUDE.md` (프로젝트 레포)

```markdown
## 업무 맥락

작업을 시작하기 전에 knowledge-load 를 먼저 실행해
관련 맥락이 있는지 확인하라. 없으면 그대로 진행하라.

작업이 끝나면 knowledge-share 로 지식 단위를 남겨라.
```

## C. `CLAUDE.md` (지식 레포)

```markdown
지식 문서는 knowledge/ 에 있다.
먼저 INDEX.md 를 읽고, touches 로 매칭해 관련 문서만 골라 읽어라.
좌표 표기가 불확실하면 _vocab.md 의 aliases 로 정규화하라.
상세가 필요할 때만 attachments 를 열어라.

문서를 맥락에 넣을 때는 반드시 함께 적어라.
- 그 문서가 현재 유효한지 (supersedes 로 덮이지 않았는지)
- 같은 좌표에 이후 문서가 몇 건 있는지
- 매칭된 문서 중 몇 건을 실제로 넣었고, 넣지 않은 것의 id 는 무엇인지

매칭됐으나 넣지 않은 문서가 있는데 그 사실을 적지 않으면,
읽는 쪽은 그 문서가 존재하지 않는다고 판단한다.
```

## D. `bin/ctx` 명령

| 명령 | 동작 |
|---|---|
| `ctx check` | 필수 필드 누락, `_vocab.md` 미등재 좌표, `supersedes` 대상 존재 여부 검사 |
| `ctx index` | 프론트매터 스캔 → `INDEX.md` 재생성 (2단계 진입 시 `INDEX-by-coord.md` 동시 생성) |
| `ctx new` | 템플릿 생성 (skill 사용 시 불필요) |
| `ctx search` | 좌표 필터 + 유효성 계산 결과 반환 (§10.5 3단계에서 추가) |

Node 기준 150줄 안쪽. 프론트매터 파싱 외에 의존성이 없다.

## E. 용어

| 용어 | 정의 |
|---|---|
| 지식 단위 (Knowledge Unit) | 공유되는 최소 단위. 프론트매터 + 4섹션 본문 + 첨부 |
| 좌표 (Coordinate) | `타입:값` 형식의 안정적 식별자. 지식이 붙는 주소 |
| 통제 어휘 (Controlled Vocabulary) | `_vocab.md`. 정본 좌표와 alias의 집합 |
| 대조 (Reconciliation) | 자유로운 표현을 정본 좌표로 수렴시키는 정규화 연산 |
| 유효성 (Validity) | 뒤에 온 기록이 이 기록을 정정하지 않았는가. 참/거짓 |
| 나이 (Age) | `date` 이후 경과 시간. **유효성과 다르다** |
| **최신성** | 같은 좌표에 뒤이어 발생한 지식 단위 수 = **후속**. 관계 용어 정본은 수행 v1.0 §6.4 |
