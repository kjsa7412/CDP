# 제1부 — 무엇을 만들려는가

## 1. 물리적 소통이 나르는 여섯 가지

"소통 없이 굴러간다"를 목표로 두려면 **지금 소통이 무엇을 나르는지** 먼저 세어야 한다.

| # | 대화 | 나르는 것 | 지금 |
|---|---|---|---|
| 1 | "이거 왜 이래요?" | 근거 | **수행 v1.0 이 푼다** — 작업 기록 |
| 2 | "지금 어떻게 돼 있어요?" | 상태 | **수행 v1.0 이 푼다** — 관리 문서 섹션 |
| 3 | "이거 결정해 주세요" | 결정 요청 | 목록은 있다(`status: 미결`). **도달하지 않는다** |
| 4 | "누가 이거 하고 있어요?" | 점유 | **없다** |
| 5 | "저 다 했어요" | 완료 통보 | **없다.** pull 해야 안다 |
| 6 | "이거 좀 해주세요" | 할당 | **없다** |

**1·2 는 이미 풀렸다.** 이 문서가 다루는 것은 3~6 이고, 그 넷은 전부 **근거가 아니라 신호**다.

### 신호에는 채널이 필요하다

문서는 **찾아보는 사람**에게만 도달한다. 프로토콜 §11.4가 지적한 함정이 그대로다 — *"모르는 사람은 부를 생각조차 하지 않는다."*

폐쇄망이면 서버도 메신저도 없다. **유일한 공유 채널은 git 저장소 자체다.**

```
보내기 = commit + push
받기   = pull
```

> **pull 은 편의가 아니라 비동기 협업의 유일한 수신 채널이다.** 뷰어 v0.2 는 읽기 전용이라 최신화를 범위 밖으로 뒀지만(v0.2 §2.2 ④), **쓰기와 협업이 들어오면 그 전제가 무너진다**(§9).

## 2. 목표를 좁게 정의한다

"물리적 소통 없이"를 문자 그대로 목표로 잡으면 이슈 트래커·채팅·워크플로 엔진을 만들게 된다. **그건 CDP 가 아니다.**

**비동기 협업에서 가장 비싼 것은 둘이다.**

| 낭비 | 원인 | 필요한 것 |
|---|---|---|
| **몰라서 못 한 일** | 결정이 필요한데 아무도 모른다 | 미결이 **관련자에게 도달** |
| **몰라서 두 번 한 일** | 같은 대상을 둘이 동시에 건드린다 | **점유가 보인다** |

**이 둘만 푼다.** 할당(6번)은 넣지 않는다 — 조직 구조와 얽혀 있고 CDP 가 답할 문제가 아니다. *(도입 신호는 §19)*

> **목표 문장**
>
> **"필요한 것이 필요한 사람에게 물어보지 않아도 도달하고, 두 사람이 같은 것을 모르고 건드리지 않는다."**

## 3. 자족하는 지식 레포

폐쇄망 PC 에 clone 하나를 옮겼을 때 **물어볼 사람이 없다.** 그러므로 레포 안에 전부 있어야 한다.

```
지식레포/                        ← 이 폴더 하나가 이관 단위다
  README.md                     이게 뭔가 · 5분 안에 시작하기
  MANUAL.md                     일상 사용법 (§15)
  CLAUDE.md                     AI 규약 — **어느 skill 을 부를지**(§8.1)

  _vocab.md   _managed.md       어휘 · 등록부
  work/       docs/             작업 기록 · 관리 문서
  INDEX.md    INDEX-by-coord.md 색인 (자동)

  .claude/skills/               ← **여기가 핵심 이동**
    cdp-work/SKILL.md             ① 검토 → ② 주입 → ③ 요청수행  (§5)
    cdp-load/SKILL.md             주입만 따로 (cdp-work 의 ②가 참조)
    cdp-save/SKILL.md             작업 기록 + 파생 갱신
    cdp-managed/SKILL.md          밀린 섹션 따라잡기
  .githooks/pre-commit
  bin/ctx  ctx.cmd  ctx.mjs   ← 껍데기 + 구현 (§3.1)

  design/                       설계서 사본 (왜 이렇게 만들었나)
  tools/cdp.exe                 앱 + ctx 실행기.  **Node 없는 PC 에서는 필수**
```

### skill 을 지식 레포에 둔다

프로토콜 §11.1 은 skill 을 프로젝트 레포의 `.claude/skills/` 에 뒀다. **지식 레포로 옮긴다.**

| | 프로젝트 레포에 두면 | 지식 레포에 두면 |
|---|---|---|
| 이관 | 레포 두 개를 옮겨야 한다 | **clone 하나** |
| 버전 | 프로젝트마다 skill 이 갈라진다 | **한 벌** |
| 개정 | 프로젝트 수만큼 배포 | pull 하면 끝 |
| 폐쇄망 | 두 벌을 맞춰 넣어야 한다 | **자족** |

프로젝트 레포에는 **가리키는 몇 줄**만 남는다(부록 B).

### LLM 을 가리지 않는다

폐쇄망에서는 Claude Code 가 아닐 수 있다.

| 구성요소 | 형태 | 근거 |
|---|---|---|
| skill | **마크다운 지시문** | 어떤 LLM 이든 읽는다. 실행 코드가 아니다 |
| `bin/ctx` | **셸 껍데기 + Node 구현 + exe 내장** | **Node 가 없어도 돈다**(§3.1) |
| 훅 | **sh 스크립트** | git 이 실행한다 |
| 앱 | **단일 exe / npx** | 네트워크 불필요(뷰어 v0.2 §7) |

### 3.1 Node 가 없는 PC 에서도 돈다

폐쇄망 PC 에 Node 런타임이 없다고 전제한다. `bin/ctx` 를 순수 Node 스크립트로만
두면 **그 PC 에서 검증 층이 통째로 사라진다** — git 훅이 `ctx check` 를 못 부르고,
미등재 좌표가 그대로 커밋된다.

**구현은 한 벌, 실행기는 둘로 만든다.**

```
bin/
  ctx        ← sh 껍데기.  실행기를 고른다
  ctx.cmd    ← cmd 껍데기.  사람이 직접 칠 때
  ctx.mjs    ← 구현.  순수 Node, 의존성 0
tools/
  cdp.exe    ← Node 런타임 + ctx.mjs 내장
```

`bin/ctx` 가 하는 일은 셋뿐이다.

```sh
#!/bin/sh
# 1) node 가 있으면 그것으로
command -v node >/dev/null 2>&1 && exec node "$(dirname "$0")/ctx.mjs" "$@"
# 2) 없으면 레포 안의 exe 로 (같은 구현이 들어 있다)
for exe in "$(dirname "$0")/../tools/cdp.exe" "$(command -v cdp.exe)"; do
  [ -x "$exe" ] && exec "$exe" ctx "$@"
done
echo "ctx: node 도 cdp.exe 도 없습니다. tools/cdp.exe 를 확인하세요." >&2
exit 1
```

**`cdp.exe` 가 `ctx` 를 첫 인자로 받으면 서버를 띄우지 않고 CLI 로 동작한다.**
이미 Node SEA 로 런타임을 품고 있으므로(뷰어 v0.2 §7) 런타임을 따로 넣을 필요가 없다.

> **sh 껍데기가 Windows 에서 도는 이유** — git 이 있으면 sh 도 있다.
> Git for Windows 가 bash 를 함께 깔고 git 훅을 그 위에서 돌린다.
> git 이 없으면 훅 자체가 없으므로 이 경로는 어차피 필요하지 않다.

| | 얻는 것 | 대가 |
|---|---|---|
| 구현 한 벌 | 로직이 갈라지지 않는다 | — |
| exe 를 레포에 커밋 | **이관 단위가 clone 하나로 유지된다**(§3) | 약 50MB. 다만 `ctx` 로직이 바뀔 때만 교체한다 |
| 껍데기가 실행기를 탐색 | Node 가 있으면 그쪽이 빠르다 | 껍데기 두 개를 맞춰야 한다 |

**exe 를 커밋하지 않는 선택도 된다.** 그 PC 에서 앱으로 문서를 읽는다면 exe 는
이미 거기 있다 — 껍데기가 `PATH` 도 훑으므로 그 경우에도 동작한다. 커밋은
**"clone 하나만 옮기면 끝난다"를 지키기 위한 값**이다.

**skill 이 마크다운이라는 점이 결정적이다.** 로컬 LLM 이 skill 을 못 부르면 사람이 그 파일을 열어 붙여넣어도 동작한다 — 지시문이지 API 가 아니기 때문이다(§21).

# 제2부 — 작업 절차 ★

## 4. 요청이 먼저다

**세션이 시작되자마자 맥락을 주입하면 안 된다.** 두 가지가 어긋난다.

### (1) 좌표 추출은 작업 이해를 전제한다

좌표는 *"이 작업이 바꾼 대상"* 이다(수행 v1.0 §5). **무엇을 바꿀지 모르면 뽑을 것이 없다.** 세션 시작 시점에는 요청이 아직 없거나, 있어도 읽히기 전이다.

```
세션 시작 → cdp-load → ???
              ↑
        무엇으로 좌표를 뽑나
```

`git diff` 와 열린 파일에서 추측할 수는 있다. 그런데 그것은 **직전 작업의 흔적**이고 지금 요청과 무관할 수 있다. 어제 만지던 파일이 열려 있다고 오늘 그것을 작업하는 것이 아니다.

### (2) 일찍 주입하면 요청의 해석이 오염된다

이쪽이 더 미묘하고 더 위험하다.

```
요청을 읽기 전에 관리 문서 섹션 5개가 들어온다
  → AI 는 그 다섯 개의 틀로 요청을 읽는다
  → 요청이 실제로 가리키는 여섯 번째 대상을 못 본다
```

**주입은 답을 좁히는 행위다.** 무엇을 좁혀야 하는지 알기 전에 좁히면 엉뚱한 곳을 좁힌다. 프로토콜 §3(2)가 지적한 *"관련 없는 문서에 주의가 분산되어 정확도가 떨어진다"* 의 더 나쁜 형태다 — 분산이 아니라 **편향**이기 때문이다.

> ## 요청이 먼저다. 요청을 이해한 뒤에 무엇을 가져올지 정한다.

## 5. 하나의 skill 이 절차를 품는다

**절차를 `CLAUDE.md` 에 나눠 적지 않는다. skill 하나가 요청 하나를 처음부터 끝까지 처리한다.**

```
cdp-work  ← 작업 요청 하나를 이 skill 로 처리한다
   │
   ① 검토       요청을 이해하고 대상을 뽑는다
   │             _vocab.md 만 읽는다.  **멈추지 않는다**
   ② 주입       필요하면 관리 문서 섹션을 읽어 맥락으로 삼는다
   │             불필요하면 건너뛴다
   ③ 요청수행   주입된 상태를 근거로 요청을 수행한다
```

| 단계 | 입력 | 출력 | 지식 레포 접근 |
|---|---|---|---|
| ① 검토 | 요청 · `git diff` · 열린 파일 | 요약 + 대상 목록 + 주입 여부 (4~6줄) | **`_vocab.md` 만** |
| ② 주입 | ①의 좌표 | 관리 문서 섹션 · 밀림 · 절단 | 읽기 |
| ③ 요청수행 | ②의 맥락 | **요청이 요구한 것** — 코드·답변·문서·분석 | — |

### 왜 하나로 묶는가

| | 절차를 규약으로 나눠 적으면 | skill 하나로 묶으면 |
|---|---|---|
| 단계 누락 | 각 단계가 별개 지시라 건너뛰기 쉽다 | **한 문서라 부분 실행이 어색하다** |
| 맥락 범위 | 세션 전체에 걸린다 | **요청 하나에만 걸린다** |
| 불필요할 때 | 규약이라 매번 걸린다 | **부르지 않으면 된다** |
| 이관 | 규약 + skill 두 벌을 맞춰야 한다 | **skill 한 벌**(§3) |

**"부르지 않으면 된다"가 결정적이다.** 주입이 필요한지를 판정 표로 가릴 필요가 없다 — **skill 을 부르는 행위 자체가 판정**이다.

| 요청 | |
|---|---|
| *"PSC043 에 연대서명 출력 추가해줘"* | `cdp-work` 로 처리 → 맥락이 주입된다 |
| *"이 정규식 왜 안 되지"* | **부르지 않는다.** 지식 레포와 무관하다 |
| *"이 함수 이름 바꿔줘"* | 부르지 않는다 |
| *"이 화면 이렇게 바꿔줘"* — **내가 그 도메인의 리더이고 내 로컬이 최신일 때** | **부르지 않는다.** 아래 |

### 안 부르는 것이 맞는 경우가 하나 더 있다

skill 을 부르지 않으면 AI 는 **자기가 가진 소스와 코드를 분석해서 작업한다.**
지식 레포의 맥락을 받지 않는다.

**그것이 맞는 상황이 있다** — 내가 그 도메인의 리더이고, 내 작업 환경이 최신일 때.

```
지식 레포        ← 내가 어제 쓴 것.  나보다 뒤에 있다
내 로컬 코드     ← 오늘 내가 만든 것.  이쪽이 정본이다
```

**이때 주입은 나를 어제로 되돌린다.** 관리 문서 섹션은 내가 쓴 것이고 내 코드보다
뒤처져 있다. 그것을 근거로 삼으면 §4(2)의 편향이 그대로 일어난다 — 이미 지나온
상태로 답을 좁힌다.

> **"낡은 맥락으로 작업한다"가 아니다.** 맥락을 아예 받지 않는 것이다.
> 이 구분이 중요한데, 낡은 것을 받았다면 갱신하면 되지만 **안 받은 것은
> 갱신할 대상 자체가 없다.** 판단 기준이 코드이고, 리더에게는 그것이 맞다.

**맥락이 요청 하나에만 걸리는 것도 이득이다.** 세션 시작에 주입하면 그 세션의 남은 모든 요청이 그 맥락을 끌고 다닌다. skill 로 묶으면 **그 요청이 끝나면 맥락의 역할도 끝난다.**

### ③ 이 "설계"가 아닌 이유

작업은 범용이다 — 코드 수정, 질문 답변, 문서 작성, 영향 분석, 견적. **"설계"는 그중 하나일 뿐이다.** 단계 이름은 `요청수행` 이 맞다.

### 기록은 이 arc 밖이다

`cdp-save`(수행 v1.0 §8.2)는 `cdp-work` 안에 없다.

```
요청1 → cdp-work
요청2 → cdp-work        ← 같은 작업의 연속일 수 있다
요청3 → cdp-work
        ────────────
        작업이 끝나면 → cdp-save  (한 번)
```

**요청 하나가 작업 하나가 아니다.** 작업 기록은 세션의 작업 단위로 남기므로(수행 v1.0 §2.1), 요청마다 기록하면 이력이 파편화된다.

### 누가 `cdp-work` 를 부르는가

skill 이 절차를 품으므로 규약은 **한 줄**로 줄어든다.

```markdown
<!-- 프로젝트 레포 CLAUDE.md -->
프로젝트의 테이블·화면·API·용어·코드 상태를 알아야 하는 작업 요청은
cdp-work skill 로 처리하라. 무관한 요청에는 쓰지 마라.
```

그래도 프로토콜 §11.4의 함정은 남는다 — *"모르는 사람은 부를 생각조차 하지 않는다."* 그것을 §8의 하네스 훅이 매 요청에 상기시킨다.

## 6. ① 검토 — 흔적을 남기고 멈추지 않는다

### 6.1 출력 형태

```
【검토】
요청  PSC043 면접심사의견등록에 심사위원 연대서명 출력물을 추가한다

대상
  screen:PSC043      변경   출력물 2종 추가
  code:PS130         ?      업무구분 코드를 쓸지 미정
  screen:PSC031      참조   첨부를 읽어오지만 PSC031 은 안 바뀜 → 좌표 아님

주입  screen:PSC043 · code:PS130
```

| 규칙 | |
|---|---|
| **짧게.** 4~6줄 | 검토가 길어지면 절차가 작업을 잡아먹는다(§6.3) |
| **좌표 아닌 것도 적는다** | 무엇을 왜 제외했는지가 판정의 근거다 |
| **`?` 를 쓴다** | 애매한 것을 단정하지 않는다 |
| **주입할 좌표를 적는다** | 무엇이 주입됐는지 사후에 확인할 수 있어야 한다 |

### 6.2 출력은 감사 흔적이지 승인 관문이 아니다

**검토를 출력한 뒤 멈추지 않는다.** 바로 ②로 간다.

| | 관문으로 두면 | 흔적으로 두면 |
|---|---|---|
| 매 요청 | **정지 1회.** 절차가 작업을 잡아먹는다 | 흐름이 끊기지 않는다 |
| 판정이 틀리면 | 미리 막는다 | **출력에 보이므로 사후 교정된다** |
| 비용 | 왕복 1회 × 모든 요청 | 토큰 몇 백 |

**틀린 주입의 비용은 틀린 답이 아니라 낭비된 토큰이다.** ③이 사용자 눈앞에서 일어나므로 판정이 어긋났으면 답변에서 드러나고, 그때 *"PS130 은 아니야"* 라고 하면 된다. **모든 요청에 정지를 걸어 그것을 미리 막는 것은 비싸다.**

> **멈추는 경우는 하나뿐이다** — **요청 자체가 무엇을 원하는지 모를 때.** *"채용 쪽 정리해줘"* 같은 요청은 되묻는다. 그건 맥락 문제가 아니라 요청 문제이고, 주입도 수행도 할 수 없다.

### 6.3 검토가 작업을 잡아먹으면 안 된다

**요청된 작업이 우선이다.** 절차는 그것을 돕는 것이고, 절차 자체가 산출물이 되면 실패다.

| 상황 | ①을 이렇게 |
|---|---|
| 사용자가 이미 대상을 명시 (*"PSC043 화면에 …"*) | **압축.** 대상 한 줄 |
| 좌표 후보가 0개로 나왔다 | ②를 건너뛰고 ③으로. `주입  없음` 한 줄 |
| 요청이 크고 모호 | **되묻는다**(§6.2) |
| 이어지는 대화 (같은 작업 계속) | **skill 을 다시 부르지 않는다.** 이미 주입된 맥락을 쓴다 |

마지막 줄이 중요하다 — **`cdp-work` 는 작업 주제가 바뀔 때만 다시 부른다.** 매 턴 부르면 같은 섹션이 반복 주입되고 절차가 소음이 된다.

### 6.4 대조는 기계가 한다

①의 판단(무엇을 바꾸는가)은 LLM 이 하지만, **이름 → 정본 좌표 변환은 기계가 한다.**

```
$ ctx match "면접심사의견등록" "PS130" "서류심사"
면접심사의견등록  →  screen:PSC043    (alias 일치 · _vocab.md:41)
PS130            →  code:PS130       (정본)
서류심사          →  screen:PSC031    (alias 일치 · _vocab.md:38)
```

`ctx match` 를 `bin/ctx` 에 추가한다(수행 v1.0 §7). **판단은 LLM, 대조는 기계** — 프로토콜 §9.5의 대조 연산을 ①에 그대로 쓴다.

**`ctx match` 가 없거나 Node 가 없으면 `_vocab.md` 를 직접 읽어 대조한다.** 어휘는 사람이 읽는 마크다운이므로 폴백이 가능하다(§21).

## 7. ② 맥락 주입 — 좌표를 인자로 받는다

`cdp-load` 의 계약이 바뀐다.

| | 전 | 후 |
|---|---|---|
| 호출 | 세션 시작에 자동 | **①의 판정 뒤에 조건부** |
| 좌표 | skill 이 스스로 추출 | **인자로 받는다** — `cdp-load screen:PSC043 code:PS130` |
| 성질 | 판단 + 기계 | **기계만.** 결정론적이고 시험 가능하다 |

**추출을 ①로 옮긴 결과 `cdp-load` 가 순수해진다.** 같은 좌표를 주면 항상 같은 것을 주입하므로, 무엇이 주입됐는지 재현하고 시험할 수 있다.

주입 **내용**은 수행 v1.0 §8.1 이 정본이다. 요약하면:

```
[좌표]   table:rp_plnd_mst
[상태]   docs/테이블정의서.md ## rp_plnd_mst      ⚠ 2건 밀림
[근거]   2026-0710-A10-어댑터-v1
         · table:rp_plnd_mst          후속 3건 — 이 부분은 갱신됐을 수 있음
         · api:/adapter/a10/plan-sync 최신
[절단]   매칭 8건 중 3건 주입. 나머지 id: …
```

**관리 문서 섹션만 주입하고 작업 기록은 기본으로 넣지 않는다.** *"왜 이렇게 됐나"* 가 필요해지는 것은 ③에서이고, 그때 열면 된다.

## 8. 절차를 고정하는 층 — 둘이다

절차를 정해도 지켜지지 않으면 의미가 없다. 프로토콜 §11.2의 판단이 여기서도 그대로다.

> *"skill 은 LLM 에 대한 지시이므로 비결정적이다. 대체로 잘 지켜지지만 항상은 아니다."*
> **skill 은 편의, hook 은 보증.**

**층은 둘뿐이다.**

| 층 | 수단 | 성질 | 환경 |
|---|---|---|---|
| 1 | **`cdp-work` skill** — 절차 전체를 품는다(§5) | 비결정적 · **편의** | skill 지원 LLM |
| 2 | **git 훅** — 커밋 시점에 기계가 검사한다 | **결정론적 · 보증** | git 있는 곳 전부 |

### 8.1 `CLAUDE.md` 에 절차를 적지 않는다

**절차를 규약으로 적으면 skill 과 중복된다.** 읽는 규칙(*"섹션만 읽어라"*), 밀림 통보,
좌표별 판정, pull 선행 — 넷 다 이미 skill 안에 있다. 같은 것을 두 곳에 적으면
한쪽만 고쳐지고, 그 순간 **어느 쪽이 맞는지 알 수 없게 된다.**

남는 것은 *"작업 요청은 `cdp-work` 로 처리하라"* 한 줄인데, **그것도 중복이다.**
skill 의 `description` 이 이미 그 판정을 담고 있다.

```yaml
description: 작업 요청을 CDP 절차로 수행한다 — ① 검토 → ② 맥락 주입 → ③ 요청수행.
  프로젝트의 테이블·화면·API·도메인 용어·코드값의 **현재 상태를 알아야 하는** 요청에 쓴다.
  지식 레포와 무관한 순수 코드 문제(정규식·빌드 오류·이름 변경)에는 **쓰지 않는다.**
```

**`description` 이 발동 규칙이다.** 하네스는 skill 목록과 설명을 매 요청의 시스템
맥락에 싣는다 — 규약 파일과 달리 **주의에서 밀려나지 않는다.**

그래서 `CLAUDE.md` 에는 **설정과 사실만** 남긴다. 절차도 읽는 규칙도 없다.

```markdown
지식 레포: C:\cdp

  docs/   관리 문서 — 지금 어떤 상태인가
  work/   작업 기록 — 무슨 일이 있었나

절차는 .claude/skills/ 에 있다.
```

#### 정정 — skill 은 **작업 레포 안에** 있어야 한다

v1.1 초안은 위 규약에 *"절차는 지식 레포의 `.claude/skills/` 에 있다"* 라고
적었다. **틀렸다.**

하네스는 **프로젝트 루트의 `.claude/skills/`** 만 읽는다. 옆 폴더를 가리키는
문장은 사람에게 하는 안내일 뿐 기계적 연결이 아니다. 실측 —

```
C:\gdi 에서 claude 를 연다      → cdp-work 가 목록에 없다. 발동하지 않는다
C:\gdi> C:\cdp\bin\ctx brief   → "지식 레포를 찾을 수 없습니다"
```

두 번째도 같은 종류의 착각이었다. `C:\cdp` 는 `C:\gdi` 의 **형제**라 상위
탐색에 걸리지 않는다. 전체 경로로 불러도 `ctx` 는 cwd 에서만 위로 찾았다.

고친 것 —

| | |
|---|---|
| `ctx` 의 레포 탐색 | cwd 탐색 뒤에 **자기 위치**를 본다. `<repo>/bin/ctx.mjs` · `<repo>/tools/cdp.exe` 의 부모가 곧 레포다 |
| 배치 | skill 을 **작업 레포에도 둔다.** 사본이지만, 두지 않으면 절차 층 자체가 없다 |
| 설치 | `ctx setup <작업 레포>` — 규약과 skill 을 함께 넣고 경로를 박는다 |

**사본이 느는 것은 이 설계가 계속 피해 온 것**이지만, 여기서는 대안이 더
나쁘다. 전역 설치(`~/.claude/skills/`)와 정션은 둘 다 **그 PC 에만** 남아
팀에 퍼지지 않는다. 퍼지지 않는 것은 절차로 못 막고, 드리프트는 막을 수
있다 — 배포본에서 나오게 하고 점검표에 넣으면 된다.

그리고 §8 의 층 구분은 그대로다. 이 사본이 낡아도 **2층(git 훅)은 지식
레포 쪽에서 돌기 때문에** 보증은 흔들리지 않는다. 낡는 것은 편의 층뿐이다.

### 8.2 하네스 훅은 넣지 않는다

v1.1 초안에는 `UserPromptSubmit` 훅으로 매 요청에 절차와 레포 상태를 재주입하는
3층이 있었다. **뺀다.**

| 훅의 논거 | 검토 |
|---|---|
| *"`CLAUDE.md` 가 긴 세션에서 밀려나니 재주장해야 한다"* | **§8.1 이 만든 문제였다.** 규약에 절차가 없으면 재주장할 것이 없다. skill `description` 은 매 요청에 실리므로 밀려나지 않는다 |
| *"살아 있는 레포 상태를 싣는다"* | 밀림은 skill 이 주입한 좌표에 대해 알려준다. 그 밖의 현황은 앱의 현황 뷰(§17)와 §13 의 도달 층이 담당한다 |
| *"skill 을 부르는 것을 잊으면?"* | 훅의 두 줄도 **같은 비결정적 프롬프트 주입**이다. 비결정을 비결정으로 덮는 것이고, 그 뒤에 **결정론적인 2층이 이미 있다** |

**마지막 줄이 결정적이다.** skill 을 건너뛰고 지식 문서를 고쳤다면, git 훅이 그
결과를 커밋 시점에 잡는다 — 미등재 좌표, 없는 앵커, 밀린 `INDEX.md`.
**피해가 발생하는 경계에서 기계가 막는다.**

### 8.2.1 닫히지 않는 구멍은 ② 가 아니라 ④ 다

초안에서 이 구멍을 *"낡은 맥락으로 설계해서 틀린 답을 냈다"* 고 적었다. **틀린 서술이다.**
skill 을 부르지 않으면 낡은 맥락을 받는 것이 아니라 **아무 맥락도 받지 않는다.**

그리고 §5 가 보인 대로 **그것이 맞는 경우가 있다.** 도메인 리더의 로컬이 정본인
상황에서는 주입이 오히려 해롭다. 따라서 *"skill 을 안 불렀다"* 를 결함으로 볼 수 없다.

**진짜 구멍은 그 다음이다.**

```
리더가 자기 코드로 올바르게 작업한다        ← 맞다
프로젝트 레포에 커밋한다                    ← 맞다
지식 레포에는 아무것도 안 쓴다              ← 여기가 구멍이다
```

그 결정이 **그 사람의 머리와 로컬 코드에만 남는다.** §1 이 세었던 여섯 대화 중
1번(*"이거 왜 이래요?"*)이 되살아난다 — 물어봐야 알 수 있는 상태로 돌아간다.

### 8.2.2 기록 누락은 밀림 검출을 무력화한다

이쪽이 더 나쁘다. §6.2 의 밀림 계산은 **작업 기록의 존재를 전제한다.**

```
applied: 2026-0821-면접심사의견-개편
  그 이후 그 좌표를 건드린 작업 기록이 있나?
    있다 → 밀렸다.  화면에 뜬다
    없다 → 최신이다
```

**리더가 코드만 바꾸고 기록을 안 남기면 "없다"가 되어 최신으로 보인다.**
그 섹션을 읽은 사람은 **틀린 것을 확신 있게** 읽는다 — 밀렸다는 표시조차 없다.

| | |
|---|---|
| 밀린 섹션 | 낡았다는 **표시가 있다**. 읽는 사람이 조심한다 |
| **기록 없는 변경** | **표시가 없다.** 최신인 척한다 |

프로토콜 §9.6 의 조용한 실패와 같은 성질이다. 그것과 다른 점은 검색이 아니라
**최신성 계산이 속는다**는 것이다.

### 8.2.3 어느 층도 이것을 막지 못한다

| 수단 | 왜 안 되나 |
|---|---|
| 지식 레포 git 훅 | **발동하지 않는다.** 지식 레포에 커밋이 없다 |
| 프로젝트 레포 훅으로 기록 강요 | 오타 수정에도 기록을 요구하게 된다. 기록할 값어치가 있는지는 **판단**이다 |
| 하네스 훅 | 비결정적이다. §8.2 에서 뺀 이유가 그대로다 |

**막을 수 없으므로 보이게 한다.** 5단계(§23)의 현황 뷰에 어긋남을 싣는다.

```
[어긋남] 최근 14일  프로젝트 커밋 37 · 지식 레포 작업 기록 2
```

차단이 아니라 신호다. 37:2 가 정상인 프로젝트도 있고 비정상인 프로젝트도 있다 —
**그 판단은 팀이 한다.** 도구는 숫자를 옆에 놓는 것까지 한다.

> 리더 본인에게도 값이 있다. 6개월 뒤 그 결정을 되짚는 첫 번째 사람은 대개
> **자기 자신**이고, 그때 코드에는 *"무엇을"* 만 있고 *"왜"* 가 없다.

`bin/ctx brief`(§23 1단계)는 그대로 만든다. 사람이 터미널에서 상태를 볼 때 쓰고,
나중에 훅이 필요해지면 그 자리에 그대로 꽂힌다.

### 8.3 2층 — git 훅이 유일한 보증이다

```sh
# .githooks/pre-commit
bin/ctx check || exit 1     # 미등재 좌표 · 없는 앵커 · 프론트매터 오류
bin/ctx index               # INDEX 재생성 후 커밋에 포함
```

| 성질 | |
|---|---|
| **LLM 과 무관** | 사람이 손으로 써도, 다른 LLM 이 써도 같이 걸린다 |
| **Node 없어도 돈다** | 껍데기가 exe 로 넘긴다(§3.1) |
| **환경 무관** | git 이 있으면 있다 |

**차단은 여기서만 한다.** 세션 층에서 *"`cdp-work` 없이 Edit 금지"* 같은 것을 걸면
오타 수정이 막히고, 그러면 사람들이 그 장치를 끈다 — 프로토콜 §9.7의 안티패턴이다.
커밋은 **의도가 확정되는 시점**이라 거기서 막는 것이 자연스럽다.

> 훅은 clone 을 따라오지 않는다. `git config core.hooksPath .githooks` 를
> `README` 5분 절차에 넣는다(§15).

# 제3부 — git

## 9. 쓰기가 들어오면 pull 이 필수가 된다

뷰어는 읽기 전용이라 낡은 clone 이어도 "낡은 것을 보여줄" 뿐이었다. **쓰기는 다르다.**

| 대상 | 낡은 상태에서 쓰면 |
|---|---|
| 작업 기록 (새 파일) | 충돌 거의 없음. 파일명이 날짜+slug 라 겹치기 어렵다 |
| **관리 문서 섹션** | **남의 갱신을 덮어 없앤다** |

```
pull 안 하고 cdp-save 를 돌리면
  → 낡은 섹션 위에서 diff 를 만든다
  → 승인하고 커밋
  → 남이 어제 추가한 컬럼이 사라진 diff 가 된다
```

**갱신 diff 는 최신 섹션 위에서 만들어져야 한다.** pull 은 성능 최적화가 아니라 **정확성 요구**다.

> ## 쓰기 전에는 반드시 pull 한다. 예외 없다.

## 10. pull 을 언제 하는가

| 시점 | 동작 | 실패하면 |
|---|---|---|
| **앱 시작** | `fetch` + `pull --ff-only` | 안내만. 읽기는 계속된다 |
| **`cdp-save` 시작 (④)** | **`pull --ff-only` 필수** | **멈춘다.** 쓰기를 시작하지 않는다 |
| **`cdp-managed` 시작** | 같음 | 같음 |
| 주기적(기본 5분) · 창 포커스 | `fetch` 만 | 조용히 무시 |
| 사용자가 누름 | `pull --ff-only` | 안내 |

**`fetch` 는 자동, `pull` 은 쓰기 직전과 명시적 클릭에만.** pull 은 작업 트리를 바꾸는 연산이라 조용히 하면 사용자가 편집 중인 파일과 충돌한다.

### ff 가 안 되면 멈춘다

```
[cdp] ⛔ 원격이 앞서 있고 로컬에도 커밋이 있습니다.
      쓰기를 시작할 수 없습니다.

      로컬 커밋 2건 · 원격 커밋 3건

      터미널에서 정리하세요:
        git pull --rebase
```

**앱과 skill 은 merge·rebase·충돌 해결을 하지 않는다.** 뷰어 v0.2 §31 의 경계선을 그대로 지킨다 — 되돌리기 어려운 연산은 사람이 터미널에서 한다.

## 11. 보내기 — commit 과 push

`cdp-save` 가 만드는 커밋은 하나다(수행 v1.0 §8.2-7).

```
작업 기록 1개 + 관리 문서 N개  →  커밋 1개
```

| 단계 | 누가 |
|---|---|
| `git add` + `commit` | **skill**. 훅이 `ctx check` 를 돌린다 |
| `push` | **앱 또는 사람.** skill 은 push 하지 않는다 |

**skill 이 push 하지 않는 이유** — 커밋은 되돌릴 수 있지만 push 는 남의 눈에 들어간다. 앱 상단에 `⬆ 보내지 않은 커밋 2건 [보내기]` 로 남고 사람이 누른다.

**단, 오래 안 보내면 경고한다.** 안 보낸 커밋은 남에게 존재하지 않는 것과 같다(§1의 5번).

```
⚠ 보내지 않은 커밋 3건 · 가장 오래된 것 2일 전
   보내지 않으면 다른 사람에게는 이 작업이 없는 것과 같습니다
```

## 12. 점유 — 두 번 하지 않기

> ### 정정 — **`진행중` 을 없앴다** (2026-09-08)
>
> 아래 절 전체가 무효다. 지식공유문서는 작업의 **완료**에서 발생하고,
> **항상 그 시점에 완료된 것이 넘어온다.** 끝나지 않은 일은 문서가 아니다.
>
> 그 상태를 두면 지식 레포가 **할 일 목록** 노릇을 하기 시작한다. 불변인
> 사건과 가변인 상태가 한 폴더에 섞이면 둘 다 안 맞게 된다 — 그것이 `미결`
> · `제안` 을 뺀 이유와 같은 이유다. `진행중` 만 예외로 남길 근거가 없었다.
>
> `status` 에 **쓸 수 있는 값이 하나도 없다.** `확정`·`완료` 는 기본값이라
> 파싱 경계에서 지우고, 나머지는 `ctx check` 가 오류로 막는다.
>
> 같은 좌표를 동시에 건드릴 걱정은 남는다. 그것은 지식 레포가 아니라
> **일감 분배**의 문제다 — 문서 형식으로 풀려던 것이 잘못이었다.
>
> 아래는 그 시점의 판단으로 남긴다.


§2 의 둘째 낭비. **새 개념을 만들지 않고 `status` 값 하나를 더한다.**

```
① 작업 시작 — 작업 기록을 status: 진행중 으로 먼저 커밋·push
     id: 2026-0903-계획서-이력테이블
     status: 진행중
     touches: [table:rp_plnd_mst]
     (본문 비어 있음)

② 작업

③ cdp-save — status: 확정 으로 바꾸고 본문·파생을 채워 커밋
```

| 규칙 | |
|---|---|
| **진행중 문서는 검색에서 제외** | 본문이 비어 있어 노이즈다 |
| **좌표 트리·현황에는 표시** | `table:rp_plnd_mst  ● kjsa 진행중` |
| **`ctx check` 는 진행중에 본문·좌표를 요구하지 않는다** | 아직 안 끝났다 |
| **3일 넘게 진행중이면 경고** | 잊고 커밋 안 한 것일 수 있다 |

**비용은 커밋 한 번이다.** 폐쇄망 비동기에서 같은 좌표 중복은 거의 확실히 발생하고, 그 비용이 커밋 한 번보다 훨씬 크다.

> **선택이다.** 혼자 하는 프로젝트나 좌표가 안 겹치는 팀은 안 써도 된다.

## 13. 미결이 도달하게 한다

§2 의 첫째 낭비. 프로토콜 §8.3 은 *"미결만 필터하면 그것이 결정 목록이다"* 라고 했다. **목록은 있는데 도달하지 않는 것이 문제다.**

### 13.1 미결은 작성자가 관리한다

**별도의 결정권자를 두지 않는다.** 작업 기록을 쓴 사람이 그 미결을 관리한다.

```
status: 미결
author: kjsa        ← 이 사람이 관리한다.  다른 필드는 없다
```

| | |
|---|---|
| 도달 대상 | `author`. 프론트매터에 이미 있다 |
| 새 필드 | **없다.** 담당자·결정권자 필드를 추가하지 않는다 |
| 사용자가 끼어드는 지점 | **작성자 하나뿐이다** |

**필드를 늘리지 않는 것이 이득이다.** 담당자 필드를 만들면 그것을 채우는 일이
새로 생기고, 비면 미결이 아무에게도 안 간다. 작성자는 **비어 있을 수 없다** —
쓴 사람이 있어야 기록이 있다.

> 작성자가 결정권자가 아닌 경우에도 마찬가지다. **작성자가 결정권자에게 가져가는
> 것까지가 작성자의 일이다.** 도구가 조직을 대신 뚫지 못하고, 뚫는 척하면
> "시스템에 올렸으니 내 일은 끝"이 된다.

### 13.2 도달하는 세 층

| 층 | 도달 방식 |
|---|---|
| 1 | pull 하면 현황 화면 최상단 — **내가 쓴 미결이 맨 위** |
| 2 | 대기 일수 표시. 오래된 것이 위로 |
| 3 | **7일 넘으면 전원의 현황에 뜬다** — 작성자가 놓치면 팀이 본다 |

**3층이 중요하다.** 1·2층은 작성자가 앱을 열어야 작동하므로, 작성자가 앱을 안 여는
동안은 아무 일도 일어나지 않는다. 3층이 그것을 팀으로 넘긴다.

> 초안에는 *"`ctx brief` 가 매 요청에 건수를 싣는다"* 는 4층이 있었다. §8.2 에서
> 하네스 훅을 빼면서 함께 뺐다. **미결 도달을 세션 층에 의존하지 않는다** — 앱을
> 여는 사람과 세션을 쓰는 사람이 같다는 보장이 없고, 폐쇄망에서는 하네스가 없을 수 있다.

> **알림은 만들지 않는다**(뷰어 v0.2 §22.2). 무시되기 시작하면 되돌릴 수 없고, 그 시점에 *"알림이 안 왔으니 없는 것"* 이라는 더 나쁜 오해가 자리 잡는다.

# 제4부 — 앱

## 14. 앱의 역할 — 계기판이지 편집기가 아니다

뷰어 v0.2 §31 은 문서 편집을 비목표로 못박았다. 근거는 *"작성은 skill 의 일이다. 앱이 하면 좌표 대조·훅 검증을 우회하는 경로가 생긴다"* 였고 **지금도 유효하다.**

| 앱이 하는 것 | 앱이 하지 않는 것 |
|---|---|
| 읽기 (뷰어 v0.2 전부) | **문서 편집·생성** |
| **git pull / push / status** | merge · rebase · 충돌 해결 |
| **현황 표시**(§16) | 이슈 트래커 · 할당 |
| **점검**(§17) | 자동 수정 |
| **매뉴얼**(§15) | — |
| skill 실행 **유도** | skill 실행 자체 |

### skill 실행 유도

앱은 AI 세션을 띄우지 않는다. **무엇을 실행하면 되는지 알려주고 복사해 준다.**

```
밀린 섹션 4건

   프로젝트 세션에서:
   ┌────────────────────────────────────┐
   │ cdp-managed 로 밀린 섹션 정리해줘   │  [복사]
   └────────────────────────────────────┘
```

**앱이 Claude Code 를 직접 부르지 않는 이유** — 폐쇄망에 무엇이 설치돼 있을지 모른다(§3). 사람이 자기 도구에 붙여넣는 편이 확실하다.

## 15. 매뉴얼 — 물어볼 사람이 없다

폐쇄망 PC 에 clone 만 받은 사람이 **처음 5분에 막히면 그것으로 끝이다.**

### `README.md` — 5분

```markdown
# 지식 레포

## 이게 뭔가
프로젝트의 "지금 어떤 상태인가"와 "왜 그렇게 됐나"가 전부 여기 있다.
사람에게 묻지 않고 여기서 찾는다.

## 5분 안에 시작하기
1. tools/cdp.exe 를 더블클릭한다 (없으면 `npx cdp`)
2. 이 폴더 경로를 넣는다
3. 왼쪽에서 좌표를 고른다 → 지금 상태가 나온다
4. `Ctrl+K` 로 자연어 검색 — "연구계획 테이블 최근 변경"

## 작업할 때
프로젝트 세션에서 요청하면 AI 가 ① 검토 → ② 맥락 주입 → ③ 설계 순서로
처리한다. 절차는 CLAUDE.md 에 있다. 자세한 것은 MANUAL.md.
```

### `MANUAL.md`

목차는 부록 A. **작업 절차와 좌표 붙이기가 가장 길다** — 그 둘이 갈리면 좌표계가 무너진다(프로토콜 §9.4).

**앱이 첫 실행 시 `README.md` 를 본문에 띄운다.** 경로 지정 다음 화면이 빈 목록이 아니라 매뉴얼이다.

> **매뉴얼은 좌표를 갖지 않는다.** 관리 문서도 작업 기록도 아니다 — 저장소 사용법이지 프로젝트 지식이 아니다.

## 16. 현황 — 세 번째 뷰

수행 v1.0 §14 는 뷰를 **대상·작업** 둘로 줄였다. **현황**을 더해 셋으로 한다 — 앞의 둘은 문서 탐색이고 이것은 **상태 관리**다.

```
현황 (⌘3)
┌──────────────────────────────────────────────────────────────┐
│  받기·보내기                                                  │
│    ⬇ 원격에 새 작업 3건                          [가져오기]   │
│    ⬆ 보내지 않은 커밋 1건 · 어제                  [보내기]    │
│                                                              │
│  내 좌표에 걸린 미결                        2건               │
│    47일  연심회 상태값 확정 대기        table:rp_rdc_mst      │
│     9일  결재선 예외 처리               screen:SEC011         │
│                                                              │
│  오래 방치된 미결 (7일+, 담당 불분명)        1건               │
│    22일  A10 재처리 책임 범위                                 │
│                                                              │
│  진행중                                     2건               │
│    kjsa      table:rp_plnd_mst      2시간 전                 │
│    임동현     screen:PSC043          ⚠ 3일 전                 │
│                                                              │
│  밀린 관리 문서 섹션                        4건   [따라잡기]   │
│    docs/테이블정의서.md   ## rp_plnd_mst      2건            │
│                                                              │
│  점검                                                        │
│    ✓ 훅 설치됨 · skill 3개 · bin/ctx 실행 가능                │
│    ⚠ 미등재 좌표 1건 · 빈 섹션 6건                            │

```

**위에서부터 "지금 내가 해야 할 일" 순서다.** 받기·보내기가 맨 위인 이유는 그것이 §1 의 3~6번을 나르는 유일한 채널이기 때문이다.

## 17. 점검 — 설치가 됐는지 사람은 모른다

폐쇄망에서 clone 만 받으면 **훅이 안 걸린다.** `.git/hooks/` 는 clone 에 따라오지 않는다(프로토콜 §11.2).

| 항목 | 검사 | 안 되어 있으면 |
|---|---|---|
| git 훅 | `core.hooksPath` == `.githooks` | **[설정하기]** 버튼 하나 |
| **하네스 훅** | 프로젝트 레포 `.claude/settings.json` 에 `ctx brief` 가 있는가 | **[설정 복사]** — §8.2 |
| `bin/ctx` | 실행 가능한가 · `--json` 지원 | 내장 검사로 폴백(뷰어 v0.2 §12) |
| skill | `.claude/skills/` 에 3개 | 목록만 표시 |
| `CLAUDE.md` | 작업 절차(§8.1)가 있는가 | **[템플릿 복사]** |
| Node | `bin/ctx` 실행에 필요 | 없으면 내장 검사로 |

**git 훅 설정만 앱이 대신 해준다.** `git config core.hooksPath .githooks` 한 줄이고, 이게 안 되면 프로토콜 §11.2 의 보증이 통째로 빠진다. **하네스 훅과 `CLAUDE.md` 는 프로젝트 레포 쪽이라 복사만 준다** — 앱이 남의 레포를 고치기 시작하면 §14 의 경계가 무너진다.

## 18. 화면 정리

```
대상 (⌘1)   좌표 트리 → 관리 문서 섹션 + 그 좌표를 바꾼 작업 목록
작업 (⌘2)   시간순 작업 기록. 필터: 미결 · 진행중 · 작성자 · 기간
현황 (⌘3)   §16
⌘K          검색 · 이동
?           매뉴얼
```

상단 바에 git 상태가 상주한다.

```
┌──────────────────────────────────────────────────────────────────┐
│ 지식레포   ⬇3 ⬆1   ⌘K 검색                          ☾  ⚙        │
```

| 표시 | 뜻 |
|---|---|
| `⬇3` | 원격에 새 커밋 3건 — 안 받으면 남의 작업을 모른다 |
| `⬆1` | 안 보낸 커밋 1건 — 안 보내면 남에게 내 작업이 없는 것과 같다 |
| 둘 다 0 | **표시가 사라진다.** 정상은 조용하다(뷰어 v0.2 §13-①) |

## 19. 비목표

뷰어 v0.2 §31 을 잇는다. **범위가 넓어졌으므로 경계를 더 분명히 긋는다.**

| 안 하는 것 | 이유 |
|---|---|
| **문서 편집·생성** | 작성은 skill 의 일. 앱이 하면 좌표 대조·훅 검증을 우회한다 |
| **merge · rebase · 충돌 해결** | 되돌리기 어렵다. 막고 안내한다(§10) |
| **자동 push** | 남의 눈에 들어간다. 명시적 클릭(§11) |
| **절차를 훅으로 강제** | 정당한 작업이 막히면 훅을 끈다(§8.2) |
| **할당**(§1 의 6번) | 조직 구조와 얽힌다. CDP 가 답할 문제가 아니다 |
| **이슈·칸반·간트** | 프로젝트 관리 도구를 만들지 않는다 |
| **알림·트레이 토스트** | 무시되기 시작하면 되돌릴 수 없다 |
| **AI 질의응답** | `cdp-load` 의 일. 검증되지 않은 두 번째 검색 경로 |
| **남의 레포 자동 수정** | git 훅 설정 한 줄만 예외(§17) |
| **사내 서버 모드** | 인증·권한 설계가 부활한다(뷰어 v0.2 §5.3) |

### 할당의 도입 신호

| 신호 | 확인 |
|---|---|
| 미결이 "누구 것인지 몰라서" 7일 넘게 방치되는 일이 반복 | 현황 3층(§13) 통계 |
| 진행중 표시가 중복 작업을 못 막는다 | 중복 사례 기록 |

둘 다 관측되면 `assignee` 필드를 검토한다. 프로토콜 §8.3 — *"없어서 오적용이 났다"* 로 추가한다.

# 제5부 — 폐쇄망

## 20. 이관 단위와 절차

**`git bundle` 하나로 옮긴다.** 폴더 복사보다 낫다 — 이력이 따라오고 되가져올 때 증분만 옮긴다.

```
[망 밖]
  git bundle create knowledge.bundle --all

[망 안]
  git clone knowledge.bundle knowledge-repo
  cd knowledge-repo
  git config core.hooksPath .githooks
  tools/cdp.exe --repo .

[되가져오기]
  git bundle create back.bundle <마지막이관커밋>..HEAD
```

## 21. LLM 이 없거나 skill 을 못 부를 때

**skill 은 마크다운 지시문이다.** 이것이 폐쇄망에서 결정적이다.

| 상황 | 동작 |
|---|---|
| Claude Code 있음 | `CLAUDE.md` 절차 + skill + 하네스 훅 전부 (§8) |
| 로컬 LLM, skill 미지원 | **`CLAUDE.md` 를 프롬프트 앞에 붙이고, `SKILL.md` 를 열어 붙여넣는다.** 지시문이지 API 가 아니다 |
| LLM 없음 | `ctx new` 로 템플릿, `ctx match` 로 좌표, `ctx where` 로 대상 문서. 사람이 쓴다 |

**세 경우 모두 `bin/ctx` 와 git 훅은 동일하게 동작한다.** 보증 층(§8 의 2층)이 LLM 과 무관하다는 것이 여기서 값을 한다.

> **앱이 `CLAUDE.md` 와 skill 본문을 화면에 띄운다.** 매뉴얼에서 누르면 렌더되고 `[전체 복사]` 가 붙는다. 붙여넣기가 정식 경로 중 하나다.

# 제6부 — 실행

## 22. 이름

`ctx-view` 는 범위를 못 담는다. **`cdp`** 로 바꾼다.

| | |
|---|---|
| 실행 파일 | `cdp.exe` · `npx cdp` |
| CLI | `cdp --repo <경로>` |
| `bin/ctx` | **그대로.** 저장소 도구는 `ctx` 가 맞다 |

## 23. 단계 계획

수행 v1.0 §17 (9일) 다음이다 — 기록 규약이 없으면 협업 층이 실을 것이 없다.

| 단계 | 작업 | 소요 | 검증 |
|---|---|---|---|
| 1 | **`cdp-work` skill(§5) + `ctx match`** | 1일 | **①검토가 4~6줄로 나오는가 · 좌표 아닌 것도 적는가** |
| 2 | `cdp-load` 를 좌표 인자 방식으로(§7) | 반일 | 같은 좌표에 같은 주입이 재현되는가 |
| 4 | git 계층 — `fetch`/`pull --ff-only`/`status`/`push` | 1일 | ff 불가 시 **멈추고 안내**하는가 |
| 5 | **쓰기 전 pull 강제**(§9~10) | 반일 | pull 없이 `cdp-save` 가 시작되지 않는가 |
| 6 | 현황 뷰(§16) | 1일 | 밀림·미결·진행중이 한 화면에 |
| 7 | 점검(§17) + git 훅 설정 버튼 | 반일 | clone 직후 훅 미설치가 잡히는가 |
| 8 | `status: 진행중`(§12) | 반일 | 진행중이 검색에 안 걸리는가 |
| 9 | 미결 도달 3층(§13) | 반일 | 7일 넘은 것이 전원의 현황에 뜨는가 |
| 10 | **`README.md` · `MANUAL.md`** | 1일 | **처음 보는 사람이 5분 안에 문서를 여는가** |
| 11 | skill 을 지식 레포로 이동 · `CLAUDE.md` 를 설정만 남기고 축소(§8.1) | 반일 | clone 하나로 절차가 따라오는가 |
| 12 | `CLAUDE.md`·skill 본문 렌더 + 복사(§21) | 반일 | 붙여넣기 경로가 동작하는가 |
| 13 | `git bundle` 이관 실측 | 반일 | **망 안에서 clone → 훅 → 앱 → 작업까지** |
| 14 | 이름 변경 | 반일 | 설정 이관 |

**합계 약 9.5일.**

**1단계와 10·13단계가 관문이다.** 1단계는 절차가 실제로 지켜지는지, 10·13은 **처음 보는 사람이 5분 안에 못 시작하면 폐쇄망에서는 그것으로 끝**이기 때문이다.

| 리스크 | 심각도 | 대응 |

```markdown
## 업무 맥락

지식 레포: ../knowledge-repo

## 작업 절차

작업 요청을 받으면 이 순서로 처리한다.
**요청된 작업이 우선이고 아래는 그것을 위한 절차다.**

① 검토 — 먼저 4~6줄로 답하라

     대상  (이 작업이 바꿀 것. 참조만 하는 것은 "참조"로 적고 제외)
     주입  (필요/불필요 + 한 줄 근거)
   이 단계에서 지식 레포의 관리 문서·작업 기록을 읽지 마라.
   이름 대조는 `ctx match "이름" …` 을 쓴다.

② 주입 — ①이 "필요"면 cdp-load <좌표…> 를 실행한다.
   불필요면 건너뛰고 ③으로 간다.

③ 설계·수행 — 주입된 상태를 근거로 답한다.
   관리 문서가 밀렸다고 나왔으면 그 사실을 답변에 포함하라.

④ 기록 — 작업이 끝나면 cdp-save.
   cdp-save 는 시작할 때 반드시 git pull 한다.
   pull 이 안 되면 쓰기를 시작하지 마라 — 남의 갱신을 덮는다.

이어지는 대화에서 작업 주제가 그대로면 ①②를 반복하지 마라.
사용자가 대상을 이미 명시했으면 ①을 한 줄로 압축하라.
요청이 크고 모호하면 ①에서 되묻고 ②③으로 가지 마라.
```
