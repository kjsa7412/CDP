## 0. 한 줄

**큐레이션은 「아직 반영 안 된 기록」 을 다룬다. 그런데 정본은 반영된 뒤에도 시간이 지나며 어긋난다 — 근거 없는 섹션 · 다른 섹션과 복제된 문단 · 서술이 쌓인 비대한 섹션 · 일지형 · 기록 없이 바뀐 현실 · 틀리게 반영된 것.** 지금 제품에는 이것을 **재는 자리도, 되돌릴 원천도** 없다. `ezipez_cdp` 실측으로 섹션 681 중 **192(28%) 는 그 좌표를 건드린 기록이 하나도 없고**(14.6만 자 — 기록만 옮겨 다시 세우면 사라진다), **약 130(19%) 은 같은 산문 줄을 다른 섹션과 나눠 갖고**(⚠ 함정 한 줄이 12 섹션에), **117 은 본문이 40줄을 넘으며**, 기록 **500(45%) 은 좌표가 0 이라 좌표로 찾아지지 않는다.** **권장안은 넷이다 — ① 진단(`core/drift.js` · 계산만 · 화면과 도구) ② 원천 채우기 — 근거 없는 섹션은 **기계가** 원문 그대로 「정본 스냅샷 기록」 으로 뜨고(LLM 이 쓰지 않는다), 좌표 0 기록은 **LLM 이 좌표정정 기록 초안**을 만든다 ③ 재유도 — 고를 좌표 묶음의 원천 전부(기록 · 스냅샷 · 기준선)에서 섹션을 다시 쓰고 **재큐레이션**(이미 있는 「가장 늦은 판정이 이긴다」)으로 남긴다 ④ 전면 재건 — ②를 끝낸 레포는 `repo new --records-from` 으로 잃는 것 없이 다시 세운다.** 새 스킬 `cdp-rebuild`(큐레이터) 하나와 기록 종류 하나(`snapshot`)가 늘고, 쓰는 길은 그대로 `save` 하나다.

## 1. 운영자의 말 · 검토의 틀

> 기존의 작업문서와 관리문서를 기반으로 다시 작업문서를 생성하는 리빌딩 스킬이 있었으면 좋겠다.
> 목적은 둘 다(정본 다시 세우기 · 기록 정리). 대상은 제품 기능. 스냅샷은 권장안(섹션 단위)으로. 큐레이션은 미반영 좌표를 위한 것이지만 **시간이 흘러서 관리문서의 싱크가 깨지는 경우를 위함이다. 더 큰 범위인 것이다.**

| **B 원천** | 정본을 다시 세울 재료가 기록에 다 있나 · 없으면 무엇으로 채우나 · 누가 쓰나 | 깊게 |

| E 제품 | 스킬 · 도구 · 화면 · 설명서 · 시험 | 보통 |

심각도 — **P0** 데이터가 조용히 틀어진다 · **P1** 되돌릴 수 없게 잃는다 · **P2** 되지만 손이 많이 간다 · **P3** 잔손.

## 5. 권장안

### 5.1 진단 — `core/drift.js` (계산만 · I8)

`loadRepo` 에서 섹션마다 D1~D5 신호를 계산한다. 저장하지 않는다.

| 신호 | 계산 | 낼 자리 |
|---|---|---|
| `unsourced` (D1) | 그 좌표를 `touches` 한 사람의 기록 · 스냅샷 · 기준선이 없다 | 섹션 · 문서 · 레포 합계 |
| `duplicated` (D2) | 정규화한 산문 문장(40자↑)이 다른 섹션에도 있다 → 짝 좌표 목록. **뺀다** — 표 행 · 경과 줄 · 인용(`>`) · 레포가 정한 반복 줄(`**SoT**` 가리킴처럼 — 문턱: 레포 섹션의 N% 넘게 반복되면 규약으로 본다) | 섹션(짝) |
| `oversize` (D3) | 경과 앞 본문 줄 수 > 서식 종류별 문턱(대장 40 · 정의 25 — cdp-curate 의 숫자를 데이터로) | 섹션 |
| `diary` (D4) | 경과 밖 날짜 시작 줄 · 「YYYY-MM-DD … 했다」 | 섹션 |
| `unreachable` (D5) | 좌표 0 · `keep` 아닌 사람의 기록(전환 기록이 keep 으로 둔 것은 따로 센다) | 레포 합계 · 기록 목록 |

- **MCP** — `brief` 에 합계 한 줄(`[CDP] 어긋남: 근거 없음 192 · 복제 130 · 비대 117 …`) · 큐레이터 도구 `drift({ doc?, coord? })` 가 섹션별 신호와 짝을 낸다.
- **화면** — 레포 관리에 「진단」 탭(문서별 막대 · 섹션 표 · 「이 묶음 다시 세우기」 → 에이전트 지시 복사). 문서 화면의 섹션 머리에 칩(「근거 없음」 · 「복제 3」) — 「미반영 n」 칩과 같은 자리.
- **`check` 에는 넣지 않는다** — 다 경고 감이고 수백 건이다. 검사 경고가 수백이면 아무도 안 본다(오류를 함부로 늘리지 않는다 — 옛 원칙 6).

### 5.2 원천 채우기 — 정본을 기록으로 되돌린다

**(가) 스냅샷 — D1 · 기계가 쓴다.** 근거 없는 섹션을 **원문 그대로** 기록 하나로 뜬다. 섹션 하나에 기록 하나(운영자 결정).

| 필드 | 값 | 왜 |
|---|---|---|
| 종류 | 새 기록 종류 `snapshot`(`recordKind`) — `baseline` 처럼 기계 기록 | 사건이 아니라 **그때의 상태**다. 사람의 작업 기록과 섞이면 「언제 · 왜」 를 지어낸 것이 된다 |
| `id` | `<YYYY-MMDD>-스냅샷-<좌표 슬러그>` | |
| `date` | 그 섹션 줄들의 **마지막 커밋 시각**(`git blame` 의 최댓값) — 오늘이 아니다 | 편입 규칙과 같다 — 오늘이면 이력 순서가 뒤집힌다 |
| `touches` | 그 좌표 하나 | |
| `source` | `docs/<문서>.md@<sha>#<헤딩>` | 어디서 떴나 |
| 본문 | 섹션 `content` 원문(헤딩 · applied 주석 · 기준선 블록 제외) | **LLM 이 다시 쓰지 않는다** — 원천층에 합성이 들어가면 그 위의 재유도가 환각을 원천으로 삼는다 |
| 판정 | 같은 save 가 큐레이션 기록 하나로 **스냅샷 전부를 `reflect`(into = 자기 좌표)** 로 둔다 | 이미 섹션에 있는 내용이다 — 대기열에 세우면 192건이 쏟아진다. `ctx migrate` 의 전환 기록과 같은 수 |

- 쓰는 길 — `save` 에 기계 입력 `snapshot: [{ coord }]`(큐레이터만 · I6) 하나를 더한다. 서버가 섹션을 읽어 기록을 짓는다 — **클라이언트가 본문을 보내지 않는다**(보낸 본문이 섹션과 다르면 스냅샷이 아니다). `ctx rebuild snapshot <레포> [--doc] [--dry]` 는 그 입력을 지어 서버에 보낸다(`baseline push` 와 같은 모양).
- 레포를 처음 v1.0 으로 올릴 때 한 번 · 그 뒤로는 진단의 `unsourced` 가 0 이 아닐 때. 한 번 뜬 섹션은 더 이상 `unsourced` 가 아니다.

**(나) 좌표 보완 — D5 · LLM 이 초안 · 사람이 승인.** `cdp-rebuild` 의 첫 단계. `unreachable` 기록을 주제로 묶어(20건 안팎) 읽고, 기록마다 **좌표정정 기록**(이미 있는 규약 — `supersedes` · touches 만 · `date` = 원 기록의 날 · 본문은 무엇이 왜 빠졌나 한 줄과 원 기록 링크) 초안을 판정표로 보인다. **원 기록은 그대로다(I3).** LLM 의 판단은 「좌표 몇 개」 로 좁다 — 본문을 쓰지 않는다. 승인된 정정 기록은 보통의 기록이라 **대기열에 선다** → (다)로 이어진다.

- 「옮길 사실이 없다」(회의 잡담 · 버린 안)면 정정하지 않고 판정표에 `keep 후보` 로만 적는다 — 그 판단은 큐레이터의 `keep` 이다.
- writer 도 정정 기록을 쓸 수 있으므로(지금 규약) 쓰는 권한은 늘지 않는다. 다만 수백 건을 묶는 절차는 큐레이터 스킬에 둔다.

### 5.3 재유도 — 고른 묶음을 원천에서 다시 세운다 (D2 · D3 · D4 · D7)

`cdp-rebuild` 의 둘째 단계. **단위는 좌표 묶음**(문서 하나 · 진단의 복제 짝 · 사람이 고른 좌표들).

```
① 모은다   묶음의 좌표마다 — 그 좌표를 건드린 기록 전부(판정 무관 · 날짜순) · 스냅샷 · 기준선 블록 · 지금 섹션 · refs
② 다시 쓴다 섹션마다 원천에서 현재형으로 — 「사실 하나에 정본 자리 하나」(복제 짝은 한 자리를 정하고 나머지는 좌표로 건다)
           · 서술은 빼고(기록의 것) · 경과는 원천 기록 링크 한 줄씩 · 기준선 블록은 그대로
③ 견준다   지금 섹션 ↔ 다시 쓴 섹션 diff + 「사라지는 사실」 목록(지금 섹션에 있는데 어느 원천에도 없는 문장)
④ 판정     큐레이터가 섹션마다 — 바꿈 · 그대로 · 사라지는 사실 살림(→ 그 문장의 원천이 없다는 뜻이니 스냅샷부터)
⑤ 남긴다   재큐레이션 save — 큐레이션 기록 하나 · curates = 묶음의 원천 기록 전부(verdict reflect · into) · sections
```

- **쓰는 길은 이미 있다** — 재큐레이션(가장 늦은 판정이 이긴다)과 `sections`. 서버 변경 없이 스킬로 시작할 수 있다.
- **③의 「사라지는 사실」 이 안전판이다.** 다시 쓰면서 지식이 빠지는 것을 원천 대조로 드러낸다 — D1 이 남아 있으면 여기서 걸린다. 그래서 순서는 **5.2(가) → 5.3** 이다.
- 큐레이션 기록에 `tags: [rebuild]` 와 진단 신호 요약을 단다 — 이력에서 「리빌딩으로 다시 쓴 섹션」 을 가른다.

### 5.4 전면 재건 — 새 레포 (D8 · 여러 D 가 겹친 레포)

지금 길(`repo new --records-from` → 큐레이션) 그대로다. **달라지는 것은 하나** — 옛 레포에서 5.2(가)를 **먼저** 돌리면 `--records-from` 이 스냅샷도 옮기므로 Q2 의 14.6만 자를 잃지 않는다. 옮긴 스냅샷은 새 레포에서 대기열에 선다(새 레포에는 섹션이 없다 — 「큐레이션부터 다시」 의 뜻). 비교 보고 — 옛 레포 ↔ 새 레포의 섹션 수 · 글자 수 · 사라진 좌표(이행 절차의 리허설 값 표와 같은 모양).

### 5.5 주기 — 「시간이 흘러서」

진단이 계산이므로 **늘 보인다**(화면 · `brief`). 리빌딩을 일정으로 돌리지는 않는다 — 다시 쓰기는 큐레이터의 승인이 있어야 한다(cdp-curate 「승인 없이 커밋하지 않는다」). 대신 `brief` · 화면이 「어긋남이 지난번보다 늘었다」 를 낼 수 있도록 **계산만으로 되는 비교**(마지막 `rebuild` 큐레이션 기록 시점의 신호 합계를 그 기록 본문에 적어 두고 지금과 견준다)를 둔다 — 상태를 저장하지 않는다(I8).
