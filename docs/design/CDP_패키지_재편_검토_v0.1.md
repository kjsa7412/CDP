## 0. 한 줄

**지금 패키지 셋 중 둘(`project_1` · `project_2`)은 `dpms` 를 이름만 바꿔 복제한 것이라 고를 이유가 없고, 남은 하나는 이름이 사내 원천 폴더(`DPMS`)다.** 콘솔 「새 지식 레포」 에서 고를 수 있는 것은 사실상 「공공 SI 40종」 하나뿐이고, 공공 SI 가 아닌 팀(애자일 제품팀 · 클라우드 운영팀 · AI 서비스팀)은 40종을 붓고 대부분을 지우거나 아무것도 없이 손으로 세워야 한다. **권장안 — 패키지를 「프로젝트 이름」 이 아니라 「일하는 방식」 으로 나눈 다섯으로 둔다.** `blank`(빈 레포) · `public-si`(옛 dpms · 공공 SI 산출물) · `agile-product`(애자일 제품 개발) · `cloud-native`(클라우드 네이티브 서비스 운영) · `ai-service`(AI · LLM 서비스). 새 셋은 「작업 기록이 곧 ADR」 · 「코드가 정본인 것은 옮기지 않는다」 를 원칙으로 12~14종씩만 둔다. 도구 · 판정은 그대로이고, 바뀌는 것은 `agent/packages/` 와 그 이름을 부르는 시험 · 하네스 · 설명서다.

### 2.4 타입 이름의 문자 제약 — 새 패키지가 지켜야 하는 것

| 자리 | 받는 것 |
|---|---|
| `core/vocab.js` `COORD` | `[A-Za-z가-힣][A-Za-z0-9가-힣_-]*` — 대문자 영문 시작도 받는다 |
| `core/tools.js` `RE_COORD`(MCP) · `core/managed.js` `RE_PATTERN_TYPE`(save 의 `managed`) | **영문이면 소문자만**, 한글 첫 글자면 뒤에 영문 · 숫자 — `C:/abs/path` 를 좌표로 받지 않으려고 |

그래서 **`API명세:` · `SLO:` · `ADR:` 같은 타입은 어휘에는 써지는데 MCP · 서버형 save 가 `E_COORD` 로 거절한다.** 새 패키지의 타입은 **한글로 시작**한다 — dpms 가 정한 규칙(「정본 문서 이름에서 서식 꼬리를 떼고, 떼서 보편적인 낱말이 되면 떼지 않는다」)과도 맞는다. 정규식을 넓히는 것은 이 작업의 일이 아니다(§6).

## 4. 결정 P1~P12 — 권장으로 닫는다

| # | 결정 | 권장 | 왜 |
|---|---|---|---|
| **P1** | 패키지 수 · 구성 | **다섯** — `blank` · `public-si` · `agile-product` · `cloud-native` · `ai-service` | 운영자의 「빈 1 · DPMS 1 · 트렌드 몇 개」. 트렌드는 셋 — 2026 의 개발 팀이 가장 흔히 서는 자리(제품을 스프린트로 · 서비스를 클라우드에서 · AI 기능을 붙여서). 넷째(데이터 플랫폼 · 모바일)는 표본이 생길 때 |
| **P2** | `dpms` 의 새 이름 | **`public-si`** · 제목 「공공 SI 산출물 세트」 · 판 1.1.0 | 내용(공공 SW 사업 산출물 — 사업관리 · 분석 · 설계 · 구현 · 시험 · 이행)을 말한다. 방법론 이름(`waterfall`)은 문서 세트를 말하지 못한다. 이름 바꿈은 `ctx package rename`(폴더 · 매니페스트 · README 제목을 한 번에) — 이미 있는 도구를 쓴다 |
| **P3** | `public-si` 안의 원천 기록 | **소스 레포의 `docs/attic/dpms-패키지/README.md` 로 옮긴다** — 패키지에는 「어디서 왔나」 한 단락만 | 「만든 기록은 받는 사람에게 가지 않는다」(agent/README). 옮기는 것은 README 두 절(「왜 40종인가」 · 「서식 원본이 없는 15종」 — 원천 사업의 폴더 · 실물을 센 것)이고, 원천 이름이 박힌 줄(`_vocab.md` 한 문장 · `관리번호.md` 의 폴더 경로)은 일반의 말로 고친다. `관리번호.md` §5(원본 대장과 다르게 준 번호)는 **남긴다** — 이름이 없고, 발주처가 원본 번호로 말을 맞출 때 되돌리는 법이라 받는 사람의 것이다. **예시 값(연구과제 업무)은 고치지 않는다** — 이름 바꿈의 범위가 아니다(§6) |
| **P4** | 복제 둘 | **지운다** | Q1 · Q3. 다중 패키지 경로는 다섯이 잰다 |
| **P5** | 「이름은 자리표시자」 정책 | **「패키지는 방식별 서식이다 · 프로젝트 맞춤은 레포 안에서」 로 바꾼다** — `rename` 은 도구로 남긴다 | K4. 패키지 README · 콘솔 › 서버 한 줄 · 개발자 설명서 · 관리자 설명서 |
| **P6** | 새 패키지의 타입 이름 | **한글로 시작** · 문서 이름에서 서식 꼬리를 뗀다 · 떼서 보편적이면 안 뗀다 · API · SLO 같은 영문 약어는 한글 낱말로(`인터페이스` · `서비스수준`) | §2.4 — MCP · save 가 대문자 영문 타입을 받지 않는다. 같은 규칙이 dpms 에 있다 |
| **P7** | 새 패키지의 원칙 | **① 작업 기록이 ADR 이다** — ADR 문서를 따로 두지 않는다(`work/` 는 불변 · 결정을 뒤집으면 같은 좌표에 새 기록 — 도구가 날짜로 순서를 센다 · `supersedes` 는 기록 자체가 틀렸을 때만, 시스템 설명서 §4.4). **② 코드가 정본인 것은 옮기지 않는다** — OpenAPI · 마이그레이션 · IaC · 프롬프트 원문은 코드 레포에 두고 문서에는 `정본 위치` 와 코드가 말하지 못하는 것(왜 · 누가 쓰나 · 호환성 · 정책)만. **③ 좌표는 바뀌고 여럿이 보는 대상에만** — 사건(릴리스 · 스프린트 · 실험)은 날짜축, 집계(로드맵 · 플래그 · 비용)는 대장 | CDP 의 work/docs 모델 그대로. ADR 을 문서로 또 두면 「왜」 가 두 곳에 생긴다 |
| **P8** | 문서 수 | **패키지마다 12~14종** · 등록부 6~9 타입 | 40종을 붓고 지우게 하지 않는다. 더할 것은 README 「더할 만한 것」 에 이름만 — 서버형은 `save` 의 `managed`(writer)로 언제든 세운다 |
| **P9** | 머리 표 · 번호 | 머리 표는 dpms 와 같은 모양(`관리번호` · `언제` · `등록부` · `좌표 값`) · **`필수 제출` 칸은 두지 않는다**(계약 제출물이 없다 — `requiredOf` 가 null) · 관리번호는 묶음 접두 + 세 자리(`PD_301`) · `관리번호.md` 는 두지 않고 README 한 절 | 문서 고르기 · 참조 찾기(`docNo`)가 번호를 쓴다. 번호는 식별자가 아니라 속성이다(dpms 와 같다) |

| **P11** | `blank` | 문서 0 · 등록부 0 · 타입 0 · `docs/.gitkeep` · `_vocab.md` 는 쓰는 법과 생성 블록만 · README 「첫날」 은 **첫 관리 문서 세우기**. `ctx repo new` 의 「다음」 은 문서 수로 가른다 | Q6~Q9 |

## 7. 수용 기준

1. `ctx package list` 가 다섯을 낸다 — 이름 · 판 · 문서(0 · 40 · 14 · 13 · 12) · 타입 · 패턴
2. `ctx package check --all` — 다섯 다 ok. 새 셋의 경고는 「서식 예시 좌표가 남아 있다」 하나뿐
3. 다섯 다 `ctx repo new` 의 첫 커밋(훅)을 지나고, `--no-examples` 로도 지난다
4. 새 셋은 `examples: "purge"`(모드 A `ctx examples --purge`) 뒤에도 `ctx check` 오류 0
5. 패키지 안에 `DPMS` · `C:\project` 가 없다 — 시험이 지킨다
6. 하네스 70 · 71 · 72 · 74 가 `public-si` 로 · `npm run check:packages` · `node --test test/*.test.mjs` 초록
7. 콘솔 「새 지식 레포」 의 패키지 선택에 다섯이 보이고 문서 고르기가 패키지마다 맞게 뜬다(문서 0 이면 안 뜬다)
