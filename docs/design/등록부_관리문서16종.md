# 관리 문서 16종 — 등록부 규격

2026-09-04 · 사용자 확정. `정정_판정모델_v2.md` §4 의 상세.

## 원천은 둘로 갈린다

**관리 문서는 자주 쓰는 내용을 하나로 모아 둔 것이다.** 모든 내용이 여기
녹지는 않는다.

| | 원천 | 왜 |
|---|---|---|
| 자주 쓰는 내용 | **관리 문서 섹션** | 매번 이력을 뒤지는 값이 비싸니 하나로 수렴시킨다. 그 대가로 갱신 부담을 진다 |
| 덜 쓰는 내용 | **그 지식공유문서 자체** | 하나로 모으는 리소스 부담이 이득보다 크다 |

**어느 쪽인지는 팀이 정한다** — 등록부에 패턴을 올리는 것이 그 결정이다
(수행 v1.0 §3.2, "입도는 좌표계가 아니라 팀이 정한다").

### 등록부에 없는 좌표는 정상이다

밀림은 **등록부에 걸리는 좌표에만** 있는 개념이다. 안 걸리는 좌표는 파생할
곳이 없는 것이 아니라 **파생이 필요 없다** — 지식공유문서가 원천이다.

> **처음에 이 문서는 "모든 좌표는 관리 문서 섹션을 가져야 한다"고 썼다. 틀렸다.**
> 밀림이 0인 것은 자리가 다 있어서가 아니라 **자리가 있는 것에 대해 파생이
> 필수이기 때문**이다. 둘을 섞으면 안 쓰는 것까지 관리 문서로 끌고 와
> 갱신 부담만 늘린다.

## 등록부 (`_managed.md`)

```
| 좌표 패턴      | 관리 문서                        | 섹션      |
|---------------|--------------------------------|----------|
| `table:*`     | docs/테이블정의서.md              | ## {값}   |
| `term:*`      | docs/DB도메인용어정의서.md         | ### {값}  |
| `code:*`      | docs/코드정의서.md                | ## {값}   |
| `screen:*`    | docs/화면설계서.md                | ## {값}   |
| `api:*`       | docs/인터페이스정의서.md           | ## {값}   |
| `req:*`       | docs/요구사항정의서.md             | ## {값}   |
| `proc:*`      | docs/프로세스정의서.md             | ## {값}   |
| `func:*`      | docs/기능정의서.md                | ## {값}   |
| `prog:*`      | docs/프로그램사양서.md             | ## {값}   |
| `batch:*`     | docs/프로그램사양서.md             | ## {값}   |
| `module:*`    | docs/프로그램사양서.md             | ## {값}   |
| `arch:*`      | docs/시스템아키텍처정의서.md        | ## {값}   |
| `issue:*`     | docs/위험및이슈관리대장.md          | ## {값}   |
| `test:*`      | docs/테스트케이스.md              | ## {값}   |
| `scenario:*`  | docs/테스트시나리오.md             | ## {값}   |
```

### 바뀐 것

| | 전 | 후 |
|---|---|---|
| 화면 | 화면정의서_연구 / _계획 / _인사 / _기타 **넷** | **화면설계서 하나** |
| 용어 | 용어집 | **DB도메인용어정의서** |
| `module:` `batch:` | 등록부 없음 | **프로그램사양서** — 모듈·배치도 프로그램이다 |
| `domain:` | 등록부 없음 · 계산 제외 | **그대로 둔다** |

**화면을 업무별로 쪼개지 않는다.** 16종 목록이 `화면설계서` 하나다.
쪼개면 등록부 패턴이 업무 코드 규칙에 묶이고, 코드 규칙이 바뀌면 등록부가
따라 깨진다 — 실제로 `screen:SE*` / `PL*` / `PS*` 가 그렇게 묶여 있었다.

**`domain:` 은 등록부에 올리지 않는다.** 업무 영역에는 "지금 상태"라고 적을
것이 없다 — 산출물이 아니라 **작업을 묶는 축**이다. 입도가 굵어 후속이 항상
많다는 원래 이유도 그대로다. 원천은 그 업무를 다룬 지식공유문서들이다.

## 좌표가 없는 관리 문서 셋

| 문서 | 축 | 왜 좌표가 아닌가 |
|---|---|---|
| **회의록** | 날짜 | 회의는 대상이 아니라 사건이다. 좌표-섹션이 1:1로 대응하지 않는다 |
| **프로그램목록** | 목록 | 목록은 집계다. 각 프로그램의 내용은 프로그램사양서가 갖는다 |
| **개발일정계획서** | 일정 | 일정은 시간축이고 계속 바뀐다 |

셋은 관리 문서이되 **등록부 대상이 아니다.** 앱은 문서로 읽고 열 수 있지만
섹션 판정을 하지 않는다.

> 이 셋이 이슈 대장과 다른 점 — 이슈는 **번호로 특정되는 대상**이라
> `issue:ISS-014` 같은 좌표를 가질 수 있다. 회의·일정은 그렇지 않다.

## 이관

`C:\cdp` 는 지금 8종이고, 16종으로 가면 **좌표 대부분의 목적지가 바뀐다.**
등록부만 갈아끼우면 그 순간 앵커 없음이 수십 건 뜬다 — `screen:PSC043` 이
`화면설계서.md ## PSC043` 을 찾는데 그 파일이 없기 때문이다.

순서를 지킨다.

```
① 새 관리 문서 8종을 만든다 (빈 파일 + 제목)
② 화면정의서_* 넷의 섹션을 화면설계서.md 로 합친다
③ 용어집.md 를 DB도메인용어정의서.md 로 옮긴다
④ _managed.md 를 갈아끼운다
⑤ ctx check — 앵커 없음이 0 이어야 한다
⑥ 남은 미작성 섹션을 채운다 (밀림이 아니므로 커밋은 통과한다)
```

**②가 실질이다.** 나머지는 파일 조작이다.

이관은 지식 레포의 데이터 변경이라 **앱이 하지 않는다.** `ctx migrate16`
같은 명령을 만들지도 않는다 — 한 번 하는 일에 도구를 만들면 그 도구가
남아서 다음 사람을 헷갈리게 한다.
