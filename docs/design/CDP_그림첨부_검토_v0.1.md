## 1. 무엇이 깨졌나 — 본문 그림

### 1.1 실측 (로컬 뷰어 · 판 v0.19.3)

`work/assets/2026-0930-사업개요/시스템 개요.png` 를 레포에 두고 `docs/시스템아키텍처정의서.md` 에 넷을 적었다.

| 본문에 적은 것 | 그려진 `<img src>` | 결과 |
|---|---|---|
| `![](../work/assets/…/시스템%20개요.png)` (표준 · 문서 기준 상대) | `../work/assets/%EC%82%AC…png` | ✗ |
| `![](<../work/assets/…/시스템 개요.png>)` (꺾쇠 · 공백) | 같음 | ✗ |
| `![](/work/assets/…/시스템%20개요.png)` (레포 루트) | `/work/assets/…` | ✗ |
| `![](images/없음.png)` (없는 파일) | `images/%EC…png` | ✗ (그리고 깨진 아이콘뿐 · 무엇이 없는지 말하지 않음) |

**파일이 있어도 전부 깨진다.** 그림 파일은 서버의 `GET /api/<repo>/file?path=…`(로컬은 `/api/file?…&t=`)로만
나오는데, 렌더러(`viewer/src/lib/markdown.js`)는 markdown-it 이 만든 `src` 를 그대로 두고 후처리(`DocView`)도 `<a>` 만
본다. 그래서 브라우저가 **화면 주소**(`/r/<repo>/doc/…`) 기준으로 `../work/assets/…` 를 풀어 SPA 의 HTML 을 받는다.
운영자 화면의 「시스템 개요」 가 이것이다 — 레포에 그림을 넣고 맞춘 것은 맞았고, 화면이 그 파일을 부르지 않았다.

같은 뿌리 둘 더:

- 문서 머리 「첨부」 목록(`Attachment`)은 파일 API 를 쓰므로 거기서는 보였다 — **두 길이 갈라져 있었다.**
- 본문의 상대 링크 `[원본](../work/assets/x.pdf)` 도 전부 「문서 열기」 로 가로채져 `x.pdf` 라는 문서를 찾다 끝난다.

### 1.2 결정

| | 결정 | 왜 |
|---|---|---|
| G1 | 본문 그림의 상대 경로는 **그 문서가 있는 폴더 기준**으로 푼다(마크다운 표준 · GitHub · VS Code 와 같다). `/…` 는 레포 루트. `docs/` · `work/` 로 시작하면 레포 루트(첨부 목록과 같은 규칙). 퍼센트 인코딩은 풀고 파일 API 에 다시 싼다 | 사람이 로컬 편집기에서 보던 그대로 서버 화면에서도 보여야 한다. 첨부 목록과 **한 함수**(`lib/repopath.js`)로 — 두 길이 다시 갈라지지 않게 |
| G2 | 렌더러는 상대 그림을 `src` 대신 `data-src` 로 낸다. 화면이 그 문서의 경로로 풀어 `src` 를 붙인다 | 렌더 결과는 원문을 키로 캐시되고(같은 원문 = 같은 HTML) 문서 경로를 모른다. `src` 로 두면 붙이기 전에 브라우저가 엉뚱한 주소를 한 번씩 부른다 |
| G3 | 못 읽은 그림은 깨진 아이콘 대신 **「그림을 찾을 수 없음 · <경로>」** 상자. 레포 밖을 가리키면 그 말로 | 무엇이 없는지 말해야 사람이 고친다. 첨부 목록의 「경로를 찾을 수 없음」 과 같은 말 |
| G4 | 그림을 누르면 원본을 새 탭에. 본문의 상대 링크 중 `.md` 가 아닌 것(pdf · xlsx · 그림)은 파일로 연다 | 도식은 본문 폭에 줄어 보인다. 문서 열기로 가로채던 것은 없는 문서를 찾았다 |
| G5 | 파일 API 는 `.svg` 에 `content-security-policy: sandbox` 를 붙인다 | 「원문」 링크로 새 탭에 연 SVG 는 같은 출처의 문서다 — 안의 스크립트가 세션 쿠키로 돈다. 그림으로 쓸 때(`<img>`)는 영향 없음 |
| G6 | 설명서 화면(`/manual`)의 상대 그림은 GitHub raw 로 | 같은 렌더러를 쓴다(D10). 지금 설명서에 그림은 없지만 넣는 순간 깨지지 않게 |

## 2. 첨부를 어떻게 들이나

### 2.1 지금

| 모드 | 그림을 넣는 길 | 문제 |
|---|---|---|
| A (지식 레포 clone 이 PC 에) | 스킬이 `work/assets/<id>/` 로 복사하고 git 이 커밋 | 된다. 다만 `cdp-save` · `cdp-edit` 에 그 절차가 없다(`cdp-import` 에 한 줄) |
| B (지식 레포가 서버에만) | **없다.** `save` 는 텍스트만 받는다(작업 기록 · 섹션 · 어휘 · 등록부) | 운영자가 한 것 — 지식 레포 clone → 그림 커밋 → push → 콘솔 「origin 과 맞추기」. 셸 · 자격 · 권한(맞추기는 admin)이 다 있어야 하고, 그 사이 누가 save 하면 non-ff 로 꼬인다. 그림 커밋에는 「왜」(작업 기록)가 없다 |

### 2.2 후보

| | 방법 | 판정 |
|---|---|---|
| ㉠ | `save` 인자에 base64 로 싣는다 | ✗ — 모델이 바이트를 **토큰으로 뱉어야** 한다. 300 KB 그림이 40만 자 · 수십만 토큰이고 MCP 몸통 상한 2 MB 에 걸린다. 에이전트가 파일을 읽어 옮겨 적는 동안 한 글자만 틀려도 깨진 그림이 커밋된다 |
| ㉡ | 서버가 URL 에서 가져온다 | ✗ — 서버는 PC 에 닿지 않는다(사내망 · 방화벽). 닿는 URL 을 받으면 서버가 아무 데나 부르는 길(SSRF)이 열린다 |
| ㉢ | **올리기 API + save 가 참조로 받는다** | ○ — 바이트는 셸의 `curl` 이 보낸다(모델은 파일 경로만 적는다). 서버는 내용 해시로 잠시 들고 있다가 **`save` 가 작업 기록 · 섹션과 한 커밋**에 넣는다 |
| ㉣ | 화면에서 끌어다 놓기(레포 얼굴) | △ — 사람에게는 가장 쉽다. 그러나 커밋에 작업 기록(왜)이 없고, 섹션에 링크를 거는 것은 여전히 save 다. ㉢ 위에 얹을 수 있다 — **다음 판** |
| ㉤ | 첨부는 레포 밖(파일 서버 · 오브젝트 저장소)에 | ✗ — 레포 하나로 옮기면 다 따라가야 한다(폐쇄망 반입 · zip 내려받기 · clone). 레포 크기는 그림 몇 MB 로 문제가 되지 않는다 |

### 2.3 결정 — ㉢

| | 결정 | 왜 |
|---|---|---|
| A1 | 자리는 **`work/assets/<작업 기록 id>/<이름>`** — 모드 A · B 같다 | 첨부는 그것을 들여온 기록에 딸린다(`cdp-import` 의 규약 · `/archive?layer=work` 가 같이 싼다). 관리 문서에서는 `../work/assets/<id>/<이름>`, 작업 기록에서는 `assets/<id>/<이름>` |
| A2 | `POST /api/<repo>/assets` — 몸통 = 파일 바이트 그대로. 인증은 `Authorization: Bearer $CDP_TOKEN`(에이전트) 또는 세션 쿠키. **writer 이상** | 에이전트 PC 에는 이미 `CDP_TOKEN` 이 있다(MCP 가 쓰는 것). 새 자격을 만들지 않는다 |
| A3 | 받은 것은 레포가 아니라 **`<data>/staging/<sha256>`** 에 둔다(24시간 · 그 뒤 지운다). 응답 `{ ref: "sha256:<hex>", size, type }` | 올리기만으로 레포가 바뀌면 save 의 「트리가 더러우면 거절」(동시 기록 M8)에 걸리고, 쓰다 만 첨부가 남는다. 같은 파일을 두 번 올려도 한 벌 |
| A4 | 종류는 **바이트로** 가린다 — png · jpg · gif · webp · pdf. 상한 10 MB. svg 는 받지 않는다 | 확장자는 거짓말할 수 있다. svg 는 스크립트를 담는다(G5). 그 밖의 원본(hwp · xlsx)은 필요해지면 늘린다 |
| A5 | `save` 입력 `assets: [{ ref, name }]` → `work/assets/<work.id>/<name>` 에 쓴다. 작업 기록 · 섹션 · 어휘와 **한 커밋** · 검사에서 걸리면 같이 되돌린다. 응답 `assets: [{ path, size }]` | save 가 유일한 쓰기이고 한 단위다(§0). 경로를 서버가 정하므로 레포 밖 · 남의 기록 폴더에 쓸 길이 없다 |
| A6 | `name` — 경로 구분자 · `..` · 제어 문자 없음, 확장자가 올린 종류와 맞아야 한다. 한 save 에 20개 · 합 30 MB | 이름 하나가 파일 경로가 되는 마지막 문이다 |
| A7 | 경고 둘 — ① 이 save 가 쓴 본문(작업 기록 · 섹션)이 가리키는 레포 안 그림이 없다 ② 올린 첨부를 어느 본문도 가리키지 않는다 | ①이 운영자가 본 증상의 쓰는 쪽 짝이다 — 링크를 잘못 적으면 커밋 전에 안다. 거절하지 않는다(편입 원문의 깨진 링크는 원문의 것이다) |
| A8 | 스킬 — `cdp-save` 에 「그림 · 첨부」 절: 모드 A 는 복사 + git, 모드 B 는 `curl` 한 줄 → `assets[]`. 서버 주소는 `.mcp.json` 의 `url` 에서 `/mcp/<repo>` 를 뗀 것. `cdp-edit` · `cdp-import` 는 그 절을 가리킨다 | 에이전트가 「첨부는 못 한다」 로 멈추지 않게. 사람이 레포를 받아 push 하는 우회가 사라진다 |
| A9 | MCP `save` 명함에 `assets` 한 줄 — 「바이트는 도구 인자로 보내지 않는다 · 올리기 API 의 ref 를 싣는다」 | ㉠ 을 모델이 스스로 시도하지 않게 |

### 2.4 남는 것 (이번 판 밖)

- ㉣ 화면에서 끌어다 놓기 — 올리기 API(A2)를 그대로 쓰고, 작업 기록을 같이 받는 작은 폼이 필요하다
- `ctx check` 전체에서 깨진 그림 경로를 찾는 검사(지금은 save 가 쓴 본문만 · A7)
- hwp · xlsx 같은 원본 첨부 — 종류 목록(A4)에 넣으면 된다. 화면은 첨부 목록의 「원문」 으로 이미 받는다
- 운영자가 이미 넣은 그림 — 경로가 문서 기준 상대이거나 `docs/` · `work/` 로 시작하면 이번 판의 화면에서 바로 보인다. 그 밖(예: 화면 주소 기준으로 적은 것)이면 G3 상자가 경로를 보여 준다
