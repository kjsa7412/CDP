## 0. 한 줄

**레포 전환과 사용자별 레포 할당은 이미 반쯤 있고 화면만 모자란다. 관리자 역할과 화면에서의
사용자 · 토큰 관리는 "명부는 서버 셸의 것"(§4.4.1)을 뒤집는 일이라 방어를 다시 세우면 된다.
토큰 원문을 보관해 다시 쓰는 것은 신원 모델을 깨므로 그대로는 하지 않고, 그 밑의 필요
(SSH 없이 발급 · 잃어도 금방 복구 · 목록이 보인다)를 다른 길로 채운다.**

## 1. 요구 — 운영자의 말 그대로

| # | 요구 | 한 줄로 |
|---|---|---|
| R1 | `/r/gdi/` 관리 프로그램에서 **관리 중인 · 접속 가능한 레포 목록**을 알 수 있고 화면에서 **넘어갈 수** 있게 | 레포 목록 · 전환 |
| R2 | **사용자마다 접속할 수 있는 레포를 할당** | 사용자별 레포 권한 |
| R3 | 사용자 중 **관리자를 지정**하고, 관리자만 볼 수 있는 화면을 주고, 거기서 **사용자를 관리** | 관리자 역할 · 사용자 관리 화면 |
| R4 | 토큰이 발급되면 **유실되지 않게 계속 보관**하고 관리 프로그램에서 **볼 수 있게**, **명세(사용자)만 바꿔 다시 쓰고**, **삭제**도 | 토큰 보관 · 재배정 · 삭제 |

## 2. 지금은 어떤가 — 실측

| | 있다 | 없다 |
|---|---|---|
| R1 레포 목록 · 전환 | 상단 레포 이름표가 **전환 메뉴**다 — `GET /repos` 로 **볼 수 있는 레포만** 싣고 `/r/<repo>/` 로 옮긴다(§6.6.2 · `App.jsx`). 관리 > **지식 레포**(서버판)에 목록 · head · 미러 · 열기 · 새 레포 세우기 | **레포가 하나면 전환 UI 를 내지 않는다** — 지금 `gdi` 하나라 보이지 않는다. 그래서 "없다" 고 느낀다. "관리 중 / 접속 가능" 구분도 없다(둘이 같다 — 권한 밖 레포는 존재를 알리지 않는다 §4.6) |
| R2 사용자별 레포 | 명부 `users[].repos`(목록 또는 `*`)가 이미 권한이다. 화면 · API · MCP 전부 이것으로 거른다 | **바꾸는 자리가 CLI 뿐** — `ctx serve user set --repos gdi,foo`. 서버 셸이 필요하다 |
| R3 관리자 | 권한 축이 `write` 하나 — save · 레포 세우기 · 작업 레포 등록. `serve init` 의 첫 사용자가 사실상 관리자 | **관리자 역할 없음.** 사용자 관리 화면 없음. 명부 편집은 CLI 만(§6.6.4 "명부 편집 없음") |
| R4 토큰 | `serve token` · `token list`(id 앞 8자 · 사용자 · 메모 · 만료 · 마지막 사용) · `revoke`. 발급 · 폐기는 `auth.log` 에 남는다 | **원문은 저장하지 않는다**(SHA-256 만 · §4.4). 화면에 토큰 자리가 **없다**(§4.4.1 · 하지 않는 것). 사용자 변경 · 만료 연장 · 메모 수정 없음 |

**세 결정이 이 요구와 부딛힌다.** 전부 의도된 것이라 근거를 먼저 본다.

| 결정 | 어디 | 왜 그렇게 정했나 |
|---|---|---|
| 발급 엔드포인트는 없다 · 명부는 서버 셸의 것 | §4.4.1 · §6.6.4 | "발급을 요청할 자격" 을 HTTP 로 다시 인증해야 하고 그것이 OAuth 의 문제라 범위 밖. 서버 셸(SSH + sudo)이 더 센 경계다 |
| 토큰 원문은 저장하지 않는다 | §4.4 · §6.4 | `auth.json` 이 열쇠 다발이 되면 그 파일 하나로 전원이 뚫린다. 해시만 있으면 새도 쓸 수 없다 |
| 전용 관리자 계정을 두지 않는다 | §4.4.2 | "그것을 누가 주는지부터 정해야 하고 그 답이 없다" — 축을 늘리지 않으려는 선택 |

## 3. 요구별 검토

### 3.1 R1 — 레포 목록 · 전환 : **화면만 고친다**

기능은 있다. 보이지 않는 이유가 둘 — 레포가 하나면 메뉴를 숨긴다, 지식 레포 화면이 관리
메뉴 안쪽에 있다. 고칠 것 —

- 상단 레포 이름표를 **항상 메뉴로** 낸다. 하나여도 `gdi ▾ (1)` 로 — 메뉴를 열면 "볼 수 있는 레포 1 · 이 서버의 레포 1" 이 보인다.
- 메뉴 안에 레포마다 **제목 · head · 미러 · 내 권한(읽기/쓰기)** 한 줄. 관리자면 **볼 수 없는 사람이 몇인지**까지.
- "관리 중 / 접속 가능" 은 **관리자에게만 갈린다** — 일반 사용자에게는 접속 가능한 것이 전부이고 나머지는 존재를 알리지 않는다(§4.6 그대로). 관리자는 서버의 레포 전부와 사용자별 권한 매트릭스를 본다(3.3 의 화면).
- 관리 > 지식 레포(서버판)는 그대로 두고, 관리자 화면에서 링크한다.

**바뀌지 않는 것** — 전환하면 화면 상태를 버린다(§6.6.2). 두 레포를 한 화면에 놓지 않는다.

### 3.2 R2 — 사용자별 레포 할당 : **모델은 있고 화면을 단다**

`users[].repos` 가 곧 할당이다. 필요한 것은 관리자 화면에서 고치는 것(3.3)과 두 가지 보완 —

- 레포를 새로 세우면(`repo new` · `POST /repos`) **누가 볼 수 있나를 그 자리에서 정한다** — 기본은 "세운 사람 + `*` 인 사용자". 지금은 `*` 아닌 사용자에게 보이지 않아 CLI 로 한 명씩 열어야 한다.
- 사용자 화면에서 **레포 × 사용자 매트릭스**(체크박스)를 한 번에 본다. 사람마다 열기보다 레포마다 여는 쪽이 실제 운영이다.

### 3.3 R3 — 관리자 역할 · 사용자 관리 화면 : **§4.4.1 을 정정하고 방어를 다시 세운다**

**요구를 받아들인다.** 근거 —

- §4.4.1 이 막은 것은 "발급을 요청할 자격을 서버가 판단하는 일" 이었다. 그런데 관리 서비스는
  이미 쿠키 세션으로 **신원을 판단하고 있고**(§6.4), `write` 로 **권한도 판단하고 있다**(레포
  세우기 · 대장 등록). 명부 편집만 셸에 남긴 것은 경계의 문제가 아니라 **축을 늘리지 않으려는
  선택**이었다(§4.4.2 "전용 관리자 계정 … 답이 없다"). 그 답을 이제 정한다 — **첫 관리자는
  `serve init` 이 만들고, 다음 관리자는 관리자가 지정한다.** 부트스트랩이 셸이라 순환이 없다.
- SSH 가 있는 사람 = 서버 담당자이고, 지식 레포 관리자 = 프로젝트 담당자다. 둘이 다른 사람인
  것이 보통이고, 후자가 사람을 붙이는 데 전자를 부르는 것이 지금의 손을 타는 자리다.

**모델** — `users[].role`: `viewer` | `writer` | `admin`. 지금의 `write:true` 는 `writer` 로 읽는다(하위 호환). `admin` 은 `writer` 를 포함한다.

| 할 수 있는 것 | viewer | writer | admin |
|---|:--:|:--:|:--:|
| 볼 수 있는 레포 읽기 · MCP 읽기 도구 | ○ | ○ | ○ |
| `save` · 레포 세우기 · 작업 레포 등록/삭제 | | ○ | ○ |
| 사용자 추가 · 역할 · 레포 할당 · 비활성 | | | ○ |
| 토큰 발급 · 폐기 · 만료 연장 · 메모 | | | ○ |
| 모든 레포 보기(권한 매트릭스) · 감사 로그 보기 | | | ○ |
| 관리자 지정 | | | ○ (자기 자신의 관리자 해제는 불가 — 마지막 관리자를 잃지 않게) |

**화면** — 관리 메뉴에 `admin` 에게만 둘이 더 뜬다.

```
관리 >  현황 · 지식 레포 · 작업 레포 · 진단      ← 지금
        사용자 · 토큰                            ← admin 만.  메뉴 자체가 안 보인다(403 을 보여 주지 않는다)
```

- **사용자** — 목록(이름 · 라벨 · 역할 · 레포 · 활성 · 토큰 수 · 마지막 사용) · 추가 · 역할 변경 · 레포 매트릭스 · 비활성/재활성. **삭제는 없다** — `active:false` 와 `left` 날짜. 그 사람이 남긴 커밋의 `author` 가 명부와 이어져야 한다(지금 규칙 그대로).
- **토큰** — 3.4.

**API** — 전부 `admin` 이어야 200. 아니면 **404**(존재를 알리지 않는다 · §4.6 과 같은 규칙).

```
GET    /admin/users                     목록
POST   /admin/users                     { name, label, role, repos }
PATCH  /admin/users/<name>              { label? role? repos? active? }
GET    /admin/tokens                    목록 (원문 없음)
POST   /admin/tokens                    { user, note, expiresDays } → { raw, id }   ← 원문은 이 응답에 한 번
POST   /admin/tokens/<id>/revoke
PATCH  /admin/tokens/<id>               { note? expires? }
GET    /admin/audit?limit=200           auth.log 의 마지막 N줄
```

**방어를 다시 세운다** — 화면에 자리가 생기면 그 자리가 가장 약한 곳이 된다(§6.6.4). 그래서 —

| | 규칙 |
|---|---|
| 감사 | 모든 `/admin/*` 쓰기가 `auth.log` 에 **행위자 · 대상 · 바뀐 값** 으로 남는다(지금 CLI 와 같은 줄 모양). 토큰 발급은 앞 8자만 |
| 관리자 토큰 | 기본 만료 **30일**(일반 90일). 관리자는 자주 갱신한다 |
| 재인증 | 쓰기 `/admin/*` 는 세션 쿠키만으로 안 된다 — **토큰 원문을 한 번 더 넣는다**(sudo 와 같은 모양 · 15분 유효). 세션 탈취로 명부를 못 바꾸게 |
| 출처 | `--admin-from <CIDR>` (선택) — 관리 API 를 사내 대역으로 좁힌다. 프록시 없는 배치의 유일한 경계가 bind 라서 |
| 속도 | `/login` · `/admin/*` 는 IP 당 분당 N회. 실패는 `serve.log` 에 |
| 셸 | **CLI 는 그대로 남는다.** 마지막 관리자가 토큰을 잃으면 `serve token --user <admin>` 이 복구 길이다. 화면에서 되는 것은 전부 CLI 로도 된다 — 어느 한쪽만 되면 어느 쪽이 정본인지 묻게 된다 |

### 3.4 R4 — 토큰 보관 · 재배정 · 삭제 : **필요는 채우고 원문 보관은 하지 않는다**

요구를 셋으로 가른다 — (a) SSH 없이 발급 · 폐기 · 목록, (b) 잃어도 금방 복구, (c) 원문을 서버가
갖고 있다가 다른 사람에게 다시 준다.

**(a) · (b) 는 3.3 의 토큰 화면이 채운다.**

- 발급 — `POST /admin/tokens` 응답에 원문이 **한 번** 온다. 화면은 그것을 큼직하게 보이고 `복사` 버튼을 두고, 닫으면 다시 못 본다고 말한다. 지금 CLI 와 같은 규칙, 자리만 화면으로.
- 잃었다 — **재발급 한 번.** 행의 `재발급` 을 누르면 옛 토큰 폐기 + 새 토큰 발급 + 원문 한 번 표시가 **한 동작**이다. 사용자는 `CDP_TOKEN` 만 바꾼다. 권한은 사람에 붙어 있어 잃는 것이 없다 — "유실되면 새로 받는다" 를 **30초짜리로** 만든다.
- 목록 — id 앞 8자 · 사용자 · 메모 · 발급 · 만료 · 마지막 사용 · 상태. 폐기한 토큰도 **회색으로 남긴다**(지금은 줄을 지운다). "이 사람 토큰이 언제 있었나" 가 이력이다.
- 만료 연장 · 메모 수정 — `PATCH`. 삭제 = 폐기(`revoke`) — 행은 회색으로 남는다.

**(c) 는 하지 않는다.** 원문을 서버가 보관하면 —

| 깨지는 것 | 어떻게 |
|---|---|
| 신원 | 토큰은 "이 사람이다" 의 증명이다. 서버가 원문을 갖고 관리자가 볼 수 있으면 **관리자가 누구로든 행동할 수 있다.** 커밋의 `author` 가 그 사람이라는 뜻을 잃는다 — §4.5 가 `author` 를 서버가 채우는 이유가 그것이다 |
| 열쇠 다발 | `auth.json`(또는 금고 파일) 하나가 새면 전원이 뚫린다. 해시만 있을 때는 새도 쓸 수 없었다 |
| 재배정 | 토큰의 사용자를 A → B 로 바꾸면 **A 가 아직 그 원문을 들고 있다.** 그날부터 A 의 요청이 B 의 이름으로 기록된다. 감사 로그가 거짓이 된다 |

토큰 원문은 **비밀번호와 같은 성질**이다 — 시스템은 해시만 갖고, 잃으면 재설정한다. 요구의
"다시 쓴다" 는 원문을 재활용하는 것이 아니라 **사람에게 다시 준다** 는 뜻으로 읽고, 그것을
재발급 한 번으로 만든다. 원문을 넘기는 손은 어차피 사람이다.

> 그래도 원문 보관을 원하면 — **금고 옵션**(§5 D3). 서버가 원문을 AES-256-GCM 으로 따로
> 암호화해 두고(`data/vault.key` · 0600), 관리자가 `보기` 를 누르면 재인증 뒤 한 번 보여 주고
> **누가 언제 어느 토큰을 봤는지** `auth.log` 에 남긴다. 기본은 **꺼짐**이고, 켜면 화면 상단에
> "이 서버는 토큰 원문을 보관한다" 띠가 상시 뜬다. 재배정은 금고를 켜도 **미사용 토큰**
> (`lastUsed: null`)에만 허용한다 — 나눠 주기 전에 받는 사람이 바뀐 경우가 그 용도다.
> 권장하지 않는다. 그러나 정하는 것은 운영자다.

## 4. 설계

### 4.1 명부 v1.2

```jsonc
{
  "version": "1.2",
  "users": [
    { "name": "kjsa", "label": "사경진 · 개발", "role": "admin",  "active": true,  "repos": ["*"] },
    { "name": "park", "label": "박 · 개발",     "role": "writer", "active": true,  "repos": ["gdi"] },
    { "name": "qa",   "label": "QA 공용",       "role": "viewer", "active": false, "repos": ["gdi"], "left": "2026-10-01" }
  ],
  "tokens": [
    { "id": "31a0f265", "sha256": "…", "user": "kjsa", "created": "2026-09-23", "expires": "2026-10-23",
      "lastUsed": "2026-09-23 14:02", "note": "노트북", "status": "active" },
    { "id": "e8b767e0", "sha256": "…", "user": "park", "created": "2026-09-23", "expires": "2026-12-22",
      "lastUsed": null, "note": "노트북", "status": "revoked", "revokedAt": "2026-09-30", "revokedBy": "kjsa" }
  ]
}
```

- `role` 이 `write` 를 대신한다. **읽을 때** `write:true` → `writer`, 없으면 `viewer` 로 접는다(v1.1 파일 그대로 읽힌다). `serve init` 의 첫 사용자는 `admin`.
- 토큰에 `id`(sha256 앞 8자 · 지금은 계산해 보이던 것) · `status` · `revokedAt/By` 가 붙는다. `revoke` 는 줄을 지우지 않고 `status` 를 바꾼다 — 판정(`decide`)은 `active` 만 통과시킨다.
- 원문은 여전히 없다. 금고 옵션이 켜져 있을 때만 **별도 파일** `data/vault.json` 에 `{ id → ciphertext }` — `auth.json` 과 섞지 않는다(새는 범위를 가른다).

### 4.2 판정 — `decide` 는 그대로, 축이 하나 는다

```
토큰 → sha256 → tokens[] 에서 status:active · 만료 전 → users[] 의 그 사람 active → 권한
권한 = { repos, role }      role ≥ writer → save · 레포 세우기 · 대장
                             role = admin  → /admin/*
```

쿠키 세션도 같다 — 쿠키에는 `user` 만, `role` 은 매 요청 명부에서 읽는다(§6.4 그대로). 그래서
관리자 해제는 **다음 요청부터** 먹는다.

### 4.4 CLI — 짝을 맞춘다

```
ctx serve user add  … --role viewer|writer|admin      (--write 는 --role writer 의 옛 이름으로 받는다)
ctx serve user set  … --role admin                    (마지막 admin 을 viewer 로 내리면 거절)
ctx serve token     … --user <이름> [--note] [--expires]
ctx serve token reissue --id <앞 8자>                  폐기 + 발급 한 번
ctx serve token set --id <앞 8자> --note … | --expires …
ctx serve token revoke --id <앞 8자>                   status: revoked (줄을 지우지 않는다)
ctx serve doctor    … 관리자 수 · 30일 넘은 관리자 토큰 · 금고 켜짐 여부를 한 줄씩
```

### 4.5 바뀌는 문서

MCP 설계서 §4.4.1(발급 엔드포인트 없음) · §4.4.2(전용 관리자 없음) · §6.6.4(명부 편집 없음) 에
**정정**을 붙인다 — 지우지 않는다. 관리자 설명서 6장(사람 관리)은 화면 기준으로 다시 쓰고 CLI 는
"셸에서도 같은 것" 으로 남긴다. 사용자 설명서 10.3 "토큰을 잃었다 → 관리자에게 재발급(화면에서 30초)".

## 5. 결정할 것 — 권장안

| # | 물음 | 권장 | 왜 |
|---|---|---|---|
| D1 | 관리자 역할과 화면에서의 명부 · 토큰 관리를 허용하나 | **허용** — `role: admin` · `/admin/*` · 재인증 · 감사 · 30일 만료 | 관리 서비스는 이미 신원 · 권한을 판단한다. 셸만 남긴 것은 경계가 아니라 미룬 결정이었다 |
| D2 | 첫 관리자는 누가 만드나 | **`serve init`(셸)** — 부트스트랩만 셸 | 순환이 없다. 마지막 관리자 복구도 셸 |
| D3 | 토큰 원문을 서버가 보관하나 | **보관하지 않는다.** 재발급 한 번으로 대신한다. 금고 옵션은 만들되 **기본 꺼짐** | 신원과 감사가 깨진다. 요구의 "다시 쓴다" 는 재발급으로 채운다 |
| D4 | 토큰의 사용자 변경(재배정) | **하지 않는다.** (금고를 켰을 때 미사용 토큰만 예외) | 옛 소유자가 원문을 들고 있다 |
| D5 | 사용자 삭제 | **없다** — 비활성 + `left`. 토큰은 폐기 행으로 남긴다 | 커밋 `author` 와 감사 로그가 명부와 이어져야 한다 |

| D7 | `/admin/*` 쓰기의 재인증 | **토큰 원문 재입력 · 15분** | 세션 탈취 한 번으로 명부가 바뀌지 않게 |

## 7. 하지 않는 것

| | 왜 |
|---|---|
| 토큰 원문을 평문으로 저장 · 화면에 상시 표시 | §3.4 — 신원 · 감사 · 열쇠 다발 |
| 사용 중인 토큰의 사용자 변경 | 옛 소유자가 원문을 갖고 있다 |
| 사용자 삭제 | `author` 와 감사가 끊긴다. 비활성으로 |

| OAuth · SSO · 비밀번호 | 범위 밖(§0). 토큰 + 명부가 이 규모의 정직한 답이다 |
| 관리 서비스 밖의 알림(메일 · 메신저) | 하지 않는 것 표 그대로 |
