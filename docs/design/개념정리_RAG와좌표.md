> **v1.0 이후** — 좌표의 원칙은 그대로다. 말은 [`용어.md`](../용어.md) v1.0 · 설계는 [`CDP_시스템설계서_v2.0.md`](CDP_시스템설계서_v2.0.md).

맥락 배포 프로토콜 개념 정리 · 팀 공유용

> 이 문서는 「AI 기반 맥락 배포 프로토콜 설계서 v1.1」의 **근거 문서**다.
> 설계서를 읽으면 거의 반드시 나오는 질문 — *"그냥 RAG 쓰면 안 되나?"* — 에 답하기 위해 만들었다.
> 설계서를 읽지 않았어도 이 문서만으로 이해되도록 썼다.

## 0. 이 질문이 자꾸 나오는 이유

"문서를 AI가 잘 찾게 한다"는 목표 아래 서로 다른 세 가지가 **전부 '검색'이라는 한 단어로 묶여 있다.** 그래서 논의가 자꾸 겉돈다.

| | 실제로 하는 일 |
|---|---|
| **저장 구조** | 지식을 어떤 단위로 쪼개 무엇을 함께 적어둘 것인가 |
| **검색 방식** | 그중 무엇을 꺼낼지 어떤 근거로 정할 것인가 |
| **주입 정책** | 꺼낸 것 중 몇 개를, 어떤 부가 정보와 함께 넣을 것인가 |

"RAG를 쓴다"는 말은 보통 이 셋을 한 묶음으로 정해버리는 선택이다. 그래서 **어느 층이 마음에 안 드는지 특정하지 않으면 비교가 되지 않는다.**

이 문서는 층을 하나씩 떼어놓고 본다.

---

## 1. 혼동 — "RAG는 정규화의 최종 단계 아닌가"

### 어디서 오는 생각인가

정규화는 데이터를 잘게 쪼개 중복을 없애는 것이고, RAG는 문서를 청크로 잘게 쪼개 벡터로 만드는 것이다. 둘 다 "잘게 쪼갠다"이니 같은 방향의 극단처럼 보인다. 자연스러운 연상이다.

### 왜 어긋나는가

**축이 다르다.**

- 정규화 = **저장 구조**를 어떻게 잡을 것인가
- RAG = 저장된 것을 **어떻게 꺼낼 것인가**

굳이 대응시키면 RAG는 인덱스 스캔에 가깝고, 정규화에 대응하는 것은 "지식을 어떤 단위로 쪼개 저장할 것인가"다.

그리고 저장 구조 관점에서 보면 **통상적인 벡터 RAG는 오히려 가장 비정규화된 형태다.** 산문을 잘라 임베딩만 붙여둘 뿐이라 중복도 모순도 그대로 안고 간다.

### 정규화가 실제로 푸는 문제

정규화는 "쪼개기 기술"이 아니라 **"같은 사실이 두 군데 적혀 있으면 언젠가 서로 달라진다"** 를 푸는 것이다.

| 문서id | 제목 | 작성자 | 작성자부서 |
|---|---|---|---|
| D1 | A10 어댑터 개편 | kjsa | 3팀 |
| D2 | 결재선 수정 | kjsa | 3팀 |

kjsa가 4팀으로 옮기면 두 줄을 다 고쳐야 한다. 하나 빠뜨리면 그 순간부터 kjsa는 3팀이면서 동시에 4팀이다.

원인은 하나다 — **`작성자부서`는 문서가 아니라 사람에 딸린 정보인데 문서 표에 얹혀 있다.** 그래서 사람 표로 떼어낸다. 이제 한 곳만 고치면 된다.

### 우리 프로토콜에 이게 어디 있나

**`_vocab.md`가 정확히 이것이다.**

각 문서가 좌표를 자유 문자열로 적는다면:

```
D1: touches: 연구계획테이블
D2: touches: tb_research_plan
D3: touches: TB_RESEARCH_PLAN
```

위 표에서 `작성자부서`를 문서마다 적어둔 것과 같은 상태다. **"이 대상의 정식 이름이 무엇인가"는 문서에 딸린 정보가 아니라 대상 자체에 딸린 정보**인데 문서마다 흩어져 있다. 3주면 표기가 갈라지고 검색이 죽는다.

`_vocab.md`는 그 정보를 **마스터 표 하나로 분리**한 것이다. 관계형 설계에서 종속된 속성을 별도 테이블로 떼어내는 것과 같은 동작이다.

> **결론 1** — 우리 프로토콜은 정규화가 덜 된 게 아니라 **더 된 쪽**이다. 다만 정규화 대상이 **메타데이터**고, 본문은 일부러 산문으로 남겨뒀다.

## 2. 혼동 — "청킹은 더 잘게 쪼개니 더 정규화된 것 아닌가"

입도만 보면 맞다.

```
통짜 300줄 문서              ← 비정규형
지식 단위 + 프론트매터        ← 어느 정도 분해
청크 + 임베딩                ← 더 잘게
```

**그런데 정규화는 연산이 두 개다.**

1. **분해** — 나눈다
2. **무손실 결합** — 나눈 것을 키로 다시 합쳤을 때 원본이 정확히 복원된다

2번이 안 되는 분해는 "덜 정규화된 것"이 아니라 **무효한 분해**다. DB 이론에서도 등급이 낮은 게 아니라 오류로 분류된다.

### 청킹이 실패하는 지점

설계서에 나오는 예시를 그대로 쓰면 — 300줄 문서의 214번째 줄을 청크로 떼어낸다.

```
"연계 실패 시 A10이 5분 주기로 자동 재시도, 수신측 중복 방지 키 필수"
```

남은 건 문장 하나다. **사라진 것:**

| 잃은 것 | DB로 치면 |
|---|---|
| 어느 API 이야기인가 | 외래키 |
| "수신측"이 누구인가 | 참조 대상 |
| 언제 결정됐고 아직 유효한가 | 시점 |
| 어느 문서에서 왔나 | 기본키 |

**조인할 키가 없으니 원본으로 되돌아갈 수 없다.** 그리고 되돌아갈 수 없으니 AI가 추정으로 메운다 — 연계 담당의 세션은 "A10이 붙여 보낸다"로, 연구관리 담당의 세션은 "우리가 구현한다"로 읽는다. 둘 다 성실히 해석했고, 다르게 읽었다는 사실은 아무도 모른다.

기준도 다르다. 정규화는 **함수 종속**이라는 명시적 근거로 쪼갠다. 청킹은 512토큰이니 문단 경계니 하는 **의미와 무관한 기준**으로 자른다. 종속 관계를 보지 않는다.

### 등급을 다시 매기면

| | 입도 | 키 보존 | 판정 |
|---|---|---|---|
| 청크 + 임베딩 | 잘다 | 없음 | **무효한 분해** |
| 지식 단위 + 좌표 | 거칠다 | `id`·`touches`·`supersedes` | 유효한 분해 |

> **정규화 등급은 "얼마나 잘게 쪼갰나"가 아니라 "쪼갠 뒤에도 복원되나"로 매겨진다.**

참고로 RAG 진영의 개선 기법들 — 청크에 부모 문서 id·제목·날짜를 붙이기, parent document retrieval, contextual retrieval — 은 **전부 청킹으로 깨진 조인 키를 사후에 복원하는 작업**이다. 방향이 우리와 같은 곳을 향하고 있고, 다만 한 번 깨뜨린 뒤 수선하는 중이다.

> **결론 2** — 청킹은 정규화의 극단이 아니라 **정규화 조건을 못 맞춘 분해**다.

## 3. 혼동 — "벡터에는 관계가 없다" / "벡터가 관계를 담는다"

둘 다 정확하지 않다. 정확히는 이렇다.

> **관계가 없는 게 아니라, 모든 관계를 "유사도"라는 한 종류로 뭉갠다.**

| | 유사도 (임베딩) | 관계 (좌표·supersedes) |
|---|---|---|
| 방향 | 대칭 — sim(A,B) = sim(B,A) | 비대칭 — "A가 B를 대체" ≠ 그 반대 |
| 종류 | 없음. 숫자 하나 | 있음. 대체·참조·소속·영향 |
| 값 | 정도 (0.74) | 참/거짓 |
| 표현 가능한 것 | "닮았다" | "이것이 저것을 무효화했다" |

### 최악으로 드러나는 지점

```
"이 좌표의 담당 모듈은 acl-adapter 다"   ─┐
                                          ├─ 코사인 유사도 0.96
"이 좌표의 담당 모듈은 batch-agg 다"     ─┘
```

**모순되는 두 진술이 임베딩 공간에서 거의 같은 자리에 있다.** 문장 구조가 같고 한 토큰만 다르기 때문이다.

유사도 관점에서 이 둘은 "거의 같은 것"이다. 그래서 검색하면 사이좋게 둘 다 올라온다. **모순일수록 더 확실하게 함께 딸려온다.** 임베딩에는 "이 둘이 양립할 수 없다"를 표현할 언어가 없다.

`supersedes: 2026-0710-a10-adapter-v1` 한 줄이 이걸 해결한다. 방향이 있고, 참/거짓이 명확하고, 필터가 결정론적이다. **1536차원 벡터가 못 하는 일을 문자열 한 줄이 한다.**

### 곁가지 — 토크나이저와 헷갈리기 쉬운 점

| 연산 | 하는 일 | 되돌릴 수 있나 |
|---|---|---|
| 청킹 | 문서 → 구절 | 원문이 남아있으면 가능 |
| **임베딩** | 구절 → 1536차원 벡터 | **불가능** |
| 토크나이저 | 텍스트 → 토큰 id 배열 | 가능 (decode하면 원문 그대로) |

토크나이저는 무손실이다. 정보를 잃는 건 임베딩이다. 그래서 실무에서도 벡터는 찾는 데만 쓰고, 맥락에 넣는 건 따로 저장해둔 원문이다.

> **결론 3** — 임베딩은 정보를 없앤 게 아니라 **구분할 수 없는 형태로 압축**한다. 대체·모순·인과·귀속이 전부 "닮음의 정도"로 납작해진다.

## 4. 혼동 — "유사도 계산은 결정론적이니 믿을 수 있다"

### 절반은 맞다

LLM에는 샘플링(temperature)이 있어 같은 입력에도 다른 출력이 나온다. **임베딩에는 그게 없다.** 같은 텍스트 → 같은 벡터, 코사인 유사도는 사칙연산, top-k는 정렬. 이 구간에 주사위는 없다.

### 그런데 성질을 세 가지로 나눠야 한다

| | 재현성<br/>*같은 입력 → 같은 출력* | 안정성<br/>*같은 의미 → 같은 결과* | 설명가능성<br/>*왜 그렇게 됐는지* |
|---|:--:|:--:|:--:|
| 임베딩 검색 | O | **X** | **X** |
| 좌표 매칭 | O | O | O |
| LLM 추론 | X | X | X |

임베딩 검색은 첫 칸만 통과한다. 그리고 **사고를 내는 건 두 번째 칸이다.**

### 안정성이 깨지는 실제 지점

**(1) 질의 표현이 조금 바뀌면 순위가 뒤집힌다.** "계획서 상태값 관련 변경"과 "planStatus 필드 추가"는 같은 걸 묻는데 다른 문서를 물어온다.

**(2) 문서가 늘면 기존 질의의 답이 바뀐다.** ← 가장 고약하다. 다음 절에서 자세히 본다.

**(3) 임계값을 정할 근거가 없다.** 유사도 0.78은 관련 있는 건가 없는 건가. 답할 방법이 없다.

> **결론 4** — 비결정론적이어서 못 믿는 게 아니라, **결정론적이지만 근거를 설명할 수 없어서** 못 믿는 것이다.

## 5. 핵심 — top-k 절단은 흔적을 남기지 않는다

이것이 이 문서에서 가장 중요한 부분이다.

### 파이프라인의 경계

```
[오프라인]
  문서 → 청킹 → 임베딩 → 벡터DB 저장          코드. LLM 없음.

[질의 시점]
① 질문 → 임베딩                              신경망. 샘플링 없음
② 유사도 계산                                산술 연산
③ 정렬                                       정렬
④ ★ top-k 절단 ★                            ← results[:5] 한 줄
⑤ 살아남은 k개를 프롬프트로 조립               문자열 결합
────────────── 여기서부터 LLM ──────────────
⑥ LLM이 그 k개만 보고 답변
```

**④는 LLM 바깥에서, LLM이 전혀 관여하지 않은 채 일어난다.** 그리고 결정적으로 — **잘린 것은 흔적을 남기지 않는다.** ⑤에 도착하는 건 그냥 문서 5개고, 6등이 있었다는 정보는 프롬프트 어디에도 없다.

LLM 입장에서 그 문서는 *탈락한 것*이 아니라 **애초에 존재하지 않았던 것**이다. 사람이라면 스크롤을 내려 6등을 볼 수 있다. **LLM에는 내릴 스크롤이 없다.**

### 실제 사고 시나리오

**8월 20일** — 배치 담당: "야간 집계 배치 관련 최근 변경 있나?"

```
1위 0.84  배치 스케줄러 변경
2위 0.81  집계 쿼리 튜닝
3위 0.79  로그 포맷 변경
4위 0.77  모니터링 알람 추가
5위 0.74  A10 어댑터 개편 (중복 방지 키!)   ← 간신히 통과
──────── top-5 절단선 ────────
```

중복 방지 키가 맥락에 들어갔다. 잘 굴러갔다.

**8월 27일** — 누군가 무관한 문서를 올린다. "배치 서버 증설 완료". 같은 사람, 같은 질문.

```
1위 0.84  배치 스케줄러 변경
2위 0.82  배치 서버 증설          ← 새로 진입
3위 0.81  집계 쿼리 튜닝
4위 0.79  로그 포맷 변경
5위 0.77  모니터링 알람 추가
──────── top-5 절단선 ────────
6위 0.74  A10 어댑터 개편          ← 밀려서 탈락
```

AI는 "관련 변경은 스케줄러와 서버 증설입니다"라고 답한다. **확신을 갖고.**

A10 문서는 조금도 변하지 않았다. 유사도 0.74도 그대로다. **무관한 문서 하나가 위에 끼어들었을 뿐인데 답이 뒤집혔다.**

### 왜 아무도 모르나

세 층이 전부 정상 동작하기 때문이다.

| 층 | 상태 |
|---|---|
| 벡터DB | top-5 정상 반환. 에러 없음 |
| 프롬프트 조립 | 5개 받아서 넣음. 에러 없음 |
| LLM | 받은 5개 안에 없으니 "없음". **틀렸다는 자각 없음** |

설계서 §9.6이 말하는 **조용한 실패**다. 좌표 오타 하나 없이, 시스템 어디에도 결함 없이 발생한다.

### 좌표는 왜 다른가

**경쟁 구도 자체가 없다.**

```
touches 에 table:tb_research_plan 이 있는가?
  → A10 어댑터 개편:  O
  → 배치 서버 증설:   X
```

참/거짓이고 서로 순위를 다투지 않는다. **문서가 만 건 늘어도 판정이 그대로다.** 밀려날 자리가 없다.

그리고 더 중요한 차이가 있다.

**좌표 방식은 잘린 것을 통보할 수 있다.**

```
[절단] 좌표 매칭 12건 중 최신 5건 주입.
       나머지 7건 id: 2026-06...
```

절단이 **흔적을 남긴다.** AI가 "더 있다"를 알고 필요하면 요청한다.

유사도 방식은 이걸 원리적으로 못 한다. 6등이 관련 있는지 없는지 **시스템 자신도 모르기 때문**이다. 0.74가 관련 있음의 근거인지 아닌지 판정할 기준이 없으니, "관련 있는데 잘렸다"고 말할 자격이 없다. 그냥 6등일 뿐이다.

| | 절단 기준 | 새 문서의 영향 | 잘린 것 통보 |
|---|---|---|---|
| 유사도 top-k | 순위 (상대적) | **기존 결과를 밀어냄** | 불가능 |
| 좌표 매칭 | 참/거짓 (절대적) | 없음 | 가능 |

> **결론 5** — 좌표로 "이게 관련 있다"를 먼저 확정하면, 그 뒤의 정렬은 **순서를 정하는 일**이지 **존재 여부를 정하는 일**이 아니게 된다. 틀려도 순서가 바뀔 뿐, 문서가 사라지지 않는다.

---

## 6. 혼동 — "그럼 맥락을 많이 넣으면 되는 것 아닌가"

아니다. 맥락을 늘리면 **다른 종류의 실패**가 시작된다. 관련 없는 내용이 주의를 분산시키고, 긴 맥락 중간의 정보는 실제로 잘 안 쓰인다.

애초에 "안전하려고 300줄을 통째로 넣는 것"이 이 프로토콜이 풀려는 문제였다. 좌표를 붙여놓고 다시 전량 투입하면 출발점으로 돌아간다.

**좌표의 이점은 많이 넣는 것이 아니라, 적게 넣어도 안전해지는 것이다.**

```
유사도만:  놓칠까 봐 20건 넣는다      (근거 없는 과잉)
좌표 있음: 3건이 전부임을 알고 3건만   (근거 있는 절약)
```

좌표 방식도 자른다. 차이는 **자르는 기준**이다.

| | 자르는 기준 | 설명 가능? | 잘린 것 통보 |
|---|---|---|---|
| 유사도 top-k | 상대 순위 0.74 | X | X |
| 좌표 + supersedes + 최신순 | 무효화됨 / 오래됨 | **O** | **O** |

"이 문서는 뒤에 온 기록이 정정해서 뺐다", "12건 중 최신 5건을 넣었고 나머지는 이것들이다" — 둘 다 사람이 검증할 수 있는 문장이다. "0.74라서 뺐다"는 검증할 수 없다.

> **결론 6** — 많이 넣어서 신뢰도가 올라가는 게 아니라, **자르는 기준이 설명 가능해져서** 올라간다.

## 7. 곁들여 — 나이와 유효성은 다르다

이 구분이 안 되면 "최신순 정렬로 충분하지 않나"라는 결론에 도달한다. 아니다.

| 개념 | 정의 | 성질 |
|---|---|---|
| **나이** | `date` 이후 경과 시간 | 참고용. **오래됐다고 틀린 게 아니다** |
| **유효성** | 뒤에 온 기록이 이 기록을 정정했는가 | **참/거짓.** 정정된 문서는 검색 제외 |

**2년 전 문서라도 정정되지 않았으면 그것이 현재의 정답이다. 어제 문서라도 오늘 정정됐으면 틀린 정보다.**

"최근에 쓰였다"와 "지금 유효하다"는 다른 것이고, 유사도에 최신성 가중치를 주는 방식(recency decay)은 이 둘을 섞는다. 그래서 완화책일 뿐 해법이 되지 못한다.

`supersedes`가 이 판정을 참/거짓으로 만든다.

## 8. 그래서 우리의 선택

### 층을 쌓는 순서

```
1층  좌표 필터        참/거짓. supersedes 제외. 후보 확정
     ↓
2층  정렬·제한        최신순 / 최신성. 절단 시 신호 부착
     ↓
2.5층 (선택) 유사도    확정된 후보 안에서만 순서 조정
     ↓
3층  맥락 주입        요약 + 유효성·최신성·절단 신호
     ↓
──── 여기서부터 LLM ────
4층  추론
```

**벡터 검색은 금지 대상이 아니다. 배치 순서의 문제다.**

- 1층 없이 2.5층만 쓰면 → 낡은 문서가 섞이고, 문서가 늘 때마다 결과가 흔들린다
- 2.5층 없이 1층만 써도 → 상당 부분 굴러간다. 좌표에 안 걸리는 질의에서만 아쉽다

> **범위가 확정된 뒤의 유사도 정렬은 틀려도 피해가 작다.**
> **범위 자체를 유사도가 정하면, 틀렸다는 사실조차 아무도 모른다.**

### 벡터 검색을 붙일 시점

두 신호 중 하나가 관측되면 검토한다. 그 전에는 붙이지 않는다.

| 신호 | 증상 |
|---|---|
| 좌표에 안 걸리는 질의가 반복됨 | "결재 로직이 왜 이렇게 복잡해졌지?" — 개념 질의. 좌표는 구조에 붙는 주소라 구조로 표현 안 되는 질문을 못 받는다 |
| 문서 본문 내부를 찾아야 함 | 문서는 찾았는데 300줄 첨부 어디에 있는지 모름 |

문서 50건 규모에서 붙이면 인제스트 파이프라인 유지비만 나가고 정확도는 좌표 필터보다 떨어진다.

### 비용은 감수되는 게 아니라 자리를 옮긴다

| | 좌표 방식 | 벡터 RAG |
|---|---|---|
| 임베딩 API | 0 | 문서마다 호출 |
| 벡터DB 운영 | 0 | 인스턴스 유지 |
| 재인덱싱 | 0 | 모델 교체 시 전량 |
| 구현 | `bin/ctx` 150줄 | 인제스트 파이프라인 |
| **사람의 작성 부담** | **좌표 3~6개 · 문서당 5분** | **0** |

```
벡터 RAG : 작성 비용 0  ·  인프라 비용 高  ·  신뢰도 낮음
좌표     : 작성 비용 有  ·  인프라 비용 0   ·  신뢰도 높음
```

**인프라 비용은 좌표 쪽이 압도적으로 싸다. 대신 유일한 비용이 사람에게 있고, 그것이 이 설계의 급소다.**

이 프로토콜의 생사는 "작성이 5분 안에 끝나는가" 하나에 달려 있다. 이 수치가 안 나오면 나머지 설계가 아무리 옳아도 시스템은 도입되지 않는다.

## 9. 한 장 요약

| 층 | 벡터 RAG | 이 프로토콜 |
|---|---|---|
| **저장 구조** | 청크 + 임베딩. 키 없음 | 지식 단위 + 프론트매터. `id`·`touches`·`supersedes` |
| **엔티티 해소** | 없음 (임베딩이 알아서 하길 기대) | `_vocab.md` aliases로 명시 |
| **검색 근거** | 유사도 (연속값) | 좌표 일치 (참/거짓) |
| **모순 표현** | 불가 — 모순일수록 가깝다 | `supersedes` |
| **절단 기준** | 상대 순위 | 유효성 + 최신순 |
| **잘린 것 통보** | 원리적으로 불가 | 가능 |
| **문서 증가의 영향** | 기존 결과가 밀려남 | 없음 |
| **인프라 비용** | 높음 | 0 |
| **작성 부담** | 0 | 문서당 5분 |

### 세 문장으로

1. **RAG는 정규화의 최종 단계가 아니다.** 축이 다르고, 저장 구조로 보면 오히려 비정규화된 쪽이다.
2. **유사도는 모든 관계를 하나로 뭉갠다.** 대체·모순·귀속이 "닮음의 정도"가 되고, 모순일수록 함께 딸려온다.
3. **유사도 절단은 흔적을 남기지 않는다.** 잘린 문서는 AI에게 *탈락한 것*이 아니라 *존재하지 않는 것*이 되고, 아무도 그 사실을 통보받지 못한다.

## 부록 — 예상되는 반문과 답

**"임베딩 모델이 좋아지면 해결되지 않나?"**
표현 분열 문제는 완화된다. 하지만 §3(방향·종류 없음)과 §5(절단이 흔적을 안 남김)는 모델 성능이 아니라 **자료구조의 성질**이다. 아무리 좋은 임베딩도 "A가 B를 대체했다"를 대칭적 유사도로 표현할 수 없다.

**"하이브리드 검색(키워드+벡터)이면 되지 않나?"**
검색 근거가 두 개로 늘 뿐, 둘 다 연속값 점수를 매겨 상위를 자르는 방식이다. §5의 절단 문제는 그대로다.

**"리랭커를 붙이면?"**
정확도는 오른다. 하지만 리랭커도 점수를 매겨 자르므로 "왜 6등인가"를 설명하지 못하고, 잘린 것을 통보하지도 못한다. 그리고 층이 하나 더 늘어 불투명해진다.

**"좌표를 사람이 붙이는 게 부담 아닌가?"**
맞다. 그게 유일한 비용이고 이 설계의 급소다. 그래서 `knowledge-share` skill이 `git diff`에서 좌표 후보를 자동 제안하고, 도입 3단계에서 실제 작성 시간을 측정한다. 5분을 넘으면 필드를 줄여야 한다.

**"좌표를 안 붙이면 그 문서는 영영 못 찾는 것 아닌가?"**
그렇다. 그래서 pre-commit hook으로 커밋 시점에 막는다. 커밋 시점에는 작성자가 맥락을 쥐고 있어 1초면 고친다.

**"그럼 벡터 검색은 아예 안 쓰는 건가?"**
아니다. 좌표 필터 **뒤에** 얹는다. 좌표로 후보 범위를 확정한 다음, 그 안에서 순서를 정하거나 첨부 본문의 관련 단락을 뽑는 데 쓴다. 붙이는 시점의 판단 기준은 §8에 있다.
