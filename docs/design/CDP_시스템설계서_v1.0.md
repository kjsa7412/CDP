# 제0부 — 이 시스템이 푸는 문제

## 0.1 문제

여러 사람이 한 시스템을 오래 고친다. 그러면 이런 질문이 생긴다.

```
"이 컬럼 왜 이렇게 생겼지"          → 지금 상태를 묻는다
"왜 그렇게 정했지"                  → 그때의 판단을 묻는다
"내가 이걸 바꾸면 누가 알아야 하지"  → 영향을 묻는다
```

세 질문의 답이 **사람의 머리와 채팅 로그와 흩어진 문서에** 있다. 그리고 6개월
뒤 그 결정을 되짚는 첫 사람은 대개 **자기 자신**인데, 그때 코드에는 *"무엇을"*
만 있고 *"왜"* 가 없다.

## 0.2 왜 검색으로 안 되는가

**같은 대상을 사람마다 다르게 부른다.** `PS_EXT_EMP_MST` · 외부인원마스터 ·
외부심의위원테이블. 검색은 이름을 맞춰야 걸리고, 안 걸리면 **"없다"** 가 된다.

그리고 근사 검색(RAG·임베딩)은 더 나쁘다 — **"없는 것"을 "비슷한 것"으로
채운다.** 없다는 사실이 답인 자리에서 비슷한 것을 주면 읽는 쪽은 그것을 답으로
믿는다.

## 0.3 그래서 좌표다

**대상마다 하나의 정본 이름을 두고, 그 이름으로만 연결한다.**

```
table:ps_ext_emp_mst
  ↑     ↑
 타입   값
```

이름표에는 의견이 없다. 그래서 **어휘 파일(`_vocab.md`)은 통제된다** — 별칭은
얼마든지 붙지만 정본은 하나다. 자연어로 물어도 별칭으로 걸린다.

## 0.4 두 층

```
work/   작업 기록 — 사건.  일어났다.  고치지 않는다.  계속 쌓인다
docs/   정본 문서 — 상태.  지금 이렇다.  덮어쓴다.  하나뿐이다
```

이 분리가 이 시스템의 **첫 번째 설계 결정**이고, 나머지가 거기서 나온다.

| | `work/` | `docs/` |
|---|---|---|
| 성질 | 불변 사건 | 가변 상태 |
| 개수 | 좌표당 N개 | 좌표당 1개 (섹션) |
| 답하는 질문 | **왜** 그렇게 정했나 | **지금** 어떻게 생겼나 |
| 낡는가 | **안 낡는다** — 사건은 사건이다 | 갱신 안 하면 낡는다 |

> **문서 단위로 "낡음"을 판정하면 반드시 절반이 틀린다.** 한 작업 기록이
> 좌표 셋을 건드렸으면 그중 하나는 최신이고 둘은 후속이 있을 수 있다.
> 낡음은 **(문서, 좌표) 쌍**의 성질이다.

# 제1부 — 프로토콜

## 1.1 파일 형식

### 작업 기록 — `work/<id>.md`

```yaml
---
id: 2026-0821-면접심사의견-개편        # 파일명과 같아야 한다 (error)
title: PSC043 개편 — 현황/작성 화면 분리
date: 2026-08-21                      # YYYY-MM-DD
author: kjsa
touches:                              # 이 작업이 **바꾼** 대상
  - screen:PSC043
  - code:PS130
supersedes: 2026-0326-테이블명-오타     # 이 기록 자체가 틀렸을 때만
attachments: [assets/psc043/layout.md]
tags: [채용]
---

(본문 — 자유 형식)
```

| 필드 | 필수 | 비고 |
|---|:--:|---|
| `id` `title` `date` `author` | **O** | 없으면 찾을 수도 판정할 수도 없다 |
| `touches` | 키는 필수 | **0개도 정상이다.** `touches: []` 로 적는다 |
| `status` | X | **쓸 수 있는 값이 없다.** 있으면 오류다. §1.6 |
| `supersedes` | X | 판정이 아니라 참조다. §1.5 |

**본문 형식을 강요하지 않는다.** v0.1 은 4섹션을 강제했고 폐기했다 — 형식을
채우는 데 힘이 들어가면 내용이 빈다.

### 정본 문서 — `docs/<이름>.md`

```markdown
## rp_pre_rview_opl_list — 사전검토의견서목록
<!-- applied: 2026-0903-SEB020-임시등록-작성일 -->

(지금 상태. 컬럼 표 등)

### 변경
· 2026-09-03 [`SEB020-임시등록-작성일`](../work/…) 임시저장 시 미기록
```

**`<!-- applied: ... -->` 가 이 형식의 유일한 규약이다.** 그 섹션이 어느 작업
기록까지 반영했는지를 말한다. `applied: null` 은 아직 아무것도 안 실었다는 뜻.

> **주석 자체에는 판정이 없다.** "이 섹션이 최신인가"는 계산해야 나온다 —
> §1.4.

### 어휘 — `_vocab.md`

```markdown
## table

- `table:rp_plnd_mst` — 계획서마스터
  aliases: 계획서, 연구계획서
- `table:rp_rdc_opl_mst` — 연관위 의견 (구)
  deprecated: 2026-03-26 오타 정정
  supersededBy: table:rp_rdc_opl_list
```

**`## <타입>` 섹션의 순서가 곧 카테고리 순서다.** 화면과 CLI 가 그 순서를 쓴다 —
알파벳순으로 다시 매기지 않는다. **팀이 어휘를 적은 순서가 팀이 정한 순서다.**

### 등록부 — `_managed.md`

```markdown
| 좌표 패턴 | 정본 문서 | 섹션 |
|---|---|---|
| `table:*` | `docs/테이블정의서.md` | `## {값}` |
| `issue:*` | `docs/위험및이슈관리대장.md` | `## {값}` |
```

**등록부에 패턴을 올리는 것이 "이건 정본 문서로 관리한다"는 결정이다.**

## 1.2 등록부에 없는 좌표는 결함이 아니다

이것이 **가장 자주 잘못 이해되는 지점**이다. 초기 설계는 *"모든 좌표는 관리
문서 섹션을 가져야 한다"* 고 썼다. **틀렸다.**

관리 문서는 **자주 쓰는 내용을 한곳에 모아 둔 것**이다. 모든 것이 거기 녹지
않는다 — 덜 쓰는 것을 하나로 모으는 리소스 부담이 이득보다 크다.

```
등록부에 있다   → 정본 문서 섹션이 지금 상태다.  갱신이 필수다
등록부에 없다   → 그 지식공유문서가 원천이다.    정상이다
```

그래서 앱은 *"관리 문서가 없다"* 라고 말하지 않고
**"원천 — 지식공유문서 N건"** 이라고 말한다.

`domain:` 은 특별하다 — **바꾸는 대상이 아니라 작업을 묶는 축**이라 등록부에도
없고 최신성 계산에서도 뺀다.

## 1.3 좌표를 붙이는 기준

**바꾼 것만이다.** 참조·호출·언급은 아니다.

판정 기준은 하나 — **6개월 뒤 그 대상을 맡은 사람이 이 작업을 찾아야 하는가.**

> *"주제인가?"* 는 답이 갈린다. **"바꿨는가?" 는 결판나고 diff 로 확인된다.**
> 그래서 후자를 기준으로 삼았다.

**없는 좌표보다 억지 좌표가 나쁘다** — 그 좌표를 찾는 사람에게 무관한 문서를
내밀기 때문이다. 그래서 좌표 0개를 정상으로 두고, 0개를 오류로 막지 않는다
(막으면 사람들이 억지로 붙인다).

## 1.4 계산은 하나다 — `later(기준, 좌표)`

```
later(기준, 좌표) = 그 좌표를 touches 에 가진 작업 기록 중 기준보다 나중인 것
```

기준을 무엇으로 주느냐에 따라 **세 가지 질문에 같은 함수가 답한다.**

| 기준 | 무엇을 묻나 |
|---|---|
| 작업 기록 | (문서, 좌표) 쌍의 최신성 — *"이 문서의 이 부분 뒤에 뭐가 더 있나"* |
| 섹션의 `applied` | 그 섹션에 **남은 갱신** |
| `null` | 그 좌표의 최신 작업 기록 |

**구현도 하나다** (`core/validity.js`). 세 곳에 따로 쓰면 규칙이 세
곳이 되고 곧 갈라진다.

### 같은 날짜는 후속이 아니다

날짜 입도가 하루라 하루 안의 순서를 알 수 없다. 그리고 `applied` 는 **하나만
가리킬 수 있는데** 하루에 같은 좌표를 두 번 건드리면 섹션은 둘 다 반영하고
`applied` 는 그중 하나만 적는다.

id 문자열로 순서를 매기면 그때 남은 하나가 **갱신 누락으로 잡힌다** — 실측에서
`screen:PLA011` 이 그랬다. 셋 다 반영했는데 1건이 남았다.

> **이 목록의 오탐은 부식성이 크다.** 한 번 틀리면 사람들이 목록 전체를 안
> 믿는다. 그래서 같은 날짜는 동료로 본다 — 선후를 모르니 단정하지 않는다.
>
> 대가로 같은 날 실제로 반영 안 된 작업을 놓친다. 그것은 섹션의 `변경` 목록이
> 실제 반영 기록이므로 거기서 보인다.

## 1.5 없는 것들 — 판정 모델의 정정

초기 설계에는 상태가 여럿 있었다. **셋을 없앴다.** 이것이 이 시스템을 이해하는
데 가장 중요한 부분이다.

### ① "밀림" 은 상태가 아니다

지식공유문서를 남기면 정본 문서 갱신은 **필수다. 선택이 아니다.** 그러면
"갱신이 밀린 섹션" 이라는 상태는 **구조적으로 존재할 수 없다** — 있으면 그건
상태가 아니라 **오류**이고, 검사가 커밋을 막는다.

미루고 싶어지는 이유 셋은 전부 성립하지 않는다.

| | |
|---|---|
| 파생이 넓다 | 넓어도 해야 한다. 넓다는 것은 그만큼 건드렸다는 뜻이다 |
| 남의 확인이 필요하다 | 필요 없다. 판단 근거가 지식공유문서에 다 있다 |
| 급하다 | **막히는 것은 코드 커밋이 아니라 지식 레포 커밋**이고, 그것은 작업이 끝난 뒤에 하는 일이다 |

**"미작성" 도 같다.** `applied` 가 낡은 것과 아예 없는 것은 같은 위반이다 —
갱신을 안 했다. 등급을 나누면(error/info) 절반이 안 막히고, 그 순간 없는
상태가 화면에 다시 생긴다. **한 건으로 낸다** — `derive-missing`.

작업 기록이 **아직 없는** 섹션은 위반이 아니다. 실을 것이 없다.

### ② "미결" · "제안" 은 CDP 의 것이 아니다

지식공유문서는 **작업의 완료에서 발생하는 문서**다. 결정을 기다리는 것은
완료가 아니라 **아젠다**이고, 아젠다는 이슈관리·TODO 같은 스케줄 문서가 다룬다.

둘을 같은 파일에 섞으면 — **불변인 사건과 가변인 상태가 섞이면** — 지식 레포가
할 일 목록 노릇을 시작하고 그 순간 둘 다 안 맞는다.

`미결` 과 `제안` 은 **같은 것이다**: 결정이 안 났다. 이름이 둘이면 한쪽만
막히고 다른 쪽으로 흘러 들어간다. 그래서 검사가 둘을 같이 잡는다.

> **판단이 끝난 부분과 안 끝난 부분을 가른다.** *"왜 이렇게 하는가"* 가
> 정해졌으면 그것은 지식공유문서다 — 남은 것이 남의 회신뿐이라면 그 **회신
> 대기만** 이슈 대장으로 보내고 작업 기록은 상태 없이 남긴다. 통째로 옮기면
> "왜 그렇게 정했나" 가 아젠다에 묻힌다.

### ③ "덮힘" 은 구조적 정보가 아니다

작업 기록은 **사건**이라 무효가 되지 않는다. 후속 작업이 그 좌표를 조금
손봤는지 완전히 뒤집었는지 **도구는 모른다.** 그래서 *"후속 있음"* 만 말하고
*"덮임"* 이라고 말하지 않는다. **아는 것만 말한다.**

`supersedes` 는 남아 있지만 **판정이 아니라 참조다** — 오기재 정정 용도로만
쓰고, 그것이 붙은 문서를 검색에서 내리거나 무효 표시를 하지 않는다. 다만
**순환과 대상 없음**은 여전히 말한다 — 그것은 의견이 아니라 깨진 참조다.

### ④ 그래서 남은 어휘

```
후속(later)     그 좌표를 이 뒤에 건드린 작업이 있다        — 사실
반영(applied)   이 섹션이 어느 작업까지 실었다              — 사실
파생 누락       갱신을 안 했다                              — 오류
섹션/문서 없음   등록부가 없는 자리를 가리킨다                — 오류
끊김            applied 가 유령을 가리킨다                   — 오류
```

**상태는 없고 사실과 오류만 있다.** 이것이 정정의 결론이다.

## 1.6 `status` — 쓸 수 있는 값이 없다

```
확정 · 완료   기본값이다. 파싱 경계에서 지운다
미결 · 제안   결정이 안 났다. 아젠다이고 갈 곳은 이슈 대장이다
진행중        그런 상태가 없다. 끝나지 않은 일은 문서가 아니다
```

지식공유문서는 작업의 **완료**에서 발생하고, 항상 그 시점에 완료된 것이
넘어온다. 그러므로 `status` 라는 칸은 **비어 있는 것이 유일한 정상**이다.

초안에는 `진행중`(점유)이 남아 있었다. 뺐다 — 그 상태를 두면 지식 레포가
할 일 목록 노릇을 하기 시작하고, 불변인 사건과 가변인 상태가 섞이면 둘 다
안 맞는다. `미결`·`제안` 을 뺀 것과 같은 이유이고, 하나만 예외로 남길 근거가
없었다.

`확정` 은 값이 아니라 **기본값**이다. 30건 중 28건이 같은 값이면 그 칸은
아무것도 구별하지 않는다. **읽는 경계에서 지운다**(`frontmatter.js`) — 그러면
이미 적힌 기존 기록도 고치러 다니지 않아도 된다.

## 1.7 보증 — git 훅이 유일하다

```
.githooks/pre-commit  →  bin/ctx check  →  error 있으면 exit 1
```

**LLM 의 선의에 의존하는 층이 하나도 없어야 한다.** skill 은 지시문이고 사람도
LLM 도 안 부를 수 있다. 그래서 **결정론적 보증은 이 한 줄뿐이고, 그것이
충분하다.**

| 등급 | 뜻 |
|---|---|
| **error** | 이 상태로 남기면 나중에 **틀린 답을 확신 있게** 준다 |
| warn | 알아야 하지만 지금 막을 근거는 아니다 |
| info | 참고 |

**error 를 함부로 늘리지 않는다.** 막히는 것이 잦으면 사람들이 `--no-verify`
를 쓰기 시작하고, 그 순간 보증 층이 통째로 사라진다.

# 제2부 — 프로그램

## 2.1 형태

```
cdp.exe  (단일 실행 파일 · ~68MB)
  ├── 로컬 HTTP 서버 (loopback only)
  ├── 화면 (dist/ 가 base64 로 인라인)
  ├── ctx CLI          cdp.exe ctx <명령>
  └── 트레이 아이콘 (Windows)
```

**폐쇄망이 전제다.** CDN·인터넷을 타는 것이 하나도 없다 — 웹폰트까지 base64
로 인라인돼 있다. `@import` 가 막히면 **조용히** 대체 폰트로 그려지고, 개발
PC 에서는 정상으로 보이므로 이관 후에야 발견된다.

## 2.2 층 구조

```
viewer/bin/ctx-cli.mjs ──┐
                         ├──▶ core/  ← **판정은 여기 한 곳**
viewer/server/index.js ──┘         repo.js  loadRepo() 가 입구
                                        ↑
                         viewer/server/adapter/    http · tray · security
                                        ↑
                                viewer/src/        화면 (React)
```

**앱과 CLI 가 같은 계산을 쓴다.** 두 곳에 판정을 두면 화면과 커밋 판정이
갈라지고, 그때 사람은 화면을 믿는다.

### `core/`

| 모듈 | 책임 |
|---|---|
| `scan.js` | 디렉터리 순회 + 증분 캐시. **읽는 경계에서 CRLF 를 정규화한다** |
| `frontmatter.js` | 프론트매터 파싱 + 층 판정(`work`/`managed`). `확정` 을 여기서 지운다 |
| `vocab.js` | `_vocab.md` → 타입 순서 · 정본 · alias · deprecated |
| `managed.js` | `_managed.md` → 좌표 패턴 → 문서 · 섹션 앵커 |
| `validity.js` | **`later()` 하나.** 섹션 상태 계산 |
| `check.js` | 검사. 등급 부여 |
| `repo.js` | 조립 — `loadRepo()` · `repoStatus()` |
| `store.js` | 화면이 쓰는 질의 — `nextNodes()`(뻗어나가기) · `docData()` · 검색 |
| `search.js` | 좌표·alias 인덱스 |
| `git.js` | fetch · status · pull --ff-only · push. **merge 는 하지 않는다** |
| `appstate.js` | 읽음 표시 · 내 좌표 · 창 상태 |
| `logger.js` | `logs/app.log` 회전 |

### 섹션 상태 — 내부 값

`validity.js` 의 `buildSectionStatus()` 가 좌표마다 하나를 낸다. **화면에
나가지 않는다** — 검사만 읽는다.

| 값 | 뜻 | 검사 |
|---|---|---|
| `ok` | 섹션이 최신 | — |
| `stale` | `applied` 뒤에 후속이 있다 | **error** (파생 누락) |
| `unwritten` | `applied` 없는데 작업 기록은 있다 | **error** (같은 건) |
| `empty` | `applied` 도 작업 기록도 없다 | 없음 — 정상 |
| `orphan` | `applied` 가 유령을 가리킨다 | error |
| `anchor-missing` · `doc-missing` | 등록부가 없는 자리를 가리킨다 | error |

> **이 값을 화면 배지로 그리지 않는다.** `stale`·`unwritten` 은 커밋 시점에
> 존재할 수 없으므로, 배지로 그리면 화면이 **없는 구분을 있는 것처럼** 말한다.

## 2.3 HTTP 어댑터

**얇게 유지한다** — 판정을 여기 두지 않는다.

```
GET  /                     화면 (인라인 에셋)
GET  /api/status           레포 요약
GET  /api/docs             문서 목록
GET  /api/managed          정본 문서 목록
GET  /api/vocab            어휘 트리 (좌표 탭·그래프가 쓴다)
GET  /api/next?kind=&key=  **뻗어나가기** — 다음 한 계층
GET  /api/coord?c=         좌표 하나의 전모
GET  /api/timeline         시간축
GET  /api/search?q=        검색 — 관리문서 · 작업문서 · 좌표 (`&force=1` 본문까지)
GET  /api/check            검사 결과
GET  /api/file?p=          첨부
GET  /api/events           SSE — 파일 변경 통보
POST /api/state            읽음·내 좌표·창 상태
POST /api/git/pull|push    ff-only pull · push
POST /api/rescan /quit /open
```

### 보안 경계 (`security.js`)

| | |
|---|---|
| 리스너 | **loopback 만.** 아니면 화면에 상시 경고 |
| 인증 | 실행 시 발급한 토큰. 없으면 401 |
| CSRF | `Sec-Fetch-Site` 검사 · Origin 검사 |
| 경로 | `/api/file` 은 레포 밖으로 못 나간다 (403) |

> **로컬 리스너는 v0.1 에 없던 위험면이다.** 가장 현실적인 사고는 브라우저에
> 열린 악성 페이지가 `localhost` 로 요청을 쏘는 것이라, 토큰과 `Sec-Fetch-Site`
> 두 겹을 둔다.

## 2.4 화면

```
┌── 찾는 곳 ──────────────────────────┬── 문서 ──────────┐
│ [관리문서] [작업문서] [좌표] [그래프] │  DocView          │
│   시작점 (Finder)                    │  ValidityBlock    │
├─────────────────────────────────────┤  SectionRail      │
│  뻗어나가기 (Explore)                │                  │
└─────────────────────────────────────┴──────────────────┘
```

**왼쪽은 찾는 곳, 오른쪽은 문서다.** 관계·이력·현황은 전부 왼쪽 아래가 답한다.

시작점 탭은 **객체 이름 그대로** 넷이다. 관리문서와 작업문서를 한 탭에 두면
층이 다른 둘을 스크롤로 가르게 된다 — 뻗어나가기가 계층을 섞지 않는 것과 같은
이유다.

상단은 — `문서 | 그래프 | 관리` 화면 전환 · 검색 · **⭮ 동기화** ·
**⚠ 검증 N** · **⋯**(매뉴얼 · 읽기 · 글자 크기 · 본문 폭 · 테마).

**동기화 버튼은 하나이고 상단에 있다.** 매일 누르는 것이고 **도는 동안 보여야
하는 것**이라 `⋯` 안에 둘 것이 아니었다. 단계(`원격 확인 중` · `받는 중` ·
`다시 읽는 중`)와 걸린 초가 버튼 자리에 그대로 뜬다 — 사내망 fetch 실측
19.5초 동안 화면이 조용하면 사람은 멎은 줄로 읽고 한 번 더 누르며, 그 두 번째
클릭은 `busy` 로 튕기므로 아무 일도 안 일어난다. **메뉴에 같은 줄을 남기지
않는다** — 같은 일을 하는 버튼 둘이 다른 영역에 살면 도는 중 표시도 둘로 갈린다.

> **push 는 상단에 없다.** 상태바에만 둔다 — 커밋은 되돌릴 수 있지만 push 는
> 남의 눈에 들어간다. 받는 것과 보내는 것을 같은 자리에 두지 않는다.
>
> **git 자격 증명은 앱이 들고 있지 않는다.** 인증은 git 이 OS 자격 증명
> 관리자로 처리한다. 앱에 넣으면 그것을 저장할 자리가 하나 더 생기고, 그
> 자리가 가장 약한 곳이 된다.

### 검색 — 이름 넷, 객체 셋

```
거는 곳   관리문서명 · 작업문서명 · 좌표명 · 좌표 alias
나오는 것 관리문서 · 작업문서 · 좌표
```

`store.js` 의 `search(q)` 하나가 답한다. 왼쪽 목록이 다루는 객체가 셋인데
검색만 `좌표 문서 / 전문 검색` 이라는 **다른 갈래**로 답하면 같은 레포를 두
가지 이름 체계로 보게 된다. 전에는 그랬다 — 관리문서는 갈래가 없어 전문 검색에
섞여 나왔고, 좌표 자체는 결과에 아예 없었다(좌표에 걸린 *작업문서*만 나왔다).

규칙 다섯.

1. **이름은 색인이 없다.** 문서 수천 개가 아니라 이름 수천 개이고, 매 타이핑마다
   훑어도 응답 예산(30ms) 안이다. 정규화 키 하나로 네 자리를 같은 규칙으로
   본다 — 공백·`_`·`-` 를 지우고 소문자로(`vocab.normKey`). `RP_PLND_MST` 도
   `rp plnd mst` 도 같은 것을 가리킨다. **질의하는 사람이 표기를 맞춰야 한다면
   그건 검색이 아니다**
2. 점수는 **어디서 걸렸나가 아니라 얼마나 맞았나**다 — 같음 100 · 앞에서 80 ·
   안에서 60 · 낱말 전부 40
3. **걸린 좌표가 문서를 끌고 온다.** 좌표를 찾은 사람은 그 좌표를 건드린
   작업문서와 그 좌표가 실린 관리문서를 보려는 것이다. 관리문서 줄은 **그 섹션
   자리에서** 연다(`nextNodes` 와 같은 규칙 — 문서에 나오는 순서로 가장 앞선
   섹션). 좌표 몇 개까지 끌고 오는지는 상한이 있다(`SEARCH_SEEDS`) — 한 글자
   질의가 좌표 200개에 걸리면 그 200개의 작업을 전부 끌고 오게 된다
4. **본문 전문 검색은 폴백이다.** 이름에서 하나도 못 찾았을 때만 돈다(`⇧⏎` 로
   강제). 그 결과도 같은 세 갈래에 접힌다 — 갈래는 *어디서 걸렸나*가 아니라
   *무엇인가*로 정한다. 그 밖 문서(README · MANUAL · `_vocab.md`)는 객체 셋에
   없으므로 결과에 넣지 않는다. 여기서 갈래를 하나 더 만들면 화면이 다루는
   객체가 검색에서만 넷이 된다
5. **왜 걸렸는지를 줄마다 말한다**(§13-⑤). alias 로 걸렸으면 그 alias 를 그대로
   보여준다. 대조 블록은 그대로 주인공이되, **좌표를 하나도 못 찾았을 때만**
   "대조 실패"를 말한다 — 좌표가 이름으로 걸렸으면 좌표 갈래가 이미 정본을
   보여주고 있고, 그때 실패를 띄우면 화면이 자기 결과를 부정한다

### 뻗어나가기 — 이 화면의 핵심

`store.js` 의 `nextNodes(kind, key)` 하나가 전부다.

```
작업문서  →  관리문서 · 좌표
좌표      →  관리문서 · 작업문서
관리문서  →  섹션
```

규칙 일곱.

1. **다음 한 계층만** 편다. 전체를 펼치면 그건 그냥 그래프 뷰다
2. 중간 열에서 다시 고르면 **그 오른쪽이 전부 교체**된다
3. **루프를 허용한다.** 같은 노드가 여러 열에 나온다 — 트리가 아니라 그래프다.
   `작업A → 좌표X → 작업A` 를 막으면 *"이 좌표를 이 작업이 또 건드렸다"* 가
   사라진다
4. **계층이 섞이지 않는다.** 위 표 그대로
5. 줄 이름은 **객체 이름 그대로** — 작업문서 · 관리문서 · 좌표 · 섹션.
   *"이 작업이 바꾼 좌표"* 처럼 관계를 문장으로 쓰지 않는다 — **열 머리에
   시작점이 있으니 관계는 자리가 말한다**
6. **가로로** 뻗는다. 세로로 쌓으면 레벨이 깊어질수록 시작점이 화면 밖으로
   나가고 지금 어디쯤인지 감이 사라진다
7. **상태 배지가 없다** (§1.5)

### 정렬 — 상태로 정렬하지 않는다

| 목록 | 기준 |
|---|---|
| 좌표 | 카테고리순(`_vocab.md` 선언 순서) + 카테고리 안 이름순 |
| 작업문서 | 작성일자순 (최신 먼저) |
| 관리문서 · 섹션 | 섹션 순서 (문서에 나오는 순서) |

내부 `sections` 배열은 **상태 급한 순**으로 정렬돼 있다. 그대로 내면 목차가
아니라 할 일 목록이 되고, **같은 것을 두 번 봐도 자리가 달라진다.**

### 좌표 그래프 (3D)

- Canvas 2D 에 손으로 만든 3D force layout. **three.js 를 쓰지 않는다** —
  CDN 이 없고, 번들하면 exe 가 크게 는다
- **배치가 결정론적이다.** 고정 시드(mulberry32)로 한 번 풀고 멈춘다 — 같은
  레포는 늘 같은 그림이라 사람이 위치를 기억할 수 있다
- **노드는 상태를 말하지 않는다.** 모두 같은 원이고 **크기만 다르다 = 작업
  건수.** 무채색이고 발광이 없다
- **이름은 전부 그린다.** 전에는 `count >= 2` 인 것만 달았는데, 작업 1건인
  좌표가 절반이 넘어 **대부분이 이름 없는 점**이었다 — 크기가 이미 건수를
  말하는데 이름까지 건수로 걸러 같은 것을 두 번 말하고 있었다.
  겹침은 **숨기지 않고 자리를 옮겨** 푼다(가까운 것 우선 · 좌우·위아래 탐색 ·
  캔버스 밖은 후보 아님 · 마지막에는 겹쳐서라도 그린다)
- **초점은 짚은 것 아니면 고정한 것**(`hover ?? lock`). 클릭이 고정하고 다시
  클릭·빈 곳 클릭이 푼다 — hover 뿐이면 마우스를 떼는 순간 사라져서
  **이어진 쪽을 눌러 볼 수가 없다**
- **1단계 이웃은 강조한다** — 원을 진하게(`ink`) 채우고 강조색 링 한 겹,
  이름도 굵게. 전에는 이웃이 *"흐려지지만 않은"* 상태여서 나머지가 빠지니
  상대적으로 도드라져 보였을 뿐, **어디까지가 1단계인지 눈으로 세야 했다.**
  이름까지 강조하는 이유는 노드만 굵게 하면 "저 점이 이어졌다"까지만 알고
  그것이 무엇인지는 다시 짚어야 하기 때문이다
- 강조할 라벨이 **자리를 먼저 고른다.** 깊이순으로만 놓으면 정작 읽어야 하는
  이름이 뒤로 밀려 엉뚱한 데 붙는다. 그리고 **굵기는 재기 전에 정한다** —
  다 잰 뒤에 굵게 바꾸면 실제 글자가 잰 상자보다 넓어져 옆 라벨과 겹친다
- **`맞춤` 은 실제로 맞춘다.** 회전을 기본값으로 돌린 뒤 투영된 실제 범위를
  재서 배율을 정한다. 이론적 상한(바깥 반지름 × 최악 원근)으로 계산해 봤더니
  실제 분포보다 훨씬 커서 배율이 눌렸다 — **재는 쪽이 정확하다**
- **배율은 둘로 나뉜다** — `base`(맞춤이 정하는 내부 값) × `zoom`(사용자 값).
  그래서 **맞춘 상태가 늘 100%** 다. 하나로 두면 열자마자 57% 같은 숫자가
  뜨고 그 숫자는 아무 기준도 가리키지 않는다
- **기본 배율은 전체 맞춤의 1.5배**(`SNUG`). 전체를 넣으면 바깥으로 밀린 고립
  노드가 배율을 정해 정작 볼 덩어리가 가운데에 작게 뭉친다 — 실측에서 프레임을
  폭 99%·높이 96% 채우는데 **중앙 절반에 잉크가 39%** 였다(고립 21/57).
  조인 뒤 52% 가 됐다. 바깥 몇 개는 프레임을 벗어나지만 `−`·끌기로 닿는다
- **카테고리 선택만 색을 쓴다.** 왼쪽 레일에서 타입을 고르면 그 좌표가
  강조색이 된다. 상태로 색을 쓰지 않는다는 원칙과 충돌하지 않는다 — 이건
  상태가 아니라 **지금 무엇을 고르고 있나**이고, 그것이 색 예산의
  파랑(상호작용)이 하는 일이다
- 배경이 테마를 따른다. `paint()`(즉시 그린다)와 `draw()`(다음 프레임 예약)를
  갈라 두고 **모든 입력이 `paint()` 를 직접 부른다** — rAF 가 멎어 있어도
  반응한다

### 색 예산

```
파랑 = 상호작용   ·   적 = 무효(깨진 참조)   ·   앰버 = 경고
```

셋뿐이다. **정상은 색이 없다** — 대부분이 무채색이어야 문제가 눈에 띈다.

## 2.5 CLI — `bin/ctx`

```
ctx check     커밋 가능한가.  error 있으면 exit 1     ← 훅이 이것만 본다
ctx index     INDEX.md · INDEX-by-coord.md 재생성
ctx match     이름 → 정본 좌표 (대조)
ctx where     그 좌표의 상태가 어느 문서 어느 섹션에
ctx derive    갱신이 남은 섹션
ctx apply     그 섹션에 붙일 변경 줄 초안 (파일은 안 고친다)
ctx term      어휘 조회
ctx brief     두 줄 요약
ctx sync      원격과의 차이 · 훅 설정 여부
ctx version   이 번들이 언제 만들어졌나
```

### 실행기 선택 — `bin/ctx` (sh)

```
node 있으면   → node bin/ctx.mjs
없으면        → cdp.exe ctx
둘 다 없으면   → 그 사실을 말하고 멈춘다
```

**exit code 까지 같다.** 그래서 git 훅이 어느 쪽에서도 돈다.

> **`bin/ctx.mjs` 는 레포 안에 산다**(폐쇄망 자족). 그래서 도구를 고치면
> 레포마다 새 번들을 넣어야 하고, **잊으면 그 레포만 옛 번들로 돌면서
> 조용하다.** `ctx version` 이 번들 시각을 찍는 이유이고, `build:ctx` 가
> `CDP_REPO` 를 같이 갱신하는 이유다.

## 2.6 단일 실행 파일 (SEA)

```
node 바이너리 복사
  → rcedit    아이콘 · 버전 (실패해도 계속 간다 — 아이콘 없어도 돈다)
  → PE 패치   Subsystem CONSOLE(3) → WINDOWS(2)   더블클릭 시 콘솔 창 없음
  → postject  NODE_SEA_BLOB 주입
  → **검증**   cdp.exe ctx version 이 날짜를 내놓아야 성공
```

**검증이 설계의 일부다.** 갓 복사한 68MB 파일은 백신이 스캔하는 동안 잠기고,
그 지점이 하필 blob 주입 직전이다. 그러면 남는 것은 **실행은 되고
`Cannot find module 'ctx'` 만 뱉는 파일** — 실패했는데 성공처럼 보인다.

그래서 세 가지를 둔다.

| | |
|---|---|
| `retryBusy()` | `EBUSY` · `Unable to commit` 이면 기다렸다 다시 (최대 12회) |
| `abort()` | 실패하면 **반쪽 파일을 지우고** 멈춘다 + `taskkill` 안내 |
| 주입 후 검증 | 위 |

> **없는 것과 깨진 것은 다르고, 깨진 쪽이 더 나쁘다.** 없으면 다시 만들지만,
> 깨진 것은 다음 사람이 정상으로 믿는다.

콘솔 서브시스템을 떼므로 stdout 이 사라진다 — 그래서 로그를 파일로 남긴다.

## 2.7 CRLF — 조용히 깨지는 자리

두 번 물렸다. **둘 다 조용했다.**

| 어디 | 무슨 일 |
|---|---|
| `_vocab.md` | Python 이 LF→CRLF 로 저장 → `split('\n')` 뒤 `\r` 이 남고 JS 정규식의 `.` 이 `\r` 을 안 먹어 **좌표가 하나도 파싱되지 않았다** (미등재 59건) |
| `.githooks/pre-commit` · `bin/ctx` | sh 스크립트에 CRLF → shebang 뒤 캐리지리턴 → **훅이 실행되지 않는다.** 커밋은 통과하고 검사는 안 돈다 |

대응 둘 —

1. **읽는 경계에서 정규화한다** (`scan.js` `readText()` · `repo.js` `readOr()`)
2. **`.gitattributes` 로 LF 를 못 박는다** (`* text=auto eol=lf`)

`core.autocrlf=true` 인 PC 에서만 깨지므로 **폐쇄망에 옮긴 뒤에 발견된다.**
그때는 물어볼 사람이 없다.

> 관리자 · 개발자)의 **원천**이다. `agent/manual/` 은 지식 레포 안으로 들어가는 짧은 판으로
> 그대로 두고, 두 벌이 어긋나면 `manual/` 이 맞다.

**루트에는 도구가 요구하는 것과 제일 위에 있는 것만 남는다** —
`package.json`·`package-lock.json` 은 npm 이, `.gitattributes`·`.gitignore` 는
git 이 루트에서만 읽는다. 그 밖에 루트에 두는 것은 `README.md` · `core/` · `manual/` 뿐이다.

**`node_modules/` 만 예외다.** npm 은 `package.json` 옆에 만들고 node 는 파일
위치에서 위로 올라가며 찾는다. `viewer/` 와 `ops/lib/` 가 둘 다 외부 의존을
쓰므로(`js-yaml`·`chokidar` / `rcedit`) 어느 한쪽으로 내리면 다른 쪽이 못
찾는다. 워크스페이스로 묶어도 루트로 끌어올려진다.

**`ops/` 와 `ops/lib/` 를 가른 이유** — 전에는 `tools/` 에
`build-exe.mjs`(스크립트가 부른다)와 `release.cmd`(사람이 더블클릭한다)가
나란히 있었다. **무엇을 직접 실행해도 되는지**를 파일을 열어 봐야 알았다.

> `.cmd` 는 **CP949 로 쓴다.** cmd.exe 가 파일을 OEM 코드페이지로 읽어서
> UTF-8 로 쓰면 한글이 `검??` 로 깨진다. 그리고 node 경로에 슬래시를 쓴다 --
> 배치에서 역슬래시가 이스케이프로 읽히는 자리가 있다(`viewerin` 이
> `viewerin` 이 됐다).

**산출물이 `dist/` 와 `build/` 로 나뉘어 있었다.** 이름이 둘이라 어디를 봐야
하는지 매번 헷갈렸고, `ctx` 번들은 세 번째 자리(`sample-repo/bin/`)에 있었다.
`out/web` · `out/ctx` · `out/exe` 로 모았다.

**`agent/` 가 따로 있는 이유가 설계다.** 전에는 스킬 4개가
`sample-repo/.claude/skills/` 안에만 있었다 — fixture 안의 사본이 사실상
원본이라 고치려면 fixture 를 고치고 다른 레포에는 손으로 복사해야 했다.
레포가 셋이면 세 번이고, **실제로 세 번 갈렸다.**

`CLAUDE.md` 도 같았다 — 시드와 GDI 생성기 **두 파이썬 파일에 문자열로** 각각
박혀 있어 한 번 갈라졌다.

원본이 하나여야 한다는 것은 `later()` 를 한 곳에 두는 것과 같은 규칙이다
(§1.4 · 불변조건 2).

### 릴리스는 버전 폴더 하나다

```
release/v0.2.0/
  cdp.exe          앱 + ctx
  knowledge-repo-<이름>/  **복사하면 그게 지식 레포다.** 패키지마다 하나씩.
                   도구(bin · .githooks · .claude · 매뉴얼)와 그 패키지의
                   문서 골격 · 등록부 · 어휘와 `tools/cdp.exe` 가 **합쳐진 채로**
  README.md        설치 안내
```

> **정정 (2026-09-14)** — 샘플 레포는 배포본에서 뺐다. **뷰어 개발용
> fixture 한 가지 용도**로 정리했고, 받는 사람에게 가지 않는다. 그래서
> `release` 가 `seed` 를 부르지도 않는다 — 부르던 시절에 덤프 없는 PC 에서
> 릴리스 한 번이 테이블정의서를 32섹션에서 1섹션으로 줄였다(`caa835a`).
> 대신 `packages/` 가 들어간다.
>
> **정정 (2026-09-14, 두 번째)** — `repo-kit/` 과 `packages/` 를 따로 주던 것을
> **합쳐서 완성된 폴더 하나**로 낸다. 그 이름들은 만든 쪽 개념이지 받는 쪽의
> 것이 아니었고, 받는 사람이 둘을 순서대로 부어야 했다. **설계서(`docs/`)도
> 뺐다** — CDP 를 고칠 사람의 것이고 서비스와 무관하다.

> **정정 (2026-09-23)** — `tools/cdp.exe` 를 폴더마다 담던 것을 **배포본 루트에 하나**로
> 되돌렸다. 패키지가 셋이 되자 배포본이 213MB(68MB×3)였다. 조립은 빈 `tools/`(`.gitkeep`)를
> 남기고, 받는 사람이 `copy cdp.exe <레포>\tools\` 한 줄을 더 한다(설치.md ③). 서버 산출물의
> `packages/` 는 원래 exe 가 없다.

**그 폴더를 통째로 옮기면 CDP 를 쓸 수 있다.** 전에는 산출물이
`build/`·`dist/`·`sample-repo/bin/` 에 흩어져 있어 **무엇을 나눠줘야 하는지
사람이 기억해야 했다** — 기억에 의존하면 빠뜨린다.

`tools/release.mjs` 가 빠진 것을 세어 **`exit 1` 로 알린다.** 없는 채로
배포되면 받는 쪽이 그것을 없는 기능으로 안다.

# 제4부 — 거부한 설계

**"이거 넣으면 좋겠다" 로 자주 돌아오는 것들이다.** 왜 안 넣었는지 남긴다.

| | 왜 |
|---|---|
| **RAG · 임베딩** | 좌표가 답이다. 근사 검색은 **"없는 것"을 "비슷한 것"으로 채운다** |
| **알림** | 무시되기 시작하면 되돌릴 수 없고, 그때 *"알림이 안 왔으니 없는 것"* 이라는 더 나쁜 오해가 자리 잡는다 |
| **관리 문서 자동 생성** | 입도는 팀이 정한다. 기계가 정하면 아무도 안 본다 |
| **지식 폴더 자동 최신화** | pull 이 유일한 수신 채널이다. 그 위에 층을 더 쌓지 않는다 |
| **본문 형식 강요** | 형식을 채우는 데 힘이 들어가면 내용이 빈다. 4섹션 강제를 폐기했다 |
| **하네스 훅으로 절차 강제** | skill `description` 이 발동 규칙이고 그 뒤에 git 훅이 있다. **비결정을 비결정으로 덮지 않는다** |
| **`CLAUDE.md` 절차 규약** | skill 과 중복된다. 두 곳에 적으면 한쪽만 고쳐진다 |
| **작업 할당 · 이슈 트래커** | 조직 구조와 얽힌다. CDP 가 답할 문제가 아니다 |
| **검토를 승인 관문으로** | 매 요청 정지 1회. 절차가 작업을 잡아먹는다. **흔적으로 두면 사후 교정된다** |
| **문서 단위 낡음 판정** | 좌표가 여럿인 문서에서 반드시 절반이 틀린다 |
| **비개발 직군 UI** | 범위 밖 |

# 부록 — 개발

```
npm run dev              vite (화면만)
npm run dev:server       서버 + viewer/fixture
npm start                서버 (빌드된 화면)
npm run seed             viewer/fixture 재생성
npm run ctx -- check     소스로 CLI 실행
npm run build:ctx        bin/ctx.mjs 번들 (CDP_REPO 도 갱신)
npm run build:exe        exe
npm run release          위 전부
npm test:tray            트레이 자체 시험 (클릭 없이)
```

**시드가 만드는 레포는 검사를 통과해야 한다.** 옛 시드는 밀림·미작성을
일부러 심어 시연했는데, 그것이 error 가 된 뒤로 **clone 직후 커밋이 막히는
샘플**이 됐다 — 폐쇄망 반입 검증(clone 해서 커밋이 되는가)이 무의미해진다.

지금 시드는 `fill_applied()` 로 작업 기록이 있는 섹션을 **그 좌표의 최신
작업**으로 채운다(옛것을 실으면 그 뒤 후속이 남아 또 오류다).
