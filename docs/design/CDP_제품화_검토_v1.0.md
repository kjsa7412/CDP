## 0. 한 줄

**CDP 는 기능은 다 있는데 손이 열 군데 든다.** 판정 엔진(`core/`) · CLI · 뷰어 ·
MCP 서버 · 관리 서비스 · 설치 꾸러미가 전부 돌고 검증 하네스 51건이 통과한다.
그런데 그것을 **만들고(빌드) · 내고(릴리스) · 올리고(배포) · 늘리고(패키지 ·
레포) · 들이는(변환)** 다섯 자리가 전부 한 사람의 PC 와 기억에 얹혀 있다.

제품화는 기능을 더하는 일이 아니라 **그 다섯 자리에서 사람을 빼는 일**이다.
순서는 CI 가 먼저다 — 나머지 넷을 자동화해도 CI 가 없으면 그 자동화가 깨진
것을 아무도 모른다. 오늘 실측이 그것을 보여 줬다(§1.3).

## 3. 갭 — 영역별 진단과 권장

각 영역을 **지금 · 문제 · 권장 · 왜 그 안인가** 로 적는다. 우선순위는 §5.

### 3.1 CI/CD — 없다 → 첫 순서

**지금** — §1.3. 빌드·번들·하네스가 전부 로컬 명령이다.

**문제** — 회귀를 잡는 자리가 사람의 기억이다. 오늘 하네스 52번이 그 증거다.
그리고 릴리스가 "내 PC 에서 되는가" 로 판정된다 — 태그 없이 0.8.0 이 나갔다.

**권장** — **GitHub Actions.** 원격이 GitHub 이고 닿는다(실측). 워크플로 둘.

| 워크플로 | 언제 | 무엇 |
|---|---|---|
| `ci.yml` | push · PR | `npm ci` → `npm run build` → `build:ctx` → **`npm test`**(단위) → **`npm run verify`**(하네스) → **패키지 검사**(§3.4). ubuntu 에서 돈다 — 서버가 Linux 다 |
| `release.yml` | 태그 `v*` | windows 에서 `npm run release`(exe 포함) → zip · ubuntu 에서 서버 산출물 tar.gz(§3.2) → **SHA256SUMS** → GitHub Release 에 첨부 |

**왜 GitHub Actions 인가** — 사내 GitLab 은 12.9 미만이고(PAT 스코프 문제로
실측됨) 러너를 세우려면 서버가 하나 더 든다. GitHub 은 이미 원격이고 러너가
공짜다. 사내 반입은 Release 자산을 받아 옮기면 된다 — 지금도 배포본을 폴더째
옮긴다.

**하네스를 CI 에서 돌리려면 둘을 고친다** — ① 52번(꾸러미 `kit/` 한 단) ②
fixture 의 `.claude/` 는 추적하지 않는데(`.gitignore`) 하네스 38 · 52 · 56 · 57 이
그것을 전제한다. fresh clone 에서는 없다. **Python 없이** `agent/` 에서 `.claude/`
를 만드는 한 줄이 필요하다 — `seed_repo.py` 가 하는 일 중 그 부분만 JS 로.

### 3.2 릴리스 · 버전 · 산출물

**지금** — 산출물이 하나다: `ops/release/v<버전>/`(69 MB · exe 포함). 서버에는

**문제** — 받는 쪽이 셋(팀원 PC · 서버 · 폐쇄망)인데 산출물은 한 모양이다.
서버 관리자가 69 MB 를 받아 두 파일을 꺼낸다. 그리고 "이 판에 무엇이 바뀌었나"

**권장** —

| 산출물 | 받는 쪽 | 담는 것 |

  닫힐 때.
- **Node 를 고정한다** — `engines: { node: ">=20" }` · `.nvmrc` `20`. 서버 절차서가
  "20 이상" 이라고 말하는 것을 코드가 말하게 한다.

### 3.3 서버 설치 · 갱신 — 10장을 스크립트 셋으로

**지금** — §2.2. B8(갱신) 이 9단계이고 계속 쓴다.

**권장** — 사람이 치는 것을 **셋**으로 줄인다. 절차서는 남긴다 — 스크립트가
무엇을 하는지 설명하는 문서로.

| | 하는 일 | 사람이 주는 것 |
|---|---|---|
| **`install.sh`** | 0~2·6장 — useradd · mkdir · 파일 배치 · **node 경로를 읽어 유닛에 박음** · daemon-reload · enable · `/healthz` 확인 · 방화벽 명령 **안내**(실행은 안 한다 — 배포판마다 다르다) | `--bind <IP>` · `--port` |
| **`upgrade.sh`** | 8장 ①②③ — `.bak` · 교체 · 화면 폴더 비우고 넣기 · restart · **`/healthz.built` 와 index 해시 대조** | tar.gz 경로 하나 |

| `ctx serve init` | 5장 — `auth.json` 만들고 첫 사용자(`--write`) 올리고 토큰 하나 발급을 **한 번에** | `--name` |

3장(git 자격)과 5장(명부·토큰)은 **사람의 절차로 남긴다.** 발급은 서버 셸에서
사람이 한다는 것이 설계다(§4.4.1). `init` 은 그 첫 번을 줄여 줄 뿐이다.

**Docker** — `Dockerfile` 하나를 둔다. systemd 없이 `ctx serve` 를 그대로 띄우는
모양. 사내 배치가 바뀌었을 때의 두 번째 길이고, **CI 에서 서버 산출물이 실제로
뜨는지 확인하는 자리**다. 기본 배치는 systemd 그대로.

**왜 sh 인가** — 서버에 있는 것은 sh · node · git 뿐이다. `install.mjs` 처럼 node
로 써도 되지만 useradd · systemctl 은 셸의 일이고, node 가 없는 상태에서 node 를
확인하는 것이 0장이다.

### 3.4 패키지 관리 — 폴더를 물건으로

**지금** — §2.4. 패키지는 폴더고, 폴더는 이름밖에 말하지 않는다.

**권장** —

1. **매니페스트 `_package.json`** 을 패키지마다 둔다 — `name` · `title` · `version` ·
   `description` · `source`(만든 기록이 어디 있나). `_vocab.md` `_managed.md` 처럼
   밑줄이 "기계가 읽는 통제 파일" 을 뜻한다. 문서 수 · 좌표 타입 · 등록부 패턴은
   **폴더에서 계산한다** — 적어 두면 갈라진다.
2. **`ctx package list · show · check`** —
   - `list` — 이름 · 판 · 문서 수 · 타입 수 · 패턴 수
   - `show <이름>` — 매니페스트 + 등록부 표 + 타입 순서
   - **`check <이름>`** — 임시 폴더에 **부어서** `ctx check` 를 돌리고, 등록부가
     가리키는 문서가 전부 있는지, 예시 좌표가 어휘와 문서에 짝으로 있는지 본다.
     **CI 가 이것을 패키지마다 돈다** — 릴리스가 깨진 패키지를 싸는 일이 없어진다.
3. 패키지가 사는 자리 — 소스에서는 `agent/packages/`, 서버 산출물에서는
   `packages/`(§3.2). `ctx` 는 `--packages <폴더>` → `CDP_PACKAGES` → 번들 위치
   기준 `../packages` → 소스 레포의 `agent/packages` 순으로 찾는다.
4. **두 번째 패키지는 만들지 않는다.** 표본이 하나인데 축을 세우면 그 축은 한
   건의 일반화다(`00_계획검토` §5). 대신 **만드는 길**을 낸다 — `ctx package new
   <이름> --from dpms` 가 폴더를 복사하고 매니페스트를 고쳐 주고 `check` 를 한 번
   돌린다. 문서 목록을 고치는 것은 사람이다.

**왜 `ctx init --package` 를 안 만드는가** — `06_패키지골격` §1 이 정했다. 설치는
복사고 방식이 둘이면 어느 것이 맞는지 묻게 된다. 그 결정은 **로컬**에 대한
것이다. 서버에서는 복사할 사람이 없으므로(§3.5) 그 자리에만 명령을 둔다.

### 3.5 지식 레포 생성 — 패키지에서 바로

**지금** — §2.3 C3 · C4. 서버의 레포는 `git clone <origin>` 뿐이다. origin 이
없는 패키지는 서버에 갈 수 없다.

**권장** — **`ctx repo new <경로> --package <이름> [--origin <url>] [--push]`.**

```
① 패키지의 완성 폴더(§3.2 packages/<이름>/)를 복사한다      "복사하면 그게 지식 레포다"
② work/.gitkeep · git init · core.hooksPath .githooks
③ 첫 커밋                                                  hooks 가 실제로 돈다 — ctx check 통과가 곧 검증
④ --origin 이 있으면 remote add · --push 면 push -u
```

같은 함수를 **관리 서비스가 부른다** — `POST /repos { name, package, origin? }`
(`write` 필요) → `<root>/<name>` 에 세우고 다음 요청부터 목록에 든다. 화면은
관리 > **지식 레포**(서버판) — 지금 서버 모드에서 빠져 있던 그 메뉴 자리에
**레포 목록 + 미러 상태 + 새 레포 만들기**가 들어간다. `GET /packages` 가 고를
목록을 낸다.

**설계서 §4.2 "등록 = 폴더를 두는 것" 은 그대로다.** `repo new` 는 그 폴더를
두는 한 가지 방법이고, clone 은 다른 방법이다. 서버가 **유일한 작성자**라는
것도 그대로다 — 세우는 것도 서버가 한다.

**왜 이것이 "레포 변환" 의 첫 답인가** — 변환의 절반은 *빈 레포를 규약대로
세우는 것*이다. 그것이 없으면 변환한 문서를 부을 자리가 없다.

## 4. 유지하는 결정 — 제품화가 뒤집지 않는 것

설계서 제4부(거부한 설계)와 MCP 설계서의 "하지 않는 것" 은 **그대로다.** 제품화
중에 "겸사겸사" 넣기 쉬운 것들이라 다시 적는다.

| | 왜 유지하나 |
|---|---|
| 판정은 `core/` 한 곳 | 새 명령(`repo new` · `import-dir` · `package check`)도 `core/` 를 부른다. 판정을 새로 짜지 않는다 |
| 기계가 merge · 자동 push 하지 않는다 | `upgrade.sh` 도 `repo new --push` 도 사람이 부른다 |
| 발급 엔드포인트 없음 | `init` 은 서버 셸의 CLI 다. HTTP 로 발급하지 않는다 |
| 알림 · 코멘트 · 구독 없음 | git 밖 상태는 명부 · 대장 둘 — **여기에 패키지 목록은 더하지 않는다.** 패키지는 폴더고 매니페스트는 그 폴더 안에 있다 |
| RAG · 임베딩 없음 | `import-dir` 가 좌표를 **추측하지 않는다.** `touches: []` 로 두고 사람이 P2 를 한다 |
| 관리 서비스에서 지식 레포 내용을 고치지 않는다 | 레포를 **세우는** 것은 내용을 고치는 것이 아니다. 세운 뒤 쓰기는 `save` 하나다 |
| 두 번째 패키지를 미리 만들지 않는다 | §3.4 — 표본이 하나다 |

## 5. 우선순위

```
P0  없으면 나머지가 무의미하다        CI · 테스트 · 하네스 수정 · Node 고정
P1  손이 가장 많이 드는 자리          서버 산출물 · install/upgrade/doctor/init · 패키지 매니페스트/검사 · repo new (CLI + 서버 + 화면)
P2  다음 프로젝트가 오면 바로 필요    import-dir · --desktop · --also · inspect 열 · 90일 경고 · Docker
P3  정리                               docs/README · attic 이동 · CHANGELOG · 절차서 재작성
```

의존 —

```
P0 CI ──▶ P1 서버 산출물 ──▶ install.sh · upgrade.sh
      └─▶ P1 패키지 매니페스트 ──▶ package check(CI) ──▶ repo new ──▶ 서버 POST /repos ──▶ 화면
      └─▶ P2 import-dir  (repo new 가 세운 레포에 붓는다)
```

**P0 이 관문이다.** P1 의 스크립트 넷은 각각 작지만 CI 없이는 "고쳤는데 깨졌다"
를 알 길이 없다. 그리고 P1 의 `repo new` 는 §3.2 의 조립 함수에 얹히므로
산출물 정리가 먼저다.

## 6. 1.0.0 의 조건

0.9.0 은 이 문서의 P0 · P1 이 닫히면 낸다. **1.0.0 은 따로 조건을 둔다** —
숫자는 약속이다.

- [ ] 서버 갱신을 `upgrade.sh` 로 세 번 이상 — 손으로 되돌린 적 없이
- [ ] 다른 팀의 md 폴더 하나를 `import-dir` 로 들였다
- [ ] "실제 작업 10건을 모드 B 로 완주"(MCP 설계서 §10 · 유일하게 남은 줄)

## 8. 위험 · 열린 것

제품화가 만들거나 드러내는 위험이다. 막는 법이 있는 것은 옆에 적었다.

| 위험 | 어디서 | 막는 법 |
|---|---|---|
| CI 의 Windows 러너에서 SEA 빌드가 다르게 돈다(백신 없음 · 경로 공백 없음) | `release.yml` | 첫 태그 릴리스를 **로컬 릴리스와 `ctx version` · 크기로 대조**한다. 다르면 로컬을 정본으로 |
| `repo new --push` 가 서버에서 origin 에 빈 레포를 만들 수 없다 — GitLab 프로젝트는 웹에서 만든다 | §3.5 | `--origin` 은 **이미 있는** 빈 프로젝트 주소다. 화면이 그것을 말한다 |
| `import-dir` 가 만든 `work/` 761건이 `touches: []` 로 서서 **좌표가 하나도 없는 레포**가 된다 | §3.6 | 의도다. P2(사람 · LLM · `cdp-import`)가 채운다. 보고서가 "좌표 0건" 을 말한다 |
| 서버 `packages/` 가 낡는다 — 서버 판과 소스 판이 다른 패키지를 든다 | §3.4 | 매니페스트 `version` · `upgrade.sh` 가 `packages/` 도 같이 갈아 낀다 |
| 하네스가 CI 에서 포트 7377 · git 사용자 설정 · 한글 경로에 걸린다 | §3.1 | `core.quotepath=false` 는 이미 넣었다. 포트는 인자로 · git 사용자는 `-c` 로 |
| `_package.json` 을 지식 레포에 부으면 **레포 안에 남는다** | §3.4 | 조립 때 뺀다 — 받는 사람에게 갈 것이 아니다(`agent/README` 의 판정 기준) |

**열린 것** — 운영자가 언제든 뒤집을 수 있게 남긴다.

1. Windows 서버는 고려하지 않았다. 확정 배치가 Linux 다.
2. 프록시(TLS)를 기본으로 켤지는 배치가 정한다. `install.sh` 는 Caddy 줄을 **주석**으로 낸다.
3. 관리 서비스의 명부 조회(읽기)는 넣지 않았다. 명부는 서버 셸의 것이라는 결정을 지켰다 — 화면에 사람 목록이 뜨는 것은 `workrepos` 의 담당자 선택뿐이다.
