## 0. 세고 나서 정했다

입도를 논하기 전에 **개수를 셌다.** 같은 실수를 두 번 했기 때문이다 —
프로그램목록의 `TAB ID` 도, 요구사항정의서의 추적 컬럼도 **헤더는 있는데 값이
0건**이었고 둘 다 세어 보고서야 알았다.

| 좌표 | 개수 | 원천 | 실측 메모 |
|---|--:|---|---|
| `req:` | **214** | 요구사항정의서 | RFP 84 + 현업 130. **추적 컬럼 0건** |
| `proc:` | **15** | 프로세스정의서 | 3단 번호. 4단 액티비티는 121개 |
| `func:` | **57** | 기능정의서 | 그중 52건이 프로그램과 연결돼 있다 |
| `arch:` | **4** | — | **원본에 ID 가 없다.** 장 4개를 팀이 등록 |
| `screen:` | **200** | 프로그램목록 TOBE | 프로그램 96 + 하위 104. **TAB ID 0건** |
| `prog:` | **200** | 같은 값 | `screen:` 과 ID 공간을 공유 |
| `table:` | **76** | 테이블정의서 `GDI` 블록 | 테이블목록 TO-BE 는 46 — **수가 다르다** |
| `term:` | 5,123 / 1,726 | DB도메인용어집 | 도메인 / 용어사전. **단위 미정** |
| `code:` | **181** | 코드정의서 공통코드마스터 | 업무구분 + 구분코드 |
| `api:` | **27** | 인터페이스정의서 | 처음에 10건이라 적었던 것을 고친다 |
| `batch:` | **15** | 그중 `처리형태 = Batch` | `Object` 가 채워진 것은 **14건** |
| `scenario:` | **100** | 통합테스트 시나리오 4시트 | 27+22+23+28. **프로그램과 1:1** |
| `issue:` | **0** | 위험및이슈관리대장 | **대장에 예시 1행뿐** |

`term:` 을 빼면 **1,089건**이다.

### `issue:` 가 0 이라는 것

대장 시트에 데이터 행이 **`ex) GDI-RIS-01` 하나**뿐이다. 실제 이슈는 건별
시트 6장(`SJ-RIS-01`~`06`)에만 있고, 그중 **4장은 머리가 `SJ-RIS-01` 로 남아
있다** — 복사하고 안 고친 것이다.

> **대장이 운영되지 않았다.** 이것이 이 패키지가 고치려는 것의 표본이다 —
> 문서가 없어서가 아니라 **작업과 문서가 이어져 있지 않아서** 비었다.
> CDP 에서는 `issue:` 좌표를 건드린 작업 기록이 있는데 섹션이 안 고쳐지면
> **커밋이 막힌다.**

## 1. D3 확정 — `screen:` 과 `prog:` 는 같은 ID 공간을 쓴다

| | |
|---|---|
| 값 | 프로그램ID · 하위프로그램ID. `ACA010` `ACA011` `SEA011` — **200개** |
| 합성 | **하지 않는다.** `ACA010`(목록)과 `ACA011`(등록)은 형제다 |
| TAB | **좌표가 아니다.** `TAB ID` 컬럼이 200행 전부 비어 있다 |

`screen:ACA010` 과 `prog:ACA010` 은 **같은 대상의 두 얼굴**이다 —
설계(화면설계서)와 구현(프로그램사양서). 등록부는 패턴 하나에 문서 하나라
충돌 없이 갈린다.

> 화면설계서 한 화면이 슬라이드 여럿에 걸치고 `화면(TAB)명` 으로 나뉘지만,
> **식별자가 없으므로 좌표로 쓸 수 없다.** TAB 은 섹션 안의 소제목으로
> 내린다.

## 2. D4 확정 — `scenario:` 는 프로그램ID, `test:` 는 쓰지 않는다

통합테스트 시나리오 100행이 **프로그램 100개와 1:1**이다. 담당자별로 시트가
갈려 있을 뿐 한 프로그램에 한 시나리오다.

```
scenario:IT-BDA010     통합테스트 시나리오
scenario:UT-BDA010     단위테스트 시나리오
scenario:PT-BDA010     성능테스트 시나리오
```

**단계 접두를 붙인다.** 형상관리대장이 셋을 별개 산출물로 세고 제출시기도
다르다(구현완료 / 테스트완료). 문서를 셋으로 두고 패턴도 셋이다.

**`test:`(테스트케이스)는 등록부에서 뺀다.** CDP 16종에는 있지만
**DPMS 47종에 대응하는 산출물이 없다**(분석 §4). 없는 문서를 가리키는 패턴을
두면 `ctx check` 가 앵커 없음을 낸다.

## 3. `proc:` 입도 — 3단 번호

| 단 | 개수 | 예 | 판정 |
|---|--:|---|---|
| 2단 | 6 | `1.1 연구과제선정` | **굵다.** 업무 영역에 가깝다 — `domain:` 축이다 |
| **3단** | **15** | `1.1.1 과제접수` · `1.2.1 수행심의관리` | **이것** |
| 4단 | 121 | `1.2.3.12 시외출장비 지급내역 조회` | **잘다.** 액티비티 하나하나다 |

3단이 기능정의서의 **중분류**와 대응한다 — `과제접수` · `수행심의관리` ·
`연구계획변경`. 두 문서가 같은 단위를 쓰고 있다는 뜻이다.

> **번호를 좌표로 쓰는 위험을 안다.** 재부여되면 좌표가 통째로 깨진다.
> 그래도 번호로 가는 이유는 **원본이 번호로 상호참조**하기 때문이다
> (슬라이드 안에서 `1.2.3.12` 를 가리킨다). 재부여 위험은 `_vocab.md` 의
> `aliases` 와 `deprecated` 로 흡수한다 — CDP 가 그 장치를 갖고 있다.

## 4. `batch:` 기준 — `처리형태 = Batch` 인 것만

27건 중 15건이다. 값은 `Object` 컬럼(`G20BdStradeInfoBatchJob`).

**15건 중 1건은 `Object` 가 비어 있다.** 그 건은 `batch:` 좌표를 만들 수 없고,
`api:` 좌표만 갖는다. 억지로 이름을 지어내지 않는다.

## 5. `term:` — D 실측으로 넘긴다

도메인(5,123) 인지 용어사전(1,726) 인지 정하지 않는다. **둘 다 CDP 가 실측한
최대(159섹션)를 한참 넘는다.** 크기가 감당되는지 보고 정하는 것이 순서다.

## 6. `arch:` — 팀이 등록하는 유일한 타입

| 값 | 무엇 |
|---|---|
| `arch:hw` | H/W 아키텍처 — 서버 · 이중화 · 망구분 |
| `arch:db` | DB 아키텍처 — 스키마 · 유저 · 접근제어 |
| `arch:sw` | S/W 아키텍처 — 라이브러리 · 버전 |
| `arch:link` | 데이터 연계 — ESB · A10 |

다른 타입은 문서에서 값을 뽑아낼 수 있지만 **이것만 원본에 ID 가 없다.**
`_vocab.md` 에 넷을 손으로 적어야 좌표가 성립한다.

## 7. `domain:` — 등록부에 올리지 않는다

DPMS 의 **업무구분**이 그 축이다 — `SY` 시스템 · `MY` 마이페이지 · `PS` 인사 ·
`AC` 회계 · `BD` 예산 · `CT` 계약 · `GW` 전자결재 · `SE` 연구과제선정 ·
`EX` 연구과제수행 · `MG` 연구과제관리.

업무 영역에는 "지금 상태" 라고 적을 것이 없다. **산출물이 아니라 작업을 묶는
축**이라 등록부에도 없고 최신성 계산에서도 뺀다(CDP `등록부_관리문서16종.md`).

> **업무구분 코드가 문서마다 다르다.** 코드정의서는 `RP`(연구과제) 하나로
> 묶는데 프로그램목록은 `SE`·`EX`·`MG` 셋으로 쪼갠다. `_vocab.md` 에
> 정본을 정하고 나머지를 `aliases` 로 건다 — **어휘 파일이 바로 이런
> 자리를 위해 있다.**

### CDP 16종판에서 바뀐 셋

| | 16종판 | 47종판 | 왜 |
|---|---|---|---|
| `batch:` | 프로그램사양서 | **인터페이스정의서** | DPMS 에서 배치는 인터페이스의 `Object` 다 |
| `module:` | 프로그램사양서 | **뺀다** | DPMS 47종에 대응 개념이 없다 |
| `test:` | 테스트케이스 | **뺀다** | 테스트케이스라는 산출물이 없다 |
| `scenario:` | 테스트시나리오 1개 | **3개로 쪼갠다** | 형상관리대장이 단위·성능·통합을 별개로 세고 제출시기가 다르다 |

### 패턴 순서가 중요한 자리

`scenario:` 셋은 **접두가 겹치지 않으므로** 순서를 안 타지만, 나중에
`scenario:*` 같은 포괄 패턴을 더하면 **반드시 셋 뒤에** 놓아야 한다.
위에서부터 먼저 걸리는 것을 쓰기 때문이다.

> **주의 — 패턴은 대소문자를 구분한다.** `patternToRegex` 가 플래그 없이
> 정규식을 만든다([managed.js:25](../../core/managed.js:25)).
> `scenario:ut-BDA010` 은 `scenario:UT-*` 에 **안 걸린다.**
>
> 그런데 **섹션 값 비교는 대소문자를 무시한다**([managed.js:156](../../core/managed.js:156)).
> 규칙이 둘로 다르다. 좌표 표기를 `_vocab.md` 에 하나로 고정해야 하는 이유다.

## 9. `_vocab.md` — 타입과 순서

**`## <타입>` 섹션 제목이 곧 타입이고, 그 순서가 화면·CLI 의 카테고리
순서다**(CDP 시스템설계서 §1.1). 알파벳순으로 다시 매기지 않는다.

타입 이름은 자유롭다 — 파서가 `## <이름>` 을 그대로 받고 좌표 형식만
`타입:값`(공백 없음)으로 검사한다([vocab.js:14](../../core/vocab.js:14)).
**`req:` `proc:` `func:` `arch:` `scenario:` 를 쓰는 데 코드 변경이 필요 없다.**

### 순서 — 사업 흐름을 따른다

```
req  →  proc  →  func  →  arch  →  screen  →  prog
                                      ↓
              table  ←  term  ←  code  ←  api  →  batch
                                      ↓
                            scenario  →  issue  →  domain
```

`_vocab.md` 섹션 순서 —

```markdown
# 좌표 어휘

## req        요구사항
## proc       프로세스
## func       기능
## arch       아키텍처        ← 값 4개를 손으로 적는다
## screen     화면
## prog       프로그램
## table      테이블
## term       용어
## code       코드
## api        인터페이스
## batch      배치
## scenario   테스트 시나리오
## issue      이슈
## domain     업무 영역       ← 등록부 비대상. 계산에서도 뺀다
```

**분석 순서가 아니라 찾는 순서다.** 요구사항에서 시작해 화면·프로그램으로
내려가고, 데이터(테이블·용어·코드)와 연계(api·batch)를 거쳐 시험·이슈로
끝난다. 사람이 "그 화면 어디 있지" 를 물을 때 훑는 순서와 같다.

### aliases 가 핵심이다

DPMS 는 같은 대상을 문서마다 다르게 부른다. 어휘 파일이 그것을 하나로 모은다.

```markdown
## table

- `table:rp_plnd_mst` — 계획서마스터
  aliases: 계획서, 계획서테이블, 연구계획서, RP_PLND_MST

## domain

- `domain:RP` — 연구과제
  aliases: SE, EX, MG, 연구과제선정, 연구과제수행, 연구과제관리
```

마지막 줄이 실제 문제를 푼다 — **코드정의서는 `RP` 하나인데 프로그램목록은
`SE`·`EX`·`MG` 셋이다**(§7).

## 10. 등록부 비대상 — 33종

47종 중 등록부에 올리는 것은 **14종**이고 나머지 **33종**은 비대상이다.
비대상은 결함이 아니다 — **파생이 필요 없다는 뜻**이고, 원천은 그 작업
기록 자체다(CDP 수행 설계서 §1.2).

| 유형 | 종수 | 왜 비대상인가 |
|---|--:|---|
| 대장형 | 10 | 집계·추적·진행이다. 좌표-섹션이 1:1이 아니다 |
| 사건형 | 10 | 날짜축이다. 회의·보고·결과는 대상이 아니라 사건이다 |
| 서술형 | 13 | 쪼갤 대상이 없다. 문서 전체가 내용이다 |

**앱은 이 33종을 문서로 읽고 열 수 있다.** 섹션 판정만 하지 않는다.

### 특히 헷갈리는 셋

| | |
|---|---|
| **프로그램목록** | `prog:` 를 다루지만 **집계**다. 각 프로그램의 내용은 프로그램사양서가 갖는다 |
| **데이터이관정의서 · ERD모델링** | **테이블**을 다루지만 정본은 테이블정의서다. 셋이 `table:*` 을 나눠 가질 수 없다 |
| **테스트 결과서 3종** | 시나리오는 상태이고 **결과는 사건**이다. 회차마다 쌓인다 |

## 11. C 에서 정하지 못한 것

| | 어디서 |
|---|---|
| `term:` 섹션 단위 — 도메인(5,123) vs 용어사전(1,726) | **D 실측** |
| 통합테스트 시나리오 100건의 프로그램ID 매핑 (원본은 한글 프로그램명) | D 변환 |
| `proc:` 번호 재부여가 실제로 일어나는가 | 운영에서 |
