## 방법 — 문서마다 넷을 묻는다

| | 묻는 것 | 왜 |
|---|---|---|
| ① **섹션 단위** | 무엇 하나가 `##` 하나인가 | 그것이 좌표다 |
| ② **상태** | "지금 어떻게 생겼나" 로 섹션에 들어갈 것 | 덮어쓰는 부분 |
| ③ **이력** | 바뀐 것을 어디에 적나. **원본은 이미 어떻게 하고 있나** | 붙여쓰는 부분 |
| ④ **등록부** | 좌표-섹션이 1:1 인가 | 아니면 등록부 비대상 |

**③이 핵심이다.** CDP 는 섹션마다 `<!-- applied: -->` 와 변경 목록을 요구하는데,
그것을 **원본이 이미 하고 있는지** 봐야 새로 만드는 부담인지 옮기는 일인지
갈린다. 실제로 셋 다 있었다 — §관통하는 발견.

> **"그날 그렇게 나왔다"** 이다. 시나리오는 대상(프로그램)에 붙고 상태가
> 갱신되지만, 결과는 회차마다 쌓인다. 원본도 그렇게 돼 있다 — 통합테스트
> 시트의 `테스트일자` · `결과(PASS·FAIL)` 컬럼이 회차를 찍는다.

## A2. 좌표형 심층 분석

### 테이블정의서 `table:` — 블록이 이미 CDP 섹션이다

5시트. 실질은 **`GDI` 시트**이고, 이것이 **54행 고정 블록 × 77개** 반복이다
(이름 있는 것 76개).

```
+0   DB USER            │ DB USER
+1   테이블 명(논리)      │ 테이블 명(논리)  → 보고서마스터
+2   테이블 명(물리)      │ 테이블 명(물리)  → RP_RPDC_MST
+3   TABLE COLUMN Key TYPE NULLABLE DEFAULT COMMENT │ LOGICAL PHYSICAL Key TYPE NULLABLE DEFAULT COMMENT 비고
+4…  컬럼 행                    ← AS-IS(1~7열) ↔ TO-BE(9~16열) 대칭
+47  변경 대상 │ 번호 │ 구분 │ 변경 명     ← **이력**
+48    1.0
+49    2.0
+50    3.0
+51  기타 특이 사항
```

| | |
|---|---|
| ① 섹션 | 테이블 하나 = 블록 하나. `table:rp_rpdc_mst` |
| ② 상태 | 컬럼 표. AS-IS ↔ TO-BE 두 벌 |
| ③ 이력 | **자리가 있다.** `변경 대상 / 번호(1.0 2.0 3.0) / 구분 / 변경 명`. 다만 **76블록 전부 비어 있다** |
| ④ 등록부 | ✔ `table:*` → `docs/테이블정의서.md` `## {값}` |

**③이 결정적이다.** 원본이 [머리 + 상태 + 이력 + 비고] 4부이고 CDP 섹션
구조와 1:1로 맞는다.

> **다만 이력과 비고는 76블록 전부 비어 있다**([`05_실측.md`](05_실측.md) §2).
> "이미 하고 있는 것을 꺼낸다" 가 아니라 **"하려고 자리를 만들어 두고 못 한
> 것을 돌아가게 한다"** 가 맞는 말이다. 자리를 설계했다는 것은 필요하다고
> 합의했다는 뜻이고, 비어 있다는 것은 **강제가 없었다**는 뜻이다.

`번호 1.0 / 2.0 / 3.0` 은 형상관리대장의 버전 칸(`최초 승인일 1.0` ·
`변경일 1.1~1.4`)과 같은 체계다. 문서 단위 버전과 섹션 단위 변경이 **같은
번호 체계를 쓰고 있다.**

**다른 시트**

| 시트 | 행 | 무엇 |
|---|--:|---|
| 테이블목록 | 3,306 | AS-IS 354 ↔ TO-BE 46 대응표 → **대장형** |
| 뷰목록 | — | 비어 있다 |
| GDI | 4,932 | 위의 블록 77개 |
| 도메인 | 2,958 | **DB도메인용어집과 중복** |
| 코드 | 1,000 | **코드정의서와 중복** |

> **중복 셋을 정리해야 한다.** 테이블정의서 안에 도메인·코드가 사본으로 들어
> 있다. 엑셀에서는 참조 편의였겠지만 MD 로 옮기면 **정본이 둘**이 된다.
> 패키지는 사본을 만들지 않고 좌표로 건다 — `term:` · `code:` 로.

**AS-IS ↔ TO-BE 가 문제다.** CDP 관리 문서는 "지금 상태" 하나다. AS-IS 는
지금이 아니라 과거다. 셋 중 하나를 골라야 한다.

| | |
|---|---|
| TO-BE 만 싣는다 | 깨끗하다. **이관 중에는 AS-IS 를 봐야 한다** |
| 둘 다 싣는다 | 표가 두 배. "지금" 이 흐려진다 |
| TO-BE 가 상태 · AS-IS 는 이관 대장으로 | **권고.** 대응표는 이미 `테이블목록` 시트에 따로 있다 |

### DB도메인용어정의서 `term:` — 3층인데 좌표는 한 층이다

3시트. 셋이 층이 다르다.

| 시트 | 행 | 단위 | 예 |
|---|--:|---|---|
| **도메인** | 5,123 | 완성된 용어 | `가격배수값` → `PRICE_MLTP_VAL` · `NUMERIC(6,2)` |
| **용어사전** | 1,726 | 어절(단어) | `가격` → `PRICE` |
| **도메인분류** | 56 | 접미어 규칙 | `AMT` = 금액 = `BIGINT` |

도메인 시트 컬럼 —
`명칭1~7`(어절 분해) · `Logical` · `Physical` · `Desciption` · `접미어` ·
`Type` · `Length` · **`등록PL` `등록일자` `수정PL` `수정일자`** · `비고`

| | |
|---|---|
| ① 섹션 | **결정 필요.** 도메인(5,123) 인가 용어사전(1,726) 인가 |
| ② 상태 | 논리명 · 물리명 · 타입 · 길이 · 접미어 · 어절 분해 |
| ③ 이력 | **있다.** 행마다 `등록PL/등록일자/수정PL/수정일자`, 용어사전엔 `수정내용` 까지 |
| ④ 등록부 | ✔ `term:*` → `### {값}` |

**섹션 수가 문제다.** 도메인을 섹션으로 잡으면 MD 하나에 `###` 5,123개다.
CDP 가 실측한 최대는 159개다(§7). **D 단계 실측 전에는 정하지 않는다.**

> 세 층을 세 문서로 쪼개는 안도 있다. 다만 CDP 16종은 `DB도메인용어정의서`
> 하나이고, **쪼개면 등록부 패턴이 층 이름에 묶인다** — 화면을 업무별로
> 쪼갰다가 되돌린 전례가 있다(`등록부_관리문서16종.md`).

### 코드정의서 `code:` — 2층. 섹션은 코드구분이다

10시트 = 흐름도 1 + **공통코드마스터** 1 + 업무별 코드상세 8(RP·AC·BD·CT·GW·PS + ASIS 2).

```
공통코드마스터   업무구분 / 업무구분명 / 구분코드 / 구분명 / 사용여부 / 시스템     181건
코드상세        업무구분 / 코드구분 / 코드구분명 / 코드 / 코드명 / 영문명 /
                신규·사용여부 / 정렬순서 / 연관업무구분 · 연관코드구분 ·
                연관공통코드 / 코드속성1~5
```

| | |
|---|---|
| ① 섹션 | **코드구분** = 업무구분 + 구분코드. `code:PS001`(직종) · `code:RP010`(연구분류) |
| ② 상태 | 그 구분에 속한 코드 목록 표 + 연관 관계 |
| ③ 이력 | **없다.** `신규여부` 가 있지만 언제·왜가 없다 |
| ④ 등록부 | ✔ `code:*` → `## {값}` |

**코드 하나하나(`code:RP010010`)를 섹션으로 잡지 않는다.** 코드는 목록으로
읽고 통째로 바뀐다 — "연구분류에 뭐가 있나" 를 묻지 "정책과제 코드가 어떻게
생겼나" 를 묻지 않는다. 181섹션은 CDP 실측 범위 안이다.

### 인터페이스정의서 `api:` `batch:` — 요약 1행 + 상세 1시트

23시트 = 정의서 1 + 다이어그램 1 + **인터페이스별 상세 21**.

정의서 시트(요약) —
`인터페이스ID / 명 / 설명 / 사용여부` +
**Source**(`시스템 / Database / Table`) + **Target**(같음) +
`전송주체 / 처리형태 / Batch구분 / 주기 / 실행시간 / 연계방식 / 연계기술 / Object`

상세 시트 —
```
인터페이스 그룹   연구통합시스템 -> 더존 알리미
인터페이스 ID    INT_RP_1009     인터페이스 명  결의서 연동현황
인터페이스 내용   G20 결의서 연동 현황
인터페이스 개요   (도해)
No │ Table Name │ Column Name │ Attribute Name │ Datatype │ PK │ NULL │ Value │ Default
```

| | |
|---|---|
| ① 섹션 | 인터페이스 하나. `api:INT_RP_1009` |
| ② 상태 | 요약 행(Source↔Target·주기·방식) **+ 컬럼 매핑표** |
| ③ 이력 | 없다 |
| ④ 등록부 | ✔ `api:*` → `## {값}` |

**요약과 상세가 갈려 있는 것이 MD 에서는 합쳐진다.** 엑셀은 한눈에 보려고
요약 시트를 따로 뒀지만, MD 는 섹션 하나에 둘 다 들어가고 **목록이 필요하면
`INDEX.md` 가 만든다.**

**세어 보니 27건**이다(앞 10건만 보고 10건이라 적었던 것을 고친다).
`처리형태` 값은 `Batch`(15) · `실시간` · `수동` 셋이고, `Object` 가 채워진
것은 15건 중 **14건**이다. `batch:` 는 처리형태가 `Batch` 인 것에만 붙인다.

### 요구사항정의서 `req:` — 추적 컬럼이 비어 있다

15시트 = 총괄표 + 공식산출물 + **분류별 13**(CNR ECR SFR SER DAR SOR COR PER QUR TER SIR PMR PSR).

분류 시트 공통 컬럼 —
`RFPID / RFP명 / RFP산출물 / 요구사항ID / 유형 / 요구사항 상세내역 /
요구사항 출처 / 식별일자 / 협의조정내용 / 수용여부 / 비고` +
추적 `검사기준 / 설계단계 / 구축단계 / 시험단계 / 안정화단계 / 완료여부`

**기능(SFR) 시트에만 추적 컬럼이 더 붙는다** —
`화면설계서 / 유형 / 화면ID / 화면명 / 프로그램ID / 프로그램명 / 시험ID / 시험명`

| | |
|---|---|
| ① 섹션 | 요구사항 하나. `req:SFR-01-01` · `req:CNR-02-01` |
| ② 상태 | 상세내역 · 출처 · 수용여부 · 검사기준 · 단계별 진행 |
| ③ 이력 | `식별일자` · `협의조정내용` 이 사실상 이력. 다만 **한 칸에 뭉쳐 있다** |
| ④ 등록부 | ✔ `req:*` → `## {값}` |

**추적 컬럼은 자리만 있고 비어 있다.**

```
요구사항ID  84건        화면ID 0 · 프로그램ID 0 · 시험ID 0
```

> **처음에 이 자리에 "가장 큰 소득" 이라고 썼다. 틀렸다.** 헤더를 보고
> 채워져 있다고 단정했다. 세어 보니 84개 요구사항 중 **한 건도 연결되어
> 있지 않다.** 프로그램목록의 `TAB ID` 와 같은 경우다 — 컬럼은 설계됐고
> 아무도 채우지 않았다.

**그래서 결론이 뒤집힌다.** `req:` → `screen:` → `prog:` → `scenario:` 연결은
**DPMS 에 없다.** 추적표를 생성물로 내릴 수 없다 — 생성할 원천이 없기 때문이다.

대신 **그 칸을 채우는 것이 이 패키지가 하는 일**이 된다. CDP 좌표가 곧 그
연결이므로, 작업 기록이 `touches: [req:SFR-02-03, screen:SEA010]` 을 적는
순간 추적이 **계산으로** 생긴다. 손으로 채워야 비는 칸이 없어진다.

**두 벌(RFP · 현업)은 ID 공간도 구조도 다르다** — 현업본을 열어 확인했다.

| | RFP본 | 현업본 |
|---|---|---|
| ID | `SFR-01-01` `CNR-02-01` `SER-01-03` | `USR-RP-01` `USR-GW-06` `USR-AC-01` |
| 시트 | 총괄 + 공식산출물 + 분류별 13 | 참고 + 요구사항 + 수기관리 + 정리용 + **건별 상세 17** |
| 축 | 제안요청서 항목 → 요구사항 | **수집 → 내부검토 → 현업협의** 3단 |
| 건수 | 58 (총괄표 합계) | 130 |

**ID 가 겹치지 않으므로 한 문서에 합쳐도 충돌하지 않는다.** `req:SFR-01-01` 과
`req:USR-RP-01` 이 같은 등록부 패턴 `req:*` 아래 공존한다.

현업본 컬럼 —
`요구사항ID / 업무구분 / 시스템 / 상세구분` ·
`요구사항내용 / 요청자 / **출처** / 수집일자` ·
`검토내용 / 검토수용` · `협의내용 / 협의일자 / 협의수용` · `비고`

**`출처` 컬럼이 회의록 파일을 가리킨다** — `GDI_BM_411_회의록_251224_착수미팅.docx`.
요구사항이 **어느 사건에서 나왔는지**를 원본이 이미 적고 있다. CDP 로 치면
정본 문서 섹션에서 `work/` 작업 기록으로 거는 링크와 같은 자리다.

### 기능정의서 `func:` — 가로축이 업무 흐름이다

1시트. `서비스 / 대분류 / 중분류 / 기능ID / **단계 1~8** / 내용 /
담당자·부서 / 프로그램ID / 프로그램명`

`단계 1~8` 은 컬럼 8개이고 각각 `필수 · 선택 · 조건` 으로 표시된다. 기능 하나가
그중 **한 칸**에 놓여 업무 흐름 상의 위치를 나타낸다.

| | |
|---|---|
| ① 섹션 | 기능 하나. `func:FNC_RP_01` |
| ② 상태 | 분류 · 단계 · 내용 · 담당 · 연결된 프로그램 |
| ③ 이력 | 없다 |
| ④ 등록부 | ✔ `func:*` → `## {값}` |

**가로 8칸을 MD 로 어떻게 옮기나.** 표를 그대로 옮기면 빈칸 7개가 따라온다.
`단계: 3 (조건)` 처럼 **값 하나로 접는 것**이 맞다 — 표의 가로 위치는
엑셀에서 흐름을 눈으로 보려던 장치이지 데이터가 아니다.

### 위험및이슈관리대장 `issue:` — 작성지침 시트가 서식의 원본이다

8시트 = 대장 1 + **건별 내역서 6** + **작성지침 1**.

대장은 3단 그룹이다 —
`식별`(ID · 유형 · 관련 영역 · 식별단계 · 이슈명 · 발생일 · 내역 설명) ·
`해결방안 수립`(처리 담당자 · 해결방안 · 완료 예정일) ·
`해결`(진행상태 · 이슈 해결일 · 처리자)

내역서는 `이슈명 / 식별ID / 작성자 / 발생일 / 완료예정일 / 최종완료일` +
**이슈 내용 · 위험 원인 분석 · 해결 결과** 세 서술 영역.

| | |
|---|---|
| ① 섹션 | 이슈 하나. `issue:SJ-RIS-01` |
| ② 상태 | 진행상태 · 담당 · 해결방안 · 기일 |
| ③ 이력 | **해결 결과 영역이 날짜별로 쌓인다** — `<7/5 기준> …` `<8/9 기준> …` |
| ④ 등록부 | ✔ `issue:*` → `## {값}` |

**`작성지침` 시트가 그대로 서식 명세다.** 항목마다 `구분 / 항목명 / 작성방법 /
필수·선택` 이 적혀 있고, **실제 대장보다 필드가 많다** — `제기자` `관리범위`
`중요도` `긴급도` `협조사항` 은 지침에 있는데 대장에는 컬럼이 없다.

> 지침과 실물이 어긋나 있다. 패키지는 **지침을 따른다** — 지침이 표준이고
> 대장은 그 프로젝트의 구현이다. 다만 필수/선택 구분은 그대로 가져간다.

대장과 내역서가 **1:1 이 아니다.** 내역서 6장 중 `SJ-RIS-02`~`04` 의 머리가
전부 `SJ-RIS-01` 로 남아 있다 — 복사하고 안 고친 것이다. **MD 로 옮기면
섹션 이름이 곧 ID 라 이런 어긋남이 구조적으로 불가능해진다.**

### 화면설계서 `screen:` · 프로그램사양서 `prog:` — D3 의 답이 나왔다

**프로그램목록(TOBE)을 실측했다.**

```
프로그램ID        96개   ACA010 ACB010 BDA010 CLA010 …
하위프로그램ID   104개   ACA011 ACB011 ACC011 ACC012 …
TAB ID            0개   ← **컬럼은 있는데 전부 비어 있다**
TAB명             0개   ← 마찬가지
```

**결론 셋.**

| | |
|---|---|
| 1 | `프로그램ID` 와 `하위프로그램ID` 는 **같은 ID 공간**이다. `ACA010`(목록) · `ACA011`(등록)이 형제이고 부모-자식 합성이 필요 없다 |
| 2 | 화면설계서의 `화면(TAB)명` 은 **좌표가 될 수 없다.** 식별자(TAB ID)가 비어 있어 이름으로만 구분된다 |
| 3 | 좌표 값은 **200개**(96 + 104)이고 `screen:` 과 `prog:` 가 그 값을 공유한다 |

즉 **`screen:ACA010` 과 `prog:ACA010` 은 같은 대상의 두 얼굴**이다 — 설계(화면
설계서)와 구현(프로그램사양서). CDP 등록부는 패턴 하나에 문서 하나이므로
`screen:*` → 화면설계서, `prog:*` → 프로그램사양서로 **충돌 없이 갈린다.**

화면설계서 실물(147장)은 화면마다 머리가 붙는다 —
`업무구분 / 분류 / 프로그램ID / 프로그램명 / 화면(TAB)명 / AS-IS 프로그램` +
화면개요 및 레이아웃. **한 화면이 슬라이드 여럿에 걸친다**(`SMB010` +
브랜드일목표가 슬라이드 18·19·20). MD 로는 섹션 하나다.

프로그램사양서(◐ 타 프로젝트)는 프로그램마다 —
`서비스 / 업무구분 / 분류 / 프로그램ID / 프로그램명 / 담당PL` + 화면 +
**동작·테이블 대응표**(`화면 / 탭 / 동작1 / 동작2 / 테이블(ASIS) / 테이블(TOBE)`) +
컬럼정보.

> **동작·테이블 대응표가 `prog:` ↔ `table:` 을 잇는다.** 요구사항정의서의
> 추적 컬럼과 같은 역할이다 — 좌표 사이의 연결이 원본에 이미 적혀 있다.

### 프로세스정의서 `proc:` — 흐름도를 텍스트로 어떻게 옮기나

40장. 표지 · 개정이력/승인내역 · 구성도 · 이후 전부 **스윔레인 흐름도**다.
`INPUT / OUTPUT / 주체(연구원 · 과제 PM · 회계 담당자) / 번호 붙은 액티비티`.

| | |
|---|---|
| ① 섹션 | **입도 결정 필요.** `1.2`(프로세스) 인가 `1.2.3.1`(액티비티) 인가 |
| ② 상태 | 액티비티 목록 · 주체 · INPUT/OUTPUT · 분기 조건 |
| ③ 이력 | **문서 단위 개정이력 슬라이드가 있다** (개정 번호/범위/내역/작성자/일자) |
| ④ 등록부 | ✔ `proc:*` → `## {값}` |

**그림을 버리고 무엇을 남기나가 이 문서의 급소다.** 흐름도의 값은 순서와
분기인데 둘 다 텍스트로 적을 수 있다. 레이아웃은 버린다.

슬라이드 20 처럼 **설계 결함을 본문에 적어 둔 것**이 있다 — *"프로세스에 결함이
존재 … 히스토리가 관리되지 않는 문제 발생 … 프로세스로 변경 필요"*. 이건 상태가
아니라 **미결 아젠다**라서 CDP 에서는 `issue:` 로 간다(위험및이슈관리대장).

### 시스템아키텍처정의서 `arch:` — ID 가 없다

15장. 표지 · 승인내역 · 목차 · **1.H/W · 2.DB · 3.S/W · 4.데이터 연계**.
전부 표다 — 서버 · 이중화 · 망구분 · OS/CPU/Mem/Disk · 라이브러리 · 버전.

| | |
|---|---|
| ① 섹션 | **원본에 ID 가 없다.** 장(章)을 좌표로 삼는 수밖에 — `arch:hw` `arch:db` `arch:sw` `arch:link` |
| ② 상태 | 구성표 · 버전표 |
| ③ 이력 | 문서 단위 승인내역(구분 · 직책 · 성명 · 일자 · **버전** · 서명) |
| ④ 등록부 | ✔ 다만 값이 **4개뿐**이고 팀이 정한 이름이다 |

> `_vocab.md` 에 `arch:` 값 넷을 **팀이 등록해야** 좌표가 성립한다. 다른
> 좌표처럼 문서에서 뽑아낼 수 없는 유일한 타입이다.

## 관통하는 발견

### ① 이력이 이미 있다 — 세 가지 형태로

CDP 가 섹션마다 요구하는 "무엇이 언제 왜 바뀌었나" 를 **원본이 이미 기록하고
있다.** 다만 형태가 셋이고, 계산할 수 없는 자리에 있다.

| 형태 | 어디 | 예 |
|---|---|---|
| **섹션 단위 이력 영역** | 테이블정의서 블록 안 | `변경 대상 / 번호 1.0 2.0 3.0 / 구분 / 변경 명` |
| **행 단위 이력 컬럼** | DB도메인용어집 | `등록PL / 등록일자 / 수정PL / 수정일자 / 수정내용` |
| **문서 단위 개정이력** | pptx 4종 | 개정 번호 · 범위 · 내역 · 작성자 · 일자 |

| **셀 안 날짜 접두** | 요구사항정의서(현업) · 위험및이슈 | `[20260204] - 연구계획서 참여율과…` · `<7/5 기준> …` |

그리고 **아예 없는 것**이 있다 — 코드정의서 · 기능정의서 · 인터페이스정의서.

> **넷째 형태가 증상이다.** 엑셀에 이력을 적을 자리가 없으니 사람들이 셀 안에
> 날짜를 접두로 붙이기 시작했다. 두 문서에서 각각 다른 표기(`[20260204]` ·
> `<7/5 기준>`)로 나타났다 — 규약 없이 필요가 만든 것이다. **섹션 밑에
> 변경 목록을 두면 이 관행이 갈 자리가 생긴다.**

> 문서 단위 이력은 *"이 문서 어딘가 바뀌었다"* 까지만 말한다. 형상관리대장의
> 버전 칸(1.0 ~ 1.4)도 같다. **섹션 단위로 내려야** *"이 테이블이 왜
> 바뀌었나"* 를 말할 수 있고, 그것이 CDP 가 더하는 값이다.

### ② 좌표 사이의 연결이 원본에 적혀 있다

| 어디 | 잇는 것 |
|---|---|
| 요구사항정의서(현업) `출처` | `req:` → **회의록**(사건) · 130건 중 7개 파일 |
| ~~요구사항정의서 SFR 추적 컬럼~~ | ~~`req:`→`screen:`→`prog:`→`scenario:`~~ **컬럼은 있으나 0건** |
| 기능정의서 프로그램ID | `func:` → `prog:` |
| 프로그램사양서 동작·테이블 대응표 | `prog:` → `table:` |
| 인터페이스정의서 Source/Target Table | `api:` → `table:` |
| 코드정의서 연관업무구분·연관코드구분 | `code:` → `code:` |

**채워진 것과 빈 것이 갈린다.** 기능→프로그램(52/57) · 인터페이스→테이블 ·
코드→코드는 실제로 적혀 있고, **요구사항→화면/프로그램/시험은 0건**이다.
가장 중요한 연결이 비어 있다 — 그것이 `GDI_AN_112 요구사항추적표` 가 따로
있는데도 실물이 없는 이유일 것이다.

### ③ 사본이 정본과 섞여 있다

테이블정의서 안에 `도메인` 시트(2,958행)와 `코드` 시트가 들어 있다. 엑셀에서는
참조 편의지만 **MD 로 그대로 옮기면 정본이 둘**이 된다. 좌표로 걸고 사본은
만들지 않는다.

### ④ 작성지침이 이미 서식 명세다

위험및이슈관리대장의 `작성지침` 시트는 항목마다 `작성방법` 과 `필수/선택` 을
적어 두었다. **다른 문서에는 이런 시트가 없다.** 패키지는 이 형식을 47종
전부에 적용한다 — 서식에 "이 칸에 무엇을 어떻게 적나" 가 없으면 사람마다
다르게 적고, 그때부터 문서가 검색되지 않는다.
