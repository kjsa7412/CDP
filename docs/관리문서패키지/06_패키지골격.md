## 0. 패키지는 **서식**이지 내용이 아니다

| 패키지가 들고 있는 것 | 들고 있지 않은 것 |
|---|---|
| `docs/` 47개 — 머리 표 · 좌표 설명 · 작성지침 | DPMS 의 테이블 76개 · 용어 4,671개 |
| `_managed.md` 15 패턴 — **완성** | 그 프로젝트의 좌표 값 |
| `_vocab.md` 타입 14개 — **값은 0개** | |

값을 넣으면 그 패키지를 고른 다른 프로젝트에 **남의 프로젝트 데이터가 따라
들어온다.** 계획에서 말한 것은 "관리문서 템플릿" 이다.

> **D 에서 변환한 DPMS 실물은 패키지가 아니다.** 그것은 예제이고, 갈 자리는
> `viewer/fixture/` 다 — CDP 가 이미 도구(`repo-kit`)와 예제(`viewer/fixture`)를
> 갈라 두었고 패키지는 그중 도구 쪽에 선다.

## 1. D7 확정 — **부어 넣는다.** 도구를 만들지 않는다

```
xcopy /E /I ..\repo-kit\* .          도구 · 매뉴얼 · skill · 훅   (모든 프로젝트 공통)
xcopy /E /I ..\packages\dpms\* .     docs/ · _vocab.md · _managed.md   (고른 것)
```

**두 줄이다.** `ctx init --package` 도, 앱 화면도 만들지 않는다.

| 근거 | |
|---|---|
| 같은 동작을 같은 방식으로 | `install.md` ③ 이 이미 `xcopy` 다. 방식이 둘이면 어느 것이 맞는지 묻게 된다 |
| **부으면 그 순간 지식 레포가 된다** | `_vocab.md` 가 지식 레포의 표지다([ctx-cli.mjs:125](../../viewer/bin/ctx-cli.mjs:125)). 지금은 관리자가 손으로 만든다 |
| 검증은 이미 있다 | 부은 뒤 `ctx check` 가 돈다. 새 보증 층을 만들지 않는다 |
| 전례 | *"한 번 하는 일에 도구를 만들면 그 도구가 남아서 다음 사람을 헷갈리게 한다"* — `등록부_관리문서16종.md` |

**언제 도구를 만드나** — 패키지가 셋 이상이 되고 고르는 일이 실제로 번거로워질
때다. 그때는 무엇이 번거로운지 알고 만들게 된다. 지금 만들면 **쓰이지 않을
선택지를 먼저 설계하는 것**이다.

### `install.md` ③ 이 이렇게 바뀐다

지금 —

> 여기까지는 복사다. **진짜 설치는 그다음이다** — `MANUAL-관리자.md` 2장.
> `_vocab.md` · `_managed.md` · `docs/` 를 만든다.

바뀌면 —

```
③ 지식 레포
   mkdir C:\cdp && cd C:\cdp && git init
   xcopy /E /I <배포본>\repo-kit\* .
   xcopy /E /I <배포본>\packages\<고른 것>\* .     ← 이 줄이 새로 생긴다
   mkdir tools && copy <배포본>\cdp.exe tools\
   git config core.hooksPath .githooks
```

**"진짜 설치는 그다음이다" 가 없어진다.** 그 문장이 가리키던 세 가지를
패키지가 들고 온다.

## 2. 폴더 구조

```
packages/                   ← CDP 레포 루트에 새로 생긴다
  README.md                 패키지가 무엇인가 · 고르는 법 · 목록
  dpms/
    README.md               이 패키지는 무엇인가 · 어디서 왔나 · 47종 목록
    _vocab.md               좌표 타입 14개.  **값은 비어 있다**
    _managed.md             15 패턴 · 14 문서
    docs/                   47개 골격
```

### 만든 기록은 패키지 **밖**에 둔다

**`caa835a` 의 교훈이다.** viewer/fixture 의 테이블정의서는 생성 원천(GDI 덤프)이
개인 PC Desktop 에 있어서 **덤프 없는 PC 에서 시드를 돌리자 32섹션이 1섹션으로
줄었고 아무 말도 안 나왔다.**

그래서 **어디 있었는지와 어떻게 변환했는지**를 남긴다. 다만 패키지 안이
아니라 [`docs/attic/dpms-패키지/`](../attic/dpms-패키지/README.md) 다 —
`agent/` 의 판정 기준은 *"받는 사람에게 가는가"* 이고 이 기록은 **안 간다.**
받는 사람에게 변환기는 원본 xlsx 가 없어 돌릴 수도 없는 파일이다.

`attic` 이 원래 그런 것을 두는 자리다 — *"지웠어도 됐지만 어떻게
만들어졌나에 답할 수 있는 유일한 기록이라 남긴다."*

### 설계서 §2.8 폴더 원칙과의 자리

| | |
|---|---|
| `kit/` | 받는 사람에게 가는 것 — **모든 프로젝트가 같은 것을 받는다** |
| `agent/packages/` | 받는 사람에게 가는 것 — **프로젝트마다 고른다** |

둘 다 "받는 사람에게 가는가" 를 통과하지만 **고르는가**에서 갈린다. 그래서
`kit/` 안이 아니라 형제로 둔다.

## 5. viewer/fixture 강등 경로

[`00_계획검토.md`](00_계획검토.md) §5 에서 "제거가 아니라 강등" 이라고 한 것의
구체안이다.

> **정정 (실측 후)** — 아래 2단계는 처음에 *"패키지 docs/ 를 부으면 덤프
> 의존이 끊긴다"* 고 썼다. **틀렸다.** 패키지에는 내용이 없으므로 덤프 의존은
> 그대로다. 실제로 부어 보니 **오류 84건**이었다 — §8.

```
1단계   agent/packages/dpms/ 를 만든다                    ← 했다
2단계   seed_repo.py 가 패키지에서 **문서 머리와 작성지침만** 가져온다
        · 코드 안 문자열이 줄어든다
        · **내용(테이블 32섹션 · work 20건)은 seed 가 그대로 만든다**
3단계   (선택) viewer/fixture 를 out/ 로 내리고 추적을 끊는다
```

**`caa835a` 는 패키지가 풀지 않는다.** 그것은 따로, 더 싸게 풀린다 — §8.

**3단계는 지금 하지 않는다.** `npm run seed` 가 Python 을 요구하므로
(`ops/lib/seed.mjs` 가 `python`·`py`·`python3` 를 뒤지다 없으면 exit 1),
생성물로만 두면 fresh clone 에서 Python 없이 `npm start` 가 안 뜬다. 그
트레이드오프는 `.gitignore` 의 `bin/` 주석이 이미 반대쪽으로 결정해 두었다.

**2단계도 실질이 크지 않다.** 문서 머리와 작성지침을 한 곳에서 관리하게 될
뿐이고, viewer/fixture 의 내용은 여전히 `seed_repo.py` 와 덤프에서 온다.

## 6. 두 번째 패키지를 어떻게 만드나

```
agent/packages/dpms/ 를 복사해 이름을 바꾼다
  ├ _managed.md    대부분 그대로.  없는 문서의 패턴만 뺀다
  ├ _vocab.md      타입 목록 그대로.  쓰지 않는 타입만 뺀다
  ├ docs/          목록이 바뀐다 — 이것이 패키지의 차이다

그리고 만든 기록을 `docs/attic/<이름>-패키지/` 에 남긴다.
```

**규약([`03`](03_템플릿규약.md))과 좌표 설계([`04`](04_좌표와등록부.md))는 패키지
사이에서 공유된다.** 패키지마다 다른 것은 **문서 목록**뿐이다.

> 그래서 규약과 좌표 설계는 `agent/packages/` 가 아니라 `docs/` 에 둔다. 패키지에
> 복사해 넣으면 두 벌이 되고, 두 벌은 갈라진다.

## 7. 만들었고, 부어서 검증했다

설계로 끝내지 않고 [`agent/packages/dpms/`](../../agent/packages/dpms/README.md) 를 실제로
만들었다.

```
packages/
  README.md
  dpms/
    README.md      46개 목록 · 첫날 절차 · 알려진 한계
    _managed.md    15 패턴 · 14 문서
    _vocab.md      타입 14개 (arch: 넷만 값이 있다)
    docs/          46개
```

**빈 레포에 부어서 `ctx check` 를 돌렸다.**

| 단계 | 결과 |
|---|---|
| 부은 직후 (작업 기록 0건) | `ctx check: 이상 없음` |
| 작업 기록 1건 추가 (좌표 2개) | **오류 4건. 커밋할 수 없습니다** |

오류 넷이 정확히 설계대로 났다 —

```
[오류] _vocab.md 미등재 좌표  2건            ← 어휘에 등록하라
[오류] 등록부가 가리키는 섹션이 없음  1건      ← table:rp_new_mst 섹션을 만들어라
[오류] 관리 문서 파생 누락  1건               ← 예시 섹션의 applied 가 null 이다
```

세 번째가 특히 중요하다. 예시 섹션(`## xx_example_mst — (예시)`)이 좌표로
**실제로 해석됐다는 뜻**이다 — 규약의 섹션 제목 형식이 도구에 그대로 먹혔다.

## 8. viewer/fixture 를 지울 수 있나 — **아직 아니다**

패키지를 만들고 나서 실제로 시험했다.

```
viewer/fixture 의 work/ 20건  +  패키지 docs/ 46개  →  ctx check 오류 84건
    미등재 좌표 53건 (table:rp_pre_rview_mst · screen:SEB011 · domain:심의 …)
    등록부가 가리키는 섹션이 없음 (나머지)
```

| | |
|---|---|
| 패키지 | **서식.** docs 46개가 `(예시)` 섹션 하나씩뿐인 빈 골격이다 |
| viewer/fixture | **내용.** docs 16종에 실제 GDI 데이터 + work 20건 |

**뷰어 fixture 로도 못 쓴다.** 빈 골격으로는 목차 · 그래프 · 뻗어나가기 ·
검색을 하나도 시험할 수 없다. 뷰어는 지식 레포를 읽는 프로그램이고 **읽을
내용이 있어야** 개발이 된다.

### 그런데 viewer/fixture 는 내부 전용이 아니다

「지울까」를 논할 때 빠뜨리고 있던 사실 둘이다.

| | |
|---|---|
| **배포본에 실린다** | `release.mjs:119` 의 `need('viewer/fixture','viewer/fixture')` — **없으면 exit 1**. 배포본 README 가 `cdp.exe --repo viewer/fixture` 로 "바로 써 보기" 를 안내한다 |
| **내용이 실데이터다** | 테이블명이 DPMS 의 실제 RP 스키마와 같고(`rp_plnd_mst` · `rp_elc_apv_mst` …), 작업 기록 `author` 에 **실명 7명**이 있다 |

즉 내부 fixture 이면서 **받는 사람이 CDP 를 처음 열어 보는 창**이다. 지우면
개발 편의만 잃는 것이 아니다.

그리고 **실명과 실제 스키마가 배포본과 함께 나간다.** 내부 배포면 문제가
아니지만 외부로 나가는 경로가 생기면 판단할 자리다. 아래의 덤프 105 KB 도
같은 성격이다 — 재생성 가능성을 얻는 대신 **실제 스키마가 git 에 영구
기록된다.**

### `caa835a` 는 이렇게 푼다 — 덤프를 레포에 넣는다

| | |
|---|---|
| `tb_column_schema_202603261054.csv` | 97.5 KB |
| `tb_table_schema_202603261054.csv` | 7.2 KB |

**105 KB 다.** 생성되는 테이블정의서.md(47 KB)의 두 배 남짓이고,
`docs/attic/data/` 에 CSV 를 둔 전례가 이미 있다. 넣으면 **어느 PC 에서도
재생성된다** — 개인 Desktop 에만 있어서 조용히 잃었던 그 결함이 사라진다.

**패키지와 무관한 일이다.** 지금 바로 할 수 있고, 패키지를 기다릴 이유가 없다.
