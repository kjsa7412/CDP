## 1. 계획을 이렇게 읽었다

```
① 관리문서 템플릿 세트를 패키지가 들고 있다   (규모별이 아니다 — §5)
② 그 템플릿으로 프로젝트 산출물을 MD 로 세운다
③ 세워진 MD 가 CDP 의 정본 문서(docs/)가 되고,
   그때부터 작업 기록(work/) · 좌표 · ctx check 가 돈다
```

**③이 이 패키지의 존재 이유다.** ①②만이면 그냥 문서 서식 모음이다. CDP 가
붙는 순간 그 문서들은 "제출하고 잊는 것" 에서 **"작업할 때마다 갱신이 강제되는
것"** 으로 바뀐다. 지금 SI 산출물이 죽는 자리가 정확히 거기다 — 검수 때 한 번
쓰고 그 뒤로 코드와 갈라진다.

그래서 이 패키지의 성패는 **서식의 품질이 아니라 좌표가 붙는가**에 달려 있다.

## 4. ★ 소득 — 좌표는 이미 문서 안에 있다

가장 걱정했던 것이 여기서 풀렸다. CDP 좌표계를 DPMS 에 **새로 부여할 필요가
없다.** 문서마다 이미 ID 컬럼을 갖고 있고, 그것이 그대로 좌표가 된다.

| 좌표 | 원천 문서 | 그 안의 컬럼 | 실측한 값 |
|---|---|---|---|
| `req:` | 요구사항정의서 | 요구사항ID | `SFR-01-01` `CNR-02-01` `SER-01-03` |
| `func:` | 기능정의서 | 기능ID | `FNC_RP_01` … `FNC_RP_10` |
| `prog:` | 프로그램목록(TOBE) | 프로그램ID · 하위프로그램ID | `MYA010` `PSC021` `SEA011` |
| `screen:` | 화면설계서 | 프로그램ID + 화면(TAB)명 | `SMB010` + `브랜드일목표` |
| `table:` | 테이블정의서 | 테이블 명(물리) | `RP_PLND_MST` `RP_PRE_RVIEW_MST` |
| `term:` | DB도메인용어집 | 논리명 / 물리명 | `가격배수값` / `PRICE_MLTP_VAL` |
| `code:` | 코드정의서 | 업무구분 + 코드구분 | `RP`+`010` (연구분류) |
| `api:` | 인터페이스정의서 | 인터페이스ID | `INT_RP_1001` … `INT_RP_1010` |
| `batch:` | 인터페이스정의서 | Object | `G20BdStradeInfoBatchJob` |
| `issue:` | 위험및이슈관리대장 | 식별 ID | `SJ-RIS-01` … `SJ-RIS-06` |
| `proc:` | 프로세스정의서 | 프로세스 번호 | `1.1.1.1` `1.2.3.12` |

**11종이 그대로 맞는다.** 패키지가 할 일은 좌표를 발명하는 것이 아니라
**"어느 컬럼이 좌표인가" 를 문서마다 한 줄씩 적는 것**이다.

### 맞지 않는 둘

| | 문제 | 후보 |
|---|---|---|
| `arch:` | 시스템아키텍처정의서에 **ID 가 없다.** H/W · DB · S/W · 데이터연계 4장 구성 | 장(章)을 좌표로 — `arch:hw` `arch:db` `arch:sw` `arch:link` |
| `test:` `scenario:` | 통합테스트에 **전용 ID 가 없다.** 번호+모듈+모듈분류+프로그램으로 특정 | 프로그램ID 를 빌린다 — `scenario:MGA010` |

`test:` 를 프로그램ID 로 빌리면 좌표 하나에 문서 둘(프로그램사양서 · 테스트케이스)이
걸린다. CDP 등록부는 **패턴 하나에 문서 하나**이므로 여기서 결정이 필요하다.

### 입도 하나가 아직 안 정해졌다 — `prog:` 와 `screen:`

프로그램목록은 `프로그램ID`(MYA010) 와 `하위프로그램ID`(MYB011) 두 층이고,
화면설계서는 다시 `프로그램ID + 화면(TAB)명` 으로 쪼갠다. 즉 **한 프로그램이
화면 여럿**이다 (`SMB010` → 브랜드월목표 · 브랜드일목표).

CDP 는 `prog:` 와 `screen:` 을 따로 두고 `prog:` 는 프로그램사양서로,
`screen:` 은 화면설계서로 보낸다. **대응 규칙을 정해야 한다** — 수행 설계서
§3.2 가 말한 "입도는 좌표계가 아니라 팀이 정한다" 가 바로 이 자리다.

## 5. "사업규모" 는 재지 않는다 — 패키지는 **고르는 것**이다

*2026-09-14 결정. 이 절은 처음에 반대로 써 있었다.*

처음 초안은 규모 축(금액 · 기간 · 인원 · 발주처)을 정하고 S / M / L 프로파일을
만들자고 썼다. **그 방향이 아니다.**

```
아니다   규모를 재서  → 그에 맞는 문서 집합을 계산한다
맞다     패키지를 만들고 → 사람이 고른다 → 작업 환경이 구성된다
```

표본이 하나뿐인데 축을 먼저 세우면 그 축은 DPMS 한 건을 일반화한 것에 지나지
않는다. **규모는 패키지가 여럿이 된 뒤에 붙는 이름표이지 지금 계산할 것이
아니다.**

그래도 대장의 두 컬럼은 버리지 않는다 — `제출여부`(`●` 넷) 와 `제출시기`(착수 시 ·
분석완료 · … · 매주 · 매월). **규모 축이 아니라 문서의 속성**으로 들고 간다.
`제출시기` 는 그대로 라이프사이클 훅이라 "지금 단계에서 갱신이 밀린 문서" 를
물을 근거가 된다.

### 패키지가 CDP 의 어디에 붙는가 — 자리가 이미 비어 있다

`agent/install.md` ③ 이 이렇게 말한다.

> 여기까지는 복사다. **진짜 설치는 그다음이다** — `MANUAL-관리자.md` 2장.

그 "그다음" 이 셋이다.

| | 빠지면 |
|---|---|
| `_vocab.md` | 좌표가 하나도 안 잡힌다 |
| `_managed.md` | 파생 검사가 아무것도 안 한다 |
| `docs/` 관리 문서 | 등록부가 가리키는 섹션이 없다 |

**지금은 이 셋을 관리자가 프로젝트마다 손으로 쓴다.** 패키지가 채우는 자리가
정확히 여기다.

```
repo-kit/    모든 프로젝트가 같은 것을 받는다    도구 · 매뉴얼 · skill · 훅
패키지/      프로젝트마다 고르는 것             docs/ 골격 · _managed.md · _vocab.md
```

`viewer/fixture/` 가 이미 이 모양이다 — 관리 문서 16종 + `_managed.md` +
`_vocab.md`. 다만 `ops/lib/seed_repo.py` **안에 문자열로 박혀 있어서 고를 수가
없다.** 패키지는 그것을 밖으로 꺼내 **여러 벌 둘 수 있게** 하는 일이다.

### viewer/fixture 는 지우는 것이 아니라 강등된다

*"그러면 viewer/fixture 를 없애면 되지 않나"* — 지금은 아니다.

배선(`npm start` · `ops/check.cmd` · `release.mjs` 의 `need()` · `build-ctx`
의 편의 사본)은 전부 고칠 수 있다. **걸리는 것은 하나다.**

`viewer/fixture/docs/테이블정의서.md` 는 32섹션 880행인데, 생성 원천인 GDI 덤프
CSV 가 **레포에 없다** — `~/Desktop/[2512-2606] GDI_작업/…/bac/` 에 있다.
그래서 그 문서의 원천은 **한 사람의 Desktop 과 git 사본 둘뿐**이고, 이미 한 번
잃었다.

> 커밋 `caa835a` — *"시드가 덤프 없는 PC 에서 테이블정의서를 지웠다 — 그리고
> 조용했다."* 32섹션이 1섹션으로 줄었고, `npm run release` 가 시드를 매번
> 부르므로 릴리스 한 번이면 벌어졌다.

**패키지가 이 결함의 해법이다.**

```
지금        seed_repo.py 안의 문자열  →  viewer/fixture/   (추적됨)
                  ↑ 덤프(개인 Desktop) 의존

패키지 후   packages/<이름>/          (파일. 덤프 의존이 끊긴다)
                  ↓ 부으면
            생성된 지식 레포           (산출물. 추적 안 해도 된다)
```

> **정정 (2026-09-14, 패키지를 만든 뒤 실측)** — 이 문단은 틀렸다.
> **패키지에는 내용이 없다.** 서식만 들고 있기로 정했으므로(`06_패키지골격.md` §0)
> 테이블정의서의 **데이터**는 패키지에 들어가지 않고, 따라서 덤프 의존도
> 끊기지 않는다. 실제로 패키지 골격을 viewer/fixture 의 `work/` 와 함께 부어
> 보니 **`ctx check` 오류 84건**이었다.
>
> `caa835a` 는 더 싸게 풀린다 — **덤프 CSV 두 개가 105 KB 다.** 레포에 넣으면
> 어느 PC 에서도 재생성된다(`06_패키지골격.md` §8). **패키지를 기다릴 이유가
> 없는 일이다.**

**순서를 뒤집지 않는다.** 지금 지우면 되살릴 원천이 없는 상태에서 지우는
것이다. 패키지를 먼저 세우면 지울 이유가 생기는 동시에 지워도 안전해진다.

> 다만 생성물로만 두는 데는 대가가 있다 — `npm run seed` 는 **Python 을
> 요구한다**(`ops/lib/seed.mjs` 가 `python`·`py`·`python3` 를 뒤지다 없으면
> exit 1 한다). fresh clone 에서 Python 없이 `npm start` 가 뜨는 편이 낫다는
> 판단은 `.gitignore` 의 `bin/` 주석에 이미 적혀 있다. **D7 에서 같이 정한다.**

### 그래서 새로 생긴 질문 — 무엇으로 고르는가

"선택해서 작업 환경을 구성한다" 가 구체적으로 무엇인지는 아직 없다. 후보 셋.

| | |
|---|---|
| 폴더를 고른다 | `packages/<이름>/` 을 지식 레포에 붓는다. 가장 단순하다 |
| `ctx` 인자 | `ctx init --package dpms` 같은 것. 훅·검사와 같은 실행기를 쓴다 |
| 앱 화면 | 지식 레포를 처음 열 때 고르게 한다. 관리자가 CLI 를 안 써도 된다 |

**D7 로 올려 둔다**(§8). 템플릿을 만들어 봐야 무엇이 자연스러운지 보인다 —
지금 정하면 서식이 도구에 끌려간다.

## 6. 대장과 실물이 어긋난 자리들

패키지가 **문서를 무엇으로 식별하는가** 를 정해야 하는 이유다.

| 문서 | 대장 | 실물 파일 | |
|---|---|---|---|
| 인터페이스정의서 | `GDI_DE_451` | `GDI_AN_241_인터페이스정의서.xlsx` | AN_241 은 대장에서 **인터페이스목록** — 다른 산출물 |
| 데이터이관정의서 | `GDI_DE_461` | `GDI_DE_601_데이터이관.xlsx` | 번호가 다르다 |
| 기능정의서 | `GDI_AN_221` | `GDI_DE_221_기능정의서.xlsx` | `DE_221` 은 **대장에 없는 번호** |
| DB도메인용어정의서 | `GDI_DE_412` | `GDI_DE_412_DB도메인용어집.xlsx` | 번호는 맞고 **이름이 다르다** |
| 착수보고서 · 사업수행계획서 | 둘 다 `GDI_BM_111` | — | **한 번호에 두 산출물** |
| 데이터이관정의서 / 데이터이관 정의서 | `DE_461` / `EC_301` | — | 띄어쓰기만 다른 유령 중복 |
| 회의록 | **대장에 없음** | `GDI_BM_411_회의록_…docx` | 폴더·번호는 있는데 대장에 안 올라 있다 |
| 프로그램사양서 | `GDI_EC_201` | `SJ_DE_APP_300_…pptx` | 타 프로젝트 서식 |

### 그리고 어긋남이 번호에만 있는 것이 아니다

`제출시기` 컬럼이 **두 시트에서 표기 규칙이 다르다.**

| 시트 | 값 |
|---|---|
| 사업관리 | `착수 시` · `설계 완료` · `사업 종료` — **띄어 쓴다** |
| 공정관리 | `설계완료` · `분석완료` · `구현완료` · `테스트완료` · `이행완료` — **붙여 쓴다** |

실제로 부딪히는 것은 하나다 — **`설계 완료`(중간보고서 1건)와 `설계완료`(개발
산출물 15건)**. 나머지는 한쪽 시트에만 있어서 충돌하지 않고, `수시` 는 양쪽에
있지만 표기가 같다.

**제출시기는 라이프사이클 축이다.** *"설계가 끝나면 무엇이 나와야 하나"* 의
답이 15건과 1건으로 쪼개지고, **빠지는 그 하나가 하필 중간보고서**다 — 설계
완료 시점의 대표 산출물이다. 엑셀에서 `설계완료` 로 필터를 걸어도 같은 일이
난다.

> **이것은 "자리는 있고 값은 없다" 와 다른 종류다.** 값은 있는데 표기가
> 갈렸고, **어느 쪽도 틀리지 않았다.** 합칠 근거가 문서 안에 없어서 둘 다
> 살아남았다. 패키지는 `설계완료` 로 합쳤다 — 소수를 다수에.


**관리번호는 정본 식별자가 될 수 없다.** 위가 그 증거다. CDP 등록부는 파일
경로로 가리키므로 **문서명이 키**가 된다 — `docs/테이블정의서.md`. 관리번호는
프론트매터에 **속성으로** 들고 있되, 그것으로 찾지 않는다.

> 이 어긋남들은 DPMS 의 흠이 아니다. 대장을 손으로 유지하면 **반드시** 이렇게
> 된다. 패키지가 풀어야 할 문제가 바로 이것이고, `ctx check` 가 이 자리에서
> 값을 한다.

## 7. 크기 — MD 한 파일이 감당하는가

실측한 행수다.

| 문서 | 규모 | MD 로 옮기면 |
|---|---|---|
| 테이블정의서 (GDI 시트) | 4,932행 | `##` 섹션 수백 개 |
| 프로그램목록 (TOBE) | 1,085행 | 좌표 수백 개 |
| DB도메인용어집 (도메인) | 2,958행 | `###` 섹션 수천 개 |
| 코드정의서 | 10시트 | 업무구분별로 갈라져 있다 |
| 요구사항정의서 | 15시트 | 분류별(CNR·ECR·SFR…)로 갈라져 있다 |
| 인터페이스정의서 | 23시트 | 인터페이스별 상세가 시트마다 |

CDP 설계서는 *"섹션이 159개인 문서도 다 들어간다"* 고 썼다. **수천 개는 실측한
적이 없다.** 특히 DB도메인용어집 2,958행은 `term:*` → `### {값}` 이므로
섹션 수천 개짜리 MD 가 된다.

**1차 이관 전에 크기 실측을 한 번 해야 한다.** 뷰어 목차 · `ctx check` 시간 ·
git diff 크기 셋을 본다. 안 되면 그때 쪼갠다 — 쪼개는 규칙을 먼저 만들지
않는다(등록부 패턴이 업무 코드 규칙에 묶이는 것을 CDP 가 이미 한 번 겪었다,
`등록부_관리문서16종.md`).
