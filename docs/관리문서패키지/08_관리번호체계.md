## 3. `GDI` 를 어떻게 뺄 것인가

사업 코드는 **사업마다 다르다.** 패키지는 서식이므로 박아 넣으면 안 된다.

세 가지 중 하나다.

| | 모양 | 사업이 바뀌면 |
|---|---|---|
| 가 | `PRJ_DE_331` (자리표시자) | **92곳** — 머리 표 46 + 파일명 46 |
| 나 | `DE_331` (사업 코드 없음) | 0곳 |
| 다 | `<사업>_DE_331` (슬롯 표기) | 92곳 + `<` `>` 가 파일명에 못 들어간다 |

**(나) 를 권한다.** 근거:

1. **지식 레포 안에는 사업이 하나뿐**이다. 46개 문서 전부에 같은 값을 적는
   자리는 정보가 0 이고, 틀릴 자리만 46개 생긴다.
2. 사업 코드가 필요한 순간은 **제출할 때**다. 그런데 제출물은 이 레포의
   정본이 아니다 — `.gitignore` 가 `/submit/` 를 막고 있고, 정본은
   `docs/*.md` 다. 제출 파일을 만들 때 앞에 붙이면 된다.
3. 사업 코드는 **한 곳에만** 적는다 — 코드룰 문서. 거기만 고치면 끝난다.

```
레포 안       docs/DE_331_화면설계서.md
제출물        GDI_DE_331_화면설계서.pptx     ← 만들 때 앞에 붙인다
사업 코드     관리번호체계.md 한 줄            ← 여기서만 고친다
```

실측했다.

| 자리 | 건수 | 고쳐야 하나 |
|---|--:|---|
| `docs/*.md` 파일명 | 46 | **예** — 이번 작업의 본체 |
| 각 문서 `# 제목` (H1) | 46 | **예** — `# BM_111 착수보고서` |
| 각 문서 머리 표 `관리번호` | 46 | **예** — `GDI_` 를 떼고 중복을 푼다 |
| `_managed.md` 의 `docs/….md` 경로 | 15 | **예** — 안 고치면 좌표가 문서를 못 찾는다 |
| 패키지 `README.md` 문서 표 | 46 | **예** — 링크가 전부 깨진다 |
| 형상관리대장 예시 행 | 3 | 예 — `EX_BM_111` 등 |
| 문서 간 md 링크 | **0** | — 없다 |
| 백틱 문서명 (`` `테이블정의서` ``) | ~190 | **아니오** — 이름이지 파일명이 아니다 |
| `agent/manual/*.md` 의 `docs/화면설계서.md` | 7 | **아니오** — 매뉴얼은 패키지와 무관한 일반 예시다 |

> **백틱 190건을 건드리지 않는 것이 중요하다.** `여기 적지 않는 것` 표는
> *"이건 `통합테스트결과서` 로 가라"* 라고 **사람에게** 말한다. 거기에
> `TE_303_통합테스트결과서` 를 적으면 읽는 속도만 떨어진다. 번호는
> 파일을 찾을 때 쓰는 것이지 문장에서 부를 때 쓰는 것이 아니다.

기술 확인 — **`docs/` 는 하위 폴더를 허용한다.** `layerOf` 가
`docs/.+\.md` 이므로 `docs/2.개발/DE_422_….md` 도 관리 문서로 잡힌다
([`core/frontmatter.js`](../../core/frontmatter.js)). §6 의 (나)안이 가능한
이유다.

## 6. 순차 배치 — 무엇이 "업무 순서"인가

*"사실상 관리문서가 프로젝트 수행을 위한 하나의 절차이다."*

이 말을 파일 순서로 옮기려면 먼저 하나를 봐야 한다.

**공정 코드를 알파벳순으로 세우면 이미 업무 순서다 — `BM` 하나만 빼고.**

```
알파벳   AN  BM  DE  EC  TE  TR
업무     BM  AN  DE  EC  TE  TR
              └── AN → DE → EC → TE → TR 은 그대로 맞는다
```

`BM` 이 어긋나는 것은 우연이 아니다. **`BM` 은 순서 축에 놓이지 않는다** —
착수보고서는 맨 앞이고 완료보고서는 맨 끝이며 주간보고·형상관리대장은 전
기간이다. 원본이 최상위를 `01. 관리 산출물` / `02. 개발 산출물` 둘로 가른 것도
그래서다.

### 세 가지 안

| | 모양 | 순서가 보이는 곳 |
|---|---|---|
| 가 | `docs/1_BM_111_착수보고서.md` | 탐색기 · git · INDEX · 화면 |
| **나** | `docs/1.관리/BM_111_착수보고서.md`<br>`docs/2.개발/AN_111_요구사항정의서.md` | 〃 |
| 다 | `docs/BM_111_착수보고서.md` (접두 없음) | 형상관리대장 · INDEX 만 |

**(나) 를 권한다.**

(가)의 문제는 **`1` 과 `BM` 이 같은 것을 두 번 말한다**는 것이다. 공정이 곧
순번이므로 앞자리는 새 정보가 없고, 어긋날 수 있는 자리만 46개 생긴다.
누가 `2_BM_…` 이라고 적어도 아무도 못 잡는다. 게다가 `1_BM_111` 은 관리번호가
네 토막인 것처럼 읽힌다.

(나)는 폴더 이름(`관리`/`개발`)과 공정 코드가 겹치지 않는다. 관리 = `BM` 하나,
개발 = 나머지 다섯이고, **개발 폴더 안에서는 알파벳이 곧 업무 순서**라
아무 장치도 더 필요 없다. 그리고 원본 `C:\project\DPMS` 와 같은 모양이다.

대가 — `_managed.md` 경로가 한 단계 깊어진다(15줄). `ctx where` 출력도 그만큼
길어진다. 그것뿐이다.

```
docs/
  1.관리/     BM_111_착수보고서.md … BM_601_보안서약서.md          11종
  2.개발/     AN_111_요구사항정의서.md …                             4종
              DE_101_시스템아키텍처정의서.md …                       16종
              EC_101_개발일정계획서.md …                              2종
              TE_101_단위테스트계획서.md …                            9종
              TR_211_운영자메뉴얼.md …                                4종
```

> §5.2 에서 분석 4종과 구현 1종이 설계로 모이므로 `AN` 8 → 4,
> `EC` 3 → 2 가 된다. 합은 그대로 46.

## 7. 화면은 지금 순서를 무시한다 — 같이 고쳐야 한다

파일명을 아무리 정렬해도 **뷰어의 관리 문서 목록은 순서대로 안 나온다.**

[`core/store.js:109`](../../core/store.js) 의 정렬이 이렇다.

```js
.sort((a, b) => b.sections - a.sections || a.name.localeCompare(b.name))
```

**섹션 수가 1순위다.** 지금 패키지를 부으면 이렇게 된다.

| `##` 수 | 문서 | 목록에서 |
|--:|---|---|
| 5 | 시스템아키텍처정의서 | 맨 위로 튄다 |
| 3 | 요구사항정의서 · DB도메인용어정의서 | 그 다음 |
| 2 | 34종 | 이름순 |
| 1 | 9종 | 맨 아래로 밀린다 |

**4종이 앞으로 튀고 9종이 뒤로 밀린다.** 절차 순서가 아니다.

그리고 이 정렬에는 패키지와 무관한 문제가 하나 더 있다 — **문서를 고칠 때마다
목록의 순서가 바뀐다.** 섹션을 하나 더 쓰면 그 문서가 위로 올라간다. 위치로
기억하는 사람에게는 목록이 매번 다른 목록이다.

→ **경로순으로 바꾼다.** 경로는 사람이 정한 것이고 섹션 수는 우연이다.

### 9.1 정정 — 이중 번호는 5종이 아니라 **6종**이었다

→ `DE_221`. 바로 옆 `DE_211` 프로세스정의서와 같은 폴더이므로 이 편이 맞는다.

### 9.2 정정 — 데이터이관정의서는 `DE_461` 이 아니라 **`DE_601`**

§5.2 에서 `DE_461` 을 고른다고 썼는데, 그 번호 자체가 대장의 오류다.

| | 대장 | 폴더·실물 |
|---|---|---|

가 DB설계와 인터페이스설계 둘을 뜻하게 되어, **§1 에서 확인한 "폴더가 곧
번호" 가 그 자리에서 깨진다.** 실물 파일 `GDI_DE_601` 이 폴더 쪽을 지지한다.

→ `DE_501` · `DE_601`.

> 두 정정 다 **대장이 아니라 폴더와 실물 파일을 믿은 것**이다. §1 에서 규칙을

> 따르는 것이 일관된다. 되돌릴 근거(발주처와 맞춘 번호 등)가 있으면

### 9.5 정렬에서 `localeCompare` 를 버린 이유

경로순으로 바꾸고 평평한 `viewer/fixture` 를 열었더니 `DB도메인용어정의서` 가
**맨 뒤**에 있었다. `ko` 로케일에서 한글이 영문보다 앞이기 때문이다.

| | 순서 |
|---|---|
| `localeCompare` (`ko`) | `1.관리/…` `2.개발/…` **회의록** `DB도메인용어정의서` `WBS` |
| 코드포인트 | `1.관리/…` `2.개발/…` `DB도메인용어정의서` `WBS` **회의록** |
| Windows 탐색기 | 숫자 → 영문 → 한글 — **코드포인트와 같다** |

탐색기와 어긋나는 것도 문제지만, 더 나쁜 것은 **기계마다 목록 순서가
달라진다**는 것이다. 로케일이 다른 팀원과 "위에서 세 번째" 가 통하지 않는다.

코드포인트 비교는 어디서나 같고 탐색기와 같으며, 한글 음절은 `U+AC00` 부터
사전 순으로 배열돼 있어 한글끼리도 제대로 선다. 패키지는 파일명이 전부
숫자·영문으로 시작해 어느 쪽이든 같았겠지만, **평평하게 쓰는 레포에서 드러났다.**

## 10. 뒤이은 결정 — 추적표 제거 · AN 재기준 · 어휘 세팅

2026-09-16, 같은 날. 셋을 더 했다.

### 10.1 요구사항추적표를 뺐다 — 좌표가 그 일을 한다

**손으로 유지하는 추적표는 반드시 갈라진다.** 원본 실측에서 요구사항정의서의
SFR 추적 컬럼(`화면설계서 / 화면ID / 프로그램ID / 시험ID …`)은
**84행 중 0행**이 채워져 있었다(02 §3 정정). 채워지지 않는 표를 서식으로
물려주는 것은 다음 사업에도 같은 빈칸을 물려주는 것이다.

CDP 에서 그 답은 계산으로 나온다.

```
ctx where req:EX-SFR-01-01     그 요구사항에 실린 작업이 전부 선다
INDEX-by-coord.md              좌표별로 파일이 만들어진다
```

`완료보고서` · `검수요청서` 가 추적표를 근거로 부르던 자리 다섯을
`요구사항정의서` 의 좌표와 `ctx where req:…` 로 바꿨다. 문서 45개.

### 10.2 `AN` 대분류를 폴더 기준으로 다시 잡았다

원본 `02. 개발 산출물/01. 분석(AN)` 에는 폴더가 둘뿐이다 —
`01. 사전분석` · `02. 요구사항분석`. 대장은 이것을 **뒤집어** 세고 있었다.

| | 대장 | 폴더 |
|---|---|---|
| 대분류 1 | 요구사항분석 | 사전분석 |
| 대분류 2 | 현황분석 | 요구사항분석 |

| 문서 | 전 | 후 |
|---|---|---|
| 요구사항정의서 | `AN_111` | **`AN_211`** |
| 인터페이스목록 | `AN_241` | **`AN_141`** |

> **여기서만 실물 파일이 대장 편이다.** `GDI_AN_111_요구사항정의서.xlsx` 가
> `02. 요구사항분석` 폴더에 있으면서 번호는 `1` 이다. §9.1 · §9.2 에서는
> 파일이 폴더 편이었는데 이 자리만 반대다. **폴더를 택했다** — §1 의 규칙을
> 폴더에서 역산했으므로 그 편이 일관되고, 규칙이 한 자리에서라도 깨지면
> 번호는 아무것도 뜻하지 않게 된다.

### 10.3 어휘를 채웠다 — 부은 직후부터 파생이 돈다

전에는 `_vocab.md` 가 `arch:` 넷 말고 **비어 있었다.** 문서마다 예시 섹션이
있는데 어휘에 없으니 좌표가 아니었고, **파생 고리를 돌려 보려면 받는 사람이
먼저 어휘를 손으로 채워야 했다.** G6 검증에서 내가 직접 겪은 일이다.

| | 전 | 후 |
|---|--:|--:|
| 등재 좌표 | 4 | **22** |
| 섹션에 닿는 것 | 4 | **22** |

`_vocab.md` 머리에 **무슨 일을 하면 무엇을 적나** 표를 넣었다 — 13행짜리
`작업 → 좌표 → 관리 문서` 대응이다. "여기 없는 일에는 좌표가 없다" 도 같이
적었다. 회의 · 보고 · 시험 결과는 사건이고 대장 · 계획서는 집계라 좌표와
섹션이 1:1이 아니다(04 §10).

**하나를 고쳐야 했다 — `batch:` 가 닿을 섹션이 없었다.** 등록부는
`batch:* → ## {값}` 인데 인터페이스정의서의 예시는 `## EX-INT-1001` 하나뿐이고
배치 Object 는 그 안의 필드로만 있었다. 등재하는 순간 `등록부가 가리키는
섹션이 없음` 이 난다. **Object 는 인터페이스와 1:1이 아니다** — 원본 실측에서
Batch 15건이 Object 14개를 나눠 썼다. 그래서 Object 를 제 좌표로 두고
`## ExPartnerBatchJob` 예시 섹션을 만들었다.

검증 — 등재 22개가 **전부** 섹션에 닿고, 작업 기록 하나(`screen:` + `table:`)를
넣으면 파생 누락 2건으로 커밋이 막히고, `applied` 를 채우면 통과한다.
