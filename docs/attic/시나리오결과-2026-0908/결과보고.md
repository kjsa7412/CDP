## 발견 1 — 같은 날 두 번째 기록은 파생 누락으로 잡히지 않는다

S2 를 시나리오대로(같은 날짜) 돌렸더니 **커밋이 통과했다.**

```
$ git commit -m "사진 첨부 용량"          ← 파생을 일부러 안 했다
[test/... 6287365] 사진 첨부 용량
exit=0
```

원인은 `viewer/server/core/validity.js:53` 이다. **의도된 것**이다 —

> 날짜 입도가 하루이므로 하루 안의 순서를 알 수 없다. (…) 이 목록의 오탐은
> 부식성이 크다. 한 번 틀리면 사람들이 그 목록 전체를 안 믿는다. 그래서
> 같은 날짜는 동료로 본다.
>
> 대가 — 같은 날 실제로 반영 안 된 작업을 놓친다.

날짜를 하루 뒤로 바꾸니 즉시 잡혔다.

```
[오류] 관리 문서 파생 누락  1건
   screen:EXD020  applied 2026-0908-출장복명-사진첨부 뒤 후속 1건
ctx check: 오류 1건. 커밋할 수 없습니다.        exit=1
```

### 이것이 얼마나 큰 구멍인가

**하루에 같은 좌표를 두 번 건드리는 것은 드문 일이 아니다.** 오전에 화면을
고치고 오후에 같은 화면의 용량 제한을 정하면, 두 번째는 파생을 안 해도
아무도 말해 주지 않는다.

문서의 논거("섹션의 `변경` 목록에서 보인다")는 **사람이 볼 때** 성립하는
것이지 기계가 막아 주는 것이 아니다. 2층(git 훅)이 보증하는 범위 밖이다.

### 제안 — 셋 중 하나

| | | |
|---|---|---|
| A | 그대로 둔다 | 오탐 0 을 지킨다. 지금 선택 |
| B | 같은 날은 **경고**로 | 커밋은 되고 눈에는 띈다. 오탐의 부식성이 낮아진다 |
| C | 날짜에 시각을 붙인다 | 근본 해결이지만 `id` 규약과 파일명이 바뀐다 |

**B 를 권한다.** 오탐이 무서운 이유는 *오류*라서 커밋을 막기 때문이다.
경고는 막지 않으므로 틀려도 부식되지 않고, 맞으면 잡힌다.

## 발견 2 — `applied` 가 진행중 기록을 가리켜도 막지 않는다 (예상 못 함)

S6 에서 `status: 진행중` 기록을 쓰고 **관리 문서까지 갱신했다.** 커밋은
통과했다. 그런데 결과가 앞뒤가 안 맞는다 —

```
$ ctx where table:rp_trip_photo_list
  상태   반영 2026-0911-출장사진-업로드구현     ← 진행중 기록
  작업   1건
    2026-09-10  2026-0910-출장사진-테이블신설   ← 목록에는 없다
```

`진행중` 은 최신성 계산에서 제외된다(`validity.js:35`) —

> 진행중은 아직 사실이 아니다. 최신성 계산에 넣으면 남의 섹션에 파생을
> 요구하게 된다 — 끝나지도 않은 일로 남을 막을 수 없다.

맞는 판단이다. 그런데 **`applied` 쪽에는 같은 판단이 없다.** 섹션은 아직
사실이 아닌 것을 "반영했다" 고 말하고, 그 기록은 계산에서 빠져 있으니
영원히 오류로 잡히지 않는다.

파생을 한 것은 **내 잘못**이다(진행중은 점유지 사실이 아니다). 문제는
도구가 그것을 통과시켰다는 것이다.

### 제안

`check.js` 에 규칙 하나 — **`applied` 가 가리키는 기록이 `진행중` 이면
오류.** 오탐 여지가 없다. 진행중 기록은 정의상 아직 반영할 사실이 아니다.
