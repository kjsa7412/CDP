## 0. 원칙 셋

**① 겹치면 CDP 가 남는다.** 이집이지 쪽이 더 익숙해도 그렇다. 두 개를 남기면
어느 쪽이 규칙인지 알 수 없고, 그것이 이 이관 전체가 피해 온 것이다(01 §1.6).

**② 남기는 기준은 "CDP 에 없는 능력"이다.** 이름이 다르다고 남기지 않는다.
*"CDP 로 못 하는 일이 무엇인가"* 만 본다.

**③ 배치는 CDP 규약을 따른다.** 사본이 느는 것이 싫어도 그렇다 —
CDP 가 이미 그 대안을 검토하고 기각했다(§6).

**④ 절차는 CDP 로 올리고, 도메인 지식은 이집이지에 남긴다.** 이 둘이 경계다.
*"커밋을 어떻게 하나"* 는 어느 프로젝트에나 있는 절차라 CDP 로 올라가고
(`ezipez-push` → `cdp-push`), *"팩터를 어떻게 만드나"* 는 이집이지에만 있어서 남는다.
**에이전트 5종도 후자다** — CDP 는 도메인을 모른다.

## 2. 겹침 판정 — 하나씩

기준은 §0 ② 다. *"CDP 로 못 하는 일이 무엇인가."*

### 2.1 ⛔ `ezipez-save` — 폐지

**절반은 죽었고 절반은 중복이다.**

```
1단계 세션 파일 선별  →  ezipez-push 와 글자까지 같다
2단계 kb.py 위키 기록 →  kb.py·wiki/·CONVENTIONS.md 가 레포째 사라졌다
3단계 라이프사이클    →  supersede·promote·archive.  CDP 는 이 개념을 없앴다(01 §1.6)
4단계 kb.py lint     →  ctx check 가 대신한다
```

3단계가 특히 중요하다. `supersede`·`archive` 는 **"덮힘" 판정**이고 CDP 는 그것을
없앴다 — *"후속이 조금 손봤는지 완전히 뒤집었는지 도구는 모른다."*
되살리면 CDP 판정 모델과 정면으로 충돌한다.

⇒ **지식 기록의 주인은 `cdp-save` 하나다.** 남는 1단계는 `ezipez-push` 가 이미 갖고 있고,
그 `ezipez-push` 도 §2.5 에서 **`cdp-push` 로 올라간다** — 결국 세션 파일 선별 규칙은
**CDP 정본 한 곳**에만 남는다.

### 2.2 ⛔ `ezipez-wiki-load` — 폐지

`cdp-load` 가 대신한다. 그리고 **검색 대상이 없다** — `ezipez_knowledge/wiki`·`STATE/` 가 사라졌다.

둘의 성격 차이가 폐지의 근거다.

| | |
|---|---|
| `ezipez-wiki-load` | **문자열 검색.** "OO 관련 기록 찾아" → grep |
| `cdp-load` | **좌표 조회.** 좌표 → 그 좌표의 정본 섹션 + 후속 판정 |

검색이 아쉬우면 `ctx match`(이름→좌표) · `ctx where`(좌표→상태) · `INDEX-by-coord.md`
가 있다. **좌표계가 있는데 grep 을 남기면 사람이 grep 만 쓴다.**

### 2.3 ⛔ `ezipez-help` — 폐지

커맨드 목록을 스킬 본문에 적어 둔 것이다. **목록이 바뀌면 낡고, 낡아도 아무도 모른다** —
이 이관이 계속 잡아 온 그 모양이다. 대신 `MANUAL.md` · `MANUAL-관리자.md` ·
`MANUAL-시스템.md` 3종이 지식 레포에 있고, `CLAUDE.md` 가 절차 목록을 든다.

### 2.4 🗑 `_deprecated/` 2종 — 삭제

`ezipez-wiki-save`(노션) · `ezipez-wiki-local`(`GitHub/wiki` 폴더). 둘 다 대상이 없다.
**`_deprecated/` 에 두는 것도 그만둔다** — 폐기 이력은 `ezipez_cdp/work/` 에 있다.

### 2.5 ⛔→🆙 `ezipez-push` — 폐기하고 **`cdp-push`** 로 교체 (CDP 본체로 승격)

**`cdp-save` 는 지식 레포 하나만 만지고 push 하지 않는다.**

> `cdp-save` §: *"막히는 것은 코드 커밋이 아니라 지식 레포 커밋이다.
> 코드를 먼저 커밋하고 그 뒤에 여기 오면 된다"* · *"push 는 하지 않는다"*

코드 레포를 커밋·push 하는 능력은 **CDP 에 아예 없다.** 그리고 그 안에 든 것이
가볍지 않다 —

```
· 세션이 실제로 만진 파일만 (도구 호출 이력에서 열거)
· ⚠ git add -A · git add . 금지 — 정확한 경로만
· 세션 밖 dirty(사전·타 세션·린터)는 건드리지 않는다
· 민감파일 제외: .env* · *.key · *.pem · credentials* · node_modules · __pycache__ · .DS_Store
· staged 검사 후 목록 밖이면 git restore --staged
```

**이것이 이 시스템에서 가장 자주 사고를 막아 온 규칙이다.** 없애면 안 된다.

#### 그런데 이것은 이집이지 전용이 아니다

위 규칙 중 **이집이지에만 해당하는 것이 하나도 없다.** 전부
*"세션이 만진 것만, 정확한 경로로, 민감파일 빼고"* 다 — 어느 프로젝트에나 같다.

⇒ **`ezipez-push` 를 폐기하고 `cdp-push` 를 CDP 제품 레포(`kit/agent/skills/`)에 신설한다.**
이집이지는 그것을 `ctx setup` 으로 **내려받는다.**

| | |
|---|---|
| 얻는 것 | 규칙이 한 곳에 산다. 고치면 `ctx setup` 이 전 레포에 퍼뜨린다 |
| 잃는 것 | **없다.** 이집이지 고유값이 애초에 없다(§4.1) |
| ⚠ 조건 | **스킬 본문에 이집이지 경로가 한 글자도 남으면 안 된다.** 남으면 CDP 스킬이 아니라 이집이지 스킬이 CDP 폴더에 있는 것이다 |

> **CDP 규약과 충돌하지 않나** — CDP 는 *"push 는 사람이"* 라고 한다. `cdp-push` 는
> **사람이 부르는 스킬**이다. 자동으로 도는 것이 아니라 사람이 부를 때만 돈다.
> `cdp-save` 가 push 를 안 하는 것과 `cdp-push` 가 있는 것은 모순이 아니다 —
> **기록과 발행을 가른 것**이고, 가른 채로 둘 다 있는 것이 맞다.
>
> ⚠ **`cdp-push` 는 지식과 무관하다.** 지식 레포를 알 필요도, 좌표를 볼 필요도 없다.
> *"이 세션이 만진 것을 커밋·push 한다"* 가 전부다. 지식 기록은 `cdp-save` 가 따로 한다.

### 2.6 ✅ `ezipez-factor-add` — 존치 (도메인 런북, 중복 아님)

Stage 0~9 오케스트레이터다. CDP 에 대응물이 없다 — CDP 는 *어떻게 기록하나*를 알지
*팩터를 어떻게 만드나*는 모른다.

### 2.7 ✅ 에이전트 5종 — 전건 존치, **단 개편한다**

CDP 에 에이전트가 없다. `ezipez_knowledge` 의존 0. 서로 안 겹친다.
**이식 대상이 아니다** — 없앨 것도 옮길 것도 없다.

**다만 낡았다.** 전건 **2026-06-08 ~ 06-29** 작성이고, 그 뒤에 이 시스템이 크게 바뀌었다.
개편 설계는 **§7** 에 따로 둔다. 이식(§2~§6)과 개편(§7)은 **다른 일**이고 순서도 다르다 —
이식이 끝나야 개편의 참조 대상(`cdp-load`·정본 20종)이 제자리에 있다.

## 3. 이식 후 구성

```
       현행                                  이식 후
────────────────────────────────  ─────────────────────────────────
스킬   ezipez-save        ⛔ 폐지        cdp-work    요청 처리
      ezipez-wiki-load   ⛔ 폐지        cdp-load    좌표 → 상태 주입
      ezipez-help        ⛔ 폐지        cdp-save    기록 + 파생 + 한 커밋
      _deprecated 2종    🗑 삭제        cdp-managed 파생 채우기
      ezipez-push        🆙 CDP 로 승격   cdp-import  밖 문서 편입
      ezipez-factor-add  ✅ 존치        cdp-edit    문서만 수정
                                       cdp-push    코드 레포 커밋·push  ← 신설
                                       ─────────────────
                                       CDP 본체 7종  (6 → 7)
                                       ezipez-factor-add  팩터 런북  ← 이집이지 고유 1종
      ─────────────────              ─────────────────
      스킬 7 (폐기 2 포함)              스킬 8 = CDP 7 + 이집이지 1

커맨드 7                                커맨드 2
에이전트 5                              에이전트 5  (무변경)
```

**스킬 수는 7 → 8 로 늘지만 겹침은 0 이 된다.** 줄이는 것이 목적이 아니라
**한 가지 일에 주인이 하나이게** 하는 것이 목적이다.

그리고 **이집이지가 자기 스킬로 들고 있는 것은 하나(`ezipez-factor-add`)만 남는다.**
나머지 일곱은 CDP 정본에서 내려온다 — 고칠 곳이 하나라는 뜻이다.

### 3.1 주인 표 — 이것 하나만 기억하면 된다

| 하려는 일 | 주인 |
|---|---|
| 요청 하나를 처리한다 | `cdp-work` |
| 좌표의 지금 상태를 본다 | `cdp-load` |
| **지식**을 기록하고 정본을 갱신한다 | **`cdp-save`** |
| 밖에서 온 문서를 들인다 | `cdp-import` |
| 코드 없이 문서만 고친다 | `cdp-edit` |
| 파생이 남았다 | `cdp-managed` |
| **코드**를 커밋·push 한다 | **`cdp-push`** |
| 팩터를 새로 만든다 | `ezipez-factor-add` → Stage 9 에서 `cdp-save` |
| 도메인 판단이 필요하다 | 에이전트 5종 (§7) |

**지식은 `cdp-save`, 코드는 `cdp-push`.** 경계가 레포다.
그리고 **기록(`cdp-save`)과 발행(`cdp-push`)은 갈라 둔다** — 기록은 훅이 막을 수 있고
발행은 사람이 정한다.

## 4. 살리는 둘의 재배선

### 4.1 `cdp-push` — 신설 스킬의 뼈대

**설정 파일이 없다. 레포 목록도 없다.** 세션이 만진 파일 경로에서 레포가 나온다.

```
① 대상 선별   이 세션이 Write/Edit/Bash 로 만든·고친 파일을 열거한다
              ⚠ git add -A · git add . 금지.  세션 밖 dirty 는 건드리지 않는다
② 레포 유도   각 경로에서 위로 올라가며 .git 을 만나는 첫 디렉터리 = 그 파일의 레포
              레포 밖 파일(/tmp 등)은 건너뛰고 보고한다
③ 제외        .env* · *.key · *.pem · credentials* · node_modules · __pycache__ · .DS_Store
④ 스테이징 검사  diff --cached --stat 이 ① 목록과 같은가.  아니면 restore --staged
⑤ 커밋·push   레포별로.  원격이 없으면 커밋까지만 하고 그렇게 말한다
⑥ 보고        레포별 커밋 해시 · 건너뛴 파일
```

**②가 이 설계의 답이다.** 실측으로 확인했다 —

```
…/ezipez_cdp/work/2026-0908-R6-….md              → ezipez_cdp
…/ezipez_cdp/_vocab.md                           → ezipez_cdp
…/Project/CDP/docs/이집이지_이관/04_….md           → CDP
…/ezipez_data/docs/RUNBOOK.md                    → ezipez_data
/tmp/scratch.txt                                 → 레포 밖 (건너뜀)

⇒ 밀 레포 3개.  목록을 아무도 적지 않았다.
```

**①③④⑤ 가 이 스킬의 값이다.** ②는 그 값을 얻는 데 필요한 전부이고, **프로젝트마다
다를 것이 하나도 없다.** 그래서 `cdp-push` 는 이집이지 경로를 한 글자도 안 갖는다.

#### 하지 않는 것 둘

**⛔ `all` 모드를 만들지 않는다.** `ezipez-push` 에는 *"7레포의 dirty 전부"* 를 미는
`all` 이 있었다. **이것을 승계하지 않는다.**

> `cdp-push` 는 **관리 중인 전체 레포를 미는 도구가 아니다.** *"이 세션에서 한 작업"* 을
> 올리는 도구다. 전부를 미는 순간 **세션 밖 dirty 를 남의 작업인 줄 모르고 올리게** 되고,
> 그것이 `git add -A` 를 금지한 이유와 같은 사고다. 범위를 넓히면 그 금지가 무의미해진다.

`all` 을 버리면 **레포 목록이 필요한 유일한 이유가 사라진다.**

**⛔ 지식 레포를 알지 않는다.** `cdp-push` 는 `.claude/cdp.json` 도 읽지 않는다.
지식 레포를 만졌으면 ②가 알아서 잡고, 안 만졌으면 상관없다.
**커밋·push 는 지식 공유와 무관한 일이다.**

### 4.2 ~~`_repos.md` 신설~~ — 폐기 (2026-09-09)

1차 개정에서 *"`cdp-push` 가 일반 스킬이 되려면 레포 목록이 스킬 밖에 있어야 한다"* 며
`_vocab.md`·`_managed.md` 옆에 **`_repos.md`** 를 신설하자고 썼다. 시나리오 다섯까지 붙였다.

**전제가 틀렸다.** 목록이 필요하다고 본 것은 `all` 모드를 승계한다고 가정했기 때문이고,
그 가정을 빼면 **세션이 만진 경로가 곧 레포**다(§4.1 ②). 스킬은 자기가 무엇을 만졌는지
이미 안다 — 그걸 따로 적어 둘 이유가 없다.

| 1차 개정이 쓴 것 | 지금 |
|---|---|
| 레포 목록을 어디 둘까 | **둘 필요가 없다** |
| `cdp.json` 은 커밋 안 되니 못 쓴다 | `cdp.json` **자체가 필요 없다** |
| 자동탐색은 형제 폴더를 가정해 위험하다 | 자동탐색이 아니다. **만진 파일에서 거슬러 올라간다** — 폴더 배치와 무관하다 |
| 목록이 하나 빠지면 조용하다 | **빠질 목록이 없다.** 만졌으면 잡히고 안 만졌으면 안 잡힌다 |

> **왜 틀렸나** — `ezipez-push` 의 기능을 하나씩 뜯지 않고 **통째로 옮기려** 했다.
> `all` 은 지식 레포까지 7개를 함께 밀던 옛 구조의 산물인데, 그 구조가 R6 으로 사라진
> 뒤에도 **기능만 남겨 두고 그것을 지탱할 파일을 새로 만들려** 했다.
> 이 이관이 계속 잡아 온 것과 같은 모양이다 — **없어진 전제 위에 서 있는 것.**

⚠ **`_repos.md` 는 만들지 않는다.** 통제 파일은 `_vocab.md` · `_managed.md` 둘로 유지한다.

## 6. 배치 — CDP 규약을 따른다

**여기가 이 설계에서 유일하게 판단이 갈리는 자리다.**

```
현행   이집이지 스킬   ~/.claude/skills/          (사용자 레벨 · 전역)
       cdp 스킬       ezipez_cdp/.claude/skills/  (지식 레포에만)
```

**둘 다 그대로 두면 안 된다.** 하네스는 **프로젝트 루트의 `.claude/skills/`** 를 읽는다.
`ezipez_web_back` 에서 클로드를 열면 **`cdp-save` 가 목록에 없다** — 절차 층이 통째로 빠진다.

전역(`~/.claude/skills/`)에 몰아넣는 안이 편해 보이지만 **CDP 가 이미 검토하고 기각했다.**

> `kit/manual/system.md` — *"전역 설치와 정션은 둘 다 **그 PC 에만** 남아 팀에 퍼지지 않는다.
> 퍼지지 않는 것은 절차로 못 막고, 드리프트는 막을 수 있다."*

⇒ **`ctx setup <작업레포>` 로 각 레포에 사본을 넣는다.** 8레포 전부.

```bash
for r in data web_back web_front data_admin ops lab qa; do
  ezipez_cdp/bin/ctx setup ~/Documents/GitHub/ezipez_$r
done
```

`ctx setup` 이 하는 일 — `.claude/skills/` 에 `cdp-*` 사본 · `CLAUDE.md` 의
`<!-- cdp:begin -->` 블록 · `.claude/cdp.json`(지식 레포 경로, 커밋 안 함).
**`cdp-` 로 시작하지 않는 남의 skill 은 건드리지 않는다.**

**`ezipez-factor-add` 도 같이 레포로 내린다.** 규칙이 둘이면 하나만 고쳐진다.
`cdp-push` 는 CDP 본체 스킬이라 `ctx setup` 이 알아서 함께 내린다 — 그것이 승격의 실익이다.

> ⚠ `ctx setup` 은 **`cdp-` 로 시작하는 것만** 건드린다. `ezipez-factor-add` 는
> setup 이 옮겨 주지 않으므로 **사람이 8레포에 넣어야 한다.** 이것이 이집이지 고유
> 스킬을 하나로 줄인 또 하나의 이유다 — 손으로 옮길 것이 하나뿐이다.

### 6.1 ⚠ `.gitignore` 를 먼저 본다

`.claude/*` 를 통째로 막아 둔 레포가 있으면 skill 이 **설치한 사람 PC 에만** 남고
**설치한 사람은 되니까 됐다고 생각한다.**

```
.claude/*
!.claude/skills/     ← 이 줄이 있어야 한다
```

`ctx setup` 이 알려는 주지만 **고치는 것은 사람이 한다.** 8레포 전부 확인 대상이다.

### 6.2 에이전트 5종은 어디에

`GitHub/.claude/agents/` **현 위치 유지.** 에이전트는 레포가 아니라 **도메인**에 속하고
(`data_master` 는 data·web_back·qa 를 가로지른다), CDP 가 관리하는 대상도 아니다.
사본을 8벌 만들 이유가 없다.

```
□ 두 레포를 만진 세션에서 cdp-push 가 그 둘만 민다  (목록 없이)

□ ezipez-factor-add 가 ezipez_knowledge 를 한 번도 언급하지 않는다
□ grep -r ezipez_knowledge ~/.claude 각레포/.claude  →  0건
□ ezipez_cdp: ctx check 이상 없음
```

**B — 개편**
```
□ 에이전트 5종에 "부산 부동산 플랫폼" 0회
□ 5종에 수치·목록·스키마가 인라인으로 없다 (좌표·정본 참조만)
□ data_master 가 DB 를 둘로 안다
□ 5종이 서로 안 겹친다 (개편 전과 같이)
```

**A 의 6번째 줄이 이 설계의 핵심 검증이다.** `cdp-push` 에 `ezipez` 가 한 번이라도
나오면 승격이 실패한 것이다 — CDP 스킬이 아니라 이집이지 스킬이 CDP 폴더에 있는 것이다.
`_repos` 와 `all` 도 같이 본다: **셋 다 0이어야 설정 없는 스킬**이다.

마지막 줄이 자기 검사다 — **이식 자체가 `cdp-save` 로 기록되고 그 기록이 검사를 통과**하면
절차가 자기 자신에게 적용된 것이다.

## 10. 하지 않는 것

| | 왜 |
|---|---|
| cdp 스킬 **사본** 수정 | **CDP 본체 소유.** 고칠 것이 있으면 CDP 레포에서 고치고 `ctx setup` 으로 내린다. 레포 사본을 고치면 다음 setup 에 덮인다. `cdp-push` 도 이제 여기 해당한다 |
| cdp-* 슬래시 커맨드 신설 | 같은 일에 입구가 둘이 된다(§5) |
| 에이전트 5종을 **A 단계에서** 손대기 | 이식과 개편은 다른 일이다(§8.2). B 에서 한다 |
| 에이전트를 새로 만들거나 없애기 | **개편 뒤에 판단한다**(§7.5). 낡은 것을 기준으로 자르면 틀린다 |
| **`_repos.md` 를 만들기** | **폐기했다(§4.2).** 통제 파일은 `_vocab.md`·`_managed.md` 둘로 유지한다 |
| `cdp-push` 에 `all` 모드 넣기 | 전체 레포를 미는 도구가 아니다. 세션 밖 dirty 를 올리게 된다(§4.1) |
| `ezipez_sns`·`service-control` 원격 생성 | 별건 판단. 이 설계는 **없는 것을 목록에 넣지 않는다**는 것만 정한다 |
| 코드 주석 24건의 경로 재작성 | `issue:ezipez_knowledge-경로참조-30건-끊김` 의 나머지 절반. 런타임 안전이라 급하지 않고, 9개 레포를 건드린다 |
| 실행 | **이 문서는 설계다.** ⑦ 검증까지 통과해야 끝이다 |
