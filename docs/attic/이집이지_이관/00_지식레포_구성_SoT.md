## 0. 완료의 정의

## 0.1 옮기는 것과 지우는 것은 다르다

이 문서에서 제일 자주 헷갈릴 자리라 먼저 못 박는다.

```
이관 = 복제다.  원본을 지우지 않는다.
```

문서가 **시스템의 일부로 그 자리에서 역할**을 하고 있으면 — 매뉴얼 · 레포 규약 ·
런북 · 롤백 절차 — **그 자리에 그대로 둔다.** 옮기는 이유는 그것이 자리를 비워야
해서가 아니라 **정보로서·작업물로서 값이 있어서**다. 같은 문서가 두 곳에 있게 되고,
그것이 맞다. 다만 **어느 쪽이 SoT 인지는 하나다 — `ezipez_cdp` 다.**

시스템의 일부가 아닌 문서는 결국 **첨부(asset)로 원본과 연결된 채 `ezipez_cdp`
안으로 들어온다.** 원본 자리에는 링크만 남는다.

**예외는 `ezipez_knowledge` 하나다.** 그것은 지식을 담는 것 말고 다른 역할이
없어서, 이관이 끝나면 존재 이유가 사라진다. 두 곳에 남겨 두면 **어느 쪽이
맞는지 모르게 되는 것이 유일한 결과**다(01 §1.6 — 이름이 둘이면 한쪽으로 흘러
들어간다). 그래서 R6 에서 로컬에서 지운다. git 원격에 형상이 남아 있어 되돌릴 수 있다.

## 2.3 판정 규칙 — 무엇이 "작업 문서"인가

**가르지 않는다. 우리가 쓴 md 는 전부 옮긴다.** 처음에 *"작업 문서냐 코드
로컬 문서냐"* 로 가르려 했는데 그 물음이 틀렸다 — §0.1 대로 **옮기는 것과
지우는 것이 다르기** 때문에, 옮길지는 물을 것이 없다.

물을 것은 **하나 남는다.**

```
이 문서는 그 자리에서 시스템의 일부로 역할을 하는가?

  예   →  원본을 그 자리에 둔다.  지식 레포에도 사본이 있다.  SoT 는 사본이다
  아니오 →  원본을 첨부(asset)로 지식 레포에 들이고, 그 자리에는 링크만 남긴다
```

`ezipez_ops/MANUAL.md` · `service-control/ROLLBACK.md` · 각 레포 `CLAUDE.md` 는
**예**다 — 사람이 그 레포를 열었을 때 거기 있어야 한다. `ezipez_qa/remediation/
batch-3.md` 같은 것은 **아니오**다 — 끝난 작업의 기록이라 지식 레포가 제자리다.

어느 쪽이든 **코드 레포에서 먼저 지우지 않는다.** 지우는 것은 이관이 끝나고,
그 레포 사람이 잃는 것이 없음을 확인한 뒤의 별도 판단이다.

## 2.4 방법

**`cdp-import` 를 쓴다.** v0.2.6 에 이것을 위해 생긴 스킬이다(01 §1.8).
59건을 손으로 하지 않는다 — 다만 절차의 ③(좌표 판정)과 **②(날짜 — 오늘이 아니다)** 는
스킬이 강제한다.

```
① pull → ② 원문 읽고 날짜 확정 → ③ 좌표 판정 → ④ 편입(원문 보존)
→ ⑤ 등록부 걸리는 정본 섹션 갱신 → ⑥ 한 커밋
```

날짜는 **git 최초 커밋 시각**을 1순위로 쓴다. 코드 레포는 커밋 이력이 살아 있어
`ezipez_knowledge` 때보다 근거가 좋다(03 §12.2 의 mtime 폴백이 필요 없다).

# R5 — 관리 문서 확정 후 현행 분석

## 3.1 왜 이것이 남아 있나

**지금 관리 문서 20종은 "옮겨진 문서에서 읽어낸 것"이지 "현행 시스템을 본 것"이 아니다.**

```
지금까지   ezipez_knowledge 문서  →  읽고  →  관리 문서 섹션
R5 에서    현행 시스템(코드·DB·xlsx)  →  분석  →  작업 문서  →  관리 문서 섹션
```

이 차이가 중요한 이유 — 이관한 문서 다수가 **작성 시점의 스냅샷**이고, 그중
일부는 이미 틀렸다는 것이 이관 중에 드러났다.

| 실례 | |
|---|---|
| 알림 kind | 문서·MEMORY 는 **22종**, 코드 `KIND_REGISTRY` 는 **24종** |
| SHP 로더 | MEMORY 는 자연환경 진행중·사물주소 미착수, 실제는 **둘 다 적재 완료** |
| 부산 하드코딩 | 05 문서 "7종", 실측 **4종** (6종 오진) |
| lock.json | 문서는 "SoT = lock.json 4종", 실제는 **파일 자체가 없다**(DB 직접조회) |

**문서를 옮기는 것만으로는 최신이 되지 않는다.** R5 가 그 간극을 닫는다.

## 3.1.1 R4 가 남긴 R5 의 입력 — 정본 섹션 없는 좌표 69

```
ctx derive   anchor-missing 69건
             그중 어느 기록의 touches 에도 있는 것  0건
```

**어휘에는 등재됐는데 정본 섹션이 없는 좌표가 69개**다 —
`factor:` 28(대분류 8 + O·S 계열) · `source:` 20 · `api:` 18 · `table:` 3.

**오류가 아니다.** 검사는 실제로 `touches` 에 쓰인 좌표만 보고, 이 69개는 아직
아무도 건드리지 않았다. 다만 **R5 가 그 좌표를 분석하는 순간 섹션이 필요해진다** —
R4 에서 9개가 정확히 그렇게 드러났다(어휘에 있었지만 아무도 안 써서 여태 안 보였다).

⇒ **R5 의 실제 작업량은 관리 문서 20종이 아니라 그 안의 섹션들이고, 69개는 아직
없는 자리다.** §3.5 진척표를 채울 때 이 수를 같이 본다.

## 3.3 ② 현행 분석 → ③ 작업 문서 → ④ 관리 문서 갱신

관리 문서 **하나당 한 바퀴**다. 20바퀴 돈다.

```
② 분석    그 문서가 다루는 대상의 SoT 를 직접 본다
          코드 · DB 스키마 · xlsx · 실행 결과.  문서를 근거로 쓰지 않는다
③ 작업문서 work/ 에 기록.  **분석이 곧 작업이다** — 무엇을 봤고 무엇이 달랐나
④ 갱신    관리 문서 섹션.  applied 를 ③ 에 착지
```

**③ 을 건너뛰지 않는다.** 관리 문서만 고치면 **출처 없는 변경**이 되고,
6개월 뒤 "왜 24종이라고 썼나"에 답할 것이 없다. `cdp-edit` 이 존재하는 이유가
그것이다(01 §1.8).

**분석에서 지키는 것 넷**

1. **SoT 를 베끼지 않는다 — 가리킨다.** 규격 B(02 §1.3). 값을 옮겨 적으면
   그 순간 두 번째 정본이 되고, 이집이지는 이미 세 번 데였다
   (`팩터.lock.json` 폐지 · `factors.json` 수기정본 · `regions.py` 오도).
2. **문서와 현행이 다르면 그 차이가 산출물이다.** 조용히 덮어쓰지 말고
   *"문서는 22종이라 했고 코드는 24종이다"* 를 작업 문서에 남긴다.
3. **확신이 없으면 채우지 않는다.** 안 채운 것은 검사가 알려주고,
   **틀리게 채운 것은 아무도 모른다**(01 §1.8).
4. **날짜는 분석한 날이다.** 이것은 이관이 아니라 새 작업이다.

# R6 — ezipez_knowledge 로컬 소멸

## 4.1 왜 지우나

이관이 끝나면 `ezipez_knowledge` 는 **지식을 담는 것 말고 다른 역할이 없다.**
매뉴얼·런북처럼 그 자리에서 시스템의 일부로 사는 문서와 다르다(§0.1).

두 곳에 남겨 두면 생기는 것은 하나뿐이다 — **어느 쪽이 맞는지 모르게 된다.**
01 §1.6 이 `미결`·`제안` 을 없앤 이유와 같다. *"이름이 둘이면 한쪽만 막히고
다른 쪽으로 흘러 들어간다."* 사람이 옛 경로를 열어 옛 문장을 읽고, 그것이
틀렸다는 것을 아무도 모른다.

**되돌릴 수 있다.** git 원격에 형상이 남아 있다.

## 4.2 선행 조건 — 전건 충족 전에는 지우지 않는다

```
① recon.py                      992 / 992  누락 0
② ctx check                     오류 0
③ git remote 에 최신이 올라가 있다   git -C ezipez_knowledge status  →  clean
                                   git log origin/main..HEAD        →  비어 있음
④ 원본 지문 무변경                 이관 중 원본을 건드리지 않았다는 증거
```

③ 이 **가장 중요하다.** 로컬에만 있는 것이 하나라도 남아 있으면 지우는 순간
그것이 사라진다. `status: clean` 만 보고 지우면 안 된다 — 커밋됐지만 push 안 된
것이 정확히 그 함정이다.

### 4.2.1 ③ 이 절반만 통과였다 — 그래도 진행할 수 있었다 (2026-09-08)

```
  M 수정 5   specs/README.md · INDEX.md · 사업진단/README.md · 수집자동화 2

git rev-list --count @{u}..HEAD                0     ← push 안 된 커밋은 없다
```

**미추적 7파일이 위험하다.** git 이 모르는 파일이라 원격에 없고, 지금 지우면

⇒ **R6 의 실질 선행조건이 하나 더 있다 — `ezipez_cdp` 가 커밋되고 원격에
