# 지식 레포 뷰어 (ctx-view) 설계서
> **v1.0 이후** — 로컬 뷰어(ctx-view · 트레이 · exe)는 없다. 화면은 서버가 낸다 — [`CDP_화면_설계서_v1.0.md`](../design/CDP_화면_설계서_v1.0.md) · 서버 없는 한 사람은 개인 서버([`CDP_시스템설계서_v2.0.md`](../design/CDP_시스템설계서_v2.0.md) §7.7).

v0.2 · 2026-09-02 · **전제 축소 개정 (§2.2)**

> **한 줄 요약** — PC에 실행 파일 하나를 두고 더블클릭하면 로컬 서버가 떠서 기본 브라우저에 뷰어가 열린다. 설치·로그인·네트워크 전송이 없다. 로컬이 되면서 v0.1이 못 했던 두 가지가 열린다 — **파일 감시**와 **`ctx check` 위임.** **git은 전혀 쓰지 않는다**(§11).
>
> 전제 문서 — 「AI 기반 맥락 배포 프로토콜 설계서 v1.1」, 「지식 레포 뷰어 설계서 v0.1」
>
> **절 참조 표기** — `프로토콜 §12.2` 는 프로토콜 설계서의 절, `v0.1 §8.3` 은 이전 판의 절, `본서 §17` 은 이 문서의 절. 문맥상 명백하면 접두어를 생략한다.
>
> **이 판의 중심은 제3부(UI/UX)다.** v0.1의 화면 설계는 ASCII 스케치 한 장과 배지 표 하나였다. 그 정도로는 만들 수 없고, 만들면 각자 다르게 만든다.
>
> **확정된 전제 (§2.2)** — ① exe 실행과 **loopback 리스너 모두 사내 PC에서 확인됨** ② 대상은 **개발 직군만** ③ 지식 레포는 로컬의 **정해진 경로에 규약대로 이미 존재한다** (`C:\project\mdviewer\sample-repo`) ④ **그 폴더를 최신화하는 일은 뷰어의 범위가 아니다.**
>
> **착수 전 확인 사항(부록 A)은 전부 해소됐다.** 남은 것은 프로토콜 측 요청 두 건(§34-1 `ctx check --json`, §34-6 `INDEX.md` 기록 시각 칼럼)이며 **둘 다 착수를 막지 않는다.**

# 제0부 — v0.1 검토와 이번 판의 전제

## 1. v0.1을 다시 읽고 — 남긴 것과 버린 것

v0.1의 판단 중 **전제와 무관한 것은 대부분 옳다.** 버려야 하는 것은 브라우저 샌드박스에서 파생된 부분뿐이다.

| v0.1의 판단 | v0.2에서 |
|---|---|
| 좌표 트리 · 문서 목록 · 본문 3분할 | **유지.** 밀도·붕괴·리사이즈 규격을 확정하고(§15) **읽기 모드를 추가한다**(§27.5) — 3분할은 찾을 때의 레이아웃이다 |
| 유효성 배지가 이 뷰어의 존재 이유 (v0.1 §8.3) | **배지는 유지, 이 주장은 철회.** 존재 이유는 **본문을 사람이 읽는 것**이고 배지는 그 앞의 판단 장치다(§13-⓿ · §17) |
| 나이를 경고색으로 칠하면 안 된다 | **원칙으로 승격.** 색 예산 자체를 규정한다(§13-①, §16) |
| `INDEX.md`를 읽지 않고 직접 집계 | **유지.** 불일치 경고도 유지 |
| 정정된 문서를 지우지 않고 흐리게 | **유지.** 좌표 타임라인에서 체인으로 시각화(§18) |
| alias 대조를 검색의 1차 경로로 | **유지하고 화면에 노출.** 대조가 보이지 않으면 사용자는 정본을 배우지 못한다(§20) |
| 읽기 전용 · 편집 비목표 | **유지.** 로컬이 되어 유혹이 커졌으므로 경계를 더 좁게 다시 긋는다(§31) |
| markdown-it · js-yaml · DOMPurify · MiniSearch | **유지.** 렌더링은 여전히 클라이언트에서 한다(§9) |
| 3단계 검증을 설계서 v1.1 원문으로 | **유지.** 여기에 조판 기준을 추가한다(§27) |
| | |
| Vercel 정적 호스팅 | **버림.** 배포 대상이 PC다(§5) |
| File System Access API · IndexedDB 핸들 | **버림.** 파일 접근은 로컬 프로세스가 한다 |
| Chrome/Edge 한정 · `webkitdirectory` 폴백 | **버림.** 브라우저 제약이 사라진다 |
| "서버 코드가 0줄이다" | **버림.** 서버가 생겼고, **그 대가로 새 위험면이 생긴다**(§7) |
| "파일 감시는 없다. 새로고침을 눌러야 한다" | **버림.** 감시한다(§10.3) |
| "Git 조작은 비목표 — 브라우저에서 할 수 없다" | **거의 유지.** 전제가 바뀌어 가능해졌지만 §2.2 ④로 다시 범위 밖이 됐다. **`git log` 읽기 하나만 예외**(§11) |
| 검증 뷰를 JS로 재구현 (v0.1 §8.5) | **버림.** 실제 `bin/ctx`에 위임한다(§12) |

> **v0.1이 스스로 기각한 경로를 채택한다.** v0.1 §4는 로컬 CLI를 *"각자 Node 설치 + 명령 실행. 비개발 직군에겐 더 어려움"* 으로 기각했다. 그 기각 사유는 **CLI라는 형태의 문제가 아니라 패키징의 문제였다.** 단일 실행 파일로 묶고 실행 시 브라우저를 자동으로 열면, 사용자가 하는 일은 v0.1과 똑같은 "더블클릭 한 번"이 된다. §5에서 확정한다.

## 2. 전제

### 2.1 실행 주체가 브라우저에서 로컬 프로세스로

v0.1의 구조는 이랬다.

```
[Vercel]  정적 파일 전송 ──▶ [브라우저 샌드박스] ──권한 프롬프트──▶ 사용자 디스크
                                     ▲
                         여기가 모든 제약의 출처였다
```

v0.2는 이렇다.

```
[사용자 PC]
  ctx-view.exe ──▶ 127.0.0.1:7373 ──▶ [브라우저] 화면
       │
       ├─ 파일시스템    제약 없음 (읽기 전용)
       └─ bin/ctx       검증 위임

  .git 을 읽지 않는다. git 명령을 한 번도 실행하지 않는다. (§11)
  네트워크로 나가는 것이 아무것도 없다. (§2.2 ④ — 최신화조차 하지 않는다)
  문서는 물론 사용 기록·검색어도 PC를 떠나지 않는다.
```

**v0.1의 보안 논거가 약해지지 않고 더 강해진다.** v0.1은 "문서가 서버로 안 간다"였는데 v0.2는 "앱 자체가 네트워크에 없다"다. 외부 호스팅 심사 대상이 아예 아니다(v0.1 부록 A-3 소멸).

### 2.2 확정된 전제와 잘라낸 범위

초판(§2.1까지)은 "로컬 실행"만 확정하고 나머지를 열어뒀다. 네 가지가 확정되면서 **설계의 3분의 1이 불필요해졌다.** 무엇을 왜 뺐는지 남겨둔다 — 나중에 전제가 다시 넓어질 때 되살릴 자리를 알아야 한다.

| 확정된 전제 | 결과 |
|---|---|
| **① exe 실행 · loopback 리스너 확인됨** | §35의 치명 리스크 1 해소. **0단계가 통째로 사라진다**(§32) — 1단계부터 시작한다 |
| **② 대상은 개발 직군** | clone 마법사 · isomorphic-git · PAT·DPAPI 저장 · 레포 자동 탐색 · MSI 배포 **전부 삭제** |
| **③ 레포는 정해진 경로에 규약대로 존재** | 첫 실행이 **경로 지정 한 화면**으로 줄어든다(§26.1). 구조 검증만 남는다 |
| ③-a **경로가 로컬 NTFS 경로** (`C:\…`) | UNC·네트워크 드라이브가 아니므로 **파일 감시가 정상 동작한다.** §35의 감시 실패 리스크 해소 |
| **④ 최신화는 범위 밖** | `fetch` · `pull` · 원격 상태 표시 · 동기화 버튼 **전부 삭제**(구 §11.2·§23.1) |

**②가 가장 크게 줄인다.** 초판 §3은 `git clone`을 *"목록에서 가장 큰 항목"* 이라 적었다 — 프로토콜 §10.2가 감수한다고 명시한 비개발 직군 진입 장벽을 실제로 낮추는 유일한 기능이었기 때문이다. **대상이 개발 직군이면 그 장벽 자체가 없다.** 그 기능이 지탱했던 논거도 함께 사라지므로, §3에서 해당 행과 단락을 지운다.

### 2.3 git을 전혀 쓰지 않는다

초판과 이 개정의 중간 판까지는 **`git log`로 커밋 시각을 읽는 기능**을 남겨뒀다. 프로토콜 §12.1의 **기록 시각**을 위해서였다. 그것도 잘라낸다. 판단을 뒤집은 근거를 남긴다 — 같은 논의가 반복될 항목이다.

| 남기려던 근거 | 재검토 |
|---|---|
| *"프로토콜 §12.1의 네 축 중 하나다"* | 기록 시각은 독립 축이 아니라 **나이 축의 하위 정보**다. 그리고 프로토콜 §12.2는 나이를 *"참고용"* 으로 못박았다. 유효성(참/거짓)·절단(통보 필수)과 무게가 다르다 |
| *"사후 정리된 문서를 판별한다"* | **판별한 다음에 할 행동이 없다.** `⛔정정됨`은 "새 문서를 읽어라", `⚠후속 2건`은 "가서 봐라"인데 `기록 +44일`에 붙는 행동이 없다. 프로토콜도 *"해석에 주의"* 까지만 적었다 |
| *"`git log` 1회 spawn. 반나절"* | **비용을 잘못 셌다.** 증분 추적에 SHA 저장 + rebase·amend·브랜치 전환 시 무효화, rename 처리, 그리고 **`core.quotepath`** — git은 한글 파일명을 8진 이스케이프로 내놓아 `2026-0817-연심회-상태값추가.md` 가 깨진다. 여기에 backdated 커밋 fixture 제작이 더 붙는다 |
| *"로컬 실행의 실질 이득"* | **이게 진짜 이유였고, 틀린 이유다.** §3의 능력 델타가 두 줄로 줄어드는 것이 빈약해 보여서 남긴 것이다. **문서의 서사를 지키려고 기능을 남기는 것은 설계가 아니다** |

**결정적으로, 기록 시각의 소유자는 뷰어가 아니다.** pre-commit 훅(프로토콜 §11.2)은 이미 커밋 시점에 돌고 있어 커밋 시각을 공짜로 안다. **`ctx index`가 `INDEX.md`에 칼럼 하나를 넣으면 뷰어는 그것을 데이터로 읽으면 된다** — git 없이. §34에 요청 사항으로 옮긴다.

> **git이 스코프를 계속 침범하던 것 자체가 신호였다.** 전제를 두 번 좁혔는데도 `pull`·`clone`·자격 증명 논의가 매번 되살아났다. **뷰어가 git을 한 줄도 실행하지 않으면 그 경계 논쟁이 끝난다.** §11이 그것을 명문화한다.

### 파일 감시는 남긴다

최신화를 뷰어가 하지 않는다는 것과, 밖에서 최신화된 것을 뷰어가 알아차린다는 것은 다른 문제다. 사용자가 터미널에서 `git pull`을 하면 감시가 그것을 잡아 화면에 반영한다 — **오히려 뷰어가 pull을 안 하기 때문에 감시가 더 중요해진다.** 그리고 감시는 git이 아니라 파일시스템 이벤트다.

## 3. 무엇이 열렸나 — 능력 델타

전제 변경으로 실제로 달라지는 것만 모았다. **이 표가 v0.2를 쓰는 이유 전부다.**

| 항목 | v0.1 (브라우저) | v0.2 (로컬) | 프로토콜 연결 |
|---|---|---|---|
| **파일 감시** | 불가. 수동 새로고침 | 가능 (실시간 반영) | §10.5 어긋난 인덱스 위험 감소 |
| **`ctx check` 실행** | 불가. JS 재구현 | 위임 | §11.2 검증 로직 이중화 제거 |
| ~~git 커밋 시각~~ | 불가 | **쓰지 않는다** (§2.3) | `ctx index`가 `INDEX.md`에 넣을 일(§34-6) |
| ~~`git pull`~~ · ~~`git clone`~~ | 불가 | **범위 밖** (§2.2 ②④) | — |
| 브라우저 지원 | Chrome/Edge 데스크톱 | 전부 | — |
| 폴더 권한 | 프롬프트 · 정책 차단 위험 | OS 계정 권한 그대로 | — |
| 대용량 첨부 원본 | 링크 텍스트만 | 존재 확인 + OS 기본앱 열기 | §8.5 예외 조항 |
| 검색 인덱스 | 메모리 · IndexedDB | 디스크 캐시 + 한글 바이그램 | v0.1 §8.4의 알려진 한계 완화 |
| 개인 상태 (읽음·내 좌표) | IndexedDB | 앱 데이터 디렉터리 | §22 새 소식이 가능해진다 |

**남은 기능적 이득은 두 줄이다.** 파일 감시와 `ctx check` 위임 — 둘 다 편의와 중복 제거이고, 프로토콜이 정의한 새 신호를 여는 것은 하나도 없다.

> **그래서 로컬로 가는 진짜 이유는 이 표가 아니다.** v0.1은 치명 리스크(사내 파일 접근 정책)를 **확인 불가 상태로 남긴 조건부 설계**였고, 그것이 exe·loopback 확인으로 해소됐다(§2.2 ①). **능력이 늘어서가 아니라 전제가 확실해져서 로컬을 고른 것이다.** 이 절을 §4보다 앞에 두고 짧게 유지하는 이유다 — 능력 델타를 근거로 삼으면 판단이 틀린다.

## 4. 무엇이 닫혔나 — 리스크는 사라지지 않고 이동했다

v0.2를 낙관적으로만 쓰면 안 된다. 로컬로 옮기면서 **하나는 해소됐고, 하나는 남았고, 하나는 새로 생겼다.**

| | v0.1 | v0.2 |
|---|---|---|
| **치명 리스크** | 사내 정책의 파일 접근 차단 (`FileSystemReadBlockedForUrls`) — **확인 불가 상태로 방치** | 미서명 실행 파일 차단 → **§2.2 ① 로 해소됨** |
| **배포·업데이트** | URL 하나. 배포 즉시 전원 최신 | **PC마다 배포. 버전 파편화** ← 유일한 실질 후퇴 |
| **새 위험면** | 없음 (서버 0줄) | **localhost 리스너.** §7에서 전면 대응 |

**(1) 치명 리스크는 해소됐다.** exe 실행과 loopback 리스너 모두 확인됐다(§2.2 ①). **v0.1은 이 검증을 못 한 상태로 설계 전체가 조건부였다.** 여기가 v0.2를 v0.1보다 낫게 만드는 실질 근거다 — **능력 델타(§3)가 아니라 이쪽이다.**

**(2) 즉시 전원 최신 배포를 잃는다.** v0.1의 진짜 이점 중 하나였다. §6.3에서 완화하지만 완전히 되찾지는 못한다. 대상이 개발 직군으로 좁혀져 `npx` 경로가 실효를 갖는 것이 유일한 위안이다.

**(3) localhost 리스너는 실재하는 위험이다.** 로컬 웹앱을 쉽게 만들려다 **브라우저에 열린 임의의 외부 페이지가 사내 문서를 긁어가는 경로**를 여는 사고가 흔하다. **대상이 개발 직군이어도 이 위험은 줄지 않는다** — 오히려 개발자는 낯선 페이지를 더 많이 연다. §7을 건너뛰면 이 설계는 v0.1보다 나쁘다.

# 제1부 — 배포 형태

## 5. 형태 결정

### 5.1 네 가지 후보

| 형태 | 사용자 동작 | 사전 요구 | 관리자 권한 | 크기 | 판정 |
|---|---|---|:--:|---|---|
| **A. 포터블 단일 실행 파일** | exe 더블클릭 → 브라우저 열림 | 없음 | **불필요** | ~90MB | **채택** |
| **B. npm · `npx ctx-view`** | 터미널 명령 | Node 20+ | 불필요 | ~3MB | **채택 (동등)** |
| ~~C. MSI 설치~~ | 설치 후 시작메뉴 | 없음 | 필요 | ~90MB | **삭제** — 비개발 직군 배포용이었다(§2.2 ②) |
| D. Tauri 데스크톱 앱 | 앱 창 | WebView2 | 형태에 따라 | ~10MB | **보류.** §7 심사가 막히면 전환(§5.4) |

**A와 B를 동등하게 낸다.** 초판은 B를 "폴백"으로 뒀는데, **대상이 개발 직군이면 B가 폴백이 아니라 주 경로일 수 있다.** 개발자에게 `npx ctx-view`는 exe 복사보다 빠르고, §6.3의 버전 파편화도 자동으로 해결된다. 어느 쪽을 쓸지는 각자 고르게 하고, 둘은 같은 npm 패키지에서 나온다.

**그래도 A를 없애지 않는 이유** — 터미널을 열지 않고 문서를 보고 싶은 순간이 실제로 있다(회의 중, 다른 작업 중). 그리고 Node 버전이 낮거나 사내 npm registry 프록시가 말썽인 PC가 반드시 하나는 있다.

**Go·Rust로 쓰면 바이너리는 10배 작아지지만 B 경로가 사라진다.** 90MB는 한 번 복사하면 끝이다. 크기로 이 결정을 바꾸지 않는다.

### 5.2 실행 흐름

```
① ctx-view.exe 더블클릭
② 콘솔 창 없음 (windows 서브시스템). 트레이 아이콘 하나만 생긴다
③ 127.0.0.1 에서 빈 포트 확보  (7373 → 7374 → … → 임의)
④ 기본 브라우저를 http://127.0.0.1:7373/?t=<1회용 토큰> 으로 열기
⑤ 레포 경로가 설정돼 있으면 즉시 로드 / 없으면 경로 지정 화면(§26.1)
⑥ 브라우저 탭이 닫히면 (하트비트 90초 소실) 프로세스 자동 종료
```

`ctx-view --repo <경로>` 로 경로를 넘기면 ⑤를 건너뛰고 그 경로를 쓴다(설정에도 저장). `--no-open` 으로 브라우저 자동 열기를 끈다. **개발 직군 대상이므로 CLI 인자를 1급으로 둔다** — 프로젝트별 바로가기나 셸 별칭으로 쓰게 된다.

> **②의 구현** — `node.exe` 를 복사하면 콘솔 서브시스템이라 더블클릭 시 검은 창이 같이 뜬다. PE 헤더의 Subsystem 을 `CONSOLE(3) → WINDOWS(2)` 로 2바이트 패치한다. **그 대가로 stdout 이 사라지므로 §6.1 의 `logs/app.log` 가 선택이 아니라 필수가 된다** — 콘솔이 없으면 문제가 났을 때 볼 데가 없다. 아이콘도 같은 이유로 필요하다: 없으면 탐색기에 Node 아이콘이 떠서 사용자가 자기 도구를 못 알아본다.

⑥이 중요하다. **로컬 서버형 도구가 미움받는 첫 번째 이유는 꺼지지 않는 것이다.** 탭을 닫으면 앱도 죽고, 트레이에서 "계속 실행"을 선택한 사용자만 남는다. 종료 직전 캐시를 디스크에 flush 한다.

> **구현 확인** — 유휴 6초로 줄여(`CTXVIEW_IDLE_MS`) 양방향을 시험했다. 하트비트가 오는 동안은 살아 있고, 끊기면 종료된다. **트레이의 "탭 닫아도 계속 실행"은 켜져 있을 때 상태바에도 표시한다** — 화면에 안 보이면 사용자가 켠 사실을 잊고 "왜 안 꺼지지"가 된다.

### 5.3 폴백 사다리

§2.2 ①로 사다리 대부분이 불필요해졌다. 남는 것은 둘이다.

| 형태 | 언제 |
|---|---|
| exe ↔ `npx` 상호 대체 | 어느 한쪽이 특정 PC에서 안 될 때. 같은 패키지이므로 기능이 동일하다 |
| 사내 서버 1대 상주 + 사내망 접속 | **v1 범위 밖**(§31). 아래 참고 |

서버 모드는 **코드 변경 없이 가능하다** — 같은 바이너리를 `--host 0.0.0.0`으로 띄우면 된다. 그러나 그 순간 인증·권한 설계가 부활하고(v0.1 §2가 없앤 바로 그것) 문서가 다시 서버에 놓인다. **가능하다는 사실만 남겨두고 v1에서는 하지 않는다.** 중요한 것은 이 구조가 나중에 그 선택을 막지 않는다는 점이다 — v0.1의 브라우저 API 구조로는 이 전환이 불가능했다.

### 5.4 Tauri를 보류하되 버리지 않는 이유

Tauri는 **localhost 리스너가 없다.** IPC로 통신하므로 §7의 위험면이 원천적으로 사라지고, 앱 창·작업표시줄·서명 대상이라는 점에서 "설치형"에 더 가깝다.

그래도 지금 채택하지 않는다. Rust 툴체인이 붙고, WebView2 런타임 의존이 생기며, 디버깅이 브라우저보다 불편하고, **무엇보다 B 경로(`npx`)가 사라진다.** §5.1에서 B를 A와 동등하게 올렸으므로 이 마지막 근거는 초판보다 무거워졌다.

> **대신 전환 비용을 미리 낮춰둔다.** §8에서 모든 로직을 `core`에 두고 HTTP는 얇은 어댑터로만 만든다. §7 심사가 막히면 **어댑터만 IPC로 갈아끼운다.** 화면 코드는 손대지 않는다. 이것이 구조를 3층으로 나누는 유일한 이유다.

## 6. 라이프사이클

### 6.1 데이터 위치

```
%LOCALAPPDATA%\ctx-view\
  config.json     레포 경로 · 내 좌표 · 테마 · 창 상태
  cache.json      파싱 캐시 (path → mtime·size·프론트매터·섹션 오프셋)
  state.json      읽음 표시 · 마지막 방문 시각 · alias 미스 로그
  logs\app.log    회전 3개 · 각 1MB
```

**포터블 모드** — exe 옆에 `ctx-view.portable` 파일이 있으면 위 경로 대신 `<exe 폴더>\data\`를 쓴다. 공유 드라이브나 USB에서 그대로 돌아간다. 사내 로밍 프로필이 이상하게 잡히는 환경에서 이 스위치가 실제로 필요해진다.

**레포 안에는 아무것도 쓰지 않는다.** 캐시도, 읽음 표시도, 설정도. §31의 경계선이다 — **레포에 커밋될 수 있는 파일을 뷰어는 단 하나도 만들지 않는다.**

### 6.2 포트

기본 7373. 사용 중이면 +1씩 20회, 그래도 없으면 임의 포트. 고정 포트를 선호하는 이유는 브라우저 북마크가 살아 있기를 원해서이고, **고정 포트가 §7.1의 위협을 키운다는 점을 알고 있으므로 토큰과 Host 검증으로 막는다.**

### 6.3 업데이트 — 잃은 것을 어디까지 되찾나

v0.1의 "배포 즉시 전원 최신"은 되찾을 수 없다. 완화만 한다.

| 수단 | 동작 |
|---|---|
| **`npx` 를 권장 경로로** | `npx ctx-view@latest` 는 항상 최신이다. **대상이 개발 직군이므로 이것만으로 파편화 문제의 대부분이 사라진다**(§5.1에서 B를 A와 동등하게 올린 두 번째 이유) |
| **레포의 버전 힌트** | 레포 루트 `.ctx-view.json`(선택)의 `minVersion`이 앱 버전보다 높으면 상단에 *"이 레포는 뷰어 0.4 이상을 권장합니다"* 배너 |
| **자동 업데이트 없음** | 사내 PC에서 자동 다운로드·자기 교체는 EDR이 가장 싫어하는 동작이다. 하지 않는다 |
| **하위 호환 규칙** | 모르는 프론트매터 필드·모르는 `supersedes` 형식을 만나도 죽지 않고 *"이 앱이 모르는 형식"* 으로 표시(프로토콜 §9.8 대비) |

**버전 파편화를 완전히 막으려 하지 않는다.** 뷰어는 읽기 전용이므로 낡은 뷰어가 만드는 최악은 "새 신호를 못 보여주는 것"이고 문서를 망가뜨릴 수 없다. 이 성질 덕에 파편화를 감수할 수 있다.

## 7. 로컬 서버의 보안 설계 ★

**이 절이 §4(3)의 대가를 지불하는 곳이다.** v0.1은 서버가 없어 이 절이 필요 없었다.

### 7.1 위협

| # | 위협 | 결과 |
|---|---|---|
| 1 | 사용자가 방문한 **임의의 외부 페이지**가 `fetch('http://127.0.0.1:7373/api/docs')` 실행 | **사내 문서 전량 유출.** 가장 현실적인 사고 |
| 2 | **DNS 리바인딩** — 공격자 도메인이 127.0.0.1로 재바인딩되어 동일 출처를 위장 | 1과 동일. 토큰만으로는 부족할 수 있다 |
| 3 | 같은 PC의 다른 사용자·프로세스가 포트에 접속 | 문서 열람 |
| 4 | 경로 순회(`../../Users/…`) 또는 레포 밖을 가리키는 심볼릭 링크 | 레포 외 파일 유출 |
| 5 | 악의적 레포의 `bin/ctx` 실행 | 임의 코드 실행 |
| 6 | 문서 본문의 원본 경로가 실행 파일을 지목 | 사용자 클릭 시 실행 |

### 7.2 대응

| 대응 | 세부 | 막는 위협 |
|---|---|:--:|
| **127.0.0.1 전용 바인드** | `0.0.0.0`은 `--host` 플래그로만 가능하고 그때 화면에 상시 경고를 띄운다. 기본값으로 절대 열지 않는다 | 3 |
| **1회용 세션 토큰** | 실행마다 32바이트 난수. 브라우저가 `?t=`로 한 번 받아 `sessionStorage`에 넣고 이후 `Authorization: Bearer`로 전송. 외부 페이지는 이 값을 읽을 수 없다 | 1 |
| **`Host` 헤더 화이트리스트** | `127.0.0.1:<port>` / `localhost:<port>` 이외의 Host는 **응답 없이 연결 종료.** DNS 리바인딩의 표준 대응 | 2 |
| **CORS 미설정** | `Access-Control-Allow-Origin`을 어떤 값으로도 내리지 않는다. `*`는 물론 금지. 프리플라이트 전부 거부 | 1·2 |
| **`Sec-Fetch-Site` 검사** | `same-origin`이 아닌 API 요청 거부 (지원 브라우저에서 추가 방어) | 1 |
| **경로 봉인** | 모든 파일 요청을 `realpath`로 해석해 레포 루트 하위인지 확인. 밖을 가리키는 심링크는 **따라가지 않고 화면에 "레포 밖을 가리키는 링크"로 표시**(§13-③) | 4 |
| **`bin/ctx` 실행 동의** | 레포별 최초 1회, **해석된 절대 경로와 파일 해시를 보여주고** 사용자가 승인해야 실행. 파일이 바뀌면 다시 묻는다 | 5 |
| **원본 열기 제한** | OS 기본앱 열기는 명시적 클릭 + 절대 경로 표시 + 실행 확장자(`exe·bat·cmd·ps1·scr·lnk·js·vbs·msi`) 거부 | 6 |
| **쓰기 엔드포인트 최소화** | 쓰기 API는 앱 상태 3종(읽음·내 좌표·설정)뿐. **레포 경로를 인자로 받는 쓰기 API는 존재하지 않는다** | 4 |
| **유휴 종료** | 하트비트 90초 소실 시 종료 → 노출 시간 자체를 줄인다 | 1·3 |
| **살균 유지** | v0.1의 DOMPurify를 그대로. 로컬이라고 렌더 전 살균을 빼지 않는다 | — |

> **`Host` 헤더 검증이 토큰보다 중요하다.** 토큰은 유출·로깅으로 새어나갈 수 있지만 Host 검증은 브라우저가 이 헤더를 위조할 수 없다는 성질에 의존한다. 둘을 겹쳐 쓴다.

### 7.3 심사에 제출할 한 문장

> 문서는 사내 Git 레포에서 사용자 PC로만 이동하고, 앱은 외부로 어떤 데이터도 보내지 않으며, 열리는 리스너는 loopback 전용·1회용 토큰·Host 화이트리스트로 봉인되고, 브라우저 탭을 닫으면 함께 종료된다.

이 문장이 통과되지 않으면 §5.4의 Tauri로 전환한다. **그 경우 화면 코드는 그대로 쓴다.**

# 제2부 — 아키텍처

## 8. 3층 구조

```
┌──────────────────────────────────────────────────────────┐
│  client/   화면 (React + Vite 정적 빌드, 서버에 내장)      │
│            렌더링 · 상태 · 라우팅 · 검색 질의             │
├──────────────────────────────────────────────────────────┤
│  adapter/  전송 (HTTP + SSE)          ← 갈아끼울 수 있는 층 │
│            토큰 · Host 검증 · 정적 서빙 · 하트비트         │
├──────────────────────────────────────────────────────────┤
│  core/     로직 (전송 무관)                               │
│            스캔 · 프론트매터 · 섹션 분해 · 캐시 · 감시     │
│            유효성·최신성 계산 · 검색 인덱스 · git · ctx 위임 │
└──────────────────────────────────────────────────────────┘
```

**층을 나누는 목적은 하나다 — §5.4의 Tauri 전환 시 `adapter/`만 버리는 것.** 그 목적이 없으면 이 규모에서 3층은 과설계다. 그래서 규칙도 하나뿐이다.

> `core/`는 HTTP를 모른다. Request·Response·소켓 타입이 `core/`에 등장하면 층이 깨진 것이다.

`core/`는 500~700줄을 예상한다. 프로토콜 부록 D가 `bin/ctx`를 150줄로 잡은 것과 같은 성질의 코드에 감시·git·검색이 더해진 정도다.

## 9. 기술 선택 — 변경분 중심

v0.1에서 바뀌는 것만 적는다. 나머지는 v0.1 §6을 그대로 따른다.

| 항목 | v0.1 | v0.2 | 근거 |
|---|---|---|---|
| 런타임 | 없음 (브라우저) | **Node 20+** | 프론트엔드 빌드에 이미 필요하다. 언어를 늘리지 않는다 |
| 패키징 | Vercel 정적 배포 | **Node SEA (단일 실행 파일)** | 공식 기능. 서드파티 패커 의존을 만들지 않는다 |
| 파일 접근 | File System Access API | `node:fs` | — |
| 감시 | 없음 | **chokidar** | `fs.watch` recursive의 Windows 엣지 케이스를 피한다 |
| git | 없음 | **없음** | §2.3 · §11. git 바이너리도, isomorphic-git도 쓰지 않는다 |
| 캐시 | IndexedDB | **JSON 파일 1개** | SQLite는 네이티브 모듈이고, **네이티브 모듈은 단일 파일 패키징을 깨뜨린다.** 수백~수천 건에서 JSON으로 충분하다 |
| 검색 | MiniSearch | **MiniSearch + 한글 바이그램 토크나이저** | §20.4 |
| 마크다운 | markdown-it (클라이언트) | **동일 (클라이언트 유지)** | 서버는 원문만 보낸다. 표현은 전부 클라이언트가 소유한다 |
| 프론트매터 | js-yaml | 동일 | v0.1 §6의 근거가 그대로 유효 |
| 살균 | DOMPurify | 동일 | §7.2 |
| 하이라이팅 | highlight.js 지연 로드 | 동일 | — |

**넣지 않는 것** — SQLite(위 근거), Electron(90MB짜리 브라우저를 또 넣는다), 상태 관리 라이브러리, ORM, 로그 프레임워크.

> **서버가 마크다운을 렌더하지 않는 이유** — 렌더를 서버로 옮기면 조판·테마·지연 로드·인쇄 스타일이 전부 서버 관심사가 되고, §8의 "adapter만 갈아끼운다"가 무너진다. 서버는 **원문 텍스트와 파싱된 메타데이터**만 낸다.

## 10. 데이터 흐름

### 10.1 시작

```
① config.json 로드 → 레포 경로 확인
② cache.json 로드 (없으면 빈 캐시)
③ 증분 스캔 (v0.1 §7.3 전략 유지 — mtime+size 동일하면 읽지 않는다)
④ _vocab.md 파싱 → 좌표·alias 테이블
⑤ 유효성·최신성 계산 (저장하지 않는다. 프로토콜 §12.2)
⑥ 검색 인덱스 구성 (메모리)
⑦ chokidar 감시 시작
```

**외부 프로세스를 하나도 띄우지 않는다.** git도, `bin/ctx`도 여기서 실행하지 않는다 — `ctx check`는 사용자가 검증 뷰를 열 때만 돌고(§12), 그 전에는 승인 절차가 먼저다(§7.2).

③~⑥은 화면을 막지 않는다. ③이 끝나면 목록이 뜨고 ⑤⑥은 준비되는 대로 배지가 채워진다.

### 10.2 스캔 단위와 캐시 키

```
캐시 키 : path
캐시 값 : { mtime, size, frontmatter, sections[], headings[], commitAt }
무효화  : mtime 또는 size 불일치
```

v0.1은 `lastModified`만 봤다. **`size`를 같이 보는 이유** — Windows에서 파일 시스템·동기화 도구·git checkout이 mtime을 보존하는 경우가 있고, 그러면 변경을 놓친다. size는 공짜로 얻는 두 번째 신호다.

`sections[]`를 캐시하는 이유는 §19의 4섹션 레일이 매 문서 열 때마다 본문을 재파싱하지 않게 하려는 것이다.

### 10.3 감시와 반영

```
chokidar (레포 루트, .git 제외, *.md + assets/**)
  ├ 변경 → 해당 파일만 재파싱 → 유효성 재계산 → SSE 로 클라이언트 통지
  ├ 추가 → 동일
  └ 삭제 → 캐시 제거 → 끊어진 supersedes 참조 재계산
```

**재계산 범위** — 한 파일이 바뀌면 유효성 체인과 최신성은 전역 영향을 받을 수 있다. 수백 건 규모에서 전역 재계산은 수 밀리초이므로 **부분 갱신을 시도하지 않는다.** 부분 갱신은 틀리기 쉽고 여기서 이득이 없다.

**화면 반영 규칙은 §23.2에서 정한다.** 요약하면: 목록은 즉시 갱신하고, **읽고 있는 본문은 절대 자동으로 바꾸지 않는다.**

### 10.4 인식하는 구조

v0.1 §7.4를 그대로 유지하고 두 가지를 더한다.

```
<레포 루트>/
  knowledge/*.md              지식 단위 (프론트매터 파싱)
  knowledge/assets/**         첨부 (렌더만)
  INDEX.md                    직접 집계하므로 읽지 않되, 불일치는 경고
  INDEX-by-coord.md           있으면 존재만 인지. 신뢰하지 않는다 ← 추가
  _vocab.md                   좌표 어휘
  TEMPLATE.md · CLAUDE.md     일반 문서
  bin/ctx                     검증 위임 대상 ← 추가
  .ctx-view.json              뷰어 힌트 (선택, §6.3)
```

**`INDEX-by-coord.md`(프로토콜 §10.5 2단계)를 신뢰하지 않는 이유는 `INDEX.md`와 같다.** 뷰어는 전량을 직접 훑으므로 역인덱스가 필요 없고, 신뢰하면 밀린 인덱스를 믿는 위험이 생긴다. 다만 **존재하면 그것과 자체 집계를 비교해 불일치를 경고한다** — `ctx index`가 밀렸다는 신호이므로 유용하다.

## 11. git — 한 줄도 실행하지 않는다

**뷰어는 git을 모른다.** `.git`을 열지도, git 명령을 띄우지도 않는다. §2.3의 결론을 규칙으로 못박는 절이다.

| 연산 | 여부 | 근거 |
|---|:--:|---|
| `log` (커밋 시각) | **X** | §2.3. 행동이 붙지 않는 신호에 증분 추적·`core.quotepath`·fixture 비용을 쓰지 않는다. `INDEX.md` 칼럼으로 받는다(§34-6) |
| `fetch` · `pull` · `status` | **X** | §2.2 ④. 최신화는 사용자가 터미널에서 한다 |
| `clone` | **X** | §2.2 ②③ |
| `commit` · `push` | **X** | §31. 프로토콜 §11.2의 보증 체계를 우회하는 경로를 만들지 않는다 |
| `merge` · rebase · 브랜치 전환 | **X** | 뷰어는 지금 디스크에 있는 것을 그대로 본다 |

**얻는 것**

| | |
|---|---|
| 의존성 | git 바이너리·isomorphic-git 둘 다 불필요. **단일 파일 패키징이 더 단순해진다**(§9) |
| 프로세스 | 시작 시 외부 프로세스 spawn이 0회(§10.1). 시작 시간과 EDR 노출면이 함께 줄어든다 |
| 경계 | **`pull` 버튼 요구를 논의할 표면 자체가 없다.** "git을 안 쓴다"가 "pull만 살짝"보다 지키기 쉽다 |
| 대상 폴더 | §2.2 ③의 "규약대로 있는 폴더"가 **git 레포가 아니어도 상관없다.** 실제로 `sample-repo`가 그렇다 |
| 검증 | backdated 커밋 fixture가 필요 없어진다(§32) |

**잃는 것은 하나다** — 프로토콜 §12.1의 **기록 시각**. §17.3의 2단은 `date` 하나만 쓴다.

> **`.git` 폴더를 감시·스캔 대상에서도 제외한다.** chokidar 감시 경로에서 `.git/**`를 빼는 것은 성능 문제가 아니라 **정확성 문제**다. git 내부 파일 변경(인덱스·로그·참조)이 문서 변경으로 오인되면 §23.2의 갱신이 무의미하게 폭발한다. `node_modules`·`dist` 같은 디렉터리도 같이 제외한다 — `sample-repo`처럼 레포가 프로젝트 폴더 안에 있으면 경로 지정이 잘못돼 상위 폴더를 가리킬 수 있다.

## 12. 검증 위임 — 두 개의 구현을 만들지 않는다

v0.1 §8.5는 `ctx check`의 검사 항목을 **JS로 다시 구현**하는 설계였다. 로컬이 되었으므로 그럴 필요가 없다.

```
검증 뷰 열기
  ├ bin/ctx 있음 + 실행 동의 있음(§7.2)
  │    → ctx check --json 실행 → 결과 표시  [정본 검증]
  └ 없음 / 거부 / 실패
       → 뷰어 내장 검사 실행 → 결과 표시  ⚠ [내장 검사 — 정본과 다를 수 있음]
```

**두 경로를 화면에서 구분해 표시하는 것이 핵심이다.** 내장 검사를 정본처럼 보여주면 뷰어와 훅이 어긋났을 때 사용자가 훅을 의심하지 않는다. 프로토콜 §11.2의 *"skill은 편의, hook은 보증"* 과 같은 구도다 — **뷰어는 편의, `ctx check`가 보증이다.** 어느 쪽 결과를 보고 있는지 숨기지 않는다.

내장 검사는 다음만 한다(정본 위임이 실패했을 때의 최소 안전망).

| 검사 | 내장 | `ctx check` 위임 |
|---|:--:|:--:|
| 필수 필드 누락 | O | O |
| `_vocab.md` 미등재 좌표 | O | O |
| `supersedes` 대상 문서 없음 | O | O |
| `id` ≠ 파일명 | O | O |
| `INDEX.md` 불일치 | O | (`ctx index`가 갱신) |
| 좌표 1개짜리 문서 안내 (프로토콜 §9.3) | O | 규칙에 따라 |
| **본문 4섹션 누락 · "왜" 비어 있음** | **O** | X ← §19.2 |
| 그 외 조직이 추가한 규칙 | X | O |

마지막 두 줄이 이 표의 요점이다. **뷰어만 할 수 있는 검사(본문 품질)와 `ctx check`만 할 수 있는 검사(조직 규칙)가 서로 다르므로, 둘은 대체 관계가 아니라 보완 관계다.**

> **프로토콜 측에 필요한 것** — `ctx check --json`. 부록 D의 현재 명세에는 없다. §34에 요청 사항으로 정리한다.

# 제3부 — UI/UX 설계 ★

## 13. 설계 원칙

**전부 프로토콜에서 유도된 것이고, 취향에서 온 것이 하나도 없다.** 화면 논쟁이 생기면 아래 대전제와 여섯 원칙으로 판정한다.

### ⓿ 대전제 — 화면의 주인은 본문이다

이 프로토콜이 벡터화를 택하지 않은 결과가 하나 있다. **문서가 사람이 읽을 수 있는 형태로 남아 있다는 것.** 청킹·임베딩된 데이터는 사람이 못 읽는다. 프로토콜 §8.1이 *"프론트매터는 기계가 읽고, **본문은 사람과 AI가 읽는다**"* 라고 쓴 것, §8.4가 *"본문은 일부러 구조화하지 않는다"* 며 산문으로 남긴 것이 전부 그 성질을 지키기 위한 선택이다.

**뷰어는 그 성질을 사람이 실제로 쓸 수 있게 만드는 도구다.** 프로토콜 §10.2가 감수한다고 한 것도, v0.1 §4가 메우겠다고 한 첫 번째 구멍도 *"raw 마크다운을 읽으라고 하는 건 무리다"* 였다. 이름이 뷰어인 이유가 그것이다.

> **v0.1 §8.3의 *"본문 위에 붙는 배지가 이 뷰어의 존재 이유다"* 는 과장이었고, 이 문서의 초판은 그것을 §17의 제목으로까지 승격시켰다.** 배지는 **읽기 전에 이 문서를 읽어야 하는지 판단시켜 주는 보조 장치**다. 존재 이유가 아니다. 존재 이유는 본문을 읽는 것이고, 배지가 본문을 밀어내면 도구가 목적을 잡아먹는다.

그래서 다음이 규칙이 된다.

| 규칙 | |
|---|---|
| **본문은 화면에서 가장 크고, 가장 조용하고, 가장 잘 읽히는 영역이다** | 나머지는 전부 본문에 딸린 것이다 |
| **정상 문서를 열면 첫 화면의 대부분이 본문이어야 한다** | 유효성 블록이 접힌 상태로 차지하는 높이의 상한을 §17.6에 못박는다 |
| **본문을 해석하지 않는다** | 요약·재구성·필드 추출·AI TL;DR 전부 없다(§31). 프로토콜 §8.4의 메타데이터/본문 분리를 뷰어가 깨면 안 된다 |
| **읽기를 방해하는 것은 기능이라도 뺀다** | 배지·알림·토스트·자동 스크롤은 전부 이 기준으로 판정한다(원칙 ⑥) |
| **긴 문서를 끝까지 읽을 수 있어야 한다** | 위치 복원·본문 폭 조절·집중 모드는 부가 기능이 아니라 본체다(§27.5~27.8) |

**이 문서에서 §19(4섹션 레일) · §27(읽기)이 중심 절이다.** §17·§18·§20~§25는 그 주위의 보조 장치이고, 절 개수가 많다는 것이 중요도를 뜻하지 않는다 — 보조 장치가 규격을 많이 요구할 뿐이다.

### ① 색은 유효성에만 쓴다. 나이에는 쓰지 않는다

프로토콜 §12.2 — *"2년 전 문서라도 정정되지 않았으면 그것이 현재의 정답이다."*

색은 화면에서 가장 희소한 신호다. **참/거짓으로 판정되는 사실에만 배정한다.** 나이·작성자·태그는 **언제나 무채색 텍스트**다. 나이에 노란색을 한 번 쓰면 사용자는 "오래된 것은 위험" 이라는 잘못된 규칙을 학습하고, 그 학습은 색을 지운 뒤에도 남는다.

색 예산은 네 개뿐이다.

| 색 | 의미 | 예 |
|---|---|---|
| 파랑 | **상호작용** (링크·선택·포커스) | 선택된 목록 행 |
| 적 | **무효** — 정정 · 섹션/문서 없음 · 끊김 | ⛔ 정정됨 |
| 앰버 | **경고** — 후속 · 밀림 · 미등재 · 인덱스 불일치 | ⚠ 후속 2건 |
| 보라 | **미결** (행동 대기) | 미결 배지 |

**초록은 쓰지 않는다.** "유효"는 정상 상태이고, 정상 상태에 색을 주면 화면의 90%가 초록이 되어 색이 의미를 잃는다. 그리고 적·초록 쌍은 색약 사용자에게 최악의 조합이다. **정상은 조용하고 이상만 소리를 낸다** — 이 규칙이 §29의 접근성 문제를 부수적으로 함께 해결한다.

### ② 절단을 조용히 하지 않는다

프로토콜 §12.3의 [절단] 신호는 AI 세션을 위한 것이지만, **UI의 목록도 정확히 같은 방식으로 조용히 실패한다.** 12건 중 5건만 보여주고 아무 말 하지 않으면 사용자는 5건이 전부라고 믿는다.

| 금지 | 대신 |
|---|---|
| 무한 스크롤로 끝을 알 수 없게 | 항상 `표시 20 / 전체 137` |
| 필터로 조용히 감추기 | `정정된 문서 3건 숨김 [보기]` |
| 상위 N건만 잘라 보여주기 | `12건 중 12건` — 다 보여줄 때도 숫자를 적는다 |
| 검색 결과 개수 생략 | `좌표 매칭 8건 · 전문 검색 미실행` |

**다 보여줄 때도 개수를 적는 이유** — 개수가 있을 때만 적으면 사용자는 개수가 없을 때 "전부인가 아닌가"를 매번 판단해야 한다. 항상 있으면 판단이 필요 없다.

### ③ 이상한 데이터는 화면에서 사라지지 않는다

프로토콜 §9.6 조용한 실패. 미등재 좌표를 필터로 걸러내면 화면은 깨끗해지고 **문제는 영원히 발견되지 않는다.**

| 이상 | 표시 |
|---|---|
| `_vocab.md` 미등재 좌표 | 좌표 트리 하단 **미등재 섹션**에 모아 표시 (v0.1 §8.1 유지) |
| `supersedes` 대상 없음 | 헤더에 `⛔ 대상 문서 없음: 2026-0710-…` — 링크가 아니라 깨진 칩으로 |
| 필수 필드 누락 | 목록 행과 본문 헤더 양쪽에 표시 |
| `id` ≠ 파일명 | 본문 헤더에 경고 |
| 레포 밖을 가리키는 링크·첨부 | 열지 않고 `레포 밖: <절대경로>` 로 표시 |
| 앱이 모르는 프론트매터 형식 | `이 앱이 모르는 형식` (§6.3 하위 호환) |

### ④ 본문이 4섹션이라는 것을 UI가 활용한다

프로토콜 §8.4는 본문 구조를 고정했다. **뷰어는 모든 지식 단위의 구조를 미리 안다.** 이건 일반 마크다운 뷰어가 가질 수 없는 정보이고, v0.1은 이걸 쓰지 않고 generic 렌더만 했다. §19에서 쓴다.

### ⑤ 정본 좌표를 사용자에게 가르친다

프로토콜 §9.5(2)는 *"사람이 정본을 외울 필요가 없어진다"* 고 했다. 맞다. 그런데 **대조를 몰래 해주면 사용자는 영원히 정본을 모른다.**

대조는 항상 화면에 드러낸다. `연구계획테이블 → table:tb_research_plan`. 몇 주 쓰면 사용자는 정본을 알게 되고, 그때부터 검색이 더 정확해진다. **뷰어는 어휘 학습 장치이기도 하다.**

### ⑥ 읽는 사람의 자리를 빼앗지 않는다

로컬 앱은 파일 변경을 실시간으로 안다. 그래서 **읽고 있는 문서를 밑에서 갈아치우는** 유혹이 생긴다. 하지 않는다.

| 상황 | 처리 |
|---|---|
| 목록의 다른 문서가 변경 | 조용히 갱신 |
| **읽고 있는 문서가 변경** | 본문 상단에 바 하나 — `이 문서가 디스크에서 변경되었습니다 [다시 읽기]`. 내용은 그대로 둔다 |
| 새 문서 도착 | 상태바 카운터 + 새 소식 뷰 배지. **토스트를 띄우지 않는다** |
| 스크롤·선택·검색어 | 갱신 후에도 유지 |

## 14. 정보 구조 — 뷰 다섯 개

v0.1은 트리·목록·본문의 3분할만 정했고 뷰 개념이 없었다. 사이드바에 다섯 개를 둔다. **여섯 번째를 추가하려면 §31을 먼저 읽는다.**

| # | 뷰 | 무엇 | 프로토콜 근거 |
|---|---|---|---|
| 1 | **새 소식** | 마지막 방문 이후 추가·변경된 문서. 내 좌표에 걸린 것 먼저 | §11.4 완화(§22) |
| 2 | **좌표** | `_vocab.md` 타입별 트리 + 미등재 섹션 | §9.1 · §9.4 |
| 3 | **최근** | 전체 시간순 평면 목록 | §10.4 *"목록만 봐도 시간 감각이 실린다"* |
| 4 | **미결** | `status: 미결` 전용. 대기 일수 정렬 | §8.3 *"미결만 필터하면 그것이 결정 목록이다"* |
| 5 | **검증** | `ctx check` 위임 결과 + 내장 검사 | §11.2 |

**검색은 뷰가 아니다** — `⌘K` 오버레이로 열리고 결과를 목록 창에 채운다. 검색은 모든 뷰에서 같은 방법으로 열려야 하므로 뷰로 만들면 오히려 멀어진다.

**좌표 타임라인도 뷰가 아니다** — 본문 창 안의 패널이다(§18). 지금 보는 문서와 함께 있어야 의미가 있다.

**첫 화면 규칙**

```
새 소식이 1건 이상 → 새 소식
없고 최근 열어본 문서 있음 → 그 문서 (읽던 위치까지. §27.6)
그 외 → 최근
첫 실행 → 경로 지정(§26.1)
```

**두 번째 줄이 §13-⓿의 반영이다.** 뷰어를 다시 열었을 때 가장 흔한 의도는 "어제 읽던 것을 이어 읽기"다. 목록으로 떨어뜨리면 사용자가 그 문서를 다시 찾아야 한다.

> **다섯 개 뷰는 전부 목적지가 아니라 경로다.** 목적지는 본문 하나다. 뷰를 늘리자는 요구가 오면 *"이 뷰가 본문에 더 빨리 도달시키는가"* 로 판정한다 — 새 종류의 목록을 만드는 것은 대개 아니다.

### 15.3 반응형 — 목표는 모바일이 아니라 분할 화면

**이 앱의 실제 두 번째 레이아웃은 에디터 옆에 반쪽으로 붙여둔 창이다.** 720px을 1급 레이아웃으로 설계한다.

| 폭 | 레이아웃 |

| ≥1200px | 3분할 |
| 900~1200px | 사이드바 자동 접힘(아이콘 레일 48px) + 목록 + 본문 |
| 720~900px | **목록과 본문 2분할.** 사이드바는 오버레이 |
| <720px | 단일 열 + 뒤로가기. 목록↔본문 전환 |

모바일은 §31의 비목표다. 다만 <720px에서 깨지지 않게만 한다 — v0.1 §9의 *"기능이 아니라 최소한의 예의"* 와 같은 태도다.

## 17. 유효성 블록 — 읽기 전에 판단시켜 주는 장치

프로토콜 §12.3이 AI 세션에 주입하는 네 줄을 **사람이 0.5초에 읽는 형태로** 옮긴다.

**이 블록의 역할은 하나다 — 본문을 읽기 전에 "이걸 읽어도 되는가"를 알려주는 것.** ⛔정정됨이면 읽지 말고 새 문서로 가야 하고, ⚠후속 2건이면 읽고 나서 그것들도 봐야 한다. 그 판단이 끝나면 **블록은 시야에서 사라져야 한다.** §13-⓿에 따라 §17.6에서 높이 상한을 못박는다.

> **초판은 이 절을 *"이 뷰어의 존재 이유"* 라고 제목에 달았다.** v0.1 §8.3의 문장을 그대로 승격시킨 것인데, 그 결과 이 문서는 배지에 5개 절을 쓰고 읽기에 1개 절을 썼다. **§13-⓿에서 그 판단을 뒤집었다.** 블록의 규격은 그대로 유지한다 — 필요한 장치이고 정밀해야 한다. 바뀐 것은 위계다.

### 17.1 세 단 구조

```
┌───────────────────────────────────────────────────────────────┐
│ ⛔ 정정됨    2026-0828-plan-status 로 대체됨            [열기 ▸] │ ← 1단: 유효성. 색 있음
├───────────────────────────────────────────────────────────────┤
│ 결정 2026-08-19 · 3주 전         확정 · kjsa · 좌표 4 · 📎 1   │ ← 2단: 시간. 무채색
├───────────────────────────────────────────────────────────────┤
│ ⚠ 이 문서의 좌표 중 1곳에 후속이 있습니다                  │ ← 3단: 최신성. 앰버
│    table:tb_research_plan          후속 2건 ▸                  │
│    api:/adapter/a10/plan-sync      최신                        │
│    module:acl-adapter              최신                        │
│    domain:연구관리                  후속 5건 ▸                  │
└───────────────────────────────────────────────────────────────┘
```

**1단과 2단을 물리적으로 분리한 선이 §13-①의 시각적 강제다.** 색이 있는 칸과 없는 칸이 눈으로 갈린다.

### 17.2 1단 — 유효성 상태

| 상태 | 표시 | 색 |
|---|---|---|
| 유효 | `✓ 유효` — 작게, 조용히 | 무채색(`text-2`) |
| **정정** | `⛔ 정정됨 · <정정한 문서> 가 바로잡음 [열기]` | `danger` |
| **부분 정정** | `◐ 부분 정정 · table:tb_research_plan 에 대해서만` | `danger` (테두리만) |
| 대상 없음 | `⛔ supersedes 대상 문서 없음: <id>` | `danger` |
| 순환 | `⛔ supersedes 순환 참조` | `danger` |

**유효 상태를 조용하게 만든 것은 의도적이다.** 정상일 때 사용자는 배지를 읽지 않고 본문으로 내려가야 한다. 놓쳐서 손해가 나는 것은 이상 상태뿐이다(§13-①).

**부분 정정은 프로토콜 §9.8이 도입 보류한 좌표 단위 무효화다.** 지금은 나타나지 않는다. 그런데 **자리를 미리 만들어 둔다** — v0.1 §14.3이 `normalizeSupersedes`를 미리 둔 것과 같은 이유이고, 화면에서도 같은 대비가 필요하다. `supersedes`가 객체 배열로 오면 이 상태가 자동으로 나타난다.

**순환 참조를 항목으로 둔 이유** — `ctx check`가 이걸 잡는지 프로토콜 부록 D에 명시되지 않았다. 잡지 않으면 무한 루프로 뷰어가 죽는다. 체인 추적에 방문 집합을 두고, 순환을 발견하면 **끊지 않고 표시한다**(§13-③).

### 17.3 2단 — 시간. 색이 없다

```
결정 2026-08-19 · 3주 전                      확정 · kjsa
```

| 규칙 | |
|---|---|
| 나이는 절대 색을 갖지 않는다 | 2년 전도 `text-2` |
| 상대 시간 + 절대 날짜를 같이 | `3주 전`만 있으면 정확한 날짜를 알 수 없고, `2026-08-19`만 있으면 감각이 없다 |
| **`date`만 쓴다** | 기록 시각(프로토콜 §12.1)은 §11에 따라 표시하지 않는다 |
| 미래 날짜 · 파싱 실패 | `⛔ date 형식 오류: <원문>` — 무채색이 아니라 오류로 취급한다(§13-③) |

**2단이 초판보다 비었다.** 그래서 규칙이 하나 더 필요하다 — **빈 자리를 다른 것으로 채우지 않는다.** 태그·첨부 수·좌표 수를 여기로 올리고 싶은 유혹이 생기지만, 이 단의 역할은 *"시간을 색 없이 보여주는 것"* 하나다. 정보를 더 넣으면 1단(유효성)과 3단(최신성)의 대비가 흐려진다.

> **`INDEX.md`가 기록 시각 칼럼을 갖게 되면(§34-6) 이 칸이 돌아온다.** 그때 표시 규칙은 이렇다 — 차이만 강조(`기록 08-23 · 결정 +4일`), 30일 이상이면 굵게 + 호버로 *"사후 정리된 문서"* 설명, **그래도 색은 주지 않는다.** 참/거짓이 아니라 해석이 필요한 정보이므로 색을 주면 §13-①이 무너진다.

### 17.4 3단 — 최신성

프로토콜 §12.2의 최신성은 **좌표별로** 계산된다. v0.1 §8.3의 배지 표는 이걸 한 줄로 뭉갰다. 좌표마다 다르므로 좌표마다 적는다.

| 규칙 | |
|---|---|
| 후속 0건인 좌표는 `최신` | 무채색. 조용히 |
| 1건 이상은 `후속 N건 ▸` | 앰버. 클릭 → §18 타임라인이 그 좌표로 |
| 3단 헤더는 **좌표 개수로 요약** | `⚠ 이 문서의 좌표 중 1곳에 후속이 있습니다` |
| 좌표 6개 초과 | 후속이 있는 좌표를 위로, 나머지는 접는다 (`+3개 좌표`) |
| 전 좌표가 최신 | 3단 전체를 **접어서** 한 줄로: `모든 좌표에서 최신 문서입니다` |

`domain:연구관리 후속 5건`처럼 **입도가 굵은 좌표는 후속이 항상 많다.** 이건 노이즈다. 그래서 `domain` 타입은 기본 접힘으로 두고, 설정에서 "최신성 계산에서 domain 제외"를 켤 수 있게 한다. 프로토콜 §9.3의 입도 문제가 화면에 그대로 나타나는 지점이다.

### 17.5 목록 행에서의 축약

같은 정보를 목록에서는 이렇게 줄인다.

```
● 08-19  A10 연계 어댑터 인터페이스 개편 — 계획서 상태…    확정  ⚠2  📎1
○ 07-10  A10 연계 어댑터 v1                                ⛔ 정정됨
● 06-12  계획서 스키마 정의                                미결  3일 대기
```

| 기호 | 의미 |
|---|---|
| `●` / `○` | 안 읽음 / 읽음 |
| `◉` | 지금 보는 문서 |
| `⛔ 정정됨` | 정정된 문서. 행 전체 `text-3`, 기본 접힘(v0.1 §8.2 유지) |
| `⚠N` | 후속 — 후속이 있는 좌표 수 |
| `📎N` | 첨부 수 |
| `미결 · N일 대기` | 미결 상태와 경과일 (프로토콜 §17 성공지표 "미결 대기 시간") |

### 17.6 높이 상한 — §13-⓿을 검사 가능하게

원칙만 적어두면 지켜지지 않는다. **숫자로 못박고 3단계에서 실측한다.**

| 상태 | 블록 높이 | 결과 |
|---|---|---|
| **정상 문서** (유효 · 전 좌표 최신) | **≤ 72px** | 1단은 `✓ 유효` 한 줄, 2단 한 줄, 3단은 `모든 좌표에서 최신 문서입니다` 한 줄로 접힘 |
| 정정 | ≤ 120px | 1단이 대체 문서 링크와 함께 확장 |
| 후속 있음 | ≤ 200px | 3단이 좌표별로 펼쳐짐. 좌표 6개 초과는 접는다(§17.4) |
| 어떤 경우에도 | **≤ 240px** | 넘으면 3단을 접고 `⚠ 후속 3곳 [보기]` 한 줄로 대체한다 |

**검사 방법** — 1920×1080 창에서 정상 문서를 열었을 때 **첫 화면 세로의 90% 이상이 본문이어야 한다.** 72px는 1080px의 7%다.

> **구현 실측 (GDI fixture 20건)** — 정상 **63px** · 후속 있음 **164px** · 순환 **97px**. 전부 예산 안이다.
>
> **처음엔 91px 이 나왔고, 줄인 방법이 크기가 아니라 설계였다.** 1단 `✓ 유효` 와 3단 `모든 좌표에서 최신` 은 **둘 다 "이상 없음"을 말한다.** 정상 상태가 화면 세로를 두 줄 차지할 이유가 없어 한 줄로 합쳤다 — `✓ 유효 · 모든 좌표에서 최신`. §13-① 의 *"정상은 조용하고 이상만 소리를 낸다"* 가 높이에도 적용된 것이고, **숫자를 못박아 두지 않았으면 이 중복을 발견하지 못했을 것이다.**

| 추가 규칙 | |
|---|---|
| 스크롤하면 블록은 **따라오지 않는다** | 판단은 처음 한 번이면 된다. 상단 고정(sticky)은 4섹션 레일만 한다(§19.1) |
| **⛔정정됨은 예외** | 정정된 문서를 읽는 동안에는 얇은 바 하나(24px)를 상단에 고정한다. *"이 문서는 정정됐습니다 → 2026-0828"*. 잘못된 정보를 읽고 있다는 사실은 계속 보여야 한다 |
| 블록에 정보를 추가하려면 | **무엇을 뺄지 먼저 정한다.** 이 블록은 자라기만 하는 종류의 UI다 |

## 18. 좌표 타임라인 — 최신성을 숫자가 아니라 형태로

"후속 2건"은 숫자라서 안 읽힌다. **`supersedes` 체인은 v0.1에서 링크 하나였고, 체인 전체를 볼 방법이 없었다.** 본문 하단 패널로 붙인다.

```
── 이 좌표의 이력 ─────────────── table:tb_research_plan  5건 ──

  2026-08-30  ●  배치 재처리 규칙 변경                       확정
                 └ 이 문서의 후속
  2026-08-28  ●  계획서 상태값 추가                          확정
                 ┐
  2026-08-19  ◉  A10 연계 어댑터 개편          ← 지금 보는 문서
                 │  supersedes
  2026-07-10  ○  A10 연계 어댑터 v1                       ⛔ 정정됨
                 ┘
  2026-06-12  ●  계획서 스키마 정의                          확정

     좌표 전환:  table:tb_research_plan ▾   (이 문서의 좌표 4개)
```

| 규칙 | |
|---|---|
| 세로 시간축, 위가 최신 | 프로토콜 §10.4의 "목록만 봐도 시간 감각" 을 축으로 승격 |
| 현재 문서 위쪽 = 최신성 | **숫자를 세지 않고 형태로 본다.** 위에 뭐가 많으면 후속이 쌓인 좌표다 |
| `supersedes` 관계는 연결선 | 실제 구현은 얇은 SVG 커넥터. 정정한 문서 → 정정된 문서 |
| 정정된 문서는 흐리게, **지우지 않는다** | 프로토콜 §9.7. 과거 결정의 근거로 필요하다 |
| 좌표 전환 드롭다운 | 문서의 좌표 여러 개를 같은 자리에서 갈아본다 |
| 5건 초과 | 현재 문서 기준 위 3 / 아래 2 + `+N건 더` (§13-②) |

**이 패널이 v0.1 대비 가장 큰 UI 추가다.** 프로토콜 §12.2의 최신성은 "경고 부착"이라고만 되어 있는데, 경고 문구는 읽히지 않고 형태는 읽힌다.

## 19. 4섹션 레일 ★ — 본문 구조를 안다는 이점

프로토콜 §8.4는 본문을 네 섹션으로 고정했다. **뷰어는 모든 지식 단위의 목차를 미리 안다.** 일반 마크다운 뷰어는 가질 수 없는 정보다.

### 19.1 레일

```
[무엇이 바뀌었나]  [왜]  [누구에게 영향 ①]  [후속 조치]
                    ▔▔                              ← 현재 위치
```

- 본문 상단에 **고정(sticky)**. 클릭하면 해당 섹션으로 스크롤
- 스크롤에 따라 현재 섹션 강조
- 섹션이 없으면 그 칸을 **흐리게 + 취소선** — 없다는 사실을 보여준다(§13-③)
- 지식 단위가 아닌 문서(`TEMPLATE.md`·`CLAUDE.md`·첨부)는 레일 대신 일반 목차

### 19.2 "왜"를 강조한다

프로토콜 §8.4 — *"이 섹션이 문서의 수명을 결정한다"*, *"6개월 뒤 이 결정을 뒤집으려는 사람이 필요로 하는 것"*.

| 처리 | |
|---|---|
| 좌측 3px 강조 바 + 배경 미세 차이 | 스크롤 중에 눈에 걸린다 |
| 레일에서 살짝 크게 | |
| **"왜"가 비었거나 없으면** | 본문 상단에 `⚠ 이 문서에는 '왜'가 없습니다 — 반년이면 쓸모를 잃습니다` (§12의 내장 검사 항목) |

### 19.3 "누구에게 영향" 개인화

프로토콜 §8.4 — *"수신자가 자기 항목을 찾는 곳"*. 내 좌표(§22)가 설정돼 있으면 이 섹션에서 내 좌표가 언급된 부분을 찾아 표시한다.

```
[누구에게 영향 ①]        ← 레일에 내 좌표 언급 개수
```

본문에서는 해당 문장에 좌측 마커와 옅은 강조. **자동 스크롤은 하지 않는다**(§13-⑥) — 대신 레일 칸 클릭 시 그 위치로 간다. 매칭은 좌표 문자열과 `_vocab.md`의 alias를 함께 본다. `연구계획테이블`이라고 산문에 쓰여 있어도 `table:tb_research_plan` 구독자에게 걸린다. **프로토콜 §9.4가 alias를 둔 목적이 검색뿐 아니라 여기서도 쓰인다.**

### 19.4 첨부

```
── 첨부 ────────────────────────────────────────────
  📄 interface-spec.md          12KB   [본문에 펼치기] [열기]
  📊 원본: 그룹웨어 > 연구관리 > A10 연계 협약서 (2026-08-12 결재완료)
        요지: 상태 동기화 주기 5분, SLA 99.5%, 장애 재처리는 A10 책임
        링크 ↗   /  로컬 경로 확인됨: Z:\연구관리\… [원본 열기]
```

| 종류 | 처리 |
|---|---|
| `assets/` 안의 텍스트·MD | 같은 뷰어로 렌더. **본문에 인라인 펼치기** 옵션 (v0.1 §12에서 관측되면 하려던 것을 기본 제공) |
| 이미지 | 인라인 표시 + 클릭 확대 |
| 프로토콜 §8.5 예외의 외부 원본 | **제목·시점·요지를 먼저**, 링크는 뒤에. 프로토콜이 *"링크는 썩지만 제목·시점·요지는 썩지 않는다"* 고 한 순서를 화면 순서로 옮긴다 |
| 로컬에 실재하는 경로 | 존재 확인 후 `[원본 열기]` (§7.2 제한) |
| 경로가 없음 | `경로를 찾을 수 없음` 표시. 숨기지 않는다 |

**첨부는 이 뷰어에서 가장 긴 문서다.** 프로토콜 §8.5의 3계층 중 *"실제로 그 인터페이스를 구현하는 한두 사람"* 이 읽는 곳이고, 인터페이스 명세는 지식 단위 요약보다 몇 배 길다. 그래서 첨부를 열었을 때 **지식 단위와 동등한 읽기 환경을 준다.**

| 규칙 | |
|---|---|
| **읽기 환경이 동일하다** | §27.5 읽기 모드 · §27.6 위치 복원 · §27.7 폭·크기 조절이 첨부에도 그대로 적용된다 |
| 4섹션 레일 대신 목차 | 첨부는 4섹션 규약을 따르지 않는다. §27.4의 `h2`/`h3` 목차로 대체(§19.1) |
| **모문서로 돌아가는 경로를 항상 둔다** | 상단에 `← 2026-0819-a10-adapter 의 첨부`. 첨부만 열려 있으면 어느 결정의 근거인지 알 수 없다 |
| 인라인 펼치기의 기본값 | **접힘.** 12KB 명세를 요약 아래에 자동 펼치면 §8.5의 3계층이 화면에서 무너진다. 펼침 상태는 문서별로 기억한다 |
| 유효성 블록 | 첨부에는 붙이지 않는다. **모문서의 유효성을 얇은 바로만 알린다** — 정정된 문서의 첨부를 읽고 있으면 그 사실이 필요하다(§17.6) |

## 20. 검색 — 대조를 화면에 드러낸다

프로토콜 §9.5(2)의 읽기 시점 대조를 구현하되, **대조 과정을 숨기지 않는다**(§13-⑤).

### 20.1 `⌘K` 오버레이

```
┌─ ⌘K ────────────────────────────────────────────────────────┐
│  연구계획 테이블 관련 최근 변경                               │
├─────────────────────────────────────────────────────────────┤
│  대조   "연구계획테이블" → table:tb_research_plan            │
│         alias 일치 · _vocab.md:12                    [복사]  │
├─────────────────────────────────────────────────────────────┤
│  좌표 문서    5건 중 5건 · 정정된 문서 1건 숨김 [보기]          │
│    ● 2026-08-30  배치 재처리 규칙 변경               확정    │
│    ● 2026-08-28  계획서 상태값 추가                  확정    │
│    ● 2026-08-19  A10 연계 어댑터 개편                확정    │
├─────────────────────────────────────────────────────────────┤
│  전문 검색    좌표 결과가 있어 실행하지 않음   [강제 실행 ⏎⇧] │
├─────────────────────────────────────────────────────────────┤
│  이동         2026-0819-a10-adapter  (id 붙여넣기 감지)       │
└─────────────────────────────────────────────────────────────┘
```

**대조 블록이 이 화면의 주인공이다.** 어떤 표현이 어떤 정본으로 정규화됐고 `_vocab.md`의 몇 번째 줄이 근거인지 보여준다. `[복사]`는 정본 좌표를 클립보드에 넣는다 — 사용자는 그걸 문서 작성이나 대화에 그대로 쓰게 되고, 그렇게 어휘가 퍼진다.

**`이동` 줄** — 입력이 `YYYY-MMDD-slug` 형태면 id로 인식해 바로 점프한다. §28.2의 공유 방식이 이걸 전제한다.

### 20.2 대조 실패 — 프로토콜 §9.7의 재료를 모으는 곳

```
├─────────────────────────────────────────────────────────────┤
│  대조 실패   "계획서 변경 승인 흐름" → 정본 좌표를 찾지 못함  │
│              [이 표현을 alias 후보로 기록]                   │
├─────────────────────────────────────────────────────────────┤
│  전문 검색   3건                                             │
│    ● 2026-07-22  결재선 처리 순서 변경                       │
└─────────────────────────────────────────────────────────────┘
```

프로토콜 §9.7 — *"alias는 발견될 때마다 추가한다. 검색이 안 걸리는 사례가 나오면 그때 쓴 표현을 alias에 넣는다."*

**v0.1은 이걸 "개인 로그로 쌓아둔다"에서 멈췄다.** 로컬 앱이면 루프를 닫을 수 있다.

```
설정 > 어휘 기여
  대조 실패한 검색어 14건 · 그중 결과를 열어본 것 6건

  "계획서 변경 승인 흐름"  → 열어본 문서: 2026-0722-approval-order
     추정 좌표: table:tb_approval_line               [채택]

  [_vocab.md 패치 생성]  →  클립보드로 복사할 텍스트를 만든다
```

생성되는 것은 **붙여넣을 수 있는 텍스트**다.

```markdown
## table
- `table:tb_approval_line` — 결재선
  aliases: 결재선테이블, 승인라인, 계획서변경승인흐름   ← 추가 제안
```

**파일을 쓰지 않는다.** 어휘 오너가 확인해 커밋해야 하고, 뷰어가 레포를 건드리면 §31이 무너진다. 클립보드까지가 뷰어의 일이다.

> **대조 실패 로그가 열어본 문서와 짝지어질 때만 가치가 있다.** 검색어만 모으면 무엇의 alias인지 알 수 없다. 그래서 "검색 실패 → 전문 검색 → 문서 열람" 까지 이어진 경우만 후보로 올린다.

### 20.3 검색 순서

v0.1 §8.4를 유지하고 강제 실행 경로를 추가한다.

```
① _vocab.md alias 조회 → 정본 좌표 정규화        [화면에 표시]
② 좌표 필터 → 유효 문서 최신순                   [정정된 문서는 개수만]
③ 좌표 매칭 0건이면 전문 검색으로 폴백           [폴백했음을 표시]
④ 사용자가 ⇧⏎ 로 강제하면 ②와 함께 전문 검색     [둘 다 표시]
```

### 20.4 한글 토크나이징 — 바이그램

v0.1이 *"MiniSearch의 기본 토크나이저는 공백 분리이므로 조사가 붙은 형태를 못 잡는다"* 고 남긴 한계를 처리한다.

```
색인 : "연구계획테이블"  → 연구·구계·계획·획테·테이·이블   (한글 2-gram)
질의 : "연구계획"        → 연구·구계·계획                  → 매칭
질의 : "연구계획테이블을" → …·이블·블을                     → 매칭 (조사 무해)
```

라틴·숫자는 기존 단어 토크나이저를 그대로 쓰고, **한글 구간만** 바이그램으로 쪼갠다. 인덱스가 3~5배 커지지만 수백~수천 건 규모에서 수 MB이므로 무의미하다.

**형태소 분석은 넣지 않는다.** 사전 수십 MB가 붙고 패키징이 무거워진다. 프로토콜 §9.5(2)에서 검색의 1차 경로는 alias 대조이므로 전문 검색은 폴백이고, 폴백에 그만한 비용을 쓰지 않는다.

### 20.5 문서 내 검색

`/`로 현재 문서 내 검색. 매칭 개수와 현재 위치(`3 / 12`)를 표시하고 `⏎`/`⇧⏎`로 이동. 브라우저 기본 찾기와 겹치지만, 본문이 가상 스크롤될 때 기본 찾기는 렌더되지 않은 부분을 못 찾는다.

## 22. 새 소식 · 내 좌표 — 프로토콜 §11.4를 어디까지 완화하나

프로토콜 §11.4의 함정은 *"모르는 사람은 `knowledge-load`를 부를 생각조차 하지 않는다"* 다. v0.1은 §4에서 *"찾아볼 생각을 안 하는 사람에게는 아무 효과가 없다"* 며 이 문제를 뷰어 밖으로 밀었다. 옳지만, **로컬 앱은 조금 더 할 수 있다.**

> **§2.2 ②로 대상이 개발 직군으로 좁혀졌지만 이 절은 그대로 남는다.** 프로토콜 §15의 사고 시나리오 주인공이 *"인터페이스가 바뀐 걸 모르는 배치 담당"* 이다 — 개발자다. §11.4의 함정은 직군 문제가 아니라 **모르는 것은 찾아보지 않는다**는 문제이고, 개발 직군만 남아도 그대로다.

### 22.1 새 소식

```
새 소식                                          마지막 방문 8/28 09:12
────────────────────────────────────────────────────────────────
내 좌표에 걸린 문서   3건
  ● 08-30  배치 재처리 규칙 변경        table:tb_research_plan  확정
  ● 08-29  결재선 순서 조정             table:tb_approval_line  미결
  ● 08-28  계획서 상태값 추가           table:tb_research_plan  확정

그 외                12건  [보기]
────────────────────────────────────────────────────────────────
        [내 좌표 3개 전부 읽음]      [내 좌표 편집]
```

**효과와 한계를 정확히 적는다.**

| | |
|---|---|
| **되는 것** | 앱을 열면, 찾을 생각을 안 했던 사람도 자기 좌표에 걸린 변경을 본다. 프로토콜 §11.4의 절반 |
| **안 되는 것** | 앱을 안 열면 아무 일도 없다. 프로토콜의 본체는 여전히 `CLAUDE.md`의 자동 발동 규칙이다 |

v0.1 §4의 결론(*"뷰어는 보조지 대체가 아니다"*)은 유지된다. **바뀐 것은 보조의 폭이다.**

### 22.2 알림을 넣지 않는 이유

트레이 상주 + 토스트 알림이면 "앱을 안 열면 아무 일도 없다"까지 풀린다. **v1에서 하지 않는다.**

> 알림은 무시되기 시작하면 되돌릴 수 없다. 하루 3건이 뜨면 2주 만에 아무도 안 본다. 그리고 그 시점에는 **"알림이 있으니 안 왔으면 없는 것"** 이라는 더 나쁜 오해가 자리 잡는다 — 프로토콜 §9.6의 조용한 실패가 알림 채널로 옮겨간 형태다.

도입 신호를 정해둔다(프로토콜 §9.8·§14.2와 같은 방식).

| 신호 | 확인 |
|---|---|
| 새 소식 뷰의 주간 열람률이 낮은데 오적용은 계속 발생 | 프로토콜 §17 오적용 로그 + 앱 로컬 통계 |
| 사용자가 먼저 알림을 요구 | 2주 운용 회고 |

### 22.3 내 좌표 설정

좌표 148개 중에서 고르라고 하면 아무도 안 한다.

| 경로 | |
|---|---|
| **자동 제안 (주 경로)** | 열어본 문서 10건의 좌표 빈도 상위 → 새 소식 상단에 `이 좌표들을 내 좌표로 추가할까요? [table:tb_research_plan] [domain:연구관리]` |
| 수동 | 검색으로 추가. 좌표 트리에서 우클릭 → 내 좌표에 추가 |
| 미설정 | 새 소식은 "전체 최근"으로 동작하고 상단에 설정 유도 한 줄 |

**§26.1에서 첫 화면의 좌표 선택 단계를 없앴으므로 자동 제안이 주 경로다.** 좌표 148개 중에서 고르라고 하면 아무도 안 하고, 앱을 열자마자 설정을 요구하면 스킵한 뒤 다시 오지 않는다. 문서 10건을 열어본 뒤 제안하면 사용자는 이미 자기 관심 영역을 행동으로 보여준 상태다 — **묻기 전에 근거를 모은다.**

### 22.4 읽음

로컬 상태이므로 개인 것이다. `state.json`에 `{ id: 읽은시각 }`. **문서가 변경되면 다시 안 읽음으로 돌린다** — 내용이 바뀌었으면 다시 볼 일이다. 무겁게 만들지 않는다: 강조는 좌측 `●` 점 하나.

## 23. 변경 감지와 반영

§2.2 ④로 동기화 UI 전체가 사라졌다. 상단 바에는 **동기화 버튼도, 원격 상태도, 가져오기도 없다.** 대신 남는 것이 더 중요해진다.

### 23.1 뷰어는 최신화하지 않는다 — 그래서 감시가 중요하다

최신화는 사용자가 터미널에서 한다. **뷰어의 일은 그 결과를 즉시, 정확히, 조용히 반영하는 것뿐이다.**

```
사용자: 다른 창에서  git pull
        ↓ (수 초)
뷰어  : 감시가 잡음 → 변경 파일만 재파싱 → 유효성 재계산
        → 목록 갱신 · 상태바 `문서 12건 갱신 · 신규 3건` 5초
```

| 원칙 | |
|---|---|
| **새로고침 버튼을 두지 않는다** | 감시가 살아 있으면 필요 없고, 버튼을 두면 사람들이 그것을 누르는 습관을 만든다. **감시가 끊겼을 때만** 나타난다(§23.3) |
| 최신화 안내를 하지 않는다 | *"원격에 새 문서가 있습니다"* 를 말하려면 `fetch`가 필요하다. 범위 밖이다 |
| 낡음을 추정하지 않는다 | 마지막 커밋이 오래됐다고 *"낡았을 수 있습니다"* 를 띄우지 않는다. **근거 없는 경고는 §13-①의 나이/유효성 혼동과 같은 오류다** |

> **이 절이 초판보다 짧아진 것은 기능이 줄어서가 아니라 책임이 명확해져서다.** 뷰어는 "지금 디스크에 있는 것"의 정확한 상(像)이고, 그 이상을 주장하지 않는다.

### 23.2 변경 반영 (§13-⑥의 구현)

| 변경 | 목록 | 본문 | 알림 |
|---|---|---|---|
| 다른 문서 변경/추가 | 즉시 갱신 | — | 상태바 카운터만 |
| **읽는 중인 문서 변경** | 갱신 | **바꾸지 않는다** + 상단 바 `[다시 읽기]` | — |
| 읽는 중인 문서 삭제 | 목록에서 제거 | 본문 유지 + `이 문서는 삭제되었습니다` | — |
| `_vocab.md` 변경 | 트리 재구성 | 유효성 재계산 | 상태바 `어휘 갱신됨` 3초 |
| **대량 변경 (사용자의 `git pull` 직후)** | 일괄 갱신 | 위 규칙 동일 | `문서 12건 갱신 · 신규 3건` 5초 |

**스크롤 위치·선택·검색어는 어떤 경우에도 유지된다.**

대량 변경은 **디바운스 300ms로 묶는다.** `git pull`이나 브랜치 전환은 수십~수백 파일 이벤트를 한꺼번에 쏟아내는데, 파일마다 재계산하면 화면이 수십 번 깜빡인다. 조용해진 뒤 한 번 계산한다.

### 23.3 스캔 상태 — 상태바가 유일한 신뢰 표시

```
문서 312 · 좌표 148 · ⚠ 검증 3 · 감시 중 · 마지막 스캔 14:22
```

v0.1은 감시가 불가능해 *"마지막 스캔 시각을 항상 표시해 착각을 막는다"* 고 했다. v0.2는 감시하므로 목적이 바뀐다 — **감시가 살아 있다는 증거**다. 그리고 §23.1에서 새로고침 버튼을 없앴으므로 **이 표시가 사용자가 화면을 믿을 수 있는 유일한 근거**가 된다.

| 상태 | 표시 |
|---|---|
| 정상 | `감시 중 · 마지막 스캔 14:22` |
| **감시 끊김** | `⚠ 감시 끊김 [다시 스캔]` — 버튼이 여기서만 나타난다 |
| 스캔 중 | `스캔 중 180/312` |

§2.2 ③-a로 경로가 로컬 NTFS(`C:\project\mdviewer\sample-repo`)임이 확인됐으므로 **정상 운용에서 `감시 끊김`은 나오지 않는다.** 그래도 이 표시와 수동 스캔을 남기는 이유는 둘이다 — chokidar는 핸들 한계·바이러스 검사·짧은 시간의 대량 변경으로 **조용히 죽는 경우가 있고**, 감시가 죽었는데 화면이 그대로면 **사용자는 최신 상태를 보고 있다고 믿는다.** 프로토콜 §9.6의 조용한 실패가 감시 계층에서 재현되는 형태이므로, 감시 생존 여부는 추측이 아니라 표시로 확인돼야 한다.

## 24. 검증 뷰 · 미결 뷰

### 24.1 검증

```
검증                                    [ctx check 재실행]  14:20 실행
────────────────────────────────────────────────────────────────
출처: bin/ctx check --json  ✓ 정본 검증
      (해시 a3f2… · 2026-08-20 승인)
────────────────────────────────────────────────────────────────
⛔ 미등재 좌표                                              2건
   table:tb_plan            2026-0715-plan-fix        [문서 ▸]
        → _vocab.md 후보: table:tb_research_plan (유사)
   screen:계획변경           2026-0801-screen-fix      [문서 ▸]
        → alias 일치: screen:계획서변경               [복사]

⛔ supersedes 대상 없음                                     1건
   2026-0803-x → 2026-0612-y (존재하지 않음)         [문서 ▸]

⚠ INDEX.md 불일치                                          1건
   집계 312건 / INDEX.md 309건 — ctx index 실행 필요
   누락: 2026-0830-…, 2026-0829-…, 2026-0828-…

⚠ 본문 4섹션 누락                                          3건   [뷰어 자체 검사]
   '왜' 없음: 2026-0822-…, 2026-0815-…
   '후속 조치' 없음: 2026-0808-…

○ 좌표 1개짜리 문서                                        7건   [안내]
```

| 규칙 | |
|---|---|
| **출처를 맨 위에 명시** | 본서 §12. `✓ 정본 검증` / `⚠ 내장 검사 — 정본과 다를 수 있음` |
| 심각도 3단 | `⛔` 커밋이 거부될 것 · `⚠` 확인 필요 · `○` 안내 |
| **고치는 방법을 같이 준다** | 미등재 좌표에는 alias 매칭·유사 좌표 후보와 복사 버튼 |
| 뷰어 자체 검사는 꼬리표를 붙인다 | 어느 것이 훅에서 걸릴지 사용자가 구분해야 한다 |
| 0건일 때 | `⛔ 0 · ⚠ 0 · ○ 7` 을 그대로 표시. 빈 화면을 만들지 않는다(§13-②) |

**미등재 좌표에 후보를 제시하는 것이 이 화면의 실질적 가치다.** 프로토콜 §9.6은 커밋 시점에 막는 이유를 *"작성자가 맥락을 쥐고 있어 1초면 고친다"* 로 설명했다. **훅이 안 걸린 PC**(`core.hooksPath` 설정을 안 한 clone, 프로토콜 §11.2)에서는 이 화면이 그 1초를 대신한다.

### 24.2 미결

```
미결                                                    4건
────────────────────────────────────────────────────────────
  47일 대기   2026-07-17  연심회 상태값 확정 대기      kjsa
  22일 대기   2026-08-11  A10 재처리 책임 범위         이OO
   9일 대기   2026-08-24  결재선 예외 처리             kjsa
   3일 대기   2026-08-30  배치 실패 시 알림 대상       박OO
────────────────────────────────────────────────────────────
        평균 20일 · 최장 47일        [내 것만]  [작성자별]
```

프로토콜 §8.3 — *"미결만 필터하면 그것이 결정 목록이다"*. 그래서 필터가 아니라 뷰다.

**대기 일수 정렬이 기본이다.** 최신순으로 정렬하면 가장 오래 방치된 것이 맨 아래로 가는데, 이 화면에서 중요한 건 정확히 그 반대다. 하단 통계는 프로토콜 §17의 성공 지표 *"미결 대기 시간"* 을 그대로 계산한 것이다 — **지표를 사람이 볼 수 있는 곳에 둔다.**

## 25. 키보드와 명령 팔레트

로컬 앱이고 매일 쓰는 도구다. 마우스만으로 쓰는 뷰어는 두 번째 주에 안 열린다.

| 키 | 동작 |
|---|---|
| `⌘K` / `Ctrl+K` | 검색·이동 (§20.1) |
| `⌘⇧P` | 명령 팔레트 (설정·테마·레포 경로 변경·검증 재실행) |
| `⌘1`~`⌘5` | 뷰 전환 |
| `⌘\` / `⌘⇧\` | 사이드바 / 목록 접기 |
| `j` `k` | 목록 이동 · `⏎` 열기 · `x` 읽음 토글 |
| `⌥←` `⌥→` | 방문 이력 뒤로/앞으로 |
| **`⌘.`** | **읽기 모드 전환** (§27.5) |
| `⌘+` · `⌘-` · `⌘0` | 본문 글자 크기 (§27.7) |
| `1`~`4` | 본문 4섹션으로 점프 (§19.1) |
| `/` | 문서 내 검색 |
| `t` | 좌표 타임라인 접기/펼치기 |
| `c` | 좌표 복사 · `⇧C` 요약 복사(§28.1) |
| `r` | 다시 스캔 (감시가 끊긴 경우. §23.3) |
| `?` | 단축키 도움 |

Windows 주 사용 환경이므로 `Ctrl` 기준으로 표기하고 macOS는 `⌘`으로 매핑한다. **방문 이력(`⌥←`)은 브라우저 뒤로가기와 함께 동작해야 한다** — 브라우저에서 열리므로 사용자는 브라우저 뒤로가기를 누른다. 라우팅을 History API로 처리한다.

## 26. 상태 화면

### 26.1 경로 지정 — 화면 한 장

§2.2 ②③으로 마법사가 사라졌다. 레포는 이미 규약대로 존재하므로 **경로를 받고 그것이 맞는지 확인해 보여주는 것이 전부다.** 자동 탐색·clone·2단계 마법사 전부 삭제.

```
┌─ ctx-view ────────────────────────────────────────────────┐
│                                                           │
│   지식 레포 경로                                           │
│   ┌─────────────────────────────────────────┐ ┌────────┐  │
│   │ C:\project\mdviewer\sample-repo         │ │ 찾기…  │  │
│   └─────────────────────────────────────────┘ └────────┘  │
│                                                           │
│   ✓ knowledge/       .md 312건                            │
│   ✓ _vocab.md        좌표 148개 · 타입 5종                 │
│   ⚠ INDEX.md         309행 — 실제 집계와 3건 차이          │
│   ○ bin/ctx          없음 — 검증은 뷰어 내장 검사로        │
│                                                           │
│                                              [열기]       │
└───────────────────────────────────────────────────────────┘
```

**세 가지 기호를 쓴다** — `✓` 규약대로 있음 / `⚠` 있지만 문제 있음 / `○` 없음(선택 항목). 위 예는 `INDEX.md`가 밀린 상태와 `bin/ctx`가 없어 내장 검사로 폴백하는 상태(§12)를 함께 보여준다. **둘 다 열기를 막지 않는다.** `.git` 항목은 없다 — §11에 따라 뷰어가 git을 보지 않는다.

| 규칙 | |
|---|---|
| **입력은 붙여넣기 우선** | 경로 텍스트 입력이 1급. `찾기…`(OS 폴더 대화상자)는 보조. 개발 직군은 경로를 이미 알고 있다 |
| **구조 검증을 즉석에서 보여준다** | 입력하는 즉시 위 5줄을 채운다. **경로가 맞는지는 폴더 이름이 아니라 이 5줄로 판단된다** |
| 규약과 다르면 열기를 막지 않는다 | `knowledge/`가 없으면 `⚠` 로 표시하고 **그래도 열 수 있게 한다.** 프로토콜 도입 초기에는 규약이 덜 갖춰져 있다(§26.2) |
| CLI로 건너뛴다 | `--repo <경로>` 면 이 화면이 아예 안 뜬다(§5.2) |
| 재지정 | 설정 또는 `⌘⇧P` → `레포 경로 변경`. 같은 화면을 다시 쓴다 |
| 총 화면 수 | **1장.** 내 좌표 선택은 §22.3의 자동 제안으로 넘긴다 |

**내 좌표 선택을 첫 화면에서 뺀 이유** — 초판은 마법사 2장 중 한 장을 여기에 썼다. 개발 직군은 앱을 열자마자 문서를 보려 하고, 설정 단계가 하나 더 있으면 그것을 스킵한 뒤 다시 오지 않는다. §22.3의 **"열어본 문서 10건의 좌표 빈도"** 자동 제안이 더 정확하고 마찰이 없다.

### 26.2 나머지 상태

| 상태 | 화면 |
|---|---|
| 스캔 중 (최초) | 진행률 + `312건 중 180건` · 완료된 문서는 먼저 목록에 뜬다 |
| 문서 0건 | `knowledge/ 에 .md 파일이 없습니다` + 인식하는 구조(§10.4) 안내 |
| `_vocab.md` 없음 | 트리 자리에 `_vocab.md가 없어 좌표 트리를 만들 수 없습니다. 최근 뷰로 보세요` + 최근 뷰 링크. **앱은 계속 동작한다** |
| 레포 경로 사라짐 | `경로를 찾을 수 없습니다: <경로>` + 다시 선택 (네트워크 드라이브 미연결 시 발생) |
| 프론트매터 파싱 실패 | 목록에 `⛔ 프론트매터 오류` 로 남기고 **본문은 원문으로 보여준다.** 목록에서 감추지 않는다(§13-③) |
| 문서 선택 안 함 | 본문 자리에 좌표 요약 카드 (문서 수·최신·미결·후속이 있는 좌표) |
| 검색 결과 0건 | `0건` + 대조 결과 + `전문 검색 강제 실행` + 최근 검색어 |
| 포트 확보 실패 | 콘솔·트레이 알림으로 안내 후 종료 |

**`_vocab.md`가 없어도 죽지 않는 것이 중요하다.** 프로토콜 도입 초기(프로토콜 §17 1단계 이전)나 다른 레포를 잘못 지정한 경우에 반드시 마주친다.

## 27. 읽기 ★ — 조판 · 렌더링 · 읽기 경험

**§13-⓿의 본체가 이 절이다.** 초판은 이 절을 렌더링 충실도만 다뤘는데, 그것은 "깨지지 않는가"이고 읽기는 "끝까지 읽히는가"다. 후자가 빠져 있었다.

지식 단위는 요약이라 짧지만(프로토콜 §8.5 *"관련성 판단이 가능한 만큼"*), **첨부는 인터페이스 명세·스키마 원문이고 길다.** 프로토콜 §8.5의 3계층 중 3계층에서 실제로 긴 읽기가 일어난다. 그리고 `_vocab.md`·`TEMPLATE.md`·`CLAUDE.md`도 이 뷰어로 읽는다. **긴 문서를 못 읽는 뷰어는 뷰어가 아니다.**

v0.1 §11은 3단계 검증을 *"설계서 v1.1 원문이 제대로 렌더되는가"* 로 뒀다. 옳은 기준이므로 유지하고, **무엇을 봐야 통과인지**를 27.1~27.4에서 확정한 뒤, 27.5~27.8에서 읽기 경험을 규정한다.

### 27.1 합격 기준 (설계서 v1.1 원문 기준)

| 요소 | 기준 |
|---|---|
| GFM 표 | 헤더 정렬 · 셀 내 인라인 코드 · 빈 셀 · `:--:` 정렬 지정 |
| **인용 안의 표** | 인용 스타일과 표 스타일이 겹쳐도 깨지지 않는다 |
| **ASCII 다이어그램** | 절대 줄바꿈되지 않고 가로 스크롤 (§27.2) |
| YAML 코드펜스 | 하이라이팅 · 들여쓰기 보존 |
| 중첩 목록 | 3단 · 목록 안의 표 · 목록 안의 코드펜스 |
| 각주 화살표 `→` `↓` `↙` | 한글 사이에서 폭이 튀지 않는다 |
| 한글·영문·숫자 혼용 | 자간·행간이 일관 |
| `**굵게**` 안의 인라인 코드 | 겹침 처리 |
| 제목 앵커 | `#` 링크 · 클릭 복사 |
| 문서 간 상대 링크 | `[…](2026-0819-a10-adapter.md)` → 뷰어 내부 이동으로 가로채기 |

**문서 간 상대 링크 가로채기**를 목록에 넣은 이유 — 지식 단위끼리 서로 참조하기 시작하면 링크가 브라우저 파일 다운로드로 흘러간다. 뷰어 내부 이동으로 바꿔야 한다. 레포 밖을 가리키면 §13-③에 따라 표시만 한다.

### 27.2 ASCII 다이어그램 — 정직하게 말해둘 한계

프로토콜 설계서와 본서의 다이어그램은 **박스 문자(`─│┌└├▾`)와 한글을 섞는다.** 일반 등폭 폰트에서 한글은 라틴 문자의 정확히 2배 폭이 아니므로 **정렬이 어긋난다.** 브라우저·폰트를 바꿔도 근본적으로 해결되지 않는다.

| 대응 | |
|---|---|
| `D2Coding` · `Sarasa Mono K` 우선 | 한글이 라틴 2배 폭으로 설계된 폰트다. 있으면 정렬이 맞는다 |
| 없으면 `Cascadia Mono` → `Consolas` | 라틴·박스 문자는 정확하고 한글 정렬만 어긋난다 |
| **폰트를 번들하지 않는다** | 실행 파일에 수 MB를 더할 만한 가치가 없다. 설정에 *"다이어그램 정렬을 위해 D2Coding 설치 권장"* 한 줄 |
| 줄바꿈 금지 | `white-space: pre; overflow-x: auto`. **다이어그램은 줄바꿈되는 순간 완전히 무의미해진다** |

### 27.3 넓은 요소

본문 읽기 폭은 760px이지만 표·코드블록·다이어그램은 그것을 넘는다.

```
        ┌──── 본문 760px ────┐
        │ 산문은 여기까지     │
   ┌────┴─────────────────────┴────┐
   │ 표·코드블록은 창 폭까지 확장    │   ← 좌우로 삐져나온다
   └────────────────────────────────┘
```

- 표: 자체 `overflow-x: auto` 컨테이너 + **첫 열 sticky**. 프로토콜 설계서의 표는 첫 열이 항목명이라 이게 있으면 훑기가 된다
- 코드블록: 가로 스크롤 + 우상단 `[복사]`
- **본문(`body`)은 절대 가로 스크롤되지 않는다.** 넓은 요소만 각자 스크롤한다

### 27.4 목차

문서 우측(≥1400px)에 `h2`/`h3` 목차를 띄운다. 4섹션 레일(§19.1)과 역할이 다르다 — 레일은 프로토콜이 고정한 4섹션, 목차는 본문이 실제로 가진 제목 구조(특히 첨부 문서와 `TEMPLATE.md` 같은 비지식단위 문서). 1400px 미만에서는 목차를 접고 레일만 남긴다.

**목차에 읽은 위치를 표시한다.** 현재 섹션 강조 + 지나온 섹션은 옅은 마커. 1,500행짜리 문서에서 어디까지 읽었는지가 목차에 없으면 목차의 절반이 쓸모없다.

### 27.5 읽기 모드 — 판단이 끝나면 도구가 사라진다

3분할은 **찾을 때**의 레이아웃이다. 읽을 때는 방해가 된다.

```
 [찾기]  사이드바 264 │ 목록 360 │ 본문           ⌘. ──▶  [읽기]  ◀── 본문만, 가운데 ──▶
```

| | |
|---|---|
| **`⌘.` 하나로 전환** | 사이드바·목록·상태바를 접고 본문을 가운데 정렬. 다시 누르면 복귀 |
| 읽기 모드에서 남는 것 | 4섹션 레일(§19.1) · 목차(§27.4) · ⛔정정됨 고정 바(§17.6) · `⌘K`. **그 넷만** |
| 검색·이동으로 문서를 열면 | **패널을 강제로 펼치지 않는다.** 읽기 모드였으면 읽기 모드를 유지한다 |
| 상태 저장 | 모드는 기억된다. 읽기 모드로 쓰는 사람은 계속 그렇게 쓴다 |

**`⌘1`/`⌘2`(개별 접기)를 그대로 두고 `⌘.`을 추가하는 이유** — 개별 접기는 두 번 눌러야 하고, 되돌릴 때 어느 폭이었는지 기억해야 한다. **읽으려고 두 번 누르게 만들면 사람들은 안 접고 좁은 본문으로 읽는다.**

### 27.6 읽기 위치 — 긴 문서는 한 번에 안 읽힌다

| 규칙 | |
|---|---|
| **문서별 스크롤 위치를 저장한다** | `state.json`. 다시 열면 그 자리로. 세션이 바뀌어도 유지 |
| 복원 방식 | 위치로 **점프**하고 상단에 `읽던 위치입니다 [처음으로]` 3초. 조용히 중간에 떨어뜨리면 사용자가 길을 잃는다 |
| 문서가 변경되면 | 위치를 버린다. 오프셋이 의미를 잃었다(§23.2의 `[다시 읽기]`와 같은 판단) |
| **읽기 진행률** | 본문 우측 얇은 바 또는 목차 상단에 `62%`. 긴 첨부에서 남은 양을 알려준다 |
| 저장하지 않는 것 | **읽기 시간·체류 시간 통계.** 로컬이라도 만들지 않는다. 쓸 데가 없고, 있으면 언젠가 지표로 쓰인다 |

### 27.7 본문 폭·글자 크기 — 읽는 사람이 정한다

§16.2의 15px/1.75/760px은 **기본값이고 강제가 아니다.** 모니터·시력·본문 성격이 사람마다 다르다.

| 조절 | 값 | 키 |
|---|---|---|
| 글자 크기 | 13 · 14 · **15** · 16 · 18px (행간은 비례) | `⌘+` / `⌘-` / `⌘0` |
| 본문 폭 | 좁게 620 · **보통 760** · 넓게 900 · 창 폭 | 설정 · `⌘⇧P` |
| 밀도 | §15.4 (목록에만 적용. 본문은 별도) | 설정 |

**"창 폭"을 선택지에 두는 이유** — 표가 많은 문서는 산문 기준 측정폭이 오히려 방해다. 프로토콜 설계서를 읽어보면 실제로 그렇다. **다만 기본값으로 두지 않는다** — 산문 130자 줄은 못 읽는다(§15.2).

브라우저 자체 확대(`Ctrl+휠`)와 충돌하지 않게 **본문 크기는 `rem`이 아니라 별도 변수로** 둔다. 브라우저 확대는 UI 전체를, 이 설정은 본문만 키운다.

### 27.8 본문에서 이어 읽기 — 좌표가 사람에게도 링크가 된다

**좌표계의 이득을 검색에만 쓰고 있었다.** 본문 산문 안의 좌표도 이동 지점이 될 수 있다.

```
## 누구에게 영향

야간 집계 배치(module:plan-batch)는 상태값 매핑을 다시 봐야 한다.
                ▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔  ← 클릭 → 이 좌표의 문서 5건
연구계획테이블 의 status 컬럼은 그대로다.
▔▔▔▔▔▔▔▔▔▔▔▔  ← alias 일치. 옅은 밑줄 → table:tb_research_plan
```

| 규칙 | 근거 |
|---|---|
| `타입:값` 형태는 **좌표 링크로** | `_vocab.md`에 있으면 링크, 없으면 `⚠` 표시(§13-③) |
| **alias 일치는 옅은 밑줄만** | 산문을 링크로 도배하면 읽기가 망가진다. 정본 좌표는 링크, alias는 힌트 |
| 오탐 시 끌 수 있다 | 설정에 `본문 좌표 링크` 토글. **읽기를 방해하면 기능이라도 뺀다**(§13-⓿) |
| 문서 하단 **백링크** | `이 문서를 참조하는 문서 2건` — `supersedes` 역참조 + 본문에서 이 id를 언급한 문서 |
| 문서 하단 **이어 읽기** | `table:tb_research_plan 의 다음 문서 → 2026-0828 계획서 상태값 추가` |

**백링크와 이어 읽기가 §18의 타임라인과 겹치지 않는다.** 타임라인은 좌표 이력을 **훑는** 패널이고, 이 둘은 본문 끝에서 **다음 한 편으로 넘어가는** 장치다. 읽기의 연속성은 목록으로 돌아가지 않고 이어지는 것이다.

> **여기서 뷰어가 벡터 RAG와 갈라진다.** 청킹된 데이터에는 "다음 문서"가 없다 — 유사도 순위만 있고 문서의 경계와 관계가 없다. **좌표와 `supersedes`가 있으므로 사람이 읽는 순서를 만들 수 있다.** 프로토콜 §13.5가 좌표의 성질로 든 것이 화면에서는 이 형태로 나타난다.

## 28. 복사 · 인쇄 · 공유

### 28.1 요약 복사 — 프로토콜과 같은 형식으로

`⇧C`. 클립보드에 들어가는 것.

```
2026-0819-a10-adapter · A10 연계 어댑터 인터페이스 개편 — 계획서 상태 동기화 추가
[유효] ⛔ 2026-0828-plan-status 로 대체됨
[나이] 결정 2026-08-19 · 3주 전 · 기록은 결정 4일 후
[최신] table:tb_research_plan 에 후속 2건 (2026-0828-plan-status, 2026-0830-batch-fix)
좌표: table:tb_research_plan, api:/adapter/a10/plan-sync, module:acl-adapter, domain:연구관리
```

**프로토콜 §12.3이 AI 세션에 주입하는 형식과 같다.** 사람이 메신저에 붙여넣어도 되고, 다른 AI 세션에 붙여넣어도 프로토콜이 기대하는 신호가 그대로 실린다. 형식을 새로 만들지 않는다.

복사 메뉴: 좌표(`c`) · 요약(`⇧C`) · id · 상대 경로 · 절대 경로 · 본문 마크다운 원문 · 렌더된 서식(메일용).

### 28.2 공유 — 링크를 만들지 않는다

로컬 앱의 URL은 `http://127.0.0.1:7373/...`이다. **다른 사람의 PC에서 열리지 않고, 포트가 바뀌면 자기 PC에서도 안 열린다.** 딥링크를 억지로 만들면 안 되는 링크를 주고받게 된다.

| 상황 | 방식 |
|---|---|
| 사람에게 문서 알려주기 | **id 복사** → 메신저에 붙여넣기 → 받은 사람이 `⌘K`에 붙여넣으면 열린다(§20.1의 `이동` 줄) |
| 사내 GitHub/GitLab이 있으면 | `remote`에서 웹 URL을 합성해 `[원격 링크 복사]` 제공 |
| 자기 PC용 북마크 | 기본 포트 7373이 유지되는 동안 동작. 보장하지 않는다 |

**커스텀 URL 스킴(`ctxview://`)을 등록하지 않는다.** 레지스트리 쓰기가 필요하고(관리자 권한·EDR 경보), §5의 포터블 원칙이 깨진다. id 붙여넣기로 충분하다.

### 28.3 인쇄

회의에 종이로 들고 가는 일은 실제로 있다. 인쇄 스타일시트는 저비용이다.

- 사이드바·목록·레일 숨김. 본문만
- **유효성 블록은 인쇄한다.** `⛔ 정정됨`이 안 찍히면 종이가 사람을 속인다
- 표는 접지 않고 폭을 줄여 전부 표시. 코드블록은 줄바꿈 허용(화면 규칙과 반대. 종이는 스크롤이 없다)
- 링크는 각주로 URL 표기
- 머리말에 `문서 id · 결정일 · 인쇄일`. **인쇄일이 있어야 종이의 나이를 안다**

| 항목 | 예산 | 초과 시 |
|---|---|---|
| 실행 → 첫 화면 | 1.5s | 스캔을 비동기로 더 밀고 목록만 먼저 |
| 최초 전량 스캔 | 1.5s | 병렬 읽기 |

# 제4부 — 실행

## 30. 이 뷰어가 여전히 풀지 못하는 것

v0.1 §4의 정직한 단락을 유지하고 갱신한다.

| | v0.1 | v0.2 |
|---|---|---|
| **찾아볼 생각을 안 하는 사람** | 효과 없음 | **부분 완화** — 앱을 열면 새 소식이 보인다. 안 열면 그대로(§22.1) |
| 프로토콜의 본체 | `CLAUDE.md` 자동 발동 규칙 | **동일.** 뷰어는 보조지 대체가 아니다 |
| 작성 마찰 (프로토콜 §16의 급소) | 무관 | **무관.** 작성은 `knowledge-share`의 일이다 |
| 좌표가 안 붙은 문서 | 못 찾음 | 못 찾음. 검증 뷰가 **사후에** 알려줄 뿐 |
| 문서 자체가 없는 것 | 알 수 없음 | 알 수 없음 |
| **본문이 부실한 것** ("왜"가 없다) | 알 수 없음 | **표시만 한다**(§19.2). 고칠 수는 없다 |
| **레포가 낡은 것** | 알 수 없음 | **알 수 없음** ← §2.2 ④. 초판은 `fetch`로 알 수 있었다 |

마지막 행이 §2.2 ④의 대가다. **뷰어는 "지금 디스크에 있는 것"만 정확히 보여주고, 그것이 원격보다 낡았는지는 모른다.** 그래서 근거 없는 추정 경고를 하지 않기로 했다(§23.1). 사용자가 `git pull`을 잊으면 뷰어는 낡은 문서를 자신 있게 보여준다 — **프로토콜 §12가 경계한 실패 양상과 같은 구조이고, 이 판에서는 그것을 사용자의 책임으로 남긴다.**

> **"뷰어를 잘 만들면 프로토콜이 완성된다"는 오해를 계속 경계해야 한다.** v0.2는 v0.1보다 화면이 훨씬 두꺼워졌고(§13~29), 그래서 투자가 이쪽으로 쏠릴 위험도 커졌다. **프로토콜 §16이 지목한 급소는 여전히 "작성이 5분 안에 끝나는가"이고, 뷰어는 그 숫자에 아무 영향을 주지 않는다.**

## 31. 비목표

v0.1 §10을 유지하고, **로컬이 되면서 새로 생긴 유혹을 추가한다.** 파일시스템이 열렸으므로 "할 수 있다"가 늘었고, 그래서 이 절이 v0.1보다 중요해졌다.

| 안 하는 것 | 이유 |
|---|---|
| **문서 편집·생성** | 작성은 `knowledge-share`의 일이다. 뷰어가 하면 좌표 대조·훅 검증을 우회하는 경로가 생기고 프로토콜 §11.2의 *"skill은 편의, hook은 보증"* 이 무너진다. **이제 기술적으로 가능해졌지만 하지 않는다** |
| **레포 최신화 전부** — `fetch` · `pull` · `clone` | **§2.2 ④.** git 연산은 `log` 읽기만 남는다(§11.1). 최신화는 사용자가 터미널에서 한다 |
| **낡음 추정 경고** | `fetch` 없이 "낡았을 수 있습니다"를 띄우는 것은 근거 없는 경고다. §13-① 나이/유효성 혼동과 같은 오류(§23.1) |
| **`git commit` / `push`** | 프로토콜 §11.2의 보증 체계를 우회하는 경로를 만들지 않는다. 경계선: **레포에 커밋될 수 있는 파일을 하나도 만들지 않는다** |
| **`_vocab.md` 수정** | 어휘는 오너가 커밋한다. 뷰어는 §20.2의 붙여넣을 텍스트까지만 만든다 |
| **여러 레포 동시 연결** | 프로토콜 §10.2 전제. 레포 전환은 되지만 동시 연결은 아니다 |
| **AI 질의응답** | `knowledge-load`의 일이다. 검증되지 않은 두 번째 검색 경로를 만드는 것이 더 나쁘다 |
| **본문 요약 · 재구성 · AI TL;DR** | **§13-⓿.** 프로토콜 §8.4는 본문을 *"일부러 구조화하지 않는다"* 고 했다. *"왜"에 담기는 제약과 트레이드오프는 필드로 쪼개는 순간 죽는다* — 요약도 같은 손실이다. **뷰어는 본문을 있는 그대로 읽히게만 한다** |
| **본문에서 필드 추출** | 위와 같은 이유. 프론트매터가 기계용, 본문이 사람용이라는 분리를 뷰어가 흐리면 안 된다 |

## 33. 도입 순서 — 프로토콜보다 뒤. 이 판정은 변하지 않는다

v0.1 §12는 프로토콜 §17의 7단계(2주 운용) 뒤에 뷰어를 두라고 했다. **v0.2에서 능력이 늘었으니 먼저 만들자는 논리가 나올 수 있는데, 반대다.**

```
프로토콜 §17 1~6단계     (기반 + skill)
        ↓
프로토콜 §17 7단계        (2주 운용)  ← 여기서 화면 설계가 결정된다
        ↓
뷰어 1~11단계             (착수 관문 없음. §2.2 ①)
```

v0.2는 화면에 대한 판단을 v0.1보다 훨씬 많이 담고 있다. **그 판단이 틀렸는지는 2주 운용에서만 드러난다.** 예를 들어 §22의 새 소식·내 좌표는 "사람들이 자기 좌표를 인지하고 있다"를 가정하는데, 이 가정이 틀리면 그 화면은 안 쓰인다.

2주 운용에서 확인할 것을 §22·§24와 연결해 적어둔다.

| 관측되면 | 설계 변경 |
|---|---|
| 좌표보다 사람으로 찾는 일이 많다 | 작성자 필터를 목록 1급으로 (v0.1과 동일) |
| `status: 미결` 추적이 주 용도다 | 미결을 첫 화면으로 (§14의 첫 화면 규칙 변경) |
| 첨부를 여는 빈도가 높다 | §19.4 인라인 펼치기를 기본값으로 |
| 좌표 트리를 안 쓰고 검색만 쓴다 | 트리를 접고 `⌘K`를 첫 화면으로 |
| **자기 좌표를 지목하지 못한다** | **§22를 접고 "최근" 중심으로.** 새 소식의 전제가 무너진 것 |
| **최신성 경고를 무시한다** | §18 타임라인을 접기 기본으로. 숫자만 남긴다 |
| 오적용 원인이 "문서 전체가 정정돼서" 로 분류됨 | 프로토콜 §9.8 도입 → §17.2 부분 정정 상태 활성화 |

## 34. 프로토콜 측에 필요한 것

뷰어 때문에 프로토콜·`bin/ctx`에 필요한 변경. **전부 작고, 뷰어 없이도 쓸모가 있는 것만 골랐다.**

| # | 요청 | 규모 | 뷰어 없이도 유용한가 |
|---|---|---|---|
| 1 | **`ctx check --json`** | 10~20줄 | O. CI 연동에 그대로 쓴다 |
| 2 | `ctx check`가 `supersedes` **순환**을 검출 | 5줄 | O. 순환은 로드 로직도 망가뜨린다 (§17.2) |
| 3 | `ctx check`가 `id` ≠ 파일명을 검출 | 3줄 | O. 프로토콜 §8.2가 일치를 요구한다 |
| 4 | `_vocab.md`의 `deprecated` 후속 좌표 표기를 기계 판독 가능하게 고정 | 형식 확정 | O. `ctx check`가 deprecated 좌표 사용을 경고할 수 있다 |
| 5 | (선택) 레포 루트 `.ctx-view.json` — `minVersion`·표시 이름 | 파일 1개 | X. 뷰어 전용 |
| **6** | **`ctx index`가 `INDEX.md`에 기록 시각 칼럼 추가** | 표 칼럼 1개 | **O. 프로토콜 §12.1이 정의한 신호인데 지금 아무도 안 보고 있다** |

6번을 부연한다. **프로토콜 §12.1은 결정 시각과 기록 시각 두 축을 정의했지만, 기록 시각을 실제로 읽어 쓰는 곳이 프로토콜 어디에도 없다.** `knowledge-load`(§11.3)는 `INDEX.md`를 보는데 거기에 커밋 시각이 없고, §12.3의 주입 신호 예시에는 *"기록은 결정 4일 후"* 가 적혀 있다. **주입하라고 정의된 값의 출처가 비어 있는 상태다.**

이걸 뷰어가 `git log`로 메우려던 것이 §2.3에서 잘라낸 판단이었다. 소유자는 `ctx index`다 — pre-commit 훅이 커밋 시점에 돌고 있어 커밋 시각을 공짜로 알고, 한 번 쓰면 `INDEX.md`에 고정된다.

```markdown
| id | date | recorded | title | status | touches |
|----|------|----------|-------|--------|---------|
| 2026-0819-a10-adapter | 2026-08-19 | 2026-08-23 | A10 연계... | 확정 | ... |
```

**얻는 쪽이 뷰어보다 `knowledge-load`다.** 뷰어는 이 칼럼이 생기면 §17.3의 빈 칸을 채우고, 없으면 그냥 안 보여준다. 반면 `knowledge-load`는 §12.3이 주입하라고 지정한 값을 지금 채울 수 없다. **뷰어 요청 목록에 넣지만 우선순위는 프로토콜 쪽 문제다.**

4번도 부연한다. 현재 `_vocab.md`의 표기는 이렇다.

```
- `table:tb_plan_history` — 계획서 변경 이력
  deprecated: 2026-06-01 → table:tb_research_plan_hist 로 통합
```

`→ ... 로 통합`은 산문이라 후속 좌표를 안정적으로 뽑을 수 없다. `deprecated: 2026-06-01` / `superseded-by: table:tb_research_plan_hist` / `note: 통합` 처럼 쪼개거나, 화살표 뒤 첫 번째 `타입:값` 토큰을 후속 좌표로 본다는 규칙을 명문화하면 된다. **뷰어는 후자로 파싱하고, 실패하면 산문을 그대로 보여준다**(§13-③).

| GET | `/api/docs` | 전체 목록 (프론트매터 + 유효성 + 최신성 + 읽음) |
| GET | `/api/docs/:id` | 원문 텍스트 + 섹션 오프셋 + 첨부 메타 |
| GET | `/api/vocab` | 좌표·alias·deprecated 트리 |
| GET | `/api/search?q=` | 대조 결과 + 좌표 매칭 + 전문 검색 (개수 항상 포함) |
| GET | `/api/check` | `ctx check --json` 위임 결과 또는 내장 검사 (**출처 필드 포함**) |
| GET | `/api/file?path=` | 첨부·이미지 (경로 봉인 통과분만) |
| GET | `/api/events` | SSE — 파일 변경·스캔 진행 |
| POST | `/api/rescan` | 수동 전량 스캔 (감시 끊김 시에만 UI에 노출. §23.3) |
| POST | `/api/state/read` · `/api/state/coords` · `/api/config` | **앱 상태만.** 레포를 건드리지 않는다 |
| POST | `/api/open` | OS 기본앱으로 원본 열기 (§7.2 제한 적용) |
| POST | `/api/heartbeat` | 유휴 종료 방지 (§5.2 ⑥) |
| POST | `/api/quit` | 명시적 종료 |

모든 요청에 `Authorization: Bearer <세션 토큰>` + `Host` 화이트리스트 검증(§7.2).

**`/api/git/*` 는 존재하지 않는다.** §11에 따라 뷰어는 git을 한 줄도 실행하지 않으므로 git 관련 엔드포인트가 하나도 없다. §2.2 ④(최신화)와 §2.3(커밋 시각) 둘 다 여기에 표면을 남기지 않는다.

## 부록 F. 이 개정에서 잘라낸 것 — 되살릴 자리

§2.2로 삭제된 항목과, 전제가 다시 넓어질 때 어디를 되살려야 하는지.

| 잘라낸 것 | 근거 | 되살릴 조건 | 되살릴 위치 | 비용 |
|---|---|---|---|---|
| **기록 시각 표시** | §2.3 | **`ctx index`가 `INDEX.md`에 칼럼을 넣으면**(§34-6) — git 없이 데이터로 온다 | §17.3 2단 | **2시간** |
| — | — | **§27(읽기)·§19는 이 표에 없다.** 잘라낼 수 있는 항목이 아니다(§13-⓿) | — | — |
| ~~`git log` 로 커밋 시각 직접 읽기~~ | §2.3 | **되살리지 않는다.** 위 경로가 정답이다 | — | — |
| `git fetch` · 원격 상태 표시 | §2.2 ④ | *"pull 잊어서 낡은 문서 봤다"* 사례가 실제로 나옴 (§35) | §23.1 상단 바 · §11 표 | 반일 |
| `git pull --ff-only` 버튼 | §2.2 ④ | 위와 동일 + 사용자가 요구 | 같은 자리 | 반일 |
| `git clone` 마법사 | §2.2 ② | 비개발 직군이 대상에 들어옴 | §26.1 | 1일 |
| isomorphic-git | §2.2 ② | git 미설치 PC가 대상에 들어옴 | §9 · §11 | 1일 (+PAT·DPAPI) |
| 레포 자동 탐색 | §2.2 ③ | 경로가 사람마다 달라 문의가 반복됨 | §26.1 | 2시간 |
| MSI 배포 | §2.2 ② | 조직 배포 채널로 표준 앱 등록 | §5.1 | 반일 |
| MSI·사내 서버 등 추가 배포 경로 | §2.2 ① | exe·npx 둘 다 막히는 PC 등장 | §5.1 · §5.3 | 상황별 |

**하나만 되살아나도 §31의 경계선은 다시 검토해야 한다.** 특히 `pull`이 들어오면 "레포에 커밋될 수 있는 파일을 만들지 않는다"는 선은 유지되지만 **작업 트리를 바꾸는 연산**이 추가되므로, §23.1의 자동/수동 구분과 로컬 변경 감지가 함께 돌아와야 한다. 반쪽만 되살리면 사용자가 편집 중인 파일과 충돌한다.
