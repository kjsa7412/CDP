# 시나리오 — 지식공유문서 만들기 (GDI 레포)

`C:\cdp` 에서 **작업 기록을 남기는 절차 전체**를 시험한다.

시험할 것은 "잘 써지나" 가 아니다. **막아야 할 때 막나** 다. 통과만 시키는
도구는 없느니만 못하다 — 사람이 도구를 믿고 확인을 그만두기 때문이다.

  S1  정상 경로            기록 + 파생 + 커밋
  S2  파생 누락            커밋이 막혀야 한다
  S3  미등재 좌표          커밋이 막혀야 한다 (그리고 두 번 막힌다)
  S4  아젠다               기록이 만들어지면 안 된다
  S5  오기재 정정          기록을 고치지 않고 새로 쓴다
  S6  진행중               유일하게 뜻이 있는 status
  S7  INDEX · 뷰어         결과가 화면에 나타나나

---

## 0. 준비 — 브랜치에서 한다

`C:\cdp` 는 **실제 지식 레포**다. 시험용 기록이 본선에 남으면 그때부터
거짓 지식이다. 브랜치를 파고, 끝나면 통째로 버린다.

```
cd C:\cdp
git switch -c test/지식공유문서-시나리오
git log --oneline -1        ← 되돌아올 자리를 눈으로 확인해 둔다
```

훅이 걸려 있는지도 지금 본다. **이것이 없으면 S2·S3 는 전부 통과해 버리고,
시험은 아무것도 증명하지 못한다.**

```
git config core.hooksPath        → .githooks
bin/ctx check                    → ctx check: 이상 없음
bin/ctx version                  → tools/cdp.exe 와 같은 날짜
```

---

## S1 — 정상 경로

### 시키는 말

> 출장복명작성(EXD020)에 **차량 미이용자용 사진 첨부 영역**을 넣어 줘.
> 그리고 입력 영역을 화면 맨 위로 올린다 — 출장자 본인이 아니어도 놓치지
> 않게.

### 일어나야 하는 것

`cdp-work` 가 세 단계로 돈다.

| | | |
|---|---|---|
| ① 검토 | `screen:EXD020` 을 뽑는다 | 레포 본문은 아직 안 읽는다 |
| ② 주입 | `cdp-load screen:EXD020` | 화면설계서 그 섹션을 읽어 온다 |
| ③ 수행 | 요청을 처리한다 | |

**②에서 이 문장이 나와야 한다** —

> 차를 안 가져간 사람이 사진을 붙이려는데 **붙일 곳이 없어서** 복명만 하고
> 담당자에게 전화했다

이미 그 이유로 입력 영역을 만든 화면이다. 그 맥락이 안 나오면 `cdp-load` 가
섹션을 못 찾은 것이고, 그러면 **이미 있는 결정을 모르는 채로 작업한다.**
시나리오에서 EXD020 을 고른 이유가 그것이다 — 맥락이 있는 자리다.

그 다음 `cdp-save` 가 **둘을 함께** 만든다.

```
work/2026-MMDD-출장복명-사진첨부.md        새로 쓴다
docs/화면설계서.md  ## EXD020            갱신 + applied 교체
```

### 확인

```
bin/ctx where screen:EXD020
    → docs/화면설계서.md  ## EXD020  ·  반영 2026-MMDD-출장복명-사진첨부

bin/ctx check                → 이상 없음
git add -A && git commit     → 통과
```

`<!-- applied: … -->` 가 **새 기록 id 로 바뀌어 있어야 한다.** 안 바뀌었으면
섹션 본문만 손대고 표시를 안 남긴 것이고, 그러면 다음 사람이 이 섹션이
언제 것인지 알 수 없다.

## S2 — 파생 누락 (**막혀야 한다**)

### 시키는 말

> 방금 것 말고, EXD020 사진 첨부 용량 제한을 20MB 로 정했다. 기록만 남겨 줘.
> 화면설계서는 나중에 정리할게.

### 일어나야 하는 것

작업 기록만 만들고 커밋을 시도한다.

```
git add -A && git commit -m "사진 첨부 용량"
```

**exit 1 로 막혀야 한다.**

```
[오류] 관리 문서 파생 누락 — 지식공유문서를 남기면 파생 갱신은 필수입니다
   screen:EXD020  docs/화면설계서.md ## EXD020

ctx check: 오류 1건. 커밋할 수 없습니다.
[pre-commit] 커밋을 중단했습니다.
```

### 왜 이것이 가장 중요한가

**"나중에 정리" 는 CDP 에 없는 상태다.** 밀림·미작성은 상태가 아니라 오류다.
여기서 커밋이 통과하면 나머지 시험은 전부 의미가 없다 — 관리 문서가 언제
낡았는지 아무도 모르게 되고, 그 순간 이 레포는 그냥 파일 더미다.

### 회복

```
cdp-managed          ← 남은 섹션을 채운다
bin/ctx derive       → 목록이 비어야 한다
git commit           → 통과
```

`--no-verify` 로 넘기는 것을 **시험 삼아서도 하지 마라.** 한 번 통하는 것을
보면 다음에 급할 때 쓴다.

---

## S3 — 미등재 좌표 (**두 번 막힌다**)

### 시키는 말

> 사진은 새 테이블 `rp_trip_photo_list` 에 넣기로 했다. 출장 건별로 여러 장,
> 파일키와 순번을 갖는다. 기록해 줘.

### 일어나야 하는 것 — 첫 번째 차단

`touches` 에 `table:rp_trip_photo_list` 가 들어가는데 `_vocab.md` 에 없다.

```
[오류] _vocab.md 미등재 좌표
   table:rp_trip_photo_list

ctx check: 오류 1건. 커밋할 수 없습니다.
```

**어휘에 없는 이름은 좌표가 아니다.** 등재하지 않고 쓰면 같은 테이블이
`rp_trip_photo` · `trip_photo_list` 로 갈라져 쌓이고, 그때는 되돌릴 수 없다.

### 회복 — 그리고 두 번째 차단

`_vocab.md` 의 `## table` 에 한 줄 올린다.

```
- `table:rp_trip_photo_list` — 출장사진목록
```

다시 커밋하면 **이번에는 다른 오류로 막힌다.**

```
[오류] 관리 문서 파생 누락
   table:rp_trip_photo_list  docs/테이블정의서.md ## rp_trip_photo_list
```

등록부의 `table:*` 이 이미 이 좌표를 테이블정의서로 보내기 때문이다.
섹션을 만들어야 끝난다.

**오류가 두 단계로 오는 것이 정상이다.** 한 번에 다 말해 주지 않는 이유는,
어휘에 없는 좌표는 아직 어느 문서로 갈지도 정해지지 않았기 때문이다.

### 확인

```
bin/ctx term rp_trip_photo_list      → 정본으로 나온다
bin/ctx check                        → 이상 없음
```

**등재 여부를 `ctx where` 로 확인하지 마라.** 등재되지 않은 좌표에도
답을 준다 —

```
$ bin/ctx where table:rp_trip_photo_list      ← 아직 어휘에 없는 상태
  문서   docs/테이블정의서.md
  섹션   ## rp_trip_photo_list
  작업   0건
```

등록부의 `table:*` 패턴으로 **살게 될 자리**를 계산한 것이지 등재됐다는
뜻이 아니다. 등재를 묻는 명령은 `ctx term` 이다 — 없으면 `_vocab.md 에
없습니다` 라고 답한다.

## S4 — 아젠다 (**기록이 만들어지면 안 된다**)

### 시키는 말

> 출장을 부분 취소하면 이미 정산된 금액을 어떻게 되돌릴지 **아직 안 정했다.**
> 다음 회의에서 논의하기로 했어. 남겨 둬.

### 일어나야 하는 것

`cdp-save` 가 **작업 기록을 만들지 않는다.** 정해지지 않은 것은 지식이
아니라 아젠다다. 위험및이슈관리대장으로 간다.

이미 `issue:ISS-004 — 출장 부분 취소 시나리오 오류` 가 있다. **거기에 붙일지
`ISS-007` 로 새로 낼지가 판단이 필요한 자리다** — 어느 쪽이든, 그 판단을
설명해야 한다. 말없이 새로 내면 대장이 중복으로 부푼다.

새로 낸다면 좌표도 함께 등재한다.

```
_vocab.md   ## issue 에 `issue:ISS-007` 한 줄
docs/위험및이슈관리대장.md   ## ISS-007 — … 섹션
```

### 음성 시험 — 억지로 밀어 본다

`work/` 에 이런 기록을 손으로 만들어 커밋해 본다.

```
---
id: 2026-MMDD-출장부분취소-환급
title: 출장 부분 취소 시 환급 방식
date: 2026-MM-DD
author: kjsa
status: 미결
touches:
  - screen:EXD020
---
```

```
[오류] status: 미결·제안 — 지식공유문서가 아니라 아젠다입니다
```

막혀야 한다.

## S5 — 오기재 정정 (기록을 고치지 않는다)

### 시키는 말

> S2 에서 20MB 라고 적었는데 확인해 보니 **10MB** 였다. 고쳐 줘.

### 일어나야 하는 것

**앞 기록을 편집하지 않는다.** `work/` 는 append-only 다. 새 기록을 쓰고
`supersedes` 로 앞 것을 가리킨다.

```
---
id: 2026-MMDD-첨부용량-정정
title: EXD020 사진 첨부 용량 정정 — 20MB → 10MB
supersedes: 2026-MMDD-사진첨부-용량
touches:
  - screen:EXD020
---
```

관리 문서 섹션은 **새 값으로** 갱신한다.

### 왜

앞 기록을 지우면 6개월 뒤 "왜 10MB 인가" 를 물었을 때 답할 것이 없다.
20MB 로 잘못 알고 진행한 구간이 있었다는 사실 자체가 맥락이다.

`supersedes` 는 **이 기록 자체가 틀렸을 때만** 쓴다. 같은 좌표를 나중에
또 바꾼 것은 적을 필요가 없다 — 그것은 계산으로 나온다.

### 확인

```
bin/ctx where screen:EXD020    → 반영이 정정 기록을 가리킨다
```

## S6 — 진행중 (점유)

### 시키는 말

> `rp_trip_photo_list` 쪽은 내가 이번 주 내내 잡고 있을 거야. 다른 사람이
> 동시에 안 건드리게 표시해 줘.

### 일어나야 하는 것

`status: 진행중` 을 단 기록. **커밋이 통과해야 한다.**

`확정`·`완료` 는 적지 않는다 — 기본값이라 파싱 경계에서 지워진다. 뜻이
있는 값은 `진행중` 하나뿐이다.

### 확인

```
bin/ctx brief          → 진행중 1건이 보인다
bin/ctx check          → 이상 없음 (경고도 아니다)
```

## S7 — INDEX 와 뷰어

```
bin/ctx index
    → INDEX.md N행 / INDEX-by-coord.md 좌표 M개
bin/ctx check
    → 이상 없음  (INDEX 불일치 경고가 사라져야 한다)
```

`tools\cdp.exe` 를 더블클릭해 눈으로 본다.

| 보는 곳 | 나와야 하는 것 |
|---|---|
| 작업문서 탭 | 새 기록들이 **작성일자순** 맨 위 · 작성자가 붙어 있다 |
| 관리문서 탭 | 화면설계서 · 테이블정의서의 해당 섹션이 새 내용 |
| 좌표 탭 | `table:rp_trip_photo_list` 가 생겼다 |
| 그래프 | 왼쪽 `screen` → `EXD020` 을 고르면 가운데로 온다 · 노드가 커졌다 |
| 뻗어나가기 | 작업문서 → 관리문서·좌표 / 좌표 → 관리문서·작업문서 |

그래프에서 **노드가 커진 것**이 곧 작업 건수다. S1·S2·S5 로 EXD020 을 세 번
건드렸으니 눈에 띄게 커져 있어야 한다.

## 정리 — 브랜치를 버린다

```
cd C:\cdp
git switch main
git branch -D test/지식공유문서-시나리오
bin/ctx check           → 이상 없음
git log --oneline -1    → 0 단계에서 확인한 그 커밋
```

`_vocab.md` 나 `docs/` 에 시험 흔적이 남지 않았는지 마지막으로 본다.
브랜치를 팠으니 남을 리 없지만, **남을 리 없다고 믿는 것과 확인하는 것은
다르다.**

## 점검표

| | 시나리오 | 통과 기준 |
|---|---|---|
| ☐ | S1 정상 | `ctx where` 가 새 기록을 가리킨다 · 커밋 통과 |
| ☐ | S1 맥락 | ② 주입에 "붙일 곳이 없어서" 가 나왔다 |
| ☐ | S2 파생 누락 | **exit 1 · `derive-missing`** |
| ☐ | S2 회복 | `cdp-managed` 뒤 `ctx derive` 가 비었다 |
| ☐ | S3 미등재 | **exit 1 · 미등재 좌표** |
| ☐ | S3 두 번째 | 등재 뒤 이번엔 `derive-missing` 으로 막힌다 |
| ☐ | S4 아젠다 | 작업 기록이 **안 만들어졌다** · 이슈대장으로 갔다 |
| ☐ | S4 음성 | `status: 미결` 이 `agenda-status` 로 막힌다 |
| ☐ | S5 정정 | 앞 기록이 **그대로 남아 있다** · `supersedes` 가 걸렸다 |
| ☐ | S6 진행중 | 커밋 통과 · `ctx brief` 에 보인다 |
| ☐ | S7 뷰어 | 다섯 자리에서 다 보인다 |
| ☐ | 정리 | 브랜치 삭제 후 `main` 이 시작 커밋 그대로 |

하나라도 **막혀야 할 것이 안 막혔으면** 그것이 이 시험의 유일한 실패다.
나머지는 고치면 되지만, 그것은 도구를 믿을 수 없다는 뜻이다.
