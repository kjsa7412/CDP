# 판정 모델 정정 — 밀림·미결·덮힘은 있을 수 없다
> **v1.0 이후** — 「밀림은 있을 수 없다 · 파생 누락은 오류」 는 뒤집혔다 — 미반영은 상태다(I7) · [`CDP_시스템설계서_v2.0.md`](../design/CDP_시스템설계서_v2.0.md) §1 · §3.6. 미결 · 제안 · 덮힘의 정정은 그대로다.

2026-09-04 · 사용자 확정. 설계 변경 **3건**.

기존 설계(수행 v1.0 §6.2 · 프로토콜 v1.1 §12.2)는 밀림을 **경고**로 두고 미결을
`status` 값으로 뒀다. 그 전제가 틀렸다.

---

## 1. 밀림 — 경고가 아니라 **있을 수 없는 상태**다

### 무엇이 바뀌나

> **지식공유문서를 만들면서 관리 문서 파생은 필수다. 선택이 아니다.**

수행 v1.0 §6.2 는 밀림을 *"경고이지 거부가 아니다"* 라고 하고 이유 셋을 댔다.
셋 다 성립하지 않는다.

| §6.2 의 이유 | 정정 |
|---|---|
| 파생의 폭이 감당 못 할 만큼 넓다 | **넓어도 해야 한다.** 폭이 넓다는 것은 그 작업이 실제로 그만큼 건드렸다는 뜻이다 |
| 관리 문서 갱신에 다른 사람의 확인이 필요하다 | **필요 없다.** 판단 근거는 지식공유문서에 이미 다 들어 있다. 그것이 지식공유문서를 쓰는 이유다 |
| 급한 커밋을 막으면 훅을 우회한다 | **분리하면 된다.** 작업 완료 커밋과 지식공유 커밋은 별개다. 코드를 먼저 커밋하고, 지식공유문서는 그 뒤에 쓴다 |

셋째가 핵심이다. **막히는 것은 코드 커밋이 아니라 지식 레포 커밋**이고, 지식
레포 커밋은 급할 이유가 없다 — 이미 작업이 끝난 뒤에 하는 일이다.

### 규칙

```
작업 기록이 새로 들어오는 커밋에는
그 작업의 좌표에 해당하는 관리 문서 섹션 갱신이 함께 있어야 한다
```

`ctx check` 에서 `stale-section` 을 **`warn` → `error`** 로 올린다. 훅이 막는다.

```
$ git commit
[ctx] ⛔ 관리 문서가 밀렸습니다  3건
       docs/테이블정의서.md    ## ps_ext_emp_mst
         applied 2026-0821-면접심사의견-개편 뒤 후속 1건
       …
       `ctx apply <좌표>` 로 초안을 받거나 cdp-managed 로 따라잡으세요
[pre-commit] 커밋을 중단했습니다.
```

### 따라오지 **않는** 것 — "관리 대상 아님" 은 그대로 둔다

밀림이 0인 것은 **자리가 다 있어서가 아니라, 자리가 있는 것에 대해 파생이
필수이기 때문**이다.

관리 문서는 **자주 쓰는 내용**을 하나로 모아 둔 것이다.

| | 원천 |
|---|---|
| 자주 쓰는 내용 | 관리 문서 섹션 — 하나로 수렴시키고 그 대가로 갱신 부담을 진다 |
| 덜 쓰는 내용 | **그 지식공유문서 자체** — 하나로 모으는 부담이 이득보다 크다 |

등록부에 안 걸리는 좌표는 파생이 필요 없다. **밀림이라는 개념 자체가 없다.**

---

## 2. 미결 — CDP 의 것이 아니다

> **지식공유문서는 작업의 완료에서 발생하는 문서다.**

미결은 완료가 아니다. 결정을 기다리는 것은 **아젠다**이고, 아젠다는 이슈관리·
TODO·일정 같은 **스케줄 형태의 문서**가 다룬다. 관점이 다르다.

| | 지식공유문서 | 이슈/아젠다 |
|---|---|---|
| 언제 생기나 | 작업이 **끝났을 때** | 문제를 **발견했을 때** |
| 무엇을 담나 | 무엇을 왜 그렇게 했나 | 무엇을 정해야 하나 |
| 성질 | 불변. 사건 | 가변. 상태가 바뀐다 |
| 어디 사나 | `work/` | `docs/위험및이슈관리대장.md` |

### 규칙

- `status` 에서 **`미결` 을 없앤다.** 남는 값은 `확정` · `제안` · `진행중`
- 기존 미결 문서는 **위험및이슈관리대장으로 옮긴다**
- `ctx brief` · 현황 화면의 "미결 도달" 계기가 없어진다 — 이슈 대장이 대신한다
- 화면의 보라색(미결)이 색 예산에서 빠진다 → **색 3개**

> 프로토콜 v1.1 §12.1 의 *"`decisions` 를 필드로 두지 않는다. `status: 미결`
> 하나로 충분하다"* 는 판단은 **문서 종류를 하나만 가정한 것**이었다. 관리 문서
> 16종에 이슈 대장이 들어오면서 그 가정이 깨졌다.

---

## 3. 덮힘 — 구조에 영향을 주지 않는다

`supersedes` 는 이미 사람이 명시할 때만 생긴다(자동 부여 없음). 그것을 확정하고,
**판정에서 뺀다.**

| | 지금 | 정정 |
|---|---|---|
| `supersedes` 선언 | 사람이 적는다 | **그대로** |
| 선언된 문서 | `유효성 = superseded`. 검색에서 내림 | **판정하지 않는다.** 검색에도 남는다 |
| 화면 | ⛔ 정정됨 (적색, 상단 고정 바) | **참조 한 줄** — "이 기록을 정정한 문서" |
| 4개념 축 | 나이 · **유효성** · 최신성 · 절단 | 나이 · 최신성 · 절단 |

### 그러면 "지금 맞는 말"은 무엇이 답하나

**두 갈래로 나뉜다.**

```
좌표의 맥락을 구성할 때        시간 순으로 최신성을 판단한다
자주 바뀌는 내용              관리 문서가 최신 데이터로 덮고 있다 -> 그 문서를 본다
```

작업 기록은 **사건**이라 쌓이기만 하고 무효가 되지 않는다. 지금 상태를 말하는
것은 관리 문서 섹션이고, 섹션은 덮어쓴다. 그래서 `supersedes` 라는 별도 축이
필요 없다 — **§1 이 밀림을 0으로 만들면 관리 문서가 항상 최신이기 때문이다.**

세 정정이 서로를 떠받친다.

## 4. 관리 문서 16종

| 관리 문서 | 좌표 타입 | 섹션 |
|---|---|---|
| 회의록 | — | 좌표 없음. 날짜축 |
| 위험및이슈관리대장 | `issue:` | `## {번호}` |
| 요구사항정의서 | `req:` | `## {ID}` |
| 프로세스정의서 | `proc:` | `## {ID}` |
| 기능정의서 | `func:` | `## {ID}` |
| 프로그램목록 | — | 목록. 사양서가 본체 |
| 프로그램사양서 | `prog:` · `batch:` · `module:` | `## {ID}` |
| 인터페이스정의서 | `api:` | `## {값}` |
| 코드정의서 | `code:` | `## {값}` |
| 시스템아키텍처정의서 | `arch:` | `## {값}` |
| 화면설계서 | `screen:` | `## {값}` |
| DB도메인용어정의서 | `term:` | `### {값}` |
| 테이블정의서 | `table:` | `## {값}` |
| 개발일정계획서 | — | 좌표 없음. 일정축 |
| 테스트케이스 | `test:` | `## {ID}` |
| 테스트시나리오 | `scenario:` | `## {ID}` |

**좌표 없는 문서 셋** — 회의록 · 프로그램목록 · 개발일정계획서. 관리 문서이되
등록부 대상이 아니다. 좌표-섹션이 1:1로 대응하지 않는 축(날짜·일정)을 쓴다.

`module:` · `batch:` 가 프로그램사양서로 간다 — 모듈·배치도 프로그램이다.

**`domain:` 은 등록부에 올리지 않는다.** 업무 영역에는 "지금 상태"라고 적을 것이
없다 — 산출물이 아니라 작업을 묶는 축이다. 원천은 그 업무를 다룬 지식공유문서들이다.

**화면정의서를 업무별로 쪼개지 않는다.** 16종 목록이 `화면설계서` 하나다.

## 5. 남는 판정

정정 뒤 앱과 `ctx` 가 내는 판정은 이것뿐이다.

| 판정 | 등급 | 뜻 |
|---|:--:|---|
| 미등재 좌표 | **error** | `_vocab.md` 에 없는 좌표를 썼다 |
| **밀림** | **error** | 관리 문서 섹션이 후속을 안 실었다 ← **승격** |
| 섹션/문서 없음 | error | 등록부가 가리키는데 자리가 없다 |
| 끊김 | error | `applied` 가 없는 id 를 가리킨다 |
| 필수 필드 누락 | error | |
| 미작성 섹션 | info | 작업 기록은 있는데 섹션이 비었다 |
| 후속 N건 | (판정 아님) | 시간 순 이력. 화면 표시만 |

**error 가 아니면 커밋을 막지 않는다.** 그리고 정상 레포에서는 전부 0이다.

## 6. 화면 — 왼쪽은 시작점과 뻗어나가기

핵심은 그래프 탐색이다.

```
┌──────────────────────────────┐
│ [위]  문서 · 좌표 · 그래프      │  시작점을 고른다
├──────────────────────────────┤
│ [아래] 뻗어나가기               │  고른 것에서 다음 노드
│   문서 A                      │
│     └ table:x  screen:y       │  ← A 의 다음 레벨
│        └ 09-02 작업B  섹션S    │  ← x 를 고르면 그 다음 레벨
│           └ …                 │
└──────────────────────────────┘
```

| 규칙 | |
|---|---|
| 한 번에 **다음 레벨 하나만** | 전체 그래프를 펴지 않는다 |
| 중간 노드를 다시 고르면 | 그 아래가 교체된다 |
| **루프를 허용한다** | 같은 노드가 여러 레벨에 나올 수 있다. 트리가 아니다 |
| 노드 = 문서 · 좌표 · 섹션 | 셋 다 클릭하면 오른쪽에 열린다 |

이 안에 필요 없는 요소는 전부 걷어낸다 — 관계 탭 · 현황 탭 · 뷰 3종.
