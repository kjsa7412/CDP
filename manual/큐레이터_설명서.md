## 0. 큐레이터가 맡는 것

### 0.1 원천 셋 · 역할 넷

```
 writer 세션 ──save(작업 기록)──▶ work/ ──▶ 대기열 ──▶ 큐레이터 세션(cdp-curate) ──save(큐레이션)──┐
 (cdp-work · cdp-save)                                판정 · 정본 · 현재형                         │
                                                                                                  ▼
 생성기(프로젝트 스크립트) ──save(기준선)── 코드 · DB 에서 기계로 ──────────────────▶ 관리 문서 docs/
                                                                                     섹션 = 정본 서술
 읽는 쪽(사람 · 에이전트) ◀── section · 화면 ── 섹션 + 기준선 블록 + 미반영 기록 ◀──── + 기준선 블록 + 경과
```

관리 문서의 원천은 셋이다 — **작업 기록**(사건 · 결정) · **큐레이터의 판단**(정본 · 현재형) · **기준선**(코드 · DB 에서 기계로 뽑은 블록).
큐레이터는 둘째를 쓰고, 셋째의 자리를 지킨다.

### 0.2 큐레이터는 레포별 권한이다

- admin 이 **서버 › 사용자 › 「레포 × 큐레이터」** 표에서 맡긴다 — 체크 하나가 그 사람의 `curate` 한 줄이다. 셸에서는
  `ctx serve user set --name <이름> --curate <레포,…>`.
- writer 중 누구에게나 줄 수 있다(팀 리드 · 문서 담당). **viewer 는 큐레이터가 될 수 없다** — 큐레이션은 쓰기다.
  볼 수 없는 레포의 큐레이터는 될 수 없다. **admin 은 모든 레포의 큐레이터다.**
- 내가 큐레이터인지 — 화면 왼쪽 메뉴에 **「큐레이션」** 묶음(대기열 · 이력 · 서식집)이 보이고, 「내 계정」 의 할 수 있는 것에 「큐레이션」 이 있다.
  에이전트 쪽은 `/mcp` 의 도구가 12건(`queue` · `forms` 가 더)이다.

### 0.3 하는 것 · 하지 않는 것

| 하는 것 | 하지 않는 것 |
|---|---|
| 대기열의 기록을 판정한다 — 반영 · 새 문서 · 기록으로 둠 | 작업 기록 고치기 · 지우기 — 불변이다(작성자가 정정 기록을 낸다) |
| 관리 문서 섹션을 쓴다 — 정본 한 곳 · 현재형 · 경과 한 줄 | 기준선 블록 안 — 생성기의 자리다 |
| 서식집에서 새 관리 문서를 세운다 · 등록부 행을 더한다 | 지식 레포 세우기 · 이름 · 원격 · 사람 · 토큰 — admin |
| 이름 · 합치기 · 폐기 · 안 쓰는 문서 지우기 · 섹션 밖 글 | 옛 레포를 기록만으로 다시 세우기 — admin(콘솔 · CLI) |
| 기준선을 올린다(생성기 · `ctx baseline push`) | 섹션 점유 · 알림 · 작업 할당 — 없다 |

## 1. 자리 — 큐레이터 폴더

큐레이션은 **큐레이터 폴더**의 Claude Code 에서 한다. 작업 레포가 아니어도 된다 — git 레포가 아니어도 되고 작업 레포 대장에
오르지 않는다. 레포마다 폴더 하나(예 `C:\curate\alpha`).

### 1.1 설치 한 줄 — `--curator`

그 폴더에서 붙여넣는다. 서버 주소 · 레포 이름만 바꾼다.

```
# PowerShell
curl.exe -fsSLo "$env:TEMP\cdp-install.mjs" http://<서버>:7374/install.mjs; if ($?) { node "$env:TEMP\cdp-install.mjs" --curator --repo <레포> . }
# 명령 프롬프트
curl -fsSLo "%TEMP%\cdp-install.mjs" http://<서버>:7374/install.mjs && node "%TEMP%\cdp-install.mjs" --curator --repo <레포> .
# macOS · Linux
curl -fsSLo /tmp/cdp-install.mjs http://<서버>:7374/install.mjs && node /tmp/cdp-install.mjs --curator --repo <레포> .
```

토큰을 물으면 붙여넣는다(이 PC 에서 처음일 때 · `CDP_TOKEN` 에 둘지 묻는다). **그 토큰이 그 레포의 큐레이터가 아니면**
설치기가 「이 토큰은 <레포> 의 큐레이터가 아닙니다」 로 멈춘다 — admin 에게 큐레이터를 청한다. 무엇이 바뀔지 보여 주고 묻는다.

```
.claude/skills/cdp-*    스킬 여섯 — cdp-work · cdp-save · cdp-push · cdp-curate · cdp-registry · cdp-rebuild
CLAUDE.md               큐레이터 블록 — 이 폴더가 그 레포의 큐레이션 자리라는 것 · 승인 · 정본 · 기준선 규칙
.mcp.json               cdp 항목 — 서버 주소 /mcp/<레포> · Bearer ${CDP_TOKEN}
.claude/cdp.json        { "server": …, "repo": … }
```

Claude Code 를 완전히 끄고 다시 켠다 → `/mcp` 에 `cdp` connected · **도구 13**(읽기 아홉 · `save` · `queue` · `forms` · `drift`).

### 1.2 갱신

새 판이 올라가 스킬이 바뀌었으면 **같은 한 줄을 다시** 돌린다(이미 최신이면 그렇게 말한다). 작업 레포용 `--update` 는 그 PC 의
작업 레포 목록만 돈다 — 큐레이터 폴더는 목록에 적히지 않는다.

> **작업 레포의 세팅은 팀이 같이 쓰는 파일이다.** 그래서 등록된 작업 레포의 설치 한 줄은 **누가 돌려도 writer kit**(스킬 셋 ·
> 프로젝트레포 블록)이다 — 큐레이터 토큰으로 돌려도 큐레이터 스킬이 그 레포에 커밋되지 않는다. 큐레이터 kit 은 큐레이터 폴더(`--curator`)에만
> 간다. 큐레이션은 큐레이터 폴더에서 한다.

## 2. 대기열

### 2.1 화면 — 「큐레이션 › 대기열」

```
┌ 대기 12 · 가장 오래된 9일 · 미반영 섹션 7 · 마지막 큐레이션 10-05 lead ─────────────┐
│ 대기열 — 오래된 순                         │ 판정 재료 — 고른 기록 하나                 │
│ ☐ 2026-0927 ERP 연계 사전조사  섹션 2      │ 반영 후보 · 섹션 없음 · 등록부 없음 ·        │
│ ☐ 2026-0929 전문 규격 초안  등록부 없음 1   │ 비슷한 서식 · 정본 후보 · 본문에만 있는 좌표  │
│ ☐ 2026-1001 주간 회의        좌표 0         │ 에이전트 지시 — 복사되는 글                │
│ [기록으로 둠…]  [에이전트 지시 복사]         │                                         │
└──────────────────────────────────────────┴─────────────────────────────────────────┘
```

- **오래된 순**이다 — 서버가 계산한다(저장하지 않는다). 오래된 것부터 다룬다.
- 기록마다 걸린 좌표를 넷으로 가른 칩이 붙는다.

| 칩 | 뜻 | 대개의 판정 |
|---|---|---|
| **섹션 n** | 그 좌표의 섹션이 있다 | 반영 |
| **섹션 없음 n** | 등록부에 패턴은 있는데 섹션이 없다 | 섹션을 세우며 반영 |
| **등록부 없음 n** | 그 타입을 받는 관리 문서가 없다 | 서식에서 새 문서 · 또는 기록으로 둠 |
| **좌표 0** | 기록에 좌표가 없다(사유는 기록에) | 대개 기록으로 둠 |

- **무엇이 대기열에 서나** — 사람이 남긴 작업 기록 중 아직 아무 큐레이터도 판정하지 않은 것. **서지 않는 것** — 큐레이션 기록 ·
  기준선 기록 · 등록부 · 문서 정리 기록(태그 `registry` · `docs-prune`) · 옛 판의 파생 정리 기록.
- **가장 오래된 대기가 14일을 넘으면** 검사가 경고한다(`curation-stale`) — 큐레이터와 admin 의 화면에만. writer 의 응답에는 싣지 않는다.
- 메뉴 배지 — 「지식 › 작업 기록」 · 「큐레이션 › 대기열」 옆 숫자가 대기 수다. 서버 › 지식 레포 표에도 레포마다 대기 · 가장 오래된 열이 있다.

### 2.2 에이전트 — `queue`

```
queue({ repo })                 대기열 — items(오래된 순) · total · oldestDays
queue({ repo, id: "<기록 id>" })  기록 하나의 판정 재료 — §3
```

`cdp-curate` 가 이것으로 시작한다. 화면과 같은 계산(`core/curation.js`)이다.

## 3. 판정 재료

대기열에서 기록 하나를 누르면 오른쪽에 뜬다. **판정 재료는 그 레포의 큐레이터만 본다**(목록은 누구나 본다).

| 재료 | 무엇 | 어디에 쓰나 |
|---|---|---|
| **반영 후보 — 섹션 있음** | 걸린 좌표 중 섹션이 있는 것 · 누르면 그 섹션으로 간다. 보라 칩이면 이미 다른 미반영이 있다 | 반영할 자리 |
| **등록부 있음 · 섹션 없음** | 패턴은 있는데 섹션이 없다 | 그 문서에 섹션을 세운다 |
| **등록부 없음** | 그 타입을 받는 문서가 없다 | 새 문서 후보 · 또는 기록으로 둠 |
| **비슷한 서식** | 등록부 없는 타입마다 서식 후보(제목 · 번호 · 등록부 타입이 그 이름을 품는 것) | §7 |
| **정본 후보** | 같은 좌표를 건드린 다른 대기 기록 | **같이 다룬다** — 따로 반영하면 같은 섹션을 두 번 쓴다 |
| **본문에만 있는 좌표** | 본문에 `` `좌표` `` 로 썼는데 `touches` 에 없다 | 기록이 그 대상을 바꿨으면 반영할지 판정표에 적는다 · 언급이면 둔다 |
| **에이전트 지시** | [에이전트 지시 복사] 가 복사하는 글 | §5 |

에이전트는 같은 재료를 세 도구로 읽는다.

| 도구 | 주는 것 |
|---|---|
| `queue({ id })` | `record`(제목 · 날짜 · 작성자 · touches · 첫 문단) · `coords`(좌표마다 `cls` · `doc` · `state` · `applied` · `pending`) · `unregisteredTypes` · `bodyOnly` · `together` |
| `work({ id })` | 기록 본문 · 큐레이션 상태. **오래된 기록부터 읽는다** — 추가했다가 이름을 바꾼 경우 최신만 읽으면 추가를 놓친다 |
| `section({ coord })` | `content`(지금 큐레이터의 글) · `applied`(**잠금 값 — 그대로 보낸다**) · `baseline`(기계 블록) · `pendingRecords`(이 좌표의 미반영 전부) · `refs`(건 정본) · `form`(그 문서의 서식) |

**기록이 홀로 서지 못하면 지어내지 않는다** — 「섹션 X 참조」 · 「DB 에서 확인」 · 값 없는 「정했다」 면 작성자에게 묻거나 대기열에 남긴다.

## 4. 판정 셋

### 4.1 기록마다 하나

| 판정 | `verdict` | 언제 | 보낼 것 |
|---|---|---|---|
| **반영** | `reflect` | 기록의 사실이 있는 섹션(또는 등록부 행만 있는 자리)에 들어간다 | `into: [좌표]` — **그 좌표들이 같은 save 의 `sections` 에 있어야 한다** |
| **새 문서** | `new` | 받을 문서가 없다 — 서식에서 세우고 반영한다 | `into` + `managed` 의 새 행 · 문서(§7) |
| **기록으로 둠** | `keep` | 섹션에 옮길 사실이 없다 — 경위 · 회의 논의 · 사전 지식 · 버린 안 · 참조만 한 기록. 기록이 원천으로 남는다 | `reason` 한 줄 |

### 4.2 판정의 규칙

- **판정은 기록 단위 · 미반영은 좌표 단위다** — 판정을 받은 기록은 대기열에서 나간다. 섹션 옆 「미반영」 은 좌표마다 따로 —
  `keep` 이면 모든 섹션에서 사라지고, `reflect` · `new` 면 **`into` 에 넣은 좌표의 섹션에서만** 사라진다. 기록이 건드린 다른 좌표의
  섹션이 그 기록보다 옛 `applied` 면 거기에는 계속 미반영으로 실린다(그 섹션은 그 기록을 아직 싣지 않았다). 그래서 기록의 `touches`
  를 하나씩 본다: 반영할 좌표는 전부 `into` 에(그 섹션은 같은 save 에), 반영하지 않는 좌표는 판정표에 까닭을 적는다. 이번 묶음에서
  다 다루지 못하면 그 기록은 이번 판정에서 뺀다 — 대기열에 남아야 다음 큐레이터가 본다.
- **확신이 없으면 판정하지 않는다** — 빼 두면 대기열에 남고 섹션 옆에 계속 실린다. `keep` 은 「옮길 것이 없다」 는 판정이라 미반영
  표시가 사라진다 — 모를 때 쓰지 않는다. 안 채운 것은 대기열이 말하지만 **틀리게 채운 것은 아무도 모른다.**
- **바뀐 게 없는데 좌표가 걸렸으면** — 그 기록이 대상을 쓰는 방식만 바꿨을 수 있다. `reflect` 로 섹션 본문은 그대로 두고 경과 한 줄만
  더한다(「컬럼 변경 없음 — 선택 모달의 묶음 키로 쓴다」). 바뀐 게 없다는 것도 사실이다. 경과에도 남길 것이 없으면 `keep`.
- **문서를 고치라는 지시 기록** — 본문의 「지시 · 바꿀 것 · 확인한 것」 이 재료다. 지금 섹션이나 다른 기록이 정한 이유와 어긋나면
  반영하지 않고 지시한 사람에게 묻는다(대기열에 남긴다).
- **좌표 0 기록**은 대개 `keep` 이다. 옮길 사실이 있으면 그 자리에 반영해도 된다 — `into` 는 기록의 `touches` 밖이어도 된다. 기록의
  `touches` 가 틀렸으면 반영은 맞는 자리에 하고 작성자에게 정정 기록을 청한다 — 좌표로 찾아오는 길은 `touches` 뿐이다.
- **등록부 밖 문서**(회의록 · 가이드처럼 좌표가 없는 사건 · 서술 문서)에 옮길 것은 `edits` 로 쓰고(§8.6) 그 기록은 `keep` ·
  `reason: "<문서> 에 반영(edits)"`.
- **가장 늦은 판정이 이긴다** — 이미 판정된 기록도 다시 다룰 수 있다(섹션을 고쳐 쓸 때).

### 4.3 화면에서 하는 판정 — 「기록으로 둠」 하나

대기열에서 기록을 고르고(체크 여럿 · 안 고르면 지금 보는 줄) **[기록으로 둠…]** → 사유(필수 — 왜 섹션에 반영하지 않나: 사전지식 ·
회의 잡담 · 다른 기록이 이미 담음) → 서버가 큐레이션 기록 하나를 지어 같은 `save` 를 탄다(한 커밋 · 한 번에 50건까지).
**반영 · 새 문서는 글을 쓰는 일이라 화면에 없다** — 에이전트 세션이 한다(§5).

## 5. 한 바퀴 — 지시 복사에서 save 까지

### 5.1 지시를 복사한다

대기열에서 기록을 고르고 **[에이전트 지시 복사]**.

```
cdp-curate alpha
대상: 2026-0901-ERP-연계-사전조사
      2026-0903-ERP-전문규격-초안
      2026-0908-ERP-연계방식-결정
정본 한 곳 · 본문 현재형 · 경과 한 줄. 판정표를 보이고 승인 뒤 save.
```

큐레이터 폴더의 Claude Code 에 붙인다. 고르지 않고 「큐레이션해 줘」 라고만 해도 된다 — 대기열 전부를 오래된 순으로 본다.

### 5.2 `cdp-curate` 가 도는 길

```
① 대기열   queue — 아직 판정 안 받은 작업 기록, 오래된 순
② 묶기     같은 좌표 · 같은 주제 — 섹션 50 이하가 save 하나
③ 재료     queue({ id }) · work · section
④ 판정     기록마다 반영 · 새 문서 · 기록으로 둠 — 사실마다 정본 자리 하나
⑤ 쓰기     정본 한 곳 · 현재형 · 경과 한 줄 · 기준선 블록 밖 · 종류별 모양(§6)
⑥ 미리보기  save({ …, dryRun: true }) — 판정표 + 섹션 diff 를 보이고 승인
⑦ save     승인받은 입력에서 dryRun 만 뺀다 — 큐레이션 기록 하나 + 섹션 · 새 문서 한 커밋
⑧ 끝 보고   커밋 · 미러 · 판정 수 · 남은 대기
```

**묶기** — 같은 좌표를 건드린 기록은 한 묶음이다(재료의 「정본 후보」 · `together`). 같은 주제(한 결정의 사전 조사 · 초안 · 결정)도
한 묶음이다 — 정본 자리를 한 번에 정한다. 한 묶음 = save 하나 = 큐레이션 기록 하나 · **섹션 50 이하.** 대기가 많으면 묶음 목록을
먼저 보이고 하나씩 승인받는다 — **한 번에 다 하지 않는다.** 큰 diff 는 승인이 형식이 된다.

### 5.3 판정표 — 승인하는 자리

```
【판정표】 큐레이션 — ERP 연계 기록 3건 · 섹션 3 · 새 문서 1
  기록                              판정       어디로 · 사유
  2026-0901-ERP-연계-사전조사         keep       사전 조사 — 결론은 방향 결정 기록이 원천
  2026-0903-ERP-전문규격-초안         new        인터페이스:ERP-결의서전송(새 문서 docs/인터페이스정의서.md · 서식 public-si/DE_501) · 이슈:ISS-007(경과 한 줄)
  2026-0908-ERP-연계방식-결정         reflect    인터페이스:ERP-결의서전송 · 이슈:ISS-007 · 시스템아키텍처:link
  정본   전문 규격 → 인터페이스:ERP-결의서전송 (이슈 · 아키텍처는 결론 한 줄 + 좌표)
【등록부 변경】 행 인터페이스:* → docs/인터페이스정의서.md ## {값} (서식 public-si/DE_501 · 새 문서)
【섹션 diff】 좌표마다 지금 content → 보낼 body (바뀐 대목만 · 새 섹션은 전문)
【dryRun】 통과 · warnings 그대로
승인하시면 커밋합니다. 판정 · 정본 · 문장을 고칠 것이 있으면 알려 주세요.
```

읽을 것 —

| 줄 | 볼 것 |
|---|---|
| 판정 | 기록마다 셋 중 하나인가 · `keep` 의 사유가 「옮길 것이 없다」 인가(「모르겠다」 가 아닌가) |
| **정본** | 한 사실이 한 섹션에만 적히는가 · 대장(이슈 · 위험)이 설계서가 되지 않았나 |
| 등록부 변경 | 새 문서가 정말 없던 것인가(이름만 다른 중복이 아닌가) · 패턴의 타입이 기록이 쓴 타입인가 |
| 섹션 diff | 본문이 현재형인가 · 경과가 한 줄씩인가 · 근거 기록에 없는 값이 들어가지 않았나 |
| dryRun | 통과했나 · 경고를 그대로 보였나 |

`dryRun` 은 서버가 권한 · 판정(`into` 가 `sections` 에 있나) · 잠금(`applied`) · 등록부 · 검사까지 돌고 **커밋하지 않는** 것이다.
고치라고 하면 고쳐서 다시 dryRun → 다시 보인다. **승인 전에는 커밋하는 save 를 부르지 않는다.**

### 5.4 큐레이션 기록

save 한 번이 **큐레이션 기록 하나**를 남긴다.

```yaml
id: 2026-0910-큐레이션-ERP연계          # YYYY-MMDD-큐레이션-<주제>
title: 큐레이션 — ERP 연계 기록 3건
date: 2026-09-10 10:20
curates:
  - { id: 2026-0901-ERP-연계-사전조사, verdict: keep, reason: 사전 조사 — 결론은 방향 결정 기록이 원천 }
  - { id: 2026-0903-ERP-전문규격-초안, verdict: new, into: [인터페이스:ERP-결의서전송, 이슈:ISS-007] }
  - { id: 2026-0908-ERP-연계방식-결정, verdict: reflect, into: [인터페이스:ERP-결의서전송, 이슈:ISS-007, 시스템아키텍처:link] }
```

- **`touches` 를 갖지 않는다** — 서버가 `touchesEmpty: 큐레이션` · 태그 `curate` 를 붙인다. 다룬 기록과 좌표는 `curates` 에 있다.
- **본문은 판정표다** — 기록마다 판정 · 어디로 · 사유, 그리고 정본을 어디로 정했나. 좌표는 **백틱 없이** 적는다(백틱 좌표는
  「본문에만 있는 좌표」 경고가 난다).
- 화면 **큐레이션 › 이력** 에 한 줄로 선다 — 언제 · 누가 · 다룬 기록 · 반영 섹션 · 새 문서 · 기록으로 둠. 누르면 판정표가 펼쳐진다
  (주소 `…/manage/curation/log/<id>`). 다룬 기록의 머리에는 「반영됨 → 좌표」 · 「기록으로 둠(사유)」 이 뜬다.

### 5.5 끝 보고

커밋 · 미러(사용자 설명서 6.9 와 같은 표) · 판정 수(반영 n · 새 문서 n · 기록으로 둠 n) · 바뀐 섹션 · 세운 문서 · **남은 대기 n건 ·
가장 오래된 m일** · 판정하지 않고 남긴 기록과 그 까닭(작성자에게 물을 것).

## 6. 섹션 쓰기 규칙

### 6.1 섹션의 모양

```markdown
## bk_member_mst — 회원마스터
<!-- applied: 2026-1006-LN010-회원번호-직접입력 -->       ← 서버가 쓴다 — 반영한 기록 중 가장 늦은 것

도서관 회원. 회원번호는 대출 화면에서 직접 넣는다(`screen:LN010`) …   ← 정본 서술 · 현재형 · 큐레이터

<!-- cdp:baseline src="개발 DB pg_catalog" asof="2026-10-04" -->
| 컬럼 | 타입 | NULL | 키 | 설명 |                                ← 기준선 블록 · 생성기만
…
<!-- /cdp:baseline -->

**경과**                                                         ← 한 줄씩 쌓는다
- 2026-04-10 [`대출등록-화면`](../work/2026-0410-대출등록-화면.md) 테이블 신설
- 2026-10-06 [`LN010-회원번호-직접입력`](../work/2026-1006-LN010-회원번호-직접입력.md) `mbr_no` 를 화면 입력으로
```

- 헤딩은 `## <값> — <설명>` — 값으로 시작한다. 레벨은 `##` 하나(옛 문서의 `###` 행은 읽기는 계속한다).
- 보내는 `body` 는 `section` 이 준 **`content` 를 고친 것**이다 — 헤딩 줄 · `applied` 주석 · 기준선 블록 없이. 헤딩과 applied 는 서버가
  붙이고, 블록은 서버가 `**경과**` 앞에 다시 붙인다. 섹션 안의 소제목은 `###` 아래나 굵은 글씨로.

### 6.2 규칙

| 규칙 | |
|---|---|
| **정본 한 곳** | 사실은 정본 섹션에만 쓴다. 다른 섹션은 한 줄 — 무엇이 바뀌었나 + 정본 좌표를 `` `좌표` `` 로 건다. `section` 이 그 정본을 한 단계 따라가 같이 싣는다 — 복제하지 않아도 읽는 쪽이 값을 본다 |
| **정본 섹션은 홀로 선다** | 그 섹션만 읽고 대상의 지금을 알 수 있어야 한다 — 판단 · 표 · 규칙 · 값 · 제약 중 대상의 성질이 된 것은 전부 옮긴다. 경위 · 논의 · 대안은 기록의 것이다 |
| **현재형으로 다시 쓴다** | 섹션은 대상의 **지금**이다. 날짜별로 덧붙이지 않는다. 뒤집힌 판단은 본문에서 지우고 경과에 한 줄로 남긴다. 「추가했다」 는 사건이다 — 섹션이 담을 것은 상태(어디에 · 누구용 · 몇 개 · 예외)다 |
| **경과는 끝 목록 한 줄씩** | `**경과**` 아래 `- YYYY-MM-DD [<id 의 주제>](<상대경로>/work/<id>.md) 무엇이` — 날짜는 기록의 날. 추가만 한다. 경과는 출처 표시지 내용이 아니다 — 경과만 붙이고 본문을 안 고치면 반영이 아니다 |
| **기준선 블록은 손대지 않는다** | 큐레이터의 글은 블록 밖에만 — 블록 표지를 본문에 넣으면 거절된다. 블록이 이미 말하는 값을 서술에 다시 옮기지 않는다. 블록이 틀렸으면 생성기 담당에게 |
| **근거보다 크게 쓰지 않는다** | 섹션이 근거 기록들보다 몇 배 크면 출처가 기록 밖이다 — 기록에 없는 것을 지어낸 것이다 |
| **정본 자리가 비어 있으면 가까운 좌표에 쓰지 않는다** | 새 좌표를 등재하고 그 섹션을 세운다. 이미 있는 좌표(이슈)가 받아 주면 대장이 설계서가 된다 |

정본은 그 사실을 **가장 오래 책임지는 대상**의 섹션이다 — 규격이면 인터페이스 · 컬럼이면 테이블 · 뜻이면 용어. 대장(이슈 · 위험)은
정본이 되지 않는다 — 결론 한 줄과 정본 좌표만 둔다.

### 6.3 종류별 모양

종류는 문서에 적혀 있지 않다 — **그 문서의 서식**(`<!-- cdp:form … -->` → 서식의 `kind`)에서 온다. 서식 없이 세운 문서는 가장 가까운 종류로 쓴다.

| 종류 | 문서 예 | 섹션은 | 덮어쓰나 |
|---|---|---|---|
| **대상** | 테이블 · 화면 · 인터페이스 · 코드 · 기능 | 대상의 현재 사양 — 표 · 규칙 · 예외 | 본문은 덮어쓴다 · 경과만 쌓는다 |
| **대장** | 이슈 · 위험 · 형상 · 일정 | 고정 표 + **결론 한 줄** + 경과. 설계 서술 금지 — 내용은 정본 좌표로 건다. 진행상태는 서식이 정한 어휘로만 | 표 · 결론은 덮어쓴다 |
| **정의** | 용어 · 도메인 용어 | 뜻 · 쓰임 · 관련 좌표. 프로젝트의 판단 · 선례 · 수치는 넣지 않는다 | 덮어쓴다 |
| **사건** | 회의록 · 보고서 · 결과서 | 결정 · 할 일 목록만. 원문 · 논의는 작업 기록 | 추가만 |
| **서술** | 가이드 · 계획서 · 매뉴얼 | 문서 전체가 내용 — 절을 고쳐 쓴다(등록부 밖이면 `edits`) | 고쳐 쓴다 |

대장 섹션이 40줄 · 정의 섹션이 25줄을 넘으면 서술이 들어간 것이다 — 정본 자리로 옮긴다. 전후 예시(일지형 → 현재형 · 대장 · 정의 ·
기준선이 있는 섹션)는 큐레이터 폴더의 `.claude/skills/cdp-curate/종류별.md`.

### 6.4 `applied` — 서버가 쓴다

- 보낼 때는 `section` 이 준 `applied` 를 **그대로** 보낸다 — **낙관 잠금**이다. 그 사이 누가 그 섹션을 바꿨으면 `E_CONFLICT`(§10).
- 새 `applied` 는 서버가 계산한다 — 이 save 의 판정 중 `into` 에 그 좌표가 있는 기록의 **가장 늦은 것**(날짜 → id). **뒤로 가지
  않는다** — 원문 날짜를 단 옛 편입 기록만 반영해도 지금 `applied` 가 더 늦은 기록이면 그대로 둔다.
- 판정 없이 섹션만 고치면(글만 다듬을 때) 그 섹션의 `applied` 가 이 큐레이션 기록이 된다 — 그래도 되지만 판정표에 적는다.
- 새 섹션은 `applied: null` · `heading: "<값> — <설명>"`.

### 6.5 링크 · 그림

경과 · 그림 링크는 **그 문서에서 본 상대경로**다 — `docs/X.md` 면 `../work/…` · `docs/1.관리/X.md` 면 `../../work/…`.
관리 문서에 그림을 넣으려면 첨부를 올리고(`POST /api/<레포>/assets` — 사용자 설명서 6.6) `save` 의 `assets` 에 싣는다 —
`work/assets/<큐레이션 기록 id>/<이름>` 에 같은 커밋으로 들어가고 본문에서는 `![설명](../work/assets/<id>/<이름>)`.

## 7. 서식에서 새 문서

### 7.1 서식집 — 화면 「큐레이션 › 서식집」

왼쪽은 서식 찾기 · 묶음 거름 · 서식 목록(이 레포가 이미 쓰는 서식은 「씀」), 오른쪽은 고른 서식의 탭 셋이다.

| 탭 | 무엇 | 문서로 가나 |
|---|---|:--:|
| **만들어지는 문서** | 서버가 **실제로 찍을** 빈 문서 그대로 — 찍는 함수와 같은 함수가 그린다 | ○ |
| **작성지침** | 무엇 · 언제 · 누가 · **여기 적지 않는 것** · 섹션 모양 | — |
| **예시** | (예시) 섹션 · 표 속 예시 | — |

묶음은 넷이다 — 서버 설치본의 `forms/`(제품 판을 따른다).

| 묶음 | 무엇 | 서식 |
|---|---|--:|
| `public-si` | 공공 SI 산출물 — 분석 · 설계 · 구현 · 시험 · 이행 · 사업관리 | 40 |
| `agile-product` | 애자일 제품 개발 — 기능 · 지표 · 화면 · API · 데이터 모델 | 14 |
| `cloud-native` | 클라우드 네이티브 서비스 운영 — 서비스 · API · 이벤트 · 서비스수준 · 런북 · 장애 | 13 |
| `ai-service` | AI · LLM 서비스 — 모델 · 프롬프트 · 평가셋 | 12 |

**팀 서식** — 팀이 만든 서식은 서버의 `<data>/forms/<묶음>/` 에 둔다(관리자가 둔다 · 갱신이 덮지 않는다 · 같은 id 면 팀 서식이 이긴다).
**문제가 있는 서식**(머리 필드 · 덩어리 셋 · `kind` · `registry` 모양)으로는 서버가 문서를 세우지 않는다 — 서식집 목록 · `ctx forms check` 가
그 문제를 말한다. 서식은 **서식이지 내용이 아니다** — 남의 프로젝트 값이 따라 들어오지 않는다.

서버 산출물의 `bin/ctx.mjs` 가 있으면 셸에서도 본다 — `ctx forms list` · `ctx forms show <묶음/번호>`(찍힐 빈 문서까지) · `ctx forms check`
(`--data <서버 데이터 폴더>` 면 팀 서식까지).

### 7.2 서식 하나의 모양

```markdown
---
form: public-si/DE_431
title: 테이블정의서               # 새 문서의 제목
number: DE_431                   # 관리번호
due: 설계완료                     # 제출시기
required: false
kind: 대상                        # 대상 · 대장 · 정의 · 사건 · 서술
registry:                        # 패턴 제안 — 패턴이 여럿인 서식도 있다
  - { pattern: "테이블정의서:*", anchor: "## {값}" }
coordValue: 테이블 물리명(소문자)
---
<!-- form:head -->      새 문서로 가는 것 — 첫 문단(대장이면 빈 표 머리)
<!-- form:guide -->     큐레이터가 읽는 것
<!-- form:example -->   큐레이터가 읽는 것
```

### 7.3 세우는 길

1. **찾는다** — `forms({ repo, q: "<말>" })`. 판정 재료의 「비슷한 서식」 · `unregisteredTypes` 가 좋은 말이다. `used: true`(화면의 「씀」)면
   이 레포에 그 서식의 문서가 이미 있다 — 새로 세우지 말고 거기 붙인다.
2. **읽는다** — `forms({ repo, form: "<id>" })` 의 `guide` — 「여기 적지 않는 것」 이 정본 자리를 정한다. `coordValue` 가 좌표의 값이 무엇인지 말한다.
3. **고른다** — 이름이 같은 서식이 묶음마다 있으면(`시스템아키텍처` 넷 · `인터페이스` 셋) 묶음을 보고 고른다. **맞는 서식이 없으면 서식
   없이** 세운다(`title` 만 — `# 제목` 한 줄). 억지로 비슷한 서식을 고르지 않는다.
4. **보낸다** — 같은 save 에 셋이 같이 간다.

```
managed:  [{ pattern: "인터페이스:*", doc: "docs/인터페이스정의서.md", form: "public-si/DE_501" }]
sections: [{ coord: "인터페이스:ERP-결의서전송", applied: null, heading: "ERP-결의서전송 — ERP 결의서 전송", body: "…" }]
work.curates: [{ id: "…", verdict: "new", into: ["인터페이스:ERP-결의서전송"] }]
```

서버는 `# <제목>` · 서식 표지 `<!-- cdp:form public-si/DE_501 -->` · `form:head` 첫 문단**만** 찍는다 — 예시 · 작성지침 · 관리번호 표 ·
`applied: null` 은 문서로 가지 않는다. 깨끗한 빈 문서에 이번 섹션이 들어간다.

- **패턴의 타입은 기록이 쓴 좌표의 타입이다** — 서식의 `registry` 는 제안이다.
- 문서 경로는 그 레포의 폴더 규약을 따른다(`docs/2.설계/…` 면 그 아래). `docs/` 밖 · `..` · 절대경로는 거절된다.
- 행 · 문서의 나머지 규칙(덮인 패턴 · 같은 패턴 · 걸리는 기존 좌표 · 어긋나는 문구)은 §8.2.

## 8. 등록부 · 문서 구조 — `cdp-registry`

기록을 섹션에 반영하는 것은 `cdp-curate`, **구조**를 바꾸는 것은 `cdp-registry` 다 — 「용어집 문서를 세워 줘」 · 「이 문서 이름 바꿔」 ·
「안 쓰는 관리 문서 지워」.

### 8.1 기록 하나가 사유다

구조만 바꾸는 save 도 작업 기록 하나와 같이 간다. 행은 사라지기도 하므로 **사유는 기록 본문에만 남는다.**

| `work.` | |
|---|---|
| `touches` · `touchesEmpty` | `[]` 와 사유 — 「등록부 정리만 했다」 · 「관리 문서 정리」 · 「서식 예시 정리」 |
| `tags` | `["registry"]` · 지우기는 `["docs-prune"]` — **이 태그가 있어야 대기열에 서지 않는다** |
| `body` | 왜 · 무엇이 어디로 갔나 · 영향받은 좌표 수 |

새 문서를 세우며 기록을 반영하는 save 라면 이 기록 대신 큐레이션 기록이 그 자리다. 승인 게이트(dryRun → 【등록부 변경】 → 승인)는 §5 와 같다.

### 8.2 행 더하기 — `managed: [{ pattern, doc, form?, title?, level? }]`

- **먼저 있는지 본다** — 같은 것을 받는 타입 · 문서가 이름만 다르게 있으면 만들지 않는다. 이름만 다른 중복이 이 기능의 첫 부작용이다.
- **패턴은 타입 하나에 `type:*`** 가 기본이다. 좁히는 것(`type:P*`)은 한 번에 걸리는 섹션이 50 을 넘어 나눠 붙일 때.
- **새 행이 걸리는 좌표는 섹션을 같이 보낸다** — 그 좌표를 이미 `touches` 한 기록이 있으면 서버가 `E_INPUT { needSections }` 로 거절한다.
  그 섹션을 쓰는 것은 기록을 반영하는 일이다 — `cdp-curate` 로 판정하며 한 save 에.
- **덮인 패턴 · 같은 패턴** — 앞 행에 완전히 덮이는 패턴은 거절된다(`detail.shadowedBy`). 같은 패턴이 다른 문서에 있으면 `E_CONFLICT`
  `detail.kind: managed` — 그 문서에 붙이거나 다른 패턴을 고른다.
- **어긋나는 문구** — 행을 더하면 그 문서 머리말의 「비대상」, `_vocab.md` · `_managed.md` 의 「<타입> 타입이 없다」 같은 줄이 거짓이 된다.
  서버가 남은 줄을 `E_INPUT { lines: ["파일:행"] }` 로 막는다 — 같은 save 의 `edits` 로 고치거나, 맞는 줄이면 `managed[].reviewed`.
- 새 행은 **등록부 맨 끝**에 붙는다(먼저 걸리는 행이 이기므로 기존 좌표의 자리가 안 바뀐다). 한 문서에는 한 레벨. 한 save 에 10건까지.

### 8.3 이름 · 합치기 · 폐기

| 하려는 것 | `managed` | 서버가 하는 것 | 안 하는 것 |
|---|---|---|---|
| 문서 이름 · 위치를 바꾼다 | `{ op: "rename", doc, to }` | 파일을 옮기고 그 문서를 가리키는 **모든 행**의 경로를 바꾼다 | 다른 문서 안의 링크(경고 — `edits` 로) |
| 문서 둘을 하나로 | `{ op: "merge", doc, into }` | `doc` 의 섹션을 `into` 끝에 잇고 행을 돌리고 `doc` 을 지운다 | 내용 병합 · 요약. 같은 이름의 섹션이 양쪽에 있으면 **전부 되돌린다** |
| 행을 폐기한다 | `{ op: "retire", pattern }` | 그 행을 지운다 | 문서 파일은 남긴다(등록부에 안 걸린 문서로) |

**`retire` 는 검사를 끄는 수단이 아니다** — 그 타입의 섹션이 정말 더 안 쓰일 때만.

### 8.4 안 쓰는 문서 지우기 — 화면 「레포 관리 › 관리 문서」

| | 행 | 파일 | 내용 | 언제 |
|---|---|---|---|---|
| `retire` | 지운다 | 남긴다 | 남는다 | 좌표 판정만 끄고 문서는 읽을거리로 |
| `merge` | `into` 로 | 지운다 | `into` 로 | 두 문서를 하나로 |
| **`drop`** | 지운다 | **지운다** | git 이력에만 | 이 프로젝트에 **필요 없는** 문서 |

화면에서 — 거름(전부 · **서식 그대로** · 쓰는 중 · 필수)으로 후보를 보고 고른다 → **미리보기**(서버의 dryRun — 지울 행 · 예시 좌표 ·
그 문서를 가리키는 다른 줄) → 줄마다 「행 지우기 · 링크만 풀기 · 알고 둔다」 → 사유 → 지우기. 한 커밋이고 `_managed.md` 의
「지운 관리 문서」 표에 남는다. 묶음(`TE_201` · `TE_202` · `TE_203`)째 지우면 서로의 참조는 고칠 목록에서 빠진다.
산문을 고쳐 써야 하는 줄은 에이전트(`cdp-registry` 의 drop)가 낫다.

- **거절되면 안 쓰는 문서가 아니다** — 기록이 반영된 섹션이나 `touches` 이력이 있으면 서버가 거절한다. 내용을 남기려면 `merge`, 좌표
  판정만 끄려면 `retire`.
- 필수 제출 문서는 경고가 온다 — 계약상 필요 없는지 묻는다.

### 8.5 서식 예시 정리 — 옛 레포

옛 패키지로 세운 레포에는 `example:` 이 붙은 어휘와 짝 섹션 · 「(예시)」 섹션이 남아 있다(검사의 `example-coord` 경고).
`save({ repo, work, examples: "purge" })` 한 번이 어휘 줄과 짝 섹션을 같이 지운다. 기록이 이미 쓴 예시 좌표는 지우지 않는다(표시만 뗀다).
`ctx migrate` 로 옮긴 레포는 이미 지워져 있다.

### 8.6 섹션 밖 글 — `edits: [{ file, old, new }]`

좌표 섹션 **밖** — 문서 머리말(첫 `##` 앞) · 등록부 밖 문서(회의록 · 가이드)의 본문 · `_vocab.md` · `_managed.md` 의 산문.

- `docs({ repo, doc })` 로 원문을 읽고 **지금 글 그대로**를 `old` 에, 바꿀 글을 `new` 에 — `old` 가 정확히 한 번 나와야 한다.
  그 사이 누가 바꿨으면 `E_CONFLICT`(다시 읽는다). 지우려면 `new: ""`. 한 save 에 20건까지.
- **못 건드리는 자리** — 좌표 섹션(→ `sections`) · `applied` 주석 · 어휘 줄(→ `vocab`) · 등록부 행(→ `managed`). 서버가 그 줄과 갈 곳을 말해 준다.

### 8.7 어휘

큐레이터의 save 로 어휘는 **더하기만** 된다 — 새 좌표 줄(`vocab: [{ coord, label, aliases }]`) · 새 타입 절. **있는 좌표에 alias 를 더하거나
폐기(`deprecated`) 표시를 하는 연산은 없다** — 서버 관리자에게 청한다(서버 관리자 설명서 7.4). alias 는 맥락 주입의 단일 실패점이다 —
새 좌표를 세울 때 aliases 를 넉넉히 넣는다(그 대상을 **부르는 말** — 줄임말 · 화면의 말 · 요구사항서의 말. 속성은 넣지 않는다).

## 9. 기준선

### 9.1 무엇인가

섹션 안의 **추출 블록** — 코드 · DB · 매뉴얼에서 **기계로** 뽑은 사실(컬럼 표 · 프로그램 목록 · 코드값)이다.

```
<!-- cdp:baseline src="운영 DB 프로그램 목록" asof="2026-10-02" -->
| 컬럼 | 타입 | … |
<!-- /cdp:baseline -->
```

| | |
|---|---|
| 누가 쓰나 | **기준선 save 만** — 큐레이터 토큰을 가진 생성기(프로젝트의 스크립트) 또는 `ctx baseline push`. 블록을 **통째로 갈아 끼운다**(멱등) |
| 누가 못 쓰나 | 큐레이션 save 는 블록 안을 못 고친다(거절). 큐레이터의 서술은 블록 밖에 |
| 대기열 · 미반영 | 기준선 기록은 대기열에 안 서고 **미반영을 만들지 않는다** — 300개 섹션을 매번 큐레이터에게 보내지 않는다. 블록의 `asof` 가 그 신선도다 |
| 섞지 않는다 | 한 save 에 기준선과 큐레이션을 섞지 않는다 — 기계의 자리와 사람의 판단은 따로 남긴다 |

왜 — 추출을 작업 기록인 척하는 일이 없어지고(작은 기록 하나가 수십 KB 의 섹션을 만들던 일), 큐레이터가 수백 섹션의 컬럼 표를 손으로
옮기지 않는다.

### 9.2 올리는 법 — JSON 하나

```json
{
  "source": "개발 DB pg_catalog",
  "asof": "2026-10-04",
  "managed": [{ "pattern": "테이블정의서:*", "doc": "docs/테이블정의서.md", "form": "public-si/DE_431" }],
  "vocab": [{ "coord": "테이블정의서:bk_member_mst", "label": "회원마스터" }],
  "items": [{ "coord": "테이블정의서:bk_member_mst", "heading": "bk_member_mst — 회원마스터", "body": "| 컬럼 | 타입 | … |" }]
}
```

`managed` · `vocab` 은 처음 세울 때만(행 · 서식 문서 · 좌표를 같은 커밋에). 올리는 길은 둘이다 — 큐레이터 토큰(`CDP_TOKEN`)으로.

```bash
# 서버 산출물의 bin/ctx.mjs 가 있으면 (Node 20)
node ctx.mjs baseline push 기준선.json --server http://<서버>:7374 --repo <레포>
# 없으면 같은 것을 curl 로
curl -sS -X POST -H "Authorization: Bearer $CDP_TOKEN" -H "content-type: application/json" \
     --data-binary @기준선.json "http://<서버>:7374/api/<레포>/baseline"
```

한 커밋이다 — 서버가 기준선 기록(`tags: [baseline]` · `baseline: { source, asof }`)을 지어 같은 `save` 를 탄다. 생성기는 **프로젝트의 것**이다
(도메인 · DB 가 프로젝트마다 다르다) — 야간 크론이나 손으로 돌린다. 제품은 블록 형식 · 입력 JSON · 올리는 길만 준다.

### 9.3 옛 레포의 섹션을 기준선으로 — `ctx baseline extract`

다시 세운 레포(§11.1)의 출발점으로, 옛 레포의 대상형 문서(테이블정의서 같은 것)의 섹션을 기준선 JSON 으로 뽑는다.

```bash
node ctx.mjs baseline extract <옛 레포 clone> --doc docs/2.개발/DE_431_테이블정의서.md [--src "…"] [--asof YYYY-MM-DD] [--form <묶음/번호>] [--to docs/…md] > 기준선.json
```

서식을 안 주면 관리번호(`DE_431`)로 서식집에서 찾는다. 결과를 읽어 보고 `push` 한다 — 옛 섹션의 사람 글까지 블록에 들어가므로,
블록으로 둘 것(기계로 뽑을 수 있는 사실)만 남기는지 본다.

## 10. 충돌 · 거절

| 응답 | 할 일 |
|---|---|
| `E_CONFLICT` (섹션) | 읽은 뒤 누가 그 섹션을 바꿨다 — `detail.current`(지금 applied) · `detail.currentWork`(그 기록 — 제목 · 작성자 · 날짜) · `detail.currentCuration`(그 기록을 반영해 섹션을 고친 큐레이션 기록 — 있을 때) · `detail.content`(지금 본문). **`content` 위에 다시 만들고 `applied` 에 `current` 를 넣어** dryRun 부터 다시. 옛 본문을 그대로 다시 보내면 그 사람의 반영이 사라진다. `truncated` 일 때만 `section` 을 다시 읽는다. 다른 큐레이터였으면 내 묶음의 기록이 이미 판정됐는지 `work({ id })` 의 큐레이션 상태로 본다 |
| `E_CONFLICT` (`edits`) | `old` 가 원문에 없다 — 읽은 뒤 바뀌었다. `docs` 로 다시 읽는다 |
| `E_CONFLICT` · `detail.kind: managed` | 같은 패턴이 다른 문서에 이미 있다 — §8.2 |
| `E_INPUT` 「into … 가 이 save 의 sections 에 없다」 | 반영한 섹션을 같이 보낸다(바뀐 게 없으면 `content` 그대로 + 경과) · 반영하지 않을 기록이면 `keep` |
| `E_INPUT` 「헤딩 줄이 있다」 · 「기준선 블록 표지가 있다」 | `body` 에 `##` 헤딩이나 블록을 넣었다 — `content` 를 고쳐 보낸다 |
| `E_INPUT` `needSections` · `lines` · `shadowedBy` | 등록부 행의 일 — §8.2 |
| `E_INPUT` 「큐레이션 · 기준선 · 옛 기계 기록이다」 | `curates` 에는 사람의 작업 기록만 넣는다 |
| `E_EXISTS` | 큐레이션 기록 id 가 있다 — 다른 id |
| `E_CHECK` | **이 save 가 만든** 오류다(같은 이름의 섹션이 둘 · 미등재 좌표 등) — `detail.findings` 를 고쳐 다시. 레포에 원래 있던 오류는 막지 않고 경고로 온다 — 그 오류를 푸는 것도 큐레이터의 일이다 |
| `E_FORBIDDEN` · `need: curate` | 이 레포의 큐레이터가 아니다 — 멈춘다 |
| `E_GIT` · `reason: dirty` | 서버 트리 문제 — 서버 관리자에게 「트리 되돌리기」. 보낼 것은 그대로다 |

`section` → 쓰기 → `save` 사이가 짧을수록 충돌이 적다 — 묶음 하나씩 읽고 바로 보낸다. **섹션 점유는 없다** — 큐레이터가 여럿이면
레포 안에서 문서나 주제로 나눠 맡는다.

## 11. 옛 레포를 넘겨받았을 때

v0.x 레포는 두 길로 v1.0 에 온다 — 어느 쪽인지는 서버 관리자가 정했다(서버 관리자 설명서 9장).

### 11.1 다시 세운 레포 — 기록만 옮겨 왔다

관리 문서가 엉망인 레포는 **빈 레포에 작업 기록만 옮겨** 다시 세운다. 관리 문서 · 등록부 행 · 옛 파생 정리 기록은 오지 않았다 —
어휘는 옮긴 기록이 쓰는 좌표만 왔다. **옮긴 기록은 전부 대기열에 서 있다.**

1. 대기열을 주제로 묶는다 — 화면의 칩(섹션 없음 · 등록부 없음)과 날짜를 보고. 예 — 「연계 · 베이스 데이터 · 시스템관리 화면 · 회의 · 사업분석」.
2. 묶음마다 **서식집에서 문서를 골라 깨끗한 빈 문서로 세우고**(§7) 반영한다. 첫 큐레이션이 레포의 모양을 정한다 — 인터페이스는 좌표로 ·
   이슈는 결론 한 줄 · 용어집은 뜻만.
3. 옛 레포의 기계적 사실(테이블 · 프로그램 목록)은 `ctx baseline extract` → `push` 로 블록째 옮길 수 있다(§9.3).
4. 옛 레포는 이름을 바꿔(`<레포>_old`) 읽기로 남아 있다 — 옛 섹션을 참고로 읽되, 정본은 새 레포에 다시 쓴다.

대기열이 0 이 될 때까지 미반영이 섹션 · 도구에 실리므로, 다시 세운 직후에도 읽는 사람이 기록을 잃지 않는다.

### 11.2 제자리로 옮긴 레포 — `ctx migrate`

관리 문서를 그대로 쓰는 레포는 **전환 기록** 하나로 옮겨 왔다 — 지금 섹션이 최신이던 좌표만 건드린 기록은 「반영됨」, 실을 섹션이 없던
기록은 「기록으로 둠」, **옛 판에서 섹션이 뒤처져 있던 좌표의 기록만 대기열에 남았다.** 서식 예시도 지워졌다.

- 남은 대기부터 다룬다. 옛 섹션에는 `**변경** · 날짜 [기록]` 줄이 남아 있을 수 있다 — 그 섹션을 다시 쓸 때 `**경과**` 목록으로 바꾼다.
- 옛 문서 머리의 관리번호 표 · `## 작성지침` 섹션은 서식 잔재다 — 정리할 때 `edits` 로 걷는다.
- 일지형 섹션(날짜별로 덧붙인 것)은 현재형으로 다시 쓴다 — 큐레이터 폴더의 `종류별.md` 의 전후 예시.

## 12. 하지 않는 것

| | 왜 · 어디로 |
|---|---|
| **승인 없이 커밋** | 판정표 + diff 를 보이고 받는다 — 틀리게 반영한 것은 아무도 모른다 |
| **한 번에 대기열 전부** | 큰 diff 는 승인이 형식이 된다 — 묶음 하나씩 |
| **기록 고치기 · 지우기** | 기록은 불변이다 — 작성자가 정정 기록을 낸다 |
| **기준선 블록 고치기** | 생성기의 자리다 — 틀렸으면 생성기 담당에게 |
| **모를 때 「기록으로 둠」** | 미반영 표시가 사라진다 — 모르면 대기열에 남긴다 |
| **화면에서 문서 편집** | 쓰기는 save 하나다 — 화면은 재료를 보이고 지시를 복사할 뿐이다 |
| **레포 세우기 · 사람 · 권한** | admin — 서버 관리자 설명서 |

## 13. 다시 세우기 — 어긋남 진단 · `cdp-rebuild`

**대기열과 다른 일이다.** 대기열(2~5장)은 **아직 반영 안 된 기록**이다. 정본은 반영된 뒤에도 시간이 지나며 어긋난다 — 미반영이 0 이어도
생긴다. 그것을 재고(진단) · 원천을 채우고 · 묶음으로 다시 세우는 것이 리빌딩이다.

### 13.1 진단 — 화면 「큐레이션 › 진단」 · 도구 `drift`

| 신호 | 뜻 | 손보는 길 |
|---|---|---|
| **근거 없음** | 그 좌표를 건드린 기록 · 스냅샷 · 기준선이 없는 섹션 — **기록만 옮겨 다시 세우면(11장) 사라진다** | 본문이 기록을 인용하면(「인용」) 그 기록의 좌표정정 · 아니면 스냅샷 |
| **복제 n** | 같은 산문 줄이 다른 섹션 n 곳에도 — 하나만 고쳐진다 | 정본 자리를 하나로 · 나머지는 좌표로 건다 |
| **비대 n줄** | 경과 앞 본문이 40줄을 넘는다 — 경위 · 논의가 쌓였다 | 현재형으로 줄이고 경과 한 줄씩 |
| **일지형** | 날짜별로 덧붙인 줄 | 지금의 상태로 다시 쓴다 |
| **좌표 없는 기록** | 좌표 0 · 좌표정정이 없는 기록 — 정본과 만나지 않는다 | 좌표정정 기록 |

근거 가리킴(「실측은 [기록](…)」) · 값 표의 같은 행 · 레포가 일부러 반복하는 줄(`**SoT**` 가리킴처럼 섹션의 5% 넘게 나오는 줄)은 복제로
세지 않는다. 문서 화면에서는 섹션 제목 옆에 같은 신호가 점선 칩으로 보인다(큐레이터에게만) — 누르면 진단으로 간다.

### 13.2 원천 채우기 — 스냅샷

**정본 스냅샷**은 근거 없는 섹션을 **서버가 원문 그대로** 기록 하나로 뜬 것이다 — 섹션 하나에 하나 · 날짜는 그 섹션 줄의 마지막 커밋 ·
출처는 `docs/<문서>@<커밋>#<헤딩>`. 섹션은 바뀌지 않고 대기열에도 서지 않는다(이미 섹션에 있는 원문이다). 사건이 아니라 **그때의 상태**라
기록 종류가 따로다(`snapshot`).

- 화면 — 진단의 [근거 없는 섹션 스냅샷 뜨기] — 미리보기로 수를 보이고 확인받는다(문서를 거르고 있으면 그 문서만 · 200 개씩).
- 셸 — `ctx rebuild snapshot --server <주소> --repo <레포> [--doc <문서>] [--dry]`.
- 본문이 기록을 인용하는 섹션(「근거 없음 · 인용」)은 기본으로 빼다 — 그 기록에 좌표만 빠졌으니 **좌표정정**이 진짜 출처를 남긴다.

### 13.3 좌표정정 · 다시 쓰기 — `cdp-rebuild`

글을 쓰는 일이라 큐레이터 폴더의 Claude Code 가 한다. 진단에서 좌표를 고르고 [에이전트 지시 복사] → 붙인다. 순서는 늘 **원천부터**다.

1. **좌표 보완** — 좌표 없는 기록을 묶음(20건 안팎)으로 읽고 기록마다 좌표정정 초안(`<원 id>-좌표정정` · 날짜는 원 기록의 날 ·
   `supersedes` · 빠진 좌표만)을 판정표로 보인다 → 승인 → 기록 save. 원 기록은 고치지 않는다. 승인된 정정은 대기열에 선다.
2. **재유도** — 고른 좌표 묶음(복제 가족 · 비대 문서)의 원천 전부(기록 · 스냅샷 · 기준선)에서 섹션을 다시 쓰고 지금과 견준다.
   **「사라지는 사실」**(지금 섹션에 있는데 어느 원천에도 없는 문장)이 있으면 그 섹션은 다시 쓰지 않는다 — 스냅샷부터.
3. **남기기** — 재큐레이션 save(큐레이션 기록 · `tags: [rebuild]` · 본문 끝에 진단 합계). 가장 늦은 판정이 이긴다.

### 13.4 레포를 통째로 다시 세울 때

11장의 「기록만 옮겨 다시 세우기」 **전에** 옛 레포에서 13.2 를 먼저 한다 — `--records-from` 은 스냅샷도 옮기므로 정본에만 있던 지식을
잃지 않는다. 옮긴 스냅샷은 새 레포에서 대기열에 선다(새 레포에는 섹션이 없다) — 큐레이션으로 다시 반영한다.

## 부록 A. 큐레이터의 도구 · 스킬 · save 입력

**스킬** — 큐레이터 폴더의 `.claude/skills/`.

| 스킬 | 언제 |
|---|---|
| `cdp-curate` | 대기열의 기록을 관리 문서에 반영 — 「큐레이션해 줘」 · [에이전트 지시 복사] · 문서를 고치라는 지시 기록 |
| `cdp-registry` | 등록부 · 문서 구조 — 행 더하기(서식) · 이름 · 합치기 · 폐기 · 지우기 · 서식 예시 정리 · 섹션 밖 글 |
| `cdp-rebuild` | 반영된 뒤 어긋난 정본 — 진단 · 원천 채우기(스냅샷 · 좌표정정) · 묶음으로 다시 세우기(13장) |
| `cdp-work` · `cdp-save` | 지금 상태 읽기 · 큐레이터 자신의 작업 기록 |
| `cdp-push` | 이 세션이 만진 파일을 그 레포에 커밋 · push(코드용) |

**큐레이터에게만 보이는 도구** — `queue`(대기열 · `queue({ id })` 판정 재료) · `forms`(`{ q }` 서식 목록 · `{ form }` 서식 하나 — head ·
guide · example · 서버가 찍을 빈 문서) · `drift`(어긋남 진단 — 13장). 나머지 열은 사용자 설명서 부록 B.

**save 입력 — 큐레이터만** (writer 가 보내면 `E_FORBIDDEN` `need: curate`)

| 입력 | 무엇 |
|---|---|
| `work.curates` | `[{ id, verdict: reflect · new · keep, into?, reason? }]` — 큐레이션 기록 |
| `sections` | `[{ coord, applied, heading?, body }]` — 좌표 하나에 하나 · 한 save 에 50 |
| `managed` | 행 더하기 `{ pattern, doc, form? }` · `{ op: rename · merge · retire · drop }` |
| `edits` | 섹션 밖 글 `{ file, old, new }` |
| `examples` | `"purge"` — 서식 예시 정리 |
| `snapshot` | `[{ coord }]` — 정본 스냅샷(13.2) · 본문은 서버가 섹션에서 · `work` 는 봉투 · 다른 쓰기와 섞지 않는다 |
| `baseline` · `work.baseline` | 기준선 블록(보통은 `POST /api/<레포>/baseline` 으로) |
| `dryRun` | `true` — 검사까지 돌고 커밋하지 않는다(승인용) |
| `vocab` · `assets` | writer 와 같다 — 어휘 더하기 · 첨부 |

예약 태그 `curate` · `baseline` · `transition` · `registry` · `docs-prune` · `derive` 도 큐레이터의 것이다.
